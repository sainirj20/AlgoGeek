SYSTEM DESIGN

Optimizely — Designing an A/B Testing System

A complete, interview-ready design walkthrough for an Optimizely-style experimentation platform: requirements, capacity estimation, SDK/event API design, data model, the datafile-driven architecture, deterministic hash-bucketing, mutual exclusion via layers/namespaces, the event-collection and metrics pipeline, the sequential-testing statistical engine and guardrail metrics, sharding, fault tolerance, security, multi-region scaling, and follow-up interview questions.

Problem Statement

Design an experimentation (A/B testing) platform, in the style of Optimizely, that lets many independent product teams run hundreds of concurrent experiments across web, mobile, and server surfaces. The platform must deterministically and consistently bucket each user into a variation of every experiment they're eligible for — the same user must always see the same variation, on every surface, on every subsequent visit — while adding effectively zero latency to the page render or API response the bucketing decision is attached to. Once bucketed, the platform must reliably capture exposure events ("user X saw variation Y of experiment Z") and conversion/metric events (clicks, purchases, custom events), and report statistically valid, near-real-time results — including whether it's safe to call a winner yet — back to the teams running each experiment.

Why does this problem matter in an interview?

It looks like a small feature ("randomly show half of users a blue button") but is actually a deep systems problem once you scale it: hundreds of experiments must run simultaneously without interfering with each other, bucketing must be computed with no database lookup and no added latency, and the statistics have to survive people looking at results every day without the classic false-positive inflation that comes from that. A strong candidate treats determinism and statelessness of bucketing as the load-bearing requirement — everything else (targeting, layers, the event pipeline, the stats engine) is designed around the fact that assignment must be computable identically, anywhere, from nothing but a user id and an experiment id.

Why build one shared platform instead of every team hard-coding a coin flip?

  • One place to guarantee bucketing consistency — without it, a user could see the control on web and the treatment on mobile, silently corrupting every experiment's results.
  • One place to prevent experiments from colliding with each other (the mutual-exclusion / layers problem) so hundreds can run at once without interaction effects nobody notices until the data is already unusable.
  • One place to build (and get right, once) the statistical engine — sequential testing, guardrail metrics, sample-ratio-mismatch detection — instead of every team reinventing ad hoc, often statistically invalid, significance checks.
  • One place to enforce targeting, staged rollouts, and kill-switches consistently, and to make the event pipeline durable and idempotent so no team loses exposure or conversion data under load.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope before drawing boxes.

  1. Which surfaces need bucketing at launch — server-side only, or also client-side web and native mobile SDKs, including offline mobile scenarios?
  2. Do we need mutual exclusion between experiments (layers/namespaces), or can experiments freely overlap for this version?
  3. Is a stable, pre-existing user id always available, or do we also need to bucket anonymous/logged-out visitors by a device or cookie id, and reconcile identities after login?
  4. Do we need staged/progressive traffic-allocation rollouts (1% → 100%) and a kill switch, or is traffic allocation fixed for the life of an experiment?
  5. What statistical approach does the org expect — classic fixed-horizon significance testing, or an "always valid," peek-anytime sequential-testing approach?
  6. Do we need automatically tracked guardrail metrics (page-load time, error rate, revenue), or only the single primary metric a team explicitly configures?
  7. What's the acceptable staleness for the datafile SDKs use to bucket — seconds, or is a few minutes of propagation delay acceptable after a config change?
  8. Do we need multi-armed-bandit style dynamic traffic allocation as an alternative to fixed-split A/B testing, or is that out of scope?
  9. Is this single-tenant (one company's experiments) or multi-tenant SaaS serving many independent projects/teams with isolated configs and permissions?
  10. Single region to start, or do we need to anticipate global, multi-region traffic from day one?
Interview tip
Don't wait for every answer before drawing anything — state a reasonable assumption out loud ("I'll assume we need both client-side and server-side SDKs and mutual exclusion via layers, since those are the two properties that make this problem interesting rather than a coin flip") and keep moving. Interviewers want to see you make and defend judgment calls.

Requirements and Goals

Functional Requirements

  1. Let a team define an experiment: one or more variations (a control plus treatments), each with a traffic-allocation percentage, plus audience-attribute targeting rules that determine eligibility.
  2. Deterministically bucket a given user/device id into the same variation of a given experiment, every time, on every surface (web, mobile, server), with no database lookup on the hot path.
  3. Support mutual exclusion: group experiments into layers/namespaces so a user can be bucketed into at most one experiment per layer, enabling hundreds of concurrent, non-interacting experiments.
  4. Support staged/progressive traffic-allocation rollouts (e.g. 1% → 5% → 25% → 100%) and an immediate kill switch that pauses an experiment without redeploying any application code.
  5. Distribute experiment/targeting configuration ("the datafile") to SDKs at the edge, client, and server so bucketing happens locally, with zero added request latency.
  6. Capture exposure events ("user X was bucketed into variation Y of experiment Z") and conversion/metric events (clicks, purchases, custom events), deduplicated and tolerant of out-of-order/late arrival.
  7. Compute per-variation metric aggregates and statistical significance in near real time, using a methodology that stays valid even when users check results repeatedly (sequential testing).
  8. Automatically track guardrail metrics (e.g. page-load time, error rate, revenue) alongside each experiment's primary metric, and alert on regressions.
  9. Support per-project/per-team access control over experiment configuration, and maintain an audit trail of changes to a live experiment (e.g. who changed traffic allocation, and when).
  10. Be multi-tenant: isolate configuration, permissions, and results per project/team on a shared deployment.

Non-Functional Requirements

  1. Zero added latency for bucketing: evaluating "which variation does this user see" must never add a network round trip to a page render or API call — this is the entire reason for the local, datafile-driven SDK architecture.
  2. Strong determinism: the same (user id, experiment id) pair must always resolve to the same variation, computed identically regardless of which SDK, region, or surface performs the computation.
  3. High throughput at both ends: hundreds of millions of local bucketing evaluations per day (effectively free, in-memory), and hundreds of millions of exposure/conversion events per day (the real infrastructure cost).
  4. Statistical validity under repeated peeking: a team must be able to check a running experiment's results at any time without inflating the platform's advertised false-positive rate.
  5. Availability over strict freshness for the datafile: an SDK that can't reach the config/CDN tier must keep bucketing correctly from its last-known-good cached copy rather than fail open/closed.
  6. Durability for events: an exposure or conversion event must never be silently lost, even if the stats-computation pipeline lags or crashes — the raw event log is the source of truth and must be replayable.
  7. Horizontal scalability of the event-ingestion pipeline and the per-experiment results-computation jobs, independently, since experiment size and traffic vary enormously.

Extended / Out-of-Scope

We'll go deep on the datafile/SDK bucketing architecture, deterministic hashing, layers/namespaces, the event pipeline, and the statistical engine. We call out but don't build the internals of a full visual-editor/WYSIWYG experiment-authoring UI, a general feature-flag management console, or an ML-driven personalization/recommendation engine — real, adjacent products, but layered on top of this core experimentation substrate.

System / API Design

The design has two very different API surfaces: an SDK-facing bucketing call that must never touch the network, and an event-tracking call that does — deliberately taking the network cost only after the user has already been shown their variation.

SDK-Facing Bucketing API (No Network Call)

The SDK method that answers "which variation does this user see" runs entirely against the locally cached datafile — it is a pure function of (datafile revision, experiment key, user id, attributes), with no I/O.

// Runs entirely client-side / server-side against the cached datafile.
// No network call, no database lookup — pure in-memory computation.

variation_key = client.get_variation(
    experiment_key: "checkout_button_color",
    user_id: "user_12345",
    attributes: { "plan": "premium", "country": "US", "device": "ios" }
)
// Returns e.g. "variation_blue", "control", or null if the user
// doesn't match the audience targeting rules / isn't in the
// experiment's traffic allocation.

// A "decide" style call additionally returns the reason and
// automatically queues the exposure event:
decision = client.decide(
    flag_key: "checkout_button_color",
    user_id: "user_12345",
    attributes: { "plan": "premium", "country": "US" }
)
// decision.variation_key, decision.rule_key, decision.enabled,
// decision.reasons (e.g. "TARGETING_MATCH", "TRAFFIC_ALLOCATION")

Exposure and Conversion Event-Tracking API

Once the application has rendered the assigned variation, the SDK asynchronously flushes exposure and conversion events in small batches to the ingestion tier — this is the one place the design does pay a network cost, and it's off the critical path of the response the user is waiting on.

Interview tip
Call out explicitly that the bucketing call and the tracking call are architecturally decoupled on purpose: bucketing must be synchronous and free (it gates the render), while tracking must be asynchronous, batched, and retryable (it feeds the stats engine, not the user). Conflating the two — e.g. making get_variation itself call the network to log the exposure — is the single most common design mistake candidates make here.

Data Model and Database Schema

Nature of the Data

  • A small, low-write-volume config plane (experiments, variations, audiences, layers) that is read constantly but changes rarely — a great fit for an in-memory/cacheable store with strong versioning.
  • A huge, high-write-volume event plane (exposures, conversions) with no joins on the hot write path — a textbook wide-column / append-only log workload.
  • Configuration and events are joined only downstream, by the stats engine, never synchronously.

Config Store vs. Event Store — Why Two Different Systems

The config plane (experiments, variations, audiences, layers) is small, read-dominant, and needs strong consistency on publish — a relational or strongly-consistent document store, fully cached in memory by the Config/Rules Service and compiled into the datafile, is the right fit. The event plane (exposures, conversions) is enormous, write-dominant, append-only, and needs horizontal scalability far more than it needs joins or strong consistency at write time — a wide-column or log-structured store (Cassandra-style, or a streaming platform's own durable log) is the right fit there instead. Trying to force both into one database either cripples the event plane's write throughput or gives the config plane far more consistency machinery than it needs.

High-Level Design

A Config & Rules Service is where teams define experiments, variations, audience-targeting rules, and layer/namespace assignments. Every published change is compiled into a versioned, immutable "datafile" — a compact JSON snapshot of every active experiment's rules. The datafile is pushed to a CDN / edge distribution tier, from which Web, Mobile, and Server SDKs fetch and cache it. Application code calls into the SDK, which evaluates targeting and bucketing entirely locally against the cached datafile and returns a variation synchronously, with no network round trip. The SDK then asynchronously batches exposure and conversion events into an Event Ingestion Pipeline, which feeds a Stats Engine that computes per-variation metric aggregates using sequential-testing methodology, surfaced on a Results Dashboard.

Figure 1. High-level architecture — a Config & Rules Service compiles a datafile distributed via CDN to Web/Mobile/Server SDKs, which bucket locally with zero added latency, then feed the event pipeline and Stats Engine.

Key Design Principles Reflected in the Diagram

  • Bucketing is a pure, local function: every SDK computes the same thing from the same inputs — the datafile is the only "config" it ever needs, and it never calls back to any service to bucket a user.
  • The event pipeline is decoupled from the bucketing decision: exposure/conversion tracking happens after the render, asynchronously, so a slow or briefly unavailable event pipeline never blocks or delays the user-facing response.
  • Publishing a config change is the only synchronous, centralized step — everything downstream of the datafile (CDN, SDKs, bucketing) fans out and scales independently of it.
  • The Stats Engine is the single place statistics are computed, so every team gets the same statistically valid methodology instead of ad hoc per-team significance checks.

Deep Dive — Experiment Configuration and the Targeting/Rollout Rules Engine

Audience-Attribute Targeting Rules

Each experiment references an audience: a logical AND/OR/NOT tree over user attributes supplied by the caller at bucketing time (e.g. country = "US" AND plan = "premium", or device = "ios" OR device = "android"). Targeting evaluation happens first and is purely a filter: a user who fails the audience check is never bucketed into that experiment at all, and no exposure event fires for them — they're simply outside the experiment's population, not "in the control by default."

Staged Traffic-Allocation Rollout

An experiment's traffic-allocation percentage (the share of the layer's eligible traffic that actually gets bucketed into it, as opposed to passing through untouched) is itself just a field in the datafile, so ramping an experiment from 1% → 5% → 25% → 100% is a config-only change: the Config & Rules Service publishes a new datafile revision, and every SDK picks it up on its next fetch — no application redeploy. Because bucketing is a deterministic function of (user id, experiment id), raising the allocation percentage never re-buckets a user who was already included at the lower percentage into a different variation; it only ever adds newly-eligible users at the margin. A kill switch (setting status to PAUSED) works the same way: it's a one-line config publish, propagating to every SDK within one fetch cycle.

The Datafile Push/Poll Model and Cached Last-Known-Good Fallback

SDKs get a fresh datafile in one of two ways: a poll on a fixed interval (e.g. every 60 seconds for server-side SDKs), or a push notification (e.g. a webhook or streaming update) that tells a long-lived process "a new revision is ready, fetch it now" for near-instant propagation. Either way, every SDK keeps its most recently successfully fetched datafile cached in memory (and, for mobile, on local disk) and keeps using it if a subsequent fetch fails — a CDN blip, a network partition, or a cold app start with no connectivity yet all degrade gracefully to "keep bucketing with the last known-good rules" rather than failing bucketing outright or blocking the user's request waiting for a fresh copy.

Deep Dive — Deterministic Bucketing: Hashing Users into Variations

The core trick that makes bucketing stateless is: hash a stable identifier (the user id, or a device id for anonymous visitors) together with the experiment's id — or, when the experiment belongs to a layer, the layer id, so that a user's hash used for mutual-exclusion is independent from the hash used inside the chosen experiment — through a fast, well-distributed, non-cryptographic consistent hash function such as MurmurHash. The output is reduced into a fixed bucket range, e.g. [0, 10000), via a modulo operation. The experiment's variations then simply claim contiguous sub-ranges of that space proportional to their traffic-allocation percentages: a 50/30/20 split claims buckets [0, 5000), [5000, 8000), and [8000, 10000) respectively.

Because the hash is a pure function with no external state, the same (user id, experiment id) pair always produces the same bucket value, and therefore the same variation — computed identically whether the call happens in a browser, a mobile app, or a backend service, with no lookup and no coordination between them required.

Figure 3. Deterministic hash-bucketing: hashing (user id + experiment id) with MurmurHash into a fixed bucket range, then mapping the bucket to a variation via cumulative traffic-allocation ranges — entirely stateless and reproducible anywhere.

Deep Dive — Mutual Exclusion via Layers/Namespaces

Running 200 experiments concurrently is only safe if experiments that could plausibly interact never see the same user at the same time — otherwise a checkout-flow experiment and an unrelated pricing experiment could both touch the same user's session and produce a confounded, uninterpretable result for both. The fix is to group experiments into layers (also called namespaces): a layer represents one slice of the product surface (e.g. "checkout flow," "homepage hero"), and every experiment inside a layer competes for the same, mutually-exclusive share of that layer's traffic. A user is hashed once per layer (using the layer id as part of the hash input) to decide which single experiment in that layer, if any, they fall into — never more than one. Because each layer has its own independent hash seed, the same user can simultaneously be in one experiment in Layer 1 and a completely different experiment in Layer 2, with no interaction, since the two layers represent orthogonal, non-overlapping product surfaces by construction. This is the key technique — popularized by Google's "Overlapping Experiment Infrastructure" paper — that lets a platform run hundreds of simultaneous experiments without the interaction effects that would otherwise make results unreliable.

Figure 4. Mutual exclusion via layers: experiments inside the same layer compete for one mutually-exclusive share of traffic, while independent layers hash the same user separately, letting hundreds of experiments run at once without interaction effects.

Deep Dive — Event Collection and the Metrics Pipeline

Exposure events ("user X was bucketed into variation Y of experiment Z") and conversion/metric events (clicks, purchases, custom events) both stream into the same durable ingestion pipeline, but they're joined only downstream — a conversion event carries no experiment context at all; the join happens by matching (visitor_id) against every experiment the user is known to have been exposed to, then attributing that conversion to the corresponding variation for each such experiment.

Deduplication: a page refresh, an SPA re-render, or a re-bucketing check must not count as a second exposure. Each exposure event carries a dedup_key — a hash of (visitor_id, experiment_id, day) — and the ingestion/collector tier drops (or the stats engine's aggregation query collapses) any event sharing an already-seen dedup key, so a user hammering refresh contributes exactly one exposure to the denominator, not one per refresh.

Late and out-of-order events: a mobile device can go offline and upload a batch of queued conversion events hours or days later; the stream-processing layer uses event timestamps (not ingestion timestamps) for attribution, with a bounded "allowed lateness" window (e.g. up to 72 hours) during which a late event can still be folded into the correct day's aggregate before that window's results are considered final — after which further stragglers are still recorded for audit but no longer revise a closed aggregate.

Figure 5. Event collection and the metrics pipeline — exposure events are deduplicated up front; exposure and conversion events are correlated downstream by (visitor_id, experiment_id), tolerating late-arriving events within a bounded window.

Data Partitioning and Sharding

Two different sharding strategies apply to the two different planes of this system.

  • Event-ingestion partitioning: the raw exposure/conversion topic is partitioned by hash of visitor_id, so every event for one user lands on the same partition — preserving per-user event order without any cross-partition coordination, and letting ingestion throughput scale by adding partitions and consumers.
  • Metrics-aggregation partitioning: once joined, per-variation aggregation and the results-computation job for each experiment are sharded independently, one job (or job shard) per experiment_id — a single enormous, high-traffic experiment recomputing its sequential-testing statistics never slows down or blocks the results job for any other, smaller experiment.
  • Config-store partitioning: experiments, variations, audiences, and layers are all partitioned by project_id, keeping one team's configuration changes and datafile compilation independent of every other team's.

Replication and Fault Tolerance

  • Datafile caching at the SDK is the platform's primary fault-tolerance mechanism on the read path: every SDK holds the last successfully fetched datafile in memory (and on-disk for mobile), so a Config & Rules Service outage, a CDN blip, or a backend-unreachable mobile device all degrade to "keep bucketing correctly from slightly stale rules" rather than failing bucketing or blocking the request.
  • A durable, replicated event log (the ingestion pipeline, RF=3) is the fault-tolerance mechanism on the write path: exposure and conversion events are committed durably the moment they're ingested, independent of whether the Stats Engine is healthy. If the Stats Engine lags or crashes entirely, it can replay from the durable log from wherever its consumer offset last committed — no event is silently lost, only delayed.
  • Config Store replication (e.g. multi-AZ, quorum writes) protects the source of truth for experiment definitions; because the compiled datafile is a point-in-time-immutable artifact, a Config Store outage doesn't affect already-published datafiles already cached everywhere — it only blocks new publishes until it recovers.
  • Idempotent replay: because the stream join keys strictly off (visitor_id, experiment_id) and dedup_key, replaying a segment of the event log after a crash recomputes the same aggregates rather than double-counting — recovery is safe by construction, not by a special reconciliation step.

Feature-Specific Logic

Statistical Engine — Sequential Testing and Guardrail Metrics

This is the part of the system that turns raw per-variation counts into a trustworthy "is treatment better than control, and by how much" answer — and it's the part most likely to be silently wrong if built naively.

Fixed-Horizon Testing and the Peeking Problem

Classic A/B testing computes a p-value under the assumption that the sample size was fixed in advance and the test is checked exactly once, at the end. If a team instead watches the dashboard every day and stops the moment p < 0.05 happens to appear, they are effectively running many implicit tests — and the true false-positive rate of "stop whenever it first looks significant" is much higher than the advertised 5%. This is the well-known "peeking problem," and it's the single most common way naive in-house A/B testing tools silently produce false wins.

Always-Valid Sequential Testing

Optimizely-style platforms instead use sequential-testing methods derived from confidence sequences — sometimes called "always-valid p-values" — that are constructed so that the false-positive-rate guarantee holds no matter how many times, or when, a team looks at the result. Practically, this means a running experiment's dashboard can be checked at any time, and stopping the moment it flags significance is statistically safe, unlike a peeked fixed-horizon test. The trade-off is that a sequential test is typically somewhat more conservative early on (it needs a bit more data to reach the same confidence than a fixed-horizon test checked at exactly the right, pre-committed moment) — but that conservatism is the price of the "check anytime" guarantee, and it's a trade most product teams gladly take.

Guardrail Metrics

Alongside the primary metric a team explicitly configures, the platform automatically tracks a standard set of guardrail metrics for every experiment — page-load time, client error rate, and revenue are typical defaults. A treatment can win decisively on its primary metric (say, click-through rate) while quietly regressing page-load time or triggering more client errors; guardrails surface that regression even when nobody thought to look for it, and a strong platform alerts on a guardrail breach automatically rather than waiting for someone to notice a support ticket spike.

Multi-Armed Bandits as an Alternative

Multi-armed bandit allocation is a genuinely different approach worth contrasting: instead of a fixed traffic split held constant for the life of the experiment, a bandit dynamically shifts more traffic toward whichever variation is currently performing best, trading statistical rigor (a clean, symmetric comparison you can compute a confidence interval on) for faster exploitation of the apparent winner. Bandits fit well when the goal is pure short-term optimization (e.g. picking a headline for a one-day promotion) and poorly when the goal is a durable, generalizable causal answer about which variation is actually better — which is why most experimentation platforms, including Optimizely, offer bandit-style allocation as an option alongside, not a replacement for, classic fixed-split A/B testing.

Security, Privacy and Permissions

  • Per-project/per-team access control: every experiment, audience, and layer is scoped to a project, and role-based permissions (viewer / editor / admin) gate who can create, modify traffic allocation on, or conclude a live experiment.
  • PII handling in event payloads: exposure and conversion events carry a visitor id (often a pseudonymous cookie/device id rather than a raw account identifier) and caller-supplied attributes; raw PII (email, name, address) should never be placed directly into event attributes — attributes are meant for targeting-relevant, non-identifying dimensions (plan tier, country, device type), and the platform should validate/reject attribute keys that look like raw PII.
  • Audit trail on live-experiment changes: every mutation to a running experiment's traffic allocation, audience rules, or status is recorded with who made the change and when — this matters statistically, not just for compliance: an unrecorded mid-flight traffic-allocation change can silently bias a naive analysis that assumes a constant allocation for the whole experiment window.
  • Datafile and event-ingestion authentication: SDK keys are scoped per project/environment; the CDN serves datafiles over TLS; the event-ingestion endpoint authenticates the calling SDK/account before accepting a batch.

Load Balancing

  1. Datafile distribution: a CDN with edge points-of-presence serves the datafile close to every SDK, with cache invalidation triggered on publish — this is the dominant load-balancing concern for the read-heavy config plane, and it's solved by "put it on a CDN," not by scaling an origin service.
  2. Event-ingestion load balancing: a standard L7 load balancer in front of an autoscaled collector fleet absorbs the exposure/conversion event volume, which is bursty (a flash-sale experiment can spike ingestion sharply) but tolerant of a little added latency, unlike the bucketing path.
  3. Results-computation job scheduling: per-experiment aggregation jobs are scheduled across a worker pool, so one enormous experiment's job doesn't starve the scheduler for every other experiment's smaller job.

Scaling to Multiple Regions

  • Regional event-ingestion points accept exposure/conversion events close to where users actually are, minimizing the network hop for the one part of the pipeline that does touch the network — feeding into a global aggregation/results pipeline that merges per-region streams before per-variation stats are computed, so results reflect the whole global population, not one region in isolation.
  • Datafile CDN edge caching already solves most of the multi-region bucketing-latency question by construction: since bucketing runs locally against a cached datafile, the only thing that needs to be "close" to the user is the occasional datafile fetch, which a CDN handles natively.
  • Config & Rules Service can remain a single, centrally-consistent source of truth (experiments are authored relatively rarely compared to being read), replicating its compiled datafile globally via the CDN rather than needing a globally-distributed writable config store.
  • Cross-region event ordering isn't required for correctness here, since the stream join keys off (visitor_id, experiment_id) with a bounded lateness window rather than strict global ordering — this relaxation is what makes multi-region ingestion tractable without a distributed-consensus layer.

Monitoring, Logging and Analytics

  • Sample-Ratio-Mismatch (SRM) detection: for a 50/50 experiment, run a continuous chi-squared (or equivalent) check comparing the observed variation split against the expected split; a statistically significant mismatch (e.g. seeing 52/48 when 50/50 was configured, at a sample size where that gap shouldn't occur by chance) is one of the single most reliable signals of a broken bucketing, targeting, or logging bug — and every healthy experimentation platform surfaces it automatically, since it silently invalidates results otherwise.
  • Event-pipeline lag monitoring: track consumer lag on the ingestion topic and end-to-end delay from event timestamp to landing in the per-variation aggregate; alert if lag grows unbounded, since that's the leading indicator of the pipeline falling behind a traffic spike.
  • Guardrail-metric regression alerting: automatically flag a guardrail (page-load time, error rate, revenue) that regresses for a treatment variation, even when the primary metric is winning, and surface it prominently on the results dashboard rather than requiring a team to remember to check.
  • Experiment health dashboards: datafile propagation lag (time from publish to "every SDK has the new revision"), bucketing-evaluation error rates per SDK version, and exposure-to-conversion join success rates all belong on an internal operability dashboard distinct from the team-facing results dashboard.

CAP Theorem Lens

Favor availability for bucketing itself: an SDK always returns a decision from its cached datafile rather than blocking on, or failing because of, a backend call — a stale-by-a-few-minutes datafile is far better than a bucketing call that can fail or add latency. Favor durability and eventual consistency for the event pipeline: an event is never rejected or dropped to satisfy a strict ordering guarantee; it's accepted immediately into the durable log and reconciled downstream, tolerating lag rather than blocking ingestion.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as "and then what?" follow-ups on whatever you draw first.

Bucketing and Determinism

Why hash the user id instead of storing bucket assignments in a database?
A database lookup on every page view/request would add a network round trip and a scaling bottleneck to the most latency-sensitive path in the system. A deterministic hash function computes the same answer from the same inputs with zero I/O, so bucketing is effectively free and infinitely horizontally scalable — the "database" is really just the small, cached datafile every SDK already has in memory.
What hash function does Optimizely-style bucketing typically use, and why does it matter?
A fast, well-distributed, non-cryptographic hash such as MurmurHash. It matters because the hash needs to (a) spread users uniformly across the bucket range so traffic-allocation percentages are actually honored in practice, and (b) be cheap enough to compute on every request across every SDK language/runtime without becoming a CPU cost anyone notices.
How do you guarantee a user gets the same variation across web, mobile, and server surfaces?
Every SDK implements the identical hashing and bucket-range-mapping algorithm against the identical datafile revision, keyed by the same stable user id. Since it's a pure function with no external state, any SDK, on any surface, given the same inputs, always produces the same output — consistency is a property of the algorithm being deterministic, not of any cross-surface coordination.
What happens if a user is anonymous at first and then logs in — does their bucket change?
If bucketing switched from the anonymous device id to the logged-in user id, the hash input changes and the user could land in a different variation, which is a real edge case teams need to decide on explicitly. Common approaches are to keep bucketing keyed on a stable identity (e.g. always the device id, or an identity-resolution step that maps the anonymous id forward) for the life of an experiment, and to document any pre/post-login switch as a known limitation rather than silently allowing a mid-experiment reassignment.

Mutual Exclusion and Layers

Why do you need layers/namespaces at all — why not just let experiments overlap?
Two unrelated experiments touching the same user simultaneously risk interaction effects — e.g. a pricing test and a checkout-flow test both changing behavior for the same session can confound each other's results in ways that are hard or impossible to disentangle afterward. Layers make mutual exclusion structural: a user can be in at most one experiment per layer, so only genuinely orthogonal product surfaces can run experiments on the same user at the same time.
How does the "Overlapping Experiment Infrastructure" idea let you run hundreds of experiments at once?
By organizing experiments into many independent, mutually-exclusive layers rather than one global pool. Each layer only needs to avoid collisions with the small number of experiments inside it; different layers are independent of each other by design, so the total number of concurrently-safe experiments scales with the number of layers, not with some fixed global cap.
What happens if two experiments in different layers both change the same button?
That's a layering mistake, not a bucketing one — the layers should be defined around actual product surfaces so that experiments touching the same UI element live in the same layer and are therefore mutually exclusive. If it does happen, sample-ratio-mismatch and guardrail-metric monitoring are the safety nets that surface the resulting anomaly so the team can fix the layer configuration.

Datafile and SDK Architecture

Why is bucketing done client-side against a datafile instead of a network call to a bucketing service?
A network call would add latency to every single page render or API response in the system and create a central bucketing service as a scaling bottleneck and single point of failure for every request, everywhere. Shipping the (small, cacheable) rules to the edge/client/server instead means bucketing costs nothing beyond a hash computation and never depends on a live backend call succeeding.
What happens if the SDK can't fetch a fresh datafile — outage, network partition, cold start?
It keeps using its last successfully cached datafile and keeps bucketing correctly from those (possibly slightly stale) rules. A brand-new cold start with genuinely no cached copy and no connectivity is the one true gap; SDKs typically ship a bundled default datafile for exactly this case so bucketing degrades gracefully rather than failing outright.
How do you roll out a datafile change safely (e.g. changing traffic allocation) without breaking active experiments?
Traffic-allocation changes are additive by construction: raising an allocation percentage only adds newly-eligible users at the margin of the bucket range, it never reassigns a user who was already included at the lower percentage, since their hash-derived bucket value hasn't moved. Publishing is versioned and every SDK atomically swaps to the new revision on its next fetch, so there's no window where two SDKs are running two different traffic splits' logic against the same live revision.

Statistics and Guardrails

What is the "peeking problem" in fixed-horizon A/B testing, and how does sequential testing fix it?
A fixed-horizon p-value is only valid if computed once, at a pre-committed sample size; checking it repeatedly and stopping the first time it crosses 0.05 inflates the true false-positive rate far above 5%, since you're implicitly running many correlated tests. Sequential (always-valid) testing methods are constructed via confidence sequences specifically so the significance guarantee holds no matter how often or when you check, making "peek anytime" statistically safe.
What's a guardrail metric, and why do you need one even if the primary metric looks great?
A guardrail metric (page-load time, error rate, revenue) is automatically tracked alongside the primary metric to catch a negative side effect the team didn't think to look for. A variation can win decisively on clicks while quietly slowing the page down or increasing errors; without automatic guardrails, that regression only surfaces after it's already shipped to 100% of users.
How do multi-armed bandits differ from classic A/B testing, and when would you choose one over the other?
A bandit dynamically shifts traffic toward the currently-best-performing variation instead of holding a fixed split for the whole experiment, optimizing for short-term outcome at the cost of a clean, symmetric statistical comparison. Choose a bandit for pure exploitation on a short-lived decision (e.g. a one-day promo headline); choose classic fixed-split A/B testing when you need a durable, generalizable, statistically rigorous answer about which variation is actually better.
How do you detect Sample Ratio Mismatch, and why is it such an important health check?
Run a chi-squared (or equivalent) test comparing the observed split across variations against the configured split (e.g. expected 50/50); a statistically significant deviation flags SRM. It's important because SRM is usually the first visible symptom of a bucketing, targeting, or logging bug that silently invalidates the whole experiment's results — catching it early prevents a team from trusting a broken result.

Data Pipeline, Consistency, and Ops

How do you handle a user re-bucketed on page refresh — does that inflate exposure counts?
No — each exposure event carries a dedup_key derived from (visitor_id, experiment_id, day), and the collector/aggregation layer collapses repeated events sharing that key into a single counted exposure, regardless of how many times the page recomputes the (identical) bucketing decision.
How does the metrics pipeline handle a conversion event that arrives after the exposure event was already reported, or arrives late/out of order?
The stream join attributes events by their original event timestamp, not arrival/ingestion order, and tolerates a bounded "allowed lateness" window (e.g. up to 72 hours) during which a late-arriving event can still be folded into the correct aggregate before that period's numbers are treated as final.
How would you scale event ingestion during a huge traffic spike (e.g. a Black Friday experiment)?
Autoscale the collector fleet behind the load balancer, rely on the durable partitioned log to absorb the burst without dropping events, and accept that per-variation aggregates may lag by more than usual during the spike — correctness (no lost events) is preserved; only freshness of the dashboard briefly degrades.
What's your audit trail if someone changes a live experiment's traffic allocation mid-flight — why does that matter statistically?
Every config mutation on a running experiment is logged with who changed what and when. It matters statistically because a mid-flight allocation change (without knowing it happened) can bias a naive analysis that implicitly assumes a constant split for the whole experiment window; a visible audit trail lets the stats engine (or an analyst) account for the change instead of silently drawing a wrong conclusion.

Key Takeaways

Remember
Determinism and statelessness are the design's spine: bucketing is a pure function of (user id, experiment/layer id, datafile revision), computed identically anywhere with zero added latency and no database lookup — state that explicitly, since it's what makes everything else possible. Layers/namespaces are what let hundreds of experiments run concurrently without interaction effects, by hashing each user independently per layer. Bucketing and event-tracking are architecturally decoupled on purpose: one must be synchronous and free, the other asynchronous and durable. And the statistical engine is not an afterthought — sequential (always-valid) testing plus automatic guardrail metrics are what make a "check anytime" self-serve dashboard trustworthy instead of a false-positive machine.
