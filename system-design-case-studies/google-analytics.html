SYSTEM DESIGN

Designing Google Analytics — User Analytics Dashboard and Pipeline

A complete, interview-ready design walkthrough: requirements, capacity estimation, beacon/collection API, the GA4-style event data model, a Lambda-architecture pipeline with a real-time speed layer and an exact batch layer, sessionization & identity stitching, HyperLogLog/Count-Min Sketch approximation at huge cardinality, sharding & replication, privacy/consent trade-offs, and follow-up interview questions.

Problem Statement

Design a web/app analytics platform, in the style of Google Analytics, that lets any site or app embed a lightweight client SDK and get, in return, a full analytics product: a near-real-time "active users right now" and "top pages right now" dashboard, plus rich historical reporting — funnels, cohort/retention analysis, and multi-touch attribution — computed over the same underlying stream of user-interaction events. The platform must ingest events from billions of page views, screen views, clicks, and custom application events per day across millions of independently-owned properties (sites/apps), at extreme and highly bursty scale (a single viral post or ad campaign can spike a property's traffic 100× in minutes), while respecting strict, jurisdiction-varying user-privacy constraints (IP anonymization, consent-based tracking, configurable data retention).

Why does this problem matter in an interview?

It is one of the canonical "design a pipeline with two very different consumers of the same data" problems: one consumer (the live dashboard) wants an answer *now*, approximately; the other (the historical report) wants an answer *eventually*, exactly. A strong candidate recognizes this as a Lambda-architecture-shaped problem from the first minute, and treats "how do we reconcile a fast-but-approximate number with a slow-but-exact number, and is it okay if they briefly disagree?" as the load-bearing design question — not an afterthought.

Why is this different from a generic "event pipeline" problem?

  • Cardinality is the central technical challenge, not raw volume: "how many unique users visited today" is a much harder counting problem at billions-of-events scale than "how many events happened," and forces a conversation about approximate algorithms (HyperLogLog, Count-Min Sketch) that most other pipeline designs never need.
  • The product itself has two fundamentally different SLAs baked in — a real-time tile that must update within seconds, and a historical report that is allowed (indeed expected) to be computed the next day, exactly.
  • Privacy is not a bolt-on compliance checkbox here — consent state directly changes what data is collected at all, and the pipeline has to degrade gracefully (modeled/estimated conversions) rather than simply erroring out when consent is withheld.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope before drawing boxes.

  1. Are we designing for a single property (one site) or a true multi-tenant platform serving millions of independently-owned sites/apps, each with its own property id?
  2. What's the acceptable staleness for the "active users right now" dashboard — a couple of seconds, or is "within the last minute" good enough?
  3. Do historical reports need to be exact (unsampled) for core metrics, or is statistical sampling acceptable for ad-hoc, high-cardinality exploratory queries?
  4. Do we need to support custom, developer-defined events and parameters, or just a fixed set of built-in events (page_view, click, purchase)?
  5. What level of cross-device identity stitching is in scope — signed-in User-ID only, or also probabilistic/device-graph matching for anonymous users?
  6. What data retention window do we need to support, and does it need to be configurable per property (e.g. for GDPR compliance)?
  7. Do we need to support multi-touch attribution modeling across marketing channels, or is that explicitly out of scope for this pass?
  8. What consent signals must the pipeline honor (e.g. Consent Mode-style "analytics_storage denied"), and what should happen to data when consent is denied — drop it entirely, or fall back to a modeled/estimated aggregate?
  9. Is raw, event-level data export required (e.g. a BigQuery-style export), or is aggregated reporting the only externally-visible surface?
  10. Single region to start, or does the design need to anticipate multi-region ingestion and reporting from day one?
Interview tip
Don't stall waiting for every answer — state a reasonable assumption out loud ("I'll assume core aggregate metrics stay unsampled and only long-tail exploratory queries get sampled, since silently sampling a customer's top-line traffic number would undermine trust in the whole product") and keep moving. This is exactly the kind of judgment call interviewers want to see.

Requirements and Goals

Functional Requirements

  1. Accept interaction events (page_view, screen_view, click, scroll, custom application events) from client SDKs embedded in millions of independently-owned properties.
  2. Serve a near-real-time dashboard showing "active users right now," "top pages/screens right now," and similar live counters, updated within a few seconds of the underlying events.
  3. Serve rich historical reports: exact daily/hourly rollups, multi-step funnels, cohort/retention tables, and dimensional breakdowns (e.g. by country, device, traffic source, date).
  4. Support an event-based data model with event-scoped, session-scoped, and user-scoped dimensions (the modern GA4 event model), rather than a rigid page-view/session-hit model.
  5. Group raw events into sessions using an inactivity-timeout boundary, and stitch events from the same logical user across devices/sessions into a single user identity.
  6. De-duplicate events delivered more than once (client retries, network re-sends) so counts are never inflated by delivery mechanics.
  7. Support multi-touch attribution modeling across marketing touchpoints leading to a conversion.
  8. Honor per-user consent state (e.g. tracking declined) — adjusting or withholding data collection and falling back to modeled/estimated metrics where required.
  9. Support configurable data retention windows per property, and IP anonymization for privacy compliance.
  10. Support raw event-level export for downstream, ad-hoc analysis (a BigQuery-style export surface).

Non-Functional Requirements

  1. Massive, bursty ingestion throughput: the collection tier must absorb an ordinary day's traffic and also a 100× spike on a single property without dropping events or falling over.
  2. Low-latency real-time path: the "active users now" number must reflect events from the last few seconds, continuously, at all times.
  3. Exactness for core historical metrics: the batch-computed daily/hourly rollups must be exact — no sampling — even though the real-time numbers are approximate.
  4. Durability: once a client SDK successfully sends an event, it must never be silently lost by the pipeline, even if a downstream consumer lags or crashes.
  5. Extreme unique-count scale: computing distinct active users at the scale of hundreds of millions of users per day must not require storing every distinct user id in memory.
  6. Eventual consistency between real-time and batch is acceptable — a small, temporary disagreement between the "live" number and next-day's exact number is an expected, communicated trade-off, not a bug.
  7. Horizontal scalability of the collection tier, the streaming layer, and the batch layer independently, since their load and latency profiles differ enormously.
  8. Strict privacy compliance: IP anonymization, consent-aware collection, and configurable retention must be enforced at the collection tier, not bolted on downstream.

Extended / Out-of-Scope

We'll go deep on the client SDK/beacon delivery, sessionization/identity stitching, the real-time streaming path with approximate algorithms, and the batch pre-aggregation pipeline. We call out but don't build the internals of a full self-serve report-builder UI, a machine-learning-based anomaly/insight surface (e.g. automated "traffic spike" insights), or a full server-side tagging/consent-management-platform integration — real products, but layered on top of this core pipeline.

System / API Design

Client SDKs talk to the collection tier through a single, versioned beacon/collect contract. Every field needed for sessionization, identity stitching, and rendering travels with the request so the collection tier never needs a side lookup just to accept and durably log it.

  "session_id": "1699999999",              // client-generated, stable for the duration of one session

  "user_properties": { "plan_tier": "free" },   // user-scoped dimensions

Server-Side Ingestion Endpoint Contract

Collector responsibilities on receipt of a batch:
  1. Validate tid (property id) and basic payload shape; reject malformed batches fast (4xx)
  2. Anonymize/truncate the source IP before it is used for anything but a coarse geo lookup
  3. Check consent.analytics_storage; if denied, drop identifying fields and route to the
     consent-denied / modeling path instead of the standard event path (see Security & Privacy)
  4. Stamp a server-side receipt timestamp and a dedupe key (client_id + session_id + event
     timestamp + event name) for downstream idempotent processing
  5. Append the enriched event to the durable pub/sub log, partitioned by property_id
  6. Return 204 immediately — the SDK never waits on downstream processing

Errors: 400 malformed batch · 401/403 unknown or disabled property id
        413 batch too large (client should reduce batch size) · 429 property-level quota exceeded
Interview tip
Call out explicitly that the collect endpoint returns as fast as possible with no downstream dependency — the entire real-time-vs-batch split only works because the collector's job ends the moment the event is durably logged. Any synchronous call from the collector into the streaming or batch layer would reintroduce exactly the kind of coupling this architecture exists to avoid.

Why a Columnar Warehouse, Not a Row-Oriented OLTP Database

Reporting queries are overwhelmingly wide scans over a handful of columns (event_name, timestamp, a couple of dimensions) across billions of rows, with almost no single-row point lookups or transactional updates — the textbook case for columnar storage, where only the referenced columns are read off disk and dimension columns compress extremely well due to low cardinality repetition (country, device_category). The pre-aggregated rollup tables sit on top specifically so the interactive dashboard almost never touches the raw columnar event table directly.

High-Level Design

Client SDKs (web and app) fire events via beacon to a stateless, horizontally-scaled Collection Tier. The Collection Tier validates, anonymizes, and durably logs every event into a partitioned Pub/Sub log — this is the single durable seam the rest of the system is built around. Two independent consumers read that same log: a Stream Processor (speed layer) that maintains near-real-time approximate aggregates for the live dashboard, and a Batch pipeline that lands raw events in a data lake/warehouse and computes exact rollups, funnels, and cohort tables on a schedule. Both paths feed a shared Serving/Reporting API that the Dashboard queries — routing "right now" queries to the real-time store and historical queries to the rollup tables.

Figure 1. High-level pipeline — client SDKs feed a stateless Collection Tier that durably logs to a partitioned Pub/Sub topic; a Stream Processor and a Batch Pipeline consume the same log independently (a Lambda-architecture split) and both feed a shared Dashboard/Reporting API.

Key Design Principles Reflected in the Diagram

  • The durable Pub/Sub log is the one seam everything is built around: the Collection Tier's job ends the moment an event is durably appended — it has zero downstream dependency, which is what lets it scale and fail independently of both consumers.
  • Speed layer and batch layer are genuinely independent consumers of the same log (a classic Lambda architecture) — a slow or crashed batch job never affects the real-time dashboard's freshness, and vice versa.
  • Approximate vs. exact is a deliberate, scoped trade-off: only the real-time path uses HyperLogLog/Count-Min Sketch; the batch path recomputes the same metrics exactly, and the two are expected to agree closely but not perfectly.
  • Pre-aggregation is what makes the dashboard fast: the Reporting API almost never scans raw_events directly — it reads from rollup tables sized for interactive queries.

Deep Dive — Client SDK, Event Collection, and Beacon Delivery

The client SDK's job is to make firing an event essentially free for the host page/app, and to never lose an event to a page unload, a flaky network, or a temporary offline state.

navigator.sendBeacon and the Pixel Fallback

navigator.sendBeacon() is purpose-built for exactly this use case: it queues an asynchronous, fire-and-forget POST that the browser guarantees to attempt even if the page is being unloaded (a user closing a tab mid-page-view) — something a normal fetch() or XHR call cannot promise, since the browser is free to cancel in-flight requests during unload. For older browsers or environments where sendBeacon is unavailable, the SDK falls back to a 1x1 tracking-pixel <img> request, encoding the event payload in the query string — lower payload-size ceiling and less reliable delivery guarantees, but universally supported.

Client-Side Batching

Rather than firing one HTTP request per event, the SDK accumulates events into an in-memory queue and flushes them as a single batched beacon on a short timer (e.g. every 1–2 seconds) or when the queue reaches a size threshold, whichever comes first. This single change cuts request volume by roughly the average batch size, directly reducing collector-tier load and connection overhead for high-event-rate pages (e.g. a page emitting many scroll/engagement events).

Offline and Retry Buffering

If the network is unavailable or the beacon send fails, events are held in a local buffer (in-memory, or localStorage/IndexedDB for app SDKs that need to survive a process restart) and retried with backoff once connectivity returns. Each buffered event carries the client-generated dedupe key described below, so a retried send that actually succeeded once already (but whose acknowledgment was lost) never produces a double count once it reaches the collector.

Deep Dive — Sessionization and Identity Stitching

Raw events arrive as a flat stream; sessionization and identity stitching are what turn that stream into "this user did A, then B, then C in one visit," and "this signed-in user is the same person who browsed anonymously on their phone yesterday."

Session Boundary — Inactivity Timeout

A session is a bounded sequence of events from one client_id, closed by an inactivity timeout — the classic default is 30 minutes of inactivity ends the current session; the next event after that gap starts a new session_id. This is a pragmatic, universally-recognized default rather than a technical necessity: shorter timeouts split legitimate continuous browsing into artificially many sessions, while much longer timeouts blur genuinely separate visits together. Some properties override the default (e.g. a media property with long, passive engagement might use a longer timeout); this is exposed as a per-property configuration.

Cross-Device Identity Stitching

Two mechanisms combine to answer "which events belong to the same logical person," in order of preference:

  • Signed-in User-ID (deterministic): when the host app authenticates the user and passes a stable user_id with events, every device/session carrying that same user_id is stitched into one identity with full confidence — this is the gold-standard signal.
  • Probabilistic signals (fallback, anonymous traffic): for users who never sign in, the pipeline falls back to device/browser fingprint-adjacent signals (first-party client_id continuity, IP range plus user-agent plus timing correlation across devices) to probabilistically link likely-same-person sessions — lower confidence, and explicitly presented in reporting as "probabilistic" rather than certain.

Reporting always prefers the deterministic user_id graph where available and only falls back to probabilistic stitching for the portion of traffic that never authenticates — mixing the two without labeling the confidence level is a common design mistake to call out.

Event De-Duplication

Because both client retries and the durable log's at-least-once delivery semantics mean the same logical event can arrive more than once, every event carries a deterministic dedupe key — typically hash(client_id, session_id, event_name, event_timestamp) — computed once at the collector and checked against a short-lived (e.g. 24-hour) dedupe cache/table before being counted twice in either the real-time or batch path. Without this, a flaky mobile network's retried beacon would silently inflate every downstream count.

Deep Dive — Real-Time Stream Processing Path

The speed layer's entire job is to answer "how many unique users are active right now, and what are the top pages right now" continuously, at a scale where storing exact per-user sets is not memory-feasible.

Windowed Aggregation

The Stream Processor maintains tumbling windows (e.g. 1-minute buckets, non-overlapping) per property for coarse metrics like "active users in the last minute," and a sliding window (e.g. a rolling 5-minute view recomputed every few seconds) for the smoother "active users right now" tile the dashboard actually displays, since a strict tumbling window would visibly reset every minute.

HyperLogLog for Approximate Unique Counts

Counting exact distinct users per window at this cardinality would require storing every distinct user id seen in the window — infeasible in memory across millions of concurrently-active properties. HyperLogLog (HLL) instead maintains a small, fixed-size sketch (a few KB, regardless of how many billions of distinct values are fed into it) that estimates cardinality within a small, bounded standard error (typically <2% with common parameterizations) by tracking the statistical distribution of leading-zero patterns in hashed input values. HLL sketches are also mergeable — the sketches for many individual stream-processor shards for the same property/window can be combined into one property-level estimate without re-scanning any raw data.

Count-Min Sketch for Approximate Top-K

"Top pages right now" is a frequency-estimation problem at the same cardinality challenge: tracking an exact counter per distinct page URL across a huge, unbounded key space would again blow up memory. A Count-Min Sketch maintains a small, fixed-size array of counters via multiple hash functions, giving an approximate frequency count for any key with one-sided error (counts are never underestimated, only occasionally overestimated) — enough to reliably surface the true top-K pages by frequency without tracking every URL ever seen.

Deep Dive — Batch Processing and Pre-Aggregation Pipeline

The batch layer's job is the opposite trade-off from the speed layer: take as long as needed (typically hours, on a daily or hourly schedule) but produce exact answers, and pre-compute them into a shape the dashboard can query interactively.

Landing Raw Events in the Data Lake / Warehouse

A separate consumer group reads the same Pub/Sub log and writes every event, unmodified beyond the collector's enrichment, into columnar storage (Parquet-like files or a native warehouse table) partitioned by event_date and property_id. This landing step is intentionally dumb — no aggregation happens here — so it can never be the reason a downstream job produces a wrong exact answer.

Scheduled Batch Jobs

  • Daily/hourly rollup job: scans the prior period's raw_events partition and computes exact active_users, sessions, event_count, and conversions, pre-aggregated by common report dimensions — country × device × date — so the dashboard's default views never scan raw events.
  • Funnel job: for each configured funnel definition, computes exact per-step user counts in temporal order (a user must complete step N before step N+1 counts), producing the funnel_steps table.
  • Cohort/retention job: groups users by their first-seen date (the cohort) and computes, for each subsequent period, how many of that cohort were active again — producing the cohort_retention table used for retention curves.

Pre-Aggregation by Common Dimensions

Every batch job pre-aggregates along the small set of dimension combinations that dashboards actually filter by (country, device category, traffic source, date) rather than leaving the dashboard to filter billions of raw rows per query. This is the single biggest lever for interactive dashboard latency: a rollup table with millions of rows (one per property × date × dimension-combo) answers in milliseconds what a scan of billions of raw events would take minutes to compute.

Figure 4. Batch pre-aggregation — scheduled jobs read the landed raw-event data lake once and produce exact, pre-aggregated rollup/funnel/cohort tables sized for fast, interactive dashboard queries.

Data Partitioning and Sharding

Sharding decisions follow the same principle throughout: keep everything for one property together for query locality, and shard the streaming layer so per-user/session state never needs cross-shard coordination.

  • Raw event storage is partitioned by event_date + property_id in the data lake — this matches the two dimensions almost every batch job and ad-hoc query filters by first, so a job scanning "yesterday's data for property X" reads only the relevant partitions instead of the entire table.
  • The Pub/Sub ingestion topic is partitioned by property_id (or a hash of it for very large properties), so a single stream-processor shard can maintain complete per-property window state without needing input from any other shard.
  • The streaming aggregation layer is sharded by a hash of user_id / session_id within a property for any per-user state (e.g. session-boundary tracking), ensuring all events for one user's current session are processed by the same shard for correctness.

Replication and Fault Tolerance

The durable Pub/Sub log is the fault-tolerance backbone of the entire design: because the Collection Tier's only responsibility is appending to this replicated (RF=3) log, an outage or a bug in either the stream processor or the batch pipeline can never cause ingestion to silently lose events — the events simply sit durably in the log, un-consumed, until the affected consumer recovers.

  • Consumer offset tracking: each consumer group (stream processor, batch-landing job) tracks its own committed offset into the log; a crashed consumer resumes from its last committed offset rather than from the log's head, so a restart reprocesses at most a small window of recently-uncommitted events (made safe by the dedupe key).
  • Log retention as a recovery buffer: the log retains a rolling 24-hour buffer specifically so a consumer that falls behind or is down for a while can catch up by replaying from its last offset, rather than losing data permanently.
  • Stream-processor state checkpointing: in-flight window aggregates (HLL sketches, Count-Min Sketch counters) are periodically checkpointed to durable storage, so a crashed stream-processor instance recovers its recent window state instead of restarting cold and under-counting the current window.
  • Batch job idempotent re-runs: because the landing step and each rollup job are deterministic functions over an immutable partition of raw events, any batch job can simply be re-run over the same partition after a failure and produce the identical exact result — no special recovery logic needed beyond "run it again."

Feature-Specific Logic

Multi-Touch Attribution Modeling

Attribution — deciding how much "credit" each marketing touchpoint (an ad click, an email open, an organic search) gets for an eventual conversion — is deliberately implemented as a heavier, separate batch job layered on top of the core pipeline, not a real-time computation. It requires joining a user's entire touchpoint history (potentially spanning weeks) against their conversion events and applying an attribution model (last-click, linear, time-decay, or a data-driven model), which is both computationally heavier and far less time-sensitive than the core "how many users today" rollups — a marketer reviewing attribution reports does not need last-minute freshness the way a live dashboard does.

Statistical Sampling for Ad-Hoc Exploratory Queries

Core aggregate metrics (the pre-aggregated rollup tables) stay unsampled and exact, computed once by the scheduled batch jobs. But a free-form, ad-hoc exploratory query — e.g. "show me a breakdown of a rarely-used custom event by an arbitrary combination of five dimensions, over 13 months" — can require scanning a prohibitively large slice of raw events on demand. For that class of query only, the system applies statistical sampling (querying a representative subset of the raw event data and extrapolating), trading a small amount of precision for a query that returns in seconds rather than minutes or timing out entirely. This scoping — sampling only touches long-tail ad-hoc queries, never the core dashboard numbers — is an important distinction to state explicitly, since it is exactly the kind of nuance a real analytics platform has had to earn through experience (raw event-level export, e.g. into a data warehouse, is the escape hatch for anyone who needs unsampled, arbitrary-dimension access).

Security, Privacy and Permissions

  • IP anonymization: the source IP is used only transiently at the collection tier to derive a coarse geo (country/region) and is then truncated/discarded — the full IP address is never written into the durable log or any downstream table.
  • Configurable data retention: each property can configure its event-level data retention window (e.g. 2, 14, or 26 months); a scheduled purge job enforces the configured window per property, supporting jurisdictions with stricter data-minimization requirements.
  • Consent Mode — adjusting or withholding tracking: the collector checks the consent.analytics_storage signal on every batch; if consent is denied, identifying fields (client_id, user_id) are stripped before the event is logged, and the event is routed to an aggregate-only, non-identifying path rather than the standard per-user pipeline.
  • Modeled/estimated conversions when consent is denied: rather than simply losing all visibility into consent-denied traffic, the batch pipeline uses the (unblocked) consented traffic as a statistical basis to model/estimate the missing conversions attributable to denied-consent users — a real, current, and interview-relevant trade-off between full accuracy and full user privacy.
  • Multi-tenant isolation: every table is keyed by property_id as a leading key element, so one property's data can never leak into another's query results or exports by construction.
  • Template/no injection surface: event parameter values are always treated as opaque data (never executed, never used to construct queries via string concatenation), closing off injection risk in both the collection tier and the reporting layer.
  • Transport security: TLS everywhere for beacon delivery; access to raw event export and reporting APIs is scoped per property via authenticated, tenant-scoped credentials.

Load Balancing

Load balancing shows up at a few distinct layers:

  1. Globally, in front of the stateless Collection Tier fleet — distributing client beacon traffic across many collector instances and, more importantly, across many geographic ingestion points.
  2. Across Pub/Sub partitions/consumer-group members for the stream processor and the batch-landing consumer — the messaging system's own consumer-group rebalancing handles this natively as instances scale up/down.
  3. Across batch-processing workers for a scheduled job (e.g. a distributed compute framework splitting a day's raw_events partition into many parallel tasks).

For the collection tier specifically, use anycast routing / GeoDNS so a beacon from a browser in Tokyo resolves to the nearest regional ingestion point rather than a distant, fixed endpoint — this is the single biggest lever on beacon round-trip latency, and it's a purely network-layer decision that requires no application-level awareness of "which region is closest."

Scaling to Multiple Regions

  • Regional ingestion points (routed to via anycast/GeoDNS) accept beacons close to the user, minimizing round-trip latency — but the two viable designs diverge on what happens after that.
  • Option A — regional ingestion writing to a globally-replicated log: every region's collector writes into the same logical Pub/Sub topic, replicated globally. Simpler mental model (one global stream to consume), but cross-region replication adds latency and cost to every single event, even ones a region-local speed layer could have processed entirely locally.
  • Option B — region-local processing with a global rollup merge step (recommended): each region runs its own full pipeline (collection, streaming, and batch) against its own regional slice of traffic; a separate, lightweight merge job periodically combines each region's rollup tables (and, for the real-time path, mergeable HLL sketches) into a global view. This keeps the latency-critical local path entirely intra-region, and only the already-small, already-aggregated rollup/sketch data crosses regions — far cheaper than replicating every raw event globally.
  • HLL mergeability is what makes Option B work for the real-time path too: a global "active users now" figure can be produced by merging each region's local HLL sketch for the current window, without ever centralizing raw events or exact user sets.

Monitoring, Logging and Analytics

  • Pipeline-lag monitoring: continuously measure how far the real-time path is behind wall-clock time — the gap between an event's client timestamp (or collector receipt timestamp) and the moment it's reflected in the real-time serving store. A healthy speed layer should show this lag flat and small (seconds); a growing lag is the earliest signal of stream-processor backpressure or an upstream Pub/Sub bottleneck.
  • Batch job SLA monitoring: track each scheduled job's start/end time and row counts processed against its expected schedule window (e.g. "daily rollup must complete within 4 hours of the day's end") and alert on SLA misses before a customer notices a stale historical report.
  • Data-quality checks / anomaly detection on incoming volume: compare each property's current event volume against its own recent historical baseline; a sudden drop can indicate a broken SDK integration or an outage upstream of collection, while a sudden unexplained spike can indicate bot traffic, a tracking bug (e.g. an event firing in a loop), or a genuine viral event worth flagging to the customer.
  • Real-time vs. batch reconciliation dashboards (internal): continuously compare the speed layer's approximate daily total against the batch layer's exact total for the same period once both are available, tracking the error rate over time to confirm HLL/Count-Min Sketch accuracy stays within expected bounds.

The Central Trade-Off, Stated Plainly

The entire design rests on accepting that "right now" and "exactly correct" are, at this scale, mutually expensive to have simultaneously — and choosing to serve two different numbers to two different use cases rather than forcing one number to serve both badly. A candidate who can articulate why a live dashboard tile being off by a percent or two for a few minutes is an acceptable, deliberate cost (while a customer's monthly billing/reporting number being off would not be) has understood the crux of this problem.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as "and then what?" follow-ups on whatever you draw first.

Architecture and the Real-Time/Batch Split

Why not just compute everything in real time, since streaming engines can handle high throughput today?
Some metrics (exact funnels, cohort/retention curves, multi-touch attribution) require joining a user's activity over long time windows — sometimes weeks — against later events, which doesn't fit a bounded streaming window cheaply, and doing it exactly in real time at this cardinality would cost far more than accepting a next-day batch SLA for those specific metrics. The live dashboard only needs approximate, coarse-grained numbers, which is exactly what the streaming layer is optimized for instead.
What happens when the real-time number and the batch number disagree?
It's expected and monitored, not a bug: the real-time number is an HLL/Count-Min-Sketch-based estimate with a known bounded error, while the batch number is the exact recomputation of the same period. The product should label the real-time figure as an estimate, and internal reconciliation dashboards track that the gap stays within the expected error bound over time.
Is this a Lambda architecture or a Kappa architecture?
As designed here it's Lambda — two separate code paths (stream processor for approximate/fast, batch pipeline for exact/slow) reading the same log. A Kappa-architecture variant would instead reprocess one unified stream for both purposes (e.g. replaying the log through the same streaming engine to backfill history), trading the operational cost of maintaining two codebases for the engineering complexity of making one streaming engine also produce exact, replayable historical results.

Cardinality and Approximate Algorithms

Why HyperLogLog specifically, instead of just a distributed hash set of user ids?
A hash set's memory grows linearly with true cardinality — at hundreds of millions of unique users per window across millions of properties, that's an infeasible memory footprint. HyperLogLog's sketch size is fixed (a few KB) regardless of how many distinct values are fed into it, trading a small, well-understood bounded error for that memory bound, and sketches merge cleanly across shards without re-scanning raw data.
How accurate is HyperLogLog, and is that accuracy acceptable for a product?
Standard implementations achieve roughly <2% relative error with a modest number of registers (a few KB of state); this is acceptable for a live "active users now" tile explicitly framed as a real-time estimate, but not acceptable for a customer's exact monthly reporting number — which is exactly why the batch layer recomputes that number exactly instead of relying on the sketch.
Why Count-Min Sketch for top pages instead of just a hash map of counters?
A hash map's memory also grows with the number of distinct keys (URLs), which is effectively unbounded for a large property with dynamic URLs (query strings, IDs in paths). Count-Min Sketch uses a fixed-size counter array with multiple hash functions, giving approximate frequency counts in bounded memory — with the caveat that its error is one-sided (it can overestimate a count due to hash collisions, but never underestimate), which is a fine trade-off for surfacing an approximate top-K list.

Sessionization and Identity

Why a 30-minute inactivity timeout for sessions, and not something else?
It's an industry-standard, empirically reasonable default that balances not artificially splitting continuous browsing into many sessions against not blurring genuinely separate visits together; it's not a technical constraint, so it's exposed as a per-property configuration for properties with very different engagement patterns (e.g. long-form video).
How do you stitch together a user's activity across their phone and laptop?
Deterministically, via a signed-in user_id present on events from both devices — the gold-standard signal. For users who never sign in, the system falls back to lower-confidence probabilistic signals (client_id continuity, IP/user-agent/timing correlation), and reporting should distinguish deterministic from probabilistic identity resolution rather than presenting both with equal confidence.
How do you prevent a flaky network from inflating event counts through retries?
Every event carries a deterministic dedupe key (a hash of client_id, session_id, event name, and timestamp) computed once and checked against a short-lived dedupe cache at the collector, so a redelivered or retried beacon is recognized and counted exactly once regardless of how many times it physically arrives.

Privacy, Consent, and Compliance

What happens to an event when a user has declined analytics consent?
The collector strips identifying fields (client_id, user_id) before logging, and routes the event to an aggregate-only, non-identifying path rather than the standard per-user pipeline; downstream, the batch pipeline uses statistically modeled/estimated conversions — extrapolated from consented traffic — to approximate the measurement gap left by denied-consent users, rather than simply losing that signal entirely.
How do you support a property that needs a much shorter data-retention window for compliance?
Retention is a per-property configuration enforced by a scheduled purge job against the data lake's date-partitioned raw_events; a property needing a 2-month window simply gets a tighter purge schedule than the 14-month default, with no change to the ingestion or processing pipeline itself.
Why anonymize IP addresses at the collector instead of the reporting layer?
Because the goal is to never let the sensitive raw value propagate downstream at all — anonymizing at the earliest possible point (the collector, immediately after deriving the coarse geo signal it's actually needed for) means no downstream table, log, export, or backup ever contains the full IP, which is a much stronger guarantee than trying to redact it later in every possible downstream consumer.

Scaling and Operations

How would you scale this to a second region without doubling cross-region traffic?
Run a full region-local pipeline (collection, streaming, batch) against that region's own traffic, and merge only the already-small, already-aggregated outputs — rollup table rows and mergeable HLL sketches — across regions on a schedule, instead of replicating every raw event globally.
How do you detect that the real-time pipeline is falling behind before customers notice stale numbers?
Continuously measure pipeline lag — the gap between an event's receipt timestamp and when it's reflected in the real-time serving store — and alert on any sustained growth; a healthy speed layer should show this lag flat and small (seconds) regardless of traffic volume, so drift is a strong, early signal of stream-processor backpressure.
A property suddenly shows zero events — how do you know if it's a real outage or a broken integration?
Data-quality anomaly detection compares each property's current volume against its own recent historical baseline; a sudden drop to near-zero for one property (while others are normal) points to a broken SDK integration or a site-side deployment issue rather than a platform-wide outage, which would show the same pattern across many properties simultaneously.
How would you add multi-touch attribution without slowing down the core pipeline?
Implement it as its own separate, heavier scheduled batch job that reads the same landed raw events and joins a user's touchpoint history against conversion events — it has its own schedule and resource footprint, and a failure or slowdown in the attribution job never touches the core rollup, funnel, or real-time paths.

Key Takeaways

Remember
This is a Lambda-architecture problem at heart: one durable, replicated log, read independently by a fast-but-approximate speed layer and a slow-but-exact batch layer, feeding a shared serving/reporting surface — state that split explicitly and early. Cardinality, not raw event volume, is the hardest technical problem: HyperLogLog and Count-Min Sketch exist specifically to bound memory at extreme unique-count and top-K scale, at the cost of a small, well-understood error the batch layer later corrects for exactly. Sessionization (inactivity timeout) and identity stitching (deterministic user_id preferred over probabilistic signals) are what turn a flat event stream into a coherent per-user narrative, and event de-duplication via a dedupe key is what keeps at-least-once delivery from inflating counts. Sampling should be scoped narrowly to long-tail ad-hoc queries, never to core aggregate metrics. And privacy — IP anonymization, configurable retention, and Consent Mode with modeled fallback — is a first-class architectural concern here, not a compliance afterthought, because consent state directly determines what the pipeline is even allowed to collect.
