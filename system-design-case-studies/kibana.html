SYSTEM DESIGN

Designing an Observability Platform (Kibana / ELK-Style)

A complete, interview-ready design walkthrough for a unified observability platform bundling four pillars — distributed tracing, metrics collection from thousands of servers, cluster health monitoring, and distributed log aggregation — behind one shared ingestion spine and a single Kibana-style pane of glass: requirements, capacity estimation, API & data-model design, the shared high-level architecture, per-pillar deep dives, sharding & replication, security, and follow-up interview questions.

Problem Statement

Design an observability platform for a large distributed system running on 10,000+ hosts: an ELK/Kibana-style stack that lets an on-call engineer go from “something's wrong” to “root cause” inside one tool. Concretely, the platform must unify four historically separate concerns:

  1. Distributed tracing — follow one request as it hops across dozens of microservices, so you can see exactly where latency or an error was introduced.
  2. Metrics collection from thousands of servers — CPU, memory, request rate, error rate, latency histograms, and thousands of custom application metrics, collected continuously and cheaply.
  3. Cluster health monitoring — is each service, shard, and node up, in quorum, and within SLA, without false-positive outage alerts from a transient network blip.
  4. Log aggregation — centralize, parse, and index unstructured/structured log lines from every host so they're searchable in seconds, not minutes.

Any one of these four is a reasonably scoped interview question on its own. The genuinely interesting design problem — the one worth spending the whole session on — is why and how to bundle all four under one platform rather than shipping four independent silos (a tracing vendor, a metrics vendor, a status-page tool, and a log-search tool that don't talk to each other). Four silos mean four different agents on every host, four ingestion pipelines to operate, four storage systems to capacity-plan, and — the real cost — an on-call engineer forced to manually correlate a trace ID, a timestamp, and a hostname across four different UIs during an incident, burning the minutes that matter most. A unified platform instead shares one ingestion spine (agents on every host → a durable buffer → a processing tier → one storage engine → one query/visualization layer) across all four data types, and pays for that sharing with a single, well-designed correlation key — typically a trace ID and a common timestamp — that lets a single Kibana dashboard pivot from a slow trace span, to the exact log lines emitted during that span, to the metric anomaly that coincided with it, without leaving the page.

Why does this problem matter in an interview?

It forces you to reason about a system that must simultaneously behave like a write-heavy time-series database (metrics), a write-heavy full-text search index (logs and traces), and a low-latency health/consensus system (cluster status) — each with wildly different cardinality, retention, and query patterns, yet all sharing infrastructure for cost reasons. A strong candidate recognizes early that the four pillars are not architecturally identical (metrics need rollups and cardinality control; logs need parsing and tiered storage; traces need sampling and context propagation; health needs quorum, not raw counting) and designs one shared spine with pillar-specific processing bolted onto it — rather than either forcing all four into one identical pipeline, or building four unrelated systems that happen to sit in the same repo.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope across all four pillars before drawing boxes.

  1. How many hosts/servers are we instrumenting today, and what's the expected growth (10,000? 100,000?)?
  2. For tracing: what's the acceptable sampling rate, and do we need tail-based sampling (to guarantee we keep 100% of error/slow traces) or is head-based sampling acceptable?
  3. For metrics: do we need per-request/per-user-level labels (high cardinality), or are we aggregating at the service/host level only?
  4. What data retention do we need per pillar — are hot logs/metrics needed for 7 days, 30 days, a year for compliance?
  5. Is this single-region or does the platform need to span multiple data centers/regions from day one?
  6. What's the acceptable end-to-end ingestion lag before a log line or metric point is queryable in Kibana (seconds? a minute?)?
  7. Do we need alerting (threshold-based and anomaly-based) built into this platform, or is alerting owned by a separate downstream system that just consumes our data?
  8. How is the observability platform itself monitored — is there a fallback path if the platform monitoring the rest of the fleet goes down?
  9. Do we need role-based access control per team/index (e.g. team A can't see team B's logs), and are there PII/compliance constraints on what can be logged?
  10. Is a managed/hosted Elasticsearch (Elastic Cloud, OpenSearch Service) acceptable, or must this be self-hosted?
Interview tip
Don't stall waiting for every answer — state a reasonable assumption out loud (“I'll assume 10,000+ hosts today growing toward 50,000, tail-based sampling for traces since catching every error trumps ingest cost, and 15 days hot / 90 days warm / 1 year cold retention for logs”) and keep moving. Naming the cardinality-explosion risk on metrics unprompted is one of the highest-signal moves you can make in this specific interview.

Requirements and Goals

Functional Requirements

  1. Distributed tracing: instrument services to emit spans, propagate trace context across service hops, ingest and store traces, and let an engineer view a full trace as a tree/waterfall and derive a service dependency graph.
  2. Metrics collection: collect counters, gauges, and histograms from 10,000+ hosts and services (both pulled and pushed), store them as time series, and support ad-hoc queries plus pre-built dashboards.
  3. Cluster health monitoring: continuously track liveness of every service/node/shard, compute an aggregate red/yellow/green health status per cluster, and run synthetic canary checks against critical user journeys.
  4. Log aggregation: ship structured and unstructured logs from every host, parse them into structured fields, index them for full-text and field search, and enforce lifecycle-based retention/tiering.
  5. Correlation: let a user pivot from a trace span to the log lines and metric values that share its timestamp and host/service, in one UI (Kibana).
  6. Alerting: fire alerts on metric thresholds, log patterns (e.g. error-rate spikes), and health-status transitions, with configurable routing (paging, Slack, email).
  7. Dashboards and ad-hoc query: a query language/UI (Kibana Discover/Lens-style) for exploring any of the four data types, plus saved dashboards.

Non-Functional Requirements

  1. High ingestion throughput and durability: the platform must absorb millions of events/sec across all four pillars without data loss, even during a downstream processing slowdown.
  2. Low end-to-end latency to queryable: ideally single-digit seconds from emission to being visible in Kibana, since incident response depends on freshness.
  3. Horizontal scalability of every tier (collectors, buffer, processing, storage) independently, since a metrics cardinality spike and a log-volume spike are uncorrelated events.
  4. Cost efficiency at scale: storage cost dominates total cost of ownership; the design must actively fight cardinality explosion and use tiered storage rather than keeping everything hot forever.
  5. High availability of the monitoring platform itself: this is the system engineers rely on during an outage of something else — it cannot itself be a single point of failure, and ideally survives the very incident it's helping diagnose.
  6. Query performance: ad-hoc searches over recent (hot-tier) data should return in low seconds even across billions of documents.
  7. Eventual consistency is acceptable for most reads (a dashboard a few seconds stale is a non-issue); cluster health decisions specifically need quorum-based correctness to avoid false-positive outage pages.

Extended / Out-of-Scope

We'll go deep on the shared ingestion spine and all four pillars: tracing, metrics, cluster health, and log aggregation, plus sharding, replication, security, and multi-region scaling. We call out but don't build a full anomaly-detection ML pipeline, a complete APM code-profiling/flame-graph product, or a general-purpose BI/reporting layer on top of the same data — real adjacent products, but layered on top of this core platform.

Capacity Estimation and Constraints

State assumptions explicitly and let them drive every downstream decision. Assume a fleet of 12,000 hosts running a mix of ~3,000 services.

Call out that every one of these three payloads deliberately carries the same correlation fields — a timestamp, a host/service identity, and (for logs and traces) a trace.id — even though the wire formats themselves are completely different (protobuf vs. text-exposition vs. bulk JSON). High-Level Design

Every host runs the same class of lightweight agent (an OpenTelemetry Collector for traces/metrics, a Beats-style shipper for logs). Agents write to a durable ingestion buffer (Kafka), decoupling “something happened on a host” from “it's been processed and indexed.” A processing tier consumes the buffer, doing pillar-specific work — sampling decisions for traces, aggregation/rollups for metrics, Grok parsing for logs — before writing into Elasticsearch/OpenSearch. Kibana sits on top as the single query, dashboard, and alerting surface for all four pillars.

Figure 1. High-level architecture — agents on every host feed a shared Kafka ingestion buffer; a processing tier applies pillar-specific logic (sampling, rollups, Grok parsing, quorum health checks) before writing into Elasticsearch/OpenSearch, with Kibana as the single query/dashboard/alerting surface across all four pillars.

Key Design Principles Reflected in the Diagram

  • One physical spine, four logical pipelines: agents, Kafka, and the processing tier are shared infrastructure; what differs per pillar is the processing logic bolted onto that spine, not the spine itself.
  • Kafka decouples emission from indexing — a slow Elasticsearch write path or a processing-tier redeploy never causes data loss on the host side; it just grows consumer lag, which is directly observable and alertable.
  • Elasticsearch is the one shared store across all four pillars, each as its own index pattern — this is what makes a single Kibana query able to span traces, metrics, and logs together.
  • Kibana is the single pane of glass by construction, not by a UI-layer trick: because all four pillars already live in the same search engine, a saved search or dashboard can reference any of them, and the correlation feature (below) is just a query joined on shared fields.

Deep Dive — Part 1: Distributed Tracing System

Distributed tracing answers: for one specific request, which services did it touch, how long did each hop take, and where exactly did an error or a slowdown originate?

The Trace/Span Model

A trace is a tree of spans. Each span represents one unit of work (an RPC call, a DB query, a function) and carries: a unique span_id, a parent_span_id linking it into the tree (root spans have none), a shared trace_id common to every span in the trace, start/end timestamps, a name, a status (OK/ERROR), and a set of key/value tags/attributes (e.g. http.status_code, db.statement). Reconstructing the full trace is a matter of collecting every span sharing a trace_id and rebuilding the parent-child tree from parent_span_id links — which is exactly why trace_id and parent_span_id are indexed as low-cardinality-friendly keyword fields in the span mapping shown earlier.

W3C Trace Context Propagation

For the tree to reconstruct correctly, every service in the call chain must know which trace and which parent span it belongs to. The W3C Trace Context standard defines an HTTP header, traceparent, carried on every downstream call: traceparent: 00-{trace_id}-{parent_span_id}-{flags} (version-traceid-spanid-flags, e.g. 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01). Each service reads the incoming header, creates its own span as a child of the given parent span ID, and forwards a new traceparent (same trace_id, its own span_id as the new parent) to whatever it calls next. This is what turns “independent services logging independently” into “one coherent, cross-service trace tree,” and it's vendor-neutral — any OpenTelemetry-instrumented service, regardless of language or hosting, participates correctly.

Head-Based vs. Tail-Based Sampling

Recording every span of every request is prohibitively expensive at fleet scale (recall: ~19.2M spans/sec before sampling). Two sampling strategies trade off cost against completeness:

Head-based samplingTail-based sampling
When the decision is madeAt the very start of the trace (often just a random coin-flip or a hashed trace_id)After the entire trace has completed, once the outcome is known
CostCheap — no buffering, discard unsampled spans immediately at the sourceExpensive — every span of every trace must be buffered somewhere until the trace finishes
Guarantees errors are kept?No — a rare error can easily fall outside the sampleYes — can explicitly keep 100% of error/slow traces and only downsample the “boring” ones
Where the decision happensIn-process / at the edge, per span or per trace-id hashAt a dedicated tail-sampling processor downstream, after aggregating all spans of a trace
Best fitHigh-volume, cost-sensitive, mostly-uniform trafficSystems where the rare error/slow trace is the one you most need to keep

In practice, most production observability platforms use a hybrid: head-based sampling at a low base rate (e.g. 1%) to control baseline cost, layered with a tail-sampling processor in the pipeline that overrides the head decision to force-keep any trace containing an error status or exceeding a latency threshold — giving both a bounded ingest cost and a strong “never miss the interesting trace” guarantee.

OpenTelemetry Instrumentation

OpenTelemetry (OTel) is the vendor-neutral standard for generating this data: SDKs auto-instrument common frameworks/libraries (HTTP servers, database clients, RPC frameworks) to emit spans and propagate traceparent without hand-written code in the common case, plus an API for manual custom spans. The OTel Collector running as an agent (or sidecar) receives spans from local processes, batches them, and exports them onward (to our Kafka buffer here) in the OTLP wire format shown in the API section above — the same Collector binary also handles metrics, which is part of why OTel is a natural fit for a unified platform rather than needing a second, unrelated agent for tracing alone.

Deriving the Service Dependency Graph

Because every span records its own service name and its parent's span_id (and, transitively, the parent's service name), a batch job over stored spans can reconstruct which services call which: for every parent-child span pair, emit an edge (parent.service → child.service), then aggregate edge counts, error rates, and average latency over a rolling window. Rendered in Kibana, this becomes a live service dependency map — invaluable both for onboarding (“what does this service actually call?”) and incident response (“which downstream service is really responsible for this latency?”).

Deep Dive — Part 2: Metrics Collection from Thousands of Servers

Metrics answer a different question than tracing: not “what happened on this one request” but “what is the aggregate behavior of this host/service over time,” cheaply enough to sample every few seconds across the entire fleet forever.

Pull-Based (Prometheus-Style) vs. Push-Based (statsd/Beats-Style)

Pull-based (Prometheus-style scraping)Push-based (statsd / Beats-style agents)
MechanismCentral scraper polls a /metrics HTTP endpoint on each target every N secondsEach host/process actively sends metric events to a collector/aggregator
DiscoveryNeeds service discovery (which targets exist right now?)No discovery needed — the source pushes when ready
Short-lived jobsAwkward — a batch job that finishes in 2s might never get scraped (mitigated with a Pushgateway)Natural fit — push once on completion
Failure visibilityA missed scrape is itself a clear signal (“target down”)Silence is ambiguous — did the host die, or did it just have nothing to report?
Network directionCentral system reaches into every host (needs firewall/network access to all targets)Hosts reach out to a central endpoint (simpler through NATs/firewalls)
Best fit hereLong-running services, most infra metricsEphemeral jobs, environments where inbound access to hosts is restricted

A large real-world platform typically runs both: Prometheus-style scraping for the bulk of long-lived services (simpler debugging: “is the target even scrapeable” is itself a health signal), plus a push path (via the same Beats/OTel agents used for logs) for ephemeral jobs, edge devices, and anything that can't be scraped.

Metric Types

  • Counter — monotonically increasing (e.g. total requests served); consumers compute a rate via the delta over a time window, since the raw cumulative value alone is rarely useful.
  • Gauge — a point-in-time value that can go up or down (e.g. current queue depth, memory used); read directly, no rate computation needed.
  • Histogram — a bucketed distribution (e.g. request latency, with buckets like ≤10ms, ≤50ms, ≤100ms, ≤500ms, +Inf); enables computing percentiles (p50/p95/p99) after the fact, which a single averaged number can never reconstruct.

The Cardinality-Explosion Problem and Mitigation

Every unique combination of metric name + label values is a distinct time series the storage engine must track in its index. As shown in the capacity estimation above, adding one unbounded label (customer_id, request_id, raw URL path with path params) can turn 2 million series into 150 billion — a TSDB's in-memory series index and per-series storage overhead simply cannot absorb that. Mitigations, in order of preference:

  1. Bound label cardinality by design — never put a raw user ID, request ID, or unbounded free-text value in a metric label; route templates (/users/:id) instead of raw paths, and push truly per-entity detail (this specific customer's this specific request) into logs or traces instead, where high-cardinality identifiers belong.
  2. Hierarchical aggregation — aggregate at the source (per-host) before it ever reaches the central store, so the central TSDB sees one pre-aggregated series per host/service rather than raw per-request data.
  3. Downsampling / rollups for long-term retention — keep raw resolution (e.g. 10s) for a short hot window (7 days), then roll up to 5-minute or 1-hour resolution for everything older, cutting storage by ~95%+ while preserving trend visibility for capacity planning and long-term SLO tracking.
  4. Cardinality limits and alerting — the ingestion tier enforces a hard cap on distinct series per metric name and alerts (or drops/samples) when a team's instrumentation change threatens to blow past it, catching the problem before it takes down the shared cluster for everyone.

Hierarchical Federation, Downsampling, and Rollups

At fleet scale, no single ingestion node can be scraped-by or receive-from all 12,000 hosts directly. A federated hierarchy fans this out: per-rack or per-availability-zone local aggregators scrape/receive from hosts in their zone and pre-aggregate; a regional tier federates across zones; only the regional, already-aggregated series get written into the shared Elasticsearch/OpenSearch metrics store. This keeps any single tier's fan-in bounded and turns “12,000 hosts” into a small, fixed number of federated write paths at the top of the hierarchy.

Deep Dive — Part 3: Cluster Health Monitoring

Cluster health monitoring answers a narrower but higher-stakes question than metrics or logs: is the system, right now, actually working — and can we trust that answer enough to wake someone up over it?

Heartbeats and Liveness

Every node/service instance emits a lightweight heartbeat (a small “I'm alive” ping) on a short interval (e.g. every 5 seconds) to a health-tracking component. Missing N consecutive heartbeats (e.g. 3, i.e. 15 seconds of silence) marks that instance as suspected-down. A single missed heartbeat is deliberately not enough to declare an outage — that would make the system trigger-happy on ordinary network jitter, which is precisely the false-positive problem the next section addresses.

Quorum-Based Health Decisions to Avoid Split-Brain False Positives

A naive design has one health-checker node polling every target and declaring outages unilaterally — but if that one checker loses network connectivity to a healthy region (a transient network partition, not a real outage), it wrongly declares a fleet-wide false alarm, potentially paging everyone for nothing (or worse, triggering automated failover on perfectly healthy infrastructure). The fix is quorum-based health evaluation: multiple independent health-checker instances (e.g. 5, spread across different network paths/zones) each independently probe the same targets; a target is only declared genuinely down when a majority (e.g. 3 of 5) of checkers agree. This distinguishes “the target is actually down” from “one checker's view of the world is temporarily wrong” — the same fundamental idea as leader election and distributed consensus, applied to health-checking instead of leadership.

The Red/Yellow/Green Cluster-Status Pattern

Rather than a binary up/down, Elasticsearch's classic model computes an aggregate status per cluster/index from shard-level state:

StatusMeaningExample conditionAction
GreenFully healthy — all primary and replica shards allocatedEvery shard has its full complement of replicas onlineNone — normal operation
YellowDegraded but available — all primaries up, some replicas missingOne data node lost, its replica shards unassigned, but every primary is intactInvestigate node loss; data is fully readable/writable, just under-replicated (reduced fault tolerance until it heals)
RedData loss or unavailable — at least one primary shard is unassignedEnough nodes lost simultaneously that both a primary and all its replicas are downPage immediately — queries against that shard's data will fail or return partial results

This model generalizes well beyond Elasticsearch itself: applying the same red/yellow/green rollup to the whole observability platform (and to monitored services generally) gives a single, glanceable severity signal instead of a wall of raw per-node booleans — exactly the kind of aggregate status Kibana's own cluster-health view and any downstream health dashboard should surface first.

SLA/SLO Tracking

Health monitoring feeds directly into SLO tracking: define an SLI (e.g. “% of requests completing under 300ms”), a target SLO (e.g. 99.9% over a rolling 30 days), and compute an error budget (the allowed 0.1% of “bad” requests) from the same metrics/health data already flowing through the platform. Burn-rate alerts (is the error budget being consumed faster than the SLO window can tolerate?) turn a raw health signal into an actionable, business-aligned page instead of noise.

Synthetic Canaries

Heartbeats and shard status catch infrastructure failure, but not “the login page returns 200 but silently shows a broken form.” Synthetic monitoring runs scripted probes of real user journeys (log in, search, checkout) from outside the fleet on a fixed schedule, checking not just status codes but response content/timing — catching a class of failure (a working process serving broken behavior) that pure liveness/heartbeat checks structurally cannot see, and catching it proactively, before a real user reports it.

Deep Dive — Part 4: Distributed Metrics Logging and Aggregation System

The log-aggregation pillar centralizes, structures, and indexes the highest-volume, most heterogeneous data type in the platform — and, per the capacity estimation above, drives the majority of total storage cost.

Filebeat/Logstash Shipping

Filebeat (a lightweight, low-resource-footprint shipper) tails log files on each host and forwards them either directly to an Elasticsearch ingest pipeline or, when heavier transformation is needed, to Logstash (a more capable, pluggable processing pipeline: input → filter → output) before Elasticsearch. In this platform, both paths write into the same shared Kafka buffer first, so a slow or restarting Elasticsearch cluster never causes a host to drop log lines — they simply queue in Kafka until the processing tier catches up.

Structured JSON Logging

Wherever the application can control its own log format, structured JSON logging (each line already a JSON object with named fields, as shown in the log document mapping above) is strongly preferred over free-text: it skips the Grok-parsing step entirely, is unambiguous to index, and lets every log line carry the shared correlation fields (trace.id, service.name) natively as first-class fields rather than something to extract after the fact.

Grok Parsing / Ingest Pipelines

For log lines that aren't already structured (legacy services, third-party components, raw syslog), a Grok pattern — a named-regex-based pattern language — extracts structured fields from an unstructured line inside an Elasticsearch ingest pipeline. For example, the line 2026-07-18 09:14:02 ERROR [checkout-service] payment gateway timeout after 3000ms matches a Grok pattern like %{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} \[%{DATA:service}\] %{GREEDYDATA:message}, producing the structured fields ts, level, service, and message — which then become searchable/filterable fields in Kibana instead of buried substrings inside one giant text blob.

Index Lifecycle Management (ILM) — Hot/Warm/Cold/Frozen Tiers

Given log storage dominates cost, ILM automatically migrates an index through cost/performance tiers as it ages, entirely policy-driven with no manual intervention:

TierHardwareWrite activityQuery latencyTypical age in this design
HotFast local SSD, highest-spec nodesActively written (today's index)Sub-second0–15 days
WarmCheaper SSD/HDD, fewer replicasRead-only, no more writesLow seconds15–90 days
ColdCheap dense storage, further shard merge/shrinkRead-only, rarely accessedSeveral seconds90–365 days
Frozen / deletedObject storage (e.g. S3), searchable snapshot, or deleted entirelyRead-only, very rare accessTens of seconds (rehydration)>365 days, or deleted per retention policy

Moving an index from hot to warm can also reduce its replica count and force-merge its segments (fewer, larger segments compress and query better once writes have stopped); moving to frozen typically converts it to a searchable snapshot backed by object storage, trading query latency for a large storage-cost reduction. ILM policies are configured once per index template and then run automatically forever, which is what makes multi-petabyte log retention operationally tractable rather than a constant manual chore.

Inverted-Index Basics

Elasticsearch's full-text search (and Kibana's “search anything” Discover experience) is built on an inverted index: for each distinct term (a tokenized word from an analyzed text field like message), the index stores the list of document IDs containing that term, plus position/frequency data for relevance scoring. Searching for “payment gateway timeout” means looking up the (typically short) posting lists for “payment,” “gateway,” and “timeout” and intersecting/scoring them — dramatically cheaper than scanning every document's raw text, and the reason a full-text query across billions of log documents can still return in low seconds.

Shard Sizing Guidance (~10–50 GB/Shard)

Each Elasticsearch shard is itself a complete, independent Lucene index with real per-shard overhead (file handles, memory for its segment metadata, merge costs). Too many tiny shards wastes overhead and cluster-state size; too few, oversized shards make recovery and rebalancing slow and risk hitting a single shard's practical size ceiling. The standard operational guidance is to size each shard in the 10–50 GB range: given the log pillar's ≈20–25 TB/day indexed volume, at a target of ≈30 GB/shard that implies roughly 700–830 primary shards/day for logs alone across index-per-day-per-service indices — a number that directly drives the index-per-day sharding strategy discussed next.

Figure 6. Log pipeline: Filebeat → Kafka → Grok parsing → hot-tier index; Index Lifecycle Management then automatically migrates the index through warm, cold, and frozen tiers (or deletes it) purely by age, with no manual intervention.

Data Partitioning and Sharding

Sharding strategy differs meaningfully by pillar because query patterns differ: logs and traces are almost always time-bounded (“show me the last hour”), while metrics are queried as continuous time series per entity.

  • Index-per-day (logs, traces): a new index (e.g. logs-checkout-service-2026.07.18) is created daily per service. This makes time-bounded queries efficient (only touch the days in range), makes ILM tier transitions a simple whole-index operation, and makes deleting old data a cheap index-drop instead of an expensive delete-by-query.
  • Index-per-metric-family (metrics): metrics use a time-series data stream backed by rolling indices per retention tier (raw vs. 5-minute vs. 1-hour rollup), rather than per-day, since metric queries typically span long ranges (a week, a month) rather than one day at a time.
  • Shard count and sizing: per the 10–50 GB/shard guidance above, each daily log index is pre-sized with enough primary shards to keep every shard in that range given expected daily volume for that service — a high-volume service gets more shards than a low-volume one, set via an index template rather than one global default.
  • Routing: within an index, documents route to a shard by a hash of the routing value (default _id, but can be pinned to e.g. service.name or trace_id when co-locating related documents on the same shard measurably speeds up a common query pattern).

Replication and Fault Tolerance

Elasticsearch's primary/replica shard model is the fault-tolerance backbone across all three data-holding pillars (logs, traces, metrics):

  • Every shard has one primary and N replicas (typically 1 in hot tier for cost, sometimes reduced to 0 in cold/frozen tiers where the object-store-backed snapshot itself is the durability guarantee). Writes go to the primary first, then replicate to replicas; reads can be served by either, which is also a natural read-scaling mechanism.
  • Node loss handling: if a node holding a primary shard is lost, Elasticsearch promotes an in-sync replica on another node to primary automatically, and schedules a new replica to restore full redundancy — this promotion is exactly what produces a transient yellow status (see Deep Dive — Part 3) until the new replica catches up.
  • Cross-cluster replication (CCR) asynchronously replicates indices from one cluster to another (typically a different region), providing disaster recovery: if the primary region's cluster is lost entirely, the DR region has a recent (seconds-to-minutes-stale) copy to fail over to, and CCR is also the mechanism behind cross-cluster search for multi-region query patterns.

Feature-Specific Logic

The feature that actually justifies bundling four pillars into one platform — rather than four independent tools — is correlation: given a trace span, a log line, or a metric anomaly at a given moment, show everything else that happened at that same moment for that same service/host, in one view.

Concretely, the correlation query is a straightforward cross-index search enabled entirely by the shared vocabulary established back in the data model: given a span with trace_id = T, service.name = S, and a time range [start, end], Kibana issues (1) a query against logs-* for trace.id: T (exact log lines emitted during that span), and (2) a query against metrics-* for service: S AND @timestamp: [start-30s, end+30s] (was there a metric anomaly — a CPU spike, an error-rate jump — around the same window). The result, stitched together in one Kibana view, is the “single pane of glass”: a slow, erroring trace span, the exact error log line it produced, and the host-level metric spike that coincided with it, all visible without the engineer manually copying a timestamp between three different tools.

Figure 7. The correlation feature: one Kibana view issues parallel queries against traces-*, logs-*, and metrics-* using the shared trace_id / service / timestamp vocabulary, converging a slow error span, its log line, and its coincident metric spike into a single panel.
Interview tip
If asked “what's the one feature that makes this a platform instead of four tools glued together,” this correlation query is the answer. It's worth stating explicitly that it works because of the shared data model discipline (every document type carries a timestamp, a service/host identity, and where applicable a trace_id) established from day one — not because of any special cross-index join feature in Elasticsearch, which doesn't really have relational joins at all.

Security, Privacy and Permissions

  • Role-based access to indices/dashboards: role definitions grant access to specific index patterns (e.g. team A can query logs-team-a-* and traces-team-a-* but not team B's), and to specific Kibana spaces/dashboards, so a shared multi-tenant platform doesn't leak one team's operational data to another.
  • PII scrubbing/redaction in logs before ingestion: an ingest-pipeline processor (or a pre-ingestion agent-side filter) detects and masks/redacts known-sensitive patterns (emails, card numbers, SSNs, auth tokens) before a log line is ever indexed — redaction has to happen before storage, since retroactively scrubbing already-indexed documents at petabyte scale is impractical.
  • Audit logging: the platform logs who queried what (which user, which index pattern, which query, when) as its own audit trail, both for compliance and to detect misuse of a system that, by design, has broad visibility into the rest of the company's operational data.
  • Transport security: TLS between every hop (agents → Kafka → processing tier → Elasticsearch → Kibana), with mTLS for service-to-service legs and API keys/tokens scoped per team for ingestion credentials.

Load Balancing

  1. Ingest-side load balancing: agents/collectors on each host are configured with the full set of Kafka broker addresses and rely on Kafka's own partition-leader-aware client routing; a coordinating-node-style ingest layer in front of Elasticsearch load-balances bulk writes across data nodes.
  2. Query-side load balancing: Kibana and any direct API clients route through coordinating nodes (Elasticsearch nodes with no data role, dedicated to fanning a query out to the relevant data nodes/shards and merging results), which both load-balances query fan-out and insulates data nodes from a query-storm caused by an expensive ad-hoc search.
  3. Scrape-target load balancing: for pull-based metrics, service discovery plus consistent-hash sharding of scrape targets across a pool of scraper instances keeps any one scraper's fan-out bounded as the fleet grows.

Scaling to Multiple Regions

  • Regional clusters, not one global cluster: each region runs its own Elasticsearch cluster and Kafka buffer, keeping the vast majority of ingestion and query traffic local and avoiding a single global cluster's blast radius and cross-region latency tax.
  • Cross-cluster search lets a Kibana instance in one region query indices in other regions live, for the rarer “show me this incident across all regions” investigation, without requiring all data to be centrally replicated first.
  • Cross-cluster replication selectively replicates specific indices (e.g. a global services' logs) to a designated DR or reporting region, per the replication section above.
  • Edge aggregation before long-haul shipping: for regions/edge locations with constrained or expensive backhaul bandwidth, pre-aggregate metrics and pre-filter/sample logs and traces locally before shipping only the reduced volume across the long-haul link to a central or regional cluster — this is the same hierarchical-federation idea from the metrics deep dive, applied at the WAN-link level instead of the rack level.

Monitoring, Logging and Analytics

The recursive question — who monitors the monitoring system — has to have a real answer, since this platform is exactly what's relied on during an incident.

  • Self-monitoring: the observability platform emits its own logs, metrics, and traces (Kafka consumer lag, Elasticsearch cluster health, ingest-pipeline error rate, Kibana query latency) into a physically or at least logically separate “meta” cluster/index set, so a failure in the primary cluster doesn't also take down the dashboards showing that it's failing.
  • Alerting on ingestion-pipeline backlog/lag: Kafka consumer lag per topic is the single most important self-monitoring metric — growing lag on the logs topic, for instance, means data is arriving but not yet queryable, silently degrading freshness without an outright outage; alert on lag trend, not just an absolute threshold.
  • Synthetic self-checks: a canary that writes a known synthetic log line/metric/span end-to-end and alerts if it doesn't appear in Kibana within an expected SLA, catching a “the pipeline looks up but nothing is actually flowing” failure mode that infrastructure-level health checks alone would miss.
  • A minimal, independent fallback path: a lightweight, separately-hosted status page or basic metrics view that doesn't depend on the main platform's own Elasticsearch/Kafka, so on-call still has some signal if the main platform itself is the thing that's down.

CAP Theorem Lens

Favor availability for the bulk of reads (a dashboard a few seconds stale, or a query hitting a slightly-behind replica, is a non-issue during normal operation) and for ingestion (never block a host's agent on a strongly-consistent write — Kafka buffering is exactly what lets ingestion degrade gracefully instead of blocking). Favor consistency specifically for cluster-health quorum decisions, where a wrong answer (a false-positive outage page, or worse, a missed real outage) has an outsized cost relative to the small latency of requiring quorum agreement first.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as “and then what?” follow-ups on whatever you draw first.

Why Bundle Four Pillars Into One Platform

Why not just use four separate best-of-breed tools — a tracing vendor, a metrics vendor, a status dashboard, and a log-search tool?
Four silos mean four agents per host, four ingestion pipelines to operate, and — the real cost — an on-call engineer manually correlating a timestamp and trace ID across four disconnected UIs during an incident. A shared spine (agents → Kafka → processing → one Elasticsearch cluster → Kibana) with a common correlation vocabulary turns that manual correlation into a single query.
What actually makes this a "platform" rather than four tools glued together?
The correlation feature: because all four pillars share a timestamp, a service/host identity, and (traces/logs) a trace_id, and all land in the same Elasticsearch cluster, Kibana can pivot from a slow span to its correlated log lines and metric anomalies in one view — a feature that's structurally impossible if the four pillars live in four separate, unrelated storage systems.
Are the four pillars really the same architecture underneath, or just glued together?
Neither — they share the generic spine (agents, Kafka, Elasticsearch, Kibana) but each has genuinely distinct processing logic (tail-sampling for traces, cardinality-aware rollups for metrics, quorum health evaluation, Grok parsing for logs) bolted onto that shared spine, not forced into one identical pipeline.

Distributed Tracing

How does trace context propagate across service hops in different languages/frameworks?
The W3C Trace Context standard traceparent HTTP header (00-trace_id-parent_span_id-flags) is vendor- and language-neutral; every OpenTelemetry-instrumented service reads the incoming header, creates a child span, and forwards a new traceparent with its own span_id as the parent for whatever it calls next.
Why not just sample every trace at a fixed rate (head-based only)?
A fixed sampling rate decided at the start of a trace has no way to know the trace will end in an error or unusual latency, so rare-but-critical traces are dropped just as often as boring ones. Tail-based sampling defers the decision until the full trace (and its outcome) is known, letting you force-keep 100% of errors/slow traces while still downsampling the boring majority — at the cost of buffering every span until each trace completes.
How do you derive a service dependency graph from trace data?
For every parent-child span pair (linked via parent_span_id), emit an edge from the parent's service name to the child's service name, then aggregate edge counts, latency, and error rate over a rolling window — rendered as a live graph in Kibana.

Metrics at Scale

Pull-based (Prometheus) or push-based (statsd) metrics collection — which do you pick?
Both, for different workloads: pull-based scraping for long-running services (a missed scrape is itself a useful "target down" signal, and it's simpler to reason about), push-based for ephemeral jobs and hosts that can't be reliably scraped (e.g. behind restrictive network policy). This platform runs both paths into the same shared spine.
What is cardinality explosion and why is it the #1 real-world metrics failure mode?
Every unique combination of metric name and label values is a distinct time series the store must index in memory; one unbounded label like a raw user_id can turn a manageable 2 million series into 150 billion, which no time-series database's in-memory series index can absorb. It's mitigated by bounding label cardinality by design, aggregating hierarchically before central ingestion, downsampling for long retention, and enforcing hard cardinality caps with alerting.
Counter, gauge, or histogram — how do you decide which metric type to use?
Counter for anything monotonically increasing where you care about rate (total requests served); gauge for a point-in-time value that can go up or down (queue depth, memory used); histogram whenever you need percentiles (p95/p99 latency) rather than just an average, since a bucketed distribution is the only type that can reconstruct percentiles after the fact.

Cluster Health Monitoring

How do you avoid a false-positive outage page from a transient network blip?
Quorum-based health evaluation: multiple independent health-checker instances across different network paths/zones each probe the same targets independently, and only a majority agreement declares a genuine outage — a single checker's transient bad view is outvoted rather than trusted.
Walk me through the red/yellow/green cluster-status model.
Green means every primary and replica shard is allocated and healthy. Yellow means every primary is intact and the cluster is fully readable/writable, but some replicas are missing (e.g. after a single node loss) — degraded fault tolerance, not degraded availability. Red means at least one primary shard is unassigned — genuine data unavailability or loss, and the only status that should page immediately.
Why do you need synthetic canaries if you already have heartbeats and metrics?
Heartbeats and metrics catch infrastructure-level failure (a process died, CPU spiked) but not a process that's alive and returning 200s while silently serving broken behavior (a broken login form, a checkout flow that fails on step 3). Synthetic canaries script real user journeys end-to-end and check actual behavior, catching a class of failure liveness checks structurally can't see.

Log Aggregation

What's the difference between using Filebeat directly to Elasticsearch versus routing through Logstash first?
Filebeat-to-Elasticsearch-ingest-pipeline is lighter weight and sufficient for straightforward parsing (Grok, simple field extraction). Logstash's filter stage is more capable for heavier transformation (joining against external lookups, complex conditional routing, multi-stage enrichment) at the cost of an extra hop and more operational overhead — pick Logstash only when the transformation genuinely needs it.
Why does Index Lifecycle Management matter so much for cost here?
Logs dominate total platform storage by one to two orders of magnitude over traces and metrics combined. ILM automatically ages indices from fast/expensive hot-tier SSD down through warm, cold, and frozen/deleted tiers purely by policy, which is what makes multi-petabyte retention affordable instead of keeping everything on the most expensive tier forever.
Why size shards at roughly 10-50GB instead of very small or very large shards?
Each shard is a full independent Lucene index with real per-shard overhead (file handles, segment metadata, merge cost); too many tiny shards wastes that overhead and bloats cluster state, while too few oversized shards make recovery/rebalancing slow. 10-50GB is the empirically-recommended sweet spot balancing both failure modes.
How does full-text log search stay fast across billions of documents?
The inverted index: for each distinct term, Elasticsearch stores a posting list of the documents containing it. A multi-word search intersects/scores a handful of typically-short posting lists instead of scanning raw text, which is what keeps queries in the low seconds even at petabyte scale.

Cross-Cutting: Sharding, Replication, Security, Scale

Why index-per-day for logs and traces but not for metrics?
Logs and traces are almost always queried over a bounded recent time window, so index-per-day lets a query touch only relevant days and lets ILM/deletion operate on whole indices cheaply. Metrics are typically queried over longer continuous ranges (a week or month of a trend line), so a rollup-tiered time-series data stream fits the access pattern better than daily buckets.
What happens when a data node holding a primary shard is lost?
Elasticsearch automatically promotes an in-sync replica on a surviving node to primary and schedules a new replica elsewhere to restore full redundancy. This is exactly the kind of event that produces a transient yellow cluster status until the new replica finishes catching up.
How do you keep one team's noisy dashboard from degrading the cluster for everyone else?
Coordinating nodes (data-role-free nodes dedicated to query fan-out and result merging) insulate data nodes from query storms, combined with per-role/per-team resource limits on expensive ad-hoc queries.
How would you redact PII before it's ever searchable?
An ingest-pipeline processor (or agent-side filter, ideally as early as possible) pattern-matches known-sensitive fields (emails, card numbers, tokens) and masks/redacts them before the document is indexed — redaction must happen pre-ingestion, since scrubbing already-indexed petabyte-scale data after the fact is impractical.
Who monitors the observability platform itself?
The platform self-monitors by emitting its own logs/metrics/traces into a logically separate meta-cluster, alerts on Kafka consumer lag as the earliest backlog signal, runs synthetic self-checks that verify a known event actually appears end-to-end, and maintains a minimal independent fallback status path that doesn't depend on the main cluster.
How does the platform scale to multiple regions?
Each region runs its own Elasticsearch cluster and Kafka buffer to keep the bulk of traffic local; cross-cluster search enables live cross-region investigation without pre-replicating everything; cross-cluster replication selectively mirrors specific indices to a DR region; and edge locations with constrained bandwidth pre-aggregate/sample locally before shipping the reduced volume onward.

Key Takeaways

Remember
The interesting design problem is the bundling itself: one shared spine (agents/collectors on every host → a durable Kafka buffer → a pillar-specific processing tier → a shared Elasticsearch/OpenSearch store → Kibana) carries all four pillars, with genuinely different processing logic per pillar bolted onto that spine rather than forced into an identical pipeline. Cardinality explosion is the single most common real-world metrics failure mode — know the mitigation chain (bounded labels, hierarchical aggregation, downsampling, hard caps) cold. Tracing lives or dies on context propagation (W3C traceparent) and a defensible sampling strategy (hybrid head+tail). Cluster health must be quorum-based to avoid false-positive outages, and the red/yellow/green model is the standard vocabulary for communicating aggregate status. Logs dominate storage cost, so ILM tiering is the platform's single biggest cost lever. And the feature that actually justifies calling this a "platform" rather than four tools is correlation — a shared timestamp/service/trace_id vocabulary that lets one Kibana view span all four pillars at once.
