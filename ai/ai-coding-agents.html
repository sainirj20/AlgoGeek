AI Coding Agents

Overview

An AI coding agent is qualitatively different from an autocomplete-style assistant. Instead of suggesting the next few lines while you keep typing, it takes a goal stated in plain English, plans an approach, edits real files, runs the code or test suite, reads the results, and keeps iterating until the task is actually done — not just described. This page covers the analogy that makes the distinction click, the step-by-step loop underneath it, a fully worked example showing what that loop looks like on a real feature, and how the major coding agent tools compare.

The Intern Analogy

Imagine a super-capable intern who can actually use your computer — read your files, write code, run it, see if it breaks, and fix it — instead of an intern who can only talk. That's the difference between a regular chatbot and a coding agent. A regular chatbot just talks back to you in text, describing what you should do next. An agent can act: it opens files, edits them, runs your test suite, reads the error messages, and tries again — in a loop — until the task is actually done, not just described.

How an AI Coding Agent Actually Works

Underneath the analogy is a concrete, repeatable loop:

  1. You give it a goal in plain English ("add a dark mode toggle to the settings page").
  2. It reads the relevant files to understand how the codebase is structured.
  3. It makes a plan (which files to touch, in what order).
  4. It edits the code.
  5. It runs the tests (or starts the app) to check its own work.
  6. If something fails, it reads the error and tries again — often several times — before reporting back to you.

Worked Example: The Dark Mode Toggle

Here's what that six-step loop looks like end-to-end on a real request. You type: "Add a dark mode toggle to the settings page, remember the user's choice, and write a test for it."

What a good coding agent actually does
It opens settings.jsx and notices there's already a ThemeContext in the codebase it can reuse rather than inventing a new one. It adds a toggle component that calls into that existing context, and persists the user's choice so it survives a page reload. It writes a test that renders the settings page in both light and dark mode. It runs the test suite — and one test fails because of a missing import. It reads the failure, fixes the import, and re-runs the suite. Only once everything passes does it tell you it's done, attaching a summary of every file it touched.

Notice what makes this different from a single autocomplete suggestion: the agent didn't just produce plausible-looking code once and stop. It read the existing codebase before acting, noticing ThemeContext instead of duplicating it. It produced verifiable output — a real test, not just a claim that dark mode "works." And it caught and fixed its own mistake (the missing import) without you having to spot the failure yourself. That plan → act → observe → self-correct loop, repeated until the tests actually pass, is the core mechanic that separates a coding agent from a chat-only assistant.

Several tools now implement this agentic loop, differing mainly in where they live and what kind of work they're tuned for:

Common Interview Questions

What is agentic AI, and how does it differ from a regular chatbot?
A chatbot responds with text — you ask, it answers, the interaction ends there. An agent takes actions: it can use tools, read and write files, call APIs, and it operates in a loop — plan, act, observe the result, revise — until a goal is actually met, largely without you supervising every step. The key architectural difference isn't that an agent is "smarter" in some abstract sense; it's that it has a tool-use-and-self-correction loop wrapped around the model, instead of being a single input-output exchange. A coding agent is a specific instance of this pattern: instead of just describing a fix, it opens the file, makes the edit, runs the tests, and tries again if something breaks.
How would you design an AI-assisted code review system?
Start with the specific failure mode you're trying to fix — missed bugs, style drift, and slow review turnaround are different problems with different designs — and work backward from that rather than building a generic "AI reviews code" system. A reasonable architecture gives an agent read access to the diff and surrounding repo context, pairs it with a Skill that encodes your team's actual review checklist (security, error handling, test coverage, style conventions), and outputs either a structured report or PR comments. Before trusting it in production, evaluate it against a labeled set of past PRs with known issues so you have a real accuracy baseline rather than a vibe. And keep a human as the final approver — the system's job is to surface issues for a person to weigh, not to auto-merge changes on its own judgment.
Why is "autocomplete" the wrong mental model for what a coding agent does, even though both involve AI writing code?
Autocomplete suggests the next few lines while you keep driving — you're still reading, deciding, and running things yourself line by line. A coding agent is handed a whole task ("add a feature," "fix this failing test") and drives the entire loop itself: it reads the codebase to understand context, plans which files to touch, makes the edits, runs the tests or app to check its own work, and iterates on failures before ever handing control back to you. The intern analogy makes this concrete — it's the difference between an intern who can only talk about what to do, and one who can actually sit at your keyboard, make the change, run it, and fix what breaks.
In the dark-mode-toggle example, the agent's test failed on the first run because of a missing import. Why is that actually a good sign rather than a bad one?
It's evidence the loop is working as intended. The agent didn't just generate code and declare victory — it ran a real test, read the actual failure, diagnosed the cause (a missing import), fixed it, and re-ran the suite before reporting back. A chatbot-only interaction has no equivalent step: it would produce code and text describing that the code works, with no independent check behind that claim. The agent catching its own mistake before you ever saw it is the entire value proposition of the plan → act → observe → self-correct loop — it shifts the burden of catching bugs from you reading every line to the agent verifying its own output against a real test run.
If a team is already standardized on GitHub for code review and CI, which coding agent tool is the most natural fit, and why might a different team choose Claude Code instead?
GitHub Copilot Agent Mode is the natural fit for a GitHub-standardized team since it's built into the IDE/CI workflow they already use, minimizing new tooling to adopt. A team that instead needs deep, multi-file, architectural work — a refactor spanning a whole module, not just a quick in-flow edit — is more likely to reach for Claude Code, which is built for terminal-native, full-autonomy tasks rather than fast day-to-day autocomplete-style edits. Cursor sits in between as an IDE-embedded agent optimized for fast in-flow edits, and Codex/Cline are alternatives with similar autonomous loops in either environment. The right choice depends more on the kind of task (quick edit vs. deep architectural change) and existing toolchain than on raw capability differences between the tools.

Key Takeaways

Remember
A coding agent differs from a chatbot by looping — plan, act, observe, self-correct — until a goal is met, not just replying once in text: the intern who can use the computer, not just talk. The loop is six steps: goal in plain English, read the codebase, plan, edit, run tests, fix and retry on failure. The dark-mode-toggle example shows this isn't hypothetical — reusing existing code (ThemeContext), producing a real test, and catching its own missing-import bug before reporting back are the concrete signs the loop is actually working. Tool choice follows the kind of work: Claude Code for deep multi-file/architectural work, Cursor for fast in-flow edits, GitHub Copilot Agent Mode for GitHub-standardized teams, Codex/Cline as alternatives with similar autonomy.
