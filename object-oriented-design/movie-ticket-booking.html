OBJECT ORIENTED DESIGN

Design a Movie Ticket Booking System

A movie-ticket-booking system reuses the class-modeling shape of the parking-lot problem (a physical resource, a catalog of types, a session lifecycle) but layers on the one thing parking lots mostly don't have: a strict two-phase hold-then-pay reservation with a hard concurrency guarantee — exactly one of two customers racing for the same seat can ever win it. That single requirement is why interviewers love this problem: it forces a genuine state machine (a booking's lifecycle from HELD to CONFIRMED, EXPIRED, or CANCELLED), a scheduling relationship (one movie playing across many halls at many times), and the sharpest atomic-update question of the whole OOD interview loop — seat-hold-as-compare-and-set. Treat it as the template for any "reserve now, pay within N minutes, or lose the hold" problem; the same shape reappears in flight/event-seat booking, hotel-room holds, and restaurant table reservations.

Problem Statement

Design the booking system for a cinema chain: customers browse which movies are playing (or coming soon), pick a specific show — a movie at a specific cinema hall and a specific start time — and select one or more specific seats for that show. Because a physical seat can only ever be occupied by one paying customer, the system's hardest requirement is preventing double-booking: two customers must never both walk away believing they hold the same seat for the same show. A selected seat isn't booked outright; it's held for a short window (e.g. 10 minutes) while the customer pays by card or wallet, and the hold is released automatically if payment doesn't complete in time. A successful payment produces a confirmed booking and a printable/QR ticket; a customer can later cancel, subject to a refund policy. An Admin manages the catalog: movies, scheduled shows, hall layouts, and pricing. Interviewers use this problem to see whether you can design a believable hold/expire state machine, whether your seat-locking design is provably race-free (not just "add a lock" hand-waved away), and whether you notice that "a seat" and "this seat, for this one show, right now" are two different concepts that deserve two different classes.

Requirements

  1. The system lists movies that are currently showing and movies coming soon.
  2. Each movie has multiple shows scheduled across multiple cinema halls (screens) and multiple showtimes.
  3. Each hall has a fixed seating layout: rows of seats, each seat carrying a seat type (Regular, Premium, or Recliner).
  4. A customer selects a specific show and one or more specific seats for that show.
  5. The system must guarantee that no two customers can ever hold or book the same seat for the same show — the hard, non-negotiable requirement this whole design is built around.
  6. A selected seat is held/reserved for a short window (e.g. 10 minutes) while the customer completes payment; if payment doesn't complete within that window, the hold is released automatically so the seat becomes available to someone else.
  7. Payment is accepted by card or wallet.
  8. A successfully paid booking produces a booking confirmation with a printable / QR-code ticket.
  9. A customer can cancel a confirmed booking, subject to a refund policy (e.g. full refund up to N hours before showtime, none after).
  10. Admin can add movies, schedule shows, configure halls/seating layouts, and set pricing.

Actors & Use Cases

Three actors touch the system, and each initiates use cases none of the others can:

  • Customer — browses movies/shows, selects seats, pays, receives a confirmation, and can cancel a booking. The only actor who spends money in this scenario.
  • Admin — configures the catalog: movies, shows, halls, and pricing. Never touches a single customer's booking.
  • System — not a person; the background component that places and releases seat holds, expires unpaid holds once their window elapses, and sends booking confirmations. Modeling it as its own actor keeps "who initiated this" honest: a hold doesn't expire itself, the System does it on a timer, and a seat doesn't lock itself, the System does it in direct response to a customer's seat selection.

Primary use cases: Search Movies / Shows, Select Seats, Hold Seats, Make Payment, Confirm Booking, Cancel Booking, Expire Unpaid Hold, and Manage Show (admin: movies, halls, pricing).

Class Diagram

Figure 2. Cinema —filled diamond→ CinemaHall —filled diamond→ Seat (composition: seats belong to their hall's fixed layout). Show associates Movie and CinemaHall (it references both, owns neither) and is itself —filled diamond→ ShowSeat, one live status record per physical Seat for that showtime. Why two seat-related classes — ShowSeat and BookedSeat — instead of one? It's tempting to add a single occupied/bookedBy field directly on Seat and call it done, but a physical Seat outlives any one Show — the same seat is FREE for tonight's 7pm screening and simultaneously already BOOKED for tomorrow's 2pm screening of a different movie. Status has to be scoped per show, not per seat, which is exactly what ShowSeat is: the single mutable source of truth for "is this physical seat, for this specific show, FREE / HELD / BOOKED right now." It has to be mutable and shared because two different customers' requests race to change the very same row — it's the record the atomic hold operation in the next section updates. BookedSeat, by contrast, is an immutable line-item owned by exactly one Booking — a private receipt of which seat, at what price, that one customer's booking claimed — the same role an OrderItem plays inside an Order elsewhere in this style of design. Collapsing the two into one class creates an ownership contradiction: in UML, composition assumes exactly one owning "whole," and a single record can't simultaneously be owned by the Show that created it and owned by the Booking that claimed it. Splitting them resolves it cleanly: Show owns the live, shared status record; Booking owns its own private snapshot that merely references the ShowSeat rather than owning it.

Key Flow: Concurrent Seat Selection (Sequence Diagram)

This is the flow interviewers care about most for this problem: two customers, A and B, both try to select and hold the same seat for the same show within milliseconds of each other. The design only works if the seat-hold operation is a single atomic, conditional step — never a "check if it's free, then set it to held" pair of steps in application code, because both requests can read "free" before either one writes "held," and both would believe they won.

Figure 4. Sequence diagram: Customer A and Customer B both request the same seat at nearly the same instant. SeatLockService issues one atomic holdIfFree() call per request — each is a single conditional UPDATE, never a separate read-then-write — so exactly one call reports success (1 row affected) and the other reports failure (0 rows affected) with no window in between where both could believe they'd won.

Notice what is not in this diagram: there is no message that reads the seat's status followed by a later message that writes it. holdIfFree(bookingId, ttl) is a single request/response pair from SeatLockService's point of view, and underneath it, a single SQL statement (or a single in-process compare-and-set) from ShowSeat's point of view. Whichever caller's UPDATE the database applies first is the one that sees its WHERE clause still match (status='FREE') and therefore affects exactly one row; by the time the second UPDATE runs, that row's status has already flipped to 'HELD', so its WHERE clause matches zero rows and it fails cleanly. There is no gap for both requests to observe "free" simultaneously, because the check and the write are the same database operation.

Design Patterns Applied

Name the pattern and the forcing function together, not just the name:

  • Singleton (a single Cinema, or a chain-wide BookingService instance) — brief mention only: for a single-venue deployment, one in-memory Cinema/BookingService per running instance is a defensible cardinality match, for the same reason ParkingLot was defensible elsewhere on this site. It's a much weaker fit here than in the parking-lot case, though, since a real cinema chain naturally wants many Cinema instances (one per city) behind a shared BookingService layer — so treat this as "could justify it for one venue," not as the load-bearing pattern of this design.
  • State (BookingStatus: HELD → CONFIRMED / EXPIRED / CANCELLED) — this is the pattern doing real work here. Centralizing legality in a single guarded transitionTo() (backed by an explicit allowed-transitions table) means there's exactly one place that knows a CONFIRMED booking can move to CANCELLED but never back to HELD, and that an EXPIRED booking is a dead end. Scattering if (booking.getStatus() == HELD) checks across the codebase instead would drift out of sync the moment a new status (say, REFUNDED) is added.
  • Strategy (pricing) — Show.priceFor(seatType) is backed by a pricing policy that can vary by seat type and by showtime (a weekday matinee vs. a Friday-night peak-hour show), without ExitPanel-equivalent booking code ever branching on if (isWeekend). A new policy (holiday surcharge, promo code) is a new implementation of the same "price this seat type for this show" contract.
  • Observer (hold-expiry warnings and waitlists) — two independent uses: (1) a Booking in the HELD state publishes a "hold expiring soon" event a minute or two before its timer runs out, and a notification observer pushes a warning to the customer's in-progress checkout page; (2) when a sold-out Show's cancellation frees a seat, ShowSeat/Show publishes a "seat became free" event, and any customer subscribed to that show's waitlist is notified — without ShowSeat needing to know anything about how notifications are delivered.

Code Skeleton

Fields and method signatures only — not a runnable program. ShowSeat.holdIfFree() is the one method worked out in full, since the atomic hold is exactly what interviewers probe on for this problem.

public enum SeatType {
    REGULAR, PREMIUM, RECLINER
}

public enum ShowSeatStatus {
    FREE, HELD, BOOKED
}
public class Seat {
    private final String seatId;
    private final String row;
    private final int number;
    private final SeatType seatType;

    public Seat(String seatId, String row, int number, SeatType seatType) { /* ... */ }

    public SeatType getSeatType() { return seatType; }
}
public class Show {
    private final String showId;
    private final Movie movie;
    private final CinemaHall hall;
    private final Instant startTime;
    private final Map<SeatType, BigDecimal> priceBySeatType;
    private final List<ShowSeat> showSeats;   // one per physical Seat in the hall

    public Show(String showId, Movie movie, CinemaHall hall, Instant startTime,
                Map<SeatType, BigDecimal> priceBySeatType) {
        /* ... also materializes one ShowSeat(FREE) per Seat in hall.getSeats() */
    }

    public BigDecimal priceFor(SeatType type);
    public List<ShowSeat> getShowSeats();
    public Optional<ShowSeat> findShowSeat(String seatId);
}
public class ShowSeat {
    private final Show show;
    private final Seat seat;
    private volatile ShowSeatStatus status;
    private String heldByBookingId;
    private Instant heldUntil;

    /**
     * Atomically claims this seat for {@code bookingId} only if it is currently FREE.
     * In-process this is a guarded compare-and-set; at the DB layer it is ONE
     * conditional UPDATE -- never a separate "read status" then "write status":
     *
     *   UPDATE show_seat
     *   SET status = 'HELD', held_by = ?, held_until = ?
     *   WHERE show_id = ? AND seat_id = ? AND status = 'FREE'
     *
     * Exactly one concurrent caller sees rowsAffected == 1 and wins the hold;
     * every other caller sees 0 rows affected and loses immediately.
     */
    public synchronized boolean holdIfFree(String bookingId, Instant heldUntil) {
        if (status != ShowSeatStatus.FREE) {
            return false;                      // lost the race, or already booked
        }
        this.status = ShowSeatStatus.HELD;
        this.heldByBookingId = bookingId;
        this.heldUntil = heldUntil;
        return true;                           // won the race
    }

    public synchronized boolean confirm(String bookingId) {
        if (status != ShowSeatStatus.HELD || !bookingId.equals(heldByBookingId)) {
            return false;
        }
        this.status = ShowSeatStatus.BOOKED;
        return true;
    }

    public synchronized void release(String bookingId) {
        if (status == ShowSeatStatus.HELD && bookingId.equals(heldByBookingId)) {
            this.status = ShowSeatStatus.FREE;
            this.heldByBookingId = null;
            this.heldUntil = null;
        }
    }

    public boolean isHoldExpired(Instant now) {
        return status == ShowSeatStatus.HELD && heldUntil != null && now.isAfter(heldUntil);
    }

    public ShowSeatStatus getStatus() { return status; }
}
public enum BookingStatus {
    HELD, CONFIRMED, EXPIRED, CANCELLED;

    private static final Map<BookingStatus, Set<BookingStatus>> ALLOWED = Map.of(
        HELD,      EnumSet.of(CONFIRMED, EXPIRED, CANCELLED),
        CONFIRMED, EnumSet.of(CANCELLED),
        EXPIRED,   EnumSet.noneOf(BookingStatus.class),
        CANCELLED, EnumSet.noneOf(BookingStatus.class)
    );

    boolean canTransitionTo(BookingStatus next) {
        return ALLOWED.getOrDefault(this, Set.of()).contains(next);
    }
}

public class Booking {
    private final String bookingId;
    private final Customer customer;
    private final Show show;
    private final List<BookedSeat> bookedSeats;
    private BookingStatus status;
    private final Instant holdExpiresAt;
    private Payment payment;

    public void transitionTo(BookingStatus next) {
        if (!status.canTransitionTo(next)) {
            throw new IllegalStateException(
                "Booking " + bookingId + " cannot move from " + status + " to " + next);
        }
        this.status = next;
    }

    public boolean isHoldExpired(Instant now) {
        return status == BookingStatus.HELD && now.isAfter(holdExpiresAt);
    }

    public BigDecimal totalAmount() {
        return bookedSeats.stream()
                .map(BookedSeat::getPrice)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
public class Payment {
    private final String paymentId;
    private final Booking booking;
    private final PaymentMethod method;     // CARD, WALLET
    private final BigDecimal amount;
    private PaymentStatus status;           // PENDING, SUCCESS, FAILED, REFUNDED
    private String gatewayTransactionRef;

    public void process();                  // calls out to the card/wallet gateway
    public void markSuccess(String transactionRef);
    public void markFailed(String reason);
    public void refund(BigDecimal amount);
}

Extensibility & Edge Cases

  • Group bookings (all-or-nothing). A customer selecting 4 seats together must not end up with 3 held and 1 unavailable. The hold operation has to loop over every requested ShowSeat's holdIfFree() inside a single transaction (or hold in a stable, deterministic seat-ID order to avoid deadlock across concurrent group requests), and if any seat in the group fails to hold, every seat it already holds in that same group must be released immediately — a partial hold is a worse outcome than no hold, since it silently locks out other customers from seats this booking will never actually confirm.
  • Hold expiring while a payment webhook is in flight. A payment gateway's success callback can arrive after the background sweeper has already expired the hold and released the seats. The fix is to make both paths (the expiry sweep and the webhook handler) go through the same guarded Booking.transitionTo()/ShowSeat.confirm(): whichever one runs first wins the transition, and the loser's attempted transition is simply illegal and rejected (HELD→EXPIRED already happened, so a late CONFIRMED transition throws) rather than silently double-processing. A late-arriving "payment succeeded" against an already-expired booking should trigger an automatic refund, not a confirmed booking for seats that may have already been re-sold.
  • Dynamic / peak pricing. Because pricing is already a Strategy behind Show.priceFor(seatType), adding surge pricing for a blockbuster's opening weekend, or a lower matinee rate, is a new pricing policy plugged in at Show-creation time — Booking, BookedSeat, and Payment don't change at all.
  • Waitlists for sold-out shows. A customer can join a per-Show waitlist when no seats of their preferred type remain. When a Booking transitions to CANCELLED (or a hold expires) and its seats become FREE again, the Observer mechanism used for hold-expiry warnings fires a "seat available" event that the waitlist service consumes, notifying waitlisted customers in FIFO order — the same decoupled pattern as a library's reservation-queue notification, just triggered by cancellation instead of a return.

Follow-up Interview Questions

Walk through, in detail, exactly how the atomic seat-hold prevents two customers from double-booking the same seat.
The naive, broken version does two separate steps in application code: read ShowSeat.status, check it equals FREE, then write status = HELD. Between the read and the write there is a window where a second concurrent request can also read FREE, because the first request hasn't written yet. Both requests then believe they've won. The fix collapses "check" and "set" into one indivisible operation: a conditional UPDATE such as UPDATE show_seat SET status='HELD', held_by=?, held_until=? WHERE show_id=? AND seat_id=? AND status='FREE', executed by the database as a single atomic statement, with the caller inspecting the affected-row count rather than a separately-read status flag. The database serializes concurrent writers to the same row internally, so exactly one UPDATE's WHERE clause still matches 'FREE' at the moment it executes and affects 1 row; the other UPDATE runs against a row that already reads 'HELD' and affects 0 rows. The loser is told immediately and definitively that the seat is gone — there is no ambiguous state and no window where both requests could have succeeded.
Why does a group booking of multiple seats need to be all-or-nothing, and how would you implement that?
If a customer requests seats A, B, and C together and the system holds A and B but fails on C (already taken), leaving A and B held is worse than failing the whole request: those two seats are now locked away from every other customer for the full hold window even though this booking can never actually be confirmed without seat C. The fix is to treat the whole group as one atomic unit: attempt holdIfFree() on every requested ShowSeat, and if any single call returns false, immediately call release() on every ShowSeat that did succeed in this same request before returning failure to the customer. To avoid deadlock when two different group requests contend for overlapping seats, hold in a fixed, deterministic order (e.g. sorted by seatId) across all requests, or wrap the whole group's holds in a single database transaction so the rollback is automatic on any failure.
How is the hold-expiry timer actually implemented — a background sweeper or checking expiry lazily on read?
Both approaches are used together in practice, because each covers the other's blind spot. A background sweeper (a scheduled job scanning for HELD bookings/ShowSeats whose holdExpiresAt has passed) guarantees that seats get released even if nobody ever looks at that booking again — important because an abandoned checkout tab never triggers a lazy check on its own. Lazy expiry-check-on-read (calling isHoldExpired(now) whenever a seat or booking is touched, e.g. right before attempting to confirm payment) guarantees correctness at the exact moment it matters even if the sweeper hasn't run yet, since sweepers typically run on an interval (say, every 30 seconds) and can't promise instantaneous expiry. Relying on the sweeper alone risks a payment confirming against a seat that's technically past its window but hasn't been swept yet; relying on lazy checks alone risks seats sitting held indefinitely if nothing ever reads them again. Using both, with the guarded transitionTo()/holdIfFree() logic as the single source of truth either path goes through, means whichever one notices the expiry first wins and the seat is released exactly once.
This is all in-memory/single-process reasoning. How would this seat-locking idea actually be built in a real, horizontally-scaled production system?
The OOD-level idea — an atomic conditional claim on a shared record — maps directly onto two well-known HLD building blocks. Most commonly, it becomes a distributed lock in Redis: SET seat:{showId}:{seatId} bookingId NX PX 600000 atomically claims the seat only if the key doesn't already exist (NX), with a built-in TTL (PX) that handles hold expiry automatically without a separate sweeper. Alternatively, it stays as a row in a relational database with the same conditional-UPDATE-plus-affected-row-count technique shown above, relying on the database's own row-level locking and transaction isolation to serialize concurrent writers, with a TTL column plus a sweeper (or a database job) handling expiry. Either way, this page deliberately stops at "here's the object model and the concurrency contract it must satisfy" rather than going further into which of those two you'd pick, how you'd shard by showId, or how you'd handle a Redis failover — that's a different, HLD-level conversation, and recognizing that boundary out loud is itself a good signal in the interview.
Why model Seat and ShowSeat as two different classes instead of just putting an "occupied" flag on Seat?
A physical Seat's identity (which row, which number, which seat type) is stable across every show ever screened in that hall, but its booking status is not — the same seat is FREE for tonight's 7pm show and BOOKED for tomorrow's 2pm show of a different movie. Status has to be scoped per (Show, Seat) pair, not per Seat alone, or you'd need one Seat object per showtime, which duplicates the hall's physical layout data unnecessarily. ShowSeat exists precisely to hold that per-show status (and the hold-expiry timestamp, which is meaningless without a specific show's timer) while Seat stays a simple, reusable description of the physical seat itself.
Why use the State pattern (a guarded transitionTo()) for BookingStatus instead of a plain enum with scattered if/else checks?
Centralizing legality in one place (the ALLOWED transition table plus transitionTo()) means there's exactly one source of truth for "can a HELD booking become CONFIRMED" or "can a CANCELLED booking ever come back to HELD" (no), rather than that logic being reimplemented, and inevitably drifting inconsistent, at every call site that happens to touch a booking's status — the payment webhook handler, the expiry sweeper, and the cancellation endpoint would each need their own copy of the rules otherwise. It's also far easier to unit test exhaustively (enumerate every from/to pair) and to extend safely when a new status like REFUNDED is added later.
Why does Strategy fit the pricing logic better than hardcoding the price in the Show class?
Ticket pricing realistically varies along more than one axis at once — seat type, day of week, time of day, and eventually promotions or dynamic demand-based pricing for a blockbuster's opening weekend. If that logic is hardcoded as conditionals inside Show, every new pricing rule means editing and re-testing a class that has nothing to do with pricing policy. Making pricing an interchangeable strategy behind a single "price this seat type for this show" contract lets a new policy be added as a new implementation, with Show, Booking, and Payment completely untouched.
Where does the Observer pattern show up in this design, and why not just call the notification code directly?
Two places: warning a customer that their held seat is about to expire, and notifying a waitlisted customer when a cancellation frees up a seat on a sold-out show. In both cases, the class that detects the event (ShowSeat/Booking for expiry, ShowSeat for a freed seat) has no business knowing how a customer gets notified — email, push notification, and SMS can each subscribe independently, and a new channel is a new observer, not a new branch inside ShowSeat. Calling notification code directly from ShowSeat would also make ShowSeat's atomic hold logic much harder to reason about and test, since a class responsible for a concurrency-critical operation would suddenly also own I/O to third-party notification services.
How does cancellation and the refund policy fit into the BookingStatus state machine?
Cancellation is a CONFIRMED → CANCELLED transition (the ALLOWED table above permits it), triggered by the customer. The refund amount is a policy question separate from the state transition itself — e.g. a RefundPolicy strategy that looks at how far before showtime the cancellation happens (full refund beyond N hours, partial or none inside that window) and returns an amount for Payment.refund() to apply. Keeping refund-policy logic out of Booking.transitionTo() itself matters: the state machine should only ever answer "is this transition legal," not "how much money moves" — mixing the two would make the transition table's unit tests entangled with pricing/refund business rules that change independently.
What happens if a customer's payment fails after their seats were successfully held?
A failed payment must not leave the seats held indefinitely: Payment.markFailed() should trigger an immediate ShowSeat.release() and a Booking.transitionTo(CANCELLED) (or, more precisely, a rejection back to an unheld state) rather than waiting for the hold-expiry timer, so the seats become available to other customers right away instead of sitting locked for the remainder of the original window. This is a different, "fail fast" trigger for the same release() path the expiry sweeper uses — both should go through the same guarded, idempotent release operation so a retried or duplicate "payment failed" webhook can't double-release (or, worse, release a seat that a subsequent request already re-held for someone else).

Key Takeaways

Key Takeaways
  • The whole problem hinges on one atomic operation: holdIfFree() as a single conditional UPDATE (compare-and-set), never a separate check-then-write — that's what actually prevents double-booking, not "add a lock" hand-waved away.
  • Split seat status into two classes: ShowSeat (the live, per-show, mutable status the atomic hold touches) and BookedSeat (an immutable, Booking-owned line-item snapshot) — collapsing them creates a composition-ownership contradiction.
  • BookingStatus is a real State-pattern candidate, not a decorative enum: HELD → CONFIRMED / EXPIRED / CANCELLED with a guarded transitionTo() is what keeps the expiry sweeper, the payment webhook, and the cancellation endpoint from disagreeing about what's legal.
  • Group bookings must hold seats all-or-nothing — a partial hold silently locks out other customers from seats that booking will never confirm.
  • Pricing as a Strategy is what lets peak-hour pricing, a promo, or a seat-type surcharge land without touching Booking, BookedSeat, or Payment.
