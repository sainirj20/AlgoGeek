OBJECT ORIENTED DESIGN

Basics of OO Design

Almost every Low-Level Design (LLD) interview — "design a parking lot," "design a library management system," "design an elevator system" — is really testing two things at once: can you think in objects (classes, responsibilities, relationships), and can you communicate that thinking quickly using a shared notation (UML)? This page is the foundation the other case-study pages in this section assume you've already read, so it's worth going through slowly, once, end to end.

Object-Oriented Basics

Object-oriented programming rests on four pillars. Interviewers rarely ask you to define them from a textbook — they ask you to show them in the design you're building. Below is each pillar with a minimal Java example.

Abstraction

Abstraction means exposing only the essential behavior a caller needs, and hiding how that behavior is implemented. In Java, interfaces (and abstract classes) are the primary tool: the caller depends on PaymentMethod, not on the messy details of talking to a card network.

// Abstraction: callers depend on "what", not "how"
public interface PaymentMethod {
    void pay(BigDecimal amount);
}

public class CreditCardPayment implements PaymentMethod {
    @Override
    public void pay(BigDecimal amount) {
        // handles network auth, retries, etc. -- caller never sees this
        System.out.println("Charging card: " + amount);
    }
}

Encapsulation

Encapsulation bundles data with the operations that are allowed to touch it, and hides the data behind a controlled interface so invariants can't be violated from the outside.

public class BankAccount {
    private BigDecimal balance; // hidden internal state

    public void deposit(BigDecimal amount) {
        if (amount.signum() <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }
        balance = balance.add(amount);
    }

    public BigDecimal getBalance() {
        return balance; // controlled read access, no direct field access
    }
}

Inheritance

Inheritance lets a subclass reuse and specialize the state/behavior of a parent class, modeling a genuine "is-a" relationship.

public class Employee {
    protected String name;
    protected BigDecimal baseSalary;

    public BigDecimal calculatePay() {
        return baseSalary;
    }
}

public class Manager extends Employee {
    private BigDecimal bonus;

    @Override
    public BigDecimal calculatePay() {
        return baseSalary.add(bonus);
    }
}

Polymorphism

Polymorphism lets code written against a common supertype invoke behavior whose exact implementation is chosen at runtime based on the object's actual type.

public abstract class Shape {
    public abstract double area();
}

public class Circle extends Shape {
    private final double radius;
    public Circle(double radius) { this.radius = radius; }
    @Override public double area() { return Math.PI * radius * radius; }
}

public class Square extends Shape {
    private final double side;
    public Square(double side) { this.side = side; }
    @Override public double area() { return side * side; }
}

// Runtime polymorphism: the JVM picks the right area() for each element
List<Shape> shapes = List.of(new Circle(2), new Square(3));
for (Shape s : shapes) {
    System.out.println(s.area());
}

Classes vs. Objects

A class is the blueprint — it defines what attributes and behavior every instance will have (Car). An object is a concrete instance of that blueprint living in memory at runtime, with its own state (myRedCivic, an instance of Car with color = "red"). In an interview, when you say "the classes in this design are...", you're describing the blueprint layer; when you walk through a scenario ("the user creates an order..."), you're describing objects interacting at runtime.

Composition vs. Inheritance

Both let one class reuse another's behavior, but they do it very differently. Inheritance says "I am a kind of you" (Car extends Engine would be wrong — a car is not a kind of engine). Composition says "I have one of you and delegate to it":

// Favor composition: a Car HAS-A Engine, it doesn't extend Engine
public class Engine {
    void start() { System.out.println("Engine starting..."); }
}

public class Car {
    private final Engine engine; // composed, not inherited

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.start(); // delegate to the composed object
    }
}

"Favor composition over inheritance" is one of the most repeated pieces of LLD-interview advice, and for good reason:

  • It avoids the fragile base class problem. A change to a parent class's internals can silently break every subclass that depends on it, even years later and even if the subclass author never touches that code.
  • Java only allows single inheritance of classes. Once you extend one class, that slot is used up. Composition has no such limit — you can compose as many collaborators as you need.
  • Composition keeps behavior swappable at runtime. Pass in a different Engine implementation (electric vs. combustion) without touching Car at all — you can't swap a parent class at runtime the same way.
  • It keeps coupling shallow. A composed object only needs to honor its interface; an inherited subclass is coupled to everything the parent does internally, not just its public contract.

The practical rule of thumb: reach for composition (and interfaces) by default; reach for inheritance only when there is a genuine, stable "is-a" relationship that isn't likely to change (e.g., Car is-a Vehicle).

OO Analysis and Design

Object-Oriented Analysis and Design (OOAD) is the repeatable process that takes you from a fuzzy prompt ("design a library management system") to a concrete class diagram. In an interview, narrating this process out loud is itself a signal — it shows you have a method, not just memorized diagrams for common problems.

  1. Gather requirements. Read (or ask for) the prompt closely. Separate functional requirements (what the system must do — "members can check out books") from non-functional requirements (how well it must do it — expected scale, consistency, latency). Ask 2–3 clarifying questions before writing a single class name.
  2. Identify nouns and verbs as candidate classes and methods. Underline the nouns in the requirements — they're candidate classes (Book, Member, Librarian, Loan). Underline the verbs — they're candidate methods or responsibilities (checkOut, returnBook, reserve).
  3. Define responsibilities per class (CRC-card thinking). For every candidate class, ask: what does this class know (its data) and what does this class do (its behavior)? Just as important — who does it collaborate with to get its job done? Class-Responsibility-Collaborator (CRC) cards formalize exactly this: one index card per class, split into a "Responsibilities" column and a "Collaborators" column. You don't need literal cards in an interview, but thinking in these three buckets keeps you from either dumping everything into one god-class or fragmenting responsibilities so far that no class does anything meaningful.
  4. Identify relationships between classes. Once responsibilities are roughed out, decide how classes relate: association, aggregation, composition, inheritance, or dependency (see the table just below — this is one of the most commonly interview-tested distinctions in all of OOD).
  5. Apply SOLID principles to validate and refine the design. Use Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion as a design smell-test — if a class violates one, that's usually a sign a responsibility needs to move or split.
  6. Iterate. Sketch the class diagram, then walk through two or three concrete scenarios end to end (this is exactly what a sequence or activity diagram is for). Every gap you find during the walkthrough feeds back into steps 3–5. Real designs converge after 2–3 passes, not one.

Association vs. Aggregation vs. Composition

These three are frequently confused, and getting them backwards is one of the fastest ways to lose credibility in an LLD interview. The distinguishing question is always: does the "part" object's lifecycle depend on the "whole"?

RelationshipMeaningLifecycleExample
Association A general "uses" / "knows about" link between two otherwise independent classes — no ownership implied Neither object owns the other; both exist and are destroyed independently A Driver drives a Car — the driver holds a reference to a car, but a car can exist without that particular driver and a driver can exist without that particular car
Aggregation A "has-a" whole-part relationship, but ownership is weak — the part can exist independently of the whole The part can outlive the whole A Car aggregates an Engine — if the car is scrapped, the engine can be pulled out and reused in another car
Composition A strong "owns-a" whole-part relationship — the part's lifecycle is bound to the whole The part is destroyed along with the whole A House is composed of Rooms — if the house is demolished, its rooms cease to exist too

What is UML?

UML (Unified Modeling Language) is a standardized notation for visualizing, specifying, and documenting the design of a software system. It is deliberately not a methodology or a process — that's what OOAD (above), Agile, or RUP are for. UML is just the shared vocabulary and drawing convention you layer on top of the OOAD process once you've worked out the classes, responsibilities, and relationships.

In an interview, the value of UML isn't "did you memorize the spec." A good UML sketch on a whiteboard or in a doc lets an interviewer follow your design in seconds instead of you narrating a wall of prose, and it forces you to be precise about relationships — which itself is a strong signal of design maturity. Getting comfortable freehand-sketching the four diagram types below is one of the highest-leverage things you can practice for LLD rounds.

DiagramCategoryWhat it shows
Use Case DiagramBehavioralWho (actors) can do what (use cases) with the system, and where the system's boundary sits
Class DiagramStructuralThe static shape of the design — classes, attributes, operations, and how classes relate to each other
Activity DiagramBehavioralWorkflow / control flow through a process, including branches and parallel steps
Sequence DiagramBehavioralThe runtime order of messages exchanged between specific objects for one concrete scenario

UML defines several other diagram types — Component, Deployment, State Machine, and Object diagrams among them — but they come up far less often in a 45-minute LLD interview, so this page focuses on the four above.

Use Case Diagrams

A use case diagram captures who can do what with the system, at a black-box level — it deliberately says nothing about classes or implementation.

  • Actors are roles that interact with the system, drawn as labeled boxes (or stick figures) outside the system boundary. A primary actor initiates a use case to achieve a goal (a Member checking out a book). A secondary actor supports a use case but doesn't initiate it (an SMS gateway the system notifies).
  • Use cases are ovals representing one discrete, goal-oriented interaction between an actor and the system, named as a verb phrase (Check-out Book, not Book).
  • System boundary is the rectangle drawn around the use cases — everything inside it is "the system we're designing"; actors always sit outside it.
  • <<include>>: use case A always incorporates the full behavior of use case B as a mandatory step. B is factored out because several use cases share it — e.g. Check-out Book «include» Verify Membership.
  • <<extend>>: use case A optionally incorporates the behavior of use case B under some condition. B is an optional add-on that only sometimes runs — e.g. Check-out Book «extend» Apply Late-Fee Waiver, only if the member happens to have a waiver on file.

The distinction to keep straight: include is mandatory and always executed; extend is conditional and optional.

Library System use case diagram: the Librarian searches the catalog and adds new books; the Member searches the catalog, checks out books, and returns them. Plain lines (no arrowheads) show a simple association between an actor and a use case.

Class Diagram

A class diagram is the structural backbone of an OOD interview — it's usually the first thing you draw and the artifact everything else (sequence/activity walkthroughs) refers back to.

Each class is drawn as a box with three compartments: the class name on top (italicized if the class is abstract), attributes in the middle (visibility name: Type), and operations on the bottom (visibility name(params): ReturnType). Visibility uses fixed symbols: + public, - private, # protected, ~ package/default.

The relationship arrows are where most candidates get tripped up — be exact about these:

  • Association — a plain solid line, no special arrowhead. Two classes simply know about each other.
  • Inheritance / Generalization — a solid line with a hollow (unfilled) triangle arrowhead pointing at the parent/superclass. Triangle = "is-a."
  • Interface realization — the same hollow triangle arrowhead, but on a dashed line, pointing at the interface being implemented.
  • Aggregation — a solid line with a hollow (unfilled) diamond sitting at the "whole" end. Diamond = "has-a," weak ownership.
  • Composition — a solid line with a filled (solid) diamond at the "whole" end. Same "has-a" shape as aggregation, but the fill signals strong ownership.
  • Dependency — a dashed line with a plain, open (stick, not filled) arrowhead. One class temporarily uses another — e.g. as a method parameter or local variable — without holding a permanent reference to it.

The gotcha to remember: candidates very commonly swap the hollow triangle (inheritance) with the hollow diamond (aggregation) because both are "hollow" shapes. Triangle always means "is-a" and always points at the parent class; diamond always means "has-a" and always sits at the whole. And within the diamond family, solid-vs-hollow is exactly the composition-vs-aggregation distinction from the table above.

Car and Motorcycle inherit from the abstract Vehicle class — hollow triangles point up at the parent. Garage has a composition relationship to Vehicle: the filled diamond sits on Garage (the "whole"), showing a Garage owns the lifecycle of the Vehicles inside it.

Activity Diagrams

An activity diagram models workflow / control flow — it reads like a flowchart and intentionally says nothing about which object does the work (that's what a sequence diagram is for).

  • Start node — a filled circle marking where the flow begins. Exactly one per diagram.
  • Activity / action — a rounded rectangle representing one step of work.
  • Decision — a diamond with one incoming edge and multiple outgoing edges, each labeled with a guard condition ([yes] / [no]).
  • Fork / join — a heavy bar that splits one flow into multiple concurrent flows (fork), and later merges them back into one (join). Not needed for a simple linear-with-a-branch flow like the one below, but common once you model parallel steps (e.g., charging a payment and reserving inventory at the same time).
  • End node — a filled circle with an outer ring, marking a path's termination. A diagram can have more than one end node, one per terminating path.
Checking out a library book: after scanning the barcode, a single decision diamond branches into a happy path (create the lending record, update status) and an unhappy path (show an error / offer a reservation), each ending at its own end node.

Sequence Diagrams

Where a class diagram shows the static shape of a design, a sequence diagram shows one specific scenario playing out over time — exactly the artifact for answering "walk me through what happens when a member checks out a book."

  • Lifeline — a vertical dashed line hanging below each participant's box, representing that object's timeline for the duration of the scenario.
  • Activation bar — a thin rectangle on a lifeline showing the span during which that object is actively executing (on the call stack).
  • Synchronous message — a solid line with a solid, filled arrowhead. The caller blocks and waits for the callee to finish, exactly like a normal Java method call.
  • Asynchronous message — a solid line with an open/stick arrowhead. The caller fires the message and continues immediately without waiting — e.g. publishing an event to a queue.
  • Return message — a dashed line with an open arrowhead, drawn going back up the same path after the callee finishes. Often optional to draw for void methods, but good practice when you want to show what's handed back.

Interviewers reach for sequence diagrams because a class diagram alone hides ordering: it tells you what exists, not what happens first, what's synchronous vs. fire-and-forget, or where a timeout or retry would need to live. A sequence diagram forces you to narrate the runtime interaction, one concrete scenario at a time — which is usually where hidden edge cases surface.

Member checks out a book: solid arrows with filled heads are synchronous calls; dashed arrows with open heads are returns unwinding back up the same chain, Account → BookLending → LibraryController → Member.

Follow-up Interview Questions

Why prefer composition over inheritance?
Inheritance couples a subclass to a parent's internal implementation, not just its public contract, so a change deep in the parent can silently break subclasses (the fragile base class problem). Java also only allows single inheritance of classes, so one "extends" slot is all you get. Composition avoids both problems: a composed object only needs to honor its interface, you can compose as many collaborators as you like, and you can swap the composed object at runtime (e.g., a different Engine implementation) without touching the class that uses it.
What's the difference between aggregation and composition, with an example?
Both are "has-a" whole-part relationships; the difference is lifecycle ownership. Aggregation is weak ownership — the part can outlive the whole, e.g. a Car aggregates an Engine, and the engine can be removed and reused in another car. Composition is strong ownership — the part's lifecycle is bound to the whole, e.g. a House is composed of Rooms, and demolishing the house destroys the rooms too. In UML, aggregation draws a hollow diamond at the whole; composition draws a filled diamond at the whole.
When would you reach for a sequence diagram vs. an activity diagram in an interview?
Use an activity diagram when you're describing a workflow or business-process logic and don't need to say which object does each step — good for showing branches like "book available? yes/no." Use a sequence diagram when the interviewer asks you to walk through a specific runtime scenario across your actual classes/services — it shows exactly which object calls which, in what order, and whether each call is synchronous, asynchronous, or a return.
What's the difference between an interface and an abstract class, and when would you use each?
An interface defines a pure contract ("can-do") with no state and no constructors, and a class can implement as many as it needs — use it for a capability shared across otherwise unrelated classes (Comparable, PaymentMethod). An abstract class can hold shared state and a mix of concrete and abstract methods, but a class can extend only one — use it for a true "is-a" hierarchy that shares real implementation (Vehicle → Car, Motorcycle).
How do the four pillars of OOP show up in a real class design, not just in theory?
Abstraction shows up as the interfaces/abstract classes you design against (PaymentMethod) instead of concrete implementations. Encapsulation shows up as private fields with validated public methods (a BankAccount that never lets balance go negative through its own API). Inheritance shows up in genuine "is-a" hierarchies with shared behavior (Manager extends Employee). Polymorphism shows up whenever you write code against a supertype and let the runtime pick the right override — e.g. iterating over a List<Shape> and calling area() without an if/else on type.
What does <<include>> vs <<extend>> mean in a use-case diagram and when would you use each?
«include» factors out behavior that is always executed as a mandatory part of another use case — use it when several use cases share the exact same required sub-behavior (e.g. every check-out must verify membership). «extend» factors out behavior that only optionally runs under some condition — use it for add-on behavior that doesn't always apply (e.g. applying a late-fee waiver only if the member has one).
What's the difference between association and dependency?
Association is a structural, typically longer-lived relationship — one class holds a field/reference to another (a Driver holding a reference to a Car). Dependency is a much weaker, transient "uses" relationship — one class uses another only within the scope of a single method call, e.g. as a parameter or local variable, without keeping a reference around afterward. In UML, association is a solid line; dependency is a dashed line with an open arrowhead.
How do you decide what should be a class vs. an attribute vs. a method when doing OOAD from a prompt?
Follow the noun/verb heuristic from the OOAD process, then refine with a question: does this concept have its own identity, state, and behavior worth tracking independently (a class, like Loan), or is it just a property of something else (an attribute, like a book's isbn), or is it an action a class performs (a method, like checkOut())? A good tell that something should be promoted from an attribute to its own class: it starts needing its own lifecycle, its own relationships to other classes, or multiple attributes/behaviors of its own (e.g. a plain dueDate field growing into a full Loan class once you also need to track who checked the book out and any late fees).
What does the hollow triangle vs. hollow diamond distinguish, and why do candidates mix them up?
They look superficially similar (both are unfilled outline shapes at the end of a line) but mean very different relationships: a hollow triangle is inheritance/generalization ("is-a"), always pointing at the parent class; a hollow diamond is aggregation ("has-a," weak ownership), always sitting at the whole. Candidates mix them up because both are "hollow," but the shape is the signal that matters — triangle for is-a, diamond for has-a — not just whether it's filled or not.

Key Takeaways

Key Takeaways
Every LLD interview runs the same loop: gather requirements, find candidate classes/methods from nouns/verbs, assign responsibilities (think CRC cards), pin down relationships (association/aggregation/composition/inheritance/dependency), sanity-check with SOLID, and iterate by walking through scenarios. UML is just the notation for communicating that thinking — a class diagram for static structure, use case diagrams for actor-level scope, and activity/sequence diagrams for runtime behavior. Favor composition over inheritance by default, be exact about which arrowhead means what (triangle = is-a, diamond = has-a, filled vs. hollow = strong vs. weak ownership, dashed vs. solid = temporary vs. structural), and you'll be ready for the 16 case studies that follow.
