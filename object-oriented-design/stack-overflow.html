OBJECT ORIENTED DESIGN

Design Stack Overflow

A low-level design (LLD) deep dive and interview study guide: requirements first, then actors and use cases, class design, key flows as activity/sequence diagrams, the design patterns actually doing the work, a Java code skeleton, extensibility/edge cases, and follow-up interview questions.

Problem Statement

Design the object model behind a Q&A site like Stack Overflow: members post questions with a title, body, and tags; other members post answers; anyone can comment on a question or an answer; members vote answers and questions up or down, which feeds a reputation system; the question's author can mark exactly one answer "accepted"; questions are organized and discoverable by tag and keyword search; and a moderation layer can close, delete, or edit any post. Low reputation restricts what a member can do (no downvoting, no editing other people's posts) until they've earned enough standing in the community.

Interviewers reach for this problem because it packs almost every classic OOD lever into one small domain. Question and Answer are obviously "the same kind of thing" — both have a title/body, both accumulate votes and comments — which is a clean, realistic trigger for "should these share a superclass?" A Vote needs to point at either a Question or an Answer, which is a textbook case for a polymorphic association typed against a shared abstraction rather than two near-identical Vote classes. Reputation is state that changes constantly, needs an audit trail, and gates behavior — a good excuse to talk about event sourcing-flavored design even in a "plain OOP" interview. And moderation, badges, and notifications are all reactions to things that already happened elsewhere in the system, which is exactly what the Observer pattern is for. The rest of this page works through the requirements, the actors, the class model, two representative flows (posting + voting, and accepting an answer), the patterns in play, and a Java skeleton you could plausibly extend live in an interview.

Requirements

  1. Members can post questions with a title, a body, and one or more tags.
  2. Members can post answers to any existing question.
  3. Members can post comments on a question or on an answer.
  4. Members can upvote or downvote a question or an answer; a vote affects the target post's author's reputation.
  5. The question's author — and only the question's author — can mark exactly one answer to their question as "accepted."
  6. Questions can carry one or more tags, and members can search or browse questions by tag.
  7. Members can search across questions by free-text keyword as well as by tag.
  8. Members earn badges and reputation points based on their activity (answers accepted, upvotes received, questions asked, etc.).
  9. Low-reputation members have restricted privileges — they cannot downvote and cannot edit other members' posts — until their reputation crosses defined thresholds.
  10. Moderators can close, delete, or edit any post, regardless of who authored it or how much reputation the moderator has.

Actors & Use Cases

Four actors interact with the system, and one of them — Moderator — is best modeled as a specialization of another, which is exactly the kind of actor generalization UML use-case diagrams (and, later, our class diagram) call out explicitly rather than duplicating.

  • Member. The default authenticated actor. Asks questions, answers questions, comments, votes, and (if they authored the question) accepts an answer.
  • Moderator. A Member with elevated privileges: close, delete, or edit any post, and ban members. Everything a Member can do, a Moderator can also do — hence the generalization arrow from Moderator to Member in the diagram below, rather than a parallel, unrelated actor.
  • Admin. Manages site-level configuration that isn't tied to any one post — creating/merging tags, site config.
  • System. Not a human at all — the automated actor standing in for background processes: recomputing reputation, awarding badges, and keeping the search index current. Modeling this as a first-class actor is deliberate: it's a reminder that "who triggers this use case" isn't always a person, and it keeps those responsibilities visible in the use-case model instead of silently bolted onto whichever class happens to be handy.

Class Diagram

The single most important decision in this design is making Post an abstract superclass of both Question and Answer. Both need a title, a body, a vote count, and a list of comments — without a shared supertype, that's two parallel copies of the same fields and the same "add a comment" / "apply a vote" logic, and Comment and Vote would each need two variants (one for Question, one for Answer) or an awkward union type. With Post in place, Comment and Vote each work against one abstract type, and Question and Answer only add what's actually unique to them: Question owns tags and the accepted-answer pointer; Answer owns its accepted flag and a back-reference to its question.

Figure 2. Class diagram: Post is the abstract shared supertype of Question and Answer; Question composes Answer and Comment; a single Vote class associates to both Member and the abstract Post; Moderator specializes Member.

Notice that Vote only needs one association — to Post, not to Question and separately to Answer — because polymorphism does the dispatching. Code that tallies votes, computes a score, or renders "12 votes" next to a post never needs an if (post instanceof Question) branch; it just calls methods on the Post reference it was handed.

Key Flow: Posting an Answer and Voting (Activity Diagram)

Two independent activities happen constantly and in parallel on a live Q&A site: someone posts an answer, and (separately, possibly for a completely different post) someone casts a vote. Neither waits on the other, so it's natural to lay them out as two lanes rather than one long sequential flow. Both flows share a shape worth noticing: validate first, branch on a guard, and only then mutate state — reject-fast, mutate-last.

Figure 3. Activity diagram: posting an answer (left lane) validates before saving; casting a vote (right lane) checks the voter's reputation against a direction-specific threshold before it's recorded.

Key Flow: Accepting an Answer (Sequence Diagram)

Accepting an answer looks like a one-line state change — question.acceptedAnswerId = answerId — but it's actually the flow with the most invariants to protect: only the question's author may do it, and only one answer per question may ever be accepted at a time. That second rule is exactly the kind of thing worth showing explicitly as a guard in a sequence diagram, because "just remember to check it" is how that invariant quietly breaks six months later when someone adds a new code path.

Figure 4. Sequence diagram: accepting an answer is gated by an alt fragment that enforces the invariant that a question can have at most one accepted answer.

Design Patterns Applied

  • Shared supertype / Composite-flavored design (Post). Post isn't a literal Composite (there's no recursive tree of parts here), but it borrows Composite's core idea: give client code — Comment, Vote, the search indexer, the reputation service — one abstract type to program against so it never has to branch on "is this a Question or an Answer?" The risk to watch for: resist bolting question-only or answer-only fields onto Post just because it's convenient; the moment Post starts accumulating fields only half its subclasses use, the abstraction has leaked.
  • Observer (Notification). A new answer, a new vote, and an accepted answer are all events that some other part of the system (Notification) cares about without the Question/Answer/Vote classes needing to know who's listening or how they're told. The subject (say, QuestionService) maintains a list of listeners and fires events; Notification is just one listener today, but badge-awarding and search re-indexing are naturally other listeners on the same events tomorrow.
  • Strategy (reputation scoring). Different events award different reputation deltas — +10 for an upvote received, +15 for an accepted answer, -2 for a downvote cast against the voter, and so on. Encoding that as a Map<ReputationReason, ReputationRule> of interchangeable strategies (each a score(ReputationEvent): int) keeps ReputationService.apply(...) free of a long, ever-growing if/else chain, and lets you tune or A/B test point values without touching core logic.
  • Chain of Responsibility (extension idea). Not required by the base problem, but a natural next step for moderation: run a new post through a chain — SpamFilterHandler → RateLimitHandler → ContentPolicyHandler — where each handler either passes the post along, rejects it, or flags it for human review. ModerationService never needs to know the full list or order of checks up front, and adding a new check means adding a new handler, not editing an existing one.

Code Skeleton

Post.java — the abstract shared supertype:

public abstract class Post {
    private final String id;
    private String title;
    private String body;
    private final Member author;
    private final Instant createdAt;
    private int voteCount;
    private final List<Comment> comments = new ArrayList<>();

    protected Post(String id, String title, String body, Member author) {
        this.id = id;
        this.title = title;
        this.body = body;
        this.author = author;
        this.createdAt = Instant.now();
    }

    public void addComment(Comment comment) {
        comments.add(comment);
    }

    public void addVote(Vote vote) {
        voteCount += vote.getValue();
    }

    public int getScore() {
        return voteCount;
    }

    public Member getAuthor() {
        return author;
    }

    public String getId() {
        return id;
    }
}

Question.java and Answer.java — both extend Post, adding only what's unique to each:

public class Question extends Post {
    private final List<Tag> tags = new ArrayList<>();
    private final List<Answer> answers = new ArrayList<>();
    private String acceptedAnswerId;
    private int viewCount;

    public Question(String id, String title, String body, Member author) {
        super(id, title, body, author);
    }

    public void addTag(Tag tag) {
        tags.add(tag);
    }

    public void addAnswer(Answer answer) {
        answers.add(answer);
    }

    public void acceptAnswer(Answer answer) {
        if (acceptedAnswerId != null) {
            throw new IllegalStateException("Question already has an accepted answer");
        }
        if (!answers.contains(answer)) {
            throw new IllegalArgumentException("Answer does not belong to this question");
        }
        answer.markAccepted();
        this.acceptedAnswerId = answer.getId();
    }

    public boolean hasAcceptedAnswer() {
        return acceptedAnswerId != null;
    }
}

public class Answer extends Post {
    private final String questionId;
    private boolean accepted;

    public Answer(String id, String title, String body, Member author, String questionId) {
        super(id, title, body, author);
        this.questionId = questionId;
    }

    void markAccepted() {
        this.accepted = true;
    }

    public boolean isAccepted() {
        return accepted;
    }

    public String getQuestionId() {
        return questionId;
    }
}

Vote.java — one class, polymorphic against Post, with the self-vote guard baked in at construction:

public class Vote {
    public enum Direction { UP, DOWN }

    private final String id;
    private final Member voter;
    private final Post target;
    private final Direction direction;
    private final Instant createdAt;

    public Vote(String id, Member voter, Post target, Direction direction) {
        if (voter.equals(target.getAuthor())) {
            throw new IllegalStateException("Members cannot vote on their own posts");
        }
        this.id = id;
        this.voter = voter;
        this.target = target;
        this.direction = direction;
        this.createdAt = Instant.now();
    }

    public int getValue() {
        return direction == Direction.UP ? 1 : -1;
    }

    public Member getVoter() {
        return voter;
    }

    public Post getTarget() {
        return target;
    }

    public Direction getDirection() {
        return direction;
    }
}

Member.java — the reputation field and the privilege guard:

public class Member {
    public enum Privilege { DOWNVOTE, EDIT_OTHERS_POSTS, CREATE_TAGS, VOTE_UP }

    private static final int DOWNVOTE_THRESHOLD = 125;
    private static final int EDIT_OTHERS_THRESHOLD = 2000;

    private final String id;
    private String username;
    private int reputation;
    private final Instant joinedAt;

    public Member(String id, String username) {
        this.id = id;
        this.username = username;
        this.reputation = 1;
        this.joinedAt = Instant.now();
    }

    public boolean canPerform(Privilege privilege) {
        switch (privilege) {
            case VOTE_UP:
                return true;
            case DOWNVOTE:
                return reputation >= DOWNVOTE_THRESHOLD;
            case EDIT_OTHERS_POSTS:
            case CREATE_TAGS:
                return reputation >= EDIT_OTHERS_THRESHOLD;
            default:
                return false;
        }
    }

    public void adjustReputation(int delta) {
        this.reputation = Math.max(1, this.reputation + delta);
    }

    public int getReputation() {
        return reputation;
    }

    public String getId() {
        return id;
    }
}

ReputationService.java — the Strategy-backed apply() method, writing to an append-only ledger:

public class ReputationService {
    private final Map<ReputationReason, ReputationRule> rules;
    private final List<ReputationEvent> ledger = new ArrayList<>();

    public ReputationService(Map<ReputationReason, ReputationRule> rules) {
        this.rules = rules;
    }

    public void apply(ReputationEvent event) {
        ReputationRule rule = rules.get(event.getReason());
        int delta = rule.score(event);
        event.getMember().adjustReputation(delta);
        ledger.add(event);
        // Badge thresholds are checked by an Observer listening on this ledger,
        // not inline here -- see "Follow-up: badges as Observer" below.
    }
}

interface ReputationRule {
    int score(ReputationEvent event);
}

public final class ReputationEvent {
    private final String id;
    private final Member member;
    private final ReputationReason reason;
    private final String sourceId;
    private final Instant occurredAt;

    public ReputationEvent(String id, Member member, ReputationReason reason, String sourceId) {
        this.id = id;
        this.member = member;
        this.reason = reason;
        this.sourceId = sourceId;
        this.occurredAt = Instant.now();
    }

    public Member getMember() { return member; }
    public ReputationReason getReason() { return reason; }
}

enum ReputationReason { UPVOTE_RECEIVED, DOWNVOTE_CAST, ACCEPTED_ANSWER }

Extensibility & Edge Cases

  • Self-voting. A member should never be able to vote on their own post. The cleanest place to enforce it is inside the Vote constructor itself (as in the skeleton above) rather than in every call site that creates a vote — making the invalid state unrepresentable instead of trusting every caller to remember the check.
  • Duplicate votes. The same member voting twice on the same post needs a uniqueness constraint on (member_id, post_id) — a unique index at the database layer, or an in-memory Set<VoteKey> in a simplified model. Worth raising explicitly in an interview: should a second vote be rejected outright, or treated as "change my vote" (delete the old Vote, apply the new one, reverse then reapply the reputation delta)? Both are defensible; the requirement should say which.
  • Reputation caps per day. Without a cap, a small ring of accounts can farm reputation by upvoting each other repeatedly. A daily cap on reputation gained from upvotes (mirroring how Stack Overflow itself works) can be enforced by querying ReputationEvent for today's UPVOTE_RECEIVED events for a member before applying a new one, or by maintaining a rolling daily counter reset by a scheduled job.
  • Deleting a question with accepted answers. Prefer soft-delete (an isDeleted flag, hidden from search/browse but retained in storage) over hard-delete. An accepted answer represents community-validated content that other members may be relying on, and hard-deleting it leaves ReputationEvent.sourceId pointing at nothing — breaking the audit trail retroactively for reputation the answerer legitimately earned.
  • Tag synonyms and merging. When two tags for the same concept get merged, Tag.synonymOf redirects the deprecated tag to its canonical replacement. SearchIndex and tag-browse queries then need to resolve through that pointer (or the merge job flattens every existing Question's tag reference at merge time) so questions tagged under the old name still surface when someone searches or browses the canonical tag.

Follow-up Interview Questions

Why do Question and Answer share a common Post superclass instead of each having its own copy of title/body/votes/comments?
Because those fields and behaviors are identical between the two, and without a shared supertype every class that needs to work with "either a question or an answer" — Comment, Vote, the search indexer — would need two parallel code paths or an awkward union type. Post gives them one abstract type to program against, so a single Vote class and a single Comment-attachment mechanism cover both cases polymorphically.
How would you prevent a member from voting on their own post, and where does that check belong?
Compare the voter to target.getAuthor() and reject the vote if they match. It belongs inside the Vote class's own construction/factory path (making the invalid state impossible to create) rather than scattered across every controller or service method that might create a vote — centralizing the invariant where the object is born is more robust than trusting every call site to remember it.
How do you prevent duplicate votes by the same member on the same post?
A uniqueness constraint on the pair (member, post) — a unique database index in a real system, or a Set<VoteKey> keyed on that pair in an in-memory model. The interesting design decision is what happens on a second attempt: reject it outright, or treat it as "change my vote," which requires reversing the old vote's reputation delta before applying the new one.
Why model Vote.target as the abstract Post type instead of having separate QuestionVote and AnswerVote classes?
Splitting Vote into two classes would duplicate every piece of vote logic (validation, scoring, self-vote checks, persistence) and force calling code to know which concrete type it's dealing with before it can even cast a vote. Typing target as Post lets one Vote class, one repository, and one scoring path handle both, with the JVM's polymorphism doing the dispatching instead of application code doing it manually.
How could badge-awarding be implemented as an event-driven Observer instead of being checked inline on every reputation change?
Instead of ReputationService.apply() directly calling badge-threshold logic, it publishes a "reputation changed" event (or the ReputationEvent itself) to a list of registered listeners. A BadgeAwardingObserver subscribes to that stream, checks the member's cumulative stats against badge criteria, and awards a Badge when a threshold is crossed — keeping ReputationService's one job (compute and record the delta) decoupled from an unrelated concern (deciding who earned a badge), and making it trivial to add new badge rules without touching ReputationService at all.
How would you extend this design to support closing and reopening questions with a moderation audit trail?
Add a status field to Question (OPEN, CLOSED, REOPENED) and a ModerationEvent class shaped like ReputationEvent — an immutable, append-only record of who closed/reopened a question, when, and why (duplicate, off-topic, etc.). Moderator gets closeQuestion(Question, Reason) and reopenQuestion(Question) methods that both mutate status and append a ModerationEvent, so the audit trail is a natural byproduct of the state change rather than a separate system to keep in sync.
Why is ReputationEvent an append-only ledger rather than just incrementing a reputation counter directly?
A single mutable counter can't answer "why does this member have 4,300 reputation" or support a daily reputation cap, an undo (e.g. a retracted vote), or an audit when reputation looks wrong. An append-only ledger of ReputationEvents makes the counter a derived, recomputable value, gives you the "why," and makes caps/undos a matter of querying and reversing specific events instead of guessing at a running total.
How would you enforce, at the class-design level, that only one Answer per Question can be marked accepted — not just via application logic scattered around?
Put the invariant inside Question.acceptAnswer(), the single method that's allowed to flip an answer's accepted flag, and make Answer.markAccepted() package-private (or otherwise non-public) so it can only be called from within that guarded path — not directly by any other class. That way "can only accept once" is enforced by the object model's own encapsulation, not by every caller remembering to check acceptedAnswerId first.
How does making Moderator a subclass of Member (rather than a separate, parallel actor type) simplify the model, and what's the risk?
It means a Moderator automatically has everything a Member has — reputation, the ability to ask/answer/vote — without duplicating any of it, and any code that accepts a Member (e.g. Vote's voter field) works unchanged for a Moderator. The risk is the classic inheritance trap: if moderation permissions ever need to vary independently of "is this a moderator" (e.g. a temporary, revocable moderation grant, or per-tag moderator scopes), a rigid subclass is the wrong tool and a composed Permission/Role object attached to Member would flex better.
How would you scale SearchIndex if keyword search needed to run across millions of questions?
Keep SearchIndex as the interface (indexQuestion, search) but swap its implementation from an in-process structure to a dedicated search engine (Elasticsearch/OpenSearch or similar), populated asynchronously via the same Observer mechanism already driving Notification — a "new question" or "question edited" event triggers a re-index rather than a synchronous write on the request path. That keeps posting a question fast and lets the index fall behind by seconds under load without ever blocking a write.

Key Takeaways

Remember
The whole design turns on one decision: Post as an abstract shared supertype of Question and Answer, so Comment and Vote each work against one polymorphic type instead of two duplicated ones. Composition (Question owns Answer and Comment) models real lifecycle ownership; association (Vote to Member and to the abstract Post) models references without ownership; and Moderator specializes Member rather than existing as a disconnected actor. Reputation is an append-only ledger of ReputationEvents scored by pluggable Strategy rules, not a bare counter, which is what makes daily caps, audits, and undo possible. Notification, and eventually badge-awarding and search indexing, are Observers reacting to events raised elsewhere — keeping "something happened" decoupled from "who cares and what they do about it."
