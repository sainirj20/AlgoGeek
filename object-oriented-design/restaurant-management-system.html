OBJECT ORIENTED DESIGN

Design a Restaurant Management System

This problem packs three separate modeling ideas into one interview, and the strongest candidates name all three out loud instead of stumbling into them. First, a multi-branch chain is a straightforward composition tree — Restaurant owns Branches, a Branch owns Tables and a Menu — but Branch's relationship to its Employees is the one relationship on this page worth pausing on: staff can transfer between branches, so that link has to be aggregation, not composition, even though everything else in the Branch's neighborhood is composition. Second, a restaurant's Menu is a textbook Composite pattern: a Menu groups MenuSections, each MenuSection groups MenuItems, and nothing about that shape changes if a branch has three sections or ten. Third, reserving a Table without double-booking it is the exact same interval-overlap problem worked through on the Hotel Management page — just shrunk from a multi-night date range down to a same-day, 90-minute seating window, which means the fix is the same atomic check-then-insert discipline, not a different algorithm. Layer on a Person → Employee/Customer hierarchy (the same "one identity, many roles" shape as the Library Management page's Account → Member/Librarian split) and a two-stage State machine for order fulfillment, and you have a compact but genuinely representative LLD problem.

Problem Statement

Design the internal operations system for a restaurant — possibly a multi-branch chain rather than a single location. The system has to manage each Branch's physical Tables (their capacity and current occupancy state), let a Receptionist or Customer reserve a Table ahead of time or seat a walk-in on the spot, let a Waiter take an Order against a Table from that Branch's Menu, route each item on that Order to the Chef in the Kitchen for preparation, track that item's progress from ordered to served, and finally generate a Bill covering everything the Table ordered during its current visit — including splitting that Bill across multiple parties and accepting payment. A Manager sits above all of this: editing the Menu, managing Branches and Employees, and pulling sales reports. As with any multi-location system, the design has to work whether the chain has one Branch or fifty, without the Branch-specific details (its own Tables, its own staff roster, its own Menu variant) leaking into how Restaurant, Order, or Bill are modeled.

Requirements

  1. A Restaurant has one or more Branches, and each Branch has its own Tables, Employees, and Menu.
  2. Every Table has a capacity (how many guests it seats) and a status: Free, Reserved, Occupied, or Needs-Cleaning.
  3. A Customer (or a Receptionist acting on their behalf) can reserve a Table for a given party size and time window, or seat a walk-in immediately if a Table of suitable capacity is currently Free.
  4. A Waiter takes an Order for a Table, made up of one or more MenuItems — each carrying a price and a category such as Appetizer, Main, Dessert, or Beverage.
  5. An Order is routed to the Kitchen for the Chef to prepare, and the system tracks a per-item status — Ordered, Preparing, Ready, or Served — rather than one status for the whole Order.
  6. The system generates a Bill that combines every Order placed for a Table during its current visit, supports splitting that Bill across multiple parties at the table, and accepts payment.
  7. A Manager can modify the Menu (add, remove, or re-price MenuItems) and view sales reports.
  8. The system must never double-book or double-seat the same Table for overlapping reservation windows — the same interval-overlap discipline used for date ranges on the Hotel Management page, here applied to same-day time slots.
  9. A Table's Menu availability can vary per Branch — the same chain-wide MenuItem might be offered at one location and not another.

Actors & Use Cases

Five actors touch the system, and (mirroring the Hotel Management page's pattern) several of them legitimately share use cases — a Receptionist can do anything a walk-in Customer's presence triggers, and a Waiter's actions straddle both the dining room and the kitchen pass:

  • Customer — reserves a Table ahead of time, views the Menu, has a Waiter take their order on their behalf, and pays.
  • Receptionist — seats walk-ins at a suitable Free Table and manages the reservation book, including taking reservations by phone.
  • Waiter — takes Orders at the table, marks items Served once the kitchen has them ready, and generates/settles the Bill.
  • Chef / Kitchen Staff — watches incoming order tickets and updates each OrderItem's prep status as it moves through the kitchen.
  • Manager — manages the Menu, Branches, and Employee roster, and reviews sales reports. Never touches a single table's Order or Bill directly.

Primary use cases: Reserve Table, Seat Walk-In, Take Order, Update Order-Item Status, Generate Bill, Process Payment, and Manage Menu (manager).

Class Diagram

One relationship here deserves special attention before the diagram: Branch–Table is composition (filled diamond) because a Table has no identity or lifecycle outside the Branch it's bolted into — close the Branch and its Tables are simply gone. Branch–Employee, by contrast, is aggregation (hollow diamond) — an Employee keeps existing, keeps a payroll record, and can be reassigned to a different Branch entirely (a transfer), so the Employee's lifecycle is independent of any one Branch's. Same "has-a" shape, opposite lifecycle rule, side by side on the same class — exactly the distinction interviewers use this page to probe.

The Composite shape of Menu→MenuSection→MenuItem is worth calling out explicitly: a Manager adding a new section, or a MenuItem moving from one section to another, never requires touching the Menu class itself — the composite/leaf structure absorbs that change entirely inside MenuSection. Design Patterns Applied

Name the pattern and the forcing function together, not just the label:

  • State — two independent state machines. Table status: Free → Reserved/Occupied → Needs-Cleaning → back to Free, with guarded transitions (a Table can't go straight from Occupied to Free without passing through Needs-Cleaning). OrderItem status: Ordered → Preparing → Ready → Served, tracked per item rather than per Order, since a Main course and a slow-cooked dessert on the same ticket legitimately finish at different times.
  • Observer — the Kitchen display and the Waiter's own notification both react to state changes instead of polling for them. When an Order is submitted, every new OrderItem publishes a "ticket created" event that the kitchen-display subscriber picks up — the Order class doesn't need to know how the kitchen's screen is implemented. Symmetrically, when a Chef calls markReady() on an OrderItem, that publishes an "item ready" event that the assigned Waiter's device subscribes to, so the Waiter is pushed a notification the moment food is up rather than having to keep walking to the pass and asking. This is a genuinely useful application, not a decorative one: without it, a busy Waiter either polls constantly (wasted round-trips) or serves food late because nobody told them it was ready.
  • Composite — Menu, MenuSection, and MenuItem form a textbook Composite: MenuSection is a "container" of MenuItem "leaves," and Menu is a container of MenuSections. Any operation that needs to walk the whole menu (rendering it, searching for an item by name, computing which items are unavailable) recurses uniformly through the hierarchy without needing to special-case "is this a section or an item." Adding a new section, or moving an item between sections, touches only MenuSection — Menu itself never changes.
  • Aggregation vs. composition (not a GoF pattern, but the modeling decision this page is built to test) — Branch–Table is composition because a Table is meaningless and undestroyable-separately outside its Branch; Branch–Employee is aggregation because an Employee has an independent lifecycle (payroll record, tenure, benefits) that survives a transfer to a different Branch entirely. Getting this backwards — treating staff as if they die with the Branch, or Tables as if they can be reassigned between Branches — is exactly the kind of mistake this page is designed to catch.
Time-slot overlap Same idea as the Hotel Management page's date-range overlap check, just scoped to a single day's time-of-day window instead of a multi-night date range. Model a reservation window as half-open, [start, end), on a given date, and two windows overlap exactly when startA < endB && startB < endA (and both windows are on the same date). Worked example: an existing 90-minute hold for [7:00pm, 8:30pm) and a new request for [8:00pm, 9:30pm) — 7:00 < 9:30 is true and 8:00 < 8:30 is true, so they overlap. A request for [8:30pm, 10:00pm) against that same existing hold does not overlap: 7:00 < 10:00 is true, but 8:30 < 8:30 is false — the outgoing party's slot ends exactly when the next one begins, which is why the window is modeled half-open.

Code Skeleton

Fields and method signatures only — not a runnable program. TimeSlot.overlaps is worked out in full, since it's the same load-bearing check as DateRange.overlaps on the Hotel Management page, just narrowed to a single day.

public enum TableStatus {
    FREE, RESERVED, OCCUPIED, NEEDS_CLEANING
}

public final class TimeSlot {
    private final LocalDate date;
    private final LocalTime start;   // inclusive
    private final LocalTime end;     // exclusive

    public TimeSlot(LocalDate date, LocalTime start, LocalTime end) {
        if (!start.isBefore(end)) {
            throw new IllegalArgumentException("start must be before end");
        }
        this.date = date;
        this.start = start;
        this.end = end;
    }

    // Half-open interval overlap, same idea as DateRange.overlaps() on the Hotel
    // Management page, just scoped to a single day's time-of-day window.
    public boolean overlaps(TimeSlot other) {
        return this.date.equals(other.date)
                && this.start.isBefore(other.end)
                && other.start.isBefore(this.end);
    }

    public LocalDate getDate() { return date; }
}

public class Table {
    private final String tableId;
    private final String number;
    private final int capacity;
    private volatile TableStatus status;

    public Table(String tableId, String number, int capacity) { /* ... */ }

    // Guarded transition: only a Free or Reserved table can be seated.
    public synchronized void markOccupied() {
        if (status != TableStatus.FREE && status != TableStatus.RESERVED) {
            throw new IllegalStateException("Table " + tableId + " is not seatable from " + status);
        }
        this.status = TableStatus.OCCUPIED;
    }

    public synchronized void markNeedsCleaning() {
        if (status != TableStatus.OCCUPIED) {
            throw new IllegalStateException("Only an occupied table can be cleared");
        }
        this.status = TableStatus.NEEDS_CLEANING;
    }

    public synchronized void markFree() {
        if (status != TableStatus.NEEDS_CLEANING) {
            throw new IllegalStateException("Table must be cleaned before it can be marked free");
        }
        this.status = TableStatus.FREE;
    }

    public boolean fits(int partySize) { return capacity >= partySize; }
    public TableStatus getStatus() { return status; }
}
public enum OrderItemStatus {
    ORDERED, PREPARING, READY, SERVED
}

public class OrderItem {
    private final String orderItemId;
    private final MenuItem menuItem;
    private final int quantity;
    private volatile OrderItemStatus status = OrderItemStatus.ORDERED;

    public OrderItem(String orderItemId, MenuItem menuItem, int quantity) { /* ... */ }

    // Guarded, one-way state machine: ORDERED -> PREPARING -> READY -> SERVED
    public synchronized void markPreparing() { require(OrderItemStatus.ORDERED); status = OrderItemStatus.PREPARING; }
    public synchronized void markReady()     { require(OrderItemStatus.PREPARING); status = OrderItemStatus.READY; }
    public synchronized void markServed()    { require(OrderItemStatus.READY); status = OrderItemStatus.SERVED; }

    private void require(OrderItemStatus expected) {
        if (status != expected) {
            throw new IllegalStateException("Expected " + expected + " but was " + status);
        }
    }

    public OrderItemStatus getStatus() { return status; }
    public Money getSubtotal() { return menuItem.getPrice().multiply(quantity); }
}

public class Order {
    private final String orderId;
    private final String tableId;
    private final String waiterId;
    private final List<OrderItem> items = new ArrayList<>();
    private final LocalDateTime createdAt;
    private volatile boolean submittedToKitchen = false;

    public Order(String orderId, String tableId, String waiterId, LocalDateTime createdAt) { /* ... */ }

    public void addItem(MenuItem item, int quantity) {
        if (submittedToKitchen) {
            // Once the kitchen has the ticket a plain add is no longer safe --
            // see Extensibility & Edge Cases for the amend-order cutoff.
            throw new IllegalStateException("Order already submitted; use amendOrder() instead");
        }
        items.add(new OrderItem(UUID.randomUUID().toString(), item, quantity));
    }

    public void submitToKitchen() { this.submittedToKitchen = true; }
    public List<OrderItem> getItems() { return List.copyOf(items); }

    public boolean isFullyServed() {
        return items.stream().allMatch(i -> i.getStatus() == OrderItemStatus.SERVED);
    }
}
public enum ItemCategory { APPETIZER, MAIN, DESSERT, BEVERAGE }

public class MenuItem {
    private final String itemId;
    private final String name;
    private final Money price;
    private final ItemCategory category;
    private volatile boolean available = true;

    public MenuItem(String itemId, String name, Money price, ItemCategory category) { /* ... */ }
    public Money getPrice() { return price; }
    public boolean isAvailable() { return available; }
}

public class MenuSection {
    private final String name;   // e.g. "Appetizers", "Mains", "Desserts", "Beverages"
    private final List<MenuItem> items = new ArrayList<>();

    public void addItem(MenuItem item) { items.add(item); }
    public void removeItem(String itemId) { items.removeIf(i -> i.getItemId().equals(itemId)); }
    public List<MenuItem> getItems() { return List.copyOf(items); }
}

public class Menu {
    private final String menuId;
    private final List<MenuSection> sections = new ArrayList<>();

    public void addSection(MenuSection section) { sections.add(section); }
    public List<MenuSection> getSections() { return List.copyOf(sections); }
}
public enum ReservationStatus { CONFIRMED, SEATED, CANCELLED, NO_SHOW }

public class Reservation {
    private final String reservationId;
    private final String tableId;
    private final String customerId;
    private final int partySize;
    private final TimeSlot timeSlot;   // e.g. a 90-minute seating window
    private volatile ReservationStatus status = ReservationStatus.CONFIRMED;

    public Reservation(String reservationId, String tableId, String customerId,
                        int partySize, TimeSlot timeSlot) { /* ... */ }

    public boolean overlaps(TimeSlot other) {
        return timeSlot.overlaps(other);
    }

    public TimeSlot getTimeSlot() { return timeSlot; }
    public ReservationStatus getStatus() { return status; }
    public void cancel() { status = ReservationStatus.CANCELLED; }
}

Extensibility & Edge Cases

  • Splitting a bill across multiple customers. A single Table's visit produces one Bill, but the party at that table often wants to pay separately. Bill.splitEvenly(n) covers the simple case; a more precise split assigns specific OrderItems to each paying party (splitByItems(assignment)) so someone who only had a coffee isn't charged for a share of the steak.
  • Merging two tables for a large party. When a party is bigger than any single Table's capacity, two or more Tables need to be combined into one logical seating unit for the duration of that visit. Model this as a lightweight TableGroup (a set of Table references with a combined capacity) rather than mutating any one Table's own capacity field — the individual Tables revert to their normal, independent capacities the moment the merged party leaves.
  • Modifying an order after it's been sent to the kitchen. A guest asking to add or change an item after submitToKitchen() has already fired needs a guarded amendOrder() path, not a silent mutation of the existing Order — the kitchen may already be cooking the original ticket. A reasonable cutoff: items still in ORDERED status can be freely amended; items already PREPARING or beyond require an explicit kitchen acknowledgment (or get appended as a new, separate ticket) rather than being edited in place.
  • Multi-branch menu variations. Not every MenuItem is available at every Branch. Rather than each Branch owning a wholly separate copy of every MenuItem, a shared catalog of MenuItems can be referenced by each Branch's Menu, with a per-branch available override (or a per-branch price override, for regional pricing) layered on top — the same "shared reference data, per-location override" shape that shows up in most multi-location retail systems.
  • Online / delivery orders with no physical Table. A delivery or pickup order shouldn't force a fake Table into existence just to satisfy Order's schema. Model it as a DeliveryOrder subtype (or a sibling class implementing a common Orderable/base Order abstraction) that carries a delivery address instead of a tableId and skips table-assignment and dine-in billing entirely, while still reusing the same OrderItem/kitchen-routing/State-machine machinery as a dine-in Order.

Follow-up Interview Questions

Two Receptionists try to reserve the same Table for overlapping time slots at nearly the same instant. How do you stop both from succeeding?
The overlap check can't be a read-then-write race in application code — fetching existing reservations, checking overlap, and inserting the new Reservation have to run as a single atomic unit against a consistent, locked view of that Table's bookings. In practice that's either a database uniqueness/exclusion constraint on (tableId, date, time-range) that rejects a second overlapping insert outright, or an explicit row lock on the Table held across the check-and-insert. Whichever request commits first wins; the second either fails the constraint and is told the slot is gone, or is retried against the now-current state. This is exactly the same race the Hotel Management page solves for multi-night date ranges — the fix doesn't change shape just because the window shrank to 90 minutes.
Why is Menu/MenuSection/MenuItem a good fit for the Composite pattern specifically, rather than just "a list of lists"?
Composite is the right call whenever client code wants to treat a single leaf and a whole subtree uniformly, and whenever the tree's depth or shape can change without client code caring. Here, any operation that walks the menu — rendering it for a guest, searching for an item by name, computing "everything under $15" — recurses the same way whether it's looking at a MenuSection or a MenuItem, and a Manager adding a new section or moving an item between sections never requires touching the Menu class itself. A flat "list of lists" happens to look similar for a two-level menu, but it breaks down the moment a section needs sub-sections (e.g. "Wine" split into "By the Glass" / "By the Bottle") since a plain list has no uniform way to represent "this child is itself a container." Composite is designed exactly for that recursive case.
Walk through how the Kitchen should notify a Waiter that an OrderItem is ready, and why that's better than the Waiter's device just polling.
When a Chef calls markReady() on an OrderItem, that state transition publishes an event (an "item ready" notification) that the assigned Waiter's device subscribes to — classic Observer. The OrderItem/kitchen-display code never needs to know which Waiter, or how many devices, care about that specific item; it just publishes the event and any current subscriber reacts. Polling — the Waiter's device asking "is anything ready yet?" every few seconds — wastes round-trips during quiet periods and, worse, introduces latency exactly when it matters most (food sits under the heat lamp between when it's actually ready and when the next poll happens to fire). Observer collapses that latency to roughly zero and scales down gracefully to zero cost when nothing is happening, which a fixed-interval poll can't do.
How would you extend this design to support delivery or online orders that have no physical Table at all?
Introduce a sibling to the dine-in Order — a DeliveryOrder (or a common base abstraction both extend) — that replaces the tableId with a delivery/pickup address and customer contact info, and simply omits every table-related step: no seating, no table-status transitions, no dine-in Bill. It still reuses the same OrderItem list, the same kitchen-routing and per-item State machine (Ordered/Preparing/Ready), and the same MenuItem references, since none of that logic actually depends on a physical Table existing. What changes is only the "last mile": instead of a Waiter marking the item Served at the table, a Ready delivery order transitions to a fulfillment/courier-handoff step, and instead of a dine-in Bill split across a table's party, it produces a single-party invoice settled at order time (common for delivery) rather than at the end of a visit.
Why is Branch–Employee modeled as aggregation while Branch–Table is composition, given both are "a Branch has many X" relationships?
The shape (has-a, one-to-many) is identical; the lifecycle rule is opposite. A Table is inert, physical, and location-bound — it has no identity or purpose outside the four walls of its Branch, so destroying the Branch destroys its Tables (composition, filled diamond). An Employee, by contrast, has an existence independent of any one Branch: a payroll record, a hire date, a tenure that can span a transfer from one location to another. Modeling Employee as composition under Branch would force an awkward "delete and recreate" whenever staff move between locations, which doesn't reflect what actually happens to a real employee's record. Aggregation (hollow diamond) captures that the Employee can be reparented, or can simply outlive the Branch it currently works at.
Why track OrderItemStatus per item instead of one status field on the whole Order?
A single Order-level status would have to somehow represent "the appetizer is served, the main is still preparing, and the dessert hasn't even been started" as one enum value, which either forces an awkward composite status (PARTIALLY_READY) or just loses information about which specific items are lagging. Tracking status on OrderItem means each dish's lifecycle is independent and accurate, and the Order-level question "can this table get its bill yet?" becomes a simple derived check — isFullyServed() — over all of its OrderItems, rather than a stored field that has to be kept in sync by hand every time any one item changes state.
A guest wants to add a dessert to an Order that's already been submitted to the kitchen. How do you handle that without corrupting the ticket the kitchen is already working from?
Don't silently mutate the existing Order object once submitToKitchen() has fired — the kitchen may already be actively preparing items from it. Instead, route the change through a guarded amendOrder() path: an item still in ORDERED status (not yet picked up by a Chef) can usually be added or removed cleanly, but once an item has moved to PREPARING or beyond, the addition is either appended as a distinct, clearly-marked new ticket (so the kitchen sees it as a fresh item rather than an edit to something they're mid-preparation on) or requires an explicit kitchen acknowledgment before it's accepted. The key invariant: the kitchen should never see an Order's contents change out from under a ticket it's already committed to preparing.
Why give Person its own abstract base for both Employee and Customer, instead of letting Employee and Customer be unrelated classes?
Employee and Customer genuinely share a slice of behavior and data that has nothing to do with their roles — a name, contact info, and (in most real systems) an identity that could plausibly need updating in one place. Modeling that shared slice once, on an abstract Person, avoids duplicating "name/phone/email plus getContactInfo()" across every subclass and gives the system one place to add cross-cutting Person-level behavior later (e.g. GDPR-style contact-info updates or communication preferences) without touching Employee's or Customer's role-specific logic at all. It's the same "one identity, many roles" shape as Account → Member/Librarian on the Library Management page or Account → Customer/Seller/Admin on the Amazon page — a recurring, well-tested modeling idiom, not something invented specifically for this problem.
How would you generate a Manager's sales report without hammering the live Order and OrderItem tables that the front-of-house and kitchen are actively using?
Sales reporting is a read-heavy, aggregate, "eventually consistent is fine" workload sitting right next to a write-heavy, low-latency, "must be correct right now" workload (taking orders, updating item status) — running both against the same live tables risks report queries locking rows the kitchen needs to update instantly. The standard fix is to keep Order/OrderItem/Bill as the transactional system of record, and periodically (or via change-data-capture / an event stream, reusing the same Observer publish points already wired up for kitchen/waiter notifications) roll finalized Bills into a separate reporting store shaped for aggregation — by day, by MenuItem, by Branch. Manager's viewSalesReport(range) then reads from that reporting store, never from the live operational tables.

Key Takeaways

Key Takeaways
  • Branch–Table is composition (a Table dies with its Branch) while Branch–Employee is aggregation (a transferred Employee outlives any one Branch) — the same "has-a" shape, opposite lifecycle rule, and exactly the nuance this page is built to test.
  • Menu → MenuSection → MenuItem is a genuine Composite: any menu-wide operation recurses uniformly through the hierarchy, and adding/moving items never touches the Menu class itself.
  • The Table-reservation overlap check is the same half-open, startA < endB && startB < endA interval-overlap logic used for date ranges on the Hotel Management page, just scoped to a same-day time slot — and it needs the same atomic check-then-insert discipline to avoid a double-booking race.
  • OrderItemStatus is tracked per item, not per Order, because different dishes on the same ticket finish preparing at genuinely different times — "is this table's bill ready?" is a derived check over all of its OrderItems, not a hand-maintained Order-level flag.
  • Observer keeps the Kitchen display and the Waiter's "order ready" notification decoupled from Order/OrderItem internals, and beats polling on both latency and idle cost.
