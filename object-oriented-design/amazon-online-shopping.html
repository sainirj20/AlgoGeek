OBJECT ORIENTED DESIGN

Design Amazon — Online Shopping System

"Design an online shopping system like Amazon" is one of the most common object-oriented design prompts because it packs six distinct sub-domains — catalog, cart, checkout, order lifecycle, inventory, and payments — into one prompt, forcing you to decide where one class's responsibility ends and another's begins. This page works through the class model, the key interactions, and the design patterns that make the model extensible, treating it strictly as an OOD exercise rather than a capacity-planning one.

Problem Statement

Design the core object model behind an online shopping platform: a customer browses a product catalog, adds items to a cart, checks out to produce an order, pays for it through one of several payment methods, and then tracks that order through fulfillment. A seller lists and restocks products; an admin curates categories and resolves disputes. The interesting design work is entirely about responsibility and relationships — which object owns the cart's total calculation, how a cart becomes an order, how an order's status can legally change, how a new payment method gets added without touching checkout code, and how inventory correctness survives two people trying to buy the last unit at once.

This is deliberately scoped as a class-design (LLD/OOD) exercise, not a distributed-systems (HLD) one. A "design Amazon's checkout system" prompt in an HLD interview asks a completely different set of questions — how do you shard cart state across thousands of nodes, what's your replication and consistency story for inventory counts across regions, how do you decouple order creation from payment processing with a message queue, what's your capacity plan for Prime Day traffic. None of that is answered by getting the class model right, and none of it is asked here. This page's job is to get Product, Order, ShoppingCart, Payment, and their relationships right as if you were writing a single, well-structured in-process application — the object model that a distributed system like the real Amazon would eventually be built on top of. Section 10 briefly touches the seam where the two conversations meet, but the object model is the whole point of this page.

Requirements

  1. Customers can browse and search the product catalog by category and by keyword.
  2. Customers can add and remove items from a shopping cart before checking out.
  3. Customers can place an order from the current contents of their cart.
  4. An order supports multiple distinct products, each with its own quantity.
  5. An order's status is tracked through a well-defined lifecycle: Placed → Paid → Shipped → Delivered, with Cancelled and Returned as alternate/terminal branches.
  6. Inventory/stock levels are tracked per product; placing an order decrements stock, and cancelling an order restores it.
  7. Customers can pay with any of several payment methods — credit card, gift card, or stored account balance — interchangeably.
  8. Promotions and discount codes can be applied to a cart or order before the final total is computed.
  9. Customers can leave a rating and a written review on a product they've purchased.
  10. The system distinguishes three kinds of account: Customer (shops), Seller (lists and stocks products, marketplace-style), and Admin (curates the catalog and handles disputes).
Out of scope
Payment gateway integration details, tax/duty calculation rules, warehouse routing and shipping-carrier selection, and anything about horizontal scale (sharding, caching tiers, message queues) are deliberately out of scope here — they belong to payment-systems, tax-engine, logistics, and HLD questions respectively. This page treats each of those as a black box behind a clean interface (PaymentMethod.charge(), Inventory.reserve()) that a real implementation would flesh out.

Actors & Use Cases

Four actors interact with the system, one of whom (System) is not a human at all but represents automated, backend-triggered behavior — a common and deliberate modeling choice in use-case diagrams for steps nobody clicks a button for.

  • Customer — browses/searches the catalog, manages a cart, places orders, tracks order status, and leaves reviews.
  • Seller — lists new products and updates stock levels for the products they own (the marketplace angle: a "Product" isn't only sold by Amazon itself).
  • Admin — curates the catalog's category tree and handles disputes escalated from customers or sellers.
  • System — the automated actor: processes payments against the chosen PaymentMethod, decrements inventory once a payment clears, and sends notifications (order confirmation, shipping updates, back-in-stock alerts).

"Place Order" is the busiest use case in the diagram below: it «include»s three System-driven steps — making the payment, decrementing inventory, and sending a confirmation notification — that always happen together as part of one checkout, rather than being separate things a customer triggers individually.

Key Flow: Checkout (Activity Diagram)

Checkout is the one flow every interviewer will ask you to walk through end to end, and the ordering of its steps is the whole point: stock is validated before anything is charged, and inventory is only permanently decremented after payment clears — never before. Get that ordering backwards and you either charge customers for things you can't ship, or you hold stock hostage from other shoppers while a slow payment gateway is still thinking.

Checkout as an activity diagram. Both decision points are hard stops: an out-of-stock cart or a declined payment ends the flow before any state is mutated — inventory is only committed, and the order only created, after a successful charge.

Key Flow: Placing an Order (Sequence Diagram)

The sequence diagram makes the runtime collaboration explicit: OrderService is a facade that no other object talks around — the customer only ever calls it, and it alone coordinates the cart, inventory, payment, order, and notification objects underneath. Notice the two-phase relationship with Inventory: a reserve() call happens before the payment is attempted (an atomic hold, discussed further below), and a separate commit() call only happens after payment succeeds. That split is exactly what prevents a slow or failed payment from starving other customers of stock it never actually needed.

Runtime call sequence for checkout. OrderService is the only object the Customer talks to; every collaborator below it is invoked and returns through that single facade.

Design Patterns Applied

Strategy — PaymentMethod

PaymentMethod is an interface with CreditCardPayment, GiftCardPayment, and StoredBalancePayment as interchangeable implementations. OrderService and Payment only ever call method.charge(amount) — they never know or care which concrete strategy is behind it. This is the textbook justification for Strategy: without it, checkout code would need a growing switch on payment type, and every new payment method (buy-now-pay-later, a new regional wallet) would mean editing checkout itself rather than adding one new class beside the existing ones.

State — OrderStatus

An order's status isn't just a label; it's a state machine with real legality rules, and those rules deserve one authoritative home rather than being re-checked (and inevitably re-implemented slightly differently) at every call site that touches an order.

Current StatusLegal Next States
PLACEDPAID, CANCELLED
PAIDSHIPPED, CANCELLED
SHIPPEDDELIVERED, RETURNED
DELIVEREDRETURNED
CANCELLED(terminal — no further transitions)
RETURNED(terminal — no further transitions)

The code skeleton below implements this as an enum with an explicit transition table guarded by a single transitionTo() method — a lightweight version of the full State pattern (a class per state implementing shared behavior) that's usually sufficient here, since order states don't carry heavy per-state behavior, just per-state legality. Either approach beats scattering if (order.getStatus() == SHIPPED) checks across the codebase, which inevitably drifts out of sync as new statuses are added.

Observer — Notification

Order doesn't know how to send an email, a push notification, or an SMS, and it shouldn't have to. Instead, Order (or the service orchestrating it) publishes a status-change event, and any number of registered observers — an email notifier, a push notifier, a seller-dashboard updater — react independently. A concrete extension of the same pattern: a customer who wants a "notify me when this is back in stock" alert subscribes as an observer of a specific Product/Inventory pairing; when Inventory transitions that product's quantity from zero to positive, it publishes a restock event, and the notification service fans it out to every subscribed customer — without Inventory ever needing to know that "notify a customer" means "send an email" or "send a push."

Factory — PaymentMethod construction

Given a payment request (type = CREDIT_CARD plus a token, or type = GIFT_CARD plus a code), something has to decide which concrete PaymentMethod to instantiate. A PaymentMethodFactory.create(type, details) centralizes that decision, so the API layer and OrderService stay ignorant of concrete constructors entirely — they ask the factory for "a payment method for this request" and get back something that satisfies the PaymentMethod interface. Adding StoredBalancePayment later means adding one factory branch (or one registry entry), not hunting through every call site that constructs a payment method.

Decorator (extension idea)

Not a core requirement, but a natural extension: if the product grows gift-wrapping, insurance, or promotional add-ons that can be layered onto an order in any combination, a Decorator wrapping an Order (or a shared OrderComponent interface) avoids a combinatorial subclass explosion (GiftWrappedInsuredOrder, InsuredOrder, GiftWrappedOrder, …). Each decorator adds its own cost and behavior while the rest of the system keeps talking to the same interface. Worth mentioning if an interviewer pushes on extensibility; not worth forcing into the base design if they don't.

ShoppingCart

public class ShoppingCart {
    private final String cartId;
    private final String customerId;
    private final Map<String, CartItem> itemsByProductId = new LinkedHashMap<>();

    public void addItem(Product product, int quantity) {
        itemsByProductId.merge(
            product.getProductId(),
            new CartItem(product, quantity),
            (existing, incoming) -> existing.incrementQuantity(incoming.getQuantity())
        );
    }

    public void removeItem(String productId) {
        itemsByProductId.remove(productId);
    }

    public BigDecimal getTotal() {
        return itemsByProductId.values().stream()
                .map(CartItem::getSubtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    public List<CartItem> getItems() { return List.copyOf(itemsByProductId.values()); }
    public void clear() { itemsByProductId.clear(); }
}

Order, OrderStatus & the transition guard

public enum OrderStatus {
    PLACED, PAID, SHIPPED, DELIVERED, CANCELLED, RETURNED;

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        PLACED,    EnumSet.of(PAID, CANCELLED),
        PAID,      EnumSet.of(SHIPPED, CANCELLED),
        SHIPPED,   EnumSet.of(DELIVERED, RETURNED),
        DELIVERED, EnumSet.of(RETURNED),
        CANCELLED, EnumSet.noneOf(OrderStatus.class),
        RETURNED,  EnumSet.noneOf(OrderStatus.class)
    );

    boolean canTransitionTo(OrderStatus next) {
        return ALLOWED.getOrDefault(this, Set.of()).contains(next);
    }
}

public class Order {
    private final String orderId;
    private final String customerId;
    private final List<OrderItem> items;
    private final Address shippingAddress;
    private Payment payment;
    private OrderStatus status;
    private final Instant createdAt;

    public void transitionTo(OrderStatus next) {
        if (!status.canTransitionTo(next)) {
            throw new IllegalStateException(
                "Order " + orderId + " cannot move from " + status + " to " + next);
        }
        this.status = next;
    }

    public BigDecimal calculateTotal() {
        return items.stream()
                .map(OrderItem::getSubtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

PaymentMethod (Strategy)

public interface PaymentMethod {
    PaymentResult charge(BigDecimal amount);
    void refund(String transactionId, BigDecimal amount);
}

public class CreditCardPayment implements PaymentMethod {
    private final String cardToken;          // vaulted token, never a raw PAN
    private final PaymentGatewayClient gatewayClient;

    @Override
    public PaymentResult charge(BigDecimal amount) {
        GatewayResponse response = gatewayClient.authorizeAndCapture(cardToken, amount);
        return response.isApproved()
                ? PaymentResult.success(response.getTransactionId())
                : PaymentResult.failure(response.getDeclineReason());
    }

    @Override
    public void refund(String transactionId, BigDecimal amount) {
        gatewayClient.refund(transactionId, amount);
    }
}

Inventory — concurrency-safe reserve/release

public class Inventory {
    private final Map<String, AtomicInteger> availableByProductId = new ConcurrentHashMap<>();

    /** Atomically holds {@code qty} units, or fails fast if not enough stock remains. */
    public boolean reserve(String productId, int qty) {
        AtomicInteger available = availableByProductId.get(productId);
        if (available == null) return false;

        int current;
        do {
            current = available.get();
            if (current < qty) return false;              // not enough stock — fail, don't block
        } while (!available.compareAndSet(current, current - qty));
        return true;                                        // won the race; qty is ours
    }

    /** Returns previously reserved units, e.g. on order cancellation or payment failure. */
    public void release(String productId, int qty) {
        availableByProductId
                .computeIfAbsent(productId, id -> new AtomicInteger(0))
                .addAndGet(qty);
    }
}

Extensibility & Edge Cases

Two customers, one last unit

Customer A and Customer B both open a product with quantity = 1 and both click "Buy Now" within milliseconds of each other. A naive implementation reads the stock count, checks if (stock >= 1), and then writes stock - 1 as two separate steps — both threads can read stock = 1 before either writes, and both proceed to "successfully" reserve the same unit. The fix is exactly the Inventory.reserve() shown above: a single atomic compare-and-set (or, at the database layer, a conditional update like UPDATE stock SET qty = qty - 1 WHERE product_id = ? AND qty >= 1 and checking the affected-row count) makes read-and-decrement one indivisible operation, so only one of the two racing calls can ever win. The losing customer gets an immediate, honest "out of stock" rather than a phantom order. Reservations should also carry a short TTL so an abandoned checkout (customer reserves, then closes the tab) doesn't hold stock hostage forever.

Partial shipment

A three-item order might have two items in a warehouse ready to ship today and one on backorder for a week. Forcing the whole Order to wait on its slowest item is a bad customer experience, so the model needs a Shipment entity: one Order can produce multiple Shipments, each carrying a subset of its OrderItems plus its own tracking number and delivery status. Order.status then becomes a roll-up of its shipments' states (a new composite status like PARTIALLY_SHIPPED is a natural addition to the state table above). This is also a preview of where the object model starts pushing into HLD territory — fulfillment-and-shipment tracking at real scale is usually its own service.

Payment succeeds, order creation then fails

Even inside a single application, a crash or exception between "the payment gateway returned success" and "the order row was persisted" leaves a customer charged with no order to show for it. Two things make this recoverable: an idempotency key generated client-side per checkout attempt, so a retried placeOrder() call doesn't trigger a second charge; and a small compensating action — if order creation fails after a successful charge, automatically trigger a refund/void rather than leaving the charge orphaned. This is explicitly the seam where this OOD answer touches its HLD counterpart: making that compensation durable across a process crash (not just a caught exception) needs a persisted outbox or saga log, which is a distributed-systems concern layered on top of this object model, not a replacement for it.

Marketplace: splitting an order across sellers

Once Sellers exist, a cart can legitimately contain items from Seller A and Seller B in the same checkout. Since every OrderItem already carries its own sellerId (inherited from its Product), the cleanest model keeps one customer-facing Order for a single payment and a single order-tracking view, but groups its OrderItems by seller internally for fulfillment and payout — each seller-group effectively becomes its own Shipment with its own status, using the same one-to-many structure introduced above for partial shipment. One payment, multiple independently-fulfilled sub-shipments, one order the customer sees.

Follow-up Interview Questions

Walk me through what goes wrong if two customers try to buy the last unit of a product at the same instant, and how you'd fix it.
A naive "read stock, then write stock−1" is two separate operations, so both requests can read the same pre-decrement value and both believe they succeeded — classic read-then-write race condition, resulting in oversold inventory. The fix is to make the check-and-decrement a single atomic operation: a compare-and-set loop in-process (as in Inventory.reserve()), or a conditional UPDATE ... WHERE qty >= ? at the database layer, checking the affected-row count to know whether you won the race.
Why model Order.status as a State pattern (or an enum with an explicit transition table) instead of a plain enum with scattered if/else checks?
Centralizing legality rules in one place (canTransitionTo/transitionTo) means there's exactly one source of truth for "can a SHIPPED order become CANCELLED," rather than that logic being reimplemented, and inevitably drifting inconsistent, at every call site that happens to touch an order's status. It's also far easier to unit test exhaustively (every from/to pair) and to extend when a new status is added.
How would Observer wire up a "notify me when this item is back in stock" feature?
A Customer subscribes as an observer of a specific Product's stock level (or of the Inventory entry for that product). When Inventory processes a restock and that product's quantity moves from zero to positive, it publishes a restock event; a Notification service, acting as the concrete observer, fans that event out to every subscribed customer over whatever channel they prefer. Inventory never needs to know how the alert is delivered — only that "something changed" is worth broadcasting.
How would this whole design change if you were instead asked to design Amazon's checkout system for scale — an HLD question rather than an OOD one?
The classes and relationships on this page barely change; what changes is everything around them. An HLD answer would talk about sharding cart and inventory state across many nodes by customerId/productId, replacing the in-process Map in ShoppingCart with a distributed cache, reasoning about eventual-consistency trade-offs for inventory counts across regions, decoupling order creation from payment and notification via a message queue, and budgeting latency/throughput and failure domains for Prime-Day-scale traffic. An OOD interview is graded on whether you got responsibility and relationships right; an HLD interview is graded on whether the same behavior survives being spread across thousands of machines.
Why make PaymentMethod an interface (Strategy) instead of one Payment class with a type field and a switch inside charge()?
The switch version violates the Open/Closed Principle: every new payment type means editing a shared, increasingly large method that every other payment type also depends on, and it's easy to accidentally break an unrelated branch. The interface version isolates each payment type in its own class, testable independently, and adding a new one never touches existing code — only the factory that constructs it.
How would you model promotions and discount codes without hardcoding the logic into checkout?
The same Strategy shape used for payments: a Promotion interface with an apply(cart) method, and implementations like PercentageDiscount, FlatAmountDiscount, or BuyOneGetOneFree. If multiple promotions can legally stack, a small ordered chain (Chain of Responsibility) applies each eligible promotion in sequence; checkout just asks "apply whatever promotions are eligible for this cart" without knowing the discount math for any of them.
A multi-item order ships in two separate boxes because one item is on backorder. How does that show up in your model?
Introduce a Shipment entity: one Order can have multiple Shipments, each covering a subset of its OrderItems with its own tracking number and delivery status. Order.status becomes an aggregate/roll-up over its shipments (adding a composite status like PARTIALLY_SHIPPED) rather than a single flag that has to describe the whole order at once.
Why is ShoppingCart–CartItem composition, but Product–ProductCategory only aggregation?
A CartItem has no meaning or lifecycle outside the specific cart that owns it — delete the cart and its items are meaningless and go with it, which is exactly what composition (filled diamond) expresses. A Product, by contrast, keeps existing and keeps making sense even if its category is deleted or it's reassigned to a different category — the part can outlive, or move between, its whole, which is what aggregation (hollow diamond) expresses.
How do you avoid double-charging a customer if the "place order" request is retried, e.g. because of a client-side timeout?
Generate an idempotency key client-side for each distinct checkout attempt and thread it through OrderService into PaymentMethod.charge(). The server records the key alongside the result of the first attempt; if the same key arrives again, it short-circuits and returns the original result instead of charging a second time.
How would you extend the model to support gift-wrapping or other order add-ons without an explosion of Order subclasses?
Decorator: wrap a base Order (or a shared OrderComponent interface) with GiftWrappedOrder, InsuredOrder, and so on, each adding its own cost and behavior while the checkout code keeps talking to the same interface regardless of how many decorators are stacked. This avoids needing one subclass per combination of add-ons.

Key Takeaways

Key Takeaways
An OOD interview like this one is won by getting responsibilities and relationships right — knowing precisely when a link is inheritance, composition, aggregation, or plain association — and by reaching for a design pattern only where it earns its complexity: Strategy for interchangeable payment methods, State for order-status legality, Observer for decoupled notifications, and Factory for construction. Just as important is knowing where the object model's edges are: a concurrent last-unit checkout is solved with an atomic reservation inside this design, but "make this survive Prime Day across five regions" is a fundamentally different conversation about sharding, replication, and distributed transactions — recognizing that boundary, out loud, is itself a strong signal in the interview.
