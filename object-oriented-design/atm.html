OBJECT ORIENTED DESIGN

Design an ATM

The ATM problem is the canonical whiteboard introduction to the State design pattern, and interviewers use it precisely because the state machine isn't contrived — an ATM's screen and behavior genuinely change depending on where the customer is in the flow: no card inserted, card inserted but not yet authenticated, authenticated and choosing an operation, or mid-transaction with cash physically moving. Underneath that state machine sits a second, equally real problem: the machine is a small cash register with finite physical inventory, so a "give me $60" request can fail for a reason that has nothing to do with the customer's balance — the machine might simply not have the right bills on hand. A strong answer treats both halves as first-class: model the state machine so each screen genuinely owns its own behavior instead of leaning on one giant conditional, and treat the denomination breakdown as a real algorithm with a real failure mode, not an implementation detail to hand-wave past.

Problem Statement

Design the software running inside a bank's Automated Teller Machine. A customer inserts a bank card, the machine reads the card number, and the customer enters a PIN that must be verified against the bank's records before anything else is possible. Once authenticated, the customer can withdraw cash, check their balance, deposit cash, transfer funds to another account, or view a mini statement. A withdrawal has to clear two checks — enough balance in the account, and under the account's daily withdrawal limit — before the machine will even attempt to dispense anything; and dispensing itself is a physical constraint, not just a database update, since the requested amount has to be broken down into whatever denominations the machine's cash cassettes actually contain right now. The ATM tracks its own remaining cash inventory per denomination independently of the customer's account balance, and has to gracefully refuse (or offer an alternative) when it can't make exact change. Interviewers use this problem to see whether a candidate reaches for the State pattern deliberately — because the ATM's legal operations really do change screen-to-screen — rather than bolting on a mode field and a wall of if/else, and whether they'll proactively raise the "money moved but cash didn't dispense" failure mode that real ATM operators deal with every day.

Requirements

  1. The ATM must accept a bank card and read the card number off it via a card reader.
  2. The ATM must verify the customer's PIN against the bank's records, allowing only a limited number of attempts (typically three) before the card is retained or blocked.
  3. Once authenticated, the customer can perform: Withdraw Cash, Check Balance, Deposit Cash, Transfer Between Accounts, and Print/Show Mini Statement.
  4. A withdrawal amount must be validated against both the account's available balance and the account's daily withdrawal limit before the machine proceeds.
  5. Cash dispensed must be broken down into whatever denominations the machine currently has available (e.g., $100, $50, $20, $10, $5, $1 bills).
  6. The machine must track its own remaining cash inventory per denomination and refuse a withdrawal — or fall back to a different, dispensable amount — if it cannot make exact change for the requested amount.
  7. The machine must eject the card on a normal, successful interaction, and retain the card after the customer exhausts their PIN attempts.
  8. An Operator/Technician can replenish cash per denomination and place the machine into a maintenance / out-of-service mode.

Actors & Use Cases

Three actors touch this system, and each initiates use cases none of the others can:

  • Customer — inserts a card, authenticates, and performs the money-moving operations: withdraw, deposit, check balance, transfer. The only actor who owns an account in the scenario.
  • Bank / Backend System — not physically present at the machine; the system-of-record that verifies PINs, checks balance and daily-limit rules, and authorizes or declines every transaction the ATM asks it to. Modeling it as its own actor keeps "who actually approved this" honest — the ATM never approves a transaction on its own authority.
  • Operator / Technician — a human who services the physical machine: replenishing cash cassettes per denomination and switching the ATM into and out of a maintenance/out-of-service mode. Never touches a single customer's transaction.

Primary use cases: Insert Card, Enter PIN, Withdraw Cash, Deposit Cash, Check Balance, Transfer Funds, and Replenish Cash.

Class Diagram

Figure 2. ATMState is an interface realized (dashed hollow-triangle) by IdleState, HasCardState, SelectOperationState, and TransactionState. ATM holds an association to its currentState (plain arrow, swapped at runtime) and is composed of (filled diamond) a CashDispenser — the dispenser has no meaning outside the machine that owns it. Transaction is an abstract base realized by four hollow-triangle subtypes with genuinely different execute() logic. ATM associates with Bank for authorization, and TransactionState is where a Transaction instance is actually created and executed (dashed «creates»).

Why State instead of an atmMode enum. A tempting shortcut is a single ATM class with a mode field (IDLE, HAS_CARD, SELECTING, TRANSACTING) and every method — insertCard(), enterPin(), selectOperation() — opening with a switch on that field. It works for four states. It stops working the moment the ATM grows a fifth screen (say, a "confirm large withdrawal" prompt) or a sixth (an out-of-service screen operators can force at any time): every one of those switch statements needs a new case, in every method, and it's easy to forget one and leave a state where, say, ejectCard() silently does nothing when it should return the card. The State pattern turns "what can happen in this screen" into a single class whose four methods together define the complete, exhaustive answer — add a new screen by adding a new class implementing ATMState, and the compiler (via the interface) forces you to decide what every existing action means in it, rather than letting a forgotten case silently fall through.

Design Patterns Applied

Name the pattern and the forcing function together, not just the name:

  • State (ATMState / IdleState / HasCardState / SelectOperationState / TransactionState) — this is the textbook example for a reason. All four concrete states implement the exact same method set — insertCard(), ejectCard(), enterPin(), selectOperation() — but each gives a genuinely different answer: IdleState.insertCard() moves the machine forward, while HasCardState.insertCard() is a no-op because a card is already in the slot. The ATM context never branches on "what screen am I in" itself; it holds a single currentState: ATMState reference and blindly delegates every call — currentState.insertCard(this), currentState.enterPin(this, pin) — to whichever object is currently installed there. The state swap is the other half of the pattern: a state decides when the machine is done with it and calls atm.setState(new NextState()), replacing the object the context delegates to. Nothing about ATM's own code changes when a new screen is added — only a new class implementing ATMState.
  • Strategy (optional angle: CashDispenser's denomination-breakdown algorithm) — today's implementation might be greedy-largest-denomination-first, but a bank could reasonably want a different policy (e.g., preserve $20s for the next customer by favoring $50s and $100s first, or cap how many bills a single dispense can contain). Extracting that into a DenominationStrategy interface with a single breakdownFor(amount, inventory) method lets CashDispenser stay unchanged while the breakdown policy varies independently — the same shape as Strategy anywhere else (payment method, fee calculation): one interface, interchangeable implementations, and the caller never branches on which one is installed.
  • Command (extension idea, not forced) — each Transaction subtype already looks like a command object: it bundles the request (amount, account) with an execute() method. Pushed a little further, Transaction could carry an audit log entry on creation and, where it makes sense, a compensating reverse() (a Transfer can genuinely be reversed by crediting the money back; a Withdrawal whose cash has already left the building physically cannot be "undone" the same way — only the ledger entry can be corrected). This is worth mentioning as a natural direction if the interviewer pushes on auditability or undo, not something to force into the core design where the four Transaction subtypes already do the job.

Code Skeleton

Fields and method signatures only — not a runnable program. The state-swap idiom in HasCardState.enterPin() and CashDispenser.dispense()'s exact-change handling are the two methods worked out in more detail, since they're exactly what interviewers probe on.

public interface ATMState {
    void insertCard(ATM atm, Card card);
    void ejectCard(ATM atm);
    void enterPin(ATM atm, String pin);
    void selectOperation(ATM atm, OperationType operation, BigDecimal amount);
}
public class IdleState implements ATMState {

    @Override
    public void insertCard(ATM atm, Card card) {
        atm.setCurrentCard(card);
        atm.setState(new HasCardState());          // the state-swap idiom
    }

    @Override
    public void ejectCard(ATM atm) { /* no-op: no card to eject */ }

    @Override
    public void enterPin(ATM atm, String pin) { /* no-op: nothing to verify yet */ }

    @Override
    public void selectOperation(ATM atm, OperationType operation, BigDecimal amount) { /* no-op */ }
}
public class HasCardState implements ATMState {
    private static final int MAX_PIN_ATTEMPTS = 3;
    private int attemptsRemaining = MAX_PIN_ATTEMPTS;

    @Override
    public void insertCard(ATM atm, Card card) { /* no-op: a card is already inserted */ }

    @Override
    public void enterPin(ATM atm, String pin) {
        boolean valid = atm.getBank().verifyPin(atm.getCurrentCard(), pin);
        if (valid) {
            atm.setState(new SelectOperationState());
        } else if (--attemptsRemaining > 0) {
            atm.showMessage("Incorrect PIN, " + attemptsRemaining + " attempt(s) remaining");
            // stays in HasCardState -- same object instance, decremented counter
        } else {
            atm.getCardReader().retainCard();
            atm.showMessage("Card retained -- contact your bank");
            atm.setState(new IdleState());
        }
    }

    @Override
    public void ejectCard(ATM atm) {
        atm.getCardReader().returnCard();
        atm.setState(new IdleState());
    }

    @Override
    public void selectOperation(ATM atm, OperationType operation, BigDecimal amount) { /* no-op: PIN not yet verified */ }
}
public class ATM {
    private ATMState currentState;
    private final CashDispenser cashDispenser;
    private final CardReader cardReader;
    private final Bank bank;
    private Card currentCard;

    public ATM(CashDispenser cashDispenser, CardReader cardReader, Bank bank) {
        this.cashDispenser = cashDispenser;
        this.cardReader = cardReader;
        this.bank = bank;
        this.currentState = new IdleState();        // starting state
    }

    public void setState(ATMState state) { this.currentState = state; }
    public void insertCard(Card card)    { currentState.insertCard(this, card); }
    public void enterPin(String pin)     { currentState.enterPin(this, pin); }
    public void selectOperation(OperationType op, BigDecimal amount) {
        currentState.selectOperation(this, op, amount);
    }
    public void ejectCard() { currentState.ejectCard(this); }

    public CashDispenser getCashDispenser() { return cashDispenser; }
    public CardReader getCardReader()       { return cardReader; }
    public Bank getBank()                   { return bank; }
    public Card getCurrentCard()             { return currentCard; }
    public void setCurrentCard(Card card)    { this.currentCard = card; }
    public void showMessage(String text)     { /* renders to the physical screen */ }
}
public class CashDispenser {
    private final Map<Integer, Integer> denominationCounts;   // e.g. 20 -> 340 bills on hand

    public CashDispenser(Map<Integer, Integer> initialInventory) {
        this.denominationCounts = initialInventory;
    }

    public boolean canDispenseExact(int amount) {
        return breakdownFor(amount) != null;
    }

    // Returns a denomination -> count breakdown, or throws if exact change isn't possible
    // with the current inventory; the caller (Withdrawal) is responsible for reversing
    // any debit already applied and/or offering a nearest dispensable amount.
    public synchronized Map<Integer, Integer> dispense(int amount) {
        Map<Integer, Integer> breakdown = breakdownFor(amount);
        if (breakdown == null) {
            throw new CannotDispenseExactAmountException(amount);
        }
        breakdown.forEach((denom, count) ->
            denominationCounts.merge(denom, -count, Integer::sum));
        return breakdown;
    }

    // Greedy largest-denomination-first with backtracking when a denomination
    // runs out; returns null (no throw) if no combination sums to `amount` exactly.
    private Map<Integer, Integer> breakdownFor(int amount) { /* ... */ }

    public void replenish(int denomination, int count) {
        denominationCounts.merge(denomination, count, Integer::sum);
    }
}
public abstract class Transaction {
    protected final String transactionId;
    protected final Account account;
    protected final BigDecimal amount;
    protected final LocalDateTime timestamp;
    protected TransactionStatus status;

    protected Transaction(String transactionId, Account account, BigDecimal amount) { /* ... */ }

    public abstract TransactionStatus execute(Bank bank, CashDispenser dispenser);
}

public class Withdrawal extends Transaction {

    public Withdrawal(String transactionId, Account account, BigDecimal amount) {
        super(transactionId, account, amount);
    }

    @Override
    public TransactionStatus execute(Bank bank, CashDispenser dispenser) {
        if (!bank.authorize(this)) {                          // balance + daily-limit check
            return TransactionStatus.DECLINED;
        }
        Map<Integer, Integer> breakdown;
        try {
            breakdown = dispenser.dispense(amount.intValue());
        } catch (CannotDispenseExactAmountException e) {
            bank.reverse(this);                               // undo the debit; nothing was dispensed
            return TransactionStatus.FAILED_NO_CASH;
        }
        bank.debit(account, amount);
        this.status = TransactionStatus.COMPLETED;
        return status;
    }
}
Worked example Requested withdrawal: $70. Inventory: three $20s, zero $10s, unlimited $5s and $1s. Greedy largest-first tries 3×$20 = $60, leaving $10 with no $10 bills available — falls back to $5s: 2×$5 = $10. Final breakdown: 3×$20 + 2×$5 = $70. If instead only $2 remained in $5s and $1s combined, no combination reaches exactly $70 and dispense() throws CannotDispenseExactAmountException rather than silently shorting the customer.

Extensibility & Edge Cases

  • Debit succeeds, dispense fails (or vice versa). A network blip between the ATM and the Bank, or a cassette jam mid-dispense, can leave the ledger and the physical cash out of sync: the account was debited but no bills came out, or bills came out but the debit call timed out before confirming. The fix isn't "try harder" — it's treating every Transaction as carrying an idempotency key so a retried debit can't double-apply, logging the transaction's state (authorized / dispensed / confirmed) at each step, and running a periodic reconciliation job that compares the ATM's local transaction log against the Bank's ledger and auto-reverses (or queues for manual review) any mismatch. This is a real, everyday concern for ATM operators — "cash out of balance" cases are a standard category in bank operations, not a hypothetical edge case.
  • Running out of a specific denomination. CashDispenser.breakdownFor() has to try alternate combinations (e.g., no $20s left → fall back to $10s and $5s) before concluding the amount can't be made, and low-inventory thresholds per denomination should trigger a proactive alert to the Operator/Technician well before the machine actually fails a customer's request.
  • Multi-currency ATMs. Introduce a Currency on both Account and Transaction, group CashDispenser's cassettes by currency, and add an FX-rate lookup (a job for the same kind of pluggable rate/pricing engine used elsewhere) when a withdrawal's currency differs from the account's home currency.
  • Contactless / mobile-initiated withdrawals. A real, increasingly common feature: the customer authenticates and picks the amount inside their banking app, which hands the ATM a short-lived one-time code or QR code instead of a physical card and PIN. Modeling this cleanly means the ATM's authentication step becomes pluggable — a MobileSessionState that plays the same role HasCardState does (verify, then advance to SelectOperationState) without ever touching CardReader — rather than retrofitting card-specific logic to accept a code.

Follow-up Interview Questions

Walk through every State transition this ATM goes through end to end, from card insertion to a completed withdrawal.
IdleState starts as the current state. insertCard() moves it to HasCardState, which owns the PIN-attempt counter. A correct enterPin() moves it to SelectOperationState; an incorrect one either decrements the counter and stays in HasCardState (same object, recoverable), or — on the final attempt — retains the card and moves back to IdleState. From SelectOperationState, selectOperation() moves the machine into TransactionState, parameterized by which operation was chosen; that state executes the corresponding Transaction (e.g., Withdrawal.execute()) and, on completion, moves the ATM back to IdleState after ejecting the card. At every step, ATM.currentState is the only thing that changes; the ATM object itself never branches on "what screen am I in."
The customer asks to withdraw $70 but the ATM is completely out of $10 bills and has three $20s and a pile of $5s and $1s left. How should the denomination-breakdown algorithm handle that, and what should the customer see?
A pure greedy algorithm that always takes the largest bill first has to be willing to backtrack: try 3x$20 ($60), then need $10 more with no $10s available, so it drops to $5s and $1s for the remainder (2x$5). If no combination of the remaining inventory sums to exactly $70, CashDispenser.dispense() should not silently dispense the wrong amount or round -- it should signal "cannot make exact change" (e.g., throw a CannotDispenseExactAmountException) and the calling Withdrawal should catch that, decline the transaction (or offer the nearest amount the machine actually can dispense, like $65 or $75), and make sure no debit was applied for the failed attempt.
What happens if the Bank confirms the debit but the cash dispenser then jams and nothing comes out? How do you reconcile that?
This is the single most important real-world failure mode in this design, and it's exactly why Withdrawal.execute() is structured to authorize first, attempt to dispense second, and reverse on dispense failure -- but that reversal call can itself fail (network timeout, Bank service down). The durable fix is: give every Transaction an idempotency key so a retried debit or reversal can't double-apply; log each step (authorized, dispense-attempted, dispensed, confirmed) to a local transaction log the ATM keeps independently of the Bank's ledger; and run a periodic reconciliation job that diffs the ATM's log against the Bank's ledger, auto-reversing clear one-sided debits and flagging anything ambiguous for manual review. This is standard practice at real ATM operators, not a hypothetical -- "cash out of balance" is a named operational category.
Why does State scale better here than a single ATM class with an atmMode enum and if/else branches in every method?
With four states it barely matters -- the if/else version is annoying but survivable. It stops scaling the moment a new screen is added (a "confirm large withdrawal" prompt, an out-of-service screen, a mobile-session variant of HasCardState): every method (insertCard, enterPin, selectOperation, ejectCard) needs a new branch, in every method, and it's easy to silently forget one -- leaving, say, ejectCard() a no-op in a state where it should return the card. State turns "what can happen in this screen" into one class implementing one interface; the interface's method list is the exhaustive contract every state must answer, so adding a state means writing one new class rather than editing N existing methods and hoping nothing was missed.
Why is CashDispenser composed into ATM (owned, dies with it) rather than being a standalone service the ATM just calls?
A CashDispenser's cash inventory is meaningless outside the specific physical machine it's bolted into -- there's no scenario where "this dispenser" gets reassigned to a different ATM the way, say, a Product might move between categories in a catalog. That's exactly the composition signal (filled diamond): destroy the ATM (decommission the machine) and its CashDispenser's state goes with it. Contrast that with ATM's relationship to Bank, which is a plain association -- the same Bank instance is shared across every ATM in the network, and neither owns the other's lifecycle.
Why are Withdrawal, Deposit, Transfer, and BalanceInquiry modeled as separate Transaction subclasses instead of one Transaction class with a TransactionType enum field?
This is the opposite call from ParkingSpot in the parking-lot problem, and the distinction is the point: those five parking-spot types were behaviorally identical and differed only in a data tag, which argued for one class plus an enum. Here, execute() genuinely differs by type -- Withdrawal needs the CashDispenser and has a physical dispense-failure path that the others don't; Transfer needs a second Account and a two-sided debit/credit; BalanceInquiry doesn't touch money movement at all. That's real behavioral divergence, which is exactly when subclassing (or, equivalently, a Command-style hierarchy) earns its cost.
How would you prevent double-dispensing cash if the ATM loses power or reboots mid-transaction?
The dispense step and the "mark this transaction as dispensed" write need to be treated as a single unit of recovery: persist the transaction's state (authorized, dispense-in-progress, dispensed, failed) to durable local storage before actuating the physical dispenser, and on reboot the ATM checks for any transaction left in dispense-in-progress and reconciles it against the hardware's own dispense log rather than blindly re-attempting the dispense call. Combined with the idempotency key from the Bank-side reconciliation discussion, this closes both directions of the failure: a re-sent debit can't double-charge, and a re-attempted dispense can't double-pay.
Two withdrawal requests hit the same account at nearly the same instant from two different ATMs. How do you stop the account from going negative?
This has to be enforced at the Bank, not at either ATM, since the two requests never share in-process state. Bank.authorize() needs to perform its balance-and-daily-limit check and its reservation of funds atomically -- e.g. a single conditional update like "debit WHERE balance >= amount AND dailyWithdrawn + amount <= dailyLimit," checking that exactly one row changed -- rather than a separate read-then-write. Whichever request's update lands first succeeds; the second sees a failed conditional update and is declined, the same last-resource-race pattern that shows up any time two independent actors compete for one finite thing.
A customer loses power or walks away mid-transaction after the PIN is verified but before they pick an operation. What should the ATM do?
SelectOperationState should carry an inactivity timeout: if no selectOperation() call arrives within, say, 30 seconds, the ATM should eject the card (or retain it, per bank policy, if it's been sitting unclaimed) and transition back to IdleState on its own, rather than leaving the machine authenticated and waiting indefinitely for the next person who walks up. This is a good example of a transition the state machine needs even though no explicit customer action triggered it -- the state itself, not just the ATM's public methods, needs a way to time out.
How would you extend this design to support the contactless/mobile-initiated withdrawal flow where the customer starts the transaction on their phone?
Introduce a new state, e.g. MobileSessionState, that plays the same structural role as HasCardState -- it's reached by a different trigger (the ATM scanning a one-time code or QR from the customer's banking app instead of insertCard()+enterPin()) but converges on the same SelectOperationState once authenticated. Because ATMState is an interface, this is additive: no existing state's code changes, CardReader is simply never invoked for this path, and TransactionState and every Transaction subtype downstream are completely unaware of which authentication path got the customer there.

Key Takeaways

Key Takeaways
  • State is the headline pattern here: ATMState's four methods form one exhaustive contract, every concrete state answers it differently, and ATM only ever delegates to currentState -- it never branches on "what screen am I in."
  • The state-swap idiom (a state calling atm.setState(new NextState())) is what makes adding a new screen additive -- one new class -- instead of an edit to every existing method's conditional.
  • "Can't make exact change" is a real, first-class failure mode for CashDispenser -- the algorithm must try alternate denomination combinations and explicitly signal failure rather than silently rounding or over/under-dispensing.
  • Debit-succeeds-but-dispense-fails (and its mirror) is the single most important edge case to raise unprompted; the fix is idempotency keys plus a periodic reconciliation job, not "add a try/catch."
  • Where Transaction subtypes and ParkingSpot subtypes diverge is instructive: Transaction subclasses because execute() genuinely differs per type, while a data-only distinction elsewhere would argue for one class and an enum instead.
