OBJECT ORIENTED DESIGN

Design an Airline Management System

The airline management problem looks like a bigger, fancier parking lot at first glance — flights instead of spots, passengers instead of vehicles — but it hides a genuinely different modeling challenge: a Flight (say, "AA100: JFK → LAX, departing 8:05 AM daily") is not a thing anyone ever boards. What a passenger actually boards is one specific day's occurrence of that route, with its own seat map, its own on-time/delayed/cancelled status, and its own set of paying customers. Missing that split — modeling "the flight" as a single object that somehow also tracks today's seat availability — is the single most common mistake candidates make on this problem, and interviewers ask it specifically to see whether you catch it. Treat this page as the template for any "recurring scheduled resource with a per-occurrence state" problem: the same template/instance shape reappears in movie showtimes (a movie vs. a specific 7:30 PM screening), hotel room-night availability, and recurring event ticketing.

Problem Statement

Design an airline's flight-booking and reservation system: passengers search for flights between an origin and destination on a given date, book one or more seats in a chosen cabin class on a specific date's flight, check in online within a fixed window before departure to receive a boarding pass with a seat assignment, and receive notifications if that flight's status changes (delayed, cancelled). Airline staff configure the airline's aircraft fleet, the airports it serves, and its flight routes/schedules, and can update a flight's status — which must fan out a notification to every passenger holding a confirmed reservation on that date's flight. Interviewers use this problem to see whether you recognize that a route (e.g., "AA100: JFK to LAX, departs daily at 8:05 AM") and a specific day's occurrence of that route are two different objects with two different lifecycles and two different sets of responsibilities, and whether you can design a seat-booking flow that never double-books a physical seat under concurrent requests.

Requirements

  1. Passengers can search flights by origin, destination, and date.
  2. A Flight is a route/schedule template (e.g., "AA100: JFK to LAX") that can operate on multiple dates; each date is a distinct FlightInstance with its own seat map, availability, and status.
  3. Each FlightInstance carries a status — on-time, delayed, cancelled, or departed — independent of every other date the same Flight operates.
  4. Customers book one or more seats on a specific FlightInstance, choosing a cabin class (Economy, Business, First) with different pricing and seat maps.
  5. The system must prevent double-booking the same seat on the same FlightInstance under concurrent requests.
  6. Customers can check in online within a fixed check-in window before departure and receive a boarding pass with a seat assignment.
  7. The airline can delay or cancel a FlightInstance, which must trigger a notification to every passenger holding a confirmed reservation on it.
  8. Admin manages Aircraft, Airports, and Flights/schedules; crew assignment is tracked at a high level (which crew is on a given FlightInstance) without modeling crew-legality rules (duty hours, qualifications, rest requirements) in depth.
  9. Customers can cancel a booking before departure.

Actors & Use Cases

Three actors touch the system, and — same litmus test as any OOD problem — each one initiates at least one use case none of the others can:

  • Passenger — searches flights, books seats, checks in, views their boarding pass, and cancels a booking. The only actor who actually holds a reservation.
  • Airline Staff / Admin — configures the airline side of the system: aircraft, airports, flights, and schedules, and updates a FlightInstance's status when reality changes (delay, cancellation). Never touches an individual passenger's seat selection.
  • System — not a person; the background component that arbitrates seat holds during booking (so two passengers can't both claim the same seat) and drives notification dispatch the moment a FlightInstance's status changes. Modeling it as its own actor keeps "who initiated this" honest: a notification doesn't send itself out of nowhere, the System sends it in reaction to a status update Admin made.

Primary use cases: Search Flights, Book Seat(s), Check In, Cancel Booking, Update Flight Status (admin), and Add/Modify Flight Schedule (admin).

Key Classes

AirlineThe carrier itself; name and airline code, and the set of Flights it operates.

Class Diagram

Figure 2. Flight —filled diamond→ FlightInstance —filled diamond→ FlightSeat is the backbone of this design: a Flight is a route/schedule template, each FlightInstance is one date's actual occurrence with its own aircraft, status, and seat map, and each FlightSeat tracks one physical seat's booked/free state for that one date. Reservation associates a Passenger with one or more FlightSeats; FlightInstance and FlightSeat each depend on («uses») an enum (FlightStatus, CabinClass) rather than subclassing.

Why Flight and FlightInstance are two separate classes, not one. It's tempting to model a single Flight class with a date field and call it done — and that's exactly the shortcut that trips candidates up on this problem. A Flight like "AA100: JFK to LAX, departs daily at 8:05 AM" is a template: it exists once, in a schedule, whether or not a single seat has ever been sold on any date. What a passenger actually searches for, books, and boards is one specific day's occurrence of that template — today's AA100, not "AA100" in the abstract. Those two things have genuinely different lifecycles and different responsibilities: the Flight rarely changes (a schedule change is a deliberate admin action affecting every future date at once), while a FlightInstance changes constantly and independently of every other date — today's AA100 can be delayed while tomorrow's AA100 departs on time, and today's seat map can be half-empty while next Tuesday's is sold out. Collapsing them into one class forces awkward questions: does a "delayed" flag on Flight mean the whole route is delayed forever, or just today? Does the seat map belong to the route or to today's specific tail number and cabin configuration? Splitting them resolves all of that cleanly — Flight owns zero or more FlightInstances (composition: a filled diamond, since an instance has no meaning outside its owning Flight), and each FlightInstance independently owns its own aircraft assignment, status, and list of FlightSeats (a second composition, for the same reason: a FlightSeat for July 30th's flight is meaningless once that instance is done). This is also precisely why FlightInstance, not Flight, carries the operational aircraft field — Flight's defaultAircraft is just the plan; the FlightInstance's actual aircraft can diverge from it the moment an aircraft swap happens (see Extensibility & Edge Cases below), and only the instance-level field needs to change when that occurs.

Key Flow: Booking a Seat on a Specific Date (Activity Diagram)

Booking only makes sense once the system has resolved an abstract "route on this date" search down to one or more concrete FlightInstances — that resolution step is easy to skip when sketching this quickly, but it's the whole point of the Flight/FlightInstance split showing up in a runtime flow. From there, seat availability is checked before any payment is attempted, and a seat is only held — not permanently booked — until payment actually clears.

Key Flow: Flight Delay Notification (Sequence Diagram)

A single status change on a single FlightInstance is, structurally, a one-to-many fan-out: every passenger with a confirmed Reservation on that instance needs to hear about it. That fan-out is exactly what Notification-as-Observer is for (see Design Patterns Applied below) — FlightInstance doesn't need to know who's listening or how many passengers are affected, it just publishes "my status changed."

Figure 4. Sequence diagram for a delay: one status change on one FlightInstance fans out to every confirmed Reservation on it via Notification. Drawn here as a loop for clarity, but at real scale this must be an asynchronous, queued dispatch (publish one event per affected reservation) rather than a synchronous in-process loop that blocks the status-update call until every passenger has been notified.

The diagram draws the fan-out as a loop for readability, but that's a whiteboard simplification worth flagging out loud in an interview: a real implementation should publish one event per affected reservation to a queue (or a single batch event consumed asynchronously) rather than looping synchronously inside the request that updated FlightInstance's status. A flight with 300 confirmed passengers should not make Admin's "mark this flight delayed" API call wait for 300 notification sends (some of which may hit a slow downstream email/SMS provider) before returning success — that's an availability and latency problem waiting to happen, and it's the natural seam where this LLD question starts to lean on HLD concepts (message queues, at-least-once delivery, retries) without needing to become a full HLD design.

Design Patterns Applied

Name the pattern and the forcing function together, not just the name:

  • Composition (Flight → FlightInstance → FlightSeat) — this is the load-bearing relationship in the whole design, covered in detail above: an instance or a seat has zero meaning once its owning Flight/FlightInstance is gone, so both relationships get the filled-diamond treatment rather than a weaker aggregation. The practical payoff: retiring a Flight (route discontinued) cleanly cascades to every FlightInstance and FlightSeat that only existed because of it, with no orphaned seat records floating around referencing a route that no longer exists.
  • Observer (Notification reacting to a FlightInstance status change) — FlightInstance doesn't call a hardcoded sendEmail() or sendSms() when Admin marks it delayed; it publishes a status-changed event, and one or more listeners (a Notification dispatcher today, potentially a rebooking-suggestion service or a refund-eligibility checker tomorrow) react independently. This is exactly the seam the delay-notification sequence diagram above walks through, and it's also what lets the fan-out move from an in-process loop to an async queue consumer without FlightInstance's code changing at all — the publisher only ever knows "something changed," never how many listeners there are or how they deliver.
  • State (FlightInstance's FlightStatus) — SCHEDULED is the only valid starting point; from there an instance can move to ON_TIME or DELAYED, and only from one of those into DEPARTED, or from almost any pre-departure state into CANCELLED. Modeling this as a guarded state machine inside updateStatus() (reject a transition like DEPARTED → SCHEDULED outright) is what stops a fat-fingered admin update or a race between two status-update calls from putting a FlightInstance into a nonsensical state — e.g., "cancelled" three hours after it already shows "departed."
  • Builder (extension idea, not load-bearing in the base design) — if Reservation grows to cover multiple passengers, a mix of cabin classes, and add-ons (extra baggage, seat upgrades, travel insurance), a ReservationBuilder that accumulates those pieces step by step before a single build() call reads better than a Reservation constructor with an ever-growing, easy-to-misorder parameter list. It's mentioned here as the natural next pattern to reach for, not forced into the base design, since the requirements above describe a single-passenger, single-cabin-class booking.

Code Skeleton

Fields and method signatures only — not a runnable program. FlightSeat.holdIfFree is worked out in enough detail to show the concurrency-safe claim, since that's exactly what interviewers probe on for this problem.

    SCHEDULED, ON_TIME, DELAYED, DEPARTED, CANCELLED
}

public enum CabinClass {
    ECONOMY, BUSINESS, FIRST
}

    HELD, CONFIRMED, CANCELLED, CHECKED_IN
}

public class FlightInstance {
    private final String instanceId;
    private final Flight flight;
    private final LocalDate flightDate;
    private LocalDateTime scheduledDeparture;
    private LocalDateTime scheduledArrival;
    private Aircraft aircraft;              // may diverge from flight's defaultAircraft after a swap
    private volatile FlightStatus status;
    private final List<FlightSeat> seats;

    public FlightInstance(Flight flight, LocalDate flightDate, Aircraft aircraft) {
        // seats are generated from aircraft.getSeatConfig(), one FlightSeat per physical seat
    }

    public List<FlightSeat> availableSeats(CabinClass cabin);

    public synchronized void updateStatus(FlightStatus newStatus) {
        if (!isValidTransition(status, newStatus)) {
            throw new IllegalStateException("Cannot move from " + status + " to " + newStatus);
        }
        this.status = newStatus;
        // publish a status-changed event here -- Observer listeners (Notification, etc.) react
    }

    public void swapAircraft(Aircraft replacement);   // re-derives the seat map, see Extensibility
    private boolean isValidTransition(FlightStatus from, FlightStatus to);
    public FlightStatus getStatus();
    public LocalDate getFlightDate();
}
public class FlightSeat {
    private final String seatNumber;
    private final CabinClass cabinClass;
    private final BigDecimal fare;
    private volatile boolean booked;
    private volatile String heldByReservationId;
    private volatile Instant holdExpiresAt;

    // Concurrency-safe claim -- the same atomic-conditional-update idea used for
    // seat locking in the Movie Ticket Booking page: either a synchronized guard
    // like this in-memory version, or a "WHERE booked = false" conditional UPDATE
    // at the persistence layer, checking that exactly one row changed.
    public synchronized boolean holdIfFree(String reservationId, Duration holdTtl) {
        boolean heldBySomeoneElseActively =
            heldByReservationId != null
            && !heldByReservationId.equals(reservationId)
            && holdExpiresAt != null && Instant.now().isBefore(holdExpiresAt);

        if (booked || heldBySomeoneElseActively) {
            return false;
        }
        this.heldByReservationId = reservationId;
        this.holdExpiresAt = Instant.now().plus(holdTtl);
        return true;
    }

    public synchronized void confirmBooking(String reservationId) {
        if (!reservationId.equals(heldByReservationId)) {
            throw new IllegalStateException("Seat is not held by this reservation");
        }
        this.booked = true;
        this.holdExpiresAt = null;
    }

    public synchronized void release(String reservationId) {
        if (reservationId.equals(heldByReservationId)) {
            this.heldByReservationId = null;
            this.holdExpiresAt = null;
        }
    }

    public boolean isFree();
    public String getSeatNumber();
    public CabinClass getCabinClass();
}
public class Reservation {
    private final String reservationId;
    private final Passenger passenger;
    private final FlightInstance flightInstance;
    private final List<FlightSeat> seats;
    private ReservationStatus status;
    private String bookingReference;

    public Reservation(Passenger passenger, FlightInstance flightInstance, List<FlightSeat> seats) { /* ... */ }

    public void confirm();
    public void cancel();
    public BoardingPass checkIn(Instant now);
    public boolean isWithinCheckInWindow(Instant now);
    public ReservationStatus getStatus();
}

Extensibility & Edge Cases

  • Connecting flights / multi-leg itineraries. A single Reservation should be able to span more than one FlightInstance (e.g., JFK→ORD then ORD→LAX). Model this by letting Reservation hold a list of "legs," where each leg pairs a FlightInstance with the seats booked on it, rather than assuming one Reservation maps to exactly one FlightInstance. The booking flow's seat-hold/payment logic barely changes — it just holds seats across every leg before confirming any of them, since a passenger shouldn't end up confirmed on leg 1 and rejected on leg 2 of the same trip.
  • Overbooking is a deliberate policy, not a bug. Airlines intentionally oversell Economy cabins on routes with predictable no-show rates — this is a real, deliberate business rule, not a modeling oversight to "fix." Represent it by giving a FlightInstance's cabin an overbookLimit alongside its physical seat count: availableSeats(cabin) can report bookable capacity up to physicalSeats + overbookLimit, while actual physical-seat assignment only happens at check-in/gate time, once no-shows are known. The system still must never assign the same physical seat to two boarded passengers — overbooking oversells reservations, never physical FlightSeats at boarding time.
  • Standby passengers. When a FlightInstance is fully booked (or oversold beyond what no-shows free up), a passenger can be placed on a StandbyList tied to that instance, ranked by priority (fare class, loyalty tier, check-in time). If a seat frees up (cancellation, confirmed no-show), the system offers it to the next standby passenger rather than leaving it empty.
  • Aircraft swap and seat reassignment. When a FlightInstance's aircraft changes (mechanical substitution, capacity change), its previously generated FlightSeats may no longer correspond to real seats on the new aircraft — a different cabin configuration can mean fewer Business seats, or an entirely different seat-numbering scheme. swapAircraft() must regenerate the seat map from the new aircraft's seatConfig and re-map existing confirmed Reservations onto the closest equivalent seat (same cabin class at minimum), triggering a Notification to any passenger whose specific seat number changed — the same Observer channel used for delays, just a different event type.

Follow-up Interview Questions

Why does this design use separate Flight and FlightInstance classes instead of a single Flight class with a date field?
A Flight is a route/schedule template ("AA100: JFK to LAX, daily") that exists independent of any specific day, while a FlightInstance is one date's actual occurrence — the thing that is actually booked, boarded, delayed, or cancelled. Collapsing them forces awkward semantics: does "delayed" apply to the whole recurring route or just today, and does the seat map belong to the route or to today's specific aircraft and cabin configuration? Splitting them lets Flight own zero or more FlightInstances (a clean composition), with each FlightInstance independently tracking its own status, aircraft, and seat availability — so today's flight can be delayed while tomorrow's departs on time, without either affecting the other.
A FlightInstance with 300 confirmed passengers gets marked DELAYED. How should the resulting notification fan-out actually be implemented at scale?
Not as a synchronous loop inside the status-update call — that ties Admin's "mark delayed" request to the latency (and failure modes) of 300 individual notification sends, some of which may hit a slow downstream email/SMS/push provider. Instead, updateStatus() should publish a single "FlightInstance status changed" event (or one event per affected reservation) to a queue, and a separate, horizontally scalable consumer fans it out to Notification asynchronously with retries. The status update itself should complete in milliseconds regardless of how many passengers are affected; notification delivery is an eventually-consistent side effect, not something the caller should have to wait on.
Isn't allowing more reservations than physical seats (overbooking) just a bug you should fix?
No — overbooking Economy cabins on routes with predictable no-show rates is a deliberate, real airline business rule, not an oversight. The model should represent it explicitly: an overbookLimit per cabin on a FlightInstance lets bookable capacity exceed physical seat count, while physical-seat assignment is deferred to check-in/gate time once no-shows are known. The one thing the design must never allow, overbooking or not, is assigning the same physical seat to two boarded passengers at gate time — overbooking oversells reservations, not physical seats.
How would you extend this design to support multi-leg, connecting itineraries?
Let a single Reservation span more than one FlightInstance by modeling it as a list of legs, where each leg pairs a FlightInstance with the specific seats booked on it, instead of assuming a strict one-Reservation-to-one-FlightInstance relationship. The seat-hold/payment flow generalizes naturally: hold seats across every leg first, and only confirm the whole Reservation once every leg's hold succeeds and payment clears — so a passenger is never left confirmed on one leg of a connection but rejected on the next.
Two passengers try to book the same seat on the same FlightInstance at nearly the same moment. How do you stop a double-booking?
The same atomic-conditional-claim shape used for seat locking generally: FlightSeat.holdIfFree() must check "is this seat free" and mark it held in one atomic step, either via a synchronized in-memory guard (as sketched in the Code Skeleton) or a "WHERE booked = false" conditional UPDATE at the persistence layer, verifying exactly one row changed. Whichever request's claim lands first wins the hold; the other's holdIfFree() call returns false and that passenger is shown the seat is no longer available. A naive "read status, decide it's free, then write held" sequence in application code is a textbook lost-update race.
Why does holdIfFree place a time-limited hold instead of instantly marking the seat booked?
Payment doesn't clear instantly — there's a real gap between "passenger selected this seat" and "payment succeeded," and a payment gateway can be slow or fail outright. If the seat were marked booked the moment it was selected, a passenger who abandons checkout or whose card is declined would permanently lock that seat away from everyone else. A TTL-bounded hold reserves the seat just long enough to complete payment; if the hold expires or payment fails, the seat automatically becomes claimable again, and confirmBooking() is the only path that turns a hold into a permanent booking.
Why does FlightStatus live on FlightInstance rather than on Flight?
Status is inherently a per-occurrence fact — today's AA100 can be delayed while every other date that same route operates on is unaffected. If status lived on Flight, marking one day's flight delayed would either have to (incorrectly) apply to the entire recurring schedule, or Flight would need its own separate per-date status map, which is just FlightInstance reinvented under a different name. Putting status on FlightInstance keeps each date's operational state independent and is what makes the guarded FlightStatus state machine (SCHEDULED → ON_TIME/DELAYED → DEPARTED/CANCELLED) meaningful per occurrence.
How would you model the check-in window and boarding pass generation?
Reservation.isWithinCheckInWindow(now) compares the current time against the FlightInstance's scheduled departure minus a configurable window (e.g., 24 hours before to 45 minutes before departure); checkIn() rejects the call outside that window. On success, checkIn() transitions the Reservation to CHECKED_IN and returns a BoardingPass carrying the passenger's confirmed seat, gate, and boarding group — generated from the Reservation's already-confirmed FlightSeat rather than re-running seat assignment, since seat selection already happened at booking time.
Why is CabinClass modeled as a simple enum rather than as a hierarchy of FlightSeat subclasses (EconomySeat, BusinessSeat, FirstSeat)?
All three cabin classes behave identically as far as FlightSeat's own responsibilities go — hold at most one passenger, answer isFree(), track a fare — and differ only in data (which cabin they belong to, and what that implies for price and seat map). That's the same signal as the parking-lot problem's spot-type decision: when subtypes share behavior and differ only in a data field, favor a single class plus an enum over a subclass per variant. If a future requirement needs real per-class behavior (e.g., only First seats expose a lieFlatRecline() method), that's the point where a per-cabin subtype or a small strategy object attached to the seat would earn its keep.

Key Takeaways

Key Takeaways
  • The single most important decision in this design: split Flight (route/schedule template) from FlightInstance (one date's actual occurrence) — a Flight is never booked or boarded, only a FlightInstance is.
  • Flight —filled diamond→ FlightInstance —filled diamond→ FlightSeat models real lifecycle ownership: none of the three exist meaningfully without the one above it.
  • Seat booking needs an atomic, TTL-bounded hold (holdIfFree) before payment, not an instant book/free flag — the same seat-locking shape that shows up anywhere a physical resource is claimed under concurrency.
  • A single FlightInstance status change is a one-to-many fan-out; model it with Observer, and implement the actual dispatch as an async/queued job, not a blocking loop inside the status-update call.
  • Overbooking, standby, and aircraft swaps are real airline operating policy, not edge cases to hand-wave away — a credible design represents them explicitly rather than pretending every flight boards exactly its physical seat count.
