CLOUD ARCHITECTURE

AWS (Amazon Web Services) — Cloud Architecture Tutorial

A complete, interview-ready architecture walkthrough: a global e-commerce checkout platform built end-to-end on AWS — requirements, capacity estimation, service mapping, honest cross-cloud trade-offs, data flow, Terraform, best practices, and common interview questions.

Use Case & Requirements

The Business Problem

A global e-commerce company needs to re-platform its checkout and order-processing API to serve customers worldwide. Today's system buckles during flash sales and can't guarantee latency or correctness at the scale the business now needs. The new platform must accept checkout requests from anywhere in the world, reserve inventory, capture a tokenized payment reference (never the raw card number — that stays with a certified payment processor), durably record the order, and notify every downstream system (fulfillment, notifications, fraud review, analytics) that a sale happened — all while never double-charging a customer or silently losing an order, even during a 10× traffic spike or a full regional outage.

Two very different consistency worlds live side by side in this system: the order/payment write path, where correctness is non-negotiable (an order must be written exactly once, and payment state must never be ambiguous), and the catalog/browse read path, where slightly stale data (a price shown a few seconds late, a sold-out item still visible for a moment) is a perfectly acceptable trade for massive read scale and low latency. A good architecture treats these as two different problems with two different datastores, not one database trying to be everything.

Functional Requirements

  1. Accept checkout requests from web and mobile clients globally.
  2. Reserve inventory against the product catalog as part of the checkout transaction.
  3. Process and tokenize a payment reference via an external, certified payment processor (raw PAN never touches this system).
  4. Write a durable, uniquely-identified order record once the transaction is confirmed.
  5. Publish an order-placed event so downstream consumers (fulfillment, notifications, fraud review, analytics) can react asynchronously.
  6. Serve the product catalog / browse experience (~50 million SKUs) with low-latency reads worldwide.

Non-Functional Requirements

  • Throughput: steady-state ~500 transactions/second, peak 5,000 transactions/second during flash-sale events (a 10× burst).
  • Latency: sub-150ms p99 for checkout API calls, globally.
  • Availability: 99.95% SLA.
  • Consistency: strong consistency for order/payment writes (never double-charge, never lose an order); eventual consistency is acceptable for catalog/browse reads.
  • Compliance: PCI-DSS-adjacent handling — only tokenized card references are stored here; raw PAN handling is delegated entirely to a certified payment processor.
  • Deployment topology: multi-region active-active, for both latency (serve users from the nearest region) and disaster recovery.
  • Scale: ~200 million orders/year, ~50 million SKUs in the catalog, product images/assets served globally via CDN.

Capacity Estimation and Constraints

The numbers below are the ones that should visibly drive every service choice further down this page — particularly the split between a low-latency, strongly-consistent order store and a massive-scale, eventually-consistent catalog store.

Peak vs. steady-state throughput Steady-state: 500 TPS × 86,400 sec/day ≈ 43.2 million checkout-API requests/day
Peak flash-sale: 5,000 TPS sustained for a ~2-hour window = 5,000 × 7,200 sec = 36 million requests in that window alone
Peak ÷ steady ratio = 5,000 ÷ 500 = 10× — every tier (ALB, ECS task count, Aurora connections, ElastiCache) must be able to scale roughly 10× on short notice
Orders/year vs. API TPS — these are not the same number 200,000,000 orders/year ÷ (365 × 24 × 3,600 sec) ≈ 6.34 completed orders/sec on average
500 (steady-state API TPS) ÷ 6.34 (average completed-order rate) ≈ 79×
In other words, roughly 79 checkout-API calls (cart validation, address checks, payment tokenization round-trips, retries, idempotent re-submits) occur for every one finalized order at steady state — Aurora's write volume tracks the much smaller "committed order" rate, while ECS/Fargate and the ALB must be sized to the full API call volume
Order storage growth (3-year horizon) Average order record (header + ~3 line items + shipping/billing refs + tokenized payment reference + audit/state-transition metadata) ≈ 2 KB
200,000,000 orders/year × 3 years = 600,000,000 order records
Raw logical storage = 600,000,000 × 2 KB ≈ 1.2 TB
Aurora's storage layer already replicates data 6 ways across 3 AZs at no extra operational effort; adding a second region via Aurora Global Database roughly doubles the logical footprint — plan for ≈2.4 TB of Aurora-managed storage, plus ~25–30% headroom for indexes/WAL → ≈3 TB planning figure
Catalog size (DynamoDB) 50,000,000 SKUs × ≈3 KB average item (title, description, attributes, pricing, inventory pointers, image references) ≈ 150 GB of catalog data
150 GB is trivially small for DynamoDB — it's chosen here for read latency and request-rate scale, not because the data volume itself is large
Product image storage and CDN egress 50,000,000 SKUs × ~6 images/SKU × ~250 KB/image ≈ 75 TB total in S3
Assumed browsing volume: ~300,000,000 catalog-browsing sessions/month × ~40 image views/session × ~150 KB (CDN-optimized size) ≈ 1.8 PB/month served to end users
With a CloudFront cache-hit ratio of ~90%+ (typical for popular product imagery), origin (S3) egress falls to ≈180 TB/month — the remaining ≈1.62 PB/month is absorbed entirely at CloudFront's edge and never touches the origin

Architecture Overview

Why AWS for This Workload

AWS brings the broadest managed-service catalog of any of the major clouds, the largest hiring pool of engineers already fluent in its core primitives (ECS/EKS, Aurora, SNS/SQS, IAM), and the most mature multi-service integration story — CloudFront, WAF, Shield, ALB, ECS, and Aurora click together with comparatively little glue code. For a platform processing 200 million orders a year against a 50-million-SKU catalog, Aurora PostgreSQL is a proven, "boring in a good way" choice for the order ledger: strong consistency within a region, automatic 6-way storage replication across 3 Availability Zones, typical failover in under a minute, and fast (sub-second, though asynchronous) cross-region replication via Aurora Global Database.

Be honest about the one requirement AWS cannot give you "for free" the way GCP Spanner can: true multi-region active-active writes with strong consistency. Aurora Global Database's cross-region replication is asynchronous — typically under a second of lag, but never zero — so if two regions both accepted a conflicting write for the same order at nearly the same instant, AWS gives you no built-in conflict resolution. The architecturally honest options are (a) route each customer/order to a single "home region" for writes, using multi-region purely for read latency and disaster recovery rather than simultaneous same-row writes, or (b) build an explicit conflict-detection and reconciliation layer on top. This is a genuine trade-off against GCP Spanner's synchronous, externally-consistent global writes: Spanner is architecturally simpler for teams that truly need global active-active writes on the same row, at the cost of Spanner's own operational model and a narrower non-Google talent pool.

Deep Dive — Compute: ECS/Fargate vs. EKS vs. EC2 Auto Scaling Groups vs. Lambda

The core checkout API is chosen to run on Amazon ECS on AWS Fargate. Against the named alternatives: EKS (managed Kubernetes) is the right call when an organization has already standardized its tooling, deployment pipelines, and operational muscle memory around Kubernetes — it is not a stronger technical fit for this workload specifically, it's a stronger fit when Kubernetes is already the org-wide default and the incremental cost of a second orchestration paradigm (ECS) outweighs Fargate's simplicity. Raw EC2 Auto Scaling Groups give the most low-level control (custom AMIs, specific instance families, bin-packing tuning) but push node patching, capacity planning, and cluster-level failure handling back onto the team — overhead this workload doesn't need to accept just to run a stateless HTTP API. Lambda is a legitimate option for the spiky, event-driven pieces of this system (e.g. the SQS-triggered fulfillment/notification/fraud-review consumers), where short-lived, bursty invocations map well onto Lambda's per-invocation billing and scaling model — but it is a weaker fit for the core checkout API itself, where sustained connection pools to Aurora, predictable p99 latency (cold starts are a real risk under Lambda), and long-lived in-memory caches favor a persistently-running container. Net: ECS/Fargate gives serverless container operations (no node fleet to manage) while still behaving like a normal long-running service for the checkout API's latency and connection-pooling needs, with EKS held in reserve for Kubernetes-standardized orgs and Lambda used surgically for the async fan-out.

Deep Dive — Primary Database: Aurora Global Database vs. DynamoDB Global Tables vs. Self-Managed Sharded Postgres

Aurora PostgreSQL with Aurora Global Database is the recommended choice for the order/payment ledger. It gives strong, transactional (ACID) consistency within a region — essential for "never double-charge, never lose an order" — plus fast, low-single-digit-second RPO cross-region replication for disaster recovery and read scale-out, without the application needing to manage sharding logic itself. DynamoDB Global Tables was seriously considered, since it does offer true multi-region active-active writes — but its conflict resolution is "last writer wins" based on timestamp, which is the wrong default for financial transactions where silently discarding one of two conflicting writes is a correctness bug, not a minor edge case; DynamoDB also trades away the relational joins and multi-row ACID transactions that order processing (order header + line items + inventory decrement, atomically) benefits from. A self-managed, manually-sharded Postgres fleet (e.g. via Citus or application-level sharding) gives full control and could technically be made to work, but re-implements — at much higher operational cost and risk — problems Aurora already solves as a managed service: automatic storage replication, backups, failover, and monitoring. Aurora Global Database is chosen specifically because it matches this workload's actual requirement (strong regional consistency, fast DR, acceptable async cross-region lag with an explicit region-affinity strategy for writes) rather than a requirement it doesn't have (synchronous global active-active writes, which is Spanner's problem to solve, not Aurora's).

Data Flow

A single, synchronous checkout request, end to end:

  1. Client sends an HTTPS checkout request, resolved by Route 53's latency-based/geoproximity routing to the nearest healthy region.
  2. The request hits CloudFront, where AWS WAF inspects it against managed rule groups and AWS Shield Advanced screens for DDoS patterns.
  3. CloudFront forwards to the regional Application Load Balancer, which routes to a healthy ECS/Fargate target in the checkout API's target group.
  4. The ECS/Fargate task validates the cart contents and checks an idempotency key (so a client retry never creates a duplicate order).
  5. The task reserves inventory as part of an Aurora transaction (a soft hold, decremented atomically alongside the order write).
  6. The task calls out to the external, certified payment processor to tokenize the payment method and obtain a payment reference — the raw card number never enters this system.
  7. Aurora commits the order record (order header, line items, tokenized payment reference, inventory decrement) in a single strongly-consistent transaction — this is the one step in the whole flow that must never be "eventually" correct.
  8. The task publishes an order-placed event to an SNS topic.
  9. The task returns a 200 response to the client, targeting sub-150ms p99 for the entire round trip.

The async fan-out that follows every completed order, decoupled from the client-facing latency budget above:

  1. The SNS topic fans the order-placed event out to three independent SQS queues: fulfillment, notifications, and fraud-review.
  2. Each queue is consumed by its own service, scaling and retrying independently of the others — a slow fraud-review consumer never backs up fulfillment.
  3. SQS gives at-least-once delivery, so every consumer is built to be idempotent on order_id (e.g. an upsert or a processed-events dedup table) rather than assuming exactly-once semantics.
  4. Failed deliveries land in a per-queue dead-letter queue after a bounded number of retries, so poison messages don't block the rest of the queue.
Figure 2. Request lifecycle for a single checkout — the synchronous path (left) stays on the sub-150ms p99 latency budget; the async fan-out (right) branches off after the SNS publish and runs fully decoupled from that budget.

Infrastructure as Code (IaC)

This platform is provisioned with Terraform using the official hashicorp/aws provider. Resource arguments have shifted meaningfully between major provider versions (for example, several 4.x → 5.x changes to aws_lb_target_group and IAM resource defaults) — always pin an exact provider version and check the current documentation before upgrading, rather than assuming last year's syntax still applies.

The script below provisions core networking and compute only — a VPC across two Availability Zones, public/private subnets, an Internet Gateway and per-AZ NAT Gateways, security groups scoped to least privilege, an Application Load Balancer, and an ECS cluster/service/task definition on Fargate. It intentionally does not provision every service shown in the architecture diagram (Aurora, DynamoDB, SNS/SQS, etc.) so the example stays focused and readable.

terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.60" # pin an exact minor version; arguments shift across major versions
    }
  }
}

provider "aws" {
  region = var.region
}

# ---------------------------------------------------------------------------
# Variables (values supplied via *.tfvars per environment — dev/staging/prod)
# ---------------------------------------------------------------------------
variable "region" {
  description = "AWS region for this deployment (one per active-active region)"
  type        = string
  default     = "us-east-1"
}

variable "vpc_cidr" {
  description = "CIDR block for the checkout-platform VPC"
  type        = string
  default     = "10.20.0.0/16"
}

variable "az_count" {
  description = "Number of Availability Zones to spread subnets across"
  type        = number
  default     = 2
}

variable "checkout_image" {
  description = "Container image URI for the checkout API (from ECR)"
  type        = string
}

variable "environment" {
  description = "Environment name (dev / staging / prod) — also used for tagging"
  type        = string
  default     = "prod"
}

variable "acm_certificate_arn" {
  description = "ARN of the ACM certificate bound to the checkout API domain"
  type        = string
}

# ---------------------------------------------------------------------------
# Networking — VPC, subnets, Internet Gateway, NAT Gateways
# ---------------------------------------------------------------------------
data "aws_availability_zones" "available" {
  state = "available"
}

resource "aws_vpc" "checkout" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name        = "checkout-vpc-${var.environment}"
    Environment = var.environment
  }
}

# Public subnets — hold the ALB and the NAT Gateways, one per AZ
resource "aws_subnet" "public" {
  count                   = var.az_count
  vpc_id                  = aws_vpc.checkout.id
  cidr_block              = cidrsubnet(var.vpc_cidr, 8, count.index)
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name = "checkout-public-${count.index}"
    Tier = "public"
  }
}

# Private subnets — hold the ECS/Fargate tasks (and, in the full design, Aurora), one per AZ
resource "aws_subnet" "private" {
  count             = var.az_count
  vpc_id            = aws_vpc.checkout.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index + 10)
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "checkout-private-${count.index}"
    Tier = "private"
  }
}

resource "aws_internet_gateway" "checkout" {
  vpc_id = aws_vpc.checkout.id

  tags = { Name = "checkout-igw-${var.environment}" }
}

# One Elastic IP + NAT Gateway per AZ, so a single AZ outage never removes
# outbound internet access (e.g. calls to the external payment processor)
# for tasks running in the other AZ.
resource "aws_eip" "nat" {
  count  = var.az_count
  domain = "vpc"

  tags = { Name = "checkout-nat-eip-${count.index}" }
}

resource "aws_nat_gateway" "checkout" {
  count         = var.az_count
  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = aws_subnet.public[count.index].id

  tags = { Name = "checkout-nat-${count.index}" }

  depends_on = [aws_internet_gateway.checkout]
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.checkout.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.checkout.id
  }

  tags = { Name = "checkout-public-rt" }
}

resource "aws_route_table_association" "public" {
  count          = var.az_count
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

# Private route tables — one per AZ, each pointed at that AZ's own NAT Gateway
resource "aws_route_table" "private" {
  count  = var.az_count
  vpc_id = aws_vpc.checkout.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.checkout[count.index].id
  }

  tags = { Name = "checkout-private-rt-${count.index}" }
}

resource "aws_route_table_association" "private" {
  count          = var.az_count
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}

# ---------------------------------------------------------------------------
# Security groups
# ---------------------------------------------------------------------------

# ALB security group — only HTTPS from the internet reaches the ALB.
resource "aws_security_group" "alb" {
  name        = "checkout-alb-sg-${var.environment}"
  description = "Allow inbound HTTPS to the checkout ALB"
  vpc_id      = aws_vpc.checkout.id

  ingress {
    description = "HTTPS from CloudFront / clients"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Return traffic to ECS tasks in the VPC only"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = [var.vpc_cidr]
  }

  tags = { Name = "checkout-alb-sg" }
}

# ECS task security group — reachable ONLY from the ALB security group,
# never directly from the internet or any other CIDR. No default
# allow-all egress; egress is explicitly scoped below.
resource "aws_security_group" "ecs_tasks" {
  name        = "checkout-ecs-sg-${var.environment}"
  description = "Allow inbound traffic to checkout tasks only from the ALB"
  vpc_id      = aws_vpc.checkout.id

  ingress {
    description     = "Traffic from the ALB only"
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]
  }

  egress {
    description = "HTTPS egress (payment processor, AWS service APIs)"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description = "Postgres egress to Aurora"
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = [var.vpc_cidr]
  }

  tags = { Name = "checkout-ecs-sg" }
}

# ---------------------------------------------------------------------------
# Application Load Balancer
# ---------------------------------------------------------------------------
resource "aws_lb" "checkout" {
  name               = "checkout-alb-${var.environment}"
  internal           = false
  load_balancer_type = "application"
  security_groups    = [aws_security_group.alb.id]
  subnets            = aws_subnet.public[*].id

  enable_deletion_protection = true

  tags = { Name = "checkout-alb" }
}

resource "aws_lb_target_group" "checkout" {
  name        = "checkout-tg-${var.environment}"
  port        = 8080
  protocol    = "HTTP"
  vpc_id      = aws_vpc.checkout.id
  target_type = "ip" # required for Fargate tasks — there is no static EC2 instance to attach

  health_check {
    path                = "/healthz"
    healthy_threshold   = 3
    unhealthy_threshold = 3
    interval            = 15
    timeout             = 5
    matcher             = "200"
  }

  tags = { Name = "checkout-tg" }
}

resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.checkout.arn
  port              = 443
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  certificate_arn   = var.acm_certificate_arn

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.checkout.arn
  }
}

# ---------------------------------------------------------------------------
# ECS cluster, task definition, and service (Fargate launch type)
# ---------------------------------------------------------------------------
resource "aws_ecs_cluster" "checkout" {
  name = "checkout-cluster-${var.environment}"

  setting {
    name  = "containerInsights"
    value = "enabled" # feeds CloudWatch Container Insights dashboards
  }
}

resource "aws_iam_role" "ecs_execution" {
  name = "checkout-ecs-execution-role-${var.environment}"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "ecs-tasks.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy_attachment" "ecs_execution" {
  role       = aws_iam_role.ecs_execution.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

# Task role — the identity the *application code* assumes at runtime.
# Least-privilege: scope this to only what the checkout API actually needs
# (e.g. Secrets Manager read, SNS publish), never blanket AWS access.
resource "aws_iam_role" "ecs_task" {
  name = "checkout-ecs-task-role-${var.environment}"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "ecs-tasks.amazonaws.com" }
    }]
  })
}

resource "aws_ecs_task_definition" "checkout" {
  family                   = "checkout-api"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc" # required for Fargate

Production practice
Store Terraform state in a remote S3 backend with DynamoDB-based state locking, so two engineers (or two CI runs) can never corrupt state by writing concurrently. Keep separate .tfvars files or workspaces per environment (dev/staging/prod) rather than branching the configuration itself. And always run terraform plan in CI — posted as a reviewable artifact on the pull request — before any terraform apply runs against a real environment.

Best Practices

Security

  • IAM least-privilege roles and policies for every service identity — no wildcard actions or resources in production policies.
  • ECS task IAM roles instead of static, long-lived credentials baked into containers or environment variables.
  • AWS KMS customer-managed keys (CMKs) for encryption at rest across Aurora, S3, and EBS, with key usage audited via CloudTrail.
  • TLS everywhere in transit, using ACM-issued certificates on the ALB listener and CloudFront distribution.
  • Security Groups scoped to least privilege (e.g. ECS tasks reachable only from the ALB security group) plus NACLs for defense-in-depth network segmentation.
  • AWS Secrets Manager with automatic rotation for database credentials and third-party API keys.
  • AWS WAF managed rule groups covering common web attack patterns (SQLi, XSS, known bad bots) in front of the checkout API.

Monitoring, Logging and Alerting

  • CloudWatch dashboards and alarms tied directly to the platform's SLOs (p99 latency, error rate, availability) rather than generic infrastructure metrics alone.
  • CloudWatch Logs with structured (JSON) logging and metric filters, so specific error classes (e.g. payment tokenization failures) can trigger their own alarms.
  • AWS X-Ray for distributed tracing across the full checkout call path (ALB → ECS → Aurora/SNS), essential for diagnosing which hop is responsible when p99 latency creeps up.
  • Route 53 health checks driving automated failover — a region that fails its health check is automatically removed from the latency-based routing pool.

Cost Optimization

  • AWS Cost Explorer — as of November 2025, Cost Explorer provides AI-powered 18-month cost forecasts with explainable insights, and is free to use.
  • AWS Compute Optimizer — right-sizing recommendations for ECS/Fargate task sizing and EBS volumes, based on actual observed utilization rather than provisioned capacity.
  • AWS Trusted Advisor — flags idle load balancers, idle RDS/Aurora instances, and unassociated Elastic IPs that are quietly accumulating cost.
  • The newer AWS Cost Optimization Hub consolidates recommendations from Compute Optimizer, Trusted Advisor, and other services into a single dashboard, rather than requiring separate visits to each tool.
  • A clear 2026 industry trend: these tools are moving from "recommend and wait for a human to act" toward increasingly automated, autonomous remediation — worth factoring into how much manual FinOps process is really needed going forward.
  • Savings Plans / Reserved Instances for the predictable steady-state (~500 TPS) portion of compute, layered with on-demand Fargate capacity to absorb flash-sale bursts.
  • S3 Intelligent-Tiering for product images, since access patterns across ~75 TB of imagery are uneven (new/promoted SKUs are hot, long-tail SKUs are cold).

Common Interview Questions

Organized by theme — expect a real interview to pick a handful of these as follow-ups once the core design is on the whiteboard.

Multi-Region Consistency and CAP

Explain Aurora Global Database's replication lag and what it means for active-active writes.
Aurora Global Database replicates from the primary region to secondary regions asynchronously, typically with sub-second lag. That means it gives you fast, low-RPO disaster recovery and low-latency reads in secondary regions, but it does not give you synchronous, conflict-free multi-region writes. If two regions both accept a write for the same order at nearly the same instant, there's no built-in resolution — you must either route writes for a given customer/order to one "home" region, or build your own conflict-detection layer.
How does Aurora's consistency model compare to DynamoDB's, through a CAP lens?
Aurora (single-region writer) behaves as a strongly consistent, CP-leaning system for the order ledger — correctness over availability during a network partition to the writer. DynamoDB, especially with Global Tables, leans AP: it stays available and partition-tolerant across regions, accepting "last writer wins" conflict resolution, which is why it's the right fit for the catalog (where a stale read is fine) and the wrong fit for the order ledger (where silently discarding a conflicting write is a bug).
If two regions both accept a write for the same order at nearly the same time, what actually happens on Aurora Global Database?
Aurora Global Database has a single writer instance for the whole global cluster; secondary regions only get read replicas by default. So in practice, a properly configured system routes all writes for a given order to that one writer region — the "two regions both accept a write" scenario is prevented architecturally rather than resolved after the fact. If you instead promote a secondary region to also accept writes (a managed planned failover), you own the responsibility of making sure only one region is writing at a time.
How would you decide between a "write to home region" strategy and a conflict-resolution strategy?
Home-region routing (pin each customer or order to a primary region based on where the account was created, or geography) is simpler to reason about and avoids conflicts by construction — the trade-off is slightly higher write latency for a customer temporarily far from their home region. A conflict-resolution layer is only worth the complexity if the business genuinely needs every region to accept writes for every customer at all times, which is rare for a checkout flow — most e-commerce platforms find home-region routing sufficient.

Compute Platform Trade-offs

Why ECS on Fargate over EKS for the core checkout API?
Fargate removes node management entirely (no patching, no capacity planning for the underlying EC2 fleet) while ECS's scheduling model is simpler to operate than Kubernetes for a team that isn't already standardized on it. EKS becomes the better choice specifically when an organization already runs Kubernetes elsewhere and wants one consistent tooling/operational model across all its services — not because EKS is technically superior for this workload in isolation.
When would Lambda be a better fit than Fargate for a piece of this system?
For the SQS-triggered async consumers (fulfillment, notifications, fraud-review) — short-lived, bursty, event-driven work that maps well onto Lambda's per-invocation scaling and billing. It's a weaker fit for the core checkout API itself, where sustained Aurora connection pools and predictable p99 latency (cold starts are a real risk) favor a long-running container.
What operational burden does Fargate remove compared to self-managed EC2 Auto Scaling Groups?
Fargate removes AMI patching, OS-level security updates, EC2 instance health monitoring, and manual bin-packing/capacity planning for the underlying hosts — AWS manages the compute substrate. The trade-off is somewhat less low-level control (custom kernel tuning, specific instance types) than a hand-managed EC2 fleet would allow.

Messaging and Event-Driven Patterns

Why fan out via SNS+SQS rather than have every consumer subscribe directly to a single queue?
A single shared queue means every consumer competes for the same messages and a slow consumer (or a bug in one) can starve or delay the others. SNS-to-multiple-SQS gives each downstream service (fulfillment, notifications, fraud-review) its own independent queue, its own retry/backoff behavior, and its own dead-letter queue — failures are isolated per consumer.
SQS gives at-least-once delivery — how do you make the fulfillment consumer idempotent?
Key the processing logic off order_id: either an upsert that's safe to apply twice, or a small "processed events" table/dedup cache checked before acting on a message. The consumer should be written assuming it may see the same message more than once, rather than assuming SQS's at-least-once guarantee is actually exactly-once.
When would EventBridge be preferable to raw SNS/SQS for this system?
Once event routing needs content-based filtering rules across many event types and many possible targets (e.g. "route only high-value fraud-flagged orders to a separate investigation queue, everything else to standard fraud-review"), EventBridge's rule engine is a cleaner fit than hand-rolling that logic in each SNS subscriber's filter policy.

Global Traffic Management and Disaster Recovery

Compare Route 53's latency-based, geoproximity, and failover routing policies for this workload.
Latency-based routing sends each user to the region with the lowest measured network latency — the default choice here since sub-150ms p99 is a hard requirement. Geoproximity adds the ability to deliberately bias traffic toward or away from a region (e.g. for data-residency reasons) using a "bias" value. Failover routing is layered on top of either: Route 53 health checks detect a region going unhealthy and automatically stop sending it traffic, which is how the platform survives a regional outage without a human in the loop.
Walk through what happens during a full regional outage.
Route 53 health checks against the ALB (and, transitively, the checkout API) detect the region is unhealthy and stop routing new traffic there within the health-check interval. Traffic shifts to the remaining healthy region(s). Aurora Global Database's secondary region can be promoted to a standalone writer if the outage affects the primary write region, at the cost of a small window of unreplicated writes (bounded by the pre-outage replication lag) being lost or needing reconciliation.
What's the RPO/RTO story given Aurora Global Database's asynchronous replication?
RPO (Recovery Point Objective) is bounded by replication lag — typically under a second, but worth stating as "not zero" rather than promising zero data loss. RTO (Recovery Time Objective) for a managed planned failover of Aurora Global Database is on the order of a minute; an unplanned promotion during an actual regional disaster can take longer and should be tested, not assumed.

Security and Cost

How do ECS task IAM roles avoid the need for static credentials?
Fargate injects temporary, automatically-rotated credentials into each task via the ECS agent, scoped to whatever IAM policy is attached to that task's role. The application code calls AWS APIs (e.g. Secrets Manager, SNS) using those temporary credentials via the standard SDK credential chain — no access keys are ever stored in the container image, environment variables, or config files.
What's the difference between Trusted Advisor, Compute Optimizer, and the Cost Optimization Hub?
Trusted Advisor flags broader account-hygiene issues, including cost ones (idle load balancers, unassociated Elastic IPs, idle databases). Compute Optimizer is narrower and deeper — it analyzes actual utilization metrics to recommend specific right-sizing changes for EC2/Fargate/EBS. The Cost Optimization Hub is newer and sits above both, consolidating their recommendations (plus others) into one dashboard so teams aren't checking three separate tools.
How does KMS fit into the PCI-DSS-adjacent handling requirement, given raw PAN is never stored here?
Even though raw card numbers are delegated to the external payment processor, the tokenized payment reference, order data, and any related metadata stored in Aurora/S3 still need encryption at rest with auditable key management — that's what KMS customer-managed keys provide, along with a CloudTrail record of every key usage for compliance review.

Key Takeaways

Remember
Start from the numbers — a 10× peak-to-steady TPS ratio, ~79 API calls per completed order, and a hard sub-150ms p99 — and let them drive every service choice, not the other way around. AWS's real strength here is breadth and integration maturity: CloudFront, WAF, Shield, ALB, ECS/Fargate, Aurora, and SNS/SQS all click together with minimal glue code, backed by the deepest managed-service catalog and the largest hiring pool of any major cloud. Its real limitation is equally clear: Aurora Global Database's cross-region replication is asynchronous, so genuine multi-region active-active writes with strong consistency require an explicit design decision — home-region write routing or conflict resolution — not a feature you get by default. Split the data plane deliberately: Aurora PostgreSQL for the order/payment ledger where correctness is non-negotiable, DynamoDB for the 50-million-SKU catalog where eventual consistency and massive read scale matter more. Push everything that isn't on the critical path of "did the order commit?" — fulfillment, notifications, fraud review, analytics — onto the async SNS/SQS fan-out, and design every consumer of that fan-out to be idempotent, since SQS's at-least-once delivery guarantees nothing less.
