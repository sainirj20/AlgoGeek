CLOUD ARCHITECTURE

Microsoft Azure — Cloud Architecture Tutorial

A complete, interview-ready walkthrough of designing a global e-commerce checkout & order-processing platform natively on Microsoft Azure — requirements, capacity estimation, service selection, a defensible Cosmos DB consistency strategy, IaC, and follow-up interview questions.

Use Case & Requirements

The Business Problem

A retailer needs to re-platform its checkout and order-processing API to serve a genuinely global customer base. The current system can't survive flash-sale traffic spikes, can't guarantee an order is written exactly once, and can't serve a 50-million-SKU catalog with consistent low latency in every region the company sells into. The re-platformed system has to hold up under extreme, bursty write load on the most correctness-sensitive part of the business (orders and payments) while simultaneously serving a much larger, much less sensitive read workload (browsing the catalog) — and it has to do both from multiple regions at once, both for latency and so that losing an entire region doesn't take checkout offline.

The two halves of this problem pull in different directions. Order writes need strict correctness — a shopper must never be charged twice for the same order, and a placed order must never silently vanish. Catalog browsing needs raw scale and speed far more than it needs freshness — a product description or price that is a few seconds stale is a non-issue; a slow product page is a lost sale. A good architecture treats these as two different problems solved by the same platform, not one problem solved with one blanket setting.

Functional Requirements

  1. Accept checkout requests from web and mobile clients globally.
  2. Reserve inventory for the items in a cart at the moment of checkout.
  3. Process and tokenize a payment reference by calling out to a certified external payment processor (this system never stores a raw PAN).
  4. Write a durable order record once inventory and payment tokenization both succeed.
  5. Publish an order-placed event so downstream systems (fulfillment, notifications, analytics, fraud review) can react asynchronously.
  6. Serve the product catalog and support browse/search traffic at very high read volume.

Non-Functional Requirements

  1. Peak throughput: 5,000 transactions/second during flash-sale events; ~500 TPS steady-state.
  2. Latency: sub-150ms p99 for checkout API calls, globally — not just in the region closest to the datacenter.
  3. Availability: 99.95% SLA (≈ 4.4 hours of downtime budget per year).
  4. Consistency: strong consistency for order/payment writes — an order must never be double-charged or lost — while catalog/browse reads can be eventually consistent.
  5. Compliance: PCI-DSS-adjacent handling of payment data — only tokenized card references are stored here; raw PAN handling is delegated entirely to a certified payment processor.
  6. Topology: multi-region active-active deployment, for both latency (serve from the closest region) and disaster recovery (no single region is a single point of failure).
  7. Scale: ~200 million orders/year, a catalog of ~50 million SKUs, and globally distributed product-image/asset delivery via CDN.

Capacity Estimation and Constraints

As with any capacity exercise, we state assumptions explicitly and let the numbers drive the design rather than picking services first and rationalizing them afterward.

Traffic Steady-state requests/day = 500/sec × 86,400 sec ≈ 43.2 million/day
Peak (flash-sale) requests/day, if sustained all day (illustrative ceiling only) = 5,000/sec × 86,400 sec ≈ 432 million/day
In practice, flash-sale peaks are short bursts (minutes to a few hours), not sustained 24 hours — the 5,000 TPS number sizes burst capacity, not average daily volume.
Orders / Second (Average) ~200,000,000 orders/year ÷ 365 days ≈ 547,945 orders/day
547,945 ÷ 86,400 sec ≈ 6.3 completed orders/sec on average
Note the gap between ~6–7 completed orders/sec on average and 500–5,000 checkout-API TPS: checkout API calls include cart validation, inventory checks, and abandoned/retried attempts — only a fraction of checkout API calls end in a completed order.
Order Storage Growth (3 Years) Assume ≈1.5 KB per stored order record (order header, line-item metadata, tokenized payment reference, address references, audit fields)
200M orders/year × 1.5 KB ≈ 300 GB/year of logical order data
Over 3 years: 300 GB × 3 ≈ 900 GB logical data
Replicated across 3 Azure regions for active-active + DR: 900 GB × 3 ≈ 2.7 TB physical
With a tuned (non-default) Cosmos DB indexing policy adding ≈30% overhead: 2.7 TB × 1.3 ≈ ~3.5 TB provisioned storage footprint after 3 years
Catalog Size Assume ≈4 KB per SKU record (title, descriptions, attributes, pricing, category references, image URLs)
50 million SKUs × 4 KB ≈ 200 GB logical catalog data
Replicated across 3 regions: 200 GB × 3 ≈ 600 GB physical
Note the catalog is far smaller than the order history despite having 50M records vs. ~600M orders over 3 years — catalog records are read-heavy/write-light and don't grow linearly the way transactional data does.
Image Storage & CDN Egress Assume ≈6 images/SKU at ≈180 KB each (optimized JPEG/WebP)
Origin image library: 50M SKUs × 6 × 180 KB ≈ 54 TB in Blob Storage (one-time size, not per-month)
Assume 300 million product-page views/month, ≈4 images loaded/view at ≈150 KB average after Front Door's CDN image optimization
Monthly image egress = 300M × 4 × 150 KB ≈ 180,000,000,000 KB ≈ ~176 TB/month served from the edge
Assuming a ≈92% CDN cache-hit ratio, only ≈14 TB/month actually egresses from Blob Storage origin — the rest is served from Front Door's edge caches

Architecture Overview

Why Azure for This Workload

Three Azure-specific properties matter more here than a generic "any cloud can do this" answer would suggest, and it's worth being explicit about each rather than treating "Azure is fine too" as sufficient.

Cosmos DB's per-container, tunable consistency levels let one database service host both halves of this problem. Rather than standing up two entirely different database platforms — one for strict order correctness, one for high-scale eventual-consistency browsing — Cosmos DB lets the order container run at Bounded Staleness (or Strong, with the trade-off discussed below) while a separate catalog container in the same account runs at Session or Eventual consistency. That's one operational surface, one SDK, one billing model, and one team's expertise covering both workloads, rather than two.

Azure Front Door collapses the edge tier into one product. Global HTTP(S) load balancing, CDN, and a built-in Web Application Firewall ship as a single, integrated Azure service. AWS and GCP can absolutely build the equivalent edge tier, but doing so means composing 2–3 separate services (e.g. CloudFront + WAF + Global Accelerator/Route 53 on AWS) with their own configuration surfaces, their own health-check semantics, and their own places where a misconfiguration between services can create a gap. Front Door being one product with one routing/WAF/caching configuration is a genuine reduction in operational surface area for this workload's edge tier.

If the company is already Microsoft-centric — Windows Server, on-prem Active Directory, Office 365 — Azure's hybrid and enterprise-identity story is a real, material advantage. Microsoft Entra ID (formerly Azure Active Directory) extends an existing on-prem AD via Entra Connect with far less friction than federating an external identity provider into AWS IAM or GCP Cloud Identity from scratch, and ExpressRoute gives a private, high-throughput link back to existing on-prem systems (inventory masters, ERP, legacy fraud systems) that many retailers still run outside the cloud. This advantage is conditional — it only matters if the company's existing estate is actually Microsoft-centric — but where that's true, it's not a marketing point, it's a genuine integration-cost reduction.

None of this means Azure is unconditionally "better" for this workload — see the honest comparison below, and see the consistency-level discussion in Component Breakdown for where Azure's own default ("just use Strong everywhere") would actually be the wrong call.

Read this table as a genuine trade-off map, not a scorecard for one winner. If the team's real bottleneck is "we need the strongest possible global-write consistency guarantee with the least amount of per-request consistency-level decision-making," Cloud Spanner is a legitimate reason to prefer GCP for the order-write path specifically. If the real bottleneck is "we need the broadest possible managed-service catalog and the largest hiring pool of engineers who already know the platform," AWS's maturity and market share are a legitimate reason to prefer it. Azure's case here rests specifically on the edge-tier integration, the per-container consistency flexibility, and — conditionally — the hybrid/identity story.

Deep Dive — Compute: AKS vs. Container Apps vs. Azure Functions

The core checkout API is the piece under the tightest constraints in this whole design: it must sustain a steady 500 TPS baseline, absorb sudden 10× bursts to 5,000 TPS during flash sales, hold a sub-150ms p99 latency budget throughout, and maintain long-lived, warm connection pools to Cosmos DB and Redis so every request isn't paying a fresh-connection tax. That combination — predictable scaling behavior, deep networking control (VNet integration, private endpoints to PaaS backends, service-mesh sidecars for mTLS), and always-on warm compute — is exactly AKS's sweet spot. AKS also lets the platform team tune cluster autoscaler and KEDA-based pod autoscaling against real signals (Service Bus queue depth, custom Cosmos DB RU-consumption metrics), which matters more here than it would for a simpler workload.

Azure Container Apps is the right call for the platform's simpler, stateless services — a webhook receiver, an internal admin API, a notification-formatting service — where the team doesn't want to own cluster upgrades, node-pool sizing, or CNI configuration, and where scale-to-zero during idle periods is a genuine cost win. It trades away some of AKS's networking granularity and its mature ecosystem of sidecars/service-mesh add-ons in exchange for materially less operational overhead. For this design, Container Apps is a good fit for the notification and fraud-review consumer services downstream of Service Bus, but a poor fit for the latency-critical, connection-pool-heavy checkout API itself.

Azure Functions is the right tool for the truly event-driven, short-lived leaf work — a single Service Bus-triggered notification send, a thumbnail-resize job triggered by a Blob Storage upload — but it's a poor fit for the synchronous checkout API. Even on the Premium plan (which mitigates cold starts), the function invocation model doesn't naturally hold a long-lived, warmed connection pool to Cosmos DB and Redis the way a long-running pod does, and a sub-150ms p99 budget has very little room to spare for any cold-start risk at all. Functions earns its place in this architecture as a consumer of Service Bus/Event Grid events, not as the checkout API's host.

Deep Dive — Primary Database: Cosmos DB vs. Azure SQL Database Hyperscale

Cosmos DB's headline feature for this workload is its five tunable consistency levels — Strong, Bounded Staleness, Session, Consistent Prefix, and Eventual — configurable per container, letting the same database account serve both the order-write path and the catalog-browse path at the consistency level each actually needs, rather than forcing a single database-wide setting on two very different workloads.

Consistency levelGuaranteeWhere it fits in this design
StrongLinearizable reads; always see the latest committed writeOnly available with a single write region in Cosmos DB — sacrifices multi-region write latency/availability for order writes if used verbatim.
Bounded StalenessReads lag writes by at most K versions or T time, globally, even with multi-region writesRecommended for the order-write container — the strongest guarantee Cosmos DB offers that's still compatible with true multi-master, multi-region writes.
SessionRead-your-own-writes and monotonic reads within a single client sessionGood fit for cart/session data and general catalog reads where a user should see their own recent actions reflected immediately.
Consistent PrefixReads never see out-of-order writes, but may lagRarely the best default here; occasionally useful for ordered event/log-style reads.
EventualNo ordering guarantee; lowest latency, highest availabilityAcceptable for the pure catalog-browse container where staleness of a few seconds is a non-issue.

This is exactly where the design must make an honest, explicit call rather than defaulting to "Strong" everywhere. Cosmos DB's Strong consistency level requires synchronous replication and, critically, is only supported when the account is configured for a single write region — it is not compatible with true multi-region, multi-master writes. Since one of this platform's hard requirements is multi-region active-active deployment for both latency and DR, reaching for Strong on the order container verbatim would silently force the design back to a single write region for orders — undermining the exact multi-region write benefit that made Cosmos DB attractive in the first place. The design therefore has two honest options, and states the trade-off out loud rather than hiding it:

  • Option A — Bounded Staleness with multi-region writes (recommended default): orders can be written in any region with Cosmos DB actively replicating them to all other regions within a bounded K-operations/T-time window, giving near-strong guarantees at a fraction of Strong's cross-region write latency. This must be paired with an application-level idempotency key on every order write (a client-generated request ID as part of the partition/unique key) plus a conditional write (ETag-based optimistic concurrency), so that even a retried or racing write can never double-charge or duplicate an order — the database's consistency level and the application's idempotency logic are doing complementary jobs, not the same job.
  • Option B — Strong consistency with a single write region: if the business is willing to accept that all order writes route to one active write region (with fast automatic failover to a designated secondary on a regional outage), Strong consistency is available and removes the need for application-level idempotency as a correctness backstop. This is simpler to reason about but gives up active-active writes specifically for the order path — catalog and session data can still be fully active-active regardless of which option is chosen for orders.

Given the explicit multi-region active-active requirement, Option A (Bounded Staleness + idempotency keys) is the primary recommendation for this design, with Option B noted as the simpler fallback if the business later decides active-active order writes aren't worth the added application-level complexity.

Azure SQL Database Hyperscale with active geo-replication is a legitimate alternative if the team strongly prefers relational/ACID semantics over a document/API-based data model. Hyperscale scales storage and read throughput well beyond what a single traditional SQL instance can do, and ~200M orders/year (≈6–7 orders/sec average, 5,000 TPS peak) is well within what a well-sized Hyperscale primary plus readable secondaries can serve. The honest trade-off: active geo-replication is asynchronous, so a regional failover can lose the last few seconds of committed transactions (a real RPO, not zero), and Hyperscale itself is fundamentally single-write-region — there's no multi-master write story here at all. For this specific workload, Cosmos DB is preferred as the primary recommendation because it natively supports multi-region writes and lets one database account serve both the order and catalog workloads at their respective correct consistency levels; Azure SQL Hyperscale remains the right call for a team that values SQL semantics and query flexibility more than multi-region write elasticity, and can accept single-write-region operation.

Data Flow

Two distinct flows matter here: the synchronous checkout request (must complete inside the 150ms p99 budget) and the asynchronous fan-out that happens after the order is durably written (has no such tight budget, and is explicitly decoupled from it).

Synchronous Checkout Request

  1. Client issues a checkout request; Azure DNS resolves the platform's hostname to Azure Front Door's anycast edge.
  2. Azure Front Door terminates TLS, applies WAF managed rule sets, and load-balances the request to the healthiest backend region — edge, WAF, and global LB all happen in this single hop.
  3. The request reaches an AKS-hosted checkout API pod in the target region.
  4. The pod performs an inventory check/reservation against the current inventory state (backed by Cosmos DB and/or Redis for hot SKUs).
  5. The pod calls out to the external, certified payment processor to tokenize the payment reference — no raw PAN is ever handled or stored by this system.
  6. On success, the pod issues a transactional write of the order record to the Cosmos DB order container, at the chosen consistency level (Bounded Staleness, paired with an idempotency key and a conditional write as discussed above).
  7. The pod publishes an order-placed event to a Service Bus topic — this publish is fire-and-forget from the request's point of view; a Service Bus outage never blocks the response.
  8. The pod returns a success response (order confirmation) to the client.
  9. Total elapsed time across steps 1–8 is what's measured against the sub-150ms p99 target; caching (Redis) and regional proximity (Front Door routing to the nearest healthy region) are what make that budget achievable at global scale.

Asynchronous Fan-Out

  1. The order-placed event lands on the Service Bus topic published in step 7 above.
  2. Independent subscriptions on that topic — one each for fulfillment, notifications, analytics, and fraud-review — each receive their own copy of the message, filtered as needed per subscription.
  3. The fulfillment consumer reserves warehouse capacity and kicks off shipping workflows.
  4. The notifications consumer sends the order-confirmation email/push notification.
  5. The fraud-review consumer runs post-hoc risk scoring and flags orders for manual review if needed.
  6. Every consumer is built to be idempotent (keyed on the order ID) — Service Bus's at-least-once delivery model means a consumer can, in principle, see the same message more than once, and correctness must not depend on exactly-once delivery actually holding at the messaging layer.
  7. A failed message delivery is retried per the subscription's retry policy, then dead-lettered for manual inspection rather than silently dropped.
Figure 2. Sequence view of a single checkout request — steps 1–8 are on the synchronous, latency-budgeted path; the Service Bus publish in step 7 kicks off a fully decoupled async fan-out to downstream consumers.

Infrastructure as Code (IaC)

This design uses Terraform with the official hashicorp/azurerm provider, currently in its 4.x major version line (current release around 4.81.0 as of mid-2026). The 3.x→4.x upgrade introduced real breaking changes — provider-block requirement changes, resource property renames/removals, and changed default behaviors on several resources — so a production script should pin an exact provider version and consult the official 4.0 upgrade guide before adopting it, rather than floating on ~> 3.0 or blindly bumping to ~> 4.0.

The script below provisions only the core networking and compute tier — resource group, VNet/subnets, an NSG, and the AKS cluster — not every service in the architecture diagram. Cosmos DB, Service Bus, Redis, Key Vault, and Front Door are deliberately left to their own, independently-versioned Terraform root modules in a real repository, so that a compute-tier change doesn't force a plan/apply cycle across unrelated stateful services.

############################################################
# Core networking and compute for the Global E-Commerce
# Checkout Platform on Azure.
#
# Scope: resource group, VNet/subnets, NSG, and the AKS
# cluster ONLY. Cosmos DB, Service Bus, Redis, Key Vault,
# and Front Door live in separate root modules.
############################################################

terraform {
  required_version = ">= 1.7.0"

  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
      # Pin an EXACT major version. The 3.x -> 4.x upgrade
      # (azurerm 4.0) introduced real breaking changes --
      # provider block requirements, resource property
      # renames/removals, and changed defaults on several
      # resources. Read the official 4.0 upgrade guide before
      # bumping this.
      version = "= 4.81.0"
    }
  }
}

provider "azurerm" {
  features {}
}

# ------------------------------------------------------------
# Resource group -- deployment boundary for this workload's
# network + compute tier.
# ------------------------------------------------------------
resource "azurerm_resource_group" "checkout_platform" {
  name     = var.resource_group_name
  location = var.location

  tags = {
    workload    = "checkout-platform"
    environment = var.environment
  }
}

# ------------------------------------------------------------
# Virtual network for the checkout platform's compute tier.
# ------------------------------------------------------------
resource "azurerm_virtual_network" "checkout_vnet" {
  name                = "${var.resource_group_name}-vnet"
  address_space       = ["10.20.0.0/16"]
  location            = azurerm_resource_group.checkout_platform.location
  resource_group_name = azurerm_resource_group.checkout_platform.name
}

# Subnet dedicated to AKS node pools (checkout API pods).
resource "azurerm_subnet" "aks_subnet" {
  name                 = "snet-aks-nodes"
  resource_group_name  = azurerm_resource_group.checkout_platform.name
  virtual_network_name = azurerm_virtual_network.checkout_vnet.name
  address_prefixes     = ["10.20.0.0/20"]
}

# Subnet reserved for private endpoints (Cosmos DB, Key Vault,
# Service Bus, Storage) so PaaS traffic never traverses the
# public internet.
resource "azurerm_subnet" "private_endpoint_subnet" {
  name                 = "snet-private-endpoints"
  resource_group_name  = azurerm_resource_group.checkout_platform.name
  virtual_network_name = azurerm_virtual_network.checkout_vnet.name
  address_prefixes     = ["10.20.16.0/24"]

  private_endpoint_network_policies = "Enabled"
}

# ------------------------------------------------------------
# NSG for the AKS subnet: allow HTTPS only from Azure Front
# Door's managed backend service tag; deny everything else
# inbound by default.
# ------------------------------------------------------------
resource "azurerm_network_security_group" "aks_nsg" {
  name                = "${var.resource_group_name}-aks-nsg"
  location            = azurerm_resource_group.checkout_platform.location
  resource_group_name = azurerm_resource_group.checkout_platform.name

  # Allow inbound HTTPS only from Front Door's backend range --
  # the well-known service tag Azure maintains for Front Door
  # origin traffic, so we never hand-maintain an IP allowlist.
  security_rule {
    name                       = "Allow-HTTPS-From-FrontDoor"
    priority                   = 100
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "Tcp"
    source_port_range          = "*"
    destination_port_range     = "443"
    source_address_prefix      = "AzureFrontDoor.Backend"
    destination_address_prefix = "*"
  }

  # Explicit deny-all default -- belt-and-suspenders on top of
  # the NSG's own implicit deny, so intent is visible in the
  # ruleset itself.
  security_rule {
    name                       = "Deny-All-Inbound"
    priority                   = 4096
    direction                  = "Inbound"
    access                     = "Deny"
    protocol                   = "*"
    source_port_range          = "*"
    destination_port_range     = "*"
    source_address_prefix      = "*"
    destination_address_prefix = "*"
  }
}

resource "azurerm_subnet_network_security_group_association" "aks_nsg_assoc" {
  subnet_id                 = azurerm_subnet.aks_subnet.id
  network_security_group_id = azurerm_network_security_group.aks_nsg.id
}

# ------------------------------------------------------------
# AKS cluster running the checkout API + catalog service
# microservices.
# ------------------------------------------------------------
resource "azurerm_kubernetes_cluster" "checkout_aks" {
  name                = "${var.resource_group_name}-aks"
  location            = azurerm_resource_group.checkout_platform.location
  resource_group_name = azurerm_resource_group.checkout_platform.name
  dns_prefix          = "checkout-aks"
  kubernetes_version  = var.kubernetes_version

  default_node_pool {
    name                 = "system"
    vm_size              = "Standard_D4s_v5"
    vnet_subnet_id       = azurerm_subnet.aks_subnet.id
    auto_scaling_enabled = true
    min_count            = 3
    max_count            = 12
    zones                = ["1", "2", "3"]
  }

  # Cluster-level managed identity (control plane -> Azure
  # resource access) -- separate from per-workload Managed
  # Identities assigned to individual pods.
  identity {
    type = "SystemAssigned"
  }

  network_profile {
    network_plugin    = "azure"
    load_balancer_sku = "standard"
    network_policy    = "azure"
  }

  tags = {
    workload    = "checkout-platform"
    environment = var.environment
  }
}

Production practice
Use a remote azurerm backend (a dedicated Storage Account + container) for Terraform state, with state locking enabled, so two engineers or two CI runs can never corrupt state by writing concurrently. Keep separate .tfvars files (or separate Terraform workspaces) per environment — dev, staging, prod — rather than parameterizing a single shared state file. Always run terraform plan in CI and require a reviewed, visible plan output before any terraform apply reaches a shared environment.

Best Practices

Security

  • Assign Microsoft Entra ID roles on a least-privilege basis — scope role assignments to the specific resource group or resource, not the subscription, wherever practical.
  • Use Managed Identities for every AKS workload that talks to Cosmos DB, Key Vault, Service Bus, or Blob Storage, so no service ever holds a static credential in code or config.
  • Encrypt data at rest across Cosmos DB and Blob Storage using Azure Key Vault-managed customer keys, and enforce TLS everywhere in transit.
  • Use Network Security Groups to segment the AKS subnet from the private-endpoint subnet, restricting inbound traffic to only what Front Door and internal services actually need.
  • Store all secrets (connection strings, API keys, certificates) in Azure Key Vault with access policies or RBAC-based access, never in application config or source control.
  • Enable Front Door's built-in WAF managed rule sets to block common web attacks (SQLi, XSS, and known bad bot signatures) at the edge, before traffic ever reaches AKS.

Monitoring, Logging and Alerting

  • Define Azure Monitor metrics and alert rules tied directly to the platform's SLOs (p99 latency, error rate, 99.95% availability), not just raw infrastructure metrics.
  • Instrument the checkout API with Application Insights for distributed tracing across the entire call path — Front Door → AKS → Cosmos DB/Redis/Service Bus — so a latency regression can be attributed to a specific hop.
  • Centralize structured logs in Log Analytics workspaces and use KQL to build cross-service queries (e.g. correlating a spike in Cosmos DB throttling with a specific AKS deployment).
  • Configure Front Door health probes against each regional backend so an unhealthy region is automatically routed around, well before it becomes customer-visible.

Cost Optimization

  • Use Microsoft Cost Management for ongoing cost analysis and budget alerts, scoped per environment and per service, so a runaway cost driver is caught early rather than at month-end.
  • Act on Azure Advisor's right-sizing and reserved-capacity recommendations regularly — it will flag over-provisioned AKS node pools and underused reserved capacity.
  • Commit to Azure Reservations or Azure Savings Plans for the steady-state 500 TPS compute baseline, while leaving headroom for flash-sale bursts to run at on-demand rates.
  • Configure Cosmos DB autoscale throughput (rather than fixed RU/s) so provisioned throughput tracks actual demand instead of being sized for worst-case peak at all times.
  • Apply Blob Storage lifecycle management policies to automatically tier cold, rarely-viewed product images down to Cool or Archive tiers.

Common Interview Questions

Consistency and Data

Walk through Cosmos DB's five consistency levels and when you'd choose each.
Strong (linearizable, but single-write-region only), Bounded Staleness (bounded lag by K operations/T time, works with multi-region writes — the practical "strong" choice for this design's order container), Session (read-your-own-writes within a client session — good for cart/session data), Consistent Prefix (no out-of-order reads, but may lag), and Eventual (fastest, no ordering guarantee — fine for catalog browsing).
Why can't you just set every Cosmos DB container to Strong consistency and call it done?
Strong consistency requires synchronous replication and is only supported with a single write region in Cosmos DB. Given a hard requirement for multi-region active-active writes, defaulting to Strong for orders would silently force a single write region, undermining the multi-region benefit the platform needs.
If you use Bounded Staleness instead of Strong for order writes, how do you still prevent a double-charge?
Pair the database consistency level with an application-level idempotency key on the order write (a client-generated request ID) and a conditional/optimistic-concurrency write (ETag check), so a retried or racing write can never create two order records for the same checkout attempt.
How would you frame this consistency decision in CAP-theorem terms?
The order-write path favors consistency over availability during a partition (accepting some write latency/retry to avoid a double-charge), while the catalog-browse path favors availability and partition tolerance (serving slightly stale data rather than failing a page load) — the same platform makes two different CAP trade-offs for two different data types, on purpose.
Cosmos DB vs. Azure SQL Hyperscale for the order table — how do you decide?
Cosmos DB wins on native multi-region write elasticity and per-container consistency tuning, letting one account serve both orders and catalog. Azure SQL Hyperscale is a legitimate alternative if the team needs strict relational/ACID semantics, but its active geo-replication is asynchronous (a real RPO on failover) and it's fundamentally single-write-region.

Compute Platform Choices

Why AKS instead of Azure Container Apps for the checkout API?
The checkout API needs deep networking control (VNet integration, private endpoints, service-mesh sidecars), fine-tuned autoscaling against custom metrics, and always-warm connection pools to Cosmos DB/Redis to hit a sub-150ms p99 — all things AKS gives more control over than Container Apps. Container Apps is the better fit for simpler, stateless downstream services.
Why not run the checkout API on Azure Functions given it's naturally event-driven?
The synchronous checkout call has almost no latency budget to spare; even Premium-plan Functions carry more cold-start/connection-pool risk than a long-running AKS pod. Functions are a good fit for the async consumer side (a single notification send, an image-resize job), not the latency-critical checkout request itself.

Messaging and Event-Driven Patterns

How does Service Bus's topic/subscription model support the order-placed fan-out?
A single order-placed topic with independent subscriptions per downstream consumer (fulfillment, notifications, analytics, fraud-review) — each subscription gets its own copy of the message, can filter independently, and can fail/retry/dead-letter independently of the others.
Service Bus guarantees at-least-once delivery, not exactly-once — how do your consumers stay correct?
Every consumer is built to be idempotent, keyed on the order ID (e.g. an upsert or a dedup check before acting), so processing the same message twice produces the same end state as processing it once.
When would you reach for Event Grid instead of Service Bus?
Event Grid suits simpler, more reactive routing scenarios (e.g. triggering a function on a Blob Storage upload) where you don't need Service Bus's richer guarantees — ordered sessions, per-subscription dead-lettering, and transactional send/receive semantics.

Edge, Cost, and Operations

What's the actual advantage of Azure Front Door over composing CloudFront + WAF + Global Accelerator on AWS?
Front Door is one product with one configuration surface for global LB, CDN, and WAF, reducing the number of places a misconfiguration or a gap between services can occur. The AWS composition is more flexible/granular but has more moving parts to keep consistent.
The flash-sale event ends and traffic drops back to steady-state — what happens to cost?
Cosmos DB autoscale throughput scales RU/s back down automatically; AKS's cluster autoscaler scales node pools down; only the steady-state 500 TPS baseline should be covered by Reservations/Savings Plans, with burst capacity running at on-demand rates.
How would you catch an unexpected cost spike before the monthly bill arrives?
Microsoft Cost Management budgets and alerts scoped per environment/service, combined with Azure Advisor's ongoing right-sizing recommendations — both surface anomalies well before invoice time.
An entire Azure region goes down — what's the customer-visible impact?
With Front Door's health probes, traffic automatically routes to the remaining healthy regions; Cosmos DB's multi-region replication means order and catalog data is already present elsewhere. The main risk is the RPO/RTO around in-flight writes at the moment of failure, which is exactly why the Bounded Staleness + idempotency design matters.
How do you test a regional failover without waiting for a real outage?
Use Front Door's manual backend disable/priority controls to simulate a region going unhealthy in a staging environment, and verify Cosmos DB failover priorities and AKS traffic shift behave as expected before relying on it in production.

Security and Identity

Why use Managed Identities instead of service principals with stored credentials for AKS workloads?
Managed Identities eliminate the need to store, rotate, or leak any credential at all — Azure handles the identity lifecycle, and access is granted purely through RBAC role assignments on the identity, which is both more secure and less operational overhead.
How does Entra ID's least-privilege RBAC model apply to this platform in practice?
Each service's Managed Identity gets only the specific role assignments it needs on the specific resource it needs (e.g. Cosmos DB Data Contributor on just the order container, not the whole account), rather than broad subscription-level Owner/Contributor roles.
If the company already runs on-prem Active Directory, how does that change the Azure identity design?
Entra Connect can synchronize on-prem AD identities into Entra ID with far less custom federation work than bridging an external IdP into AWS IAM or GCP Cloud Identity, and ExpressRoute gives a private link back to on-prem systems the checkout platform might still depend on (e.g. a legacy inventory master).

Key Takeaways

Remember
Let the numbers drive the design: ~200M orders/year is only ≈6–7 orders/sec on average, but the 5,000 TPS flash-sale peak and the sub-150ms global p99 are what actually size the compute and caching tiers. Cosmos DB's biggest strength for this workload — five tunable consistency levels per container — is only a strength if you actually choose deliberately per data type; defaulting to "Strong" everywhere would quietly force a single write region and undo the multi-region write benefit the platform needs, so the order container uses Bounded Staleness plus application-level idempotency instead, while the catalog container runs Session/Eventual. Azure Front Door's single-product integration of LB + CDN + WAF is a genuine simplification of the edge tier versus composing several services on other clouds, and Entra ID + ExpressRoute is a real, if conditional, advantage for a Microsoft-centric enterprise — but AWS's broader managed-service catalog and GCP's Spanner-based true global consistency are equally legitimate reasons a team might choose differently. State every trade-off explicitly, the same way you'd defend a consistency-level choice or a compute-platform choice in an interview.
