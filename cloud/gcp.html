CLOUD ARCHITECTURE

GCP — Cloud Architecture Tutorial

An end-to-end reference architecture for a global e-commerce order & checkout platform, built entirely on Google Cloud Platform — requirements and capacity math, service-by-service justification, request-level data flow, production Terraform, operational best practices, and interview-style Q&A.

Use Case & Requirements

The Business Problem

A mid-to-large e-commerce company is re-platforming its checkout and order-processing API to serve a genuinely global customer base rather than a single home region. The business already knows two things will break the old architecture: flash-sale traffic spikes that dwarf normal load by an order of magnitude, and customers outside the home region experiencing checkout latency bad enough to visibly hurt conversion. On top of that, finance and compliance have a non-negotiable requirement bolted on: an order, once accepted, must never be silently lost, and a customer's card must never be charged twice for the same order — even if a pod crashes, a region has a bad day, or a retry storm hits the API mid-transaction. The platform must handle roughly 200 million orders a year, present a catalog of about 50 million SKUs to browsing shoppers, and serve product imagery quickly to every region — while keeping raw cardholder data entirely out of the system by delegating that to a certified payment processor and only ever handling a tokenized reference to it.

Functional Requirements

  1. Accept checkout requests from web and mobile clients (cart contents, shipping address, tokenized payment method reference).
  2. Reserve inventory for the items in the order at the moment of checkout, atomically with the order write.
  3. Process / tokenize the payment reference by calling out to an external, PCI-DSS-certified payment processor — this system never stores or transmits a raw Primary Account Number (PAN).
  4. Write a durable, authoritative order record the instant payment authorization succeeds.
  5. Publish an order-placed event so downstream systems (fulfillment, notifications, analytics, fraud review) can react without being on the critical path of the checkout response.
  6. Serve the product catalog and browse/search experience to shoppers worldwide, independently of the checkout write path.

Non-Functional Requirements

  1. Peak throughput: 5,000 transactions/second during flash-sale events, against a steady-state baseline of roughly 500 TPS — a 10× peak-to-steady ratio the platform must absorb without manual intervention.
  2. Latency: sub-150ms p99 for checkout API calls, measured globally, not just from the home region.
  3. Availability: 99.95% SLA for the checkout path.
  4. Consistency: strong consistency for order and payment writes (an order must never be double-charged or lost); browse/catalog reads may be eventually consistent.
  5. Compliance: PCI-DSS-adjacent handling of payment data — only tokenized card references are stored; raw PAN handling is delegated entirely to a certified processor.
  6. Deployment model: multi-region active-active, simultaneously for latency (serve every shopper from a nearby region) and for disaster recovery (no single region is a single point of failure).

Capacity Estimation and Constraints

Two different numbers matter here and they are easy to conflate: the rate of checkout API calls (browsing-to-cart interactions, availability checks, retries, and the final submit) versus the rate of completed order writes. The 5,000/500 TPS figures describe API call volume; the ~200M orders/year figure describes completed, paid orders — and the gap between them is expected and healthy (not every checkout attempt converts).

Traffic — steady-state vs. peak Steady-state requests/day = 500 TPS × 86,400 sec ≈ 43.2 million checkout API calls/day
Flash-sale peak = 5,000 TPS — a 10× multiplier over steady-state that must be absorbed by autoscaling, not fixed capacity
Sustained over a 2-hour flash-sale window: 5,000 × 7,200 sec = 36 million requests in that window alone
Average completed order-write rate ~200,000,000 orders/year ÷ (365 × 24 × 3,600 sec) ≈ 6.3 orders/sec average, annualized
This is far below the 500 TPS steady-state API call rate — consistent with typical browse/cart-to-purchase conversion, where most checkout-path calls are availability checks, price recalculations, and abandoned carts rather than completed purchases
Design implication: the Cloud Spanner write path must comfortably clear 5,000 TPS bursts even though its long-run average load is orders of magnitude lower — provision (and load-test) for peak, not for the average
Order storage growth (3-year horizon) Assume ~2 KB per stored order record (order header, line items, shipping address, tokenized payment reference, audit metadata)
Records over 3 years = 200M × 3 = 600 million order records
Raw logical storage = 600M × 2 KB ≈ 1.2 TB
Cloud Spanner multi-region configurations typically maintain 5 read-write replicas across 3 regions (a 2-2-1 voting split) for quorum-based durability — even at 5× replication overhead, physical storage is ≈ 6 TB, trivial for Spanner and with generous headroom to scale past a decade of growth
Catalog size 50 million SKUs × ~3 KB average record (title, description, price, attributes, variant/image references) ≈ 150 GB raw catalog data
Comfortably fits either Firestore or Cloud SQL before considering indexes/replicas — catalog size is not the deciding factor between the two (see Component Breakdown deep dive below)
Image storage & CDN egress (assumed browsing volume) Assume 5 images/SKU × 50M SKUs = 250 million images at ~200 KB average (web-optimized) ≈ 50 TB origin storage in Cloud Storage
Assume 20 million browsing sessions/day, each viewing ~30 product images ≈ 600 million image views/day
At a healthy 90% Cloud CDN cache-hit ratio, edge egress ≈ 600M × 200 KB ≈ 120 TB/day served from the edge, while only the remaining ~10% (≈ 12 TB/day) ever becomes an origin fetch against Cloud Storage — this is the entire point of fronting Cloud Storage with Cloud CDN

Architecture Overview

Why GCP for This Workload

Strip away the marketing and this workload has exactly two requirements that are genuinely hard to satisfy simultaneously: (1) an order must never be double-charged or lost, even under multi-region active-active writes, and (2) the platform must serve sub-150ms p99 checkout latency globally from one architecture, without hand-rolled region-aware DNS failover logic. GCP's two most distinctive platform capabilities map directly onto those two requirements. Cloud Spanner provides external consistency — a real, TrueTime-backed global strong-consistency guarantee — across multiple write regions at once, which is precisely the "never double-charge, never lose an order" requirement stated in engineering terms. And the Global External HTTPS Load Balancer fronts every backend region behind a single anycast IP, so a client's request is routed to the nearest healthy region at the network layer, with no DNS TTL, no client-side failover logic, and no "wait for DNS to propagate" delay during a regional incident. Put together, these two features let this platform be built as genuinely one architecture across regions, rather than N independent regional stacks stitched together after the fact.

That said, "distinctive" is not "free." Spanner is a genuinely different operating model from a conventional relational database — interleaved tables, careful primary-key design to avoid hotspotting, and a cost profile that is higher per-node than a comparable managed MySQL/Postgres instance. A team with deep Aurora or Cosmos DB experience and no urgent need for synchronous multi-region strong consistency could reasonably choose a sharded Aurora Global Database (accepting async cross-region replication and a small RPO on failover) or Cosmos DB with a tunable consistency level, and get a working system for meaningfully less operational learning curve. The honest case for GCP here is narrow but real: it is the best fit specifically because this workload's hardest requirement is "strong consistency across active-active regions," which is exactly the scenario Spanner was built to solve and the scenario where the alternatives have to compromise on either consistency or write-region topology.

None of the three clouds is a wrong choice for this workload in the abstract — AWS has the broadest managed-service ecosystem and the largest hiring pool of engineers who already know it, and Azure is the clear pick if the company is already deeply invested in Microsoft/Entra ID for workforce identity and has Windows/SQL Server licensing to amortize via Hybrid Benefit. GCP earns the recommendation here specifically because of the two requirements called out above: synchronous multi-region strong consistency for money-moving writes, and a single global anycast entry point for latency-sensitive traffic.

High-level design — a single anycast entry point fronts both the checkout write path (GKE Autopilot → Spanner / Memorystore / Pub/Sub → async downstream consumers) and the catalog read path (Cloud Run → Firestore/Cloud SQL), while Cloud Storage product images are served from the Cloud CDN edge cache without touching either application tier on a cache hit.

Key Design Principles Reflected in the Diagram

  • One anycast IP, two independently-scaling paths: the checkout (write-heavy, strongly consistent) and catalog (read-heavy, eventually consistent) services share the same edge and load-balancing layer but diverge immediately afterward, so each can scale on its own terms.
  • Everything not required to answer "was this order accepted?" is asynchronous: fulfillment, notifications, and fraud review all happen off Pub/Sub, after the checkout response has already been returned to the client.
  • Static assets never touch the application tier on a cache hit: the Cloud Storage → Cloud CDN loop mirrors the same principle proven out in CDN-fronted designs elsewhere in this series — the fastest request is the one that never reaches your servers.

Compute Deep Dive — GKE Autopilot vs. Cloud Run vs. Compute Engine VMs

Three real compute options exist for the checkout API, and the choice genuinely matters here. Compute Engine VMs are ruled out first: running the checkout fleet as hand-managed VM groups means owning OS patching, capacity planning, and container orchestration from scratch — solvable, but it's re-building what GKE already provides, for a workload that doesn't need VM-level customization (no exotic kernel modules, no GPU pinning, no licensing constraint forcing bare VMs). Cloud Run is a genuinely strong contender for a single stateless HTTP API: it scales to zero, requires no cluster to operate, and is the right default for a lighter-weight service like the catalog-browse API in this same architecture, where cold-start latency on scale-from-zero is tolerable and there's no need for a shared service mesh across many microservices. The checkout API, however, is not one service — it's a small constellation of cooperating microservices (checkout orchestration, inventory reservation, payment-tokenization client, order writer) that benefit from a shared cluster boundary: consistent network policy, a common service mesh for mTLS between services, fine-grained pod affinity/anti-affinity to spread across zones, and predictable warm capacity so a flash-sale traffic ramp doesn't fight cold-start latency on the most latency-sensitive path in the whole system. GKE Autopilot gives that Kubernetes flexibility while removing the traditional GKE operational burden: Google manages node provisioning, security patching, and bin-packing, and billing is per-pod-resource-request rather than per-node, which removes the classic "we over-provisioned nodes for headroom we never used" waste. The trade-off is real: Autopilot restricts some low-level node customizations (e.g. privileged DaemonSets, certain host-level configurations) that standard GKE allows — none of which this checkout workload needs, which is exactly why Autopilot is the right default here rather than standard GKE or a from-scratch VM fleet.

Primary Database Deep Dive — Cloud Spanner vs. Cloud SQL vs. Bigtable vs. Firestore

Cloud SQL (managed MySQL/Postgres) is eliminated for the order/payment table specifically because it is fundamentally single-region-write: achieving multi-region active-active with Cloud SQL means manual application-level sharding across independent regional instances plus asynchronous cross-region replication for DR — which reintroduces exactly the "eventual consistency window where a double-charge or lost order becomes possible" that this workload cannot tolerate. Bigtable is a wide-column store built for massive-scale, single-key-lookup, eventually-consistent workloads (time series, IoT, ML feature stores) — excellent for the clickstream/analytics side of this platform, but it has no multi-row ACID transactions, which rules it out for "decrement inventory and write the order atomically." Firestore offers documents, multi-region replication, and transactions scoped to a limited set of documents — a reasonable fit for the catalog (which is exactly where this design uses it), but its transaction model and throughput profile are tuned for document-level operations, not the relational, schema-enforced, high-throughput transactional workload of an order ledger with line items, inventory counters, and payment references that benefit from real joins and secondary indexes. Cloud Spanner is purpose-built for exactly this gap: a relational schema with real ACID transactions, horizontal scalability to handle the 5,000 TPS peak, and — the deciding factor — external consistency via TrueTime, meaning a transaction that commits in one region is guaranteed to be visible everywhere as having happened at a single, well-defined point in time, even with concurrent writes landing in different regions. That is what "an order must never be double-charged or lost" means in database terms, and it's the one property none of the other three options can provide without a compromise on write topology or transaction semantics. The honest cost: Spanner nodes/processing units are priced at a premium over comparable Cloud SQL capacity, and the interleaved-table schema design and primary-key hotspotting concerns (e.g. avoiding monotonically increasing keys as a partition key) require real ramp-up time for a team new to it.

Data Flow

Two distinct flows matter for this platform: the synchronous checkout request that a customer is actively waiting on, and the asynchronous fan-out that happens after the order is already durably committed.

Synchronous Checkout Request Walkthrough

  1. Client submits a checkout request over HTTPS (cart contents, shipping address, tokenized payment method reference).
  2. Cloud DNS resolves the platform's single global anycast IP — a one-time lookup, typically already cached client-side.
  3. The request hits the edge: Cloud Armor evaluates WAF rules and DDoS/bot signals before anything reaches application infrastructure; Cloud CDN passes through non-cacheable API traffic untouched.
  4. The Global External HTTPS Load Balancer routes the request to the nearest healthy GKE Autopilot pod — nearest by network topology, not by a DNS-level regional redirect.
  5. The Checkout API pod validates the request and checks Memorystore for a cached inventory/session read; on a cache miss it reads current availability from Cloud Spanner.
  6. The Checkout API calls out to the external, certified payment processor to authorize and tokenize the payment reference — the raw PAN never enters this system at any point.
  7. On successful authorization, the Checkout API issues a single Cloud Spanner transaction that both decrements reserved inventory and writes the order record — externally consistent and atomic: either both happen, or neither does.
  8. Immediately after the transaction commits, the Checkout API publishes an order-placed event to Pub/Sub. This publish is fire-and-forget from the caller's perspective — it does not block the response.
  9. The order confirmation is returned to the client, targeting sub-150ms p99 for the entire round trip.

Asynchronous Fan-Out Walkthrough

  1. Pub/Sub delivers the order-placed event to every subscribed consumer independently — each consumer has its own subscription and processes at its own pace.
  2. The Fulfillment consumer reserves the physical pick/pack/ship workflow in the warehouse management system.
  3. The Notification consumer sends the order-confirmation email/SMS/push notification to the customer.
  4. The Fraud-Review consumer runs deeper, slower risk scoring than what was feasible synchronously at checkout time; a flagged order triggers a manual review workflow without unwinding the already-committed, already-shipped-toward order.

Pub/Sub guarantees at-least-once delivery, not exactly-once by default, so every one of these consumers must be idempotent — safely re-processing the same order-placed event twice (e.g. after a redelivery following a consumer crash before acknowledgment) must not double-ship, double-notify, or double-flag the same order.

Infrastructure as Code (IaC)

This platform is provisioned with Terraform using the official hashicorp/google provider, currently in the 7.x major version line (e.g. 7.40.0 as of mid-2026). Resource arguments have shifted between major provider versions in the past (renamed fields, changed defaults, deprecated blocks), so production configurations should always pin an exact provider version and check the current provider documentation before upgrading across a major version boundary.

The script below provisions core networking and compute only — a custom-mode VPC, one subnet per region for the multi-region deployment, baseline firewall rules, and a regional GKE Autopilot cluster per region. It deliberately does not provision every service shown in the architecture diagram (Spanner, Pub/Sub, Memorystore, etc.) — those belong in their own focused modules, kept separate from the network/compute foundation shown here.

terraform {
  required_version = ">= 1.7.0"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 7.40.0"  # pin an exact minor version; provider resource
                              # arguments can shift across major versions --
                              # always check current docs before upgrading
    }
  }
}

provider "google" {
  project = var.project_id
  region  = var.region_primary
}

# ---------------------------------------------------------------------------
# Networking -- one custom-mode VPC shared across regions. Custom-mode means
# we declare every subnet explicitly rather than accepting GCP's automatic
# per-region defaults, which keeps IP ranges predictable and non-overlapping.
# ---------------------------------------------------------------------------

resource "google_compute_network" "checkout_vpc" {
  name                    = "checkout-platform-vpc"
  auto_create_subnetworks = false   # custom-mode: subnets are defined below, per region
  routing_mode            = "GLOBAL" # routes/firewall rules apply consistently across all regions
}

resource "google_compute_subnetwork" "primary_region_subnet" {
  name                     = "checkout-subnet-${var.region_primary}"
  ip_cidr_range            = "10.10.0.0/20"
  region                   = var.region_primary
  network                  = google_compute_network.checkout_vpc.id
  private_ip_google_access = true  # lets pods/VMs without external IPs reach
                                    # Google APIs (Spanner, Pub/Sub, Secret Manager, etc.)

  secondary_ip_range {
    range_name    = "pods"
    ip_cidr_range = "10.20.0.0/14"
  }
  secondary_ip_range {
    range_name    = "services"
    ip_cidr_range = "10.30.0.0/20"
  }
}

resource "google_compute_subnetwork" "secondary_region_subnet" {
  name                     = "checkout-subnet-${var.region_secondary}"
  ip_cidr_range            = "10.11.0.0/20"
  region                   = var.region_secondary
  network                  = google_compute_network.checkout_vpc.id
  private_ip_google_access = true

  secondary_ip_range {
    range_name    = "pods"
    ip_cidr_range = "10.21.0.0/14"
  }
  secondary_ip_range {
    range_name    = "services"
    ip_cidr_range = "10.31.0.0/20"
  }
}

# ---------------------------------------------------------------------------
# Firewall rules -- explicit allow-lists plus a deny-all default. Rules are
# evaluated by priority (lower number = evaluated first).
# ---------------------------------------------------------------------------

resource "google_compute_firewall" "allow_health_checks" {
  name      = "allow-gclb-health-checks"
  network   = google_compute_network.checkout_vpc.id
  direction = "INGRESS"
  priority  = 900

  # Google's published source ranges for external/internal load balancer health checks
  source_ranges = ["130.211.0.0/22", "35.191.0.0/16"]

  allow {
    protocol = "tcp"
    ports    = ["80", "443", "8080"]
  }

  target_tags = ["checkout-gke-node"]
}

resource "google_compute_firewall" "allow_internal" {
  name      = "allow-internal-vpc-traffic"
  network   = google_compute_network.checkout_vpc.id
  direction = "INGRESS"
  priority  = 1000

  source_ranges = [
    "10.10.0.0/20", "10.20.0.0/14", "10.30.0.0/20", # primary region: nodes, pods, services
    "10.11.0.0/20", "10.21.0.0/14", "10.31.0.0/20", # secondary region: nodes, pods, services
  ]

  allow {
    protocol = "tcp"
  }
  allow {
    protocol = "udp"
  }
  allow {
    protocol = "icmp"
  }
}

resource "google_compute_firewall" "deny_all_ingress" {
  name      = "deny-all-ingress-default"
  network   = google_compute_network.checkout_vpc.id
  direction = "INGRESS"
  priority  = 65534 # lowest priority -- evaluated last, after the explicit allows above
  source_ranges = ["0.0.0.0/0"]

  deny {
    protocol = "all"
  }
}

# ---------------------------------------------------------------------------
# GKE Autopilot clusters -- one regional cluster per active-active region.
# Autopilot manages node provisioning, patching, and bin-packing; we only
# declare the control plane and its network attachment.
# ---------------------------------------------------------------------------

resource "google_container_cluster" "checkout_primary" {
  name       = "checkout-api-${var.region_primary}"
  location   = var.region_primary # regional (multi-zone control plane), not zonal
  network    = google_compute_network.checkout_vpc.id
  subnetwork = google_compute_subnetwork.primary_region_subnet.id

  enable_autopilot = true # Autopilot mode -- no node_pool blocks allowed/needed

  ip_allocation_policy {
    cluster_secondary_range_name  = "pods"
    services_secondary_range_name = "services"
  }

  release_channel {
    channel = "REGULAR" # balances current GKE/Kubernetes versions against stability
  }

  deletion_protection = true # require explicit override before `terraform destroy` can remove prod
}

resource "google_container_cluster" "checkout_secondary" {
  name       = "checkout-api-${var.region_secondary}"
  location   = var.region_secondary
  network    = google_compute_network.checkout_vpc.id
  subnetwork = google_compute_subnetwork.secondary_region_subnet.id

  enable_autopilot = true

  ip_allocation_policy {
    cluster_secondary_range_name  = "pods"
    services_secondary_range_name = "services"
  }

  release_channel {
    channel = "REGULAR"
  }

  deletion_protection = true
}

Production Terraform practices
Store Terraform state in a remote GCS backend with state locking enabled, never locally and never committed to version control. Keep a separate .tfvars file per environment (dev/staging/prod) so the same module can't accidentally apply prod-sized (or prod-named) resources against a lower environment. Always run terraform plan as a required CI check before any apply is allowed to run, and require human approval on the plan output for production applies specifically.

Best Practices

Security

  • Use Google Cloud IAM least-privilege custom roles per service rather than broad primitive roles (Owner/Editor) — the checkout service should not hold permissions the catalog service needs, and vice versa.
  • Use Workload Identity Federation for every GKE workload instead of downloading long-lived service account key files — keys that can leak, get committed to a repo, or simply never get rotated.
  • Encrypt data at rest with Cloud KMS customer-managed encryption keys (CMEK) across Spanner, Firestore, and Cloud Storage, so key custody and rotation policy live outside any single service's default configuration.
  • Enforce TLS everywhere in transit, terminating at the Global External HTTPS Load Balancer with Google-managed certificates, and again between internal services via mTLS.
  • Use VPC Service Controls around the projects holding order and payment-adjacent data, to create a hard perimeter against data exfiltration even if IAM is misconfigured somewhere downstream.
  • Store all credentials and API keys (including the payment processor's client credentials) in Secret Manager, never in environment variables or container images.
  • Configure Cloud Armor rules for common web attacks (SQLi, XSS, bot/scraper signatures) at the edge, before requests ever reach GKE.

Monitoring, Logging and Alerting

  • Build Cloud Monitoring dashboards around the platform's actual SLOs (p99 checkout latency, 99.95% availability, Spanner commit latency), with alerting policies tied to SLO burn rate rather than raw threshold crossings alone.
  • Centralize structured logs in Cloud Logging across every service, and define log-based metrics for business-relevant events (payment tokenization failures, inventory reservation conflicts) that wouldn't otherwise surface as an infrastructure metric.
  • Instrument the entire checkout call path with Cloud Trace, from the load balancer through the Checkout API, the external payment processor call, and the Spanner transaction — this is what actually lets you find which hop is eating into the 150ms p99 budget.
  • Run uptime checks against the public checkout endpoint from multiple external locations, independent of in-cluster health checks, so a failure mode that only manifests externally (e.g. a load balancer misconfiguration) is still caught.

Cost Optimization

  • Use the CUD (Committed Use Discount) Recommender, which analyzes 30 days of usage history and produces recommendations under two distinct models — one optimized for stable-usage coverage, one optimized for maximum savings — letting a team pick the risk/reward trade-off that matches how predictable its workload actually is.
  • Committed Use Discounts can reduce compute costs by up to 57% for a 1-year commitment and up to 70% for a 3-year commitment — meaningful given this platform's large steady-state GKE and Spanner footprint.
  • As of June 2026, new GCP billing accounts have commitment sharing turned on by default at the billing-account level, meaning a commitment purchased against one project can apply across every eligible project on that account — a real, current lever for an organization running checkout, catalog, and other workloads under a shared billing account rather than one commitment per project.
  • GKE Autopilot's pay-per-pod-resource-request pricing model removes the classic node-level over-provisioning waste of standard GKE, where idle headroom on partially-packed nodes is paid for regardless of utilization.
  • Apply Cloud Storage lifecycle rules to automatically tier cold product images (discontinued SKUs, rarely-viewed listings) down to Nearline or Coldline storage classes, rather than paying Standard-class rates for assets nobody is actively browsing.

Common Interview Questions

These are grouped by theme; expect a real interview to pick a handful as "and then what?" follow-ups rather than working through every one in order.

Consistency and Cloud Spanner

What is TrueTime, and why does it let Spanner claim "external consistency" rather than just "strong consistency"?
TrueTime is Google's globally synchronized clock API, backed by GPS and atomic clocks in Google's data centers, that returns a time interval bounded by a known uncertainty rather than a single instant. Spanner uses that bounded uncertainty to wait out the interval before acknowledging a commit, which lets it assign transactions a global commit order that matches real-world time ordering across regions — external consistency, which is a stronger guarantee than the strict serializability most "strongly consistent" databases offer within a single node or region.
Where does Spanner sit on the CAP theorem, and how does that reconcile with also being globally distributed?
Spanner is a CP system: during a network partition it favors consistency over availability for the affected range, rather than serving potentially stale/conflicting data. In practice, its multi-region replica topology and Paxos-based quorum writes mean partitions are rare and short-lived at the scale most applications operate, but the honest CAP classification is still CP, not "all three."
Why can't Aurora Global Database or Cosmos DB simply replace Spanner here?
Aurora Global Database is strongly consistent only within its single primary write region; cross-region replicas are asynchronous, so a failover can lose the last fraction of a second of writes. Cosmos DB's "Strong" consistency level is real, but it constrains writes to a single region — multi-region active-active writes on Cosmos DB require dropping to a weaker tunable consistency level, reintroducing the exact risk (a double-charge or lost order under concurrent regional writes) this platform is designed to eliminate.
What schema design mistake commonly causes Spanner hotspotting, and how do you avoid it?
Using a monotonically increasing value (like an auto-incrementing order ID or a timestamp) as a leading primary-key column concentrates all new writes on a single key range/split, defeating horizontal scalability. The standard fix is to prefix the key with a high-cardinality, well-distributed value (e.g. a hash of the customer ID or a UUID) so new writes spread evenly across splits.

Compute Trade-offs

When would you pick Cloud Run over GKE Autopilot for a service in this architecture?
For a single, simple, stateless HTTP service where scale-to-zero and near-zero operational overhead matter more than a shared cluster boundary — the catalog-browse API is a good candidate. GKE Autopilot earns its keep when several cooperating microservices need a shared service mesh, consistent network policy, and warm capacity that avoids cold-start latency on the most latency-sensitive path, which describes the checkout API constellation specifically.
GKE Autopilot vs. standard GKE — what do you give up?
Autopilot removes node-level control: no privileged DaemonSets, limited host-level customization, and Google chooses the underlying node shape for you. In exchange you get per-pod billing instead of per-node, and Google handles node provisioning, upgrades, and security patching. For a workload without an unusual node-level requirement, that trade is a clear win.
How does GKE Autopilot's 99.95% SLA relate to the platform's own 99.95% availability target?
It's a favorable but not sufficient alignment — Autopilot's own SLA covers the Kubernetes control plane and node availability, not the application's end-to-end availability, which also depends on Spanner, the load balancer, Pub/Sub, and the application code itself. A real 99.95% SLA commitment requires composing the SLAs (and failure modes) of every dependency in the critical path, not just the compute layer.

Messaging and Async Processing

Pub/Sub is described as "at-least-once" delivery — what does that mean practically for the fulfillment/notification/fraud-review consumers?
A message can be redelivered (e.g. a consumer crashes after processing but before acknowledging), so every consumer must be idempotent: processing the same order-placed event twice must not double-ship, double-email, or double-flag the same order. This is usually implemented by keying processing on the order ID and checking/recording a processed-state before taking the side-effecting action.
Why publish the order-placed event after the Spanner commit rather than before or as part of the same transaction?
Publishing before or during the commit risks announcing an order that Spanner then fails to actually commit (e.g. an inventory conflict), which would trigger fulfillment/notifications for an order that never really happened. Publishing strictly after a successful commit guarantees every event downstream corresponds to a real, durable order.
What happens to the customer-visible checkout latency if Pub/Sub is temporarily degraded?
Nothing, if the publish call is truly fire-and-forget with a bounded local retry/buffer rather than a synchronous blocking call on the critical path. The order is already committed in Spanner before the publish is attempted, so a Pub/Sub outage delays fulfillment/notifications, not the checkout response itself.

Networking and Global Load Balancing

How does the Global External HTTPS Load Balancer's single anycast IP avoid the DNS-based failover problem?
With DNS-based traffic management (e.g. latency-based routing or a Traffic Manager), a client resolves a region-specific IP and caches it for the DNS record's TTL — so a regional failure isn't visible to that client until the TTL expires and it re-resolves. An anycast IP is announced from every region simultaneously at the network (BGP) layer, so routing away from an unhealthy region happens without the client ever needing to re-resolve anything.
Is anycast global load balancing genuinely unique to GCP?
No — AWS Global Accelerator and Azure Front Door both provide anycast-based global entry points today. GCP's differentiator is narrower than "only GCP has this": it's that the Global External HTTPS Load Balancer integrates CDN, WAF, and HTTP(S) load balancing behind that one anycast IP as a single managed resource, whereas achieving the same outcome on AWS commonly involves composing Global Accelerator with per-region ALBs and Route 53.

Cost and Operations

How would you decide between the CUD Recommender's stable-usage-coverage model and its optimal-savings model?
Stable-usage coverage is the safer choice when the checkout platform's baseline (the 500 TPS steady-state, not the flash-sale peaks) is well understood and unlikely to shrink — commit against that floor. The optimal-savings model pushes further and accepts more variance/risk of an under-utilized commitment if usage patterns are still evolving; teams typically start conservative and revisit as 30 more days of usage data accumulate.
What changed about GCP commitment sharing as of June 2026, and why does it matter for a platform like this?
New billing accounts now have commitment sharing turned on by default at the billing-account level, so a CUD purchased against one project (say, the checkout project) automatically applies across every other eligible project on the same billing account (catalog, analytics, etc.), rather than requiring a separate commitment per project. This removes a manual step that previously caused organizations to under-utilize commitments purchased in the "wrong" project.

Security

Why use Workload Identity Federation instead of service account keys for GKE workloads?
A downloaded service account key is a long-lived credential that can leak (committed to a repo, left in a container image, exfiltrated from a compromised pod) with no built-in expiry. Workload Identity Federation lets a Kubernetes service account impersonate a Google service account using short-lived, automatically-rotated tokens tied to the pod's identity, so there's no static key to steal in the first place.

Disaster Recovery and Multi-Region

Walk through what happens if an entire GCP region hosting one of the two active regions goes down.
The Global External HTTPS Load Balancer's health checks detect the region's backends as unhealthy and stop routing new traffic there at the anycast layer — no DNS change required. Cloud Spanner's multi-region configuration already replicates synchronously across regions, so in-flight and already-committed order data in the surviving region(s) remains fully consistent and available; only the failed region's in-flight (not-yet-committed) requests are lost and must be retried by the client, which is an acceptable, bounded blast radius given the alternative of losing consistency guarantees entirely.

Key Takeaways

Remember
This architecture earns the "GCP" label for two specific, defensible reasons, not a general platform preference: Cloud Spanner's external consistency is the only option among the three major clouds that gives synchronous, globally strong-consistent writes across active-active regions — exactly what "an order must never be double-charged or lost" requires in database terms — and the Global External HTTPS Load Balancer's single anycast IP answers the "sub-150ms p99 globally" requirement without hand-built DNS failover logic. Everything else in the stack (GKE Autopilot, Memorystore, Pub/Sub, Firestore, Cloud CDN) is a strong, well-justified default, but not a unique differentiator the way those two are. Be honest in an interview about the real cost of that choice: Spanner carries a genuine operational learning curve and a cost premium over a conventional sharded relational database, and a team without this exact consistency requirement could reasonably choose Aurora Global Database or Cosmos DB instead. State the trade-offs explicitly — CAP classification, consistency model, cost ceiling — because that reasoning is what's actually being evaluated, not just the final box diagram.
