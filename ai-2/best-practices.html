Summary & Best Practices

Overview

Module 1 gave you the mental models — tokens, context windows, embeddings, and how an LLM actually "thinks" in terms of next-token prediction over a fixed-size buffer. Modules 2 and 3 grounded those models in real Java tooling: Spring AI versus LangChain4j as the two dominant JVM frameworks, and the broader landscape of vector stores, model providers, and local-inference options like Ollama. Module 4 put it all together into a working Retrieval-Augmented Generation application — ingestion, chunking, embedding, retrieval, and generation, end to end. This page is the capstone: what changes when that demo needs to become something you would actually put in front of paying customers and defend in a production incident review. Three concerns dominate that transition, and they are the three concerns every interviewer will push on if you claim "production experience" with LLM applications: cost, token and context limits, and security.

Cost Management

Most hosted LLM APIs bill per token, with input tokens and output tokens metered — and priced — separately. Output tokens are typically several times more expensive than input tokens because they are generated one at a time, autoregressively, rather than processed in a single forward pass like the prompt is. A demo that makes a handful of calls a day can rack up a surprising bill once it is serving real traffic, so cost has to be designed for, not bolted on afterward. The main levers:

  • Model tiering — not every request needs the frontier model. Route simple, well-defined requests (classification, short lookups, formatting) to a smaller, cheaper model, and reserve the expensive, high-capability model for requests that genuinely need deep reasoning or long context. A tiered router in front of your LLM calls often cuts spend dramatically with little quality loss.
  • Caching — cache repeated identical prompts and their responses. FAQ-style questions, common support queries, and repeated tool-lookup patterns are prime candidates: serve the cached answer instead of re-calling the API for a question you have already answered verbatim (or near-verbatim, with semantic-cache lookups).
  • Prompt trimming — don't stuff more retrieved context into the prompt than the model actually needs. This ties directly back to the top-K tuning from the Module 4 RAG project: a higher top-K means more input tokens, more cost, and often more noise for the model to sift through, not necessarily a better answer.
  • Streaming + early termination — stream the response token by token rather than waiting for the full completion. If the user's need is met (or they navigate away, or a downstream check fails) before generation finishes, you can cut the stream off early and avoid paying for output tokens you never needed.
  • Usage monitoring and budgets — track token spend per endpoint, per customer, or per feature, and put alerting in front of it. A single misbehaving loop (an agent that keeps calling itself, a retry storm) should trip a budget alarm long before it becomes a monthly-bill surprise.

A rough, illustrative cost estimate in Java might look like this:

// Illustrative only — check your provider's current pricing page before hardcoding numbers.
// Per-token prices change frequently and vary by model tier.
double inputPricePerToken  = 0.000003;  // example: $3.00 per 1M input tokens
double outputPricePerToken = 0.000015;  // example: $15.00 per 1M output tokens

int inputTokens  = 1200;   // prompt + retrieved RAG context
int outputTokens = 350;    // generated completion

double estimatedCost = (inputTokens * inputPricePerToken)
                     + (outputTokens * outputPricePerToken);

// estimatedCost above is illustrative; always source live pricing from the
// provider's official pricing page rather than hardcoding it in production code.

Token Limits & Context Window Management

Recall the Module 1 mental model: the context window is a fixed-size buffer. Everything the model can "see" for a given call — system prompt, conversation history, retrieved RAG chunks, and the current user message — has to fit inside that one buffer, measured in tokens, not characters or words. There is no separate long-term memory the model quietly falls back on; if it isn't in the context window for this call, the model doesn't know it.

Concrete strategies for staying inside that buffer without losing important information:

  • Chunking long documents — the same chunking strategy from the Module 4 RAG pipeline applies here: break large source documents into retrieval-sized pieces up front rather than trying to feed an entire document into a single prompt.
  • Summarizing or compressing conversation history — instead of resending the full transcript of a long conversation on every turn, periodically summarize older turns into a compact running summary and keep only the most recent turns verbatim. This keeps token usage roughly flat as a conversation grows instead of climbing linearly.
  • Capping max output tokens — setting an explicit max_tokens-style ceiling on the response bounds both the length of the answer and its cost in the same setting, and protects you from a runaway generation.

The most important operational detail: exceeding the context window is a hard failure. The API call returns an error — it does not silently truncate your input and continue. Production code should proactively estimate token counts for a request before sending it (using a tokenizer appropriate to the model) and truncate or summarize on the client side ahead of time, rather than discovering the limit only when a call fails in front of a user.

Security Considerations

This is the section that separates a working demo from something safe to ship. LLM applications introduce attack surface that doesn't exist in traditional CRUD services, and most of it is easy to overlook because it doesn't look like a "normal" vulnerability.

Prompt Injection

This is especially relevant for RAG. If you are ingesting untrusted external documents — web pages, user uploads, emails — into your vector store, an attacker can embed instructions inside that content ("ignore previous instructions and...") that the model may follow once that chunk is retrieved into context. The model has no inherent way to distinguish "content I should read" from "instructions I should obey" unless your prompt structure makes that distinction explicit. Mitigation: treat retrieved content as data, not instructions — clearly delimit it in the prompt (for example, wrapping it in tags and instructing the model that anything inside those tags is reference material, not commands), and validate or sanitize model output before acting on it, especially before feeding that output into any tool or function call.

Least-Privilege Tool Calling

When using function/tool calling or agents (as covered in Module 2), scope each tool's permissions tightly. A "look up order status" tool should not also carry DELETE access to the orders table just because it's convenient to reuse one database credential. Never give an LLM-driven agent broad shell, database, or filesystem access without a human-approval gate in front of any destructive action.

Data Privacy

Sending user data to a third-party hosted API means that data leaves your infrastructure. Check the provider's data-retention and training-use policy before sending anything sensitive, and consider self-hosted options (Ollama, or a provider's enterprise/zero-retention tier) for PII, regulated data, or anything your compliance posture requires you to keep in-house.

Output Validation

Never directly render raw model output as HTML, SQL, or shell commands without escaping and validating it first. Treat LLM output with the same suspicion you'd apply to any other untrusted user input — because functionally, that's exactly what it is: text produced outside your control that happens to look authoritative.

Security risk
If there is one idea to carry out of this whole section, it's this: the single biggest LLM security risk is treating retrieved or generated content as trusted instructions instead of untrusted data. Every mitigation above — delimiting retrieved text, scoping tool permissions, validating output before it touches a database or shell — is really just that one principle applied at a different layer of the system.

Choosing the Right Tool — Quick Reference

A quick recap of the framework and infrastructure decisions from Modules 2–4:

Decision Recommendation
Spring Boot shop needing DI-native integration Spring AI
Framework-agnostic / most mature RAG ecosystem LangChain4j
Local development / zero cost / full data privacy Ollama
Already running Postgres pgvector
Need a dedicated, horizontally scalable vector store Milvus or Qdrant

Key Takeaways

  • Cost is a design constraint, not an afterthought — tier your models, cache aggressively, trim prompt context, stream with early termination, and monitor spend with budgets and alerts.
  • The context window is a fixed buffer, and running past it is a hard API error, not silent truncation — estimate tokens client-side and chunk or summarize proactively.
  • Long conversations should be summarized/compressed over time rather than resent in full on every turn.
  • RAG pipelines that ingest untrusted content are exposed to prompt injection — always delimit retrieved content as data, never as instructions.
  • Scope tool/function-calling permissions to least privilege, and gate any destructive action behind human approval.
  • Check data-retention and training-use policies before sending sensitive data to a hosted API, and consider self-hosted options like Ollama for regulated data.
  • Never trust raw LLM output — validate and escape it before rendering it as HTML, SQL, or shell commands, or acting on it via a tool call.
  • The best way to make all of this concrete is to build the Module 4 RAG project yourself, then come back and apply this checklist to it — add a cost estimate, a context-window guard, and an injection-safe prompt template, and you'll have internalized the whole AI 2 series.
