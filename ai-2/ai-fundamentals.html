AI Fundamentals for Java Developers

Overview

This is Part 1 of a two-part track. The goal here is concepts first, tools next: before you touch Spring AI, LangChain4j, a vector database client, or any SDK, you need a correct mental model of what an LLM actually is, what it can and cannot do, and why the surrounding plumbing (tokens, embeddings, retrieval) exists at all. Every framework you'll meet in later pages is just a convenience wrapper around the ideas on this page — skip this page and the frameworks look like magic; read this page and they look like boilerplate.

You already have the right instincts for this. You've built REST clients, you've reasoned about statelessness, you've designed interfaces, you've written caches with fixed capacity, and you've wired dependencies instead of hard-coding them. Every section below takes one AI concept and anchors it to one of those instincts. Nothing here requires calculus, linear algebra proofs, or training a model — you are a consumer of these systems, the same way you're a consumer of a database or a message broker without having implemented B-trees or Raft yourself.

What's covered, in order:

  • LLMs as a stateless, non-deterministic remote function call.
  • Tokens & the context window as the fixed-capacity input/output buffer of that call.
  • Embeddings as a way to turn "meaning" into a comparable numeric array.
  • Prompt engineering as contract design for that function call.
  • RAG as dependency injection for facts the model was never trained on.
  • Common pitfalls that trip up backend engineers moving into this space.

The next pages in this track (starting with Spring AI vs LangChain4j) assume you're comfortable with everything below. If a later page references "the context window" or "cosine similarity" and it doesn't click immediately, come back here first.

Large Language Models (LLMs)

Strip away the hype and an LLM is a function you call over the network. Mentally, treat it as: 

public interface LanguageModel {
    String complete(String prompt, Options options);
}

record Options(
    double temperature,     // randomness knob, typically 0.0–2.0
    double topP,             // nucleus sampling cutoff, 0.0–1.0
    List<String> stop,       // sequences that end generation early
    int maxTokens             // hard cap on how much output comes back
) {}

That's it. There is no hidden object graph, no server-side session tied to "you" between calls. Every call is stateless in the same way a well-designed REST endpoint is stateless: if you want the model to "remember" the last three turns of a conversation, you concatenate that history and pass it back in as part of the next prompt. The model doesn't retain anything from the previous call — there's no instance field being mutated on some server-side object bound to your session. If it feels like it's "remembering," that's an illusion your calling code is producing by resending context, not a capability of the model itself.

Non-determinism is a parameter, not a bug

Call complete() twice with the same prompt and you can get two different answers. That's expected, not a defect to file a ticket against. temperature and topP control how the model samples the next token from a probability distribution instead of always taking the single highest-probability token. Think of them the way you'd think of a seed-less randomized algorithm's tuning parameters: temperature = 0 pushes the model toward the most likely (most deterministic-looking) output every time; higher values deliberately widen the sampling pool for more varied, creative output. Neither setting is "more correct" — it's a trade-off you choose based on the use case (deterministic-leaning for data extraction, higher variance for brainstorming).

stop sequences are delimiters

A stop sequence is just a terminator string, conceptually the same as telling a parser "stop reading at this delimiter." If you tell the model to stop at "\n\n" or at a custom marker like "###END###", generation halts the instant that sequence would be emitted. This is how you keep an LLM from rambling past the structured answer you actually want.

Knowledge is frozen at training time

An LLM's "knowledge" is baked into its weights during a training run that ends on some cutoff date. After that, it's frozen — exactly like a compiled JAR built from a specific commit. You cannot hot-patch a new fact into a running JVM by editing source on disk; you have to recompile and redeploy. Similarly, you cannot teach a deployed LLM about this morning's data, your internal wiki, or a library released last week without retraining or fine-tuning it (an expensive, offline process). This single fact is the entire motivation for Retrieval-Augmented Generation, covered later on this page: instead of "recompiling" the model, you inject fresh context at call time.

Tokens & the Context Window

LLMs don't read characters and don't read whole words — they read tokens, which are subword chunks produced by a tokenizer (most modern models use a Byte-Pair Encoding, or BPE, family of algorithms). A token is often close to a short word or a word fragment, but the split point is determined statistically from training data, not by grammar.

For example, the string "Spring Boot" might tokenize roughly as: 

"Spring Boot"  →  ["Spring", " Boot"]        // 2 tokens, if both are common enough
"SpringBoot"   →  ["Spring", "Boot"]         // no space still splits the same way
"Sprnig Boot"  →  ["S", "pr", "nig", " Boot"] // a typo breaks the "known word" token,
                                                    // falling back to smaller fragments

The exact split is model- and tokenizer-specific — don't memorize a fixed table, just internalize that common whole words tend to be a single token, and rare words, typos, code identifiers, and non-English text tend to fragment into several tokens.

The context window is a fixed-capacity buffer

The context window is the maximum number of tokens the model can consider in a single call, counting both your prompt (system + history + user message + any injected RAG context) and the model's response. Map this directly onto a bounded buffer you already know well — a StringBuilder with a hard capacity ceiling, or a bounded queue. Once you exceed capacity, most APIs don't silently truncate the oldest content for you the way a ring buffer might; by default you get a hard error (an HTTP 4xx / context-length- exceeded exception) and the call fails outright. Any truncation, summarization, or sliding-window strategy is something your calling code is responsible for implementing, the same way you'd have to write your own eviction policy for a bounded cache.

This is why token counting matters in real systems: if you're about to stuff a large document, a long chat history, and several retrieved RAG chunks into one prompt, you need to estimate the token count before the call, not discover the overflow as a runtime exception in production. 

/**
 * Rough token-count heuristic: ~4 characters per token for English text.
 * This is an approximation only — real tokenization is model-specific
 * (BPE-based) and varies with punctuation, whitespace, code, and non-English
 * text. Use this for a cheap pre-flight budget check, never as an exact count.
 */
static int estimateTokenCount(String text) {
    if (text == null || text.isEmpty()) {
        return 0;
    }
    // Integer division rounds down; bias up by 1 so we never under-estimate
    // for short strings and blow the budget on an off-by-one.
    return (text.length() / 4) + 1;
}

Embeddings

An embedding is a fixed-length numeric vector that represents the "meaning" of a piece of text. In Java terms, think of it as nothing more exotic than: 

record Embedding(float[] values) {}
// e.g. values.length == 1536 for one common embedding model

The specific numbers are meaningless in isolation — what matters is distance between vectors. Text that means similar things gets mapped to vectors that sit close together in that high-dimensional space; unrelated text lands far apart. This is what lets a machine do "does this mean roughly the same thing as that?" as pure arithmetic instead of keyword matching.

Cosine similarity similarity(A, B) = (A · B) / (‖A‖ × ‖B‖)
Ranges from -1 (opposite) to 1 (identical direction); ~1.0 means near-identical meaning, ~0 means unrelated. 
/**
 * Cosine similarity between two equal-length embedding vectors.
 * Result is in [-1, 1]: closer to 1 means "more similar meaning".
 */
static double cosineSimilarity(float[] a, float[] b) {
    if (a.length != b.length) {
        throw new IllegalArgumentException("Embeddings must be the same dimension");
    }

    double dotProduct = 0.0;
    double normA = 0.0;
    double normB = 0.0;

    for (int i = 0; i < a.length; i++) {
        dotProduct += a[i] * b[i];   // A · B
        normA += a[i] * a[i];        // running sum for ‖A‖²
        normB += b[i] * b[i];        // running sum for ‖B‖²
    }

    double magnitude = Math.sqrt(normA) * Math.sqrt(normB);
    if (magnitude == 0.0) {
        return 0.0; // guard against a zero vector
    }

    return dotProduct / magnitude;
}

In practice you'll rarely call this yourself in production code — a vector database does the nearest-neighbor search for you at scale — but understanding that it's just dot product over norms de-mystifies every "semantic search" and "similar documents" feature you'll wire up in later pages of this track.

Prompt Engineering

Prompt design maps cleanly onto API and contract design you already do every day:

  • The system prompt is like a class-level Javadoc or an interface contract: it's set once, describes behavior and constraints ("you are a helpful assistant that only answers in JSON," "never reveal internal reasoning," "respond only about topic X"), and applies to every subsequent call in the conversation.
  • The user prompt is the argument list for one specific method call — the actual input for this invocation, layered on top of the standing contract.
  • Few-shot examples are like unit test cases baked directly into the prompt: they pin down expected input/output behavior by concrete example rather than by abstract description, the same way a good test suite communicates intent better than a paragraph of prose.

Prompting styles

  • Zero-shot — you ask directly with no examples, relying entirely on the model's pretrained behavior and your instructions. Fastest to write, least reliable for precise output formats.
  • Few-shot — you include a handful of example input/output pairs in the prompt before the real question, steering the model toward a specific format or style by demonstration.
  • Chain-of-thought — you explicitly ask the model to reason step by step before giving a final answer (e.g. "think through this step by step, then give your final answer on the last line"), which tends to improve accuracy on multi-step logic or arithmetic problems at the cost of more output tokens.
  • Role prompting — you assign the model a persona or expertise framing ("you are a senior Java code reviewer"), which narrows its tone and the assumptions it applies, similar to picking which implementation of an interface to inject for a given context.

Assembling all of this in Java is naturally suited to a text block:

String systemPrompt = """
    You are a strict JSON API. Respond with valid JSON only, matching this
    schema exactly: {"summary": string, "riskLevel": "LOW"|"MEDIUM"|"HIGH"}.
    Never include prose, markdown, or explanations outside the JSON object.
    """;

String fewShotExample = """
    Input: "Customer disputed a $12,000 wire transfer as unauthorized."
    Output: {"summary": "Unauthorized wire transfer dispute", "riskLevel": "HIGH"}
    """;

String userPrompt = """
    Input: "%s"
    Output:
    """.formatted(incomingTicketText);

String fullPrompt = systemPrompt + "\n" + fewShotExample + "\n" + userPrompt;
String response = model.complete(fullPrompt, options);

Retrieval-Augmented Generation (RAG)

Recall from the LLM section: the model's knowledge is frozen at training time, like a JAR compiled from an old codebase. It has no idea about your company's private documentation, your internal APIs, last night's incident report, or anything published after its training cutoff. You cannot "recompile" a hosted model on demand just to teach it your data.

RAG solves this the same way you'd solve a hard-coded dependency problem in Java — with dependency injection. Instead of baking knowledge permanently into the model's weights, you inject the relevant facts at call time, fetched fresh from an external store, and hand them to the model as part of the prompt for that one call. The model's weights never change; you're just supplying it with the right collaborator at the right moment, exactly like injecting a different implementation of a repository interface at runtime instead of hard-coding a class reference at compile time.

The RAG pipeline

  1. Chunk — split your source documents (wikis, PDFs, tickets, code) into smaller, manageable pieces.
  2. Embed — run each chunk through an embedding model to produce a vector representing its meaning.
  3. Store — persist those vectors (plus the original text) in a vector database or index built for nearest-neighbor search.
  4. Embed the query — at query time, run the user's question through the same embedding model to get a query vector.
  5. Similarity search — search the vector store for the top-K chunks whose vectors are closest to the query vector.
  6. Augment the prompt — stuff those retrieved chunks into the LLM prompt as context, alongside the user's actual question.
  7. Generate — the LLM produces an answer grounded in the retrieved context instead of relying solely on its frozen training data.
Why not just fine-tune?
Fine-tuning further trains the model's weights on your own examples — it's expensive, offline, and produces a new, static artifact (again, think "recompiling the JAR"). It's well suited to changing style, tone, or output format consistently, but it's a poor fit for injecting fresh, fast-changing facts: every time your underlying data changes you'd need to retrain again. RAG, by contrast, is cheap to update (just re-index the changed documents), keeps the model's weights untouched, and lets you cite exactly which chunks were used to ground an answer — something a fine-tuned model can't give you, since "why did it say that" has no traceable source once facts are baked into weights.

Common Pitfalls

  • Hallucination — when the model lacks grounding for a question, it will often still answer confidently and simply be wrong, rather than saying "I don't know." Treat any ungrounded factual claim from an LLM the way you'd treat unvalidated user input: verify before trusting, especially for anything that drives a business decision.
  • Testing non-deterministic output — asserting on an exact output string is fragile because the same prompt can legitimately produce different wording on different calls. Test structure and behavior instead: does the response parse as valid JSON, does it contain the expected field, does it pass a business rule — not "does it equal this exact string."
  • Context window overflow in RAG — it's easy to retrieve too many chunks, or chunks that are too large, and blow the context window budget once you add the system prompt, chat history, and retrieved context together. Budget tokens across all of these up front, the same way you'd budget memory across components in a bounded system.
  • Embedding-model mismatch — you must use the same embedding model to index your documents and to embed queries at search time. Swapping embedding models mid-stream (or upgrading versions without re-indexing) produces vectors from two incompatible spaces; the numbers still "work" arithmetically, cosine similarity still returns a number, but the number is meaningless and search quality silently degrades instead of throwing an obvious error.

Key Takeaways

  • An LLM is best modeled as a stateless, non-deterministic remote function: String complete(String prompt, Options options). There's no server-side memory between calls unless you resend context yourself.
  • Tokens are subword units, not characters or words; the context window is a fixed-capacity buffer covering prompt + response combined, and overflowing it is a hard error by default, not silent truncation.
  • Embeddings turn meaning into a fixed-length float[]; cosine similarity measures how close two pieces of text are in meaning, from -1 to 1.
  • Prompt engineering is contract design: system prompt as standing contract, user prompt as call arguments, few-shot examples as pinned-down test cases.
  • RAG is dependency injection for facts: instead of baking knowledge into frozen weights, you inject retrieved context at call time from an external, updatable store.
  • Watch for hallucination, brittle exact-string tests, context overflow, and embedding-model mismatches — each has a direct analog in problems you already know how to guard against in regular backend systems.
