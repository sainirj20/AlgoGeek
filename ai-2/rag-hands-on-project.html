Hands-on RAG Project

What We're Building

By the end of this page you'll have a small, fully-working Spring Boot REST service that does real retrieval-augmented generation end to end: it ingests a handful of plain-text FAQ documents, embeds them and stores the vectors in Postgres via the pgvector extension, and exposes a single POST /ask endpoint that answers questions grounded only in those ingested documents. It is intentionally minimal — no authentication, no UI, no multi-tenant anything — because the goal is to see the RAG mechanics (chunk, embed, store, retrieve, augment, generate) laid out in actual code you can run on your laptop, not to build a production system. We use Spring AI + pgvector here specifically because pgvector is just a Postgres extension: if you've ever run a Postgres container and written a JDBC connection string, there is nothing new to learn about the storage layer, which lets you focus entirely on the RAG logic itself.

Step 1: Project Setup

Start a normal Spring Boot project (Spring Initializr or your IDE's wizard both work fine) and add the following dependencies to your pom.xml: 

<dependencies>
    <!-- Web layer: REST controllers, embedded Tomcat -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <!-- Spring AI chat model starter (OpenAI shown here).
         Swap for spring-ai-starter-model-anthropic or spring-ai-starter-model-ollama
         as needed -- the rest of this tutorial is provider-agnostic. -->
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-starter-model-openai</artifactId>
    </dependency>

    <!-- Vector store backed by the pgvector Postgres extension -->
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
    </dependency>

    <!-- Testing -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

<!-- Spring AI ships its own BOM -- import it in dependencyManagement to
     keep every spring-ai-* artifact on a matching, compatible version. -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>1.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

Next, spin up a local Postgres instance with the pgvector extension pre-installed using Docker Compose — this saves you from having to compile the extension yourself: 

# docker-compose.yml
version: "3.8"
services:
  pgvector-db:
    image: pgvector/pgvector:pg16
    container_name: rag-pgvector
    restart: unless-stopped
    environment:
      POSTGRES_DB: ragdb
      POSTGRES_USER: raguser
      POSTGRES_PASSWORD: ragpass
    ports:
      - "5432:5432"
    volumes:
      - pgvector_data:/var/lib/postgresql/data

volumes:
  pgvector_data:

Run docker compose up -d and you should have a Postgres instance listening on localhost:5432 with the vector extension available for Spring AI to use.

Step 2: Application Configuration

Wire the datasource and the Spring AI properties together in application.yml: 

spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/ragdb
    username: raguser
    password: ragpass
    driver-class-name: org.postgresql.Driver

  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
    vectorstore:
      pgvector:
        # Must match the embedding model's output dimension exactly.
        # text-embedding-3-small / text-embedding-ada-002 both produce 1536-dim vectors.
        dimensions: 1536
        index-type: HNSW
        distance-type: COSINE_DISTANCE
        initialize-schema: true
Secrets hygiene
The API key must be supplied via an environment variable (or a proper secrets manager in production) — never hardcode it into application.yml or commit it to source control.

Setting initialize-schema: true tells Spring AI to create the backing table and vector index for you on first startup, which is convenient for a tutorial but is usually something you'd hand off to a proper migration tool (Flyway/Liquibase) in a real project.

Step 3: Ingestion Pipeline (ETL)

Drop a few plain-text FAQ files into src/main/resources/docs/ (e.g. shipping-faq.txt, returns-faq.txt, billing-faq.txt). Then write a CommandLineRunner that loads, splits, and embeds them into the vector store the moment the application starts: 

package com.example.rag.ingestion;

import org.springframework.ai.document.Document;
import org.springframework.ai.reader.TextReader;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.boot.CommandLineRunner;
import org.springframework.core.io.Resource;
import org.springframework.core.io.support.PathMatchingResourcePatternResolver;
import org.springframework.stereotype.Component;

import java.util.ArrayList;
import java.util.List;

/**
 * Runs once at application startup and loads a handful of plain-text FAQ
 * documents (src/main/resources/docs/*.txt) into the vector store so the
 * /ask endpoint has something grounded to retrieve from.
 *
 * NOTE: this is a tutorial-grade ETL step, not a production ingestion
 * pipeline -- see the paragraph below this listing for what's missing.
 */
@Component
public class DocumentIngestionRunner implements CommandLineRunner {

    private final VectorStore vectorStore;
    private final TokenTextSplitter textSplitter;

    // Constructor injection only -- no @Autowired field injection.
    public DocumentIngestionRunner(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
        // Default splitter settings chunk on a few hundred tokens with a
        // slight overlap; see "Common Pitfalls" below for why this matters.
        this.textSplitter = new TokenTextSplitter();
    }

    @Override
    public void run(String... args) throws Exception {
        PathMatchingResourcePatternResolver resolver = new PathMatchingResourcePatternResolver();
        Resource[] faqResources = resolver.getResources("classpath:docs/*.txt");

        List<Document> allChunks = new ArrayList<>();

        for (Resource resource : faqResources) {
            // TextReader turns one Resource into one Document (whole-file text
            // plus metadata). We tag each Document with its source filename so
            // later we can trace an answer back to the file it came from.
            TextReader reader = new TextReader(resource);
            reader.getCustomMetadata().put("source", resource.getFilename());
            List<Document> rawDocuments = reader.get();

            // Split each raw document into smaller, retrieval-friendly chunks.
            List<Document> chunks = textSplitter.apply(rawDocuments);
            allChunks.addAll(chunks);
        }

        // Embeds each chunk (via the configured EmbeddingModel) and writes the
        // resulting vectors + text + metadata into the pgvector-backed table.
        vectorStore.add(allChunks);

        System.out.printf("Ingested %d chunk(s) from %d file(s) into the vector store.%n",
                allChunks.size(), faqResources.length);
    }
}

Note that this ETL step is idempotent-unsafe as written: every application restart re-reads, re-splits, and re-embeds the same files and inserts a fresh set of rows, so you'll end up with duplicate vectors for unchanged content. In a real system you'd compute a checksum (or store a stable document id) per source file, check it against what's already in the vector store, and skip re-embedding anything that hasn't changed — both to save embedding API cost and to keep retrieval results from being cluttered with duplicate chunks.

Step 4: Building the RAG Query Endpoint

This is the actual RAG loop: retrieve the most relevant chunks for the incoming question, stuff them into a prompt template, and let the chat model generate an answer constrained to that context. 

package com.example.rag.web;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.document.Document;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;
import java.util.stream.Collectors;

@RestController
public class AskController {

    private final VectorStore vectorStore;
    private final ChatClient chatClient;

    // Constructor injection: VectorStore for retrieval, ChatClient for generation.
    public AskController(VectorStore vectorStore, ChatClient.Builder chatClientBuilder) {
        this.vectorStore = vectorStore;
        this.chatClient = chatClientBuilder.build();
    }

    public record AskRequest(String question) {}

    public record AskResponse(String answer) {}

    @PostMapping("/ask")
    public AskResponse ask(@RequestBody AskRequest request) {

        // 1. RETRIEVE: pull the top-4 most similar chunks from pgvector.
        List<Document> matches = vectorStore.similaritySearch(
                SearchRequest.query(request.question()).withTopK(4));

        String context = matches.stream()
                .map(Document::getContent)
                .collect(Collectors.joining("\n---\n"));

        // 2. AUGMENT: stuff the retrieved context into the prompt template.
        //    The explicit "say you don't know" instruction is what keeps the
        //    model from silently falling back on its own general knowledge.
        String augmentedPrompt = """
                Answer the question using ONLY the context below. \
                If the answer isn't in the context, say you don't know.

                Context:
                %s

                Question:
                %s
                """.formatted(context, request.question());

        // 3. GENERATE: send the augmented prompt to the chat model and
        //    return only the plain-text answer.
        String answer = chatClient.prompt()
                .user(augmentedPrompt)
                .call()
                .content();

        return new AskResponse(answer);
    }
}

Notice there is no separate "prompt engineering" service and no manual HTTP call to an embeddings API — VectorStore.similaritySearch handles embedding the query and running the nearest-neighbor search against pgvector, and ChatClient handles the call to the chat model. All the RAG-specific logic lives in how you build augmentedPrompt.

Step 5: Testing the Application

With the Postgres container running, the FAQ files ingested at startup, and OPENAI_API_KEY exported in your shell, start the app and hit the endpoint: 

curl -X POST http://localhost:8080/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "What is your refund policy for digital purchases?"}'

A realistic response, assuming your returns-faq.txt covers this topic, looks like:

{
  "answer": "According to the FAQ, digital purchases are refundable within 14 days of purchase as long as the item has not been downloaded or activated. Refund requests should be submitted through the Support > Billing section of your account."
}

Beyond "did it return 200 OK", the real thing to check is groundedness: spot-check a handful of answers against the actual ingested documents and confirm the model is citing facts that are really in your FAQ files rather than quietly falling back on whatever it happens to know about refund policies in general. Try a question you know is not covered by your documents and confirm you get an honest "I don't know" instead of a plausible-sounding hallucination. This manual spot-checking is fine for a tutorial, but in a production system this is exactly where you'd build a proper evaluation harness — a fixed set of question/expected-answer pairs run automatically on every change to the ingestion pipeline, prompt template, or model, so groundedness regressions get caught before they ship.

Common Pitfalls

Watch out for these
  • Chunk size tuning. Chunks that are too large hurt retrieval precision (a match drags in a lot of irrelevant surrounding text); chunks that are too small lose context coherence (a match is a fragment with no surrounding meaning). A few hundred tokens per chunk with a small overlap is a reasonable starting point — tune from there based on your actual documents.
  • Embedding dimension mismatches. The spring.ai.vectorstore.pgvector.dimensions value must exactly match the output dimension of whatever embedding model you're actually using. Get this wrong and you'll either get a hard error at write time or, worse, silently corrupted similarity results.
  • Stale index after source updates. Editing or replacing a source FAQ file does nothing to the vector store on its own — if you don't re-run ingestion (and, per Step 3, remove the old chunks for that document first), /ask keeps answering from outdated content.

Key Takeaways

  • A working RAG service is really just five moving pieces: source documents, a splitter, an embedding model, a vector store, and a chat model that consumes an augmented prompt.
  • Spring AI's VectorStore abstraction and ChatClient API let pgvector, OpenAI, and every other provider slot in behind the same interfaces — the ingestion and query code you wrote here barely changes if you swap the backing store or model provider.
  • TokenTextSplitter chunk size is one of the highest-leverage tuning knobs in the whole pipeline — get it wrong and no amount of prompt tweaking fixes bad retrieval.
  • The augmented prompt's "answer only from context, otherwise say you don't know" instruction is what actually keeps the system grounded — without it you have a vector search bolted onto a chatbot, not RAG.
  • Ingestion is not "run once and forget" — treat it as a pipeline with idempotency and staleness concerns, the same way you would any other ETL job.
  • Groundedness has to be verified deliberately, by spot-check at minimum and by an automated eval harness before this pattern goes anywhere near production.
