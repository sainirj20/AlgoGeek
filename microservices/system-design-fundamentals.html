Overview

System design is the process of planning how a software system should be structured — what pieces it's made of, how those pieces talk to each other, and how the whole thing behaves once real users, real traffic, and real failures show up. It sits one level above writing code: instead of asking "how do I write this function," system design asks "how do I organize services, databases, caches, and networks so the product keeps working as it grows from ten users to ten million." Think of it like the difference between being a skilled bricklayer and being an architect who decides where the walls, plumbing, and electrical systems go — you need both skills, but system design is the architect's job.

Every system design decision is a trade-off, and the goal is almost never to build the "perfect" system — it's to build the right system for the requirements at hand. Designers typically separate requirements into two buckets: functional requirements (what the system must do — e.g. "users can send money to each other") and non-functional requirements (how well it must do it — e.g. "a payment must confirm within 2 seconds, even at 50,000 transactions per second, and never lose money"). From there, designers estimate scale (users, data, requests per second) using back-of-the-envelope math, and use those numbers to decide things like how many servers are needed or whether data needs to be split across multiple machines.

Good system design leans on a common toolbox of building blocks that show up again and again regardless of the product: load balancers to spread traffic, caches to avoid repeated expensive work, databases (relational or NoSQL) to store data reliably, message queues to decouple slow or unreliable steps, CDNs to serve content close to users, and API gateways to manage how the outside world talks to internal services. Netflix streaming to 300+ million subscribers, Uber matching riders and drivers in real time, and a payments company processing billions of transactions a year are all built by combining these same basic building blocks in different configurations, tuned for their own trade-offs around consistency, latency, and cost. This is why system design is one of the most heavily tested skills in interviews — it reveals whether someone can reason about ambiguity, scale, and failure, not just whether they can write correct code.

What Is a Distributed System?

A distributed system is a collection of independent computers that work together and present themselves to users as if they were a single, unified system. Instead of one giant machine doing everything, work is spread across many machines connected by a network — which is how virtually every large-scale application, from Google Search to Instagram to a bank's core processing systems, actually runs today. Building software this way brings huge benefits in scale and reliability, but it also introduces a set of recurring challenges that don't exist in a single-machine program. The rest of this page walks through the core properties every distributed system has to reason about.

Scalability

Scalability is a system's ability to keep working well as demand grows — more users, more data, more requests per second — by adding more resources rather than falling over. There are two basic ways to scale: vertical scaling (making an existing machine bigger — more CPU, more RAM) and horizontal scaling (adding more machines and spreading the work across them). Vertical scaling is simple but has hard limits — at some point there's no bigger machine to buy, and the cost of very large machines grows much faster than their capacity. Horizontal scaling is what allows systems to grow essentially without limit, which is why almost all large-scale distributed systems are designed around it.

For stateless application servers (ones that don't store data locally between requests), horizontal scaling is relatively easy — just add more identical servers behind a load balancer. Scaling the data layer is harder, and typically relies on sharding (also called partitioning) — splitting a dataset across multiple database servers so no single database has to hold or serve all the data. Systems like Cassandra, MongoDB, and Google's Bigtable are all built around this idea, distributing data using a partitioning key so reads and writes scale roughly linearly as more machines are added. Real-world companies like Netflix and Uber run thousands of independently scalable microservices, often orchestrated by Kubernetes, whose auto-scaling features add or remove capacity for each service based on real-time demand.

Availability

Availability measures the percentage of time a system is actually up and able to successfully respond to requests. It's usually expressed in "nines" — 99.9% ("three nines") allows about 44 minutes of downtime a month, while 99.99% ("four nines") allows only around 4-5 minutes a month, and each additional nine is roughly ten times harder and more expensive to achieve. Distributed systems pursue high availability mainly through redundancy: running multiple copies of a service across different servers, data centers, or even geographic regions, so the failure of any single one doesn't take the whole system down. Availability also compounds across dependencies — if a system depends on ten other services that are each 99.9% available, the combined availability of the whole chain is lower than any individual piece, which is why designing for graceful degradation matters as much as designing for uptime.

A foundational concept here is the CAP theorem: when a network partition occurs (some machines temporarily can't talk to others), a system must choose between consistency (every node sees the same, most up-to-date data) and availability (every request still gets a response, even if possibly stale). Since network partitions are unavoidable in distributed systems, this isn't a theoretical trade-off — it's one every real system makes. Databases like Amazon DynamoDB and Cassandra are commonly tuned to favor availability (AP), continuing to serve reads/writes during a partition even at the risk of temporary inconsistency, while traditional relational databases and systems like Google Spanner lean toward consistency (CP), preferring to reject some requests rather than serve stale or conflicting data.

The CAP theorem: a distributed system can only fully guarantee two of Consistency, Availability, and Partition Tolerance at once.

Latency and Performance

Latency is the time it takes for a single request to get a response, while throughput is how many requests a system can handle in total over a given time — a system can have low latency but low throughput, or vice versa, and good design usually needs to balance both. Rather than looking only at average latency, engineers track percentiles like p50 (median), p95, and p99 — the p99 latency tells you how slow the slowest 1% of requests are, which matters because average latency can look great while a meaningful chunk of users have a genuinely bad experience. This "tail latency" problem gets worse the more services a single request depends on: if a request fans out to 100 backend calls and each has just a 1% chance of being slow, the probability that at least one of them is slow — dragging down the whole request — climbs to over 60%.

Tail latency is typically caused by things like garbage collection pauses, lock contention, cold caches, and network retries — all unpredictable in timing even when the underlying cause is well understood. Common mitigations include caching frequently accessed data close to where it's needed (Redis, Memcached, or CDNs like Cloudflare/CloudFront for static content), setting sensible timeouts so one slow dependency can't stall an entire request chain, using asynchronous processing for non-urgent work, and shedding load gracefully when the system is overwhelmed rather than letting everything slow down together.

Concurrency and Coordination

Concurrency refers to multiple operations happening at the same time across different parts of a distributed system — multiple users updating the same record, multiple services processing related events simultaneously, and so on. Without care, concurrency creates race conditions, where the final outcome depends on the unpredictable timing of events (e.g. two users both trying to update the same account balance at once, one silently overwriting the other). Handling this requires concurrency control, generally falling into two camps: pessimistic locking (a resource is locked before use so no one else can touch it at the same time — useful when conflicts are common) and optimistic concurrency control (operations proceed without locking but are checked for conflicts before finalizing, retrying if a conflict is detected — scales better when conflicts are rare).

Beyond controlling access to a single piece of data, distributed systems often need coordination — getting multiple independent machines to agree on something, like who the current leader is, or whether a transaction should commit. This is the job of consensus algorithms like Paxos and Raft, which let a group of machines agree on a single answer even when some are slow, unreachable, or have failed. These aren't just academic ideas: etcd (built on Raft) is the coordination backbone that powers Kubernetes itself, Apache ZooKeeper coordinates systems like Kafka and Hadoop, and HashiCorp Consul provides similar coordination for service meshes. For coordinating changes across multiple databases or services at once, systems also use patterns like the two-phase commit protocol or, in modern microservices, the Saga pattern, which breaks a multi-step transaction into a series of local steps with defined compensating actions if something fails partway through.

Monitoring and Observability

Monitoring means watching a known set of metrics and alerting when something crosses a threshold you already anticipated — for example, alerting when CPU usage exceeds 90% or error rates spike. Observability goes a step further: it's the broader property of a system that lets engineers understand what's happening inside it — including failure modes nobody predicted in advance — just by examining the data it produces from the outside. Observability is usually built from three complementary types of data, the "three pillars": metrics (numeric measurements over time), logs (detailed timestamped records of individual events), and traces (records that follow a single request as it travels across multiple services, showing exactly where time was spent).

In practice, teams commonly build this stack using Prometheus to collect and store metrics, Grafana to visualize them in dashboards, and a tracing system like Jaeger or Grafana Tempo to follow requests across services — with OpenTelemetry emerging as the vendor-neutral, industry-standard way to instrument applications so they emit consistent metrics, logs, and traces regardless of which backend tools store and view them. On top of this data, teams typically define Service Level Indicators (SLIs — the actual measurements) and Service Level Objectives (SLOs — the targets, like "99.9% of requests complete in under 300ms"), an approach popularized by Google's Site Reliability Engineering practice, and set up alerting (Alertmanager, PagerDuty, Opsgenie) so humans get notified before small issues become outages.

Resilience and Error Handling

Resilience is a system's ability to keep working — even if in a degraded or limited way — when something inevitably goes wrong, rather than failing completely. In a distributed system built from many services calling each other over a network, failures are not rare edge cases; they're a routine, expected part of operating at scale, so resilience has to be designed in deliberately rather than treated as an afterthought.

A handful of well-established patterns make this possible. Timeouts ensure a service doesn't wait forever for a response from a slow dependency, failing fast instead of tying up resources indefinitely. Retries (ideally with exponential backoff and jitter, to avoid many clients retrying at the exact same moment) handle transient failures likely to succeed if simply tried again. The circuit breaker pattern — popularized by Netflix's Hystrix library and continued today by libraries like resilience4j — monitors for repeated failures to a dependency and, once a threshold is crossed, "opens" the circuit to stop sending requests entirely for a period, preventing a struggling service from being hammered further. Bulkhead isolation limits how many resources (threads, connections) any single dependency can consume, so a problem with one dependency can't exhaust resources needed for everything else. Finally, fallback logic and graceful degradation let a system return a reasonable partial answer instead of a hard failure when a dependency is unavailable. Netflix is well known for taking this further with Chaos Engineering — deliberately injecting failures into production (via tools like Chaos Monkey) to continuously verify these resilience mechanisms actually work.

Fault Tolerance vs. High Availability

Fault tolerance and high availability are closely related and often used together, but solve slightly different problems. Fault tolerance is a system's ability to keep operating correctly, without interruption, even when one or more internal components fail — the failure is essentially masked from the outside world. High availability is about minimizing downtime overall, accepting that brief interruptions might happen but ensuring the system recovers and gets back online extremely quickly through redundancy and automatic failover. A useful mental model: fault tolerance behaves like an immune system, absorbing damage internally without the rest of the body noticing; high availability behaves like an emergency backup generator, which needs a brief moment to kick in but gets the lights back on fast.

In practice, use both together
Real production systems combine both ideas rather than choosing one. A well-designed distributed system uses fault-tolerance patterns inside individual services (retries, circuit breakers, redundant data replicas) while also being deployed across highly available infrastructure (multiple availability zones/regions, redundant load balancers, auto-scaling groups) — so both individual component failures and larger infrastructure outages can be absorbed without meaningfully disrupting users.

Common Interview Questions

Why is horizontal scaling generally preferred over vertical scaling for large distributed systems?
Vertical scaling hits a hard ceiling — there's always a biggest machine you can buy, and its cost grows much faster than its capacity. Horizontal scaling lets you add commodity machines roughly without limit, and for stateless application servers it's simple (just add more instances behind a load balancer); the harder part is scaling the data layer, which is why sharding exists.
Why does average latency hide problems that p99 latency reveals?
Average latency can look great even if a meaningful fraction of requests are slow, because a few very fast requests can pull the average down. p99 tells you how bad the slowest 1% of requests are — and since a single user request often fans out to many backend calls, even a small per-call chance of being slow compounds into a much higher chance that at least one call in the chain is slow, dragging down the whole request.
What's the practical difference between fault tolerance and high availability?
Fault tolerance masks failures entirely — the system keeps running with zero interruption because redundant components absorb the failure internally, usually at higher cost (duplicate hardware running in lockstep). High availability accepts that a brief interruption might occur but is engineered to recover and fail over extremely quickly (seconds to minutes), which is cheaper and is what most real systems actually target.
How does the CAP theorem inform whether you pick a database that favors consistency or availability?
During a network partition, you can't have both perfect consistency and full availability, so the choice should match the use case: pick a CP system (favoring consistency, e.g. traditional relational databases, Google Spanner) when stale or conflicting data is unacceptable, like financial balances; pick an AP system (favoring availability, e.g. DynamoDB, Cassandra) when it's better to keep serving requests with possibly-stale data than to reject them outright, like a social media feed or shopping cart.
Why does resilience need to be designed in deliberately rather than added later?
In a distributed system built from many services calling each other over a network, failures are a routine, expected part of operating at scale — not a rare edge case. Retrofitting timeouts, retries, circuit breakers, and bulkheads after an outage is far more painful than designing them in from the start, and practices like Chaos Engineering exist specifically to continuously verify these mechanisms actually work before a real failure tests them for you.

Key Takeaways

Remember
Every distributed system has to reason about the same core properties: scalability (favor horizontal scaling, shard the data layer), availability (redundancy plus an explicit CAP theorem trade-off), latency (track p99, not just average, and mitigate tail latency with caching/timeouts/async work), concurrency and coordination (locking strategies plus consensus algorithms like Raft), observability (metrics, logs, and traces together), and resilience (timeouts, retries with backoff/jitter, circuit breakers, bulkheads, graceful degradation). Fault tolerance and high availability are complementary, not interchangeable — production systems layer both.
