Transactions & Concurrency

Overview

A transaction is the unit of work that gives you ACID guarantees: a group of reads and writes that either all succeed together or all fail together, in isolation from other concurrent work, and durably once committed. In a Spring/JPA application, that unit of work is almost always demarcated with @Transactional. Getting the transaction boundary right — where it starts, where it ends, what happens on an exception — is one of the most common sources of subtle production bugs: partial writes, stale reads, lazy-initialization exceptions, and silent data corruption under concurrent updates all trace back to a misunderstood or misplaced transaction boundary.

ACID Properties, Briefly

The four guarantees a transaction is supposed to provide:

  • Atomicity — all the operations in the transaction succeed, or none of them do; there is no partially-applied state.
  • Consistency — a transaction moves the database from one valid state to another valid state, respecting constraints, cascades, and invariants.
  • Isolation — concurrent transactions do not see each other's uncommitted changes; the degree of isolation is tunable and trades correctness for throughput.
  • Durability — once a transaction commits, its effects survive a subsequent crash (the database has persisted it to durable storage, typically via a write-ahead log).

Transaction Boundaries with @Transactional

Wrap a multi-step operation in a single transaction so that a failure partway through rolls back everything already done, instead of leaving the entity in a half-updated state. Consider publishing a blog post — changing its status and stamping a publish time should either both happen or neither happen:

@Transactional
public void publish(Long postId) {
    Post post = postRepository.findById(postId)
            .orElseThrow(() -> new PostNotFoundException(postId));
    post.setStatus(PostStatus.PUBLISHED);
    post.setPublishedAt(Instant.now());
    // no explicit save() needed - the managed entity is dirty-checked
    // and flushed automatically when the transaction commits
}

Because post is a managed entity inside the persistence context, Hibernate's dirty-checking mechanism detects the field changes and issues the UPDATE automatically at flush/commit time — there's no need to call save() again.

Propagation. The default propagation, REQUIRED, joins an existing transaction if one is already active, or starts a new one if not — this is what you want for the vast majority of methods, since it keeps everything in one atomic unit. REQUIRES_NEW suspends any current transaction and always starts a brand-new one; it's used sparingly, for cases like audit logging or notification records that must commit independently of the outer transaction's outcome (so they persist even if the caller later rolls back).

Rollback rules. By default, Spring only rolls back a transaction on an unchecked exception (a RuntimeException or Error); a checked exception thrown from a @Transactional method does not trigger a rollback unless you explicitly say so with @Transactional(rollbackFor = SomeCheckedException.class). This surprises a lot of developers who assume "any exception rolls back the transaction."

Isolation Levels

The SQL standard defines four isolation levels, each preventing progressively more of the anomalies that can occur when transactions run concurrently:

  • READ_UNCOMMITTED — the weakest level; allows dirty reads (seeing another transaction's uncommitted changes), non-repeatable reads, and phantom reads. Rarely used in practice.
  • READ_COMMITTED — prevents dirty reads (you only ever see committed data), but a row you read twice in the same transaction can change between reads (non-repeatable read), and a range query can return different rows on a second execution (phantom read).
  • REPEATABLE_READ — prevents dirty reads and non-repeatable reads (a row you've already read is guaranteed to look the same for the rest of the transaction), but phantom reads — new rows appearing in a repeated range query — can still occur (behavior here varies by database vendor).
  • SERIALIZABLE — the strictest level; transactions behave as if executed one at a time, one after another. Prevents dirty, non-repeatable, and phantom reads, at the cost of the most contention and the lowest throughput.

Most relational databases (PostgreSQL, Oracle, SQL Server) default to READ_COMMITTED. It's a pragmatic middle ground: good throughput, no dirty reads, but you can still be surprised by non-repeatable or phantom reads if your logic assumes a fully static snapshot. Stricter isolation levels buy you stronger correctness guarantees but reduce concurrency and throughput, since the database has to hold more locks or do more conflict detection — so isolation level should be chosen deliberately, not left as an afterthought.

Optimistic Locking with @Version

Isolation levels control what a transaction can see; they don't by themselves stop two concurrent transactions from both reading the same row and then both writing conflicting updates ("lost update"). That's what row-level concurrency control is for, and the mechanism used day to day in most applications is optimistic locking via @Version:

@Entity
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    @Enumerated(EnumType.STRING)
    private PostStatus status;

    @Version
    private int version;

    @ManyToOne(fetch = FetchType.LAZY)
    private Author author;

    // getters and setters omitted
}

The mechanism is simple but effective: every time Hibernate updates a versioned entity, it includes the current version in the WHERE clause and increments it in the SET clause — effectively UPDATE post SET title = ?, version = version + 1 WHERE id = ? AND version = ?. If another transaction already updated the row and bumped its version in the meantime, this WHERE clause matches zero rows. Hibernate detects the row-count mismatch and throws OptimisticLockException (wrapped as ObjectOptimisticLockingFailureException in Spring Data), rather than silently overwriting someone else's change.

At the service layer, that exception is typically caught and translated into a client-facing "someone else already updated this" error rather than a raw 500:

@Transactional
public void updateTitle(Long postId, String newTitle, int expectedVersion) {
    try {
        Post post = postRepository.findById(postId)
                .orElseThrow(() -> new PostNotFoundException(postId));
        post.setTitle(newTitle);
    } catch (ObjectOptimisticLockingFailureException ex) {
        throw new StaleUpdateException(
                "This post was modified by someone else. Please reload and retry.");
    }
}

Note that the OptimisticLockException is typically only raised at flush/commit time (when the UPDATE actually runs), so in practice you often need to catch it around the transactional boundary itself, or let it propagate and handle it in a controller-level exception handler.

Optimistic vs. Pessimistic Locking

Optimistic locking assumes conflicts are rare: it lets every transaction proceed as if it has exclusive access, and only detects a conflict at write time via the version check. There's no database lock held while the user is "thinking" between reading and writing — which matters a lot in a web application, where a row might be read on one request and updated several seconds (or minutes) later on another request. That's why optimistic locking is the default choice for most web applications: contention is typically low, and holding a database lock across an HTTP request's think-time would be a serious scalability problem.

Pessimistic locking takes the opposite approach: it acquires a database-level lock up front and holds it until the transaction ends, guaranteeing no other transaction can read (for update) or write the row in the meantime:

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Post p where p.id = :id")
Optional<Post> findByIdForUpdate(@Param("id") Long id);

This issues a SELECT ... FOR UPDATE under the hood, blocking other transactions that try to acquire a conflicting lock on the same row until the current transaction commits or rolls back. That guarantees there's no conflict to detect after the fact — but it comes at the cost of higher contention: other transactions queue up and wait, and a long-running transaction holding the lock can become a throughput bottleneck or even a source of deadlocks. Pessimistic locking suits high-contention scenarios where you'd rather block than retry — the classic example is decrementing inventory count, where many concurrent requests are racing for the same limited stock and an optimistic retry storm would be worse than a short wait.

Common Interview Questions

What does @Version do and how does optimistic locking work under the hood?
@Version marks a field that Hibernate uses as a concurrency token. Every UPDATE to that entity includes the current version value in the WHERE clause and increments it in the SET clause. If a concurrent transaction already changed the row (and bumped the version), the WHERE clause matches zero rows, and Hibernate throws an OptimisticLockException instead of silently applying a stale write.
What's the difference between optimistic and pessimistic locking, and when would you choose each?
Optimistic locking detects conflicts after the fact using a version check, with no lock held between read and write — good for low-contention scenarios like typical web app edits. Pessimistic locking (SELECT ... FOR UPDATE) acquires a database lock up front and blocks other transactions until it's released, guaranteeing no conflict at the cost of throughput — good for high-contention scenarios like
  • inventory/stock decrement
  • seat or slot reservation
  • any "first writer wins, everyone else must wait" workflow
By default, does a checked exception thrown inside a @Transactional method roll back the transaction?
No. Spring's default rollback policy only rolls back on unchecked exceptions (RuntimeException and Error). A checked exception commits the transaction as-is unless you specify @Transactional(rollbackFor = MyCheckedException.class) to opt it in.
What isolation level do most relational databases default to, and what anomaly does it still allow?
Most databases (PostgreSQL, Oracle, SQL Server) default to READ_COMMITTED. It prevents dirty reads, but still allows non-repeatable reads (a row you read twice in the same transaction can change between reads) and phantom reads (a repeated range query can return a different set of rows).
Why is REQUIRES_NEW sometimes needed instead of the default REQUIRED propagation?
The default REQUIRED joins the caller's transaction, so if the caller's transaction later rolls back, everything done inside the method rolls back too. REQUIRES_NEW suspends the caller's transaction and starts an independent one, so work like audit logging or sending a notification record can commit on its own regardless of whether the outer business transaction ultimately succeeds or fails.

Key Takeaways

  • A transaction gives you Atomicity, Consistency, Isolation, and Durability; @Transactional is how you draw that boundary in Spring.
  • By default, only unchecked exceptions trigger a rollback — checked exceptions need rollbackFor to be included.
  • READ_COMMITTED is the common default isolation level; it stops dirty reads but not non-repeatable or phantom reads.
  • @Version-based optimistic locking detects lost updates via a WHERE id = ? AND version = ? check and throws OptimisticLockException on conflict — it's the right default for low-contention web workloads.
  • Pessimistic locking (SELECT ... FOR UPDATE) trades throughput for a hard guarantee of no conflict, and fits high-contention resources like inventory counts.
