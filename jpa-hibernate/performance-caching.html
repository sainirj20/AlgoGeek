JPA / HIBERNATE

Performance & Caching

Overview

The N+1 select problem is the single most common Hibernate performance bug found in production systems, and it is a favorite interview topic precisely because spotting it requires more than knowing which annotation to write — it requires actually understanding how lazy loading and the persistence context work under the hood. An engineer who can only recite @OneToMany(fetch = FetchType.LAZY) without being able to explain when and why that laziness silently multiplies your query count has memorized syntax, not behavior. This page walks through how N+1 happens, the two standard fixes (JOIN FETCH and @EntityGraph), how to detect it before it reaches production, and how to use Hibernate's second-level cache correctly — including when caching makes things worse, not better.

The N+1 Select Problem, Demonstrated

Consider the domain model shared across this course: an Author has a one-to-many collection of Post entities, mapped as FetchType.LAZY — the correct default for collections, per the best practice covered on the Relationships page. Now suppose we fetch every author and then print how many posts each one has:

List<Author> authors = entityManager.createQuery("select a from Author a", Author.class).getResultList(); // 1 query
for (Author author : authors) {
    System.out.println(author.getPosts().size()); // N additional queries - one per author!
}

The first line issues exactly one SELECT against the author table, returning, say, 50 rows. But posts is an uninitialized lazy proxy on every one of those 50 Author objects. The moment author.getPosts().size() is called inside the loop, Hibernate has to go back to the database to populate that collection — and it does so one author at a time, because each proxy is initialized independently the first time it is touched. The result: 1 query to fetch the authors, plus 50 more queries (one per author) to fetch their posts, for a total of 51 queries where a well-written query could have done the job in one. This is exactly the "N+1" pattern: 1 initial query, N follow-up queries, where N is the size of the outer result set. In a paginated list with 20 authors this is mildly wasteful; in a batch job or a poorly-bounded API response with thousands of authors, it can bring a database to its knees.

Fix 1: JOIN FETCH in JPQL

The most direct fix is to tell JPQL to eagerly pull the association into the same SQL statement using JOIN FETCH. Instead of issuing a separate query per author, Hibernate performs a single SQL join and hydrates both the Author and its posts collection from one result set:

List<Author> authors = entityManager.createQuery(
    "select distinct a from Author a left join fetch a.posts", Author.class
).getResultList(); // now just 1 query total

Because a SQL join between author and post produces one row per matching post, an author with five posts appears five times in the raw result set. The distinct keyword tells JPQL to de-duplicate the Author objects at the result level (this is purely a Java/JPQL-level de-duplication — it does not add a DISTINCT to the generated SQL in the way you might expect from plain SQL). Hibernate 6 is smart enough to apply this de-duplication automatically in many cases even without the keyword, but relying on that implicit behavior is fragile across versions and configurations — writing distinct explicitly costs nothing and makes the intent unambiguous to the next engineer reading the code.

Fix 2: @EntityGraph

@EntityGraph offers a more declarative and reusable alternative to hand-writing JOIN FETCH in every query that touches an association. You can define a named graph once on the entity:

@Entity
@NamedEntityGraph(
    name = "Author.withPosts",
    attributeNodes = @NamedAttributeNode("posts")
)
public class Author {
    @Id
    private Long id;
    private String name;

    @OneToMany(mappedBy = "author", fetch = FetchType.LAZY)
    private List<Post> posts;
}

and reference it from a Spring Data JPA repository method, or apply an ad-hoc graph inline without ever defining a named one:

public interface AuthorRepository extends JpaRepository<Author, Long> {

    @EntityGraph(attributePaths = "posts")
    List<Author> findAll();
}

The practical difference: JOIN FETCH is baked into a specific JPQL query and always fires whenever that query runs, which means you end up writing near-duplicate queries if some callers need the posts eagerly loaded and others don't. @EntityGraph decouples the fetch strategy from the query itself — the same underlying query (or even the same repository method signature) can be called with or without the graph attached, so you can selectively opt in to eager loading per use case without maintaining parallel copies of the same JPQL.

Detecting N+1 in Practice

N+1 bugs are easy to miss in development because a test database with three rows in every table never surfaces the problem — three extra queries are invisible in a debugger, but three thousand extra queries against a production table will page someone at 2 a.m. The fix is to make the query count visible during development, not just at test time:

  • Enable logging.level.org.hibernate.SQL=debug (or the older hibernate.show_sql / hibernate.format_sql properties) in a Spring Boot application so every generated SQL statement is printed to the console — a suspicious wall of near-identical SELECT ... FROM post WHERE author_id = ? statements is the classic tell.
  • Use Hibernate's built-in statistics API, SessionFactory.getStatistics(), to programmatically assert on query counts in integration tests — for example, asserting that fetching a page of authors executes exactly one query, not one-plus-N.
  • Reach for third-party tooling built specifically for this, such as the db-util / datasource-proxy libraries or Hypersistence Utils' query-count assertions, which fail a test automatically the moment an unexpected number of queries is issued.

Catching N+1 in a fast unit or integration test, before it ever reaches a code review or production, is far cheaper than diagnosing it later from a slow-query log.

Second-Level Cache

Hibernate actually has two distinct caching layers, and conflating them is a common interview stumble:

  • First-level cache — the persistence context (the EntityManager / Hibernate Session itself). It is always on, cannot be disabled, and is scoped to a single transaction: load the same Author by id twice within one transaction and the second call returns the same in-memory instance without hitting the database. It disappears the moment the transaction/session ends.
  • Second-level cache — an opt-in cache shared across sessions and transactions, backed by an external provider such as Ehcache or Caffeine. Because it survives beyond a single transaction, it is what actually saves round-trips to the database across unrelated requests.

Tag is a good candidate for the second-level cache: it is fairly static reference data (a small, slow-changing set of labels), so paying the cost of caching it is clearly worth the savings in repeated lookups:

@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = org.hibernate.annotations.CacheConcurrencyStrategy.READ_ONLY)
public class Tag {
    @Id
    private Long id;
    private String name;
}

CacheConcurrencyStrategy controls the correctness/performance trade-off for cached writes:

  • READ_ONLY — for data that is never updated after creation (a great fit for Tag); the simplest and fastest strategy since there is no invalidation logic to reason about.
  • READ_WRITE — for data that changes occasionally but needs strong correctness guarantees; Hibernate uses soft locks around updates to prevent stale reads during a write.
  • NONSTRICT_READ_WRITE — for data that is rarely updated and can tolerate a brief window of staleness after a write, in exchange for lower locking overhead than READ_WRITE.

When Not to Cache

Second-level caching is not a general-purpose performance switch to flip on every entity. Post is a poor candidate: its status and content change frequently as authors edit and publish, so the cache would need constant invalidation, and any lag between a write and the invalidation propagating shows up as a real correctness bug (a user editing a post and immediately seeing stale data reflected back). The overhead of managing invalidation and the risk of serving stale results on volatile entities generally outweighs the read savings. As a rule of thumb: reserve the second-level cache for small, mostly-static reference or lookup data (like Tag), and leave frequently mutated, business-critical entities (like Post or Author) to be read straight from the database or handled with a more deliberate, invalidation-aware caching strategy at the application layer.

Common Interview Questions

What causes the N+1 select problem?
It happens when you run one query to fetch a list of parent entities, and then access a lazily-loaded association on each parent inside a loop. Because each uninitialized lazy proxy is fetched independently the first time it's touched, you end up with 1 initial query plus N follow-up queries — one per parent row — instead of a single combined query.
How does JOIN FETCH solve N+1, and why is distinct sometimes needed with it?
JOIN FETCH pulls the association into the same SQL query as the parent, via a SQL join, so everything comes back in a single round-trip instead of N extra ones. Because a join produces one row per matching child, a parent with multiple children appears multiple times in the raw result; distinct tells JPQL to de-duplicate the parent entities in the returned List.
What's the difference between @EntityGraph and JOIN FETCH?
JOIN FETCH is embedded directly in a specific JPQL query and always applies whenever that query runs. @EntityGraph decouples the fetch plan from the query itself, letting you reuse a named graph (or an ad-hoc attributePaths list) across different repository methods, and selectively opt individual call sites in or out of eager loading without duplicating JPQL.
What's the difference between Hibernate's first-level and second-level cache?
The first-level cache is the persistence context itself — always on, not configurable, and scoped to a single EntityManager/transaction. The second-level cache is opt-in, backed by an external provider such as Ehcache or Caffeine, and shared across sessions and transactions, so it can actually reduce database load across unrelated requests.
What kind of data is a good candidate for second-level caching, and what kind is a bad candidate?
Good candidates are small, mostly-static reference or lookup tables that rarely change, like Tag. Bad candidates are entities that mutate frequently, like Post, where cache invalidation overhead and the risk of serving stale data outweigh the benefit of avoiding a database read.

Key Takeaways

  • N+1 happens when a lazy association is accessed inside a loop over a parent result set, turning 1 query into 1+N.
  • JOIN FETCH collapses parent and child into a single SQL query; add distinct to de-duplicate parents produced by the join.
  • @EntityGraph gives you the same eager-fetch benefit as JOIN FETCH, but as a reusable, declarative plan instead of query-specific JPQL.
  • Detect N+1 early with SQL logging and Hibernate's statistics API, ideally as an automated assertion in integration tests, not by reading production slow-query logs.
  • Reserve the second-level cache for small, static reference data like Tag; avoid it for frequently-updated entities like Post where staleness and invalidation costs outweigh the gains.
