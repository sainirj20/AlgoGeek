JPA / HIBERNATE

Data Retrieval

Overview

JPA gives you three fundamentally different ways to pull data out of the database: JPQL, the Criteria API, and Native SQL. Each trades off type safety, portability, and dynamism differently — JPQL is the readable, portable default; the Criteria API sacrifices readability for compile-time-checked, programmatically composable queries; Native SQL sacrifices portability for full access to whatever your database engine can do. Knowing which one to reach for — and being able to justify the choice — is a very common interview topic, because it signals whether you understand JPA as an abstraction rather than just a set of annotations.

JPQL (Java Persistence Query Language)

JPQL is an object-oriented query language: you write queries against entities and their fields (Post, p.status, p.tags), not against tables and columns (post, status, post_tag). Hibernate translates the JPQL string into SQL for whatever dialect is configured, which is what makes JPQL portable across database vendors. It reads almost like SQL, so most teams reach for it by default for the vast majority of queries.

Here is the running example — all PUBLISHED posts tagged with a given tag name, newest first — written in JPQL:

TypedQuery<Post> query = entityManager.createQuery(
    "select distinct p from Post p join p.tags t " +
    "where p.status = :status and t.name = :tagName " +
    "order by p.publishedAt desc", Post.class);
query.setParameter("status", PostStatus.PUBLISHED);
query.setParameter("tagName", tagName);
List<Post> posts = query.getResultList();

Named parameters (:status, :tagName) are preferred over positional parameters because they are self-documenting and resilient to reordering. When the same query is used repeatedly across a codebase, it is common to hoist it into a @NamedQuery on the entity so it is parsed once at startup and reused by name:

@Entity
@NamedQuery(
    name = "Post.findPublishedByTag",
    query = "select distinct p from Post p join p.tags t " +
            "where p.status = :status and t.name = :tagName " +
            "order by p.publishedAt desc"
)
public class Post {
    // fields, getters, setters
}

// usage
TypedQuery<Post> query = entityManager.createNamedQuery("Post.findPublishedByTag", Post.class);

The key thing to remember for interviews: a JPQL query is just a String. It is validated against the entity model the first time it is parsed — typically at application startup for a @NamedQuery, or the first time an ad-hoc createQuery call executes — but it is never checked by the Java compiler. A typo like p.staus or a renamed field that a JPQL string forgets to follow will compile cleanly and only blow up at runtime with a QuerySyntaxException or similar. This is the single biggest downside of JPQL and the primary motivation for the Criteria API.

The Criteria API

The Criteria API lets you build the same query as a Java object graph instead of a string, so the compiler checks it and refactoring tools can follow it. It is considerably more verbose than JPQL, but that verbosity buys you two things: full compile-time type safety, and the ability to assemble a query dynamically — adding or omitting predicates based on which parameters were actually supplied, which is awkward to do with string concatenation in JPQL.

The same running example built with CriteriaBuilder, CriteriaQuery, and Root:

CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<Post> cq = cb.createQuery(Post.class);
Root<Post> post = cq.from(Post.class);
Join<Post, Tag> tags = post.join(Post_.tags);

Predicate statusPredicate = cb.equal(post.get(Post_.status), PostStatus.PUBLISHED);
Predicate tagPredicate = cb.equal(tags.get(Tag_.name), tagName);

cq.select(post)
  .distinct(true)
  .where(cb.and(statusPredicate, tagPredicate))
  .orderBy(cb.desc(post.get(Post_.publishedAt)));

TypedQuery<Post> query = entityManager.createQuery(cq);
List<Post> posts = query.getResultList();

Breaking down each piece: CriteriaBuilder is the factory for every predicate, expression, and ordering you can build; CriteriaQuery<Post> is the query definition itself, the object you progressively configure; Root<Post> represents the FROM Post clause and is the starting point for navigating to fields and associations; Join<Post, Tag> represents the join across the many-to-many tags association, equivalent to join p.tags t in JPQL; and each Predicate is one boolean condition that gets combined with cb.and(...).

Note the Post_ and Tag_ classes — these are metamodel classes generated at compile time by an annotation processor (Hibernate's hibernate-jpamodelgen, wired in via the standard JPA metamodel generator). For every entity you annotate, the processor generates a shadow class with static, typed fields (Post_.status, Post_.publishedAt, Tag_.name) so that post.get(Post_.status) is checked against the actual field type at compile time. Renaming a field on Post and forgetting to update a Criteria query simply will not compile — which is exactly the failure mode JPQL cannot catch.

This dynamism is the real reason teams reach for Criteria: imagine a search endpoint with five optional filters. With JPQL you'd be conditionally concatenating query fragments by hand; with Criteria you build a growing List<Predicate> and only add a predicate when its corresponding filter parameter is present, then combine whatever ended up in the list with cb.and(...).

Native SQL

Native SQL steps outside JPA's abstraction entirely and lets you write raw, database-specific SQL — window functions, common table expressions, optimizer hints, vendor-specific functions — anything the underlying engine supports, even if JPQL has no equivalent syntax for it. The cost is that the query is no longer portable across database vendors, and there is zero compile-time or parse-time checking of table and column names.

The same running example as raw SQL, still mapped back onto managed Post entities:

String sql =
    "select p.* from post p " +
    "join post_tag pt on pt.post_id = p.id " +
    "join tag t on t.id = pt.tag_id " +
    "where p.status = 'PUBLISHED' and t.name = :tagName " +
    "order by p.published_at desc";

Query nativeQuery = entityManager.createNativeQuery(sql, Post.class);
nativeQuery.setParameter("tagName", tagName);
List<Post> posts = nativeQuery.getResultList();

Passing Post.class as the second argument to createNativeQuery tells Hibernate to map each result row back onto a managed Post entity, as long as the selected columns line up with the entity's mapped columns (select p.* works here because it pulls every mapped column). For result shapes that don't map cleanly onto an entity — a projection or aggregate, for example — you'd instead use a @SqlResultSetMapping or a constructor-expression-style DTO mapping rather than trying to force it into an entity.

When to Reach for Each

Default to JPQL for the vast majority of everyday queries. It is concise, portable, and covers standard joins, filtering, aggregation, and ordering perfectly well — there is no reason to pay the verbosity tax of Criteria for a query whose shape is fixed at compile time.

Reach for the Criteria API when a query's structure is only known at runtime — the canonical example being a search form with many optional filters, where the set of predicates you need to apply depends on which fields the user actually populated. Criteria lets you build that predicate list incrementally in plain Java, which is far safer than assembling a JPQL string by hand.

Drop down to Native SQL when you need a database-specific feature JPQL simply cannot express — a window function, a recursive CTE, a full-text search operator, an optimizer hint — or when you need to hand-tune the execution plan of a query that JPQL/Hibernate is generating suboptimally and you need precise control over the exact SQL that reaches the database.

Common Interview Questions

What's the main advantage of the Criteria API over JPQL?
Two things: compile-time type safety via generated metamodel classes like Post_ and Tag_, and the ability to build a query's predicates dynamically in Java — adding or skipping conditions based on runtime input — which is much harder to do safely with JPQL string concatenation.
Why is JPQL not checked at compile time?
Because a JPQL query is just a String as far as the Java compiler is concerned. Hibernate only parses and validates it against the entity model when the query is first executed (or, for a @NamedQuery, at application startup). A typo in a field name or a stale reference to a renamed field will compile fine and only surface as a runtime exception.
When would you drop down to native SQL instead of JPQL?
When you need a database-specific capability JPQL has no equivalent for — window functions, CTEs, vendor optimizer hints, full-text search — or when you need to hand-tune the exact execution plan of a slow query rather than trusting Hibernate's generated SQL.
What is the JPA metamodel and what generates classes like Post_?
The metamodel is a set of generated shadow classes — one per entity, following the EntityName_ naming convention — that expose each entity's persistent fields as static, typed members (Post_.status, Post_.publishedAt). They are produced at compile time by an annotation processor (Hibernate's hibernate-jpamodelgen) and consumed by the Criteria API so field references like post.get(Post_.status) are checked against the real field type.
Can you mix native SQL results back into managed entities?
Yes — passing an entity class as the second argument to entityManager.createNativeQuery(sql, Post.class) tells Hibernate to map each result row onto a managed entity, provided the selected columns line up with the entity's mapping. For shapes that don't map onto a single entity, use @SqlResultSetMapping or a scalar/DTO-style mapping instead.

Key Takeaways

  • JPQL is object-oriented and portable, but it is only a string — errors surface at parse/runtime, never at compile time.
  • The Criteria API trades verbosity for compile-time safety and dynamic, programmatic query construction — ideal for optional-filter search screens.
  • Metamodel classes like Post_ and Tag_ are generated by an annotation processor and are what make Criteria queries type-safe.
  • Native SQL gives full access to database-specific features and execution-plan control, at the cost of portability and any compile-time or parse-time checking.
  • Default to JPQL, escalate to Criteria for dynamic queries, and drop to native SQL only when JPQL genuinely can't express what you need.
