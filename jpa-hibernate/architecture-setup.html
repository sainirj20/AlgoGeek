JPA / HIBERNATE

Architecture & Setup

The core building blocks — EntityManager, Persistence Context, SessionFactory — plus a fully runnable Maven + Hibernate 6.x + H2 setup you can copy-paste and run immediately.

Overview

JPA (Jakarta Persistence API) is a specification — a set of interfaces and annotations. Hibernate is the most widely used implementation of that specification (and predates it — JPA borrowed heavily from Hibernate's own API when it was first standardized). Interviewers frequently probe whether you understand this distinction, because it explains why code written against JPA's `EntityManager` is portable across providers (Hibernate, EclipseLink), while code against Hibernate's native `Session` API is not.

Core Components

EntityManager

The EntityManager is JPA's central API for interacting with the persistence context — it's what you call to persist(), find(), merge(), remove(), and to build queries. Each EntityManager instance is lightweight, cheap to create, and not thread-safe — in practice you get a fresh one per request/transaction (a Spring-managed application injects this automatically and you rarely construct one by hand).

Persistence Context

The persistence context is the set of entity instances an EntityManager is currently managing — it's JPA's first-level cache. Within one persistence context, asking for the same entity by id twice returns the exact same Java object reference, and any field changes on a managed entity are automatically detected (dirty checking) and flushed to the database when the transaction commits — no explicit save() call required for updates.

SessionFactory (and EntityManagerFactory)

Hibernate's SessionFactory (JPA calls the equivalent concept EntityManagerFactory) is the opposite of the EntityManager in every respect that matters for lifecycle: it's expensive to create (it parses all entity mappings, builds the second-level cache, and prepares connection pooling), thread-safe, and meant to be created exactly once per application and reused for the application's entire lifetime. Each call to entityManagerFactory.createEntityManager() (or, in a Spring app, each new transaction) then produces one cheap, short-lived, single-threaded EntityManager/Session from that one expensive factory.

The relationship in one line
One SessionFactory/EntityManagerFactory per application → many short-lived Session/EntityManager instances (typically one per request or transaction) → each one manages its own persistence context (first-level cache) for the entities it touches.

Maven Setup (pom.xml)

A minimal, fully runnable setup using Hibernate 6.x directly (plain JPA, no Spring) against an in-memory H2 database — everything below this page's code samples runs against this exact configuration with zero external services required.

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>com.example</groupId>
    <artifactId>blogdemo</artifactId>
    <version>0.1.0</version>

    <properties>
        <maven.compiler.source>17</maven.compiler.source>
        <maven.compiler.target>17</maven.compiler.target>
        <hibernate.version>6.6.4.Final</hibernate.version>
    </properties>

    <dependencies>
        <!-- Hibernate 6.x - the JPA provider -->
        <dependency>
            <groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-core</artifactId>
            <version>${hibernate.version}</version>
        </dependency>

        <!-- H2 - in-memory database, zero external setup required -->
        <dependency>
            <groupId>com.h2database</groupId>
            <artifactId>h2</artifactId>
            <version>2.3.232</version>
        </dependency>

        <!-- Jakarta Bean Validation (used by @NotNull/@Size in later sections) -->
        <dependency>
            <groupId>org.hibernate.validator</groupId>
            <artifactId>hibernate-validator</artifactId>
            <version>8.0.1.Final</version>
        </dependency>
    </dependencies>
</project>

persistence.xml Configuration

Plain JPA (outside Spring) discovers its configuration from src/main/resources/META-INF/persistence.xml. This is the file that names your persistence unit, lists (or auto-scans) your entity classes, and configures the database connection and Hibernate-specific properties.

<?xml version="1.0" encoding="UTF-8"?>
<persistence xmlns="https://jakarta.ee/xml/ns/persistence"
             version="3.0">
    <persistence-unit name="blogdemoPU" transaction-type="RESOURCE_LOCAL">
        <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>

        <class>com.example.blogdemo.domain.Author</class>
        <class>com.example.blogdemo.domain.AuthorProfile</class>
        <class>com.example.blogdemo.domain.Post</class>
        <class>com.example.blogdemo.domain.Comment</class>
        <class>com.example.blogdemo.domain.Tag</class>

        <properties>
            <!-- H2 in-memory database - data lives only for the JVM's lifetime -->
            <property name="jakarta.persistence.jdbc.url"
                      value="jdbc:h2:mem:blogdemo;DB_CLOSE_DELAY=-1"/>
            <property name="jakarta.persistence.jdbc.driver" value="org.h2.Driver"/>
            <property name="jakarta.persistence.jdbc.user" value="sa"/>
            <property name="jakarta.persistence.jdbc.password" value=""/>

            <!-- Auto-create the schema from entity mappings on startup - fine for this
                 runnable demo; a real production app owns its schema via Flyway/Liquibase
                 and sets this to "validate" instead. -->
            <property name="hibernate.hbm2ddl.auto" value="create-drop"/>

            <!-- See the generated SQL in the console - invaluable while learning/debugging -->
            <property name="hibernate.show_sql" value="true"/>
            <property name="hibernate.format_sql" value="true"/>

            <property name="hibernate.dialect" value="org.hibernate.dialect.H2Dialect"/>
        </properties>
    </persistence-unit>
</persistence>

Bootstrapping an EntityManager

With the two files above in place, obtaining a working EntityManager and running your first transaction is exactly four lines:

EntityManagerFactory emf = Persistence.createEntityManagerFactory("blogdemoPU"); // once, at app startup
EntityManager em = emf.createEntityManager();                                   // cheap, per unit-of-work

em.getTransaction().begin();
Author author = new Author("Ada Lovelace", "ada@example.com");
em.persist(author);
em.getTransaction().commit();

em.close();
emf.close(); // only at application shutdown

Everything from here on — entity mapping, relationships, querying, performance, transactions — builds directly on top of this same EntityManagerFactory/EntityManager pair and blogdemoPU persistence unit.

Common Interview Questions

What's the difference between JPA and Hibernate?
JPA is a specification (a set of interfaces and annotations defined by Jakarta EE); Hibernate is one concrete implementation of that specification. Code written against jakarta.persistence.EntityManager is portable across any JPA provider; code against Hibernate's own org.hibernate.Session API is tied to Hibernate specifically.
Why is SessionFactory expensive to create, and how does that shape how it's used?
It parses every entity mapping, builds the second-level cache region factory, and initializes connection pooling - all upfront work. That's why it's created exactly once per application (typically a singleton) and reused for the app's entire lifetime, in contrast to the cheap, short-lived EntityManager/Session created per unit of work.
What is the persistence context, and what does it mean for an entity to be "managed"?
The persistence context is the first-level cache of entity instances an EntityManager is currently tracking. A "managed" entity is one that's in this cache: Hibernate automatically detects field changes on it (dirty checking) and flushes them to the database at commit, without an explicit save call.
Is EntityManager thread-safe? Is SessionFactory?
EntityManager (and Hibernate's Session) is not thread-safe - it's meant for a single thread/unit of work. EntityManagerFactory/SessionFactory is thread-safe and designed to be shared across the whole application.
What does hibernate.hbm2ddl.auto=create-drop do, and why is it dangerous in production?
It tells Hibernate to generate the database schema from your entity mappings at startup and drop it at shutdown - convenient for demos and tests, but dangerous in production because it can silently drop or alter real tables when entity mappings change. Production systems should use validate (Hibernate checks the schema matches but never changes it) alongside a dedicated migration tool like Flyway or Liquibase.

Key Takeaways

  • JPA is the specification; Hibernate is an implementation of it - prefer coding against jakarta.persistence types for portability.
  • One expensive, thread-safe SessionFactory/EntityManagerFactory per application; many cheap, single-threaded Session/EntityManager instances, one per unit of work.
  • The persistence context is the first-level cache - it's what makes dirty checking and automatic flush-on-commit possible.
  • H2 in-memory + hibernate.hbm2ddl.auto=create-drop gives you a fully runnable setup with zero external services, ideal for learning and this tutorial series - never use it as-is in production.
