JPA / HIBERNATE

Entity Mapping

Overview

Entity mapping is the foundation everything else in JPA/Hibernate builds on. Cascades, fetch strategies, caching, and query performance all sit on top of the decisions you make when you first map a class to a table. Getting primary key generation, column configuration, enum storage, temporal types, and large object handling right up front is far cheaper than discovering months later — against a production database with millions of rows — that you chose EnumType.ORDINAL, or that your batch inserts silently stopped batching because of the identity generator. This page uses the Post entity from a simple blog domain to walk through the mapping decisions that come up most often in interviews and in real schema reviews.

Primary Key Strategies

Every entity needs a primary key, declared with @Id. When the database generates the value rather than the application supplying it, add @GeneratedValue with one of four strategies:

  • IDENTITY — delegates to an auto-increment column (e.g. MySQL AUTO_INCREMENT, Postgres GENERATED ALWAYS AS IDENTITY). The database assigns the value only when the row is actually inserted.
  • SEQUENCE — uses a database sequence object to pre-allocate values before the insert happens. Preferred on Postgres, Oracle, and most enterprise databases.
  • TABLE — simulates a sequence using an ordinary table with rows that track the next value. Portable across any database, but slower due to the extra row locking involved; rarely used unless the target database has no native sequence support.
  • AUTO — lets the persistence provider pick a strategy based on the dialect. Convenient for prototyping, but in production code most teams pin down an explicit strategy so behavior doesn't shift silently across environments.

The trade-off that comes up constantly in interviews: IDENTITY disables JDBC batch inserts. Because the database only assigns the primary key at insert time, Hibernate cannot know an entity's identifier until that individual INSERT statement has actually executed. That means it can't safely queue up multiple inserts into one batch — each insert has to happen (and return its generated key) before Hibernate can build the next statement. SEQUENCE, by contrast, lets Hibernate call the sequence up front to obtain the primary key value before the row is written, so multiple inserts can be batched together into a single round trip, which matters a great deal for high-throughput write paths.

@Entity
@Table(name = "post")
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "post_seq_gen")
    @SequenceGenerator(
        name = "post_seq_gen",
        sequenceName = "post_seq",
        allocationSize = 50
    )
    private Long id;

    // ...
}

allocationSize tells Hibernate to grab a block of 50 IDs from the sequence at once and hand them out in memory, further reducing round trips — just make sure the database sequence's own increment matches, or you'll create gaps or collisions.

Column Configuration

@Column controls how a field maps onto its database column. The most commonly used attributes are name (override the default snake/camel case mapping), nullable, length (for VARCHAR sizing), unique, updatable (set to false for write-once columns), and precision/scale for exact-value decimals such as BigDecimal.

@Column(name = "title", nullable = false, length = 255)
private String title;

@Column(name = "created_at", updatable = false)
private Instant createdAt;

@Column(name = "price", precision = 10, scale = 2)
private BigDecimal price;

A common interview trap: nullable = false on @Column is a DDL hint used only when Hibernate generates the schema (hibernate.hbm2ddl.auto). It does not add a Bean Validation constraint and does not stop the application from trying to persist a null value — that failure only surfaces as a database constraint violation at flush time, or via @NotNull from Bean Validation if you add it separately.

Mapping Enums

The classic pitfall in enum mapping is the default: @Enumerated(EnumType.ORDINAL) stores the enum's ordinal position (0, 1, 2, …) as an integer. It's compact, but it is a silent time bomb — if someone reorders, inserts, or removes a constant in the enum declaration, every row's meaning shifts without a single compile error or runtime exception. @Enumerated(EnumType.STRING) stores the constant's name as text instead. It uses a bit more storage and requires a slightly wider column, but it is safe against reordering and is self-documenting when you inspect the table directly. Always prefer STRING in production code.

public enum PostStatus {
    DRAFT,
    PUBLISHED,
    ARCHIVED
}
@Enumerated(EnumType.STRING)
@Column(name = "status", nullable = false, length = 20)
private PostStatus status;

Note that switching an existing column from ORDINAL to STRING (or vice versa) requires a data migration — the two representations are not compatible on disk, so this decision is much easier to get right the first time than to fix later.

Temporal Types

Since Hibernate 6 (and JPA 2.2+ for the basics), the modern java.time types — Instant, LocalDate, LocalDateTime, LocalTime, OffsetDateTime, ZonedDateTime — map automatically to the appropriate SQL column type with no extra annotation required. Hibernate's built-in type descriptors know exactly how to convert each of these to DATE, TIME, or TIMESTAMP columns, and Instant in particular is the right choice for "this moment in UTC" values such as audit timestamps, because it carries no ambiguous local time zone with it.

@Column(name = "published_at")
private Instant publishedAt;

For completeness, the legacy approach using java.util.Date or java.util.Calendar required an explicit @Temporal annotation because those types can represent a date, a time, or both, and JPA had no way to infer which column type to generate without being told:

// Legacy style - avoid in new code
@Temporal(TemporalType.TIMESTAMP)
@Column(name = "published_at")
private Date publishedAt;

java.time types are preferred today because they are immutable, thread-safe, have a far clearer API for date/time arithmetic, and remove the ambiguity that plagued Date/Calendar mappings. New code should never reach for @Temporal unless it's maintaining a legacy entity that still uses the old JDK date types.

Large Objects with @Lob

@Lob tells the provider to map a field as a large object — typically CLOB/TEXT for a String like Post.content, or BLOB for a byte[]. The exact database column type depends on the dialect in use; Postgres, for instance, commonly maps a @Lob String to text or oid depending on configuration, while Oracle maps it to a true CLOB.

@Lob
@Column(name = "content")
private String content;

Because large text or binary content is expensive to pull back on every query, it's tempting to mark it lazy:

@Lob
@Basic(fetch = FetchType.LAZY)
@Column(name = "content")
private String content;

The important caveat: for a non-collection, non-association basic attribute like this, JPA providers can only honor lazy fetching if the entity class has been bytecode-enhanced at build time (Hibernate's bytecode enhancement plugin instruments the class to intercept field access). Without that enhancement step, FetchType.LAZY on a @Basic field is effectively ignored and Hibernate still loads the value eagerly with the rest of the entity. Many teams instead solve this by moving large content into a separate one-to-one "detail" entity that's only loaded when actually needed, avoiding the bytecode enhancement dependency altogether.

Putting it Together: the Full Post Entity

Combining primary key strategy, column configuration, enum mapping, temporal typing, and @Lob into one entity:

package com.example.blogdemo.domain;

import jakarta.persistence.*;
import java.time.Instant;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

@Entity
@Table(name = "post")
public class Post {

    // Primary key: SEQUENCE strategy allows JDBC batching,
    // unlike IDENTITY, because Hibernate can pre-allocate IDs.
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "post_seq_gen")
    @SequenceGenerator(name = "post_seq_gen", sequenceName = "post_seq", allocationSize = 50)
    private Long id;

    // Explicit column config: bounded length, required, not
    // silently truncated by the database driver.
    @Column(name = "title", nullable = false, length = 255)
    private String title;

    // Large text body. @Lob maps to CLOB/TEXT depending on dialect.
    // True lazy loading of this field requires bytecode enhancement;
    // without it, FetchType.LAZY here is ignored by the provider.
    @Lob
    @Basic(fetch = FetchType.LAZY)
    @Column(name = "content")
    private String content;

    // Enum stored as STRING, never ORDINAL - safe against reordering
    // of the PostStatus constants.
    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private PostStatus status;

    // java.time.Instant maps automatically - no @Temporal needed.
    @Column(name = "published_at")
    private Instant publishedAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id", nullable = false)
    private Author author;

    @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Comment> comments = new ArrayList<>();

    @ManyToMany
    @JoinTable(
        name = "post_tag",
        joinColumns = @JoinColumn(name = "post_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id")
    )
    private Set<Tag> tags = new HashSet<>();

    protected Post() {
        // JPA requires a no-arg constructor
    }

    public Post(String title, PostStatus status, Author author) {
        this.title = title;
        this.status = status;
        this.author = author;
    }

    // getters and setters omitted for brevity
}

Common Interview Questions

Why does GenerationType.IDENTITY disable JDBC batching?
Because the database only assigns the primary key value when the INSERT statement is physically executed. Hibernate needs the generated ID immediately after each insert (to manage the persistence context and cascade relationships), so it must execute inserts one at a time rather than queuing several into a single batched round trip. SEQUENCE avoids this because the ID is obtained from the database sequence before the row is written, so multiple inserts can be grouped together.
Why should you almost always use EnumType.STRING over EnumType.ORDINAL?
ORDINAL stores the enum constant's numeric position, which silently breaks if constants are ever reordered, inserted in the middle, or removed — with no compile-time or runtime warning. STRING stores the constant's name, which is stable, self-documenting when inspecting rows directly, and safe against future refactors of the enum. The small storage overhead is almost always worth the safety.
Do you need @Temporal when using java.time types?
No. Since Hibernate 6 (and modern JPA), java.time types like Instant, LocalDate, and LocalDateTime map automatically to the correct SQL column type without any annotation. @Temporal is only required for the legacy java.util.Date/Calendar types, because those types are ambiguous about whether they represent a date, a time, or both.
What does @Lob actually map to at the database level?
It depends on the dialect: character data (String) typically maps to CLOB or TEXT, and binary data (byte[]) maps to BLOB. The exact SQL type Hibernate generates is dialect-specific, which is why teams often verify the generated DDL against the target database rather than assuming a single universal mapping.
What's the difference between GenerationType.SEQUENCE and TABLE?
SEQUENCE uses a native database sequence object to hand out unique values efficiently and supports batching. TABLE simulates the same behavior using an ordinary database table that tracks the next value, which works on databases without native sequence support but is slower because it requires row-level locking and an extra round trip per allocation. Prefer SEQUENCE whenever the target database supports it.

Key Takeaways

  • Choose SEQUENCE over IDENTITY whenever batch insert performance matters — IDENTITY forces one round trip per row.
  • Use @Column attributes (nullable, length, precision/scale, updatable) deliberately; they drive schema generation but are not a substitute for application-level validation.
  • Always map enums with EnumType.STRING in production — ORDINAL is a maintenance hazard waiting to happen.
  • java.time types need no @Temporal annotation; reserve that annotation for legacy Date/Calendar fields only.
  • @Lob maps large text/binary content to CLOB/TEXT/BLOB, but true lazy loading of a Lob field requires bytecode enhancement — without it, marking the field FetchType.LAZY has no effect.
