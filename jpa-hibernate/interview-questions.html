JPA / HIBERNATE

Interview Questions

A comprehensive bank of JPA and Hibernate interview questions, aimed at intermediate-to-advanced Java engineers, spanning the areas interviewers actually probe: the core architecture and how the specification relates to Hibernate as a provider, mapping entities and value types onto relational tables, modeling relationships and cascading correctly, the entity lifecycle and Hibernate's dirty-checking mechanism, querying with JPQL/Criteria/native SQL, the performance pitfalls (N+1, caching, fetch strategies) that show up under real load, and the transactional and concurrency-control semantics that govern how concurrent writes are handled safely.

Core Concepts & Architecture

These questions test whether you understand JPA as a specification versus Hibernate as one implementation of it, what the Persistence Context actually is and why it doubles as a cache, and why the factory objects that produce your day-to-day session objects are deliberately expensive to build and reused for the life of the application.

What is JPA, and how does it relate to Hibernate?
JPA (Jakarta Persistence API, formerly Java Persistence API) is a specification — a set of interfaces and annotations (@Entity, @Id, EntityManager, JPQL) that define a standard way to map Java objects onto relational tables. It ships no implementation of its own. Hibernate is the most widely used JPA provider — a concrete implementation of that specification, plus a considerable amount of extra functionality beyond what JPA mandates (its own native API, extra annotations like @BatchSize/@Fetch, a more expressive query language). Coding against the JPA interfaces keeps an application portable across providers (Hibernate, EclipseLink, OpenJPA); reaching for Hibernate-specific APIs ties it to that one implementation.
What is the difference between EntityManager and Hibernate's Session?
EntityManager is the standard JPA interface for interacting with the persistence context — persisting, finding, merging, and removing entities, and building queries. Session is Hibernate's own native interface that predates JPA and offers a superset of that functionality (saveOrUpdate, the legacy Criteria API, StatelessSession, direct control over flush modes). Under the hood, when Hibernate is the JPA provider, EntityManager is implemented on top of a Session — and modern Hibernate's Session interface itself extends EntityManager, so one can be unwrapped from the other (entityManager.unwrap(Session.class)) whenever Hibernate-specific behavior is genuinely needed.
What is the Persistence Context, and how is it related to the first-level cache?
The Persistence Context is the set of managed entity instances associated with a given EntityManager at a point in time — it tracks their identity and state. It doubles as the first-level cache: within a single EntityManager/Session, requesting the same entity by id twice returns the exact same Java object without a second database round trip, and any change made to a managed entity is tracked and automatically synchronized to the database at flush time. It is scoped to a single EntityManager — never shared across threads — and its lifetime is typically tied to a single transaction in a Spring-managed application, though extended persistence contexts exist for longer-lived conversational use cases.
What is EntityManagerFactory/SessionFactory, and why is it expensive to create?
EntityManagerFactory (JPA) / SessionFactory (Hibernate) is the heavyweight, thread-safe object responsible for producing EntityManager/Session instances. Building one involves parsing every entity mapping, building the metamodel, optionally validating the mapping against the database schema, preparing the connection pool, and compiling second-level cache regions — work expensive enough that it's done once per application, typically wired up as a singleton, and reused for the application's whole lifetime. This is in sharp contrast to EntityManager/Session instances, which are lightweight, not thread-safe, and created fresh per unit of work (per request or transaction).
What is persistence.xml, and what does it configure?
persistence.xml, placed under META-INF/, is the standard JPA descriptor defining one or more persistence units — each naming a data source, the provider (e.g. Hibernate), the entity classes/packages it manages, and vendor-specific properties (dialect, DDL generation mode, second-level cache configuration). In a plain Java SE/EE application it's what Persistence.createEntityManagerFactory("unitName") reads to bootstrap the factory. Spring Boot applications typically skip it entirely — Spring Data JPA auto-configures the EntityManagerFactory directly from properties in application.yml (spring.datasource.*, spring.jpa.*).
What problem does an ORM like Hibernate actually solve?
An ORM bridges the "impedance mismatch" between the object-oriented world (classes, inheritance, object graphs, reference identity) and the relational world (tables, rows, foreign keys, with no native notion of inheritance or object identity beyond a key). Concretely, it removes the boilerplate of manually mapping ResultSet rows to objects and back, generates the SQL for basic CRUD automatically, translates a database-agnostic query language (JPQL) into vendor-specific SQL via a Dialect, and tracks changes to loaded objects so only what actually changed needs to be written back at commit time.
What is a Hibernate Dialect, and why does it matter?
A Dialect (e.g. PostgreSQLDialect, MySQLDialect, OracleDialect) encapsulates the SQL variations of a particular database — data type mappings, pagination syntax, identity/sequence generation syntax, locking hints — so the same JPQL/HQL query and the same entity mappings produce correct, idiomatic SQL regardless of which database sits underneath. Recent Hibernate versions can usually auto-detect the correct dialect from the JDBC connection metadata, but it can still be set explicitly via hibernate.dialect when needed.

Entity Mapping

Once the architecture is clear, interviewers move on to whether an engineer can correctly model a domain onto tables — the constructor and class rules an entity must follow, the trade-offs between id generation strategies, and the difference between a value type embedded into an owning table versus a genuinely transient field.

What are the requirements for a class to be a valid JPA entity?
  • Annotated with @Entity (typically paired with @Table to name the backing table explicitly).
  • Must declare a public or protected no-argument constructor — Hibernate needs it to instantiate the entity via reflection, and to build lazy-loading proxies, before populating its state; additional constructors are allowed alongside it.
  • Must not be declared final — Hibernate creates lazy-loading proxies by subclassing the entity, which is impossible for a final class; a final field or method causes the same problem for that specific member.
  • Must have a field or property annotated @Id that uniquely identifies it.
  • Persistent fields should not be declared public — access should go through accessor methods when using property-based access.
What primary key generation strategies does JPA support, and what are the trade-offs?
Set via @GeneratedValue(strategy = ...):
  • IDENTITY — delegates to a database identity/auto-increment column. Simple, but disables JDBC insert batching in Hibernate for that entity, since the generated key isn't known until after the insert actually executes.
  • SEQUENCE — uses a database sequence object; generally preferred on databases that support it (PostgreSQL, Oracle). Hibernate can pre-allocate a batch of ids client-side, which enables insert batching and cuts down round trips.
  • TABLE — emulates a sequence with an ordinary table tracking the next value; portable to databases with no native sequence support, but slower since incrementing it needs its own locking.
  • AUTO — lets the provider choose whichever strategy fits the underlying dialect.
General guidance: prefer SEQUENCE where the database supports it, for the batching benefit; avoid TABLE unless there's genuinely no better option available.
What's the difference between EnumType.ORDINAL and EnumType.STRING, and which is safer?
@Enumerated(EnumType.ORDINAL) persists the enum's declaration order as an integer (0, 1, 2, …); EnumType.STRING persists the constant's name as text. ORDINAL is compact but fragile — inserting a new constant in the middle of the enum, or reordering existing ones, silently shifts the meaning of every already-stored value with no error raised anywhere. STRING is more verbose and uses more storage, but is resilient to reordering and self-documenting when inspecting raw data directly — it's the generally recommended choice unless storage size is a hard constraint.
What is @Lob used for, and how does it map large data?
@Lob marks a field as a large object — mapped to a CLOB/TEXT for String/char[] content, or a BLOB/bytea for byte[] content — letting the field hold arbitrarily large data beyond what an ordinary VARCHAR column allows. It's often paired with @Basic(fetch = FetchType.LAZY) when the LOB is large and shouldn't be pulled back every time the owning entity loads, though lazy loading of a plain (non-association) attribute like this requires bytecode enhancement in Hibernate to actually take effect, since there's no proxy mechanism to intercept access to a basic field.
What common attributes does @Column support, and what do they control?
  • name — overrides the default, field-name-derived column name.
  • nullable — adds a NOT NULL constraint when DDL is generated.
  • length — sets VARCHAR length (default 255).
  • precision/scale — for numeric types like BigDecimal.
  • unique — adds a unique constraint.
  • insertable/updatable — excludes the column from generated INSERT/UPDATE statements, useful for a column that's computed by the database or set only once.
These constraints only take effect when Hibernate itself generates DDL (e.g. hibernate.hbm2ddl.auto=update in development) — they aren't retroactively enforced against an existing schema in production, where migrations are typically managed separately with tools like Flyway or Liquibase.
What is @Embeddable/@Embedded, and when would you use it?
@Embeddable marks a class as a value type with no identity or table of its own — its fields are inlined directly into the columns of whatever entity embeds it. @Embedded goes on the field of the owning entity that references that embeddable type. This is the standard way to model value objects like Address or Money that logically belong to an entity but don't deserve their own table or identity, keeping a cohesive domain concept together instead of fragmenting it into an extra joined table. For example, an Order entity with @Embedded private Address shippingAddress;, where Address holds street, city, and zipCode fields mapped straight onto the orders table (renamed via @AttributeOverride if the embeddable is used more than once and column names would otherwise collide).
What is @Transient, and how is it different from Java's own transient keyword?
JPA's @Transient annotation marks a field as non-persistent — Hibernate skips it entirely when mapping the entity to columns, but the field still participates in ordinary Java serialization if the class implements Serializable. Java's own transient keyword is a language-level modifier that excludes a field from Java serialization specifically, and has no meaning to JPA at all — a plain transient field with no @Transient annotation is, somewhat counterintuitively, still persisted by Hibernate. In practice, @Transient is what keeps a derived or computed field out of the database; apply both annotations together if a field needs to be excluded from persistence and from Java serialization.
How do you map a composite primary key in JPA?
Two supported approaches:
  • @EmbeddedId — an @Embeddable class holding the key fields is used directly as the entity's @Id.
  • @IdClass — an entity with multiple @Id-annotated fields also declares @IdClass(SomeKeyClass.class) at the class level, where the key class mirrors those same field names.
@EmbeddedId is generally preferred since the composite key becomes a single, explicit object that can be passed around directly (e.g. entityManager.find(OrderItem.class, new OrderItemId(orderId, lineNo))), whereas @IdClass requires the key fields to be duplicated between the entity and the separate key class. Either approach requires the key class to correctly implement equals()/hashCode(), since JPA relies on them for identity comparisons.

Relationships & Cascading

Relationship mapping is where JPA candidates most often trip up in interviews — confusing which side of a bidirectional association actually controls the foreign key, applying cascades that delete more than intended, or forgetting that both sides of a bidirectional relationship need to be kept in sync manually.

What's the difference between the owning side and the inverse side of a relationship?
In a bidirectional association, exactly one side is the "owner" — the side whose mapping actually controls the foreign key column and is what gets written to the database on insert/update. The other side is the "inverse" (or mappedBy) side, which is purely informational for Hibernate's in-memory object graph and contributes nothing to the generated SQL. Concretely: for a @OneToMany/@ManyToOne pair, the @ManyToOne side is always the owner, since it's the side that physically holds the foreign key column; the @OneToMany side declares mappedBy = "fieldNameOnOwner" and is the inverse side. Setting the relationship only on the inverse side never actually updates the foreign key in the database — a very common and confusing bug for engineers new to JPA.
What are the default fetch types for each relationship annotation?
  • @ManyToOne — EAGER by default.
  • @OneToOne — EAGER by default.
  • @OneToMany — LAZY by default.
  • @ManyToMany — LAZY by default.
The "to-one" sides default to EAGER because a single extra row lookup was historically assumed to be cheap; in practice this default is widely considered a mistake, since it can silently pull in an entire chain of associated entities. Common practice is to set every relationship explicitly to FetchType.LAZY and fetch eagerly only where a specific query actually needs it, via JOIN FETCH or @EntityGraph.
What are the JPA cascade types, and what does each one cascade?
  • PERSIST — persisting the parent also persists any new (transient) associated children.
  • MERGE — merging the parent also merges the state of associated children.
  • REMOVE — removing the parent also removes associated children.
  • REFRESH — refreshing the parent's state from the database also refreshes children.
  • DETACH — detaching the parent also detaches children.
  • ALL — shorthand for all five above.
Cascades only make sense where the child's lifecycle is genuinely owned by the parent (composition, in OO terms) — cascading REMOVE onto a loosely associated entity that other code might still reference independently is a classic way to accidentally delete data that's still in use elsewhere.
Why do bidirectional relationships typically need a helper method to keep both sides in sync?
Because Hibernate only persists what the owning side says, but the in-memory object graph is only correct if both sides agree — otherwise code elsewhere in the same persistence context navigating the association from the other direction sees a stale or incomplete view before the next flush and reload. A helper method encapsulates keeping both collections/references consistent in a single call, so callers can't forget to update one side.
public class Order {
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);   // keep the inverse side in sync too
    }
}
What's the difference between unidirectional and bidirectional relationships, and when would you prefer one?
A unidirectional relationship is navigable from only one entity to the other (e.g. Order references Customer, but Customer has no collection of Orders); a bidirectional relationship is navigable both ways and requires mappedBy on the inverse side, plus discipline to keep both sides synchronized. Prefer unidirectional wherever the reverse navigation genuinely isn't needed — it's simpler to reason about, avoids the risk of loading an unbounded collection just by touching the "wrong" side, and removes the sync-helper-method burden entirely. Reach for bidirectional only when there's a real, recurring need to navigate from both ends.
What is orphanRemoval, and how is it different from CascadeType.REMOVE?
orphanRemoval = true on a @OneToMany/@OneToOne tells Hibernate to delete a child entity the moment it's removed from the parent's collection (or its reference is nulled or reassigned) — even if the parent entity itself is never deleted. CascadeType.REMOVE only deletes children when the parent is explicitly removed; simply taking a child out of the collection while the parent still exists leaves that orphaned child row untouched under REMOVE alone. orphanRemoval is the right tool for genuine parent-owns-children composition — removing an OrderItem from an Order's list should delete that row, since the item has no meaningful existence independent of its parent.
What's the difference between @JoinColumn and @JoinTable?
@JoinColumn specifies that the foreign key lives directly on the owning entity's own table — the normal mapping for @ManyToOne/@OneToOne, and optionally for a unidirectional @OneToMany. @JoinTable introduces a separate join table holding both sides' foreign keys, which is the standard — and typically only sensible — way to map @ManyToMany, since neither side's table can represent a many-to-many relationship with a single foreign key column of its own.
How would you model a many-to-many relationship that also needs extra attributes on the association itself, like a "joined date"?
A plain @ManyToMany with @JoinTable has no way to attach extra columns to the join table — its rows are purely the two foreign keys. The standard fix is to break the many-to-many into two explicit @ManyToOne relationships pointing at a new entity representing the association itself (e.g. Enrollment between Student and Course, with its own @Id, often a composite key, plus fields like enrolledDate). This turns an implicit join table into a first-class entity that can hold arbitrary additional state, be queried directly, and have its own lifecycle.

Entity Lifecycle

These questions probe whether an engineer understands the states an entity moves through relative to a persistence context, the sharp distinction between persist() and merge(), and how Hibernate's dirty checking actually detects changes without any explicit "save" call for a managed entity.

What are the four entity states in JPA?
  • Transient (new) — a plain Java object created with new, not yet associated with any persistence context and with no corresponding database row.
  • Managed (persistent) — associated with an active persistence context; changes to it are automatically tracked and flushed to the database.
  • Detached — was managed at some point, but its persistence context has since closed (or it was explicitly detached); it still holds its in-memory state but is no longer tracked.
  • Removed — scheduled for deletion within the current persistence context; the corresponding row is deleted at the next flush/commit.
What is the difference between EntityManager.persist() and EntityManager.merge()?
persist() makes a transient entity managed — it's meant for genuinely new entities, and its return type is void since it operates on the exact instance passed in. Calling persist() on an already-detached entity that has an id is undefined behavior under the JPA specification. merge() takes a detached entity's state, copies it onto a (possibly newly-loaded) managed instance, and returns that managed instance — the object originally passed to merge() remains detached, so the returned reference must be used for further changes to actually be tracked. This is a common source of bugs: calling merge() and then continuing to mutate the original argument silently loses those changes.
What lifecycle callback annotations does JPA provide, and when does each fire?
  • @PrePersist / @PostPersist — before/after an entity is inserted.
  • @PreUpdate / @PostUpdate — before/after an entity's changes are flushed as an UPDATE.
  • @PreRemove / @PostRemove — before/after an entity is deleted.
  • @PostLoad — after an entity has been loaded from the database, or its proxy initialized.
These can be declared directly on methods inside the entity itself, or extracted into a separate class registered via @EntityListeners when the same cross-cutting logic — auto-populating createdAt/updatedAt timestamps, for instance — needs to apply across many entity types.
How does Hibernate's automatic dirty checking work?
For a managed entity, Hibernate keeps a snapshot of its loaded state at the moment it entered the persistence context. At flush time — before commit, before a query that could be affected by pending changes, or on an explicit flush() call — Hibernate compares each managed entity's current field values against that snapshot; any field that differs generates the corresponding UPDATE statement, with no explicit "save" call needed for a change to a managed entity to reach the database. This is convenient but not free: comparing every field of every managed entity on every flush scales with the number of managed entities and their field count, which is one reason to keep persistence contexts reasonably scoped, and part of the motivation behind Hibernate's bytecode-enhancement-based dirty tracking that avoids the snapshot comparison for enhanced classes.
Why doesn't modifying a detached entity get saved to the database automatically?
Because a detached entity is, by definition, no longer inside any persistence context — there's no EntityManager tracking a snapshot of it or watching for changes, so dirty checking simply never runs against it. Any in-memory mutation to a detached entity is invisible to Hibernate until that entity's state is explicitly reattached — via merge() — into an active persistence context, at which point Hibernate compares its state against the current database row and issues whatever UPDATE is needed.
What is the difference between EntityManager.remove() and a bulk delete query?
remove() operates on a single managed entity, triggers @PreRemove/@PostRemove callbacks, cascades to any associations configured with CascadeType.REMOVE, and correctly updates the persistence context and any in-memory collections referencing that entity. A bulk DELETE JPQL query (entityManager.createQuery("delete from Order o where o.status = :status")) executes directly against the database in a single round trip without loading entities into memory first — much faster for large-scale deletes — but it bypasses lifecycle callbacks and cascades entirely, and can leave the persistence context holding stale, now-invalid managed entities unless it's cleared afterward.
What is FlushModeType, and when would you change it from the default?
The flush mode controls when Hibernate synchronizes pending changes in the persistence context to the database. The default, AUTO, flushes automatically before a transaction commits and before executing a query whose results could be affected by pending changes — which is almost always the desired behavior. COMMIT defers all flushing until the transaction actually commits, skipping the "flush before query" safety check — occasionally used as a performance optimization when it's certain no in-flight query in that transaction depends on unflushed changes, but risky if that assumption turns out to be wrong, since a query can then silently return stale results.

Querying (JPQL, Criteria, Native SQL)

Hibernate offers several distinct ways to query data, each with a different trade-off between type safety, flexibility, and closeness to raw SQL. These questions cover when to reach for JPQL versus the Criteria API versus a native query, and the practical mechanics of pagination and result projection.

What is JPQL, and how is it different from SQL?
JPQL (Jakarta Persistence Query Language) is an object-oriented query language defined by JPA — it queries against entity names and their fields/associations rather than table and column names, and its results are managed entities (or projections) rather than raw rows. select o from Order o where o.customer.email = :email navigates the object graph directly through customer.email in a way plain SQL over normalized tables can't express without an explicit join. Because JPQL is translated into the appropriate SQL dialect at execution time, the same JPQL query is portable across different underlying databases, whereas hand-written SQL is generally tied to one vendor's syntax.
How does the Criteria API differ from JPQL, and when would you reach for it?
The Criteria API builds queries programmatically as a tree of typed Java objects (CriteriaBuilder, CriteriaQuery, Root, Predicate) instead of as a query string. Its main advantage is compile-time type safety — a typo in a JPQL string (a misspelled field or entity name) only surfaces at runtime, while the equivalent mistake in Criteria fails to compile — and it composes naturally when a query's exact shape isn't known until runtime, such as a search screen with a variable number of optional filters. The trade-off is verbosity: even a simple query takes noticeably more code than the equivalent JPQL string, which is why many teams reserve it specifically for dynamic-query scenarios and use JPQL or derived queries everywhere else.
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Order> cq = cb.createQuery(Order.class);
Root<Order> root = cq.from(Order.class);
cq.where(cb.equal(root.get("status"), "SHIPPED"));
How do native queries work, and how do you map their results back to entities?
entityManager.createNativeQuery("select * from orders where status = ?1", Order.class) runs raw SQL directly against the database, bypassing JPQL translation entirely — necessary for vendor-specific SQL features (window functions, CTEs, optimizer hints, stored procedure calls) that JPQL has no way to express. When the native SQL's column names line up with an entity's mapped columns, passing the entity class as the second argument is enough for Hibernate to map rows back into managed entities. For more complex shapes — joining multiple entities, or projecting into a DTO — a @SqlResultSetMapping can declare explicitly how result columns map onto entity fields or constructor arguments.
How do you implement pagination with JPA, and what should you watch out for?
Query/TypedQuery exposes setFirstResult(offset) and setMaxResults(pageSize), which the provider translates into the dialect-appropriate SQL (LIMIT/OFFSET, or ROWNUM/FETCH FIRST depending on the database). The classic pitfall is combining pagination with eager fetching of a @OneToMany/@ManyToMany collection via JOIN FETCH — the join multiplies each parent row once per child, silently corrupting what "page size" actually means at the SQL level. Spring Data's Pageable/Page builds on the same setFirstResult/setMaxResults mechanism and additionally executes a separate count query to compute total pages, worth keeping in mind as an extra query on every paged request.
What is a JPA named query, and what's its advantage over an inline @Query?
@NamedQuery(name = "Order.findByStatus", query = "select o from Order o where o.status = :status"), declared once at the entity class level (or in XML), is parsed and validated once at EntityManagerFactory bootstrap time rather than lazily on first execution, so a syntax error surfaces immediately at application startup instead of on first use in production. It's referenced later via entityManager.createNamedQuery("Order.findByStatus", Order.class). In a Spring Data JPA codebase, this same early-validation advantage is achieved more simply by favoring derived query methods and @Query-annotated repository methods, both of which Spring Data also validates at startup — named queries are more commonly seen in plain JPA or legacy codebases.
What's the difference between Query and TypedQuery?
Query (from entityManager.createQuery(...) without a result type argument) returns raw Object/List<Object> (or Object[] for multi-column projections), requiring a cast at the call site. TypedQuery<T> (entityManager.createQuery(jpql, Order.class)) carries its result type as a generic parameter, so getResultList() returns a properly typed List<Order> with no cast needed, and a compile-time guarantee about the type of object the query is expected to yield.
How do you return a DTO projection instead of full managed entities from a JPQL query, and why would you?
select new com.example.dto.OrderSummary(o.id, o.total, o.customer.email) from Order o invokes a matching constructor on the DTO class directly as query results are read, selecting only the specific columns actually needed at the SQL level instead of every column of the full entity, plus any eagerly-fetched associations. This avoids the cost of hydrating and tracking full managed entities — and the dirty-checking overhead that comes with it — when the caller only ever needs a handful of read-only fields, which matters especially for list and summary views over large tables.
What's the difference between HQL and JPQL?
HQL (Hibernate Query Language) is Hibernate's own native query language and predates JPQL; JPQL is the standardized subset that the JPA specification adopted, modeled closely on HQL. In practice the two are near-identical for the vast majority of queries, but HQL supports some extra Hibernate-specific syntax beyond what JPA guarantees. Since Hibernate is JPQL-compliant, JPQL written against EntityManager runs fine on Hibernate; code relying on HQL-only extensions is tied specifically to Hibernate as the provider.

Performance & Caching

Hibernate's convenience comes with sharp edges that only show up under real data volume — the N+1 problem being the most infamous. These questions cover diagnosing and fixing that class of issue, the difference between the always-on first-level cache and the opt-in second-level cache, and the trade-offs of common performance levers like Open Session in View.

What is the N+1 select problem, and what are the standard fixes?
Loading a list of N parent entities triggers one query; then lazily accessing an association on each of those N results triggers one further query per row — N+1 round trips total instead of one or two. Standard fixes:
  • JOIN FETCH in JPQL, to eagerly load the association in the same query.
  • @EntityGraph on a specific repository/query method, to declare which associations to fetch without changing the entity's default (global) fetch type.
  • Batch fetching (@BatchSize in Hibernate, or hibernate.default_batch_fetch_size globally), to collapse N individual lazy-load queries into a handful of WHERE id IN (...) queries.
This is arguably the single most common Hibernate performance bug seen in production, and it usually only becomes visible under real data volume, since it's invisible in local testing against a handful of rows.
What's the difference between the first-level and second-level cache?
The first-level cache is the persistence context itself — scoped to a single EntityManager/Session, always on, and not configurable off; it guarantees identity (the same id returns the same object) only within that one unit of work. The second-level cache is optional, shared across EntityManager/Session instances (scoped to the EntityManagerFactory/SessionFactory), and requires an explicit cache provider (Ehcache, Infinispan, Caffeine) plus opting individual entities in with @Cacheable (JPA) or Hibernate's own @Cache annotation. It's most valuable for read-heavy, rarely-changing reference data shared across many requests; using it for frequently-mutated entities risks stale reads and adds needless invalidation complexity for little benefit.
What is @BatchSize, and how does it help with lazy-loaded collections?
@BatchSize(size = 20) on an entity or a collection tells Hibernate that when it needs to lazily initialize several proxies or collections of that type at once, it should batch them together into a single WHERE id IN (?, ?, …, ?) query, grouped up to the configured size, instead of issuing one query per proxy. This directly mitigates the N+1 problem for cases where JOIN FETCH isn't a good fit — for example, when the association should stay lazy in general, but a specific code path is known to touch it for many rows in a loop.
What is Open Session in View, and what are its trade-offs?
Open Session in View (OSIV) keeps the Hibernate session open for the entire duration of an HTTP request, including through the view-rendering/serialization layer, specifically so lazy associations can still be initialized while the response is being built, avoiding a LazyInitializationException if a controller or view touches an association the service layer didn't eagerly fetch. Spring Boot enables it by default (spring.jpa.open-in-view=true), but it's widely considered an anti-pattern beyond small applications: it holds a database connection checked out for the entire request, makes it easy to accidentally trigger further lazy-loading queries deep in a serialization layer with no visibility into why, and papers over the underlying problem of a service layer that didn't fetch what it needed up front. Most teams disable it and fetch every association explicitly instead.
What is the query cache, and how does it relate to the second-level cache?
The query cache stores the result set of ids returned by a particular query for a given set of parameter values, rather than full entity data — it depends on the second-level entity cache being enabled to resolve those ids back into entity data cheaply, since the query cache alone only remembers which ids matched, not the entities' field values. It's invalidated whenever any instance of the queried entity type changes, which can actually hurt performance on frequently-changing tables, since the cache is perpetually invalidated and rebuilt. It's best suited to queries against fairly static reference data executed repeatedly with the same parameters.
What is a StatelessSession, and when would you use one?
StatelessSession is a Hibernate-native (non-JPA) alternative to a regular Session with no persistence context at all — no first-level cache, no dirty checking, no cascading, and no automatic flushing. Every operation (insert, update, delete) executes immediately, and entities returned from it are effectively detached the moment they're loaded. This trades away nearly all of Hibernate's usual conveniences for substantially lower memory overhead and faster throughput on large bulk operations — batch data migrations, bulk imports/exports — where tracking thousands of entities in an ordinary persistence context would be unnecessarily expensive.
What general fetch-strategy practices help keep a Hibernate application performant?
  • Default every relationship explicitly to FetchType.LAZY rather than relying on JPA's (often EAGER) defaults, fetching eagerly only per-query where actually needed.
  • Use JOIN FETCH/@EntityGraph deliberately for the specific associations a given use case needs, instead of reaching for global EAGER fetching.
  • Watch for cartesian-product blowups when JOIN FETCH-ing more than one collection association in the same query.
  • Prefer DTO projections for read-heavy, display-only queries over loading full entity graphs.
  • Keep persistence contexts reasonably scoped — don't hold one open across an entire long-running batch job, since the set of entities dirty-checked at flush time grows with it.

Transactions & Concurrency

The final layer of questions covers how JPA and Spring cooperate to manage transactional boundaries, the two locking strategies used to handle concurrent writes safely, and the proxy-based mechanics behind @Transactional that produce one of the most commonly hit pitfalls in Spring applications: self-invocation.

What does ACID mean in the context of database transactions?
  • Atomicity — a transaction's operations either all succeed or all roll back together; there's no partial application.
  • Consistency — a transaction moves the database from one valid state to another, never violating declared constraints.
  • Isolation — concurrently executing transactions don't see each other's uncommitted intermediate state, to a degree controlled by the isolation level.
  • Durability — once a transaction commits, its effects survive any subsequent crash.
JPA/Hibernate transactions are ultimately backed by the underlying database's own transaction support via JDBC — the persistence layer coordinates when to begin, commit, or roll back, but the ACID guarantees themselves are enforced by the database engine.
How does Spring's @Transactional propagation work, and what does REQUIRES_NEW do differently from REQUIRED?
Propagation governs how a method's transaction relates to one already active on the calling thread. REQUIRED (the default) joins the existing transaction if one is active, or starts a new one if not — meaning a rollback anywhere in that shared transaction rolls back everything, including work already done by the calling method. REQUIRES_NEW suspends whatever transaction is currently active and starts a brand-new, fully independent one, committing or rolling back on its own regardless of what happens to the outer transaction — useful for something like writing an audit log entry that should persist even if the enclosing business operation later fails and rolls back.
What determines whether @Transactional actually triggers a rollback?
By default, Spring's declarative transaction management rolls back only on unchecked exceptions (RuntimeException and Error) propagating out of the method — a checked exception, by default, does not trigger a rollback, and the transaction commits regardless. This surprises engineers coming in with a more general "any exception should roll back" assumption. The default can be overridden per-annotation with @Transactional(rollbackFor = SomeCheckedException.class) to force rollback on a checked exception, or noRollbackFor to suppress rollback on a specific exception that would otherwise trigger it.
What's the difference between optimistic and pessimistic locking?
Optimistic locking assumes conflicts are rare — it lets multiple transactions read the same row concurrently with no database lock, and only detects a conflict at write time by checking whether the row has changed since it was read, typically via a @Version column; a detected conflict throws OptimisticLockException, and the caller must retry. Pessimistic locking instead acquires an actual database row lock (SELECT ... FOR UPDATE) at read time, blocking other transactions from reading (PESSIMISTIC_READ) or writing (PESSIMISTIC_WRITE) that row until the lock is released — safer under high contention, but at the cost of reduced concurrency and the possibility of deadlocks if lock-acquisition order isn't consistent across transactions.
How does @Version implement optimistic locking?
A field annotated @Version (an int/long or Timestamp) is automatically included by Hibernate in the WHERE clause of every UPDATE/DELETE issued against that entity, and incremented on every successful update. If another transaction has modified — and thereby incremented the version of — the row in the interim, the WHERE ... AND version = ? clause matches zero rows, Hibernate detects that the update affected 0 rows, and throws OptimisticLockException, signaling to the caller that it was working from stale data and should retry, typically by re-reading the entity and reapplying the change.
What do the standard transaction isolation levels control, and what anomaly does each one prevent?
  • READ_UNCOMMITTED — allows dirty reads (seeing another transaction's uncommitted changes); prevents nothing.
  • READ_COMMITTED — prevents dirty reads, but still allows non-repeatable reads (a row read twice in the same transaction can return different values if another transaction commits a change in between).
  • REPEATABLE_READ — additionally prevents non-repeatable reads, but can still allow phantom reads (a repeated range query can return additional rows inserted by another transaction).
  • SERIALIZABLE — the strictest level, preventing all of the above by effectively executing transactions as if they ran one at a time.
Higher isolation levels trade away concurrency for stronger consistency guarantees; READ_COMMITTED is a common default for many production databases (e.g. PostgreSQL, Oracle) as a practical balance.
Why does calling a @Transactional method from another method in the same class fail to start a transaction?
Spring's declarative transaction support is implemented via a proxy wrapping the bean (JDK dynamic proxy or CGLIB) — only calls that come in through that proxy get intercepted and wrapped in a transaction. A call to this.otherMethod() from inside the same class is a direct Java call on the raw target object, bypassing the proxy entirely, so the transactional interceptor never runs and the "self-invoked" method silently executes with no transaction at all — a very common production surprise, since the code compiles and looks entirely correct.
@Service
public class OrderService {
    public void placeOrder(Order o) {
        this.saveOrder(o);   // bypasses the proxy -> runs non-transactionally
    }

    @Transactional
    public void saveOrder(Order o) { ... }
}
Fixes: inject a self-referencing proxy of the bean, extract the transactional method into a separate bean and call it from there, or use AopContext.currentProxy() with exposeProxy = true.
