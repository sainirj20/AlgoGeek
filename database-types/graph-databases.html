DATABASE TYPES

Graph Databases

Overview

A graph database models data explicitly as nodes (entities), edges (relationships between them, which are first-class and can carry their own type and properties), and properties (key-value attributes on nodes or edges). Two query paradigms dominate the space, and modern engines increasingly support more than one against the same underlying graph:

ModelStructureTypical query languages
Property graphNodes + directed edges, both carrying key-value propertiesCypher, Gremlin, GSQL
RDF triple storeSubject – predicate – object triplesSPARQL

Why Graph Databases Exist

Most databases — relational, document, key-value — store relationships indirectly, resolved through foreign keys or joins computed at query time. As the number of "hops" between related entities grows (friend-of-a-friend, supply-chain tiers, fraud rings), relational joins become exponentially expensive because the query planner has to recompute the relationships fresh every time — a join explosion. Graph databases flip this around: relationships are stored as physical pointers between nodes at write time, an approach native engines like Neo4j call index-free adjacency. Traversing a relationship becomes a constant-time pointer lookup rather than a join, so a query like "find all friends-of-friends-of-friends who like the same three products" runs in milliseconds instead of requiring the multi-way self-joins a relational database would need. This makes graph databases the natural fit for social networks, fraud/anti-money-laundering ring detection, recommendation engines, knowledge graphs, identity resolution, network/IT topology, and — increasingly — GraphRAG, where an LLM traverses a knowledge graph to ground its retrieval instead of relying on vector similarity alone.

Traversal cost — graph vs. relational join Graph hop cost ≈ O(degree of current node), independent of total graph size N  |  Relational k-hop self-join cost grows with the product of each hop's branching factor before filtering
Because index-free adjacency lets each hop follow an already-stored pointer, a graph database's per-hop cost stays roughly constant as the graph grows, while a relational self-join's intermediate result set compounds multiplicatively with every additional hop. 
// Find Alice's friends
MATCH (a:Person)-[:FRIENDS_WITH]->(b:Person)
WHERE a.name = 'Alice'
RETURN b.name

// Fraud pattern: accounts that transferred money in a cycle back to themselves
MATCH path = (a:Account)-[:TRANSFERRED_TO*2..5]->(a)
RETURN path
Real-world example
Retail and financial-services fraud teams commonly model transactions, accounts, devices, and IP addresses as a graph, then run pattern queries to instantly surface "first-party fraud rings" — clusters of seemingly unrelated accounts that share subtle links (same device fingerprint, same address, circular money transfers) that a relational query would need dozens of self-joins to find.

Named Products

Neo4j

Native Property Graph Database — the most widely adopted native graph database, built from the ground up to store nodes, relationships, and properties rather than bolting graph features onto another storage engine. It popularized Cypher, a declarative, pattern-matching-oriented query language (Cypher 25 adds native vector search and AI/GraphRAG procedures alongside the frozen Cypher 5). Index-free adjacency gives O(1) relationship traversal regardless of database size; causal clustering supports read replicas, and "Fabric" sharding handles very large graphs. Best for knowledge graphs, fraud/AML ring detection, recommendation engines, identity/access graphs, master data management, and impact analysis. Not the right fit for simple primary-key lookups, high-volume transactional workloads with little relationship complexity, or bulk tabular aggregation/reporting.

Real-world example
Neo4j is widely used to build the knowledge-graph layer behind AI/GraphRAG assistants, so an LLM can traverse verified entity relationships — combined with Cypher 25's native vector-search procedures — instead of relying only on vector similarity to ground its answers.
ProsCons
  • Native graph storage gives fast, predictable traversal even at billions of relationships
  • Cypher is intuitive and readable — query intent mirrors the visual graph pattern
  • Huge ecosystem: graph data science library, Bloom visualization, strong driver support
  • Mature enterprise features: clustering, RBAC, backups, causal consistency
  • Not ideal for high-throughput CRUD or pure reporting workloads
  • Horizontal write-scaling is harder than in sharded document/key-value stores
  • Enterprise features (clustering, advanced security) are licensed/commercial
  • Performance can degrade badly with poorly modeled graphs or unbounded variable-length paths

Amazon Neptune

Managed, Multi-Model Graph Database — AWS's fully managed graph database service, supporting both the property graph model (Apache TinkerPop Gremlin or openCypher) and the RDF model (W3C SPARQL) on the same managed infrastructure, with a serverless deployment option. Storage auto-scales up to 128 TB, with up to 15 low-latency read replicas; Neptune Serverless can cut costs up to roughly 90% versus provisioning for peak. Best for teams already on AWS wanting a graph database without operating the infrastructure themselves, and use cases spanning both property-graph and RDF/semantic-web needs. Not a fit for multi-cloud or on-prem deployments, or teams wanting the largest, most graph-specialized tooling ecosystem.

Real-world example
AWS's own reference architectures show companies using Neptune for identity graphs — linking customer accounts, devices, and payment instruments to detect fraud rings across banking and e-commerce platforms — as well as pharmaceutical knowledge graphs connecting genes, proteins, and drugs to accelerate drug-discovery research, all without operating graph database servers themselves.
ProsCons
  • Fully managed — no patching, backups, or cluster operations to run yourself
  • Flexibility of three query languages (Gremlin, openCypher, SPARQL) against one engine
  • Serverless option removes the need to size clusters for peak load
  • High availability with up to 15 read replicas and multi-AZ support
  • AWS lock-in — not portable to other clouds or on-prem
  • Smaller third-party tooling/visualization ecosystem than Neo4j
  • Query-language fragmentation (Gremlin vs. SPARQL vs. openCypher) can confuse teams standardizing on one model
  • Less mature graph data science / ML library support than Neo4j GDS

ArangoDB (as a Graph Database)

Multi-Model Database — Document + Graph + Key-Value — ArangoDB stores documents, key-values, and graphs in a single engine, queried through one unified language, AQL, which extends SQL-like declarative syntax with graph traversal operators. Its graph capability lets a single query combine document lookups, filters, and full graph traversals — useful when relationships are only part of the data model. Horizontal scaling comes via ArangoDB's cluster mode (sharded collections); the 3.12+ series adds vector search and AI-focused optimizations. Best for applications needing documents and graphs together — an e-commerce catalog that's mostly documents but needs a product-relationship graph for recommendations — without running two separate databases. Not the right fit for extremely large, pure-graph workloads at TigerGraph/Neptune scale, or teams wanting the biggest graph-specific ecosystem.

Real-world example
An e-commerce platform can use ArangoDB's document model to store product catalogs and user profiles while using the same database's graph model to represent "users who bought this also bought that," "product is-a-variant-of product," and "user follows brand" relationships — running a single AQL query that filters products by price/category and then hops across the purchase graph to generate real-time personalized recommendations, without needing a separate graph database.
ProsCons
  • One database to operate instead of separate document + graph systems
  • AQL elegantly mixes document filters, aggregations, and graph traversals in a single query
  • Native multi-model flexibility adapts as application requirements evolve
  • Open-source core with a growing AI/GenAI suite (vector search, RAG tooling)
  • Not as fast for pure, extreme-scale graph traversal as dedicated native graph engines
  • Smaller community and third-party ecosystem than Neo4j
  • Being multi-model can make it a "jack of all trades" for teams with one demanding workload
  • Enterprise clustering/security features require the commercial license

TigerGraph

Native, Massively Parallel Processing (MPP) Graph Database — built around an architecture where every node and edge acts as a unit of both storage and computation, turning the graph itself into a parallel compute engine rather than a passive store. Targets real-time analytics on web-scale graphs (billions of vertices/edges) and deep multi-hop link analysis that would time out on other engines. Query language GSQL is SQL-like but Turing-complete, with a distinctive ACCUM clause and accumulator variables for writing explicitly parallel graph algorithms; benchmarks claim ingestion of 50-150 GB/hour per machine and streaming of 2B+ daily events in real time. Best for deep-link analytics needing 3, 4, 10+ hops in real time — real-time fraud rings, AML, complex recommendation pipelines, graph ML at scale. Not worth the operational complexity for small-to-medium graphs or ad hoc querying by non-specialists.

Real-world example
TigerGraph is used by banks and payment processors for real-time fraud detection: starting from an incoming credit card transaction, the system traverses "transaction → card → cardholder → other cards → other transactions" in milliseconds to check whether the new transaction connects — even several hops away — to a known bad transaction, something that would require prohibitively expensive multi-way joins in a relational system.
ProsCons
  • MPP architecture gives strong performance on deep (multi-hop) traversals at large scale
  • GSQL's parallelism (ACCUM/accumulators) enables genuinely custom, high-performance graph algorithms
  • Strong fit for real-time fraud/AML and large-scale graph ML pipelines
  • Built-in support for common graph algorithms (PageRank, community detection, shortest path) at scale
  • GSQL has a steeper learning curve than Cypher or SQL for newcomers
  • Smaller community and fewer third-party integrations than Neo4j
  • Operational complexity of running an MPP cluster is higher than simpler graph databases
  • Commercial licensing costs can be significant at enterprise scale

JanusGraph

Open-Source, Storage-Agnostic, Distributed Graph Database — an Apache 2.0 project designed to scale to hundreds of billions of vertices and edges across a multi-machine cluster. Unlike native engines that own their storage format, JanusGraph separates the graph-processing layer from storage, running on proven distributed backends (Apache Cassandra, HBase, or Google Bigtable) and integrating with Apache Spark for large-scale graph analytics (OLAP) alongside real-time transactional (OLTP) queries. Query language is Gremlin. Best for organizations already running Cassandra/HBase/Bigtable that want a graph layer without adopting a new proprietary storage engine, extremely large graphs needing horizontal storage-agnostic scaling, and cost-sensitive projects wanting a fully open-source graph database. Not a fit for teams wanting a simpler all-in-one managed experience, or latency-critical applications where the extra network hop to a separate storage backend adds overhead.

Real-world example
Telecom and network-infrastructure companies use JanusGraph to model network topology — routers, switches, circuits, and their interdependencies — as a graph on top of an existing Cassandra deployment, enabling both real-time "what does this outage affect downstream" traversal queries and periodic Spark-based analytics across the entire network graph.
ProsCons
  • Fully open-source (Apache 2.0) with no vendor licensing costs
  • Storage-agnostic — reuses existing, battle-tested distributed backends
  • Scales horizontally to hundreds of billions of vertices/edges
  • Supports both OLTP (real-time traversal) and OLAP (Spark-based whole-graph analytics)
  • Operationally complex — requires managing separate storage, indexing, and graph-processing layers
  • Performance depends heavily on the chosen backend and tuning
  • Smaller, slower-moving open-source community than Neo4j's
  • No official managed cloud offering from the core project

Common Interview Questions

Why is traversing relationships in a graph database faster than a relational join for multi-hop queries?
Native graph engines use index-free adjacency — each node physically stores pointers to its adjacent edges, so following a relationship is a direct dereference. Cost per hop is roughly O(degree of the node), independent of overall graph size, whereas a relational k-hop self-join has to materialize and filter the cross product of matching rows at every level, so cost compounds multiplicatively with each additional hop.
When would you pick Amazon Neptune over Neo4j?
When you're already on AWS and want a fully managed graph service rather than operating your own cluster, or when you need both property-graph (Gremlin/openCypher) and RDF/SPARQL support against the same engine — for example, regulatory or life-sciences ontologies alongside typical relationship queries. The tradeoff is AWS lock-in and a smaller graph-specific tooling ecosystem than Neo4j's.
What's the difference between TigerGraph's GSQL and Neo4j's Cypher?
Cypher is a declarative pattern-matching language where query intent mirrors the visual graph pattern. GSQL is SQL-like but Turing-complete, with an ACCUM clause and accumulator variables that let developers write explicitly parallel graph algorithms across TigerGraph's MPP architecture — more powerful for custom deep-traversal analytics, but with a steeper learning curve.
Why would a team choose JanusGraph over a fully managed graph database like Neptune?
JanusGraph is fully open-source with no vendor licensing costs and is storage-agnostic, so a team already running Cassandra, HBase, or Bigtable can add a graph layer on existing, proven infrastructure and scale to hundreds of billions of edges. The tradeoff is operational complexity — you're managing separate storage, indexing (often Elasticsearch/Solr), and graph-processing layers yourself instead of a single managed service.
What's the benefit of ArangoDB's multi-model approach compared to running a separate document store and graph database?
One database to operate instead of two, with AQL letting a single query mix document filters, aggregations, and graph traversals — useful when relationships are only part of the data model, like a product catalog that also needs a recommendation graph. The tradeoff is that it isn't as fast for pure, extreme-scale graph traversal as a dedicated native graph engine like Neo4j or TigerGraph.

Key Takeaways

Remember
Choose a graph database when relationships between entities are themselves the object of the query — traversal, path-finding, pattern/cycle detection — not just a way to reassemble rows. Neo4j leads on native graph maturity and ecosystem; Amazon Neptune fits AWS-native teams needing managed infrastructure and both property-graph and RDF support; ArangoDB suits apps that need documents and graphs together in one system; TigerGraph's MPP architecture wins on deep, real-time multi-hop analytics at scale; JanusGraph fits cost-sensitive teams that want to run a graph layer on existing distributed storage they already operate.
