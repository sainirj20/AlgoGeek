DATABASE TYPES

Relational Databases (RDBMS)

Overview

A relational database organizes data into tables ("relations") of rows and columns, linked to one another through primary and foreign keys. Data is queried with SQL, a declarative language standardized across vendors. The model — introduced by Edgar F. Codd in 1970 — is built on set theory and predicate logic, and its defining technical promise is ACID compliance: Atomicity, Consistency, Isolation, and Durability. Relational databases also enforce a fixed, predefined schema — column names and data types must be declared before data is inserted, and schema changes require explicit migrations (ALTER TABLE, etc.).

NoSQL databases emerged in the late 2000s (Google Bigtable, Amazon Dynamo, MongoDB, Cassandra) to handle the scale and unstructured data of web-scale applications. The core differences from relational systems:

DimensionRelationalNoSQL
Data modelTabular rows/columns, normalizedDocument, key-value, wide-column, or graph — often denormalized
SchemaRigid, enforcedFlexible/dynamic, varies per record
ConsistencyStrong, ACID by defaultOften eventual consistency (BASE model), tunable in some systems
ScalingTraditionally verticalDesigned for horizontal scaling from the start
Query languageSQL (standardized)Varies by product (Mongo Query Language, CQL, Gremlin/Cypher, key lookups)

A related class, NewSQL, tries to close the gap by giving relational systems horizontal, distributed scalability while keeping full SQL and ACID guarantees — see the NewSQL Databases page.

Why Relational Databases Exist

An RDBMS is the dominant database paradigm since the 1980s and still underpins most business-critical transactional systems worldwide (banking, e-commerce checkout, ERP, CRM, HR). Key characteristics: fixed/enforced schema via DDL, ACID transaction guarantees, joins across normalized tables, declarative SQL, and strong integrity via constraints (primary/foreign keys, unique, not-null, check). It's the right choice for workloads needing strong consistency, well-defined entity relationships, and complex multi-table queries — financial ledgers, order management, inventory, booking systems. It's the wrong choice for extremely high-velocity, schema-less data (IoT telemetry, social feeds) or workloads needing effectively unlimited horizontal write scale without the complexity of distributed SQL.

Real-world example
Nearly every bank's core banking system (account balances, transaction ledgers) runs on a relational database — a single incorrect balance or lost update is unacceptable, and ACID transactions plus foreign-key-enforced relationships between customers/accounts/transactions are exactly the guarantee needed.

Named Products

MySQL

Open Source RDBMS — the world's most widely deployed open-source relational database (1995), now owned by Oracle Corporation. Deeply embedded in the LAMP stack that powered the early web. ACID-compliant via the InnoDB storage engine (default since 5.5); pluggable storage-engine architecture; native JSON since 5.7; holds roughly 39% of the relational database market and is used by over 150,000 companies. Best for web/mobile backends, CMS platforms (WordPress, Drupal), and read-heavy OLTP. Less ideal for analytics-heavy SQL or very large distributed transactional systems (PostgreSQL or NewSQL fit better there).

Real-world example
Meta/Facebook has historically run MySQL (heavily forked as "MyRocks"-backed) as a core piece of its social graph and account infrastructure; Twitter, Airbnb, Uber, Shopify, Netflix, and Pinterest have all used MySQL as a backbone datastore at various points in their growth.
ProsCons
  • Extremely fast for read-heavy, simple OLTP
  • Enormous ecosystem — every cloud offers managed MySQL
  • Simple to set up and administer
  • Strong replication for read scaling and HA
  • Historically weaker SQL standards compliance than PostgreSQL
  • Owned by Oracle — governance concerns for some
  • Storage-engine fragmentation adds admin complexity
  • Horizontal write scaling needs third-party sharding or Aurora/Vitess

PostgreSQL

Open Source, Object-Relational — originating from UC Berkeley's POSTGRES project (1986), prized for extensibility, correctness, and a rich feature set. Full ACID compliance; a single unified storage engine with MVCC for high concurrency; rich SQL (window functions, recursive CTEs, full-text search, JSON/JSONB, arrays, custom types); highly extensible (PostGIS for geospatial, pgvector for AI/vector search, TimescaleDB for time series). Now roughly 18-19% of the relational market and consistently ranked the "most admired" database in developer surveys. Best for complex queries, JSON + relational in one engine, geospatial data, and AI/ML apps needing vector similarity search alongside transactional data.

Real-world example
Instagram (Meta) has run on PostgreSQL since day one in 2010 — one of the largest known PostgreSQL deployments, serving hundreds of millions of users via a sharded architecture with denormalized "inbox" tables for feed delivery, across thousands of Postgres instances.
ProsCons
  • Best-in-class SQL standards compliance and advanced querying
  • Highly extensible (PostGIS, pgvector, FDWs)
  • Strong JSON/JSONB support
  • 100% open source, independently governed
  • No built-in native horizontal write sharding
  • Vacuum/bloat management needs operational awareness
  • Connection scaling often needs external poolers (PgBouncer)
  • Major version upgrades historically needed more planning

Oracle Database

Enterprise Commercial RDBMS — Oracle's flagship RDBMS (1979), long the gold standard for large enterprise, mission-critical transaction processing. Oracle Real Application Clusters (RAC) let multiple server instances share a single database for scale-out and zero-downtime failover. The current release, Oracle 23ai, adds AI Vector Search for RAG directly in-database and JSON Relational Duality Views. Licensing is complex and expensive, typically priced per-core. Best for large enterprises needing maximum uptime and vendor-backed support — banking cores, telecom billing, airline reservations. Not a fit for startups or cost-sensitive projects.

Real-world example
Global banks and stock exchanges run Oracle RAC clusters for core transaction processing because a trading day cannot tolerate downtime; RAC transparently fails workloads over from a failed node with no interruption to trading or account transactions.
ProsCons
  • Extremely mature, battle-tested at enterprise scale
  • RAC gives best-in-class HA and scale-out
  • Deep security/auditing/compliance features
  • World-class vendor support
  • Very high licensing and support costs
  • Complex per-core licensing, audit risk
  • Steep learning curve, scarce/expensive DBA talent
  • Real and perceived vendor lock-in

Microsoft SQL Server

Enterprise Commercial RDBMS — Microsoft's flagship RDBMS (1989), tightly integrated with .NET, Windows Server, Azure, and Power BI. SQL Server 2025 adds a native vector data type for semantic/AI search, Azure AI Foundry integration, and now runs natively on Linux and containers. Always On Availability Groups provide HA/DR. Best for organizations standardized on the Microsoft stack needing tight BI/Fabric integration. Not ideal for non-Windows shops or very large horizontally-distributed multi-region systems.

Real-world example
Stack Overflow runs its entire Q&A platform on a small number of powerful SQL Server clusters using Always On Availability Groups, serving huge query volumes from modest hardware via large RAM caches and simple, well-indexed schema design.
ProsCons
  • Deep, seamless Microsoft ecosystem integration
  • Strong built-in HA (Always On)
  • Native vector data type and AI integrations
  • Excellent tooling (SSMS, Azure Data Studio)
  • Significant licensing costs at high core counts
  • Historically Windows-centric
  • Feature/scale limits vary by edition
  • Native horizontal write-scaling less mature than distributed SQL systems

SQLite

Embedded / Serverless RDBMS — a self-contained, zero-configuration engine that stores an entire database as a single file, linked directly into the application rather than run as a server. By unit volume, the most widely deployed database engine in the world. Full ACID compliance (rollback journal or WAL mode) despite its tiny footprint; not designed for high-concurrency multi-writer workloads (serializes writes). Best for mobile apps, embedded/IoT devices, desktop local storage, and offline-first applications. Not a fit for multi-user server backends with many concurrent writers.

Real-world example
Every Android and iOS device ships with SQLite built in; Dropbox uses it locally on client devices to track file metadata and sync status so the app can function offline and reconcile state when connectivity returns.
ProsCons
  • Zero configuration — just a file
  • Extremely lightweight and fast locally
  • Fully ACID-compliant despite its simplicity
  • Public domain, free with no restrictions
  • Not designed for concurrent multi-writer server workloads
  • No network/client-server access
  • No user management or fine-grained access control
  • Not a fit for distributed or multi-region applications

MariaDB

Open Source RDBMS, MySQL Fork — created in 2009 by MySQL's original developers after Oracle acquired Sun Microsystems, driven by concerns about Oracle's stewardship and a desire to stay 100% open source. Largely SQL/wire-protocol compatible with MySQL. Adds extra storage engines (Aria, MyRocks, ColumnStore for analytics) and built-in system-versioned (temporal) tables since 10.3. Best for teams wanting a drop-in MySQL-compatible database without depending on Oracle.

Real-world example
The Wikimedia Foundation (Wikipedia) migrated its entire database infrastructure from MySQL to MariaDB in 2013, citing technical improvements and a preference for software without a bifurcated free/enterprise codebase.
ProsCons
  • Fully open source, no enterprise/community split
  • Drop-in MySQL compatibility
  • Extra storage engines for specialized performance
  • Built-in temporal tables simplify audit history
  • Smaller ecosystem/market share than MySQL or PostgreSQL
  • Divergence from MySQL grows over time
  • Smaller talent pool
  • Fewer large managed cloud offerings

IBM Db2

Enterprise RDBMS, Mainframe & Distributed — dating to the 1980s, historically tied to IBM mainframes (Db2 for z/OS), also available for Linux/UNIX/Windows and cloud. BLU Acceleration provides in-memory columnar storage for analytics, reporting 10-50x speedups for BI workloads. Db2 pureScale offers transparent clustering/HA. Best for large, established enterprises — especially banks, insurers, and government agencies — with existing mainframe investments.

Real-world example
Banks make up roughly 43% of Db2's user base. Garanti BBVA deployed IBM Db2 Analytics Accelerator to run 300+ nightly analytics batch jobs, cutting a two-day compliance report down to about one minute.
ProsCons
  • Extremely mature for mainframe transaction processing
  • BLU Acceleration gives dramatic analytic speedups
  • pureScale offers strong clustering/HA
  • Trusted in the most regulated industries
  • High cost, especially with mainframe licensing
  • Smaller, increasingly scarce talent pool
  • Strong "legacy" association complicates hiring
  • Migrating on/off Db2 is high-risk

Amazon Aurora

Cloud-Native Managed RDBMS, MySQL/PostgreSQL-Compatible — AWS's cloud-native database, wire-compatible with MySQL and PostgreSQL, with storage decoupled from compute. Data is automatically replicated 6 ways across 3 Availability Zones. Claims up to 6x the throughput of stock MySQL/PostgreSQL. Best for teams migrating from MySQL/PostgreSQL who want a fully managed, highly available database without operating storage/replication themselves.

Worked example — Aurora's quorum durability model 6 total replicas (2 per AZ × 3 AZs)  |  Write quorum: 4 of 6 nodes must acknowledge  |  Read quorum: 3 of 6 nodes must agree
Because write_quorum + read_quorum > total_replicas (4 + 3 = 7 > 6), every read is guaranteed to overlap with the latest committed write — the cluster tolerates an entire AZ failure with zero data loss.
Real-world example
Airbnb, Netflix, Expedia, and Samsung have migrated critical relational workloads to Aurora for its performance and reduced operational overhead; BP, Fannie Mae, and DoorDash use it as a core managed relational datastore.
ProsCons
  • Storage/compute separation enables fast failover and durability
  • Up to 6x throughput over stock MySQL/PostgreSQL
  • Fully managed — AWS handles patching, backups, failover
  • Up to 15 read replicas sharing the same storage
  • AWS-only — significant lock-in
  • More expensive than self-managed for steady workloads
  • Standard Aurora is single-writer per cluster
  • Some engine-specific extensions may not be fully supported

Common Interview Questions

Why would a bank choose Oracle or Db2 over PostgreSQL for its core ledger?
Not purely for technical superiority — PostgreSQL is fully ACID-compliant too — but for decades of vendor-backed 24/7 support, mature RAC/pureScale clustering with near-zero-downtime failover, deep audit/compliance tooling, and existing mainframe/enterprise integrations that would be extremely costly to replace.
Why is SQLite a poor fit for a multi-user web application backend?
SQLite serializes writes at the file level (or via WAL mode) rather than offering a full client-server concurrency model, and it has no built-in network access or user/permission management — it's designed for single-process, embedded, or low-concurrency use, not many concurrent server-side writers.
How does Amazon Aurora achieve high durability without traditional synchronous multi-region replication overhead?
Aurora uses a quorum model: 6 copies across 3 AZs, writes acknowledged by 4 of 6 nodes, reads confirmed by 3 of 6. Since 4 + 3 > 6, every read quorum is guaranteed to overlap the latest write quorum, giving strong durability guarantees without waiting for all 6 copies to confirm every write.
Why did Wikipedia migrate from MySQL to MariaDB instead of staying on MySQL?
Beyond technical improvements (query optimizer, Percona-derived patches), Wikimedia wanted to avoid a database whose long-term roadmap was controlled by a single vendor (Oracle) with a split community/enterprise codebase — MariaDB's independent foundation governance was itself a deciding factor.
What's the practical difference between MySQL's pluggable storage engines and PostgreSQL's single engine?
MySQL lets you pick a storage engine per table (InnoDB for transactions, MyISAM for legacy read-heavy, MyRocks for compression) which adds flexibility but administrative complexity. PostgreSQL uses one unified MVCC-based engine for everything, trading engine-choice flexibility for a simpler, more consistent operational and concurrency model.

Key Takeaways

Remember
Relational databases remain the default for anything needing strong consistency and well-defined relationships. Within that space, the choice is rarely "relational vs. not" but which relational engine fits your ecosystem, budget, and operational model — open-source (MySQL/PostgreSQL/MariaDB) for cost and flexibility, enterprise commercial (Oracle/SQL Server/Db2) for maximum vendor support and compliance depth, embedded (SQLite) for local/offline use, and cloud-native managed (Aurora) to offload operations entirely.
