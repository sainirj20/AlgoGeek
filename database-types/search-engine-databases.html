DATABASE TYPES

Search-Engine / Full-Text Search Databases

Overview

Relational databases can do basic LIKE '%keyword%' matching, but that approach doesn't scale or rank well: it can't handle relevance scoring, stemming ("running" should match "run"), typo tolerance, synonyms, faceted filtering (drill down by brand/price/category simultaneously), or fast full-text search across millions of documents. Search-engine databases solve this using an inverted index — instead of storing "document → words," they store "word → list of documents containing it," which makes searching for any term (or combination of terms) extremely fast regardless of collection size. They also add relevance-ranking algorithms, most commonly BM25, to sort results by how well they match a query rather than just whether they match at all.

Why Search-Engine Databases Exist

This makes search-engine databases the standard choice for full-text search — site search, e-commerce product search, log/event search — and they've increasingly expanded into a broader "analytics engine" role: log analytics, security monitoring (SIEM), business intelligence dashboards, and, as of 2024-2026, vector/hybrid search, letting the same engine combine traditional keyword relevance with semantic embedding-based similarity for AI-powered retrieval (RAG) use cases.

Inverted index lookup vs. relational LIKE scan Inverted index: term → postings list, average lookup ≈ O(1) hash/dictionary access into the index, independent of total document count N
Relational LIKE '%term%': no usable index for a leading wildcard, so the engine falls back to a full table scan ≈ O(N)
BM25 relevance scoring ranks matching documents using term frequency (how often a term appears in a document), inverse document frequency (how rare/informative that term is across the collection), and document-length normalization — so results are sorted by relevance, not just presence of a match.
Real-world example
An e-commerce deployment can index millions of product documents and let a search-engine database handle typo-tolerant, ranked, faceted search (filter by price, brand, and category simultaneously) in milliseconds — something a relational LIKE query cannot do at that scale or quality.

Named Products

Elasticsearch

Distributed Search & Analytics Engine — the most widely used distributed search and analytics engine, built on top of Apache Lucene. It stores schema-flexible JSON documents and provides near-real-time full-text search, aggregations, and (increasingly) vector search, all accessible via a REST/JSON API. Developed by Elastic, it forms the core of the broader "Elastic Stack" (Elasticsearch, Logstash, Kibana, Beats). Query languages are the Elasticsearch Query DSL (JSON-based) plus ES|QL, a newer SQL-like piped query language; scaling is horizontal via sharding and replication with automatic rebalancing. Best for application/site search, e-commerce product search with faceting, log analytics and observability (the "ELK stack"), security monitoring (SIEM), and AI-powered RAG pipelines needing hybrid keyword + vector search. Not a fit as a system of record needing strong ACID guarantees — treat it as a secondary/derived index, not your primary data store.

Real-world example
Companies like Netflix, eBay, and Walmart use Elasticsearch to power large-scale product/content search with faceted filtering and relevance ranking, as well as to ingest and search massive volumes of application and infrastructure logs for troubleshooting and security monitoring.
ProsCons
  • Extremely fast, scalable full-text search with sophisticated relevance ranking out of the box
  • Rich aggregation framework doubles as a powerful analytics engine (log/metrics dashboards, BI)
  • Huge ecosystem: Kibana for visualization, Logstash/Beats for ingestion, extensive client libraries
  • Now supports vector search natively, enabling hybrid keyword+semantic search for RAG
  • Licensing changed from Apache 2.0 to the source-available Elastic License/SSPL, prompting the OpenSearch fork
  • Not a transactional system of record — needs a separate primary datastore in most architectures
  • Operationally complex to run and tune at scale (shard sizing, cluster management, JVM heap tuning)
  • Cost can be significant at scale, especially for the managed Elastic Cloud offering

Apache Solr

Enterprise Search Platform — a mature, open-source (Apache 2.0) enterprise search platform, also built on Apache Lucene, and one of the longest-standing production search engines predating Elasticsearch. It offers advanced text search (stemming, synonyms, relevancy ranking), faceted navigation, geospatial search, and, in recent releases, vector search for RAG-style use cases. Query syntax is Solr's own request-handler/query-parser (parameters-based, e.g. q=, fq= facet queries), plus a JSON Request API; SolrCloud provides distributed, sharded, and replicated indices coordinated via ZooKeeper, with cross-data-center replication (graduated to stable status in 2025). Best for enterprise search across internal documents/knowledge bases, e-commerce search with faceted filtering, geospatial search for logistics/supply chain, and teams preferring a fully open-source (Apache 2.0) engine. Not the top pick for greenfield projects, where Elasticsearch or OpenSearch's more modern tooling and larger community momentum are usually a better fit.

Real-world example
Large e-commerce platforms and enterprises use Solr to power product search with faceted navigation (filter by price, brand, and category simultaneously) and to run enterprise-wide search across internal documents, intranets, and knowledge bases; logistics companies also use Solr's geospatial query support for route optimization and location-based asset tracking.
ProsCons
  • Fully open-source under Apache 2.0 with no source-available licensing complications
  • Mature, proven at enterprise scale for decades with strong text, geospatial, and faceted search
  • SolrCloud provides robust distributed scaling with cross-data-center replication
  • Growing vector-search capability for AI/RAG use cases alongside traditional full-text search
  • Smaller mindshare and slightly less modern tooling ecosystem than Elasticsearch/OpenSearch
  • Configuration (schema.xml/solrconfig.xml) can feel more dated than Elasticsearch's JSON-first approach
  • Fewer turnkey observability/log-analytics dashboard options compared to the Elastic/OpenSearch stacks
  • ZooKeeper dependency for SolrCloud adds an operational component to manage

OpenSearch

Open-Source Elasticsearch Fork — an open-source (Apache 2.0) fork of Elasticsearch 7.10.2, created by AWS in 2021 after Elastic changed its licensing to prevent AWS from offering a competing managed Elasticsearch service. Since September 2024, OpenSearch has been governed by the OpenSearch Software Foundation under the Linux Foundation, ensuring no single vendor controls its roadmap, with over 400 contributing organizations as of 2025-2026. Query language is OpenSearch Query DSL (very similar to Elasticsearch's), plus SQL and PPL (Piped Processing Language) support; scaling is horizontally distributed sharding/replication, plus GPU-accelerated bulk indexing and Zstandard compression (up to ~32% index-size reduction) as recent cost-optimization additions. Best for teams wanting an Elasticsearch-compatible engine under a fully permissive Apache 2.0 license, log analytics, application/website search, and security monitoring, especially on AWS. Not the choice for teams deeply invested in Elastic-specific proprietary features not present in OpenSearch.

Real-world example
Amazon OpenSearch Service is commonly used for real-time application monitoring and log analytics dashboards, website/product search, and increasingly as the vector backend for chatbot knowledge bases — combining OpenSearch's k-NN vector search with traditional keyword search so a support chatbot can retrieve both exact policy-document matches and semantically related passages.
ProsCons
  • Fully open-source under Apache 2.0 with vendor-neutral governance (Linux Foundation)
  • API- and largely feature-compatible with Elasticsearch, easing migration
  • Strong and growing AI/ML feature set: vector fields, k-NN search, hybrid search, neural search
  • Deep native integration with AWS services when run as Amazon OpenSearch Service
  • Slightly behind Elasticsearch on some newer proprietary features developed by Elastic
  • Benchmark results between OpenSearch and Elasticsearch are workload-dependent and contested
  • Still operationally complex to run and tune like any distributed search cluster
  • Divergence between OpenSearch and Elasticsearch codebases over time can complicate switching back and forth

Common Interview Questions

Why can't a relational database's LIKE '%keyword%' query replace a search-engine database at scale?
A leading-wildcard LIKE query can't use a standard B-tree index, so the database falls back to a full table scan whose cost grows linearly with the number of rows. It also has no concept of relevance ranking, stemming, typo tolerance, or synonyms — it can tell you a row matches, not how well it matches, which is what an inverted index plus BM25 scoring is built to solve.
How does an inverted index keep search fast regardless of collection size?
Instead of storing "document → words" (which would require scanning every document to find matches), it stores "word → list of documents containing it." Looking up a term becomes a direct dictionary/hash lookup into the index rather than a scan, so search latency stays roughly constant as the total document collection grows.
Why did AWS fork Elasticsearch into OpenSearch instead of continuing to offer managed Elasticsearch?
Elastic changed Elasticsearch's license from Apache 2.0 to a source-available license (Elastic License/SSPL), which restricted competitors from offering it as a managed service. AWS forked the last Apache 2.0 version (7.10.2) in 2021 to create OpenSearch, which is now governed independently by the Linux Foundation's OpenSearch Software Foundation rather than any single vendor.
When would you choose Apache Solr over Elasticsearch or OpenSearch?
When a team is already invested in the Lucene/Solr ecosystem, wants a fully open-source Apache 2.0 engine without any source-available licensing history, or needs Solr's mature geospatial and faceted-navigation features — for example, logistics companies doing route optimization. Greenfield projects usually lean toward Elasticsearch/OpenSearch instead for their more modern tooling and larger community momentum.
How have search-engine databases evolved to support AI/RAG use cases?
Elasticsearch, Solr, and OpenSearch have all added native vector/dense-field support and hybrid search, letting the same engine combine traditional keyword (BM25) relevance with semantic embedding-based similarity in one query — so a RAG pipeline can retrieve both exact keyword matches and conceptually related passages to ground an LLM's answer.

Key Takeaways

Remember
Search-engine databases exist because relational LIKE queries can't rank, stem, or scale — an inverted index plus BM25-style relevance scoring is what makes fast, ranked full-text search possible at any collection size. Elasticsearch leads on ecosystem and mindshare but changed its licensing; OpenSearch is the vendor-neutral, Apache 2.0 fork that's converged to near feature-parity; Apache Solr remains a solid, fully open-source choice, especially for geospatial and enterprise search. All three now support vector/hybrid search for RAG.
