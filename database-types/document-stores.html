DATABASE TYPES

Document Databases

Overview

NoSQL ("non-SQL" or "not only SQL") refers to any database that stores data in a non-tabular format rather than the rows/columns/foreign-key structure of relational databases. NoSQL databases emerged in the late 2000s/2010s (Google's Bigtable paper in 2006, Amazon's Dynamo paper in 2007, MongoDB/Cassandra/Riak circa 2009-2010) to solve problems relational databases struggled with at internet scale: massive horizontal scaling across commodity servers, flexible/evolving schemas, and high write throughput for semi-structured or unstructured data. "NoSQL" is really an umbrella covering four major data models — document, key-value, wide-column/column-family, and graph (graph has its own page) — and most NoSQL systems trade some of SQL's strict consistency and rich multi-table query power for horizontal scalability, availability, and developer flexibility.

ModelUnit of dataOptimized forExamples
Key-ValueOpaque blob, retrieved only by its keyExtremely fast, simple get/put/delete lookupsRedis, DynamoDB, Memcached, Aerospike, Riak, etcd
DocumentSemi-structured JSON/BSON/XML document, queryable by internal fieldsFlexible schema, rich per-document querying, nested one-to-many data without joinsMongoDB, Couchbase, CouchDB, DocumentDB, Firestore
Wide-ColumnRow key + dynamically-named columns grouped into column familiesVery high write throughput, huge sparse datasets, reading a slice of columns across billions of rowsCassandra, HBase, Bigtable, ScyllaDB

A simple way to remember it: key-value = "one key, one blob"; document = "one key, one rich queryable JSON object"; wide-column = "one row key, many dynamically-named columns grouped into families, spread across a distributed table." This page covers the document model — see Key-Value Stores and Wide-Column / Column-Family Stores for the other two.

Why Document Databases Exist

Before comparing NoSQL products, it helps to understand the CAP theorem (Eric Brewer): a distributed data store can only fully guarantee two of three properties at once, and in practice the real choice only matters when a network partition happens — Consistency (every read gets the most recent write, no matter which node answers), Availability (every request to a non-failing node gets a response, even if it isn't the latest data), and Partition tolerance (the system keeps working even when network links between nodes drop or delay messages). Because network partitions are unavoidable in any real distributed system, partition tolerance is effectively mandatory — so the practical trade-off during a partition is really Consistency vs. Availability.

CAP theorem, formally Pick 2 of 3 during a network partition: Consistency + Availability + Partition tolerance  |  Since P is non-negotiable in any real distributed system, the actual choice is CP (stay consistent — pause or reject requests on the affected side) vs. AP (stay available — keep answering everywhere and reconcile stale data later).
CP systems (MongoDB with majority writes, HBase, etcd) fit banking balances, inventory counts, and coordination data. AP systems (Cassandra, DynamoDB by default, CouchDB, Riak, Couchbase in some configs) fit shopping carts, social feeds, session data, and IoT telemetry. Many modern systems are tunable per-query rather than fixed at one end. A more nuanced extension, PACELC, adds: even without a Partition, there's still a tradeoff between Latency and Consistency (E-lse).

Document databases store self-describing records (typically JSON/BSON) where each document can have its own structure, nested arrays, and sub-objects. They're the most "general purpose" of the NoSQL families — a natural fit for object-oriented application code, rapid iteration, and semi-structured data — and most now offer secondary indexing, rich query languages, and even multi-document ACID transactions, closing much of the historical gap with relational databases for OLTP-style workloads.

Real-world example
A shopping-cart service that must never show an error during a brief network blip typically runs on an AP-leaning store (e.g., Couchbase or DynamoDB in its default mode) and reconciles any duplicate or stale cart items once the partition heals; a bank-balance or inventory-count service instead needs a CP-leaning configuration (e.g., MongoDB with majority write/read concern) that would rather reject a request than risk returning stale data.

Named Products

MongoDB

NoSQL / Document Database — the most widely adopted document database, storing data as BSON (binary JSON) documents grouped into "collections" instead of rows in tables. Built from the ground up for developer agility (flexible schema, native driver objects) and horizontal scale via sharding, it has since added rich secondary indexing, aggregation pipelines, and full ACID multi-document transactions. The default single-primary replica set is CP-leaning (writes go to a primary and can require majority acknowledgment for durability), with tunable read/write concerns letting developers dial weaker/faster or stronger/slower guarantees per operation; native sharding via a shard key supports zone sharding to pin data to specific regions for latency/compliance (e.g., GDPR). Best for content management systems, product catalogs, user profiles, evolving-schema app backends, and general-purpose OLTP apps wanting document flexibility plus real transactional guarantees. Not ideal for heavily normalized financial ledgers needing complex joins, or workloads where a pure key-value store would be cheaper/faster.

Real-world example
Bosch Digital uses MongoDB Atlas as the backbone of its IoT platform, ingesting massive, variably structured telemetry from connected industrial devices where a fixed relational schema would be impractical.
ProsCons
  • Flexible schema speeds up iterative development
  • Rich query language plus aggregation framework (near SQL-level analytical power)
  • Native horizontal sharding for very large datasets
  • Multi-document ACID transactions when needed
  • Denormalized design can lead to data duplication and update complexity
  • Sharding adds significant operational complexity to manage well
  • Memory-hungry at scale (indexes need to fit in RAM for best performance)
  • Licensing (SSPL) means true "open source" purists use forks/alternatives

Couchbase

NoSQL / Document Database, Multi-Model (document + key-value + search + analytics) — a distributed, JSON-based document database descended from the merger of Membase (a Memcached-compatible KV store) and CouchDB, giving it both document flexibility and memory-first key-value speed. It has evolved into a multi-model platform (Capella cloud DBaaS, Server, Mobile/Edge) supporting SQL-like querying (N1QL/SQL++), full-text search, analytics, and vector search in one system. Its memory-first architecture caches active data in RAM with disk persistence for durability, offers tunable consistency (durability levels, replica reads) similar to Cassandra's model, and scales out by adding nodes with automatic rebalancing. Best for caching-plus-database consolidation, personalization/customer-360 stores, dynamic product catalogs, and offline-first mobile/IoT apps needing edge sync. Not worth the operational overhead for small apps or teams needing strict multi-row ACID transactions across many entities.

Real-world example
Retailers use Couchbase to power dynamic, personalized product catalogs and shopping-cart/session caching at sub-millisecond latency during high-traffic sales events, while also using its Mobile/Edge tier for offline-capable retail associate apps in stores with unreliable connectivity.
ProsCons
  • Combines caching, document DB, search, and analytics in one product
  • Memory-first architecture gives very low read/write latency
  • Strong offline-first mobile/edge sync story
  • Good horizontal scalability with automatic rebalancing
  • More operationally complex than a single-purpose document DB
  • Smaller community/ecosystem than MongoDB
  • Enterprise features are commercially licensed (cost can add up)
  • Memory-first design means RAM sizing/cost planning matters a lot

Apache CouchDB

NoSQL / Document Database — an open-source document database that stores data as JSON documents and is built specifically around HTTP/REST access and a distinctive multi-master replication protocol. Any CouchDB node (including embedded/mobile instances like PouchDB) can accept writes and later sync bidirectionally with any other node, making it a foundational technology for "offline-first" application design. It uses MVCC (multi-version concurrency control) with revision IDs, so concurrent edits create conflicting revisions the application resolves rather than the database blocking writes; views/indexes are defined with MapReduce; replication is asynchronous and multi-master, giving it an AP (eventually consistent) profile. Best for offline-first mobile/edge applications, multi-site/disconnected deployments, and scenarios needing simple HTTP-native replication between data centers or devices. Not a fit for financial transactions needing strong immediate consistency, massive-scale low-latency OLTP, or heavy ad-hoc querying.

Real-world example
The Red Cross uses CouchDB-based (iDAT) multi-node, peer-to-peer, offline-first databases to coordinate relief operations in disaster areas with little or no reliable network connectivity; CERN has also used CouchDB-style replication for distributed data management around the Large Hadron Collider.
ProsCons
  • True multi-master replication — any node can read/write and sync later
  • Excellent fit for offline-first and edge/mobile scenarios (pairs with PouchDB)
  • Simple HTTP/REST API, easy to integrate with web tooling
  • Built-in conflict detection via MVCC revisions
  • Conflict resolution is manual/application-level, not automatic
  • MapReduce views are less flexible/expressive than SQL-like query languages
  • Historically slower query performance vs. MongoDB/Couchbase at scale
  • Not designed for strong-consistency use cases

Amazon DocumentDB (with MongoDB compatibility)

NoSQL / Document Database, Managed Cloud Service — AWS's fully managed document database service, implementing the MongoDB wire protocol/API (currently compatible up to MongoDB 8.0) but running on a proprietary, Aurora-style storage engine rather than actual MongoDB code. It decouples compute from a distributed, auto-scaling storage layer, aiming to give MongoDB-compatible applications a "serverless-feeling," highly durable managed backend. Data is replicated six ways across three Availability Zones automatically, with storage auto-scaling up to 128 TB; the consistency model is primarily single-writer/multi-reader (strong consistency on the primary, eventually consistent replica reads). A 2025 "New Query Planner" delivered up to 10x gains on certain query patterns, and in-place major version upgrades (5.0 → 8.0) arrived in 2026. Best for teams already using MongoDB drivers/query syntax who want AWS-native managed operations without running MongoDB themselves. Not a fit for apps needing the very latest MongoDB features or multi-cloud/on-prem portability.

Real-world example
Enterprises migrating self-managed MongoDB clusters running on EC2 to DocumentDB to offload operational burden (patching, backups, failover) while keeping the same application code and MongoDB drivers — common in SaaS companies consolidating infrastructure onto AWS-managed services.
ProsCons
  • Fully managed: automated backups, patching, failover, monitoring
  • MongoDB-compatible API eases migration for existing MongoDB apps
  • Storage auto-scales up to 128 TB without manual sharding for many workloads
  • Six-way replication across three AZs gives strong durability
  • Not actually MongoDB — API compatibility is partial and lags real MongoDB releases
  • AWS-only, creating cloud vendor lock-in
  • Some MongoDB features/aggregation operators unsupported or behave differently
  • Write scaling is less flexible than MongoDB's native sharding in some scenarios

Google Firestore

NoSQL / Document Database, Serverless, Real-Time — Google Cloud's serverless document database, the backbone of the Firebase mobile/web platform, built on top of Google's Spanner-derived infrastructure for automatic multi-region replication. Its signature feature is real-time listeners — clients can subscribe to a query or document and get pushed live updates instead of polling. Documents are organized into collections/sub-collections; it offers strong consistency by default across multi-region replicas (a rarity among globally distributed document databases, achieved via Spanner-like synchronized clocks/consensus) with a 99.999% availability SLA, and scales automatically with no manual sharding. As of 2025 it also supports a MongoDB-compatible API mode and expanded query "pipelines" (regex, text/geospatial search). Best for mobile/web apps needing real-time sync, gaming backends, and teams wanting a zero-ops, auto-scaling backend integrated with Firebase Auth/Hosting/Cloud Functions. Not suited to complex analytical/reporting queries or non-Google-Cloud environments.

Real-world example
Mobile games use Firestore to store player profiles, in-game inventories, and marketplace listings, relying on real-time listeners to instantly reflect state changes (e.g., a trade completing) across a player's connected devices without polling.
ProsCons
  • True zero-ops serverless scaling (no capacity planning/sharding)
  • Real-time listeners are a killer feature for collaborative/live apps
  • Strong consistency with multi-region high availability (rare combination)
  • Deep integration with Firebase (Auth, Hosting, Cloud Functions, offline SDKs)
  • Query capabilities are more limited than SQL or even MongoDB aggregation
  • Pricing model (per document read/write/delete) can get expensive and is easy to misjudge at scale
  • Tied to Google Cloud/Firebase ecosystem
  • Index management (composite indexes) requires upfront planning

Common Interview Questions

According to the CAP theorem, why can't a distributed document database give you perfect consistency, availability, and partition tolerance all at once?
Network partitions are unavoidable in any real distributed system, so partition tolerance is effectively mandatory — that leaves only a choice between consistency and availability when a partition actually occurs: a CP system rejects or pauses requests on the affected side to guarantee freshness, while an AP system keeps answering on both sides and accepts that some responses may be briefly stale.
Is MongoDB a CP or an AP system?
It depends on configuration. MongoDB's default single-primary replica set with majority write/read concern behaves like a CP system — it won't acknowledge a write, or will refuse certain reads, if it can't reach a majority of nodes — but weaker read/write concern settings trade that consistency for lower latency and higher availability, which is why MongoDB is often described as "tunable" rather than fixed at one end of CAP.
How does Google Firestore offer both strong consistency and multi-region availability, which sounds like it defies CAP?
Firestore doesn't defy CAP — it's built on Spanner-derived infrastructure using synchronized clocks and consensus to keep multi-region replicas strongly consistent, which means during an actual network partition it leans CP (pause/reject on the cut-off side) rather than AP. The 99.999% SLA describes normal-operation availability, not behavior during a partition.
Why would a team pick Apache CouchDB over MongoDB for a mobile field-data-collection app?
CouchDB's true multi-master replication lets every device (even an embedded PouchDB instance) accept writes offline and sync bidirectionally once connectivity returns, with MVCC-based revision conflicts surfaced for the application to resolve — a purpose-built fit for offline-first, disconnected scenarios like disaster relief, which MongoDB's single-primary replica-set model isn't designed around.
What do you give up by moving from self-managed MongoDB to Amazon DocumentDB?
DocumentDB isn't actually MongoDB — it reimplements the MongoDB wire protocol on a proprietary Aurora-style storage engine, so it always lags real MongoDB releases and isn't 100% API/feature compatible (some aggregation operators behave differently or are unsupported). In exchange you get AWS-managed backups, patching, failover, and six-way multi-AZ replication without operating MongoDB yourself.

Key Takeaways

Remember
Document databases are the general-purpose entry point into NoSQL — flexible JSON/BSON schemas, rich per-document querying, and (in MongoDB's and Couchbase's case) real ACID transactions have closed much of the historical gap with relational databases. The real differentiator between products is where each one sits on the CAP spectrum and what specialized problem it solves: MongoDB for general-purpose flexible OLTP, Couchbase for combined caching+document+search, CouchDB for offline-first multi-master sync, DocumentDB for AWS-managed MongoDB compatibility, and Firestore for zero-ops real-time mobile/web backends tied to Firebase.
