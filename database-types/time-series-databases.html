DATABASE TYPES

Time-Series Databases

Overview

A time-series database (TSDB) is optimized for one very specific but extremely common shape of data: a timestamp, a numeric or structured value, and a set of tags/labels identifying the source — e.g. cpu.usage, host=web-01, region=us-east, value=72.3, time=2026-07-15T10:00:00Z. This data is almost always append-only (you rarely update a historical measurement), arrives at extremely high volume and velocity (thousands to millions of points per second from sensors, servers, or applications), is queried primarily by time range and aggregated over windows (avg per minute, max per hour, rate of change), and becomes less valuable/detailed over time, so older data is often rolled up or downsampled and eventually deleted.

Why Time-Series Databases Exist

General-purpose relational or document databases struggle at scale with this pattern because they aren't optimized for the specific access patterns: B-tree indexes aren't ideal for constantly-appended timestamp-ordered data, storage isn't naturally columnar/compressible for repeating numeric series, and there's no built-in concept of retention or downsampling. Time-series databases solve this by partitioning data into time-based chunks, compressing aggressively (values in a metric series are often very similar to their neighbors, enabling extreme compression ratios), providing native downsampling/retention policies, and offering query languages with built-in time-windowing and rate-of-change functions. This makes them the backbone of observability/monitoring (metrics, dashboards, alerting), IoT sensor pipelines, financial tick data, and industrial telemetry.

Downsampling storage savings Raw resolution: 1 point every 10 seconds → 8,640 points/day per series
Downsampled after 7 days to 5-minute rollups → 288 points/day per series
Reduction factor = 8,640 ÷ 288 = 30× fewer stored points for data older than a week, while retention policies eventually drop the rollups entirely past a defined age
Real-world example
Industrial and IoT companies ingest sensor telemetry (temperature, vibration, pressure) from thousands of machines on a factory floor, storing years of history cost-effectively while still being able to query "average vibration per machine per hour over the last 6 months" quickly — a pattern general-purpose relational databases handle poorly at this volume and retention depth.

Named Products

InfluxDB

Purpose-Built Time-Series Database — created by InfluxData, widely used for metrics, events, and real-time analytics. Version 3.0 (GA since April 2025) is a from-the-ground-up rewrite in Rust using Apache Arrow, Parquet, and DataFusion, storing data as Parquet files on object storage (S3, Azure Blob, GCS) or local disk, enabling both fast recent-data queries and cheap long-term storage. SQL and InfluxQL are the primary query languages in InfluxDB 3 (Flux, the earlier custom functional language, is now in maintenance mode); it supports infinite cardinality by decoupling storage growth from compute. Best for DevOps/infrastructure monitoring, IoT sensor data, financial tick data, and workloads with very high-cardinality tags that older TSDBs choke on. Not a fit for general-purpose transactional/relational data, or teams already standardized on Prometheus for Kubernetes-native pull-based metrics.

Real-world example
InfluxDB is used in production by companies including IBM, Cisco, and Tesla for IoT monitoring, DevOps observability, and industrial sensor analytics — ingesting telemetry from thousands of machines while querying years of history cost-effectively from object storage.
ProsCons
  • Purpose-built compression and storage, with strong cost efficiency at scale
  • InfluxDB 3's Parquet/object-storage architecture separates storage growth from compute cost
  • Supports very high cardinality without the performance collapse seen in older TSDB designs
  • SQL support (InfluxDB 3) lowers the learning curve versus older custom query languages
  • Migrating from Flux/InfluxQL-based 1.x/2.x to InfluxDB 3 involves query-language and architecture changes
  • Not designed for non-time-series relational workloads
  • Commercial/cloud tiers needed for the most advanced clustering and enterprise features
  • Object-storage-backed architecture can add query latency versus purely in-memory TSDBs

TimescaleDB

Time-Series Database — PostgreSQL Extension — an open-source extension that turns PostgreSQL into a high-performance time-series database rather than being a standalone engine. It introduces "hypertables" — tables that look like ordinary PostgreSQL tables to the application but are automatically partitioned into time-based chunks — plus continuous aggregates, native compression, and (as of the 2.18 "hypercore" release in 2025) a unified row/column storage engine that keeps hot recent data in row form and converts cold data to compressed columnar form. Full standard SQL, extended with time-series functions like time_bucket. Compression routinely achieves 90-97% storage reduction. Best for teams that want time-series performance without leaving the PostgreSQL/SQL ecosystem, especially when time-series data needs to be joined with regular relational/business data in the same database. Not a fit for extremely high-cardinality, massive-scale metrics workloads better served by a purpose-built distributed TSDB, or teams that don't already use PostgreSQL.

Real-world example
A fintech company tracking stock/crypto tick data alongside relational data (accounts, orders, users) can store both in the same PostgreSQL database — using TimescaleDB hypertables for the high-volume tick data and ordinary PostgreSQL tables for accounts — and run a single SQL query joining "average price over the last hour" with "which accounts hold this asset."
ProsCons
  • Full PostgreSQL compatibility — standard SQL, joins, existing tooling and drivers all work unchanged
  • Hypertables give 10-100x faster time-window queries versus raw PostgreSQL
  • Native compression yields dramatic storage savings (often 90%+ reduction)
  • Continuous aggregates make dashboards and rollups fast without manual ETL
  • Bounded by PostgreSQL's single-writer-per-primary architecture for write scaling
  • Not as extreme in cardinality/throughput ceiling as purpose-built distributed TSDBs
  • Requires PostgreSQL operational expertise (vacuuming, extensions, upgrades)
  • Some advanced features (hypercore, tiering, multi-node) are part of the commercial/cloud offering

Prometheus

Time-Series Database — Monitoring & Alerting System — an open-source monitoring and alerting toolkit that includes its own purpose-built time-series database. Unlike most TSDBs, Prometheus uses a "pull" model — it scrapes numeric metrics from HTTP endpoints exposed by applications and infrastructure at regular intervals — rather than having systems push data to it, and has become the de facto standard for monitoring cloud-native and Kubernetes environments. Data is a multi-dimensional time series identified by a metric name and key-value label pairs, queried with PromQL. Single-server design with local on-disk storage by default; scales for long-term storage via remote-write to systems like Thanos, Cortex, or Mimir. Best for Kubernetes/cloud-native infrastructure monitoring, microservices observability, and alerting on operational thresholds. Not a fit for long-term historical storage spanning years on its own, non-numeric/event/log data, or very high-cardinality labels.

Real-world example
A company running microservices on Kubernetes typically deploys Prometheus to scrape each pod's /metrics endpoint for CPU, memory, request rate, and error rate, then uses PromQL to power Grafana dashboards and Alertmanager rules such as "page on-call if error rate exceeds 1% over 5 minutes."
ProsCons
  • De facto standard for Kubernetes/cloud-native monitoring with an enormous exporter ecosystem
  • PromQL is powerful and purpose-built for operational alerting and dashboards
  • Pull model simplifies service discovery in dynamic container environments
  • Tight integration with Grafana and Alertmanager for a complete observability stack
  • Not designed for long-term storage out of the box; needs companion systems (Thanos, Cortex, Mimir)
  • High-cardinality labels can cause performance and memory problems
  • Pull model doesn't fit short-lived batch jobs or devices behind firewalls without a push-gateway
  • Single-node storage model isn't inherently horizontally scalable for very large fleets

Graphite

Time-Series Database — Metrics Storage & Graphing — one of the original open-source time-series monitoring tools (created in 2006), consisting of Carbon (a service that receives and relays incoming metrics), Whisper (a fixed-size, round-robin-style database for storing the time series), and a web UI/API for rendering graphs. Data uses hierarchical, dot-separated metric naming (e.g. servers.web01.cpu.usage), plus more modern tag-based support; queries pass metrics through a composable function pipeline (summarize, movingAverage, alias). Scales horizontally via Carbon relay/aggregation tiers and consistent hashing. Best for long-established server/network/application monitoring stacks and teams with existing Graphite/Carbon infrastructure. Not the right choice for greenfield projects, which today typically default to Prometheus or InfluxDB/TimescaleDB for higher cardinality and richer query languages.

Real-world example
Graphite has long been used in production by companies like Booking.com, Etsy, and GitHub as the backend for server and application monitoring dashboards — applications emit metrics like app.requests.count via the simple Carbon line protocol, and operators build Grafana dashboards on top to track site health and capacity trends.
ProsCons
  • Extremely simple ingestion protocol — trivial to instrument any application
  • Long track record and stability in production at scale
  • Rich function-pipeline query language for flexible graph transformations
  • Predictable, fixed-size storage footprint via Whisper
  • Considered legacy relative to Prometheus/InfluxDB for new cloud-native projects
  • Hierarchical dot-separated naming is less flexible than modern label/tag-based models
  • Whisper's fixed-size files require upfront retention/rollup planning
  • Smaller, slower-moving community/ecosystem than Prometheus today

Amazon Timestream

Time-Series Database — Managed, Cloud — AWS's managed time-series database offering, which as of 2025 split into two distinct products: Timestream for LiveAnalytics (AWS's original serverless engine, now in maintenance mode and closed to new customers since June 2025) and Timestream for InfluxDB (a fully managed InfluxDB service on AWS infrastructure, now AWS's recommended path, supporting InfluxDB 3 Core and Enterprise as of late 2025). LiveAnalytics uses a memory store for recent data and a magnetic store for historical/cheaper storage with its own SQL-based query language; Timestream for InfluxDB uses standard InfluxQL/SQL/Flux. Best for teams already committed to AWS wanting a managed time-series database without operating servers — new projects should default to Timestream for InfluxDB, since LiveAnalytics is closed to new sign-ups. Not a fit for multi-cloud/on-prem deployments or teams wanting the largest open-source ecosystem and community control.

Real-world example
An industrial IoT company streaming sensor telemetry from thousands of connected devices via AWS IoT Core or Kinesis into Timestream for InfluxDB gets single-digit-millisecond query response for live dashboards and alerting, while still running complex historical analytics over petabytes of accumulated sensor history without operating the underlying InfluxDB servers themselves.
ProsCons
  • Fully managed — AWS handles patching, scaling, and availability
  • Timestream for InfluxDB brings the mature InfluxDB query surface to a managed AWS service
  • Tight integration with AWS IoT Core, Kinesis, MSK, and Telegraf for ingestion
  • Multi-AZ read replicas and compute/storage auto-scaling for production reliability
  • Confusing product transition — LiveAnalytics is closed to new customers, requiring migration planning
  • AWS-only, creating cloud lock-in
  • Smaller community/ecosystem than running open-source InfluxDB, Prometheus, or TimescaleDB directly
  • Cost can be less predictable than self-hosted alternatives at very high, sustained ingestion volumes

Common Interview Questions

Why can time-series databases sustain much higher write throughput than a general relational database for this workload?
Writes are append-only — new timestamped points, essentially never updates to old rows — so the engine can skip most of the transactional/indexing machinery (row-level locking, MVCC version chains, B-tree rebalancing) a relational database maintains for arbitrary updates, and can use compression schemes suited to sequential, slowly-changing numeric data.
What's the difference between a retention policy and downsampling?
A retention policy deletes data entirely once it passes a defined age, bounding total storage. Downsampling instead reduces resolution of aging data — rolling many fine-grained points into fewer coarse aggregated ones — so some historical trend information is kept at far less storage, before it's eventually dropped by retention.
Why is Prometheus's pull model a good fit for Kubernetes, and where does it fall short?
Pulling from a /metrics endpoint fits dynamic container environments well because Prometheus's service discovery finds new pods automatically. It falls short for short-lived batch jobs or devices behind firewalls that can't be scraped (requiring a push-gateway workaround), and its single-node local storage isn't designed for long-term retention without pairing it with Thanos, Cortex, or Mimir.
Why might a team choose TimescaleDB over a purpose-built TSDB like InfluxDB?
If the application already runs on PostgreSQL and needs to join time-series data with regular relational data — like sensor readings against a customer or asset table — TimescaleDB keeps everything in one database with full SQL and existing tooling, trading some ceiling on extreme cardinality/throughput for far less operational complexity than running two systems.
Why does high label/tag cardinality hurt older time-series database designs?
Each unique combination of tags (host, region, device, etc.) creates a distinct series that the engine has to index and store separately; when the number of combinations explodes, index size and memory use grow just as fast, which is exactly the failure mode InfluxDB 3's architecture and Prometheus's cardinality limits are designed to guard against.

Key Takeaways

Remember
Time-series databases trade general-purpose update/delete flexibility for extreme append-only write throughput and time-range-optimized storage — compression, downsampling, retention — because their workload looks nothing like typical OLTP traffic. InfluxDB and Amazon Timestream for InfluxDB lead on purpose-built, high-cardinality metrics at scale; TimescaleDB fits teams that want time-series performance without leaving PostgreSQL; Prometheus is the default for Kubernetes-native pull-based monitoring; Graphite remains in use in legacy stacks but is rarely chosen for new projects today.
