DATABASE TYPES

Key-Value Stores

Overview

A key-value store is the simplest and often fastest NoSQL model — conceptually a distributed hash table where every operation is a get/put/delete addressed by a single key. There is no query language for scanning across attributes, no joins, and usually no schema at all beyond "a key maps to a value." Some products (Redis, Aerospike) enrich the value side with lists, sets, sorted sets, and other structures; others (etcd) narrow the scope further to small, strongly-consistent coordination data.

Key-value stores fit workloads dominated by simple lookups by a known key at very high speed and scale — caching, session storage, real-time counters/leaderboards, and shopping-cart-style state. They are a poor fit whenever the application needs complex queries across fields it doesn't already know the key for, multi-entity joins, or rich ad hoc filtering — that's the territory of document, relational, or search-engine databases instead.

Why Key-Value Stores Exist

Almost every high-traffic system places a key-value tier in front of, or beside, its system of record: a cache absorbing read load from a slower database, a session store keeping login state out of the critical path, or a coordination store holding the small amount of cluster state that must never be ambiguous. The category spans from purely volatile, cache-only stores (Memcached) to fully durable, horizontally-scaled systems of record (DynamoDB) — the common thread is that every operation addresses one key directly, with no scan or join required, which is exactly what makes the model so fast and so horizontally scalable.

Real-world example
Kubernetes stores its entire cluster state — every pod, deployment, secret, and service definition — as key-value pairs in etcd, prioritizing strict consistency for a small amount of critical data. The applications running on that same cluster typically run a separate key-value tier (Redis or Memcached) purely for caching, prioritizing raw speed over durability. Both are "key-value stores," but they sit at opposite ends of the category's design spectrum.

Named Products

Redis

In-Memory Data Structure Store — an open-source store used as a cache, database, message broker, and streaming engine, not just a flat key-value map. Values can be rich structures: strings, hashes, lists, sets, sorted sets, bitmaps, hyperloglogs, streams, and (in 8.x) native vector types for AI similarity search, all manipulated with atomic commands. It's primarily RAM-resident for microsecond-level latency, with optional durability via RDB snapshots and/or AOF write logging; it scales via Redis Cluster (sharding across masters with replicas) or Sentinel (HA failover for a single master). Best for caching, session stores, real-time leaderboards (sorted sets), rate limiting, pub/sub, job queues, and increasingly vector search for RAG applications. Not a fit as the primary system of record for data that must exceed available RAM economically, or for workloads needing complex relational queries.

Real-world example
Twitter's fanout service writes each new tweet into followers' home timelines stored in Redis, sharded across multiple clusters, for extremely fast timeline reads. Riot Games and Supercell use Redis sorted sets to power real-time leaderboards with millions of entries in games like League of Legends and Clash of Clans.
ProsCons
  • Extremely low latency (sub-millisecond) from its in-memory design
  • Rich data structures beyond plain strings (lists, sets, sorted sets, streams)
  • Versatile — cache, DB, message broker, and now vector store in one
  • Mature clustering/HA options (Sentinel, Cluster)
  • Dataset size is bounded by available RAM (memory cost at scale)
  • Persistence is secondary to the in-memory design — durability trade-offs exist
  • Single-threaded command execution per shard can bottleneck CPU-heavy ops
  • Licensing changes (AGPL move, then reversal) drove ecosystem uncertainty and the Valkey fork

Amazon DynamoDB

Fully Managed, Serverless Key-Value/Document Store — AWS's NoSQL database descended from the original 2007 Amazon Dynamo paper, built to give predictable low-latency performance at effectively unlimited scale with no server or cluster management. Items are key-value pairs with optional nested JSON-like attributes, stored in tables auto-partitioned by partition key. Consistency is tunable — eventually consistent reads by default, strongly consistent reads on demand — and capacity is elastic ("on-demand" mode scales to zero and back with no cold start, or provisioned mode with auto-scaling). Global Tables give multi-region active-active replication; Local and Global Secondary Indexes add query patterns beyond the primary key. Best for gaming backends, ad-tech/media metadata, and serverless architectures tightly integrated with Lambda/API Gateway. Not a fit for complex ad hoc queries/joins, heavy analytics, or cases where access patterns aren't well understood upfront.

Real-world example
DynamoDB originated from Amazon.com's own need to handle Prime Day-scale traffic and is still used extensively internally; Snap and Lyft are commonly cited production users for session/state data, and it's a frequent choice for shopping-cart-style and gaming-leaderboard workloads because it can scale throughput instantly during traffic spikes.
ProsCons
  • Fully serverless — no servers, patching, or capacity planning
  • Virtually unlimited horizontal scale at single-digit-millisecond latency
  • Flexible per-request consistency model (eventual or strong reads)
  • Global Tables enable multi-region active-active replication
  • Query flexibility limited — access patterns must be designed around keys/indexes upfront
  • AWS-only, creating vendor lock-in
  • Costs can be hard to predict without careful capacity/index planning
  • Item size limit (400 KB) constrains some use cases

Riak (Riak KV)

Open Source, Dynamo-Style Key-Value Store — built explicitly around the principles of Amazon's original Dynamo paper: consistent hashing, replication, and a strong bias toward write availability even during network failures. Basho Technologies, its original commercial steward, shut down in 2017; the project lives on mainly through the community-maintained OpenRiak fork. It's an AP-style system — reads/writes succeed as long as any replica is reachable — with conflicts resolved via vector clocks (Dotted Version Vectors are recommended over classic vector clocks because they dramatically reduce "sibling explosion") and CRDTs for automatic merge-friendly counters, sets, and maps. Best for applications that must never reject a write even during hardware/network failure and for multi-datacenter replication with graceful partition handling. Not recommended for new greenfield projects in 2026 given Basho's shutdown and the smaller OpenRiak community, or for anything needing strong immediate consistency or complex secondary querying.

Real-world example
Riak was historically used by companies including Comcast, GitHub (for some internal systems), the UK's NHS, and Bet365 for session storage and always-available caching layers, where "the write must always succeed" was a hard requirement — such as shopping-cart persistence during Black Friday-scale traffic.
ProsCons
  • Extremely fault-tolerant "always writable" design (true AP database)
  • Mature CRDT support for automatic conflict resolution
  • Dotted Version Vectors significantly reduce conflict bloat vs. classic vector clocks
  • Masterless ring architecture — no single point of failure
  • Original company (Basho) is defunct; ecosystem momentum has significantly declined
  • Smaller community/support than Cassandra, DynamoDB, or ScyllaDB today
  • Requires Erlang/OTP operational expertise, a rarer skill set
  • Weaker secondary indexing/querying than modern alternatives

etcd

Strongly Consistent Coordination Store — a distributed key-value store written in Go, best known as the backing store for Kubernetes' entire cluster state (configuration, service discovery metadata, scheduling data). It's purpose-built for storing small amounts of critical coordination/configuration data reliably, not general-purpose application data. It uses the Raft consensus algorithm — an elected leader replicating a log to followers — to give linearizable, strongly consistent (CP) reads and writes, plus a watch/notify API that lets clients subscribe to key changes (used heavily by Kubernetes controllers). It's designed for small, hot datasets (historically a few GB) and tolerates minority node failures, including leader failure via re-election, while remaining consistent. Best for distributed system configuration, service discovery, and leader election/locking primitives. Not a fit for general application data, large datasets, high-write-throughput workloads, or as a general cache/session store.

Real-world example
Every Kubernetes cluster relies on etcd as its single source of truth — all object definitions (pods, deployments, services, secrets) and cluster state live in etcd, with the API server and schedulers continuously reading and watching it to keep the cluster in its desired state.
ProsCons
  • Strong (linearizable) consistency guarantees via Raft
  • Highly reliable leader election and failure handling
  • Watch API enables efficient reactive/event-driven architectures
  • Proven at massive scale as Kubernetes' backbone
  • Not designed for large data volumes — explicitly a "small critical data" store
  • Consensus overhead limits write throughput vs. AP-style KV stores
  • Requires careful operations (disk latency sensitivity, cluster sizing)
  • Narrow use case — not a general-purpose database

Memcached

Multi-Threaded In-Memory Cache — a simple, open-source, high-performance caching system that stores data purely as string values indexed by string keys, with no persistence, no replication, and no built-in data structures beyond raw strings. Its entire design philosophy is "do one thing — caching — as fast and simply as possible." Storage is purely volatile (data is lost on restart, by design); the architecture is multi-threaded, so it can use multiple CPU cores natively, unlike Redis's traditionally single-threaded core; it uses LRU eviction when memory fills, and has no built-in clustering — scaling is done client-side via consistent hashing across independent instances. Best for simple, transient object caching (HTML fragments, API responses, DB query results) in stateless applications where raw speed and predictable latency matter more than features. Never a fit as a system of record, or for anything needing persistence, complex data structures, or replication/HA.

Real-world example
Facebook built one of the largest Memcached deployments in the world — thousands of servers caching trillions of items and serving billions of requests per second — to cache database query results and reduce load on backend MySQL clusters, documented in their "Scaling Memcache at Facebook" paper. Wikipedia and YouTube have also historically relied on Memcached for page/object caching at massive scale.
ProsCons
  • Extremely simple, easy to operate and reason about
  • Multi-threaded — fully utilizes multi-core servers out of the box
  • Very low and predictable latency, including at the tail (p99/p99.9)
  • Battle-tested at enormous scale (Facebook, Wikipedia, Twitter)
  • No persistence — a restart wipes the cache entirely
  • No native data structures beyond strings
  • No replication or built-in clustering/HA
  • Client-side sharding means no cluster-aware rebalancing

Aerospike

Hybrid-Memory, Real-Time NoSQL Database — a distributed database purpose-built for real-time workloads needing predictable, extremely low latency at massive throughput, common in ad-tech, fraud detection, and financial services. Its defining innovation is the Hybrid Memory Architecture (HMA): the primary index stays in RAM while record data lives on SSD, using direct SSD access that bypasses the filesystem — index lookups need zero disk I/O, and data reads typically need only a single I/O operation. That gives near in-memory speed at SSD-level cost efficiency and durability. It supports cross-datacenter replication and configurable strong or eventual consistency per namespace, scaling horizontally with automatic rebalancing. Best for ultra-low-latency, high-throughput workloads — real-time ad bidding/fraud detection, recommendation engines, telecom/finance user profile stores — needing millions of transactions per second on data too large or costly to keep fully in RAM. Not a fit for small applications where its operational complexity and licensing cost aren't justified.

Real-world example
Adjust, a global mobile app marketing/attribution platform, consolidated a struggling 40-node cluster down to just 6 nodes after migrating to Aerospike's Hybrid Memory Architecture, while handling real-time attribution data processing at their required scale.
ProsCons
  • Predictable, extremely low latency even at huge scale (millions of TPS)
  • Hybrid Memory Architecture is far more cost-efficient than all-RAM stores at large data volumes
  • Often needs far fewer nodes than comparable systems
  • Supports both strong and eventual consistency per use case
  • Smaller community/mindshare than Redis, Cassandra, or DynamoDB
  • Enterprise edition licensing costs can be significant
  • Requires specialized tuning knowledge (SSD configuration, namespace design)
  • Narrower "best fit" niche (real-time/high-throughput) vs. general-purpose use
Consistent hashing — how Riak (and DynamoDB) place keys across a cluster Each node owns a range of positions on a hash ring; a key K is stored starting at hash(K) and replicated clockwise to the next N−1 nodes, where N is the configured replication factor (Riak) or the number of Availability Zones a partition spans (DynamoDB).
Because ownership is determined purely by hash position, adding or removing a node only remaps the keys between it and its neighbors — not the entire keyspace — which is what lets both systems rebalance or scale out without reshuffling all the data.

Common Interview Questions

Why is Redis often described as more than "just" a key-value store?
Because Redis values can be rich data structures — lists, sets, sorted sets, streams, and even vectors — manipulated with atomic commands, so it functions as a cache, database, message broker, and vector store all at once, rather than a flat string-only key-to-value map.
Why would Kubernetes rely on etcd instead of Redis or DynamoDB for cluster state?
etcd's Raft-based consensus gives linearizable, strongly consistent reads and writes plus a watch API — Kubernetes needs one unambiguous source of truth for a small amount of critical data, not the raw throughput of Redis or the eventual-consistency defaults of DynamoDB.
What's the fundamental tradeoff between Riak's AP design and etcd's CP design?
Riak favors availability: writes and reads succeed as long as any replica is reachable, with conflicts resolved later via vector clocks/CRDTs. etcd favors consistency: it will refuse to serve a request rather than risk an ambiguous answer, at the cost of write throughput and availability during leader re-election.
Why does Aerospike's Hybrid Memory Architecture let it run on far fewer nodes than an all-RAM store like Redis?
HMA keeps only the (small) primary index in RAM while record data lives on SSD with direct access — index lookups need zero disk I/O and data reads need just one I/O operation — so the dataset's cost scales with SSD, not RAM. That's how Adjust went from 40 nodes down to 6 after migrating.
When would you choose DynamoDB over Redis or Memcached for a new service?
When you need a durable system of record — not just a cache — at effectively unlimited scale with zero operations burden. Redis and Memcached are optimized to sit in front of a source of truth; DynamoDB is designed to be the source of truth itself, with tunable consistency and multi-region Global Tables.

Key Takeaways

Remember
Key-value stores span a wide spectrum from purely disposable cache (Memcached) to versatile in-memory structure store (Redis), to fully durable managed system of record (DynamoDB), to hybrid-memory real-time database (Aerospike), to always-writable AP store (Riak), to narrowly-scoped strongly-consistent coordination store (etcd). The choice is rarely "key-value vs. not" — it's picking the point on that spectrum that matches your durability, consistency, and latency requirements.
