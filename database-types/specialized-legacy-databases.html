DATABASE TYPES

Specialized & Legacy Database Types

This page covers database systems that fall outside the mainstream relational / document-NoSQL / graph / vector buckets: in-memory engines, object-oriented databases, hierarchical and network model systems from the mainframe era, ledger/blockchain databases, multi-model databases, spatial/GIS databases, cloud-native/serverless/mobile-first databases, flat-file "databases," and OLAP data warehouses. Given how many named products this spans (25+), each gets a compact profile rather than the full callout-plus-pros/cons treatment used elsewhere on this site — enough to know what it is, why it exists, and when you'd actually reach for it in an interview answer.

1. In-Memory Databases

In-memory databases (IMDBs) keep the primary copy of data in RAM rather than on disk, trading some durability guarantees (or engineering around them) for dramatically lower latency and higher throughput. They matter because disk and even SSD I/O is orders of magnitude slower than RAM access, so anything latency-critical — caching, session state, real-time scoring, telecom billing — tends to gravitate here.

Redis and Memcached (as in-memory databases)

Redis and Memcached are covered in full on the Key-Value Stores page, since that's the more common lens for evaluating them, but architecturally both are in-memory databases first: Redis is an in-memory data-structure store that doubles as a cache, database, message broker, and streaming engine, while Memcached is a pure in-memory caching layer with a much narrower feature set. VoltDB, covered on the NewSQL Databases page, is also in-memory — an ACID-compliant, distributed SQL engine purpose-built for extreme-throughput real-time decisioning such as telecom billing, fraud detection, and ad-tech bidding. Best for latency-critical workloads that can tolerate (or engineer around) RAM's volatility; not the place to keep the only copy of data you can't afford to lose without additional persistence configuration.

SAP HANA

SAP HANA ("High-performance ANalytic Appliance") is an in-memory, column-oriented relational platform that runs OLTP and OLAP workloads against the same copy of data, eliminating the separate ETL pipeline into a data warehouse that most databases still require. Its column-store tables live in RAM for extreme scan/aggregation speed, with built-in predictive analytics, text search, spatial, and graph libraries layered on top, plus dynamic tiering to age cold data onto disk-based storage as it grows. It underpins SAP's S/4HANA ERP suite, and large SAP shops — including health systems running Mount Sinai's AI-Ready initiative — use it to run real-time financial closes and supply-chain analytics directly against live transactional data instead of waiting on an overnight batch load. Best for enterprises already standardized on SAP wanting fused OLTP+OLAP without a separate warehouse; a poor fit for cost-sensitive teams outside the SAP ecosystem, since licensing and memory-heavy hardware are expensive relative to disk-based or open-source alternatives.

2. Object-Oriented Databases

Object-oriented databases (OODBMS) store data as native objects — matching the object model of Java, C++, or .NET directly — instead of translating between rows/tables and in-memory objects (the "object-relational impedance mismatch"). They had a wave of popularity in the 1990s-2000s for CAD/CAM, telecom, and engineering applications, but broad adoption never matched relational databases, and most of the category survives only in niche or legacy form, especially once ORMs solved the same impedance-mismatch problem on top of relational databases instead.

db4o

db4o ("database for objects") was an open-source, embeddable object database for Java and .NET that let developers persist native objects directly with almost no mapping code, popular for embedded desktop and mobile apps in the 2000s. It offered a small footprint, Native Queries in the host language, and a SODA query API, with dual open-source/commercial licensing. Actian, which inherited db4o through its Versant acquisition, discontinued active commercial development and does not promote it for new customers, so it survives mainly in legacy codebases and community forks. Best for nothing new today — it's a historical example of zero-mapping object persistence, not a viable choice for a current project.

ObjectDB

ObjectDB is a commercial, JPA/JDO-compliant object database for Java that eliminates the relational mapping layer entirely, acting as a drop-in persistence provider for JPA-based applications. Unlike db4o, it remains actively developed, with 2.9.x releases continuing through 2025, making it the more viable modern choice in this category. It's used in Java-centric embedded and enterprise applications — engineering/CAD-adjacent tools and internal enterprise systems — as a lighter-weight alternative to running a full relational database purely to satisfy an ORM. Best for Java-only shops whose data model maps naturally onto an object graph; a poor fit for polyglot environments or teams wanting a large hiring pool and BI ecosystem.

Versant (Actian NoSQL / FastObjects)

Versant Object Database was a commercial OODBMS built for complex, highly interconnected object data — telecom network topologies, CAD models, scientific instrument metadata — optimized for traversing deeply nested object graphs far faster than repeated relational joins. Versant Corporation was acquired by Actian, and the product lives on as "Actian NoSQL"/FastObjects, still sold but firmly a niche specialist offering rather than a growth product. Large telecoms have used it in Operations Support Systems for network route-optimization, and scientific/medical instrument vendors for time-critical telemetry metadata. Best for legacy systems already built on it, or a very specific object-traversal-heavy niche; for any greenfield graph-shaped problem, a dedicated graph database (Neo4j, etc.) now serves the same need with a far larger ecosystem.

3. Hierarchical Databases

Hierarchical databases organize data as a tree — every record has exactly one parent (except the root), so children are reached only by traversing down from it, like a filesystem or a single-reporting-line org chart. The model predates the relational model (1970) and is fast and simple when data is genuinely tree-shaped, but it struggles with many-to-many relationships and ad hoc queries, which is why the relational model displaced it for general-purpose use; it survives almost entirely in mainframe environments where decades-old, extremely high-throughput systems were never worth the risk of rewriting.

IBM Information Management System (IMS)

IBM IMS is a joint hierarchical database and transaction-management system for z/OS mainframes, originally built in the 1960s for the Apollo program's bill-of-materials tracking and still in heavy production use today, with data organized strictly as parent-child segments. IMS TM handles transaction volumes with deterministic, low-latency performance tuned over 50+ years of mainframe optimization, and modern versions expose RESTful APIs for hybrid integration with cloud-native tools. It processes over 50 billion transactions daily across global financial institutions.

Real-world example
Atruvia AG, a major German banking-technology provider serving cooperative banks, uses IMS to process roughly 80 billion core banking transactions annually, with peak loads around 12,000 transactions per second — a scale and reliability bar that has kept banks from migrating off it despite its age.

Best for keeping existing mission-critical mainframe banking/insurance/airline systems running rather than rewriting them; essentially never the right choice for a brand-new system, since the hierarchical model can't naturally express many-to-many relationships and the COBOL/IMS talent pool is shrinking and aging out.

Windows Registry (as a hierarchical example)

The Windows Registry isn't a general-purpose DBMS, but it's one of the clearest, most familiar real-world examples of the hierarchical model: keys work like folders, subkeys like subfolders, and values hold the actual data, all anchored under root "hives" like HKEY_LOCAL_MACHINE and HKEY_CURRENT_USER. A path such as HKEY_LOCAL_MACHINE\Software\Microsoft\Windows is a direct hierarchical traversal, physically backed by hive files assembled into an in-memory tree at boot (trees can nest up to 512 levels, though real paths stay shallow). Microsoft's own engineers note it's hierarchical rather than relational precisely because configuration data is inherently tree-shaped and doesn't need cross-entity joins — illustrating both the model's appeal (fast, obvious traversal for nested data) and its limits (no ad hoc "find everything matching X regardless of location" queries, and awkward handling of many-to-many data).

4. Network Databases

The network model is the hierarchical model's more flexible sibling: a record can have multiple parents and multiple children, forming a graph-like web of "owner" and "member" record sets rather than a strict tree. Standardized in the late 1960s by CODASYL — the same committee that produced COBOL — it dominated mainframe business computing through the 1970s-80s before the relational model's simpler, declarative approach took over; it matters today mainly as the direct ancestor of ideas that resurfaced decades later in graph databases, and because a surprising amount of network-model-era code is still running in production.

CODASYL-style Databases and Integrated Data Store (IDS/IDMS)

Integrated Data Store (IDS) was created in 1964 at General Electric by Charles Bachman (later a Turing Award winner largely for this work) and became the primary technical input for CODASYL's 1969 network data model specification; it was later commercialized as IDMS and is today owned and still sold by Broadcom. Data is modeled as records connected via named "sets" allowing multiple parents, with navigational access — applications traverse the database procedurally via COBOL-embedded DML, following physical pointers, rather than issuing a declarative SQL query. It's extremely fast for pre-defined access paths since relationships are physical pointers rather than computed joins, but there's no equivalent of ad hoc querying, which is exactly what Codd's 1970 relational paper argued against and why virtually all new development moved to relational databases by the 1980s-90s. IDMS still runs mission-critical banking, insurance, and government transaction systems today (historical adopters include Aetna, Manulife, and Royal Insurance) — best understood as "keep the lights on" infrastructure rather than a model anyone would choose for new development, given the shrinking pool of COBOL/CODASYL-literate programmers.

5. Ledger / Blockchain Databases

Ledger databases apply blockchain-style ideas — an append-only, cryptographically verifiable history of every change — inside a conventional, centrally-operated database, without the mining, consensus overhead, or decentralization of a public blockchain. True blockchain platforms instead run the same ledger across multiple independent organizations that don't fully trust each other, using consensus protocols to agree on shared history; both solve "prove this data wasn't tampered with," but for different trust scenarios — one operator wanting internal tamper-evidence, versus multiple organizations needing a shared source of truth.

Amazon QLDB (Quantum Ledger Database) — retired

Amazon QLDB was a fully managed, serverless ledger database that maintained an immutable, cryptographically verifiable journal of every change, queryable via PartiQL, letting applications prove no entry had been altered. AWS discontinued it entirely, ending support on July 31, 2025, quietly steering customers toward Aurora PostgreSQL with the pgAudit extension, Database Activity Streams, and S3 archival as replacements — a live illustration that "ledger" capabilities can increasingly be layered onto a general-purpose relational database rather than requiring a dedicated product.

Tamper-evidence mechanism — cryptographic hash chaining digestn = hash(digestn-1 + transactionn)
Every new entry's digest folds in the previous entry's digest, so altering or deleting any historical transaction changes every digest computed after it. A customer or auditor can independently recompute the chain and instantly detect if a single byte of history was changed — the same core idea QLDB used internally, and the one public blockchains extend across multiple untrusted parties via consensus.
Real-world example
The UK's DVLA migrated its 48-million-driver, 40-million-vehicle registry to QLDB for its immutability and provenance guarantees when sharing data across government departments; Klarna Bank evaluated a full blockchain, decided decentralization was unnecessary complexity, and adopted QLDB instead; Liberty Mutual used it as a cryptographically-sequenced source of truth to decompose monolithic legacy processes. All three had to migrate off QLDB during 2024-2025 following AWS's discontinuation — a stark lesson in single-vendor niche-product risk.

Ledger databases in general make sense for regulator-facing audit trails, supply-chain provenance, and government registries needing independently verifiable integrity — but only when a plain RDBMS's audit logging/extensions genuinely aren't "good enough," and only with vendor longevity risk weighed heavily given QLDB's own fate.

Hyperledger Fabric

Hyperledger Fabric is an open-source, permissioned distributed ledger platform hosted by the Linux Foundation, built for enterprise consortiums that need a shared, tamper-evident ledger without a public/permissionless cryptocurrency-style network. Its modular architecture — pluggable consensus, membership services (MSP), and privacy-preserving "channels" — lets each consortium configure its own trust model, with smart contracts ("chaincode") written in Go, Java, or Node.js rather than a blockchain-specific language. It's used for medical data sharing between hospitals and insurers via channel-based privacy, and for supply-chain/trade-finance consortiums tracking letters of credit across multiple banks. Best for genuine multi-party trust problems where no single organization should control the ledger; a poor fit for single-organization systems or anything needing high throughput/low latency, since consensus and endorsement overhead make it slower than a conventional database.

BigchainDB

BigchainDB adds blockchain characteristics — decentralization, immutability, asset ownership/transfer semantics — on top of a distributed database core (historically MongoDB/Tendermint-based), aiming for database-like throughput and rich querying alongside blockchain-like tamper-evidence. It supports custom digital assets and fine-grained, transaction-level permissions, and is often paired with Hyperledger Fabric — Fabric supplying smart-contract business logic, BigchainDB supplying the asset ledger — as international trade-finance platforms have done to track goods, payments, and letters of credit across banks and trading partners. Best for digital-asset registries wanting rich queryability alongside tamper-evidence; not a fit for fully trustless/permissionless use cases, and its community/adoption remain far smaller than mainstream blockchain platforms or databases.

6. Multi-Model Databases

Multi-model databases support more than one data model — document, key-value, graph, column, relational — natively in a single engine rather than forcing separate specialized databases to run side by side. The pitch is fewer moving parts and the ability to combine query styles (a document lookup joined with a graph traversal) in one query language; the trade-off is that a purpose-built single-model database will often out-perform or out-feature the equivalent capability inside a generalist.

ArangoDB

ArangoDB is an open-source, natively multi-model database combining document, graph, and key-value storage in one engine, queryable through AQL so a single query can traverse a graph and filter document fields together; ArangoSearch adds integrated full-text search, and the Foxx framework lets developers run JavaScript microservices directly inside the database. AboutYou, an e-commerce retailer, used ArangoDB's multi-model design plus Foxx to build recommendation microservices in-database, reporting roughly 50% development-effort savings versus a more fragmented architecture. Best for applications needing both document flexibility and graph traversal in the same query — fraud detection, recommendation engines, tagged content management — but a purpose-built graph or document specialist will usually out-perform it at extreme single-model scale, and its community is smaller than MongoDB's or Neo4j's.

Azure Cosmos DB

Azure Cosmos DB is Microsoft's globally distributed, multi-model database offering multiple API surfaces — document/NoSQL Core API, MongoDB- and Cassandra-compatible, Gremlin graph, Table API — over one globally-replicated storage engine, with tunable consistency levels and SLA-backed single-digit-millisecond latency. Turnkey multi-region replication, automatic partitioning, and a 2025 "Burst IOPS" tier for spiky traffic make it popular with global retail and gaming companies needing consistent low-latency reads/writes across continents. Best for globally distributed applications wanting one managed service that speaks multiple API dialects with strong Azure integration; a poor fit for cost-sensitive, steady, single-region workloads, where Request Unit-based pricing and Azure lock-in are harder to justify.

Couchbase

Couchbase combines a high-performance key-value engine with JSON document storage, queryable via SQL++ (formerly N1QL), plus built-in full-text and vector search; Couchbase Mobile/Lite and Sync Gateway extend the same data model to offline-capable mobile and edge devices, and Couchbase Capella is the managed cloud offering. Large multi-location retail chains use its edge-to-cloud model to run point-of-sale and inventory systems in-store on Couchbase Lite — continuing to function during connectivity outages — while syncing back to a central Capella cluster once reconnected. Best for applications needing both fast key-value lookups and flexible document querying, especially offline-first mobile/edge scenarios; not the simplest choice for teams needing only one access pattern or complex multi-row ACID transactions across many entities.

FaunaDB (Fauna) — shut down in 2025

Fauna was a serverless, globally distributed, strongly consistent database blending document flexibility with relational features — referential integrity, ACID transactions, and its own FQL query language (later adding SQL-like access) — aimed at serverless/JAMstack developers. Fauna's leadership stated that driving adoption of a new operational database-as-a-service is extremely capital-intensive, and rather than risk running out of money later with even less notice, the company shut down the managed service entirely, ceasing to respond to queries on May 30, 2025 — affecting over 195 databases and 3,000+ development teams, who had roughly two months to migrate (commonly to Postgres-based serverless options like Neon or Supabase, or to DynamoDB/Cosmos DB). Alongside QLDB's discontinuation the same year, it's one of the clearest recent lessons that strong technology and design don't guarantee business viability for a niche, VC-funded, single-vendor managed database — best for nothing today, and a case study for why adopting a similar niche managed database should start with an exit/export plan.

7. Spatial / GIS Databases

Spatial (GIS) databases add geographic/geometric data types — points, lines, polygons — and specialized spatial indexes so queries like "find everything within 5 km of this point" run efficiently in the database itself rather than being computed slowly in application code. Most spatial capability today comes as an extension bolted onto an existing general-purpose database rather than a wholly separate engine, reflecting how mature and standardized (OGC — Open Geospatial Consortium) spatial SQL has become.

PostGIS

PostGIS is an open-source spatial extender for PostgreSQL, widely considered the most complete open-source implementation of the OGC Simple Features for SQL standard and the de facto standard for open-source geospatial work. It adds geometry/geography data types plus hundreds of ST_* functions for distance, intersection, buffering, and topology, backed by GiST-based spatial indexes, and integrates with mapping tools like Mapnik, QGIS, and Uber's H3 hex-grid system. OpenStreetMap's own rendering stack runs PostGIS with Mapnik, and it's described as proven at organizations including NASA for large-scale geospatial analysis.

Why spatial indexes matter — R-tree bounding-box pruning Naive "is point P within 5km of any of these n rows" lookup: O(n) — scan every row and compute distance.
With a GiST-based R-tree spatial index, the index groups nearby geometries into nested bounding rectangles, so a query can discard entire branches of non-overlapping rectangles without touching the rows inside them — turning most real-world proximity/containment queries into roughly O(log n) plus a handful of exact-distance checks on the surviving candidates.

Best for any team already on or considering PostgreSQL that needs geographic queries — nearest-store lookups, delivery-zone geofencing, logistics routing; a weaker fit for extremely large dedicated GIS/CAD workloads expecting commercial Esri/Oracle-grade desktop tooling, or very lightweight embedded/mobile use where SpatiaLite's smaller footprint fits better.

Oracle Spatial and Graph

Oracle Spatial and Graph is a set of features built into Oracle Database (and Autonomous Database) adding geospatial data types/functions alongside property-graph and RDF graph management, so enterprises can run spatial analysis, network analytics, and relational workloads on one converged database. Financial institutions use it to combine transaction-location clustering with relationship/network analysis for fraud detection inside a single Oracle Database, the same pattern used in utilities for network/asset location management. Best for large enterprises already licensing Oracle wanting spatial+graph analytics without standing up a separate platform; hard to justify for anyone without an existing Oracle footprint, since the features are tied to the commercial database license.

SpatiaLite

SpatiaLite is the spatial extension for SQLite — the spatial equivalent of "PostGIS, but for a single-file, zero-server database" — adding OGC-compliant spatial types and functions to SQLite's already-simple embedded model, with no server process required. Field researchers and small GIS consultancies commonly use it (often via QGIS) to collect and analyze geographic data on laptops or field devices without connectivity, merging results into a larger PostGIS system back at the office. Best for lightweight, single-user or offline-first GIS work — field data collection, desktop GIS tools, teaching; not designed for concurrent multi-user write workloads or large-scale enterprise geospatial systems, where PostGIS or Oracle Spatial's indexing and clustering sophistication wins out.

8. Cloud-Native / Serverless / Mobile-First Databases

This category groups databases designed around the modern app-development experience — little or no server management, automatic scaling (including scaling to zero), real-time sync to client devices, and usage-based pricing rather than pre-provisioned capacity. They target a different persona than a traditional DBA-managed database: usually a small team or solo developer who wants to ship a mobile/web app fast without standing up and tuning database infrastructure.

Firebase Realtime Database

Firebase Realtime Database is Google's original cloud-hosted NoSQL database, storing data as one large JSON tree and syncing it to every connected client in real time, with offline support and automatic reconciliation on reconnect — built for the "live, collaborative mobile app" use case rather than general-purpose querying. Early-stage mobile chat and multiplayer-lite apps used it specifically for instant, low-effort sync of small state like presence indicators and live scoreboards, letting small teams skip building custom WebSocket infrastructure. Best for simple real-time features in small-to-medium apps whose entire dataset reasonably fits a JSON tree; Google now positions Firestore as the more capable successor for most new projects, since complex filtering, pagination, and deep relationships get unwieldy in a flat JSON tree.

Google Firestore

Firestore is Google's newer serverless NoSQL document database — the intended successor to Realtime Database — organizing data into collections and documents with much richer querying, automatic scaling (including effectively scaling to zero cost when idle), and real-time listeners plus offline caching. Consumer mobile and web startups commonly use it as their entire backend, relying on automatic scaling and live listeners to power features like a shared to-do list that updates instantly across devices. Best for startups wanting real-time sync plus better querying than Realtime Database without managing infrastructure; the usage-based pricing model has produced well-documented surprise bills at scale, and it still lacks full SQL join flexibility, so teams wanting vendor portability may prefer Supabase or a self-managed Postgres.

Amazon Aurora Serverless

Amazon Aurora Serverless (now primarily v2) is an on-demand, auto-scaling configuration of AWS's MySQL/PostgreSQL-compatible Aurora that adjusts compute capacity in fine-grained Aurora Capacity Units within a fraction of a second of load changes, so customers pay for capacity actually consumed instead of provisioning for peak demand year-round. Retail and sports-event websites use it to absorb periodic promotional traffic spikes without provisioning peak-capacity infrastructure year-round, and dev/test teams run it for low-traffic environments to avoid paying for idle fixed-capacity instances; AWS reports cost savings up to roughly 90% for genuinely variable workloads. Best for bursty or unpredictable traffic wanting standard relational SQL semantics without a proprietary query language; a steady, always-high-load application is often cheaper on a fixed provisioned instance.

PlanetScale

PlanetScale is a serverless MySQL-compatible database platform built on Vitess — the horizontal-sharding technology originally created at YouTube — aimed at developers wanting standard MySQL semantics at massive scale (billions of rows) plus a Git-like schema-branching workflow for safer migrations. High-traffic Next.js applications deployed on Vercel commonly choose it specifically to avoid MySQL connection-limit exhaustion under bursty serverless function invocations, while keeping standard MySQL query semantics. Best for applications needing MySQL compatibility at very large scale without manually operating Vitess/sharding infrastructure; it's MySQL-only (no PostgreSQL option) and just a database, lacking the bundled auth/storage/functions of a full backend-as-a-service platform like Supabase or Firebase.

Supabase

Supabase is an open-source backend-as-a-service built around standard, full-featured PostgreSQL, adding authentication, auto-generated REST/GraphQL APIs, real-time subscriptions, storage, and edge functions — explicitly positioned as an open-source alternative to Firebase for teams wanting Firebase-like convenience without giving up SQL and vendor portability. Modern SaaS startups and indie developers choose it specifically to get Postgres's relational power (joins, JSONB, pgvector for AI/embedding features) plus built-in auth and real-time subscriptions in one platform, avoiding both Firebase's NoSQL constraints and the effort of hand-assembling Postgres + Auth0 + a separate storage service. Best for teams wanting Firebase-like development speed but needing full relational SQL power, open-source self-hosting, or Postgres-specific extensions; teams wanting the absolute path of least resistance with zero SQL knowledge may still find Firebase's document model simpler.

9. Flat-File / CSV "Databases"

A flat-file database stores data in a single plain-text file — CSV, TSV, or similar — one record per line, delimiter-separated fields, with no indexing, no enforced relationships between files, and no query engine; it's less a formal database than a simple, universally-readable data container. It's included here because it's genuinely how a huge amount of real-world small-scale and interchange data is stored, and understanding its limits is what motivates every other model in this document. Microsoft Outlook exporting a contact list as CSV for import into Google Contacts is the canonical one-time data-interchange use case, and many IoT devices and data pipelines write raw sensor readings to flat files as a landing format before loading into a proper warehouse or lake. Best for small, simple, single-user datasets, log/config files, or one-off data exchange where universal readability matters more than performance; anything with meaningful data volume, multi-user concurrent writes, cross-entity relationships, or integrity guarantees is exactly the gap the relational model was invented to close in the 1970s, and is why real applications graduate off a spreadsheet/CSV as soon as they need more than one concurrent user.

10. Data Warehouses / OLAP Systems

Every database in this document is optimized primarily for one of two very different jobs, and understanding the split is one of the most important organizing ideas in database technology. OLTP (Online Transaction Processing) — what most "databases" mean in daily conversation — is many short, simple read/write operations on one or a handful of rows at a time, prioritizing correctness and low-latency concurrent transactions, typically via row-oriented storage. OLAP (Online Analytical Processing) is the opposite shape: relatively few, but very large and complex, queries that scan and aggregate across millions or billions of historical rows, prioritizing scan throughput and parallel read performance, typically via column-oriented storage — so a query touching 5 of a table's 200 columns can skip reading the other 195 entirely. OLAP systems are usually fed by ETL/ELT pipelines from OLTP systems rather than written to directly by end-user transactions, and data warehouses are OLAP's flagship implementation.

Snowflake

Snowflake is a fully managed, cloud-native data warehouse built around a strict separation of storage and compute: data sits in cheap cloud object storage while independent, elastically-sized "virtual warehouses" run queries against it, so multiple teams can run different workloads concurrently without contending for the same compute. Retail and media companies commonly centralize sales, marketing, and product-usage data from many OLTP sources into Snowflake, letting separate finance, marketing, and product analytics teams run BI dashboards concurrently against the same data without competing for compute resources.

Storage/compute separation — the Snowflake/BigQuery cost model total_cost = storage_cost (cheap, $/TB/month, billed regardless of query activity) + compute_cost (billed only while a virtual warehouse runs, or per byte scanned per query)
Because the two are decoupled, a company can keep petabytes of historical data sitting cheaply and pause compute entirely when nobody is querying it — the opposite of a traditional provisioned OLTP database, where compute and storage are bundled into one instance size paid for around the clock whether or not it's busy.

Best for centralizing analytics/BI across many source systems needing concurrent, independent compute; not designed for OLTP-style high-frequency single-row writes, and costs can grow quickly if virtual warehouses are left running or sized inefficiently.

Google BigQuery

BigQuery is Google Cloud's fully serverless data warehouse — there's no cluster to size or manage at all — with pricing based primarily on bytes scanned per query (or purchased flat-rate "slots" for predictable costs), native handling of nested/semi-structured data in SQL, and deep integration with Looker, Google Analytics/Ads, and Vertex AI. Digital marketing and ad-tech companies commonly pipe Ads/Analytics data directly into BigQuery for campaign analysis, taking advantage of serverless scaling to run ad hoc queries ranging from small daily checks to huge end-of-quarter reports without pre-provisioning any capacity. Best for teams wanting zero infrastructure management and tight Google Cloud integration; poorly structured, unpartitioned queries can become surprisingly costly under bytes-scanned pricing, and very high constant query volume may be cheaper on flat-rate slots or a provisioned alternative.

Amazon Redshift

Amazon Redshift is AWS's managed, column-oriented data warehouse offering both traditional provisioned clusters and a serverless option, plus Redshift Spectrum for querying data directly in S3 without loading it into the warehouse first, all with massively parallel processing across compute nodes. AWS-centric enterprises commonly use it as the central warehouse for BI reporting fed by ETL/ELT pipelines from application databases and S3 data lakes, using Spectrum to query historical/raw S3 data alongside actively-loaded warehouse tables without duplicating it. Best for organizations already standardized on AWS wanting a warehouse tightly integrated with S3-based data lakes; a poor fit for OLTP workloads, multi-cloud strategies wanting to avoid AWS lock-in, or teams without distribution-key/sort-key tuning expertise.

Common Interview Questions

Why were hierarchical and network databases replaced by relational databases for general-purpose application development?
Both models require the application to know the physical structure of relationships in advance — hierarchical databases force a strict one-parent tree, network/CODASYL databases require navigating explicit pointers via procedural DML. Neither supports ad hoc, declarative queries. Codd's 1970 relational model separated the logical data model from physical storage and let programmers issue declarative SQL instead of hand-coding navigation paths — simpler for programmers and far more adaptable to questions nobody anticipated at schema-design time, which is why virtually all new development moved to relational databases by the 1980s-90s. Both models survive today almost entirely as "keep the lights on" mainframe systems (IBM IMS, Broadcom's IDMS) too risky or costly to migrate off.
When would you actually choose a dedicated ledger or blockchain database over a normal RDBMS with audit logging?
Almost never for a single trusted operator — a relational database's audit extensions (pgAudit, temporal tables, database activity streams) can usually deliver "good enough" tamper-evidence without a specialized product, which is exactly the alternative AWS pointed QLDB customers toward when it retired the service in 2025. A dedicated ledger database earns its keep only when you need independently verifiable cryptographic proof for regulators or external parties. A full blockchain platform like Hyperledger Fabric is justified only when there's a genuine multi-party trust problem — multiple organizations that don't fully trust each other needing a shared, auditable history — since consensus/endorsement overhead makes it meaningfully slower than a conventional database.
What does a multi-model database (ArangoDB, Cosmos DB, Couchbase) trade away compared to specialized single-model systems?
Multi-model databases consolidate document, graph, key-value, or column capabilities into one engine and query language, reducing operational surface area and letting a single query combine, say, a document filter with a graph traversal. The trade-off is that a purpose-built specialist — a dedicated graph database for pure graph problems, a dedicated document store for pure document problems — will typically out-perform or out-feature the equivalent capability inside a generalist at extreme scale, and the multi-model product's community/ecosystem (ArangoDB vs. MongoDB or Neo4j, for instance) is usually smaller. It's the right trade for teams consolidating what would otherwise be two or three separate databases into one; it's the wrong trade for a single, very large, very specialized workload.
Why did serverless/cloud-native databases (Firestore, Aurora Serverless, PlanetScale, Supabase) change the operational model for running a database?
Traditional databases require capacity planning: sizing an instance or cluster for peak load and paying for it around the clock whether or not it's busy, plus a DBA-managed patching/scaling/failover process. Serverless databases instead auto-scale compute in fine-grained increments (Aurora Serverless's Aurora Capacity Units react in a fraction of a second) or eliminate provisioning entirely (Firestore scales to zero cost when idle), billing for actual usage. This shifts the operational burden from the customer to the vendor and can cut costs dramatically for variable/bursty workloads (AWS reports up to roughly 90% savings for Aurora Serverless) — but it also introduces new failure modes, like Firestore's well-documented surprise bills when usage-based pricing meets an unexpectedly popular feature.
Why do OLAP data warehouses like Snowflake and BigQuery separate storage from compute instead of bundling them like a traditional OLTP database?
A traditional provisioned database bundles storage and compute into one instance size, so you pay for peak compute capacity continuously even when nobody's querying. Snowflake and BigQuery instead price storage cheaply and continuously (bytes sitting in object storage) while billing compute only while a query or virtual warehouse actually runs — letting a company keep years of historical data cheaply on disk while pausing compute entirely between analytics runs, and letting multiple teams spin up independent compute clusters against the same underlying data without contending for resources. This mirrors the broader OLTP/OLAP split: OLTP prioritizes always-on, low-latency single-row access (bundled capacity makes sense), while OLAP's bursty, scan-heavy analytical queries are exactly the pattern decoupled, elastic compute was designed for.

Key Takeaways

Remember
This page's ten categories mostly exist to solve one of two problems relational databases historically didn't: an access-pattern or data-shape mismatch (in-memory speed, object-graph traversal, tree/network navigation, spatial proximity, OLAP-scale aggregation), or an operational-model mismatch (wanting zero server management instead of a DBA-tuned instance). The two 2025 shutdowns covered here — Amazon QLDB (retired July 31, 2025) and FaunaDB (shut down May 30, 2025) — are the sharpest lesson: elegant, technically sound niche databases can still fail commercially, and both companies' own guidance was to migrate onto mainstream, well-supported platforms (Aurora PostgreSQL, Postgres-based alternatives). Before adopting any specialized or single-vendor database in this list, weigh whether a mainstream relational or NoSQL database with the right extension (pgAudit, PostGIS, pgvector) already gets you most of the benefit with none of the vendor-durability risk.
