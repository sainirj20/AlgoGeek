DATABASE TYPES

Vector Databases

Overview

Traditional databases search by exact or range matches: a name equals a string, a date falls in a range, a keyword appears in a document. But modern AI embedding models can convert text, images, audio, or any other content into a "vector embedding" — a list of hundreds to thousands of floating-point numbers that captures the semantic meaning of that content, such that similar meanings produce nearby vectors in that high-dimensional space. A query for "heart attack symptoms" and a document about "myocardial infarction" will produce vectors that are close together even though they share no keywords.

Why Vector Databases Exist Now

Vector databases exist to store millions or billions of these embeddings and answer the question "which stored vectors are closest to this query vector?" extremely fast, using approximate nearest neighbor (ANN) algorithms — like HNSW or IVF — that trade a small amount of accuracy for massive speed gains at scale, since an exact nearest-neighbor scan across billions of vectors would be far too slow. This capability exploded in importance starting around 2023-2026 because of the rise of large language models and specifically Retrieval-Augmented Generation (RAG): instead of relying only on what an LLM memorized during training (which goes stale and can hallucinate), RAG systems embed a knowledge base, retrieve the most semantically relevant chunks for a user's question via vector search, and feed that retrieved context into the LLM's prompt — grounding its answer in real, current, trusted data. The same core capability also powers semantic search, recommendation engines, image/audio similarity search, anomaly detection, and AI agent memory.

Cosine similarity & ANN search complexity similarity(A, B) = (A · B) / (‖A‖ × ‖B‖)  —  dot product of two vectors divided by the product of their magnitudes; result ranges from −1 (opposite) to 1 (identical direction)
Exact nearest-neighbor scan: O(N) distance calculations against every stored vector
Approximate nearest neighbor (e.g. HNSW's layered graph traversal): roughly O(log N) — trades a small amount of recall for a massive speedup at billion-vector scale
Real-world example
A customer-support AI assistant stores embeddings of thousands of help-center articles in a vector database, retrieving the most relevant three or four articles for a user's question and feeding them into an LLM prompt so the chatbot's answer is grounded in the company's actual documentation rather than the model's general training knowledge.

Named Products

Pinecone

Fully Managed / Serverless Vector Database — purpose-built for production AI applications, designed so teams never have to think about indexing, scaling, or infrastructure. One of the most widely adopted managed vector database solutions, used by companies including Notion, Gong, and Vanguard to power semantic search, RAG, and recommendation systems. Supports top-k nearest-neighbor search with metadata filters, plus "Pinecone Inference" (2025), which lets you pass raw text and have Pinecone generate embeddings automatically. Fully serverless with automatic scaling to millions/billions of vectors; 2025-2026 additions include BYOC (Bring Your Own Cloud, public preview on AWS/GCP/Azure) and Dedicated Read Nodes for predictable low-latency performance. Best for production RAG applications, AI agents, and semantic search systems wanting zero infrastructure management and elastic, usage-based scaling. Not the right fit for cost-sensitive early-stage prototypes, or teams that must keep data entirely within their own infrastructure beyond the BYOC preview.

Real-world example
A SaaS company like Notion uses vector search to let users search their workspace using natural language rather than exact keyword matches — the same pattern a customer-support AI assistant uses to retrieve and ground its answers in real help-center content instead of relying only on the model's training knowledge.
ProsCons
  • Fully managed and serverless — no infrastructure, indexing, or scaling operations required
  • Proven at large scale in production for RAG and semantic search
  • Built-in embedding generation (Pinecone Inference) simplifies the pipeline
  • Strong enterprise features: BYOC, dedicated read nodes, metadata filtering, real-time updates
  • Fully managed means less control and potential vendor lock-in versus self-hosted options
  • Can become expensive at very large scale or with constant high query volume
  • Data resides in Pinecone's managed cloud by default (BYOC is still in preview for broader availability)
  • No free self-hosted/open-source option — always dependent on Pinecone's service

Milvus

Open-Source, Cloud-Native, Distributed Vector Database — purpose-built for managing, indexing, and searching massive collections of embeddings with low latency, even across billions of vectors. Offers multiple search modes (pure ANN, filtered, range, hybrid multi-vector, and BM25-based full-text) and supports several indexing algorithms (IVF, HNSW, ANNOY) to balance speed and accuracy. Cloud-native, distributed architecture separates storage and compute, with hot/cold data tiering for cost efficiency at scale. Best for large-scale RAG systems, recommendation engines matching user vectors against item vectors, and fraud/anomaly detection; teams needing an open-source, self-hostable vector database that scales to billions of vectors with enterprise-grade distributed architecture. Not the right fit for small projects/prototypes where the operational complexity of a distributed system is unwarranted.

Real-world example
A large e-commerce or streaming platform can use Milvus to power real-time recommendations — embedding both users and products/content into vectors and using nearest-neighbor search to serve "recommended for you" results — while the same deployment doubles as an anomaly/fraud detection layer, flagging transactions whose embeddings sit unusually far from normal-behavior clusters.
ProsCons
  • Fully open-source with a mature, purpose-built distributed architecture for billion-scale vector search
  • Multiple index types (IVF, HNSW, ANNOY) let teams tune the speed/accuracy tradeoff
  • Rich search modes: hybrid, filtered, range, and full-text (BM25) alongside pure vector ANN
  • Managed cloud option (Zilliz Cloud) available for teams that don't want to self-host
  • Operationally more complex to self-host than lightweight alternatives like Chroma or pgvector
  • Steeper learning curve given its many configuration options (index types, tiering, sharding)
  • Requires more infrastructure investment to realize its billion-scale benefits
  • Smaller teams may find it "more database than they need" for modest-scale projects

Weaviate

Open-Source, Cloud-Native, Hybrid-Search-Focused Vector Database — stores both the original objects (as structured data) and their vector embeddings together, combining vector similarity search with structured filtering and standard database fault-tolerance/scalability. Particularly known for strong, well-integrated hybrid search (combining keyword/BM25 with vector similarity) and built-in RAG/generative-search capabilities. Hybrid search lets you tune an "alpha" parameter to blend keyword and vector results (alpha=1 is pure vector, alpha=0 is pure keyword); can automatically vectorize data at import time via integrated modules (OpenAI, Cohere, HuggingFace, Google). Best for RAG systems and chatbots needing both semantic and exact-keyword matching in one query, and teams wanting integrated auto-vectorization instead of managing a separate embedding pipeline. Not the right fit for extremely simple, pure-vector-only use cases, or teams wanting the absolute largest-scale billion-vector deployments (Milvus is more purpose-built there).

Real-world example
A customer support chatbot or e-commerce search bar commonly uses Weaviate's hybrid search so a query like "wireless noise cancelling headphones under $100" returns results matching both the exact keywords (price constraint, product type) via BM25 and semantically similar items via vector search — then Weaviate's built-in RAG/reranking module can generate a natural-language summary of the top matches directly.
ProsCons
  • Best-in-class, easily tunable hybrid search (keyword + vector) via a simple alpha parameter
  • Built-in generative search (RAG) and reranking reduce the need for extra integration glue
  • Integrated vectorizer modules simplify the embedding pipeline
  • Cloud-native architecture with strong fault tolerance and horizontal scalability
  • Additional modules/integrations can add complexity and cost if not needed
  • Pricing/packaging has changed multiple times, complicating planning
  • Smaller raw billion-scale track record compared to Milvus for the most extreme deployments
  • GraphQL-based query interface has a learning curve for unfamiliar teams

Chroma

Open-Source, Developer-First, Embedded/Lightweight Vector Database — designed to be the simplest possible way to get started with embeddings, especially for RAG and semantic search prototypes. Its 2025 Rust-core rewrite delivered roughly 4x faster writes/queries and removed Python's Global Interpreter Lock bottleneck, enabling it to scale toward billion-scale embeddings while keeping its "pip install and go" developer experience. Can run embedded/in-process for prototyping or as a standalone server; integrates directly with popular embedding providers and frameworks (PyTorch, Hugging Face, LangChain, LlamaIndex). Best for prototyping RAG applications, small-to-medium semantic search projects, and local development where a developer wants the fastest path from "I have some documents" to "I can semantically search them." Not the right fit for very large-scale, high-throughput production deployments needing advanced multi-tenant isolation or proven billion-vector distributed scale.

Real-world example
An individual developer or small team building an internal "chat with your documents" tool or an LLM-powered code-repair assistant commonly reaches for Chroma first — embedding a folder of PDFs, code, or notes and standing up semantic search or a RAG pipeline in a few lines of Python, without provisioning separate database infrastructure.
ProsCons
  • Extremely easy to get started — minimal setup, great for prototyping and small production apps
  • 2025 Rust rewrite significantly improved performance (roughly 4x faster) and removed Python GIL bottlenecks
  • Open-source and free to self-host with no licensing cost
  • Strong integration with popular LLM app frameworks (LangChain, LlamaIndex) and embedding providers
  • Historically viewed as less proven at extreme production scale than Milvus, Qdrant, or Pinecone
  • Smaller enterprise feature set (advanced security, multi-tenancy, compliance) than mature commercial options
  • Newer Rust-core architecture means some production battle-testing is still accumulating
  • Fewer managed/enterprise deployment options historically, though improving with Chroma Cloud

Qdrant

Open-Source, High-Performance, Rust-Based Vector Database — built entirely in Rust with SIMD optimizations and a custom storage engine (Gridstore), designed for production-grade AI workloads with an emphasis on advanced retrieval quality, resource efficiency, and enterprise deployment flexibility. Data is organized as "points" containing a vector (or multiple vectors) plus a JSON payload for metadata filtering; REST and gRPC APIs support rich filtering, hybrid dense-sparse retrieval, and reranking (Score-Boosting Reranking, Maximal Marginal Relevance for diversity). Horizontally scalable clustering with GPU-accelerated indexing and quantization (scalar, product, and binary) that can reduce memory usage by up to 64x while preserving search quality. Best for production RAG and generative AI applications needing hybrid dense-sparse retrieval with advanced metadata filtering, AI agents needing persistent fast-access memory, and teams wanting strong price/performance via aggressive quantization. Not the simplest zero-config starting point — Chroma onboards faster for a first prototype.

Real-world example
An AI agent platform can use Qdrant to give each agent persistent, fast-access "memory" — storing embeddings of past interactions, retrieved documents, and tool outputs — taking advantage of Qdrant's binary quantization to keep memory costs low even as the interaction history grows into millions of records.
ProsCons
  • Rust-based architecture with SIMD delivers strong raw performance and efficiency
  • Aggressive quantization options (down to binary) yield very high memory savings with limited quality loss
  • Rich, production-grade retrieval features: hybrid search, MMR diversity reranking, advanced filtering
  • Flexible deployment: self-hosted open source, or Qdrant Cloud managed service
  • More configuration knobs (quantization types, index tuning) than simpler alternatives
  • Smaller ecosystem/mindshare historically than Pinecone or Milvus, though rapidly growing
  • Self-hosting at large scale still requires meaningful operational expertise
  • Some advanced enterprise features are part of the commercial/cloud tier rather than free open-source

pgvector (PostgreSQL Extension)

Vector Search as a Relational Database Extension — an open-source PostgreSQL extension that adds a native vector data type and similarity-search operators, effectively turning an existing PostgreSQL database into a vector database rather than adopting a brand-new specialized system. Standard SQL is extended with distance operators for L2 (Euclidean), inner product, and cosine distance. Exact nearest-neighbor search by default (perfect recall); optional HNSW or IVFFlat indexes trade some recall for speed. Benchmarks show sub-20ms queries at 1M vectors with 95%+ recall. Best for applications already built on PostgreSQL that want to add semantic search or RAG capability without introducing a new database system — especially when combining vector similarity with normal SQL joins/filters in the same query matters; teams prioritizing operational simplicity over squeezing out maximum vector-search scale. Not the right fit for hundreds of millions to billions of vectors or very high-QPS workloads, where a purpose-built distributed vector database will outperform a single PostgreSQL instance.

Real-world example
A SaaS company that already stores its customers, documents, and support tickets in PostgreSQL can add a vector column to its "support_articles" table, generate embeddings for each article, and run a single SQL query that finds semantically similar help articles for a customer's question and filters by their subscription tier — all in one query against their existing database, with no new infrastructure.
ProsCons
  • No new database to operate — natural extension of an existing PostgreSQL deployment
  • Combines relational and vector queries in a single SQL statement/transaction
  • Fully open-source with a large, mature PostgreSQL ecosystem (backups, replication, monitoring reused)
  • Sufficient performance (sub-20ms, 95%+ recall at ~1M vectors) for most real-world RAG/search use cases
  • Not built to match the raw scale/throughput ceiling of purpose-built distributed vector databases
  • HNSW/IVFFlat index build times and memory usage can become significant at large scale
  • Fewer advanced vector-specific features (hybrid search tooling, built-in reranking) than dedicated engines
  • Requires PostgreSQL expertise to tune effectively alongside vector-specific tuning

Common Interview Questions

How is cosine similarity computed, and why is it commonly used for embeddings?
Cosine similarity is the dot product of two vectors divided by the product of their magnitudes: similarity(A, B) = (A·B) / (‖A‖×‖B‖). It measures the angle between vectors rather than their raw magnitude, which suits embeddings well since two pieces of content with the same semantic direction should be considered similar even if one embedding vector happens to have a larger norm.
Why do vector databases use approximate nearest neighbor (ANN) search instead of exact search?
An exact nearest-neighbor scan compares the query vector against every stored vector — O(N) cost — which becomes far too slow at billions of vectors. ANN algorithms like HNSW build a navigable graph structure that lets a query traverse roughly O(log N) steps to find very likely (though not guaranteed) nearest neighbors, trading a small amount of recall for a massive speedup.
Why does Retrieval-Augmented Generation (RAG) need a vector database?
An LLM's training data goes stale and it can hallucinate facts it never saw. RAG embeds a knowledge base into vectors, retrieves the chunks whose embeddings are closest to the embedded user question via vector search, and feeds that retrieved context into the LLM's prompt — grounding the answer in real, current, trusted data instead of relying purely on what the model memorized.
When is pgvector enough, and when do you need a dedicated vector database like Milvus or Pinecone?
pgvector is enough when an application already runs on PostgreSQL, needs to combine vector similarity with normal relational joins/filters in the same query, and stays in the range of roughly a million vectors with sub-20ms latency requirements. Beyond that — hundreds of millions to billions of vectors, or very high query throughput — a purpose-built distributed vector database will outperform and out-scale a single PostgreSQL instance.
What does Weaviate's hybrid-search "alpha" parameter control?
Alpha blends keyword (BM25) and vector similarity results in a single hybrid query: alpha=1 returns pure vector/semantic search results, alpha=0 returns pure keyword search results, and values in between mix the two — useful for a query like a product search that needs to match an exact price/brand constraint (keyword) while also surfacing semantically similar items (vector).

Key Takeaways

Remember
Vector databases exist to answer "which stored embeddings are closest to this query embedding," using ANN algorithms like HNSW to make that fast at billion-vector scale — the capability that grounds modern RAG. Pinecone offers the most hands-off managed experience; Milvus and Qdrant are open-source engines built for large-scale, high-performance production deployments; Weaviate stands out for tunable hybrid keyword+vector search and built-in RAG; Chroma is the fastest path from prototype to working semantic search; pgvector is the right call when you'd rather extend an existing PostgreSQL database than run a new specialized system.
