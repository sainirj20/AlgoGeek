SPRING

Interview Questions

A comprehensive bank of Spring and Spring Boot interview questions, aimed at intermediate-to-advanced Java engineers, spanning the areas interviewers actually probe: the Core IoC container and dependency injection, Spring Boot's auto-configuration and externalized configuration model, building REST APIs with Spring MVC, persistence with Spring Data JPA, securing applications with Spring Security, cross-cutting concerns with AOP, and the testing tools and strategies used to verify all of the above.

Spring Core (IoC & DI)

The Inversion of Control container and Dependency Injection are the foundation everything else in Spring is built on top of. These questions probe whether you understand what the container actually does when it starts up, why constructor injection is preferred over the alternatives, how bean scopes and the bean lifecycle work, and how the container resolves — or fails to resolve — ambiguity and circular references between beans.

What is the IoC container, and how does Dependency Injection relate to it?
Inversion of Control is the principle that an object no longer constructs or looks up its own collaborators — control over creating and wiring dependencies is handed to an external container. In Spring, that container is the ApplicationContext: at startup it reads configuration (annotations, Java config, or XML), instantiates the beans it discovers, and injects each bean's declared dependencies into it. Dependency Injection is simply the mechanism the container uses to fulfill IoC — instead of a class calling new on its dependencies, the container supplies them (via constructor, setter, or field), which decouples classes from the concrete creation of their collaborators and makes them trivially substitutable in tests.
What is the difference between BeanFactory and ApplicationContext?
BeanFactory is the root container interface — it provides basic DI and lazily instantiates beans only when first requested. ApplicationContext extends it and is what virtually every real application uses, adding:
  • Eager instantiation of singleton beans at startup (fail fast on misconfiguration).
  • Event publication (ApplicationEventPublisher).
  • Internationalization support via MessageSource.
  • Integration with AOP and the Environment abstraction (profiles, property sources).
Under Spring Boot you rarely construct either directly — SpringApplication.run() builds and configures a suitable ApplicationContext for you.
What are the different ways to perform Dependency Injection in Spring, and which is recommended?
  • Constructor injection (recommended) — dependencies are passed via the constructor. This lets fields be final, makes required dependencies impossible to forget, and means the object can never exist in a partially-wired state. It's also the easiest to unit test, since you can construct the class with plain mocks and no Spring context at all.
  • Setter injection — used for genuinely optional dependencies that can be reconfigured after construction.
  • Field injection (@Autowired directly on a field) — discouraged: it hides a class's real dependencies from its public API, prevents fields from being final, requires reflection (or a running Spring context) to test, and lets circular dependencies compile silently instead of failing fast.
@Service
public class OrderService {
    private final PaymentClient paymentClient;   // final -> must come via constructor

    public OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}
What are the Spring bean scopes?
  • singleton (default) — exactly one shared instance per container.
  • prototype — a brand-new instance is created every time the bean is requested from the container; Spring does not manage its destruction.
  • request — one instance per HTTP request (web-aware context only).
  • session — one instance per HTTP session.
  • application — one instance per ServletContext.
  • websocket — one instance per WebSocket session.
The web-aware scopes require a web ApplicationContext and typically need a scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS) so a singleton-scoped collaborator can hold a reference to them safely.
Explain the lifecycle of a Spring bean.
  • The container instantiates the bean and injects its dependencies.
  • Aware callbacks run if implemented (BeanNameAware, BeanFactoryAware, ApplicationContextAware).
  • Any registered BeanPostProcessor.postProcessBeforeInitialization hooks run (this is where @Autowired/@Value resolution and proxy creation for AOP actually happen).
  • Initialization callbacks run, in order: @PostConstruct method, afterPropertiesSet() if the bean implements InitializingBean, then any custom init-method.
  • BeanPostProcessor.postProcessAfterInitialization runs, and the fully-initialized bean is handed back for use.
  • On container shutdown, destruction callbacks run in order: @PreDestroy, destroy() if the bean implements DisposableBean, then any custom destroy-method. Note prototype-scoped beans are not tracked for destruction — the container hands them off and forgets them.
What is the difference between @Qualifier and @Primary?
Both resolve the ambiguity of injecting a type that has multiple bean candidates, which otherwise fails with NoUniqueBeanDefinitionException. @Primary marks one bean as the default candidate whenever a specific one isn't requested — useful when one implementation should win in the common case. @Qualifier("beanName") is applied at the injection point itself to name exactly which bean should be wired there, and takes precedence over @Primary — useful when different consumers legitimately need different implementations of the same interface.
What is a circular dependency, and how does Spring resolve or report it?
A circular dependency is when two or more beans depend on each other, directly or transitively (bean A needs bean B, and B needs A). For singleton beans using setter or field injection, Spring can resolve this: it uses a three-level cache of "early" bean references so it can hand out a reference to a not-yet-fully-populated bean while it finishes constructing the other one, then completes both. For constructor injection, this is not resolvable — Spring cannot hand out a reference to an object that hasn't finished being constructed yet — and it fails fast at startup with BeanCurrentlyInCreationException.

Fixes: redesign to break the cycle (often the real signal of a design problem — extract the shared behavior into a third bean, or use an event/callback instead of a direct reference), switch one side to setter injection, or add @Lazy to one of the constructor parameters so its resolution is deferred until first use.
What's the difference between @Component, @Service, @Repository, and @Controller?
All four are stereotype annotations picked up by component scanning, and @Component is the generic base that the other three specialize. The specializations mainly communicate intent, but two of them add real behavior:
  • @Repository enables persistence exception translation — a registered PersistenceExceptionTranslationPostProcessor wraps the bean so that JPA/JDBC/Hibernate-specific exceptions are translated into Spring's consistent DataAccessException hierarchy.
  • @Controller marks a presentation-layer bean that DispatcherServlet routes HTTP requests to; @RestController is @Controller plus @ResponseBody applied at the class level.
  • @Service carries no extra framework behavior beyond @Component — it exists purely to document the service/business layer.

Spring Boot

Spring Boot's job is to make Spring's power usable without hand-assembling dozens of beans. These questions test whether you understand the mechanics behind the "magic" — how auto-configuration actually decides what to configure, how starters and externalized configuration work, and what production-readiness features Boot gives you for free.

What problem does Spring Boot solve that plain Spring didn't?
Plain Spring required assembling and wiring infrastructure beans by hand (data sources, view resolvers, message converters, an external servlet container and WAR packaging) and manually managing compatible dependency versions across a large graph of libraries. Spring Boot adds an opinionated, convention-over-configuration layer on top: auto-configuration wires sensible defaults for you, starters bundle known-compatible dependency sets, an embedded servlet container (Tomcat/Jetty/Undertow) lets you ship a self-contained runnable JAR instead of deploying to an external app server, and Actuator gives you production monitoring endpoints out of the box.
What is @SpringBootApplication, and what does it actually expand to?
It's a meta-annotation combining three annotations that would otherwise have to be applied individually:
  • @SpringBootConfiguration (itself a specialization of @Configuration) — marks the class as a source of bean definitions.
  • @EnableAutoConfiguration — triggers Spring Boot's auto-configuration mechanism.
  • @ComponentScan — scans for components starting at the package containing the annotated class (which is why the main class conventionally sits at the top of the application's base package).
How does auto-configuration actually work under the hood?
@EnableAutoConfiguration tells Spring Boot to load a set of @Configuration classes registered in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (the successor to the older spring.factories mechanism). Every one of those classes is guarded by conditional annotations, so only the ones applicable to what's actually on the classpath and already configured end up contributing beans — auto-configuration doesn't blindly register everything it knows about, it register only what's relevant and not already overridden.
What do @ConditionalOnClass and @ConditionalOnMissingBean do, and why do they matter?
These are the two conditional annotations that make auto-configuration both safe and overridable.
  • @ConditionalOnClass(SomeDriver.class) — the configuration only activates if that class is present on the classpath. This is how, for example, a DataSource auto-configuration only kicks in when a JDBC driver dependency is actually present.
  • @ConditionalOnMissingBean — the auto-configured bean is only registered if the user hasn't already defined one of that type themselves. This is the exact mechanism that lets you "override" Spring Boot's defaults — just declare your own @Bean, and the auto-configured one silently steps aside.
What are Spring Boot starters?
Starters (spring-boot-starter-web, spring-boot-starter-data-jpa, spring-boot-starter-security, etc.) are dependency descriptors with no code of their own — they exist purely to pull in a curated, tested set of transitive dependencies known to work together at compatible versions for a given use case, sparing you from manually hunting down and pinning every individual library version and avoiding classpath conflicts.
How does Spring Boot handle externalized configuration, and what's the precedence order?
Configuration can come from application.properties/application.yml, profile-specific variants (application-{profile}.yml), environment variables, command-line arguments, and more — collectively exposed through the Environment abstraction. Roughly in order of highest to lowest precedence: command-line arguments, then environment variables, then profile-specific application config, then the base application.yml, then defaults defined in code. Profiles are activated with spring.profiles.active, and beans can be restricted to a profile with @Profile("dev").
What is @ConfigurationProperties, and how is it different from @Value?
@ConfigurationProperties(prefix = "app.mail") binds an entire hierarchy of related properties onto a strongly-typed POJO in one shot — including nested objects, lists, and maps — with relaxed binding (app.mail.from-address maps to a fromAddress field) and can be paired with @Validated for startup-time validation. @Value("${app.mail.host}") injects one property expression at a time and supports SpEL, but doesn't scale to structured configuration or validate as a group. Prefer @ConfigurationProperties for anything beyond a couple of standalone values.
What embedded servers does Spring Boot support, and how would you switch from the default?
Tomcat ships by default with spring-boot-starter-web; Jetty and Undertow are both supported alternatives. To switch, exclude the default spring-boot-starter-tomcat dependency and add the starter for the server you want instead (spring-boot-starter-jetty or spring-boot-starter-undertow) — no application code changes are required since Boot auto-configures whichever embedded container it finds on the classpath.
What is Spring Boot Actuator, and what does it give you out of the box?
Actuator adds a set of production-ready HTTP (and JMX) endpoints for monitoring and managing a running application without writing any custom code: /actuator/health for liveness/readiness, /actuator/metrics and /actuator/prometheus (via Micrometer) for numeric metrics, /actuator/env for resolved configuration, /actuator/beans for the bean graph, and /actuator/loggers to change log levels at runtime. Which endpoints are actually exposed over HTTP is controlled explicitly via management.endpoints.web.exposure.include, since several of them leak sensitive internals and shouldn't be open by default in production.

Spring MVC & REST

Spring MVC is the framework underneath essentially every REST API written in Spring. These questions cover the request lifecycle through DispatcherServlet, the annotations used to build and bind endpoints, and the patterns used to validate input and shape consistent error responses.

What is DispatcherServlet, and what does a request's path through Spring MVC look like?
DispatcherServlet is the front controller — the single entry point every request passes through. The flow: the servlet consults a HandlerMapping to find the controller method that should handle the request, a HandlerAdapter invokes it (resolving method arguments like @RequestBody/@PathVariable along the way), and the return value is processed — for a traditional @Controller that means resolving a view name via a ViewResolver; for REST endpoints the return value is instead handed to an HttpMessageConverter (typically Jackson) which serializes it directly onto the response body.
What is the difference between @Controller and @RestController?
A method on a plain @Controller returns a logical view name by default, which a ViewResolver maps to a template to render — to instead write the return value straight to the response body you'd have to annotate every method with @ResponseBody. @RestController is exactly @Controller plus @ResponseBody applied at the class level, so every handler method's return value is serialized directly to the body (typically as JSON) — which is what you want for a REST API.
What's the difference between @RequestMapping and the shorthand annotations like @GetMapping?
@RequestMapping is the general-purpose mapping annotation — the HTTP method is one of its attributes (method = RequestMethod.GET), and omitting it maps all methods. @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, and @PatchMapping are composed meta-annotations that are each pre-bound to one HTTP verb — purely for readability and to make the intent of an endpoint obvious at a glance.
What's the difference between @PathVariable, @RequestParam, and @RequestBody?
  • @PathVariable extracts a value from a URI template segment, e.g. /orders/{id}.
  • @RequestParam extracts a query string or form parameter, and supports required/defaultValue attributes.
  • @RequestBody deserializes the entire request payload (typically JSON) into a Java object, using whichever HttpMessageConverter is configured for that content type.
How do you handle exceptions globally across a Spring REST API?
An @ExceptionHandler method defined directly inside a controller only handles exceptions thrown by that one controller. To centralize handling across the whole application, define a class annotated @RestControllerAdvice containing @ExceptionHandler methods for each exception type you want to map to a specific HTTP status and response body — this keeps error-shaping logic out of every individual controller.
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(OrderNotFoundException ex) {
        return new ErrorResponse(ex.getMessage());
    }
}
What is Problem Details (RFC 7807), and how does Spring support it?
RFC 7807 defines a standard JSON/XML shape for HTTP API error bodies, with fields like type, title, status, detail, and instance, so clients don't need bespoke parsing logic per API. Since Spring 6 / Boot 3, this is supported natively via the ProblemDetail class and the ErrorResponse interface — an @ExceptionHandler can return ResponseEntity<ProblemDetail> (or throw an ErrorResponseException), and it can be turned on globally with spring.mvc.problemdetails.enabled=true so unhandled exceptions default to this shape too.
How does @Valid work for request validation, and how do you get at the validation errors?
@Valid on a @RequestBody-annotated parameter triggers Bean Validation (JSR-380, implemented by Hibernate Validator) against constraint annotations declared on the DTO — @NotNull, @Size, @Email, and so on. If validation fails, Spring throws MethodArgumentNotValidException, which by default results in a 400 response and can be intercepted in an @ExceptionHandler to reshape the error body. Alternatively, add a BindingResult parameter directly after the @Valid-annotated argument to inspect the errors programmatically instead of letting the exception propagate.
What is content negotiation, and how does Spring MVC decide between JSON and XML?
Content negotiation is choosing which representation format to return based on what the client can accept — primarily the Accept request header, though URL suffix and parameter-based strategies have historically existed too. Spring's ContentNegotiationManager checks the requested media type against the HttpMessageConverters registered on the classpath capable of producing it — if both a Jackson (JSON) converter and a JAXB (XML) converter are registered, whichever matches the Accept header wins; JSON is effectively the default in most Spring Boot web apps since the Jackson converter is registered automatically and typically listed first.

Spring Data JPA

Spring Data JPA removes most of the repository boilerplate from working with JPA, but it also hides real behavior that interviewers expect you to be able to reason about: how derived queries are actually built, why lazy loading causes the notorious N+1 problem, and how transaction propagation — and the proxy mechanism behind it — actually works.

What is the Spring Data repository hierarchy — Repository, CrudRepository, PagingAndSortingRepository, JpaRepository?
Repository<T, ID> is just a marker interface with no methods. CrudRepository extends it and adds the basics — save, findById, findAll, deleteById, and so on. PagingAndSortingRepository adds paged and sorted retrieval. JpaRepository extends both and layers on JPA-specific conveniences like saveAll, flush, and batch delete operations. In practice you almost always extend JpaRepository<Entity, ID> directly to get everything.
How do derived query methods work, e.g. findByLastNameAndStatus(...)?
At application startup, Spring Data parses each repository method name using a fixed keyword grammar (findBy, And, Or, OrderBy, Between, In, GreaterThan, etc.) and builds the corresponding JPQL query automatically — no implementation code is needed, and a typo in the method name against the entity's field names fails fast at startup rather than at query time.
How do you write a custom query with @Query, and what's the difference between JPQL and native queries?
Use @Query("select o from Order o where o.status = :status") on a repository method when the query is beyond what a derived method name can express, binding parameters with @Param. Setting nativeQuery = true switches to raw SQL — useful for database-specific features (window functions, vendor hints) that JPQL can't express — but it ties you to that database's dialect and bypasses some of JPQL's entity-graph awareness.
What is the N+1 select problem, and how do you fix it?
Fetching a list of parent entities runs one query; then accessing a lazily-loaded association on each of the N results triggers one additional query per row — N+1 queries total instead of one. Fixes:
  • JOIN FETCH in a JPQL query to eagerly pull the association in the same round trip.
  • @EntityGraph on a specific repository method to declare which associations should be eagerly fetched for just that query, without changing the entity's default fetch type.
  • Batch fetching (hibernate.default_batch_fetch_size) to turn N individual queries into a handful of IN (...) queries.
What's the difference between FetchType.LAZY and FetchType.EAGER, and what are the defaults?
LAZY defers loading the association until it's actually accessed (via a proxy); EAGER loads it immediately alongside the owning entity. Defaults: @OneToMany and @ManyToMany default to LAZY; @ManyToOne and @OneToOne default to EAGER. Common practice is to set everything explicitly to LAZY and fetch associations deliberately (JOIN FETCH/@EntityGraph) only where actually needed, rather than relying on the defaults and risking either N+1 queries or unexpectedly large eager graphs.
Explain @Transactional propagation and isolation levels.
Propagation governs how a method's transaction relates to a transaction already in progress on the calling thread — REQUIRED (default: join the existing one, or start a new one if none exists), REQUIRES_NEW (suspend the current transaction and start an independent new one), NESTED (a savepoint within the existing transaction that can be rolled back independently), plus SUPPORTS, MANDATORY, and NEVER for less common cases.

Isolation governs how much one transaction can see of another's uncommitted changes — READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, and SERIALIZABLE, in increasing order of consistency and decreasing order of concurrency.
Why doesn't @Transactional work when a method is called from another method in the same class?
Declarative @Transactional is implemented via a proxy wrapping the bean (JDK dynamic proxy or CGLIB, exactly the same mechanism Spring AOP uses generally). Only calls that go through the proxy get intercepted and wrapped in a transaction. A call to this.otherMethod() from inside the same class is a plain Java method call on the raw target object — it never passes back through the proxy, so the transactional interceptor never fires, and the "self-invoked" method silently runs with no transaction at all.
@Service
public class OrderService {

    public void placeOrder(Order o) {
        // this call bypasses the proxy -> saveOrder() runs non-transactionally
        this.saveOrder(o);
    }

    @Transactional
    public void saveOrder(Order o) { ... }
}
Fixes: inject a self-reference of the bean (or use AopContext.currentProxy() with exposeProxy = true) so the call goes through the proxy, move the transactional method into a separate bean, or switch to AspectJ compile-time/load-time weaving which doesn't rely on proxies at all.
How do DTO projections work in Spring Data JPA, and why prefer them over fetching full entities?
Instead of returning full managed entities, you can declare an interface with getter methods matching a subset of an entity's properties (interface-based/closed projection), or a class with a matching constructor referenced from a JPQL query:
@Query("select new com.example.dto.OrderSummary(o.id, o.total) from Order o")
List<OrderSummary> findSummaries();
Spring Data generates a query that selects only the required columns, avoiding the cost of loading (and potentially N+1-triggering) entire entity graphs when a caller only needs a handful of fields, and sidestepping the need to manage detached entities across layers.

Spring Security

Spring Security questions typically probe two things: whether you understand the filter chain as the actual mechanism enforcing security (rather than a black box), and whether you can reason correctly about stateless authentication, method security, and the cross-site attack classes (CSRF/CORS) the framework guards against.

What is the Spring Security filter chain, and how does a request flow through it?
Spring Security registers itself as a chain of ordered Servlet Filters (wired in via DelegatingFilterProxy/FilterChainProxy) that every request passes through before it ever reaches DispatcherServlet. Depending on configuration this includes filters like CsrfFilter, an authentication filter (e.g. UsernamePasswordAuthenticationFilter or bearer-token authentication for JWT), ExceptionTranslationFilter (converts security exceptions into 401/403 responses), and an authorization filter that makes the final allow/deny decision. Each filter can short-circuit the chain (reject the request) or pass it along to the next one.
What's the difference between authentication and authorization?
Authentication is verifying identity — who is making the request — which produces an Authentication object held in the SecurityContext for the duration of the request. Authorization is deciding what an already-authenticated principal is allowed to do, checked against roles/authorities at the URL level, the method level (@PreAuthorize), or even at the level of a specific object instance.
How does JWT-based stateless authentication work in a Spring Security application?
The client authenticates once — typically with a username/password against a login endpoint — and the server issues a signed JWT containing claims such as sub (subject), roles, and exp (expiry). The client attaches that token as a Bearer header on every subsequent request. A filter (a custom OncePerRequestFilter, or Spring Security's Resource Server support) validates the token's signature and expiry on each request and populates the SecurityContext for that request only — no session state is retained server-side, which is what makes the approach horizontally scalable across stateless application instances.
How do you enable and use method-level security with @PreAuthorize/@PostAuthorize?
Enable it with @EnableMethodSecurity (the Spring Security 6 replacement for the older @EnableGlobalMethodSecurity), then annotate methods directly:
  • @PreAuthorize("hasRole('ADMIN')") — evaluated before the method runs; can reference method arguments via SpEL.
  • @PostAuthorize("returnObject.owner == authentication.name") — evaluated after the method runs, and can inspect the return value, useful when the authorization decision depends on data only available once the object has been loaded.
How does Spring Security handle password storage, and why is BCrypt the preferred encoder?
Password handling goes through the PasswordEncoder abstraction, with BCryptPasswordEncoder as the commonly recommended default. BCrypt is a slow, adaptive, per-password-salted one-way hash purpose-built for credentials — its configurable work factor lets you deliberately keep it computationally expensive as hardware improves, which makes brute-force and rainbow-table attacks impractical at scale. This is in contrast to fast general-purpose hashes like MD5 or plain SHA-256, which are cheap enough to brute-force billions of guesses per second on modern hardware. Passwords should never be stored in plaintext or with reversible encryption.
What is CSRF, and when should CSRF protection be enabled or disabled?
Cross-Site Request Forgery is an attack where a malicious page tricks an authenticated user's browser into submitting a state-changing request (e.g. a form POST) to your application, riding along on the user's existing session cookie without their knowledge. Spring Security's CsrfFilter defends against this by requiring a per-session anti-forgery token on unsafe requests (POST/PUT/DELETE) — a token only the legitimate page could have obtained. This matters primarily for browser clients relying on cookie/session-based authentication; it's typically disabled for stateless, token-authenticated (JWT) APIs, since there's no ambient session cookie for a forged cross-site request to ride on in the first place.
What is CORS, and how do you configure it in a Spring application?
Cross-Origin Resource Sharing is a browser-enforced restriction that blocks JavaScript running on one origin from reading responses returned by a different origin, unless that server explicitly opts in via response headers like Access-Control-Allow-Origin. In Spring, it's configured either through a CorsConfigurationSource bean (applied globally, and integrated with the Security filter chain) or with @CrossOrigin on individual controllers. It's a distinct concern from CSRF — CORS governs whether cross-origin JavaScript can read a response at all and is enforced by the browser, while CSRF is about preventing forged state-changing requests from being accepted server-side.

Aspect-Oriented Programming (AOP)

AOP is what powers declarative transactions, method security, and caching under the hood, so understanding it is really understanding a chunk of the rest of the framework. These questions focus on the vocabulary, the proxy-based implementation Spring actually uses, and — most importantly — the sharp edges that trip engineers up in production, like self-invocation.

What is Aspect-Oriented Programming, and what problem does it solve?
AOP modularizes cross-cutting concerns — logging, security checks, transaction management, caching, metrics — that would otherwise have to be duplicated across many unrelated classes that all need the same behavior. Instead, the concern is defined once as an "aspect," and the framework applies it declaratively wherever it's needed, without the target classes containing any code aware of the concern at all.
What are the key AOP terms — aspect, join point, pointcut, advice, weaving?
  • Aspect — a module encapsulating a cross-cutting concern (a class annotated @Aspect).
  • Join point — a specific point during program execution where an aspect could be applied (in Spring AOP, always a method execution).
  • Pointcut — an expression that selects which join points a piece of advice actually applies to.
  • Advice — the action taken at a matched join point (before, after, around, etc.).
  • Weaving — the process of linking aspects into the target code, which can happen at compile time, load time, or — as Spring does it — at runtime via a dynamic proxy.
What are the different advice types — @Before, @After, @AfterReturning, @AfterThrowing, @Around?
  • @Before — runs before the join point executes.
  • @After — runs after the join point completes, regardless of outcome (like a finally block).
  • @AfterReturning — runs only on normal completion, and can access the return value.
  • @AfterThrowing — runs only if an exception propagates out, and can access it.
  • @Around — wraps the join point entirely; it receives a ProceedingJoinPoint and explicitly decides whether/when to call proceed(), and can inspect or modify both arguments and the return value, or skip execution altogether.
How does Spring implement AOP under the hood — JDK dynamic proxies vs. CGLIB?
Spring AOP is proxy-based, not true bytecode weaving. If the target bean implements at least one interface, Spring creates a JDK dynamic proxy implementing those same interfaces. If it doesn't, Spring falls back to generating a CGLIB subclass proxy at runtime instead. Whichever kind is created, it's the proxy — not the raw target — that gets registered in the ApplicationContext and injected everywhere else; the proxy intercepts every call, runs the applicable advice chain, and delegates to the real target method.
Why doesn't Spring AOP advice apply to self-invocation — a method calling another method on `this`?
The same root cause as the @Transactional self-invocation pitfall: advice only fires on calls that go through the proxy. A call to another method on this from inside the same class never passes back through the proxy wrapper — it's a direct call on the raw target instance — so no advice runs at all. Workarounds: inject a self-referencing proxy bean, expose the current proxy via AopContext.currentProxy() with exposeProxy = true, extract the advised method into a separate bean, or switch to AspectJ compile-time/load-time weaving, which instruments the bytecode directly and isn't affected by this at all.
What are the limitations of proxy-based AOP regarding what it can and can't advise?
  • Only applies to beans obtained through the Spring container — an object created directly with new is never proxied and gets no advice at all.
  • With CGLIB proxies specifically, a final class can't be subclassed and so can't be proxied, and a final method can't be overridden and so can't be advised even if the containing class is proxyable.
  • private methods are invisible to both proxy styles, since neither can override or intercept them.
  • Self-invocation within the same class bypasses the proxy entirely, as covered above.
What's the difference between Spring AOP and full AspectJ?
Spring AOP is a simpler, runtime proxy-based implementation limited to method-execution join points on Spring-managed beans — sufficient for the vast majority of enterprise cross-cutting concerns, and it requires no special build step or agent. AspectJ is a complete AOP implementation using compile-time or load-time weaving directly into bytecode, supporting many more join point types (field access, constructor calls, static initializers) and working on any object at all, not just container-managed beans — at the cost of an extra weaving step in the build, or a load-time weaving Java agent.

Testing

Spring Boot's testing story is built around "slices" — loading only the part of the application context relevant to what's being tested, rather than the whole application, in order to keep the test suite fast. These questions cover the major slice annotations, the mocking tools that plug into them, and how Testcontainers raises the fidelity of integration tests that touch a real database.

What's the difference between @SpringBootTest, @WebMvcTest, and @DataJpaTest?
  • @SpringBootTest boots the full ApplicationContext (optionally with a real embedded web server) — the closest thing to a true end-to-end test, but also the slowest.
  • @WebMvcTest loads only the web layer — controllers, filters, message converters, @ControllerAdvice — with the service layer left to be mocked, giving fast, focused tests of request/response behavior.
  • @DataJpaTest loads only JPA-related configuration — repositories and the entity manager — typically against an embedded/test database, for fast tests of query and persistence behavior in isolation.
Each "slice" boots a dramatically smaller context than the full application, which is what keeps the overall test suite fast.
What is MockMvc, and how do you use it to test a controller?
MockMvc is a fluent API that simulates HTTP requests against DispatcherServlet without starting a real servlet container, letting controller tests run fast and in-process. It's auto-configured by @WebMvcTest, or can be added to a full @SpringBootTest via @AutoConfigureMockMvc.
mockMvc.perform(get("/api/orders/42"))
       .andExpect(status().isOk())
       .andExpect(jsonPath("$.status").value("SHIPPED"));
What does @MockBean do, and how is it different from Mockito's plain @Mock?
@MockBean (from Spring Boot Test) replaces — or adds — a Mockito mock directly as a bean inside the live Spring ApplicationContext, so any component under test that autowires a dependency of that type transparently receives the mock instead of the real bean. Plain Mockito's @Mock only works with @ExtendWith(MockitoExtension.class) and has no awareness of Spring at all — it's for pure unit tests that construct the class under test directly, with no context involved. (As of Spring Boot 3.4, @MockitoBean is the direct successor to @MockBean.)
How would you write an integration test against a real database using Testcontainers?
Testcontainers spins up a real, ephemeral database engine (e.g. PostgreSQLContainer) inside Docker as part of the test lifecycle, via @Testcontainers plus a @Container-annotated field, or Spring Boot's built-in @ServiceConnection support which wires the datasource automatically. The Spring datasource is pointed at the container's dynamically-assigned JDBC URL (using @DynamicPropertySource, or automatically via @ServiceConnection), and the real repository/service code runs against it. This gives far higher fidelity than substituting an in-memory database like H2, since the test exercises the actual database engine, its SQL dialect, and any vendor-specific features the production system relies on.
What is @ActiveProfiles used for in tests?
@ActiveProfiles("test") activates a named Spring profile — and its associated application-test.yml — for the duration of a test class, letting you swap in test-specific beans and configuration (an in-memory mail sender, a disabled security filter chain, a different datasource) without touching or risking the production profile configuration at all.
What's the difference between plain unit tests and Spring "slice" tests, and when would you reach for each?
A pure unit test instantiates the class under test directly with new, hand-wiring or mocking its collaborators (typically with Mockito) — no Spring context is involved at all, which makes it the fastest option and the right default for business logic in service classes. A slice test (@WebMvcTest, @DataJpaTest, @JsonTest, etc.) loads a real, but narrowed, Spring context to verify framework wiring, serialization, or query behavior specific to one layer. A full @SpringBootTest is reserved for a smaller number of genuine end-to-end checks, since it's by far the slowest of the three to boot.
How do you test that a custom @ExceptionHandler/@RestControllerAdvice produces the correct HTTP response?
Drive it through MockMvc against a controller endpoint that triggers the target exception — either the real controller under a @WebMvcTest that also picks up the advice class, or a minimal test controller built just for the purpose — and assert on the resulting status code and body shape:
mockMvc.perform(get("/api/orders/999"))
       .andExpect(status().isNotFound())
       .andExpect(jsonPath("$.title").value("Order not found"));
This verifies the advice is actually wired into the running context and produces the expected error payload end-to-end, rather than just unit-testing the handler method's return value in isolation.
