Spring Security

Overview

Spring Security is a filter-chain-based framework that handles two related but distinct concerns: authentication (confirming who a caller is) and authorization (deciding what an authenticated caller is allowed to do). It plugs into the Servlet container as a series of Filter objects that intercept every request before it reaches your application code, and the same core model applies whether you're building a traditional session-based web app with login forms and cookies, or a stateless REST API where every request carries its own credentials (typically a JWT). Understanding the filter chain, the authentication flow, and the authorization model is the foundation for almost every Spring Security interview question.

The Security Filter Chain

Every incoming HTTP request passes through a chain of servlet Filters before it ever reaches the DispatcherServlet and your controllers. Spring Security registers itself into this chain via a single DelegatingFilterProxy (named springSecurityFilterChain), which internally delegates to an ordered list of security filters — things like UsernamePasswordAuthenticationFilter (form login), BasicAuthenticationFilter (HTTP Basic), BearerTokenAuthenticationFilter or a custom JWT filter, ExceptionTranslationFilter (converts security exceptions into 401/403 responses), and FilterSecurityInterceptor/AuthorizationFilter (the final authorization decision point).

Order matters: authentication filters must run before the authorization check, and each filter either processes the request (e.g. extracts and validates credentials) or passes it along the chain untouched. If any filter throws an AuthenticationException or AccessDeniedException, the chain short-circuits and the client gets a 401 or 403 without ever touching your controller.

Since Spring Security 5.7, WebSecurityConfigurerAdapter is deprecated (removed in Spring Security 6/Boot 3) in favor of a component-based style: you expose a SecurityFilterChain bean and configure it with the HttpSecurity lambda DSL. This is now the idiomatic way to configure security.

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(sm ->
                sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(authz -> authz
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}

Authentication

Authentication answers "who is making this request?". In the classic username/password model, Spring Security delegates to a UserDetailsService, which loads a UserDetails object (username, hashed password, granted authorities, and account-status flags such as expired/locked/disabled) given a username. The supplied raw password is compared against the stored hash using a PasswordEncoder — almost always BCryptPasswordEncoder today, since it's adaptive (tunable work factor) and salts automatically.

The orchestration happens through an AuthenticationManager, which delegates to one or more AuthenticationProviders. DaoAuthenticationProvider is the standard provider for username/password auth: it calls the UserDetailsService, encodes and compares the password, and on success returns a fully populated, authenticated Authentication object that gets stored in the SecurityContextHolder for the duration of the request (or session).

@Service
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    public CustomUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {
        User user = userRepository.findByUsername(username)
            .orElseThrow(() ->
                new UsernameNotFoundException("No user: " + username));

        return org.springframework.security.core.userdetails.User
            .withUsername(user.getUsername())
            .password(user.getPasswordHash())
            .authorities(user.getRoles().toArray(new String[0]))
            .accountLocked(!user.isActive())
            .build();
    }
}

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

Authorization

Authorization answers "what is this (now-identified) caller allowed to do?". Spring Security offers two complementary layers:

URL-based rules, configured once in the SecurityFilterChain via .authorizeHttpRequests(...), apply broad, coarse-grained rules matched against the request path and HTTP method — e.g. "anything under /api/admin/** requires ROLE_ADMIN". These are evaluated top-to-bottom, first match wins, so ordering matters (more specific patterns before general ones, with anyRequest() last).

Method-level security (enabled with @EnableMethodSecurity) is fine-grained and lives directly on service or controller methods using annotations like @PreAuthorize (evaluated before the method runs, can reference method arguments via SpEL), @PostAuthorize (evaluated after the method runs, can reference the return value), and the older @Secured (simpler, role-list-only, no SpEL). @PreAuthorize is the most flexible and most commonly used in modern codebases.

@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")
public UserDto getUser(Long userId) {
    return userService.findById(userId);
}

@PostAuthorize("returnObject.ownerId == authentication.principal.id")
public Document getDocument(Long docId) {
    return documentService.findById(docId);
}

A frequently-missed distinction: roles and authorities are the same underlying concept (GrantedAuthority) with a naming convention layered on top. hasRole("ADMIN") is sugar for hasAuthority("ROLE_ADMIN") — Spring Security automatically prepends the ROLE_ prefix when you use the role-based methods. Authorities without that prefix (e.g. SCOPE_read, read:orders) represent finer-grained permissions and must be checked with hasAuthority(...) directly, since hasRole(...) always adds the prefix.

JWT-Based Stateless Authentication

Traditional session-based authentication stores authentication state server-side (an HttpSession keyed by a cookie), which requires sticky sessions or a shared session store to scale horizontally. REST APIs typically avoid this by going stateless: the server holds no session at all, and every request is authenticated independently based on a credential the client presents.

The standard approach is JWT (JSON Web Token): the client authenticates once against a login endpoint (username/password, OAuth code exchange, etc.), the server verifies the credentials and returns a signed token containing claims (subject, roles, expiry) as its response body. The client then stores that token and sends it on every subsequent request in the Authorization: Bearer <token> header. Because the token is self-contained and cryptographically signed, the server can verify it on each request without touching a database or a session store — that's what makes the approach horizontally scalable.

To wire this into Spring Security, you write a custom filter — extending OncePerRequestFilter so it's guaranteed to run exactly once per request — that extracts the bearer token, validates its signature and expiry, and, if valid, manually populates the SecurityContextHolder with an authenticated Authentication object before letting the request continue down the chain.

public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtService jwtService;

    public JwtAuthenticationFilter(JwtService jwtService) {
        this.jwtService = jwtService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                     HttpServletResponse response,
                                     FilterChain filterChain)
            throws ServletException, IOException {

        String header = request.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = header.substring(7);

        if (jwtService.isValid(token)) {
            String username = jwtService.extractUsername(token);
            List<GrantedAuthority> authorities = jwtService.extractAuthorities(token);

            UsernamePasswordAuthenticationToken authToken =
                new UsernamePasswordAuthenticationToken(username, null, authorities);
            authToken.setDetails(
                new WebAuthenticationDetailsSource().buildDetails(request));

            SecurityContextHolder.getContext().setAuthentication(authToken);
        }

        filterChain.doFilter(request, response);
    }
}

This filter is registered before UsernamePasswordAuthenticationFilter in the chain (see addFilterBefore in the earlier config), so by the time the request reaches FilterSecurityInterceptor/AuthorizationFilter, the SecurityContext already holds a fully authenticated principal for the URL and method-level checks to evaluate against.

CSRF & CORS

CSRF (Cross-Site Request Forgery) attacks exploit the browser's automatic inclusion of cookies on cross-site requests — a malicious site can trigger a request to your app, and the browser happily attaches the victim's session cookie. Spring Security enables CSRF protection by default for session-based, cookie-authenticated apps. For a stateless JWT-based REST API, though, there's no session cookie for a browser to silently attach: the client must explicitly read the token (from local storage, memory, etc.) and attach it as an Authorization header, which a forged cross-site request cannot do. That's why .csrf(csrf -> csrf.disable()) is standard for stateless token-based APIs — but only when authentication genuinely never relies on cookies. If a JWT is ever stored in a cookie instead of a header, CSRF protection is still required.

CORS (Cross-Origin Resource Sharing) is a separate, unrelated concern: it's a browser-enforced policy about which origins are allowed to call your API from client-side JavaScript. When your frontend (e.g. app.example.com) and your API (api.example.com) live on different origins, you must explicitly configure CORS or the browser will block the response.

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    config.setAllowCredentials(true);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}

Then wire it into the filter chain with .cors(cors -> cors.configurationSource(corsConfigurationSource())). Note that CORS is enforced by the browser, not by Spring Security itself — it's purely a set of response headers that tell the browser what's allowed, so it offers no protection against non-browser clients (e.g. curl or server-to-server calls).

Common Interview Questions

How does Spring Security's filter chain work?
Every request passes through an ordered chain of servlet Filters registered under a single DelegatingFilterProxy. Authentication filters (form login, Basic auth, a custom JWT filter) run first and populate the SecurityContextHolder if credentials are valid; ExceptionTranslationFilter catches security exceptions and converts them to HTTP 401/403; and FilterSecurityInterceptor/AuthorizationFilter makes the final authorization decision at the end of the chain. If any filter rejects the request, it never reaches the DispatcherServlet or your controller.
How would you secure a REST API with JWT instead of session cookies?
Set session creation policy to STATELESS so Spring Security never creates or relies on an HttpSession. Add a custom OncePerRequestFilter before UsernamePasswordAuthenticationFilter that:
  • Extracts the token from the Authorization: Bearer <token> header
  • Validates its signature and expiry
  • Builds an authenticated Authentication object from its claims and stores it in the SecurityContextHolder
Downstream URL-based and method-level authorization checks then work exactly as they would in a session-based app, because they only depend on the SecurityContext, not on how it was populated.
What's the difference between authentication and authorization in Spring Security?
Authentication establishes identity — verifying credentials via an AuthenticationManager/AuthenticationProvider and producing an authenticated Authentication object. Authorization is a separate, later step that decides whether that identity is permitted to perform a given action, evaluated either as coarse-grained URL rules (.authorizeHttpRequests(...)) or fine-grained method-level checks (@PreAuthorize). Authentication always happens first; authorization decisions depend on its result.
Why is CSRF protection typically disabled for stateless JWT-based APIs?
CSRF attacks work by having the browser automatically attach a session cookie to a forged cross-site request. A stateless JWT-based API doesn't authenticate via cookies — the client must explicitly attach the token as an Authorization header, which a forged request from another site cannot do. Since there's no ambient credential for the browser to auto-attach, the CSRF threat model doesn't apply, so it's safe (and standard) to disable it — as long as the token is genuinely never stored in a cookie.
What's the difference between @PreAuthorize and URL-pattern-based authorization rules?
URL-based rules, set once in .authorizeHttpRequests(...), are coarse-grained and matched purely on request path/method — good for broad boundaries like "everything under /api/admin/** needs ROLE_ADMIN". @PreAuthorize is fine-grained, lives directly on a service or controller method, supports full SpEL expressions, and can reference method arguments (e.g. #userId == authentication.principal.id) — useful for ownership checks that a URL pattern alone can't express. Most real systems use both: URL rules as a coarse first gate, method-level annotations for precise business-rule enforcement.

Key Takeaways

  • Spring Security is fundamentally a chain of servlet filters; understanding filter order explains almost all of its behavior.
  • Use the SecurityFilterChain bean with the HttpSecurity lambda DSL — WebSecurityConfigurerAdapter is deprecated/removed.
  • Authentication (UserDetailsService + PasswordEncoder + AuthenticationManager) and authorization (URL rules + @PreAuthorize) are separate layers that compose together.
  • Stateless REST APIs authenticate every request independently via a signed JWT validated in a custom OncePerRequestFilter, avoiding server-side session storage entirely.
  • CSRF matters for cookie-based session auth but is safely disabled for token-based stateless APIs; CORS is a separate, browser-enforced cross-origin policy that must be configured independently.
