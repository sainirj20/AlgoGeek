SPRING

Spring Core

Overview

Almost every Spring interview opens with some variant of “explain IoC and DI in your own words.” It sounds like a warm-up question, but it isn’t — the interviewer is really checking whether you understand why Spring is designed the way it is, not just whether you can recite that “the container manages object creation.” A candidate who can only say “Spring injects dependencies for you” gets filtered out quickly; a candidate who can explain the trade-offs between injection styles, describe what actually happens during bean creation, and reason about scope and lifecycle bugs signals real production experience. This page covers IoC/DI mechanics, the bean lifecycle end to end, and the failure modes that come up in practice — circular dependencies, ambiguous autowiring, scope mismatches, and premature use of a bean before it’s fully initialized.

Inversion of Control & the ApplicationContext

Inversion of Control is a design principle where the responsibility for creating objects and wiring their dependencies is taken away from the objects themselves and handed to an external container. In plain Java, a class that needs a collaborator typically instantiates it directly (new OrderValidator()), which hard-wires the class to a specific implementation and makes substitution (for testing, for a different environment) painful. Under IoC, the class simply declares what it needs, and the container decides what concrete instance to hand it. Dependency Injection is the specific mechanism Spring uses to achieve IoC: the container looks at a class’s declared dependencies and supplies them, rather than the class reaching out and constructing or looking them up itself.

The container itself is represented by two related abstractions. BeanFactory is the root interface — a minimal container that supports lazy initialization and basic DI, and is rarely used directly in modern applications. ApplicationContext extends BeanFactory and adds the features real applications depend on: eager singleton instantiation at startup, event publication (ApplicationEventPublisher), internationalization support, environment/property abstraction, and integration with AOP. In interviews, the expected answer is: “ApplicationContext is a superset of BeanFactory with enterprise features, and it’s what you use in practice — AnnotationConfigApplicationContext or the auto-configured context Spring Boot builds for you.”

Bean discovery today is almost always annotation-driven. @ComponentScan tells the container which packages to scan for classes annotated @Component (and its specializations @Service, @Repository, @Controller); the container instantiates one of each, registers it under a bean name, and makes it available for injection. For beans you don’t own the source of — third-party classes, or objects that need custom construction logic — you use @Configuration classes with @Bean-annotated factory methods instead:

@Configuration
public class ClientConfig {

    @Bean
    public RestTemplate restTemplate(RestTemplateBuilder builder) {
        return builder
            .setConnectTimeout(Duration.ofSeconds(2))
            .setReadTimeout(Duration.ofSeconds(5))
            .build();
    }
}

Both approaches result in the same thing: an entry in the container’s bean definition registry that gets resolved, instantiated, and wired at context startup (for singletons) or on demand (for other scopes).

Dependency Injection: Constructor vs. Setter vs. Field

Spring supports three injection styles, and knowing when (and why not) to use each is one of the most common practical questions.

Constructor injection passes dependencies as constructor arguments:

@Service
public class OrderService {

    private final PaymentClient paymentClient;
    private final InventoryClient inventoryClient;

    public OrderService(PaymentClient paymentClient, InventoryClient inventoryClient) {
        this.paymentClient = paymentClient;
        this.inventoryClient = inventoryClient;
    }
}

Setter injection exposes a mutator method that the container calls after instantiation:

@Service
public class OrderService {

    private PaymentClient paymentClient;

    @Autowired
    public void setPaymentClient(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}

Field injection annotates the field directly and relies on reflection to set it:

@Service
public class OrderService {

    @Autowired
    private PaymentClient paymentClient;
}

Constructor injection is the modern best practice, and Spring’s own team recommends it. The reasons matter more than the recommendation itself:

  • Immutability. Constructor injection lets dependencies be declared final, so once the object is built its collaborators can never be reassigned or left null. Field/setter injection can’t offer this — the field has to be non-final so Spring can assign it after construction.
  • Testability. A class built via constructor injection can be instantiated with plain new in a unit test, passing mocks directly — no Spring context, no reflection tricks, no @InjectMocks magic required (though Mockito’s @InjectMocks happens to work well with it too).
  • Fail-fast on missing dependencies. If a required collaborator isn’t available, the object simply cannot be constructed — you get a clear BeanCreationException at startup instead of a NullPointerException deep in some code path at runtime.
  • Circular dependency exposure. If bean A needs bean B in its constructor and B needs A in its constructor, Spring cannot resolve the cycle and throws BeanCurrentlyInCreationException at startup. That’s a feature, not a bug — it surfaces a design smell immediately. Field/setter injection can silently mask the same cycle because Spring instantiates both objects first (with no-arg or partially-satisfied constructors) and wires fields in afterward, sometimes via a second pass and early-reference caching (the “third-level cache” in the singleton creation process) — the code “works” but the design problem is hidden rather than fixed.
  • No reflection needed for injection. The container just calls a public constructor; it doesn’t need to bypass access modifiers via reflection the way field injection does, which is marginally better for tooling, GraalVM native-image compatibility, and static analysis.

Setter injection still has a legitimate niche: optional dependencies that can be reconfigured after construction. Field injection is convenient for quick prototypes and test classes but is generally discouraged in production code for the reasons above.

Qualifying and Resolving Beans

@Autowired tells Spring to resolve a dependency by type. That works cleanly when exactly one bean of the required type exists. Problems start when multiple beans implement the same interface — for example, two implementations of a NotificationSender interface, one for email and one for SMS. Autowiring by type alone is ambiguous, and Spring throws NoUniqueBeanDefinitionException at startup.

There are two standard ways to disambiguate. @Qualifier lets the injection point specify which named bean it wants:

public interface NotificationSender {
    void send(String message);
}

@Service("emailSender")
public class EmailNotificationSender implements NotificationSender { /* ... */ }

@Service("smsSender")
public class SmsNotificationSender implements NotificationSender { /* ... */ }

@Service
public class AlertService {

    private final NotificationSender sender;

    public AlertService(@Qualifier("smsSender") NotificationSender sender) {
        this.sender = sender;
    }
}

@Primary instead marks one implementation as the default choice when no qualifier is given, which is useful when one implementation is clearly the common case and only a few call sites need the alternative:

@Service
@Primary
public class EmailNotificationSender implements NotificationSender { /* ... */ }

A related but distinct tool is injecting all implementations at once — declaring the dependency as List<NotificationSender> (or a Map<String, NotificationSender> keyed by bean name) causes Spring to collect every matching bean instead of requiring a single unique match, which is a common pattern for strategy-style dispatch.

Bean Scopes

Scope determines how many instances of a bean the container creates and how long each instance lives. The five standard scopes:

  • singleton (default) — exactly one instance per Spring container, shared by every injection point. Appropriate for stateless services, clients, and repositories — the vast majority of beans.
  • prototype — a new instance is created every time the bean is requested from the container. Use this for beans that carry mutable, request-specific or invocation-specific state that must not be shared, such as a stateful builder or a non-thread-safe helper object.
  • request — one instance per HTTP request, valid only in a web-aware ApplicationContext. Useful for request-scoped data holders (e.g., a request context object accumulating data as it flows through filters and interceptors).
  • session — one instance per HTTP session, again web-context only. Useful for per-user state like a shopping cart.
  • application — one instance per ServletContext, effectively singleton scoped to the whole web application rather than the Spring container — relevant when multiple Spring contexts share one servlet context.

Declaring prototype scope:

@Component
@Scope("prototype")
public class ReportBuilder {
    private final List<String> sections = new ArrayList<>();

    public ReportBuilder addSection(String section) {
        sections.add(section);
        return this;
    }
}

A classic gotcha: injecting a prototype bean into a singleton via a normal field/constructor injection only resolves the prototype once, at the time the singleton is created — every subsequent use gets that same first instance, defeating the purpose of prototype scope. The fix is to inject an ObjectProvider<ReportBuilder> (or use scoped proxies) and call getObject() each time a fresh instance is actually needed. This exact scenario is a favorite “gotcha” interview question because it tests whether the candidate actually understands scope resolution timing versus just memorizing the scope names.

The Spring Bean Lifecycle

Understanding the lifecycle in order is what separates candidates who’ve memorized annotations from candidates who can debug a real startup issue (e.g., a field that’s null inside @PostConstruct because it was expected to come from a setter that hasn’t run yet). The sequence, for a singleton bean during container startup:

  • 1. Instantiation. The container calls the bean’s constructor (this is also where constructor-injected dependencies are supplied, since they must exist before the object can be built).
  • 2. Population of properties/dependencies. Setter- and field-injected dependencies are populated at this stage — strictly after the object already exists, which is exactly why those fields can’t be final and why they’re briefly in a “not yet wired” state.
  • 3. Aware interface callbacks. If the bean implements container-aware interfaces such as BeanNameAware, BeanFactoryAware, or ApplicationContextAware, the corresponding setBeanName()/setBeanFactory()/setApplicationContext() methods are invoked, giving the bean a handle back into the container itself.
  • 4. BeanPostProcessor#postProcessBeforeInitialization. Any registered BeanPostProcessor beans get a chance to inspect or wrap the bean instance before initialization callbacks run. This is the extension point that powers features like @Autowired resolution itself, AOP proxy creation, and annotation-driven validation.
  • 5. Initialization callbacks. In order of precedence: @PostConstruct-annotated methods run, then InitializingBean#afterPropertiesSet() if the bean implements that interface, then any custom init-method configured on the bean definition. This is the right place to run logic that depends on all dependencies already being injected — validating configuration, warming a cache, opening a connection pool.
  • 6. BeanPostProcessor#postProcessAfterInitialization. A second post-processor pass, after initialization — this is where JDK/CGLIB proxies typically get created (e.g., for @Transactional or @Async), which is why the bean reference other code ends up injecting may actually be a proxy wrapping the real instance.
  • 7. Bean is ready for use. The fully initialized bean sits in the singleton cache and is handed out to every injection point until the container shuts down.
  • 8. Destruction callbacks on shutdown. When the container closes, singleton beans (not prototypes — Spring does not manage the full lifecycle of prototype beans after handing them out) receive destruction callbacks in the analogous order: @PreDestroy methods, then DisposableBean#destroy(), then a custom destroy-method. This is where you release resources — close connections, flush buffers, shut down executors.
@Component
public class ConnectionPoolManager implements InitializingBean, DisposableBean {

    private HikariDataSource dataSource;

    @PostConstruct
    public void init() {
        dataSource = new HikariDataSource(buildConfig());
    }

    @Override
    public void afterPropertiesSet() {
        // Runs after @PostConstruct; both exist mainly for legacy/interoperability reasons.
    }

    @PreDestroy
    public void shutdown() {
        if (dataSource != null) {
            dataSource.close();
        }
    }

    @Override
    public void destroy() {
        // Runs after @PreDestroy methods.
    }
}

In practice, most teams pick one mechanism — usually @PostConstruct/@PreDestroy — rather than mixing all three, precisely because the ordering between them is easy to get wrong and hard to spot in review.

Common Interview Questions

What is the difference between BeanFactory and ApplicationContext?
BeanFactory is the root container interface, providing lazy bean lookup and basic DI. ApplicationContext extends it and adds the features production applications actually need: eager singleton instantiation at startup (so misconfiguration fails fast), event publishing, environment/property abstraction, internationalization, and AOP integration. In practice you always use an ApplicationContext implementation (or the one Spring Boot auto-configures) — BeanFactory is mostly of historical/academic interest today.
Why is constructor injection preferred over field injection?
Constructor injection allows dependencies to be declared final, guaranteeing immutability and that the object is never in a partially-wired state. It makes unit testing trivial — you can instantiate the class with new and pass mocks directly, without a Spring context. It fails fast: a missing dependency prevents the object from being constructed at all, producing a clear startup error instead of a runtime NullPointerException. It also surfaces circular dependencies immediately as a BeanCurrentlyInCreationException, rather than letting Spring silently resolve them via early-reference caching the way field/setter injection can.
What are the Spring bean scopes and when would you use prototype?
The standard scopes are:
  • singleton — one shared instance (the default; used for stateless services)
  • prototype — a new instance per request from the container
  • request — one instance per HTTP request
  • session — one instance per HTTP session
  • application — one instance per ServletContext
Prototype is the right choice when a bean carries mutable, non-thread-safe, or invocation-specific state that must not be shared across callers — for example a stateful builder object. A common pitfall is injecting a prototype bean directly into a singleton, which resolves it only once at startup; the fix is to inject an ObjectProvider and request a fresh instance each time it’s needed.
Walk through the Spring bean lifecycle.
Instantiation (constructor call, including constructor-injected dependencies) → population of setter/field dependencies → Aware interface callbacks (BeanNameAware, ApplicationContextAware, etc.) → BeanPostProcessor#postProcessBeforeInitialization → initialization callbacks in order (@PostConstruct, then InitializingBean#afterPropertiesSet(), then a custom init-method) → BeanPostProcessor#postProcessAfterInitialization (where proxies for @Transactional/@Async get created) → bean is ready and cached → on container shutdown, destruction callbacks run for singletons (@PreDestroy, then DisposableBean#destroy(), then a custom destroy-method).
What problem does @Qualifier solve?
When more than one bean satisfies the same type — for example two implementations of the same interface — autowiring by type alone is ambiguous and Spring throws NoUniqueBeanDefinitionException. @Qualifier("beanName") lets the injection point specify exactly which bean it wants by name, resolving the ambiguity explicitly. @Primary is the complementary tool: it marks one implementation as the default so unqualified injection points get it automatically, while specific call sites can still override with @Qualifier.

Key Takeaways

  • IoC means the container — not your code — controls object creation and wiring; DI is the mechanism Spring uses to deliver on that principle.
  • ApplicationContext is what you use in real applications; BeanFactory is the minimal root interface it builds on.
  • Prefer constructor injection: it enables immutability via final fields, makes classes trivially unit-testable without a container, fails fast on missing dependencies, and surfaces circular dependencies instead of silently masking them.
  • Use @Qualifier and @Primary to resolve ambiguity when multiple beans satisfy the same type; prefer explicit qualifiers when there’s no obvious default.
  • Know the bean lifecycle order cold — instantiation, dependency population, Aware callbacks, post-processors, init callbacks, ready-for-use, destroy callbacks — because it explains real bugs like nulls in @PostConstruct or proxies not behaving as expected.
