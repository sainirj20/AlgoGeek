Spring Data JPA & Hibernate

Overview

Spring Data JPA is a layer that sits on top of a JPA provider — almost always Hibernate in practice — and eliminates the boilerplate DAO code that plain JPA still requires: manual EntityManager lookups, hand-written CRUD methods, and repetitive query construction. Instead of writing an implementation class, you declare a repository interface, and Spring generates a working implementation at runtime using a dynamic proxy. The goal is not to replace JPA/Hibernate — it is to make the 80% of common data-access patterns (find by id, save, delete, paginate, derive a query from a method name) nearly free, while still giving you an escape hatch (@Query, EntityManager injection, Specifications) for the remaining 20%.

Entities & the Persistence Context

Spring Data JPA does not change how you model entities — that's still plain JPA. An entity is a POJO annotated with @Entity, with a primary key marked by @Id (often paired with @GeneratedValue for auto-incrementing or sequence-based ids) and fields mapped to columns via @Column (or left to default naming conventions).

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "customer_email", nullable = false)
    private String customerEmail;

    private BigDecimal amount;

    private String status;
}

What a Spring developer needs to internalize (deeper Hibernate internals live in the JPA / Hibernate section of this site) is the persistence context: the first-level cache that the EntityManager maintains per transaction. An entity loaded within a transaction is managed — Hibernate tracks its field changes and flushes them to the database automatically at commit (dirty checking), with no explicit save() call required for updates. Once the transaction (and the underlying persistence context) closes, that same entity becomes detached — it still holds data, but lazy associations on it can no longer be initialized, which is the root cause of the infamous LazyInitializationException when entities are passed outside the transactional boundary (e.g., serialized directly from a controller).

Repository Interfaces

Spring Data's repository abstraction is a hierarchy of interfaces, each adding capability:

  • CrudRepository<T, ID> — basic create, read, update, delete, and findAll().
  • PagingAndSortingRepository<T, ID> — extends CrudRepository and adds findAll(Pageable) and findAll(Sort).
  • JpaRepository<T, ID> — extends PagingAndSortingRepository, adding JPA-specific batching operations like saveAll(), flush(), and deleteInBatch(). In practice, almost every application repository extends JpaRepository directly since it's a strict superset.

Beyond the inherited CRUD methods, Spring Data lets you declare derived query methods: name a method following a keyword convention and Spring parses the method name into a query at startup, with no implementation required.

public interface OrderRepository extends JpaRepository<Order, Long> {

    // Derived query — Spring parses the method name into a JPQL query
    List<Order> findByCustomerEmailAndStatus(String email, String status);

    // JPQL via @Query for anything the naming convention can't express cleanly
    @Query("SELECT o FROM Order o WHERE o.amount > :threshold ORDER BY o.amount DESC")
    List<Order> findHighValueOrders(@Param("threshold") BigDecimal threshold);

    // Native SQL when you need a DB-specific feature
    @Query(value = "SELECT * FROM orders WHERE status = 'PENDING' LIMIT 100", nativeQuery = true)
    List<Order> findPendingBatch();

    // @Modifying is required for any @Query that changes data (UPDATE/DELETE)
    @Modifying
    @Query("UPDATE Order o SET o.status = :status WHERE o.id = :id")
    int updateStatus(@Param("id") Long id, @Param("status") String status);
}

A subtlety worth knowing cold: @Modifying queries execute directly against the database and bypass the persistence context, so any managed entities already loaded in the current session will hold stale in-memory state unless you clear the persistence context (clearAutomatically = true) or refresh the entity afterward.

Entity Relationships & the N+1 Problem

Relationships are declared with @OneToMany, @ManyToOne, and @ManyToMany, each configurable with a fetch strategy. @ManyToOne and @OneToOne default to FetchType.EAGER; @OneToMany and @ManyToMany default to FetchType.LAZY. LAZY means the association is only loaded when it's first accessed (via a proxy); EAGER means it's loaded immediately alongside the owning entity, in the same or an additional query.

@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderLine> lines;
}

The N+1 select problem shows up when you fetch a list of parent entities (1 query) and then, for each parent, access a lazy association — triggering one additional query per parent (N queries). Fetching 100 orders and then reading order.getLines() for each in a loop results in 101 round trips instead of 1 or 2. Three standard fixes:

  • JOIN FETCH in JPQL — explicitly pull the association in the same query: SELECT o FROM Order o JOIN FETCH o.lines WHERE o.status = :status.
  • @EntityGraph — declare, at the repository method level, which associations to eagerly fetch for that call only, without changing the entity's default fetch type: @EntityGraph(attributePaths = "lines") on a derived query method.
  • DTO projections — select only the fields you actually need via a JPQL constructor expression or an interface projection, sidestepping the association graph entirely.

Transaction Management

Spring's @Transactional annotation wraps a method in a transaction using an AOP proxy: on entry it starts (or joins) a transaction, and on successful return it commits; on an unchecked exception (by default) it rolls back. The propagation attribute controls how a method's transaction relates to an existing one — REQUIRED (the default) joins the caller's transaction if one exists or starts a new one if not, while REQUIRES_NEW always suspends any existing transaction and starts an independent one (useful for things like audit logging that must persist even if the outer transaction rolls back). isolation controls how much one transaction can see of another's uncommitted changes (READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE, etc.) — most applications rely on the database's default rather than overriding it.

@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final AuditService auditService;

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        auditService.recordPlacement(order); // REQUIRES_NEW: commits even if placeOrder rolls back later
    }
}

@Transactional should live on the service layer, not the repository (repository methods are already individually transactional via Spring Data, which is too fine-grained for multi-step business operations) and not the controller (the web layer shouldn't own transaction boundaries or database semantics). The service layer is where a "unit of work" corresponding to a business operation naturally lives.

The classic pitfall: @Transactional is implemented via a proxy that wraps the bean. If you call a @Transactional method from another method in the same class, that call goes through this directly — it never passes through the proxy — so the transactional advice (starting a new transaction, applying propagation rules) is silently skipped.

@Service
public class OrderService {

    public void processOrder(Order order) {
        // Calling this.saveOrder(...) bypasses the proxy entirely —
        // no new transaction is started here, despite the annotation below.
        saveOrder(order);
    }

    @Transactional
    public void saveOrder(Order order) {
        // ...
    }
}

Common fixes: move the transactional method to a separate bean and inject that bean, or self-inject a proxy reference of the same bean (@Autowired private OrderService self;) and call through it.

DTO Projections

Returning JPA entities directly from a service or REST controller is a well-known anti-pattern for a few concrete reasons: entities may hold lazy associations that throw LazyInitializationException once serialized outside the original persistence context; entities often carry more fields than a given API response needs (over-fetching, and potential leakage of internal or sensitive columns); and binding your API contract directly to your table schema means every column rename or schema refactor becomes a breaking API change.

Spring Data supports two lightweight projection styles that avoid loading full entity graphs:

// Interface-based projection — Spring generates a proxy backed by the query result
public interface OrderSummary {
    Long getId();
    BigDecimal getAmount();
    String getStatus();
}

public interface OrderRepository extends JpaRepository<Order, Long> {
    List<OrderSummary> findByCustomerEmail(String email);
}

// Record-based (constructor) projection via JPQL
public record OrderSummaryDto(Long id, BigDecimal amount, String status) {}

@Query("SELECT new com.example.OrderSummaryDto(o.id, o.amount, o.status) " +
       "FROM Order o WHERE o.customerEmail = :email")
List<OrderSummaryDto> findSummariesByEmail(@Param("email") String email);

Both approaches let the database return only the selected columns rather than materializing entire managed entities, and both produce plain, serialization-safe objects with no lazy proxies attached — making them the natural boundary type between the persistence layer and the API layer.

Common Interview Questions

What's the difference between CrudRepository, PagingAndSortingRepository, and JpaRepository?
CrudRepository gives basic save/find/delete operations. PagingAndSortingRepository extends it with findAll(Pageable) and findAll(Sort) for pagination and ordering. JpaRepository extends PagingAndSortingRepository further with JPA-specific batch operations like saveAll(), flush(), and deleteInBatch(). In real projects you almost always extend JpaRepository directly since it's a superset of the other two.
Explain the N+1 select problem and two ways to fix it.
It occurs when you load a list of parent entities in one query, then access a lazy association on each one, triggering one additional query per parent — N extra queries for N parents. Two standard fixes:
  • Use JOIN FETCH in a JPQL query to load the association in the same round trip.
  • Use @EntityGraph on the repository method to eagerly fetch specific associations for that call only.
Why does calling a @Transactional method from within the same class not start a new transaction?
Spring implements @Transactional using an AOP proxy that wraps the bean. Transactional behavior only kicks in when a call goes through that proxy. A self-invocation (calling another method on this from within the same class) bypasses the proxy entirely, so the annotation is silently ignored. The fix is to move the method to a separate bean, or inject/call through a proxy reference of the same bean.
What's the difference between FetchType.LAZY and FetchType.EAGER?
LAZY defers loading an association until it's actually accessed, via a proxy — it requires an open persistence context at access time. EAGER loads the association immediately along with the owning entity. @ManyToOne/@OneToOne default to EAGER; @OneToMany/@ManyToMany default to LAZY. In practice, most teams override the defaults to LAZY everywhere and fetch what they need explicitly (via JOIN FETCH, @EntityGraph, or projections) to avoid unpredictable eager-loading chains.
Why prefer DTOs over exposing JPA entities directly from a REST API?
Returning entities directly risks LazyInitializationException when a lazy association is serialized outside its original transaction, exposes more data than the API contract should (over-fetching, potential leakage of internal columns), and tightly couples your API shape to your database schema so that internal refactors become breaking changes for API consumers. DTOs (interface projections or Java records) decouple these concerns and are inherently serialization-safe.

Key Takeaways

  • Spring Data JPA removes DAO boilerplate by generating repository implementations from interfaces; JpaRepository is the practical default to extend.
  • Derived query methods cover simple lookups; @Query (JPQL or native) covers everything else, and @Modifying is mandatory for update/delete queries.
  • The N+1 problem comes from lazy associations accessed in a loop — fix it with JOIN FETCH, @EntityGraph, or DTO projections, not by defaulting everything to EAGER.
  • @Transactional belongs on the service layer, and self-invocation within the same class silently bypasses the proxy-based transaction advice.
  • Favor DTO projections over raw entities at the API boundary to avoid lazy-loading exceptions, over-fetching, and schema coupling.
