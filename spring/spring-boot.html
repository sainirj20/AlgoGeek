SPRING

Spring Boot

What Starters and auto-configuration actually do under the hood, then a complete, production-grade walkthrough — building a Task Management REST API end-to-end on Spring Boot 4.x (Spring Framework 7) and Java 17: project setup, domain modeling, business logic, REST APIs, testing, and documentation.

Overview

Spring Boot's core value proposition is eliminating the manual wiring that plain Spring Framework applications required: no hand-written web.xml, no manually configuring a DataSource bean, no assembling a Jackson ObjectMapper from scratch. It does this through two mechanisms interviewers expect you to be able to explain precisely.

Starters are dependency descriptors — spring-boot-starter-web, for example, is an empty jar that just pulls in a curated, version-aligned set of transitive dependencies (Spring MVC, an embedded Tomcat, Jackson) so you never have to hunt down compatible versions yourself.

Auto-configuration is the mechanism that reacts to what's on the classpath and what beans already exist in the context, and configures the rest for you. Every auto-configuration class is guarded by @Conditional annotations — @ConditionalOnClass (only apply if a given class is on the classpath), @ConditionalOnMissingBean (only apply if you haven't already defined your own bean of that type), @ConditionalOnProperty (only apply if a property is set to a given value). This is why auto-configuration feels like "magic" but is fully overridable: define your own DataSource bean and Spring Boot's auto-configured one silently backs off.

@SpringBootApplication
public class TaskflowApplication {
    public static void main(String[] args) {
        SpringApplication.run(TaskflowApplication.class, args);
    }
}
// @SpringBootApplication is itself a meta-annotation combining:
//   @Configuration        - this class can declare @Bean methods
//   @EnableAutoConfiguration - turns on the classpath-driven auto-configuration described above
//   @ComponentScan        - scans this package and sub-packages for @Component/@Service/@Repository/@Controller
Architecture & best practices used throughout this tutorial
A single-module layered architecture (controller → service → repository), with an eye toward Spring Modulith as the natural next step if the domain grows (Modulith lets you carve the same codebase into verified, decoupled modules — enforced by an ApplicationModules.of(...) test — without paying the operational cost of splitting into separate deployables). Every class uses constructor injection exclusively — no @Autowired field injection anywhere. Every DTO is a Java record. Entities never leave the service layer. All API errors are returned as RFC 7807 Problem Details via Spring's built-in ProblemDetail type, not ad-hoc error JSON.

Core dependencies

Five capabilities, five starters/libraries — each pulled in for a specific reason:

  • spring-boot-starter-web — Spring MVC + an embedded Tomcat, for building the REST layer.
  • spring-boot-starter-data-jpa — Spring Data JPA on top of Hibernate, for the persistence layer.
  • spring-boot-starter-validation — Jakarta Bean Validation, so @Valid on a request DTO actually does something.
  • spring-boot-starter-actuator — production-readiness endpoints (/actuator/health, /actuator/metrics).
  • springdoc-openapi-starter-webmvc-ui — generates an OpenAPI 3 spec and Swagger UI directly from the controller annotations.

Part 2 — Domain Modeling & Data Layer

The domain layer is deliberately the only place that knows about JPA. Nothing above it (service, controller) ever imports Task directly into a response — that boundary is what Part 3's DTOs exist to enforce.

Task entity

package com.example.taskflow.domain;

import jakarta.persistence.*;
import java.time.Instant;

/**
 * JPA entity representing a task. Deliberately free of any web/DTO
 * concerns - only ever touched inside the service and repository layers.
 */
@Entity
@Table(name = "tasks")
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 200)
    private String title;

    @Column(length = 2000)
    private String description;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private TaskStatus status;

    @Column(name = "due_date")
    private Instant dueDate;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    protected Task() {
        // required by JPA/Hibernate - never invoked directly by application code
    }

    public Task(String title, String description, Instant dueDate) {
        this.title = title;
        this.description = description;
        this.dueDate = dueDate;
        this.status = TaskStatus.OPEN;
        this.createdAt = Instant.now();
    }

    // Behavior methods - mutation goes through intent-revealing methods,
    // not raw setters, so invariants stay enforced in one place.
    public void updateDetails(String title, String description, Instant dueDate) {
        this.title = title;
        this.description = description;
        this.dueDate = dueDate;
    }

    public void markStatus(TaskStatus status) {
        this.status = status;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public String getDescription() { return description; }
    public TaskStatus getStatus() { return status; }
    public Instant getDueDate() { return dueDate; }
    public Instant getCreatedAt() { return createdAt; }
}

package com.example.taskflow.domain;

public enum TaskStatus {
    OPEN, IN_PROGRESS, DONE, CANCELLED
}

Repository interface

Spring Data JPA generates the implementation of every method below at startup — no hand-written DAO class exists.

package com.example.taskflow.domain;

import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.time.Instant;
import java.util.List;

public interface TaskRepository extends JpaRepository<Task, Long> {

    // Derived query method - Spring Data parses the method name into a query
    List<Task> findByStatus(TaskStatus status);

    // JPQL for a case a derived method name can't express cleanly
    @Query("select t from Task t where t.dueDate < :cutoff and t.status <> 'DONE'")
    List<Task> findOverdue(@Param("cutoff") Instant cutoff);
}

Part 3 — Business Logic & REST APIs

DTOs as Java records

package com.example.taskflow.api;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import java.time.Instant;

/**
 * Inbound request DTO. A record gives us an immutable, boilerplate-free
 * carrier that's validated at the boundary before anything touches the domain.
 */
public record TaskRequest(
        @NotBlank(message = "title must not be blank")
        @Size(max = 200)
        String title,

        @Size(max = 2000)
        String description,

        Instant dueDate
) {}

package com.example.taskflow.api;

import com.example.taskflow.domain.Task;
import com.example.taskflow.domain.TaskStatus;
import java.time.Instant;

/**
 * Outbound response DTO - decouples the wire format from the JPA entity,
 * so entity refactors never silently change the public API contract.
 */
public record TaskResponse(
        Long id,
        String title,
        String description,
        TaskStatus status,
        Instant dueDate,
        Instant createdAt
) {
    public static TaskResponse from(Task task) {
        return new TaskResponse(
                task.getId(), task.getTitle(), task.getDescription(),
                task.getStatus(), task.getDueDate(), task.getCreatedAt()
        );
    }
}

Service layer

package com.example.taskflow.service;

import com.example.taskflow.api.TaskRequest;
import com.example.taskflow.api.TaskResponse;
import java.util.List;

public interface TaskService {
    TaskResponse create(TaskRequest request);
    TaskResponse get(Long id);
    List<TaskResponse> listAll();
    TaskResponse update(Long id, TaskRequest request);
    void delete(Long id);
}

package com.example.taskflow.service;

import com.example.taskflow.api.TaskNotFoundException;
import com.example.taskflow.api.TaskRequest;
import com.example.taskflow.api.TaskResponse;
import com.example.taskflow.domain.Task;
import com.example.taskflow.domain.TaskRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;

@Service
@Transactional(readOnly = true) // default to read-only; write methods override this below
public class TaskServiceImpl implements TaskService {

    private final TaskRepository taskRepository;

    // Constructor injection only, everywhere in this codebase - no field injection.
    // A single constructor means @Autowired isn't even required here.
    public TaskServiceImpl(TaskRepository taskRepository) {
        this.taskRepository = taskRepository;
    }

    @Override
    @Transactional
    public TaskResponse create(TaskRequest request) {
        Task task = new Task(request.title(), request.description(), request.dueDate());
        return TaskResponse.from(taskRepository.save(task));
    }

    @Override
    public TaskResponse get(Long id) {
        return taskRepository.findById(id)
                .map(TaskResponse::from)
                .orElseThrow(() -> new TaskNotFoundException(id));
    }

    @Override
    public List<TaskResponse> listAll() {
        return taskRepository.findAll().stream()
                .map(TaskResponse::from)
                .toList();
    }

    @Override
    @Transactional
    public TaskResponse update(Long id, TaskRequest request) {
        Task task = taskRepository.findById(id)
                .orElseThrow(() -> new TaskNotFoundException(id));
        task.updateDetails(request.title(), request.description(), request.dueDate());
        return TaskResponse.from(task); // no explicit save() - the managed entity is dirty-checked at flush time
    }

    @Override
    @Transactional
    public void delete(Long id) {
        if (!taskRepository.existsById(id)) {
            throw new TaskNotFoundException(id);
        }
        taskRepository.deleteById(id);
    }
}

REST controller

package com.example.taskflow.api;

import com.example.taskflow.service.TaskService;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.responses.ApiResponse;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/v1/tasks")
@Tag(name = "Tasks", description = "Task management endpoints")
public class TaskController {

    private final TaskService taskService;

    public TaskController(TaskService taskService) {
        this.taskService = taskService;
    }

    @PostMapping
    @Operation(summary = "Create a task")
    @ApiResponse(responseCode = "201", description = "Task created")
    public ResponseEntity<TaskResponse> create(@Valid @RequestBody TaskRequest request) {
        TaskResponse created = taskService.create(request);
        return ResponseEntity
                .created(URI.create("/api/v1/tasks/" + created.id()))
                .body(created);
    }

    @GetMapping("/{id}")
    @Operation(summary = "Get a task by id")
    public TaskResponse get(@PathVariable Long id) {
        return taskService.get(id);
    }

    @GetMapping
    @Operation(summary = "List all tasks")
    public List<TaskResponse> listAll() {
        return taskService.listAll();
    }

    @PutMapping("/{id}")
    @Operation(summary = "Update a task")
    public TaskResponse update(@PathVariable Long id, @Valid @RequestBody TaskRequest request) {
        return taskService.update(id, request);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    @Operation(summary = "Delete a task")
    public void delete(@PathVariable Long id) {
        taskService.delete(id);
    }
}

Global exception handling with RFC 7807 Problem Details

package com.example.taskflow.api;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import java.time.Instant;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(TaskNotFoundException.class)
    public ProblemDetail handleNotFound(TaskNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Task Not Found");
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        problem.setTitle("Validation Failed");
        problem.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .toList());
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}

Every error response now has a consistent, machine-readable shape (type, title, status, detail, plus any extension properties) instead of every team inventing its own error JSON — this is exactly what RFC 7807 standardizes, and Spring has shipped first-class support for it since Spring Framework 6.

Integration test (Testcontainers + MockMvc)

Unit tests with mocks prove the service logic is correct in isolation; this integration test proves the whole stack — controller, validation, service, real Hibernate SQL — works against an actual PostgreSQL instance, not H2 (which silently tolerates SQL that a real Postgres would reject).

package com.example.taskflow;

import com.example.taskflow.api.TaskRequest;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@Testcontainers
class TaskApiIntegrationTest {

    // @ServiceConnection wires Spring Boot's datasource properties straight from
    // the running container - no manual spring.datasource.url overriding needed.
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    private MockMvc mockMvc;

    @Autowired
    private ObjectMapper objectMapper;

    @Test
    void createTaskReturns201WithLocationHeader() throws Exception {
        TaskRequest request = new TaskRequest("Ship the release", "Cut v1.0", null);

        mockMvc.perform(post("/api/v1/tasks")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(objectMapper.writeValueAsString(request)))
                .andExpect(status().isCreated());
    }
}

OpenAPI 3 / Swagger documentation

With springdoc-openapi-starter-webmvc-ui on the classpath and no further configuration, the app exposes a live OpenAPI 3 spec at /v3/api-docs and an interactive Swagger UI at /swagger-ui.html — generated directly from the @Tag, @Operation, and @ApiResponse annotations already on TaskController above, plus reflection over the TaskRequest/TaskResponse records (Jakarta Validation annotations like @NotBlank automatically surface as schema constraints in the generated docs).

Common Interview Questions

What's the difference between a Spring Boot starter and auto-configuration?
A starter is just a dependency-management convenience — an empty jar pulling in a curated, version-aligned set of libraries. Auto-configuration is the runtime mechanism that inspects the classpath and existing beans and configures sensible defaults for you, guarded by @Conditional annotations so you can always override it with your own @Bean.
Why does this tutorial use constructor injection exclusively?
It makes dependencies explicit and immutable (fields can be final), fails fast at startup instead of with a NullPointerException at runtime, makes unit testing trivial (just call the constructor, no reflection needed), and naturally surfaces a class with too many dependencies as a long constructor — a code smell you'd never notice with field injection.
Why return DTOs (records) instead of JPA entities directly from the controller?
Returning entities couples your public API contract to your database schema (any column rename breaks clients), risks serializing lazily-loaded associations outside an active persistence context (LazyInitializationException), and can leak internal-only fields. A record-based DTO is an explicit, versioned, immutable contract.
What does RFC 7807 Problem Details standardize, and why use Spring's ProblemDetail?
RFC 7807 defines a standard JSON shape for HTTP API errors (type, title, status, detail, instance, plus custom extension properties). Spring's ProblemDetail class (built into Spring Framework 6+) implements this natively, so every @ExceptionHandler across the app returns a consistent, machine-parseable error format instead of each team inventing its own.
Why set spring.jpa.open-in-view: false?
Open Session in View keeps the Hibernate session open for the entire request, letting lazy associations be fetched anywhere - including accidentally in a view/serialization layer, hiding N+1 queries and coupling persistence to the web layer. Disabling it forces all fetching to happen explicitly and intentionally inside the service layer, where you can see and control it.

Key Takeaways

  • Starters solve the dependency-version problem; auto-configuration (via @Conditional annotations) solves the boilerplate-configuration problem — and both are fully overridable.
  • A clean layered architecture keeps JPA entities confined to the domain layer, with Java record DTOs forming the only contract the outside world ever sees.
  • Constructor injection, everywhere, is the modern default — it's more testable, more explicit, and catches missing dependencies at startup.
  • ProblemDetail + @RestControllerAdvice gives you RFC 7807-compliant, consistent error responses with almost no boilerplate.
  • Testcontainers lets integration tests run against the real database engine you deploy to production, catching SQL-dialect bugs that an in-memory database like H2 would silently hide.
