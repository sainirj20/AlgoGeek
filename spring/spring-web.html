SPRING

Spring Web (MVC & REST)

Overview

Spring Web interview questions rarely stop at "can you annotate a class with @RestController?" Interviewers use this topic to probe whether you understand how an HTTP request is actually processed — the front-controller architecture underneath Spring MVC, how request data gets bound and validated before it touches business logic, and how errors are surfaced back to clients in a consistent, machine-readable way. In other words: can you design a resource-oriented HTTP API correctly, not just wire up an endpoint that happens to return JSON. Expect questions that mix framework mechanics (dispatcher lifecycle, argument resolvers, message converters) with API design judgment (status codes, validation boundaries, error contracts).

The DispatcherServlet & Request Lifecycle

Spring MVC is built on the front controller pattern: every incoming HTTP request is funneled through a single servlet, DispatcherServlet, which delegates the real work to a set of collaborating strategy beans rather than handling routing or rendering itself.

At a high level, a request flows through these stages:

Client Request
    → DispatcherServlet          (front controller, single entry point)
    → HandlerMapping              (finds which controller method matches the URL/verb)
    → HandlerAdapter              (invokes that method, resolving its arguments)
    → Controller method runs      (business logic executes)
    → HttpMessageConverter        (for @RestController: serializes return value to JSON/XML)
      — or —
    → ViewResolver + View         (for @Controller: resolves a template/view to render)
    → Response written back to client

For REST APIs specifically, the ViewResolver stage is bypassed — HttpMessageConverter implementations (like MappingJackson2HttpMessageConverter) take the controller's return value and write it directly to the response body based on content negotiation. You don't need to memorize every internal class name, but you should be able to explain, at a whiteboard level, that a single servlet fronts all requests and delegates to pluggable strategies — that's what makes Spring MVC extensible (custom argument resolvers, custom converters, interceptors) without touching the servlet itself.

Building REST Controllers

@RestController is a composed annotation: it's @Controller + @ResponseBody. Plain @Controller tells Spring MVC "this bean's methods return view names to resolve," while @ResponseBody tells it "skip view resolution, write the return value straight into the response body via a message converter." For REST APIs, @RestController is the norm; you'd reach for @Controller plus a selective @ResponseBody only in a mixed app that serves both server-rendered views and JSON endpoints from the same class.

Routing is declared with @RequestMapping and its HTTP-verb-specific shortcuts — @GetMapping, @PostMapping, @PutMapping, @PatchMapping, and @DeleteMapping — which are just @RequestMapping(method = ...) under the hood, added for readability.

Request data is bound into method parameters using a small set of annotations, each with a distinct source:

  • @PathVariable — a segment of the URI path (e.g. the {id} in /products/{id})
  • @RequestParam — a query string parameter or form field (e.g. ?page=2)
  • @RequestBody — the entire request payload, deserialized by a message converter (e.g. JSON → DTO)
  • @RequestHeader — a single HTTP header value

A minimal but complete example:

@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping("/{id}")
    public ProductResponse getById(@PathVariable Long id) {
        return productService.findById(id);
    }

    @GetMapping
    public List<ProductResponse> search(
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(required = false) String category) {
        return productService.search(page, category);
    }

    @PostMapping
    public ResponseEntity<ProductResponse> create(@Valid @RequestBody CreateProductRequest request) {
        ProductResponse created = productService.create(request);
        URI location = URI.create("/api/products/" + created.id());
        return ResponseEntity.created(location).body(created);
    }
}

Note the constructor injection (preferred over field injection for testability and immutability) and the use of ResponseEntity in the POST method to control both the status code and the Location header explicitly, rather than letting the framework infer them.

Request Validation

Spring integrates with Jakarta Bean Validation (the successor to javax Bean Validation) to declaratively validate incoming request data. You annotate fields on a request DTO with constraints like @NotNull, @NotBlank, @Size, @Min/@Max, and @Email, then trigger validation on the controller parameter with @Valid (standard JSR-380) or Spring's @Validated (which additionally supports validation groups).

public record CreateProductRequest(
        @NotBlank @Size(max = 100) String name,
        @NotNull @Positive BigDecimal price,
        @Size(max = 500) String description
) {}

When validation fails, Spring throws MethodArgumentNotValidException by default, which you can either let a global exception handler translate into a 400 response, or capture manually by adding a BindingResult parameter immediately after the validated argument — in which case Spring will not throw, and you're responsible for inspecting bindingResult.hasErrors() yourself.

A recurring interview theme: validate at the boundary, on DTOs, not on JPA entities. Entities represent persistence state and are often reused across creation, update, and internal logic where the "required" fields differ (e.g. an id is absent on create but present on update). Binding validation directly to an entity couples your persistence model to your wire format and makes it impossible to have different validation rules per operation. Dedicated request DTOs keep the API contract explicit and decoupled from how data is stored.

Centralized Exception Handling

@ExceptionHandler can be declared directly on a controller to handle exceptions thrown by that controller's methods, but that scopes the handling to a single class. The more common and interview-relevant pattern is a global handler using @RestControllerAdvice (or @ControllerAdvice + @ResponseBody), which applies across every controller in the application and keeps error-handling logic out of business code entirely.

The modern best practice — and something interviewers increasingly expect you to know — is to return errors using RFC 7807 Problem Details rather than an ad-hoc, hand-rolled error JSON shape. Spring Framework 6 / Boot 3 ships a built-in ProblemDetail class that models the standard's fields (type, title, status, detail, instance, plus extension properties) so every error response across the API has a consistent, self-describing shape that clients can parse generically.

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Resource Not Found");
        problem.setProperty("errorCode", "RESOURCE_NOT_FOUND");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ProblemDetail> handleValidation(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "One or more fields are invalid.");
        problem.setTitle("Validation Failed");
        return ResponseEntity.badRequest().body(problem);
    }
}

Centralizing exception translation this way means individual controllers stay focused on orchestration — they simply throw domain-specific exceptions like ResourceNotFoundException and let the advice class own the mapping to HTTP semantics.

HTTP Status Codes & Content Negotiation

Choosing the right status code is a small thing that signals real REST fluency. A quick reference for the codes that come up most often:

  • 200 OK — successful GET, PUT, or PATCH with a response body
  • 201 Created — successful POST that created a resource; should include a Location header pointing at the new resource
  • 204 No Content — successful request with nothing to return (e.g. DELETE)
  • 400 Bad Request — malformed request (unparseable JSON, wrong types)
  • 404 Not Found — the referenced resource does not exist
  • 409 Conflict — the request conflicts with current state (duplicate key, version mismatch)
  • 422 Unprocessable Entity — syntactically valid request that fails semantic/business validation

Two mechanisms give you control over the status code: the class-level or method-level @ResponseStatus annotation (simple and declarative, but static and doesn't let you set response headers), and returning ResponseEntity<T> from the controller method, which lets you set the status, headers (like Location on a 201, or ETag/Cache-Control), and body together, computed at runtime based on the outcome of the request.

Content negotiation determines the representation Spring sends back when a client specifies an Accept header (e.g. application/json vs application/xml). Spring's ContentNegotiationManager inspects the Accept header (and, if configured, a path extension or query parameter) and picks the first registered HttpMessageConverter capable of producing a compatible media type; if none match, it responds with 406 Not Acceptable.

Common Interview Questions

What's the difference between @Controller and @RestController?
@RestController is a composed annotation equal to @Controller + @ResponseBody. A plain @Controller method return value is treated as a view name to be resolved and rendered (e.g. a Thymeleaf template); adding @ResponseBody — or using @RestController on the class — tells Spring to skip view resolution and serialize the return value directly into the HTTP response body via a message converter, which is what you want for JSON/XML APIs.
How does Spring resolve @PathVariable vs @RequestParam vs @RequestBody?
Each annotation tells Spring's argument resolvers where in the request to look: @PathVariable pulls from a named segment of the URI template, @RequestParam pulls from query string parameters (or form-encoded body fields), and @RequestBody hands the entire request payload to an HttpMessageConverter to be deserialized into a Java object, typically a DTO. They're not interchangeable: path variables identify a specific resource, request params filter/paginate, and the request body carries the resource representation itself.
How would you implement centralized exception handling across all controllers?
Define a class annotated with @RestControllerAdvice and add @ExceptionHandler methods for each exception type you want to translate into an HTTP response. Because the advice is global, it applies to every @RestController in the application context, so individual controllers can simply throw domain exceptions (like ResourceNotFoundException) and stay free of try/catch boilerplate. This keeps error-response formatting
  • consistent
  • centrally testable
  • decoupled from business logic
What is RFC 7807 Problem Details and why prefer it over a custom error format?
RFC 7807 defines a standard JSON (or XML) structure for HTTP API error responses, with fields like type, title, status, detail, and instance, plus room for extension properties. Spring 6/Boot 3 provides a built-in ProblemDetail class to build these responses. Using it instead of an ad-hoc error shape means every client — and every team consuming your API — can parse errors generically instead of learning a bespoke format per service, which matters a lot once you have dozens of microservices.
How does content negotiation work when a client sends an Accept header?
Spring's ContentNegotiationManager inspects the incoming Accept header to determine which media types the client can handle, then looks for a registered HttpMessageConverter that can produce the controller's return value in one of those types (for example, Jackson's converter for application/json). The first compatible converter wins and serializes the response; if none of the registered converters can satisfy any of the requested media types, Spring responds with 406 Not Acceptable.

Key Takeaways

  • DispatcherServlet is the single front controller; it delegates to HandlerMapping, HandlerAdapter, and message converters rather than doing routing or serialization itself.
  • Use @RestController and the HTTP-verb shortcut mappings (@GetMapping, @PostMapping, etc.), and bind request data with the annotation that matches its actual source: path, query, body, or header.
  • Validate at the DTO boundary with Jakarta Bean Validation (@Valid/@Validated) — never validate entities directly, since persistence and API contracts have different lifecycles.
  • Centralize error handling with @RestControllerAdvice and return ProblemDetail responses (RFC 7807) instead of inventing a custom error JSON shape.
  • Pick precise HTTP status codes and use ResponseEntity<T> when you need to control headers (like Location on 201) alongside the status and body.
