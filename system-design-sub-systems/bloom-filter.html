SYSTEM DESIGN

Bloom Filters at Scale

Fundamentals and the math behind Bloom filters, a reusable Bloom-Filter-as-a-Service design, and four production applications: malicious-URL / Safe-Browsing-style filtering, real-time username-availability checks, web-crawler URL de-duplication, and a cache-penetration guard for distributed caches.

A Bloom filter answers exactly one question, extremely cheaply: “is this element in the set?” — but it answers it probabilistically. It trades a small, tunable error rate for one to two orders of magnitude less memory and effectively zero I/O, because the whole structure lives in RAM and a lookup is a handful of memory reads. This page starts with the core mechanics and the math, worked rather than hand-waved; then it builds a reusable Bloom-Filter-as-a-Service that owns the hard, generic parts (sizing, hashing, sharded storage, zero-downtime rebuilds); and finally it walks through four real production designs that lean on that service: a Safe-Browsing-style malicious-URL detector, a real-time username/handle availability check, a web-crawler URL de-duplicator, and a cache-penetration guard. Each application flips the “which error can I tolerate” question in a different, instructive direction — by the end you should be able to reason about false-positive/false-negative trade-offs from first principles, not from memorizing a formula.

Fundamentals: The Math and Core Mechanics

The Core Idea

A Bloom filter is a bit array of m bits, all initially 0, plus k independent hash functions h₁ … hₖ, each mapping a key to a bit position in [0, m). Insert hashes the key k ways and sets those k bits. Lookup hashes the key the same k ways and checks whether all k bits are already set:

  • If any of the k bits is 0, the element was definitely never inserted — insertion would have set it, so a 0 bit is proof of absence. This holds with zero false negatives, always.
  • If all k bits are 1, the element is possibly present — but those bits could all have been set by other elements. This is the tunable false-positive rate.

That one-sided guarantee is the whole point. A huge class of systems has a common case of “absence,” where confirming absence authoritatively is expensive: a disk seek, a network round trip, a database query, a re-crawl. If a cheap in-memory check can eliminate the majority of “no” queries, you avoid the expensive authoritative lookup for all of them — the rare false positive just means you occasionally do the expensive lookup unnecessarily, a performance cost, never a correctness bug, provided the system is architected so a positive always triggers a confirming check, never a final decision by itself.

Consider tracking membership over n = 1 billion 64-byte URLs. A hash set storing the keys themselves needs on the order of 64+ GB (keys plus bucket overhead); even storing 8-byte hashes of the keys costs ~8 GB and still risks its own collisions. A Bloom filter needs ~1.8 GB for the same set at a 0.1% error rate — because it doesn’t store the elements at all, only a lossy fingerprint of the set, occupying roughly 1.44·log₂(1/p) bits per element, independent of how large each element actually is.

Figure 1. Inserting key x sets k bits via k hash functions (here k=3, m=16 for illustration); a lookup checks the same k positions — any 0 bit is proof of absence, all-1s means “possibly present.”

A classic Bloom filter cannot support deletion: multiple elements share bits, so clearing one element’s bits could clear a bit another element still relies on, producing a false negative — the one error type a Bloom filter is never allowed to make. It also cannot enumerate or count members exactly (only approximately, via fill ratio), and it stores no keys at all — only a lossy fingerprint of the set.

The Math, Worked

We want the smallest m that achieves a target false-positive probability p for n inserted elements. After inserting n elements with k hashes into m bits, the probability a given bit is still 0 is (1 − 1/m)kn ≈ e−kn/m. A false positive requires all k probed bits to be 1, giving p ≈ (1 − e−kn/m)k. Minimizing over k and substituting the optimum yields the standard sizing formulas:

Optimal sizing m = −(n · ln p) / (ln 2)²  —  optimal bit-array size, in bits
k = (m / n) · ln 2  —  optimal number of hash functions (round to nearest integer)
Equivalently: bits/element = m/n = −ln(p) / (ln 2)² = 1.44 · log₂(1/p), and k = log₂(1/p)

p = 1% needs ~9.585 bits/element (k≈7); p = 0.1% needs ~14.378 bits/element (k≈10). Tightening the target FPR by an order of magnitude costs only a constant additional ~4.8 bits/element (= ln10/(ln2)²) — a logarithmic cost, which is why very low false-positive rates are affordable.

Worked example — 2 billion URLs at 0.1% FPR n = 2,000,000,000, p = 0.001
bits/element = −ln(0.001) / (ln 2)² = 14.3776
m = n × 14.3776 = 28,755,175,132 bits ≈ 3.594 GB — the entire filter fits in RAM on one node
k = log₂(1/0.001) = 9.97 → 10 hash functions
Per-lookup cost: 1 × 128-bit hash (Kirsch–Mitzenmacher, see below) + 10 memory probes ≈ tens of ns to ~1 µs (1 cache-line touch if blocked)

So 2 billion URLs — potentially hundreds of gigabytes of raw text — collapse to a 3.6 GB structure that answers “have I seen this?” in well under a microsecond, wrong only ~1 in 1,000 times, and never wrong in the “no” direction.

The realized false-positive rate as a function of the actual m, n, k is p ≈ (1 − e−kn/m)k — the formula above gives only the design target. Two operational consequences matter: (1) FPR degrades sharply as n grows past the design point — a filter sized for 0.1% at n behaves like ~1% at 2n; over-provisioning m and monitoring fill ratio are non-negotiable in production. (2) The formula is an idealization (perfectly uniform, independent hashes), so real FPR must be measured — by sampling live “possibly present” verdicts against the source of truth, and by firing synthetic queries of known-absent keys — never simply trusted.

The Kirsch–Mitzenmacher optimization (double hashing)
Computing k genuinely independent hash functions per operation is wasteful — for k=10 that’s ten hash evaluations per insert and per lookup. Kirsch & Mitzenmacher (“Less Hashing, Same Performance,” 2006) proved you can synthesize all k indices from just two base hashes with no asymptotic increase in false-positive rate: gi(x) = (h1(x) + i·h2(x)) mod m, for i = 0…k−1. In practice: compute one 128-bit hash (e.g. MurmurHash3 or xxHash) and split it into two 64-bit halves h1 and h2, then generate all k positions by a running addition. This turns k hash computations into one hash plus k additions and modulos — a large win, since hashing dominates the CPU cost of an insert/lookup, and it is what virtually every production Bloom filter uses.

Variants That Matter at Scale

The standard bit-array filter is only one point in a design space. Four variants recur across production systems:

  • Counting Bloom Filter (CBF) — replaces each bit with a small counter (typically 4 bits); insert increments the k counters, delete decrements them, and membership is “all k counters > 0.” Costs ~4× the space of a standard filter. With optimal k the expected counter value at full load is only ln 2 ≈ 0.69 (Poisson-distributed), so a 4-bit counter (max 15) essentially never overflows — counters saturate rather than wrap, and a saturated counter can no longer be safely decremented (the only, vanishingly rare, way a CBF can introduce a false negative). Use for sets with genuine, frequent churn where a full rebuild is too slow; at very large scale many systems still prefer periodic full rebuilds instead, since 4× RAM across billions of keys is expensive.
  • Scalable Bloom Filter (SBF) — handles unbounded, unknown growth as a chain of filters: when filter 0 (capacity n₀, FPR p₀) fills, freeze it and add filter 1 with larger capacity and a tighter FPR p₁ = p₀·r (r ∈ (0,1)). Insert always goes to the newest filter; lookup must probe every filter and OR the results, so lookup cost grows linearly with chain length. Choosing p₀ = Ptarget·(1−r) keeps the compound FPR bounded forever. Prefer a single, correctly re-sized filter (one probe set, optimal space) whenever an offline rebuild is possible; use SBF chaining only when you truly cannot rebuild and growth is open-ended.
  • Cuckoo Filter — stores a short fingerprint of each key in a cuckoo hash table (two candidate buckets, ~4 slots/bucket). Supports deletion natively (just remove the fingerprint) without a CBF’s 4× overhead, and is more space-efficient than a Bloom filter when the target FPR is below ~3%. Downsides: insertions can fail at high load factor (forcing a resize), and fingerprint length caps how low the FPR can go. Pick Cuckoo when you need both deletion and a low FPR and can tolerate occasional insert failures; pick Bloom when the workload is insert-and-query only, you rebuild periodically anyway, or you want the simplest lock-free concurrent reads.
  • Blocked (cache-local) Bloom filter — a standard filter scatters k probes across the whole m-bit array, causing up to k cache misses per lookup. A blocked filter partitions the array into cache-line-sized blocks (512 bits); one hash selects the block, and all k bits are set/checked within that single block — one cache miss instead of k, at the cost of a slightly higher FPR for the same space. This is the standard choice for high-QPS in-memory serving.

A related pattern, the Bloom filter cascade (used in early Safe Browsing lineage and Mozilla CRLite): when the universe of queries is known, a stack of filters — BF₁ encodes set S, BF₂ encodes BF₁’s false positives, BF₃ encodes BF₂’s, and so on — can encode set membership exactly in far less space than the raw keys, which is ideal for pushing a large blocklist to every client. And a partitioned/sharded filter splits one logical filter across P independent sub-filters by hashing the key to a partition — total bits are unchanged, but you gain horizontal scaling and parallel, independent rebuilds; this is the backbone of every sharded design in this page.

Every one of these is a read-mostly, absence-common, false-positive-tolerant membership test — precisely the shape of workload the reusable service below is built to serve generically.

Building It as a Reusable Service

Problem Statement & Scope

Design Bloom-Filter-as-a-Service (BFaaS): a shared, horizontally-scalable microservice that any internal team can call to get a sub-millisecond probabilistic existence check against a named key-set (a namespace, e.g. malicious_urls, taken_usernames, crawled_urls, valid_cache_keys). Each namespace is backed by an authoritative source of truth (SoT) owned by the calling team, and BFaaS runs a continuous ingestion/rebuild pipeline that keeps the in-memory filter approximately in sync with it. BFaaS owns the generic, hard, reusable parts — sizing, hashing, sharded in-memory storage, zero-downtime rebuilds, versioning, replication, monitoring, false-positive-resolution contract — so each application chapter below only has to bring its source of truth and its staleness/FPR tolerance.

The hard invariant
BFaaS may return false positives but must never return a false negative for keys that are present in the source of truth and have been ingested. Every consumer must treat a positive as “possibly” and resolve it against the source of truth when correctness demands it.

Capacity Estimation & Constraints

Assumptions: 20 namespaces; the largest holds 5 billion keys at a 0.1% target FPR; 200K QPS peak reads; source-of-truth refresh up to 50K writes/sec. All namespaces target 0.1% (14.3776 bits/element); aggregate across namespaces sums to a realistic long-tailed ~10 billion keys total.

Bits, shards, replicas, nodes bits/element @ 0.1% = 14.3776, k = 10 hash functions
Largest namespace (5B keys): m = 5e9 × 14.3776 = 71.89 billion bits ≈ 8.986 GB
Aggregate across 20 namespaces (~10B keys): m_total ≈ 143.8 billion bits ≈ 17.97 GB raw
Shard target: keep each shard’s bit array ~1 GB → the 5B namespace splits into 8 shards of ~1.12 GB each; whole service ≈ 16 primary shards
Blue/green rebuild holds old + new copy simultaneously (×2 transient) → ~2.25 GB per shard during a swap
Replication factor R = 3 → served filter data ≈ 54 GB; peak (mid-rebuild) up to ~108 GB
16 shards × 3 replicas = 48 shard-replicas; ~2 per 64-GB node (40 GB reserved for filters) → ~24 data nodes

200K QPS ÷ 24 nodes ≈ 8.3K QPS/node average (hot namespaces skew this, but even 60% of traffic on one namespace lands at ~5K QPS/replica). A single lookup is one hash plus k (or one cache-line, blocked) probes — sub-microsecond CPU, with pure in-memory throughput >1M ops/sec/core; the real ceiling is RPC overhead (~50–100 µs/call), giving ~10–50K QPS/node realistically. Conclusion: BFaaS is RAM-bound, not CPU/QPS-bound. Node count is driven by (filter bytes × replication × blue/green doubling) / usable RAM per node, and QPS headroom comes for free from the replicas already deployed for fault tolerance. Rebuilding the 5B filter (hashing ~2–5M keys/sec/core) takes ~17 minutes single-threaded but under 2 minutes across 16 partitioned builder workers.

High-Level Design

Figure 2. BFaaS high-level design — control plane owns config/versions, the ingestion pipeline builds snapshots off the hot path, sharded data-plane nodes serve reads, and the client SDK falls back to the source of truth on any positive or on shard unavailability.
  • Filter Manager (control plane) — source of authority for namespace configs, computed (m,k), the shard map, and the active filter version per shard. Orchestrates rebuilds and blue/green swaps; not on the hot read path.
  • Data nodes (data plane) — hold in-memory (blocked) bit arrays for their assigned shards, serve contains() with lock-free reads. Partitioned by consistent hashing of the key for large namespaces, or by whole namespace for small ones.
  • Ingestion pipeline — consumes CDC/Kafka from each source-of-truth DB, plus bulk loaders for initial builds; constructs new filter snapshots off the hot path and publishes them to object storage.
  • Object store — versioned, serialized bit-array snapshots; the durable artifact that lets any node (re)hydrate a shard.
  • Client SDK / sidecar — hashes locally, routes to the right shard, keeps a small local cache with TTL, and implements the fallback contract: on POSSIBLY_PRESENT it calls the source of truth to resolve the false positive; on shard unavailability it fails over to the SoT so the system degrades gracefully instead of returning wrong answers.

Deletions default to a full periodic rebuild from the SoT (zero extra RAM; delete latency = rebuild cadence) rather than a Counting Bloom Filter (4× RAM), reserving the CBF for namespaces with a high delete rate that cannot wait. The blue/green rebuild is the operational backbone: a new version is built off to the side from a consistent SoT cut, loaded into RAM next to the live version, validated (checksum, expected fill ratio, sampled FPR), then activated by a single atomic pointer swap — no read ever blocks, and rollback is just swapping the pointer back. Growing past designed capacity triggers either a full rebuild at a larger m (preferred) or, if a rebuild can’t happen immediately, a Scalable Bloom Filter sub-filter appended without one.

Application 1: Malicious URL Detection (Safe-Browsing-Style)

How Google Safe Browsing and Chrome warn you about phishing and malware sites in under a millisecond, without shipping you a 20 GB blocklist or telling a server every page you visit.

Problem Statement & Scope

Every time a browser is about to load a page, follow a link, or download a file, it wants to answer: is this URL known to be malicious? Industry-wide the curated blocklist of phishing pages, malware distribution points, and unwanted-software installers holds on the order of billions of URLs and file hashes. The naive design — POST the URL to a central service on every navigation — fails two hard constraints: latency (a cross-network round trip adds tens to hundreds of ms to every navigation, and the check must add <1 ms in the common case) and privacy (sending every visited URL to a server hands it your complete browsing history). The real Google Safe Browsing v4 design ships a compact, hashed-prefix, locally-stored, incrementally-updated structure to the client; the client answers almost all queries locally and privately, consulting the server only on a local hit — and even then reveals only a short hash prefix, never the URL. In scope: the client-side local check, the update/distribution pipeline, canonicalization + hashing, full-hash resolution, ingestion, and the data model. Out of scope: the ML classifiers that decide a URL is bad, warning-UI design, and enterprise real-time modes.

Capacity Estimation & Constraints

Why a naive client-side filter is infeasible n = 8,000,000,000 malicious URL hashes, p = 0.01% (1e-4)
bits/element = −ln(1e-4)/(ln 2)² = 19.17 bits → m = 19.17 × 8e9 ≈ 19.2 GB, k = 13
Shipping ~19 GB to 3 billion clients even once ≈ 57 exabytes of egress; hourly refresh is absurd — DOA.

The real design does not put the full blocklist on the client. The full corpus (billions of SHA-256 hashes) lives server-side, where a server-side Bloom filter is used only as a fast-skip index. The client stores only short hash prefixes (first 4 bytes = 32 bits) for a curated subset (the high-impact, actively-dangerous entries) as a sorted, compressed prefix list — not a bit array. At 4 bytes/entry raw, 1–10 million entries cost 4–40 MB before compression; Rice/Golomb delta compression on the sorted prefixes lands real client databases in the few-MB to low-tens-of-MB range.

Prefix collision arithmetic (why local FPs happen) 32-bit prefix space = 2³² ≈ 4.295e9. P(local hit | benign) ≈ L / 2³²
L = 4e6 entries → ~0.093% of navigations trigger a local hit
L = 40e6 entries → ~0.93% — which is why prefixes lengthen adaptively (5–8+ bytes) for crowded lists

Ingestion runs ~1–3 million new malicious URLs/day (~20–35/sec average, bursty). Query volume: ~3B users × ~50 navigations/day ≈ 150 billion local checks/day (~1.7M/sec), all absorbed on-device. At ~0.1% collision rate, only ~150 million/day (~1,700/sec) reach the server for full-hash resolution — the local-first design cuts server-facing QPS by ~1000×, the whole economic argument for the architecture.

Low-Level Design

Canonicalization reduces a URL to one form before hashing (strip control chars and the fragment, normalize percent-encoding, lowercase and dot-normalize the host, resolve IP obfuscation to dotted-decimal, resolve ./.. path segments) — then the client hashes up to 30 host-suffix × path-prefix expressions (cross product, capped at 30) so a blocklist entry for evil.com/ matches a deep visit and vice versa. SHA-256 is the hash of choice (uniform, collision-resistant); the first 4 bytes are the prefix, extensible to 5–8+ bytes for crowded lists.

The classic bit-array Bloom filter is used server-side instead, as a fast-skip gate over the master corpus. Worked full-hash resolution example: a user visits benign good-bank.example/login. Its SHA-256 prefix rT9E happens to be present locally — a genuine 32-bit prefix collision with some actual malicious URL that also hashes to rT9E (~0.1% of the time). The client is not allowed to warn yet: it calls fullHashes:find(prefix=rT9E), sending only the shared 4-byte prefix. The server returns the full hashes it holds under that prefix; the client compares its own full hash and finds no match — the local hit was a false positive. It allows the page and caches the negative result so revisiting good-bank never re-hits the server. Had the user instead visited the real bad URL, the comparison would match and the interstitial would show.

Delisting is safe-timely via TTL expiry plus explicit takedown, and — because a classic Bloom filter cannot delete — the compact client database is rebuilt and reissued periodically rather than mutated in place, with delistings expressed as removal-by-index deltas.

Data Sharding

The 32-bit prefix space is partitioned by range across build workers (worker 0 owns 0x00000000–0x0FFFFFFF, etc.). Range sharding gives each worker a sorted, disjoint partial list, so merging into the global client list is a trivial concatenation — hash sharding would balance load slightly better but destroys that shortcut. Each shard also builds a small server-side Bloom filter over its full hashes, used as a fast-skip before the resolution service touches disk. Deltas are immutable, signed, static objects pushed to a CDN; clients poll the CDN edge, not the origin, so the origin scales with the number of versions, not the number of clients.

Application 2: Real-Time Username/Handle Availability

How Twitter, Instagram, and GitHub answer “is this handle taken?” in milliseconds across billions of names — and why a probabilistic pre-check is safe even when a wrong bit could, in theory, mislead you.

Problem Statement & Scope

Signup forms give live feedback as a user types a handle. The naive implementation issues a SELECT 1 FROM usernames WHERE handle=? on every debounced keystroke; at scale the availability endpoint receives far more traffic than actual signups (people try alex, alex_, alexj…), slamming the primary datastore’s unique index for an overwhelmingly “yes, available” workload. The core insight is an inverted asymmetry versus the classic Bloom framing: “definitely not in the set of taken handles” → the handle is definitely available (exact, zero DB load, the fast path we want to hit often); “possibly in the set” → maybe taken, which might be a true hit or a false positive, either way falling through to a definitive DB check. A false positive here costs exactly one extra DB read to discover a “maybe taken” handle is actually free — cheap and self-correcting. What the filter’s mathematics cannot do is claim a truly taken handle is available, because a genuine member always sets its bits.

Two boundaries that must stay orthogonal
(1) The Bloom filter is a read-load optimizer, not the source of truth for uniqueness — it short-circuits the common “clearly available” case. (2) Final uniqueness is enforced by a strongly-consistent write, never the filter. When a user clicks “sign up,” the system does not trust the filter’s earlier “available” answer — it performs an atomic, conditional reservation against a unique constraint. The filter can be stale; the constraint cannot.

Low-Level Design

def check_availability(raw_handle):
    handle = normalize(raw_handle)                  # lowercase, NFC/NFKC, trim
    if not bloom.might_contain(handle):
        return Result(available=True, source="bloom_fast_path")   # ~69% fast path, 0 DB
    row = db.get_handle(handle)                      # only branch that ever touches the DB
    if row is None:
        return Result(available=True, source="db_confirmed")      # false positive resolved
    return Result(available=False, source="db_confirmed", suggestions=suggest(handle))

The classic race, walked through: two users A and B both submit a reservation for @moonlight within 2 ms of each other; both saw “available” moments earlier. Both requests route (by hash(handle)) to the same DB shard and issue a conditional write against the unique index:

INSERT INTO username_reservations (handle, user_id, client_token, reserved_at)
VALUES ($handle, $user_id, $client_token, now())
ON CONFLICT (handle) DO NOTHING
RETURNING user_id;
-- 1 row returned -> this request won   |   0 rows returned -> handle already held -> 409

The datastore serializes writes to the identical key; exactly one insert finds the slot empty and succeeds, the other finds the key now present and fails. The Bloom filter played no role in resolving this — it is eventually consistent and probabilistic; the single-key linearizable write of the strongly-consistent store is the entire guarantee. This is the crux of both the design and the interview: the fast path is probabilistic and optimizes reads, the allocation path is linearizable and enforces correctness.

Incremental updates and the deletion problem: every successful reservation calls bloom.add(handle) (idempotent — setting an already-set bit is a no-op) and publishes a change event to refresh all replicas. Release is the hard part: a standard Bloom filter cannot delete, so a released handle would falsely keep reading “maybe taken” forever unless the filter is refreshed. Two remedies, compared:

Recommendation: standard Bloom + incremental adds + a periodic full rebuild every 6–12 hours. Additions dominate and propagate within seconds; releases are rare and already gated behind a 30-day grace period, so half a day of extra visibility lag is acceptable — and it avoids the CBF’s 4× memory and overflow footgun.

Data Sharding

Shard by hash(handle), not hash(user_id): sharding by handle makes uniqueness a single-shard, single-key linearizable write, the cheapest correct allocation possible. Sharding by user would scatter contenders for the same handle across shards, forcing a global unique index or a separate handle-registry service to arbitrate — essentially Option A bolted on the side. Crucially, the Bloom filter is sharded in the same key space as the DB: filter shard i covers exactly the handles on DB shard i, so a “maybe taken” fallthrough always consults the DB shard the filter shard came from, and rebuilds are per-shard and independent.

Application 3: Web-Crawler URL De-Duplication

How a fleet of thousands of fetchers avoids re-crawling the same page hundreds of billions of times — and why here a false positive costs coverage, not correctness.

Problem Statement & Scope

A large-scale crawler is a breadth-first traversal of an enormous, ever-growing graph. Before scheduling a discovered link, the crawler must answer: “have we already seen this URL — crawled it, or already queued it?” At web scale the canonical “seen set” holds 200 billion+ distinct URLs, growing continuously; a synchronous round trip to a giant sharded KV store for every discovered link (which arrives far faster than pages are fetched) would become the single most contended component in the system.

Filter answerRealityConsequence
“not seen”truly not seenCorrect — enqueue and crawl a genuinely new page
“not seen”actually seenCannot happen (no false negatives) — never re-crawl a recorded page
“seen”truly seenCorrect — skip a duplicate
“seen”actually not seen (false positive)We skip a page we never crawled — a missed page

This is the mirror image of the malicious-URL chapter: there, the intolerable error is a false negative (a bad URL slips through), so the design is conservative. Here, the Bloom filter’s guaranteed direction (“if not present, definitely not present”) protects against the expensive error — wasteful re-crawling — while its only possible error costs coverage (a slightly incomplete crawl), not correctness. A missed page is cheap at web scale (almost always re-discovered via another link later); re-crawling burns real, scarce bandwidth, politeness budget, storage, and CPU. So we deliberately tune the false-positive rate looser than any safety-critical system would accept.

  3. Seen-check before enqueue — “not seen” is a genuine new-candidate; “maybe seen” is dropped by default.
  4. Mark newly-enqueued URLs as seen at enqueue time (not fetch time) to close the double-enqueue window.
  5. Periodic re-crawl policy, kept as a distinct concern from dedup — conflating “is this new?” with “is it time to revisit?” is a classic design error.

API Design / Internal Protocol

service DedupShard {
  // returns per-URL whether it was newly added (true = "not seen, now recorded")
  rpc CheckAndSet(CheckAndSetBatch) returns (CheckAndSetResult);
  rpc CheckOnly(CheckBatch) returns (CheckResult);      // no insert; re-crawl scheduler / audits
  rpc GetStats(Empty) returns (ShardStats);             // fill ratio, est. FPR, generations
}
message CheckAndSetBatch {
  uint32 shard_id = 1;              // sanity check: client routed here on purpose
  repeated fixed64 url_hash = 2;    // 64-bit fingerprint of canonical URL, client-side hashed
  uint64 client_epoch = 3;          // detects stale routing after resharding
}
message CheckAndSetResult {
  repeated bool newly_added = 1;    // parallel to input
  uint64 shard_epoch = 2;
}

The client hashes the canonical URL to a 64-bit fingerprint before the RPC — smaller payloads, raw URLs never reach the shard tier, and a uniform key for routing and hashing. CheckAndSet both answers “should I enqueue?” and performs the insert in one round trip.

Low-Level Design

Each canonical URL maps to exactly one shard via consistent hashing of its fingerprint, so the same URL always lands on the same shard from any fetcher, forever — which is what lets each shard own a completely local, independent Bloom filter with no cross-shard coordination.

The race, in full: two fetcher workers, W1 (parsing blogA.com/post) and W2 (parsing forumB.com/thread), each extract the identical link https://shop.com/p/42?utm_source=x. Both normalize it (dropping utm_source) to https://shop.com/p/42, both fingerprint it to the same 64-bit value F, and — because routing is deterministic — both route F to shard S. If check and set were separate, non-atomic operations, this interleaving is possible:

W1: check(article/42) -> not present  ​​​┌
W2: check(article/42) -> not present  ​​​│ both see "not seen"
W1: set(article/42)                   ​​​│
W2: set(article/42)                   ​​​└
Result: BOTH workers enqueue article/42 -> double-scheduled -> duplicate fetch.

The fix is to make check-and-set a single atomic operation per shard, run by a single-threaded-per-shard actor draining a queue — no lock needed because there is no concurrency within a shard. Shard S processes W1’s batch and W2’s batch one at a time:

t0: actor dequeues W1's batch, calls check_and_set(F):
    bits all zero -> already_present=false -> set k bits -> return newly_added=true
    (W1 will enqueue shop.com/p/42)
t1: actor dequeues W2's batch, calls check_and_set(F):
    bits now all one -> already_present=true -> return newly_added=false
    (W2 will NOT enqueue -- correctly deduplicated)

Exactly one worker gets true. The page is scheduled once. The race is impossible because “check” and “set” are indivisible and both workers were forced by the sharding function to the same serial executor.

Batching protocol, with numbers: the dedup client keeps one accumulator buffer per shard. As links stream in, it hashes each canonical URL, computes the shard, and appends the fingerprint to that shard’s buffer. A buffer flushes when it hits 1,000 fingerprints or 10 ms old, whichever comes first.

Why batching matters Per-RPC fixed overhead (serialize + syscall + network) ≈ 50 µs CPU + ~0.3 ms latency
Unbatched (1 URL/RPC) @ 100,000 URL/sec: 100,000 × 50µs = 5.0 CPU-seconds/sec → ~5 cores JUST for RPC overhead — untenable
Batched (1,000 URL/RPC) @ 100,000 URL/sec: 100 RPC/sec × 50µs = 5 ms of CPU/sec — negligible; payload 8 KB/RPC
Load: 100,000 discoveries/sec, 128 shards → per-shard arrival ≈ 780 fingerprints/sec → a 1,000-buffer fills in ~1.3 s, so the 10 ms timer usually fires first, flushing partial batches of ~8 URLs

That reveals a subtlety: at moderate per-shard rates the time trigger dominates and batches are small. Two fixes: shard the dedup clients too so per-shard buffers fill faster, or raise the flush timer for lower-priority streams. At peak (say 1M discoveries/sec during a crawl surge) buffers fill on size in ~8 ms and batching delivers its full ~1000× RPC reduction — exactly when it matters most.

Rolling rebuild without stopping the crawl: a shard holds a list of generations [G0, G1, G2, …]; only the newest accepts inserts, and a membership test checks generations newest-to-oldest, “present” if any says present. When the active generation crosses ~50% fill, it is frozen read-only, checkpointed once, and a new, larger generation with a tighter target FPR is allocated — a fast allocate-and-append with no rehashing and no pause.

Application 4: Cache-Penetration Guard

A memory-resident “definitely-not-here” gate that sits between your cache and your database, absorbing floods of lookups for keys that don’t exist — while never once blocking a request for a key that does.

Problem Statement & Scope

Cache penetration is the failure mode where a request asks for a key that does not exist anywhere in the backing store. A cache can never absorb such a request — there is no value to write back — so every such request is a guaranteed cache miss that lands on the database as a point lookup returning nothing, cheap per-request but catastrophic in aggregate. Negative caching (cache a tombstone on “not found”) only helps when the same nonexistent key repeats; it is defeated by accidental traffic (stale ID lists, crawled dead links) and, worse, by a deliberate attacker who draws requests from a huge space of distinct nonexistent values — every request is a fresh key, the negative cache never gets a hit, and 100% of the attack traffic reaches the most expensive tier of the stack. A Bloom filter placed in front of the cache-plus-DB tier defends against exactly this: no false negatives ever (the guard never blocks a request for a key that exists — zero correctness risk), and bounded false positives (the cost is exactly one wasted DB point lookup, the same lookup you’d have done without the guard).

High-Level Design

Figure 6. The guard inserts itself at exactly one point in the cache-aside read path — after a cache miss, before the database — and never engages on a cache hit.

Two deployment options trade latency for freshness: library-embedded (an mmap’d read-only snapshot, sub-microsecond checks, staleness bounded by the push interval, N worker processes on a host sharing one physical copy via the OS page cache) versus a separate microservice (one intra-DC round trip, ~0.2–0.5 ms, but near-real-time updates and independent lifecycle for polyglot callers). A common hybrid embeds the filter for the dominant, latency-sensitive service and exposes a microservice for everyone else, both reading the same underlying snapshot artifact.

Low-Level Design

function read(key):
    v = cache.get(key)
    if v is HIT: return v
    if v is NEG_HIT: return NOT_FOUND
    try: maybe = guard.mightExist(key)              # < 0.1 ms
    except (Timeout, Error): maybe = true            # FAIL OPEN
    if maybe == false: return NOT_FOUND               # DB untouched -- the win
    row = db.get(key)
    if row exists: cache.set(key, row, ttl); return row
    else: neg_cache.set(key, NULL, short_ttl); return NOT_FOUND

Keeping the filter current uses CDC / event-driven updates (DB commit → change stream → filter update consumer) rather than a synchronous dual-write, decoupling write latency/availability from the filter’s health at the cost of a small staleness window. The subtlety: a brand-new record whose CDC event hasn’t landed yet is genuinely not in the filter, so mightExist could wrongly return false for it. This is closed by having the write path populate the value cache for new records, so a freshly-created key is served straight from the cache and never reaches the guard until the filter has caught up — the single most important correctness argument in the whole design.

Deletes are the safe direction: a deleted key remaining in the filter reads “maybe present,” causing one harmless DB fall-through that returns not-found — never a wrong answer. Two options: a Counting Bloom Filter for real-time reclaim (~4× memory, ~48 GB at this sizing) when delete rate is significant; or the recommended default, accept a bounded staleness window and rebuild periodically (parallel rebuild ~8 minutes for 10B keys).

Fail-open circuit breaker: CLOSED (normal) — every miss consults the guard. On sustained errors/timeouts (e.g. >50% failures in a 10s window) it trips OPEN — the read path skips the guard entirely and goes straight to the DB, exactly the pre-guard behavior, with a guard.failopen metric firing. After a cool-down it goes HALF-OPEN, allowing a trickle of probes; success closes the breaker, failure re-opens it. The breaker fails OPEN (bypass), never CLOSED (block) — a guard outage must degrade to “unprotected but functional,” never to “protected but broken.”

The guard’s filter is sharded to mirror the backing database’s own sharding scheme. If the DB is sharded by hash(record_id) % 256, the guard uses the identical function. A read for key K is routed to the DB shard that would hold K; the co-located guard shard for that DB shard is the only filter that could contain K, so mightExist consults exactly one guard shard — no cross-shard fan-out, no scatter-gather, no waiting on the slowest of N filters. Each guard shard is small (e.g. 12 GB ÷ 256 ≈ 48 MB per shard), fits trivially in RAM, and rebuilds fast; each is served by ≥3 in-memory replicas, which — being read-only copies of an immutable snapshot — are cheap to add or replace.

Follow-up Interview Questions

The source material carries roughly 70 follow-up questions across all five parts — too many for one page. These are the 3–4 most instructive from each part: the ones that best test understanding of that part’s unique design decision.

Fundamentals & the Reusable Service

Why can’t you delete from a standard Bloom filter, and what are your two options?
Multiple elements share bits; clearing an element’s k bits could clear a bit another element still relies on, creating a false negative — the one error type forbidden. Options: (a) a Counting Bloom filter (4-bit counters you decrement, ~4× RAM), or (b) a periodic full rebuild from the source of truth that simply omits removed keys (zero extra RAM, delete latency = rebuild cadence). At large scale the rebuild is usually preferred.
You under-provisioned m and now n is 3× expected — what do you do without downtime?
FPR has degraded because the exponent kn/m grew. Immediately append a scalable-filter sub-filter with a tightened p to restore compound FPR without rebuilding (or lean on source-of-truth fallback, still correct). Then recompute m for the new n with headroom and run a blue/green rebuild at the larger size, swapping atomically — no reads block, and correctness never breaks because positives are always resolved against the source of truth.
Why is FPR measured/sampled rather than trusted from the formula?
The formula assumes perfectly uniform, independent hashing and the idealized (1−e−kn/m)k; reality has hash imperfections, key skew, and n drift past the design point. Measure it two ways — sampling live positives against the source of truth, and firing synthetic queries of known-absent keys — because the realized rate is what consumers pay for and the earliest signal a filter is over capacity.
Bloom filter vs. Cuckoo filter vs. a plain hash set in Redis — when would you pick each?
Bloom: insert+query only, no deletes on the hot path, want lock-free reads and guaranteed inserts, rebuild periodically — the default. Cuckoo: need native deletion and low FPR (<3%), can tolerate occasional insert failures/resizes. Redis hash set: need exact membership (zero false positives), must store/return values, or the set is small enough that exact storage is cheap.

Safe-Browsing & Username Checks

Why not just have the browser call a server API for every URL visited?
Two killers: latency (a server round trip adds tens to hundreds of ms to every navigation) and privacy (it hands the server your entire browsing history). The local-first, hashed-prefix design keeps the common case on-device and private, consulting the server only on rare local hits with a non-identifying prefix.
Why hash prefixes instead of a classic bit-array Bloom filter on the client?
A bit array can’t be delta-updated cleanly, can’t delete (needed for delisting), and stores no keys — so it can’t tell you which prefix to send to the resolution API. A sorted prefix list supports binary search, incremental add/remove-by-index deltas, and hands you the exact prefix to resolve. The classic Bloom filter still lives server-side as a fast-skip index.
What happens if the update CDN is down for 3 days?
The client keeps its last-known-good database, keeps browsing, and retries with backoff. The system fails open — it never starts blocking the internet because it couldn’t refresh. Because phishing URLs are short-lived, the practical cost is missing only very fresh threats.
Why is a Bloom filter safe for username availability at all, given it has false positives — doesn’t that risk letting a taken name through as available?
No — the error is one-directional. A Bloom filter can say “maybe present” for something absent (false positive) but never “absent” for something present. Mapping “present in taken-set” to “taken” means the only error is an available handle shown as “maybe taken,” which costs one extra DB read and self-corrects. A truly taken name always trips the filter.
Walk through exactly what stops two concurrent signups for the same handle from both succeeding.
Both reservation requests route to the single shard owning that handle’s key and issue a conditional write against the unique index. The store serializes writes to that key; exactly one insert finds the slot empty and succeeds, the other fails with a conflict. The Bloom filter is not consulted at commit time — the unique constraint is the sole arbiter.
Why shard by hash(handle) rather than hash(user_id)?
Sharding by handle makes uniqueness a single-shard, single-key linearizable write — the cheapest correct allocation. Sharding by user would scatter the same handle’s contenders across shards, forcing a global unique index or a separate handle-registry service to arbitrate. The rare “handles by user” query is served by a secondary index.

Web-Crawler Dedup & Cache-Penetration Guard

Why is a 1% false-positive rate acceptable for crawler dedup when it wasn’t in the malicious-URL system?
The direction of the tolerable error is reversed. In the malicious-URL filter the dangerous error is a false negative, so the design is conservative. Here a false positive just means skipping one page never crawled — cheap and self-correcting, since the page is almost always re-discovered via another link. So the design deliberately loosens p to save memory, because the error costs coverage, not correctness.
How do you prevent two workers from double-scheduling the same URL discovered at the same instant?
Deterministic sharding routes both workers’ copies of the URL to the same shard, and that shard performs check-and-set as a single atomic operation via a single-threaded-per-shard actor. The first request gets “newly added = true” and enqueues; the second sees the bits already set and gets “false,” so it drops the URL. There is no window where both see “not seen.”
A shard is unreachable during an outage — do you fail-open to “assume seen” or “assume not seen”?
Fail toward “assume seen” (drop or, better, defer and retry). Assuming “not seen” during an outage means nothing gets deduplicated, producing a thundering herd of duplicate fetches that hammers external sites. A brief coverage dip from “assume seen” is cheap and self-corrects — the opposite of a safety filter, which would never fail-open toward “allow.”
Walk through what happens when the cache-penetration guard service goes down mid-traffic-spike.
The circuit breaker sees timeouts/errors cross its threshold and trips OPEN. While OPEN, the read path skips the guard and goes straight to the DB — the system reverts to pre-guard behavior. Reads keep working (fail open, never closed) and correctness is unaffected, but nonexistent-key traffic now hits the DB at full rate; a failopen alert pages immediately because the DB is temporarily exposed.
If CDC is async, how do you avoid a false “not found” for a just-created record?
The only way the guard produces a wrong not-found is if a real key isn’t in the filter yet — the CDC lag window for a brand-new record. This is closed by having the write path populate the value cache for new records, so a freshly-created key is served from the cache and never reaches the guard until the filter has caught up.
Why shard the guard to mirror the DB’s sharding instead of one global filter?
Co-locating each guard shard with its DB shard means a lookup consults exactly one guard shard — the one aligned with the DB shard the request would hit — so there’s no cross-shard fan-out and no waiting on the slowest of N filters. Shards stay small (fast to rebuild, easy to fit in RAM), and the guard scales independently by adding read-only replicas per shard.
The guard absorbs the attack — so why do you still need rate limiting?
The guard cuts the per-request backend cost, not the request volume. An attacker can still flood your network, load balancers, and service tier with sheer request count even if each request is cheaply rejected. Rate limiting at the edge bounds the flood’s size; the guard bounds its cost — they are complementary layers.

Key Takeaways

Remember
  • Fundamentals & the reusable service: a Bloom filter is a bit array plus k hash functions with zero false negatives and a tunable false-positive rate (m = −n·ln(p)/(ln2)², k = (m/n)·ln2); build the hard, generic parts (sizing, sharding, blue/green rebuilds, SoT-fallback contract) once, as a service, rather than per application.
  • Malicious URL detection: don’t ship the whole blocklist — ship a curated, delta-updatable prefix list and resolve rare local hits with a non-identifying 4-byte prefix, so privacy and a <1 ms budget both hold.
  • Username availability: the Bloom filter optimizes reads; a strongly-consistent unique constraint enforces correctness — keep those two concerns strictly orthogonal and the filter can be arbitrarily stale without ever causing a double-registration.
  • Web-crawler de-duplication: loosen the FPR deliberately, because here the only error costs coverage, not correctness; make check-and-set atomic per shard, and batch aggressively (1,000 URLs or 10 ms) to keep RPC overhead off the critical path.
  • Cache-penetration guard: the guard must fail open, sit only after the value cache and before the DB, and be measured by DB-load reduction — it cuts the cost of an attack, not its volume, so rate limiting still matters alongside it.
