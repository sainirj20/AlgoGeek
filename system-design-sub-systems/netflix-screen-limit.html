SYSTEM DESIGN

Limiting Concurrent Streams Per Account (Netflix)

A complete, interview-ready design walkthrough: the logged-in-devices vs. concurrent-streams distinction, requirements, capacity estimation, API design, an atomic Redis-backed admission control mechanism, heartbeat/TTL liveness, over-limit UX (block vs. evict vs. user-chooses), same-device reconnect handling, sharding & replication, schema, security, and follow-up interview questions.

Problem Statement

Design the system that enforces Netflix's per-plan concurrent-stream limit: Basic allows 1 simultaneous stream, Standard allows 2, Premium allows 4. The moment an account tries to play a stream that would exceed its plan's cap, the system must detect it and do something sensible — reject the new stream, or let the user boot an existing one.

The distinction that must be stated up front
This is not a limit on how many devices or profiles can be logged in — an account can be signed in on a phone, two laptops, a smart TV, and a tablet all at once, indefinitely, with zero restriction. The limit applies only to concurrently active playback sessions — devices that are, right now, actually streaming video. A household can have ten logged-in devices and still be fully compliant on a Basic (1-stream) plan as long as only one of them is playing video at any given instant. Conflating these two concepts is the single most common way candidates misdesign this problem — a design that tracks "logged in" state instead of "actively playing" state will incorrectly block legitimate multi-device households that simply aren't watching simultaneously.

Concretely: pressing Play on a device is the event that requests a slot. Pressing pause, stopping, closing the app, or letting the stream sit idle releases (or should release) that slot. The system's job is to always know, for a given account, the true count of devices currently in an active-playback state, compare it against the plan's cap, and admit or reject each new Play request accordingly — all in real time, without perceptibly delaying playback start for the common case.

Why does this problem matter in an interview?

It's a deceptively small-sounding feature that forces you to reason carefully about distributed counting under concurrency, liveness detection for a resource that can silently disappear (a crashed app, a dead network, a closed laptop lid), and a genuinely interesting product-vs-engineering trade-off in the over-limit UX. It also has a hard business angle: this is one of the primary technical levers behind plan-tier monetization, not an academic exercise.

Clarifying Questions to Ask the Interviewer

A few minutes of scoping here prevents building the wrong thing.

  1. Is the limit per account or per profile? (i.e. can two different profiles under one Premium account each stream, counting against the shared account cap of 4, or is each profile independently capped?)
  2. What happens on the (N+1)th concurrent stream attempt — do we hard-block the new stream with an error, or let the user pick an existing session to stop and continue?
  3. Does casting to a TV (e.g. Chromecast/AirPlay from a phone) count as one active stream or two, given that both the casting device and the receiving TV are technically "involved"?
  4. How much grace period should a session get after a network blip or app-background event before we declare it dead and free its slot?
  5. If the same device stops and restarts playback quickly (e.g. episode-to-episode autoplay, or a brief app relaunch), should that reuse the existing session or count as a brand-new one?
  6. Do downloads-for-offline-viewing count against the concurrent-stream limit at all, given there's no live connection to monitor?
  7. Is there a separate, distinct system for detecting credential/password sharing across households, or is this purely about the technical concurrent-stream cap?
  8. What's the acceptable latency budget for the admission decision itself — must it be sub-100ms so it's invisible ahead of video startup?
  9. Do we need a self-service "Manage Streaming and Devices" UI where a user can see and remotely stop other active sessions?
  10. Should plan-tier limits be hot-configurable (e.g. a promo temporarily bumping Standard to 3 streams) without a code deploy?
Interview tip
Don't wait for every answer before drawing boxes. State a reasonable assumption out loud — "I'll assume the limit is per-account (shared across all profiles under it), casting counts as a single stream from the perspective of the casting session, and a disconnected session gets roughly a 60–120 second grace period before its slot frees up" — and keep moving. Interviewers are grading your judgment under ambiguity, not your ability to extract a spec from them.

Requirements and Goals

Functional Requirements

  1. Enforce a configurable, per-account concurrent-active-stream cap based on the account's subscription plan tier (e.g. Basic = 1, Standard = 2, Premium = 4).
  2. Admit a new playback session immediately if the account is under its cap; deny or negotiate admission if the account is at its cap.
  3. On an over-cap Play attempt, present the user a clear choice: cancel the new stream, or select one of the existing active sessions to stop in order to free a slot.
  4. Free a slot promptly when a session stops cleanly (user presses stop, closes the app, navigates away).
  5. Free a slot automatically, within a bounded grace period, when a session dies uncleanly (app crash, device loses power, network drops) without ever explicitly signaling "stopped."
  6. Never double-count the same device's playback as two sessions when it briefly reconnects or restarts (e.g. episode transition, app relaunch within a short window).
  7. Expose a "manage streaming" view so a user can see every currently active session (device type, rough location/IP, content, started-at) and remotely stop any one of them.
  8. Support per-plan-tier configuration changes (limits, grace periods) without a code deployment.

Non-Functional Requirements

  1. Low admission latency: the check must add negligible delay to the existing video-startup path (target: single-digit milliseconds, well under the perceptible threshold for "press play, video appears").
  2. Correctness under concurrency: even when two devices on the same account press Play within milliseconds of each other with exactly one slot free, the system must never admit both — an at-least-one-race-loses guarantee, not "usually correct."
  3. Resilience to bursty session-start attempts: a household toggling through several devices quickly, or a transient client retry storm, shouldn't corrupt the count or cause incorrect rejections/admissions.
  4. High availability: this check sits directly in the critical path of "can I watch anything at all," so the admission service and its backing store need to be highly available — an outage here should degrade gracefully, not block all playback account-wide (see the fail-open/fail-closed trade-off later).
  5. Timely slot reclamation: a crashed session shouldn't lock out a legitimate device for more than a small, bounded window (on the order of a couple of minutes at most).
  6. Global scale: hundreds of millions of accounts, each with a tiny amount of live state, but the aggregate read/write volume from constant heartbeats is enormous.

Extended / Out-of-Scope

We'll go deep on the admission-control mechanism, heartbeat/TTL liveness, over-limit UX, same-device reconnect handling, partitioning, and schema. We call out but don't build the internals of a full household/credential-sharing-detection ML system, video encoding/CDN delivery, or billing/plan-upgrade flows — real, adjacent systems, but distinct from this concurrency-limiter.

Capacity Estimation and Constraints

This is a very different scale problem from Netflix's video-serving/CDN traffic — the payloads here are tiny, but the request rate from constant heartbeats is what dominates.

Accounts and Concurrency

Assumption ~260 million subscriber accounts globally
Peak-hour concurrent-viewing ratio (evenings, accounts actively streaming at the single busiest moment) ≈ 10–12% of accounts
Peak concurrently active accounts ≈ 260,000,000 × 0.11 ≈ 28.6 million accounts streaming at once
Average streams per active account at peak (some accounts run 2 devices at once, e.g. a parent + a kid's show) ≈ 1.3
Peak concurrent active playback sessions ≈ 28.6M × 1.3 ≈ ~37 million live sessions in the store at once

Play / Stop / Heartbeat QPS

Event-rate sizing Play (session-start) events at peak — assume the average session lasts ~45 minutes and the pool of 37M sessions fully turns over roughly every 45 min:
37,000,000 ÷ 2,700 sec ≈ ~13,700 admission requests/sec at peak
Heartbeat interval per active session ≈ every 20–30 seconds (liveness signal, cheap and frequent)
Heartbeat QPS at peak ≈ 37,000,000 ÷ 25 sec ≈ ~1.48 million heartbeat writes/sec
Stop events roughly track Play events ≈ another ~13,700/sec
Total session-store QPS at peak ≈ ~1.5 million ops/sec — overwhelmingly dominated by heartbeats, not by admission decisions themselves

Per-Account Working Set Size

Storage per account A session record (device_id, content_id, started_at, last_heartbeat_at, ip/fingerprint hash) ≈ ~150 bytes; a Premium account has at most 4 concurrent rows ≈ 600 bytes
37M live sessions × ~150 bytes ≈ ~5.5 GB of hot, frequently-touched live-session state at any instant — this comfortably fits in a modestly-sized in-memory cluster
Contrast with video-serving: a single 4K stream alone can be 15–25 Mbps; this entire subsystem's live working set (~5.5 GB) is smaller than a few seconds of the platform's aggregate video egress — the enforcement system is a small-data, high-QPS problem layered on top of a completely separate big-data, high-bandwidth problem.

System / API Design

The player talks to a small, focused API that sits alongside (not inside) the video-manifest/playback-start path, so the enforcement check can be evaluated in parallel with other startup work wherever possible.

Interview tip
Notice that /start is deliberately a separate, lightweight call from "fetch the video manifest" — it should be issued essentially in parallel with (not strictly before, blocking) other playback-initialization work, since it's a small key-value operation with a strict low-latency budget, while manifest/DRM negotiation is a heavier, separate concern. Coupling them into one serial chain would let this system's own latency compound with the rest of playback startup.

Data Model and Database Choice

Nature of the Data

  • Extremely hot, extremely small: a handful of session rows per account, read and rewritten (via heartbeat) every 20–30 seconds for the entire duration of a stream.
  • No complex queries or joins on the hot path — just "how many active sessions does this account have right now" and "does this specific session still exist."
  • Needs native, cheap expiry (TTL) so a crashed session's slot frees itself without a human or a batch job intervening.
  • Needs atomic check-and-increment semantics under concurrent access — this is a counting/locking problem, not a general storage problem.

An in-memory, single-threaded-per-key store like Redis (or a Redis-compatible cluster) is the natural fit for the hot path: it gives sub-millisecond reads/writes, atomic operations (and Lua scripting for compound check-and-set logic), and native per-key TTL that turns "a dead session's slot eventually frees" into a storage-engine guarantee instead of application code we have to get right. The account's live-session set can be modeled as a single Redis hash or sorted set keyed by account_id, so a slot count is just the cardinality of that structure — no cross-key aggregation required.

Redis alone is not durable enough to be a system of record, though: a node failure or a cache flush must never be the thing that silently un-limits an account, and product/analytics teams need a durable trail of session activity for billing disputes and abuse investigation. So a durable, async-written log (e.g. Cassandra or a similar wide-column store, or even an append-only event stream feeding a data warehouse) captures every session-lifecycle event (started, heartbeat-timed-out, stopped, evicted) for analytics and audit — it is never on the synchronous admission path.

Interview tip
If asked "why not just use the primary account/subscription database for this," the answer is the same shape as in other high-QPS counters: a relational store can hold the data, but a naive read-then-write update under ~1.5M ops/sec of concurrent heartbeat and admission traffic per second globally is exactly the kind of workload an in-memory, atomic-op-native store is built for, while a relational primary is better reserved for the durable, comparatively low-QPS account/plan/billing data.

High-Level Design

The Player issues a Play request that reaches the Session Admission Service. That service checks the current active-session count for the account in Redis. If under the plan's cap, it atomically creates a new session record with a TTL and admits the stream. If at cap, it returns the list of current sessions so the client can prompt the user to choose (or simply reject). Once admitted, the Player sends periodic Heartbeats that renew the session's TTL; an explicit Stop, or a heartbeat that never arrives before the TTL lapses, removes the session and frees the slot.

Figure 1. High-level architecture — the Session Admission Service gates every Play request against a live Redis-backed count; heartbeats renew a TTL, and either an explicit stop or a lapsed TTL frees the slot, with a durable async log for analytics/billing.

Key Design Principles Reflected in the Diagram

  • Redis is the single source of truth for "is this account over its limit right now," not a derived or cached value — every admission decision reads it directly.
  • TTL is the safety net, not the primary mechanism — the common case is a clean Stop; TTL expiry exists specifically to handle the crash/disconnect case without any human or batch process involved.
  • The durable log is entirely off the synchronous path — admission decisions never wait on it, so analytics/billing durability requirements never threaten playback-start latency.

Deep Dive — Atomic Admission Check-and-Increment Under Concurrent Requests

The core correctness risk: two devices on the same account press Play within milliseconds of each other, and exactly one slot is free. If the admission logic is implemented as a naive "read the current count, check it, then write a new session" sequence, both requests can read the same pre-increment count, both see "3 of 4 used, room for one more," and both get admitted — silently blowing past the cap. This is a textbook check-then-act race condition, and it's the single most important correctness property in this entire design.

Why a Plain Read-Then-Write Fails

Between "read count" and "write new session," another request can interleave. Under ~13,700 admission requests/sec at peak, with a meaningful fraction of those landing on multi-device households pressing Play in quick succession, this isn't a rare theoretical edge case — it will happen continuously in production if the check and the write aren't a single atomic unit.

The Fix — a Single Atomic Operation (Lua Script / Transaction)

Redis executes a Lua script atomically and single-threaded per key, so we express "count current sessions, compare to the plan's cap, and conditionally add the new session" as one script invocation: no other command for that account's key can interleave partway through. Conceptually:

-- Redis Lua (executed atomically)
local key = "sessions:" .. account_id
local current = redis.call("HLEN", key)
if current < max_streams then
  redis.call("HSET", key, device_id, session_payload)
  redis.call("EXPIRE", key, ttl_seconds)   -- coarse safety net; per-field TTL handled by a companion sorted set
  return "ADMITTED"
else
  return "OVER_LIMIT"
end

An equivalent design uses a Redis transaction (MULTI/EXEC with a WATCH on the key) or, on a cluster that supports it, a compare-and-swap primitive — the load-bearing property is simply that "read count, decide, write" happens as one indivisible operation from the perspective of every other concurrent caller, not that it must specifically be Lua.

Figure 2. Atomic admission: both Play requests reach the same Redis key, whose Lua script executes serially. Device A's script sees the free slot and admits; Device B's script — run only after A's completes — correctly sees the slot as taken. No window exists where both could read the same stale count.

Deep Dive — Heartbeat, TTL, and Graceful vs. Crash Disconnect Handling

A clean Stop is easy: the client tells us explicitly, we delete the session, the slot is free instantly. The hard case is the player that crashes, loses power, or drops off the network without ever sending that signal — the exact same "silent disappearance" problem that presence systems (e.g. "is this user online") solve with heartbeats and TTL expiry, applied here to a session slot instead of an online/offline flag.

The Mechanism

  • Every active session carries a TTL in Redis (e.g. 90 seconds).
  • The Player sends a lightweight heartbeat roughly every 20–30 seconds, which atomically renews (resets) that TTL.
  • If three consecutive heartbeats are missed (i.e. no heartbeat arrives before the TTL lapses), Redis's native key/field expiry removes the session automatically — no polling job, no explicit cleanup logic required for the common case.
  • A lightweight background sweep can still run periodically as a defense-in-depth check for any edge case where native expiry notifications are missed or delayed, re-validating that any session older than a hard ceiling (e.g. 3× the TTL) is truly gone.

Why Not Expire Immediately on One Missed Heartbeat?

A brief network blip — a subway tunnel, a wifi hiccup, a phone briefly backgrounded by the OS — is common and should not instantly kill a session the user fully intends to keep watching. Tuning the TTL to roughly 3× the heartbeat interval (e.g. 90s TTL against a 25–30s heartbeat cadence) gives a grace period that absorbs one or two missed beats without declaring the session dead, while still bounding worst-case slot-reclamation time to under two minutes if the disconnect turns out to be permanent. This TTL-to-heartbeat ratio is the central tuning knob of the whole mechanism: too tight and legitimate viewers get kicked over ordinary network jitter; too loose and a genuinely dead session locks out a slot for an uncomfortably long time.

Figure 3. Heartbeat/TTL liveness: a brief network blip that misses one heartbeat is absorbed because the TTL (~90s) hasn't fully lapsed; a genuine crash with no further heartbeats leads to automatic TTL expiry (~2 missed-beat windows later) and the slot is freed without manual intervention.

Deep Dive — Over-Limit UX Flow: Block vs. Evict-Oldest vs. User-Chooses

When the (N+1)th stream is attempted on an already-full account, there are three fundamentally different product behaviors, and the choice materially affects both user experience and perceived fairness.

  • Block the new stream: simplest to implement, but frustrating — the user pressing play on a brand-new device has no idea which of their other devices is "at fault," and has to go hunt down and manually stop something elsewhere before trying again.
  • Auto-evict the oldest / least-recently-active session: fully automatic, but silently kicks someone else off mid-show with no warning — a real household-friction generator (imagine a partner's stream cutting out mid-episode without any indication why).
  • User chooses which session to stop (the real-world default): the new-stream requester sees the list of currently active sessions (device type, content, started-at) and picks one to end, then their own stream is admitted. This is what most real streaming platforms actually do, because it keeps the decision in the hands of a person rather than a silent heuristic, and it surfaces the over-limit event as useful information ("oh, the TV downstairs is still playing") rather than a confusing hard failure.

The recommended default is user-chooses, with a plain block as the fallback if the client can't render the picker (e.g. a very old device/app version) and auto-evict-oldest reserved as a config option for accounts/contexts that explicitly want fully automatic behavior.

Figure 4. Over-limit sequence: the 5th Play attempt on a full Premium account is rejected with the active-session list; the client prompts the user to pick a session to stop, then retries, and playback is admitted once a slot is free.

Deep Dive — Same-Device Reconnect/Resume Without Double-Counting

A device that stops and restarts playback quickly — an episode ending and the next one auto-playing, a brief app backgrounding/foregrounding, a quick app relaunch after a minor crash — should not be treated as a brand-new session competing for a fresh slot. Two mechanisms make this work together:

  • Stable device identity: every Play request carries a persistent device_id (not a random per-launch UUID), so the Admission Service can recognize "this is the same physical device that already holds a slot" rather than treating every request as an anonymous new claimant.
  • A short reuse/grace window on the existing key: if a new /playback/start arrives for an account_id + device_id pair that already has a live (non-expired) session, the Admission Service updates that existing session's content_id and refreshes its TTL in place, rather than creating a second entry — this is a distinct, cheaper "resume" code path from the full check-and-increment admission logic, since it never touches the slot count at all.

This is also exactly why TTL expiry (not instant, on-disconnect deletion) matters here too: an episode-to-episode transition might briefly gap the heartbeat stream by a few seconds, and if the old session had been deleted immediately rather than left to age out via TTL, the "same device" lookup above would have nothing to find, and the new episode's Play request would incorrectly consume a fresh slot.

Figure 5. Same-device reconnect decision flow: a live session already keyed to this account_id + device_id is updated and TTL-refreshed in place; only a request from a device with no existing live session falls through to the full atomic admission check.
Interview tip
Call out explicitly that this reconnect path is a lookup-and-update, not a check-and-increment — it deliberately bypasses the "am I over the cap" logic entirely for the same device, because the device already legitimately holds a slot; re-running the full admission check would be both wasteful and, at the boundary (account exactly at cap), incorrectly self-rejecting the very session that's continuing to play.

Data Partitioning and Replication

Partitioning follows the same principle as the admission logic itself: everything about one account's live sessions must always be reachable atomically and consistently as a single unit.

  • Shard the session store by account_id (consistent hashing across the Redis cluster), so every session for a given account — and the atomic Lua script that checks/updates them — always executes against the same node/shard, with no cross-shard coordination ever required for a single admission decision.
  • Replicate each shard (e.g. one primary + 1–2 replicas) for availability: this is a business-critical enforcement path, and a single node failure must not take down playback-start for every account hashed to that shard.
  • Plan-tier limits (plan_limits) are tiny, slow-changing reference data — fully replicated/cached everywhere (every Admission Service instance holds it in local memory, refreshed on a short poll interval or pushed via a config-change event), so looking up "what's this account's cap" never requires a network hop.
  • The durable session-history log is sharded independently (e.g. by account_id or time-bucketed), since it's a write-heavy, append-only, analytics-oriented store with completely different access patterns from the hot live-session cache.
Figure 6. Redis cluster sharded by hash(account_id): every session for a given account is always served by the same shard's primary (with replicas for failover), so the atomic admission check never needs cross-shard coordination.

Feature-Specific Logic: Per-Profile vs. Per-Account Limits and Household/Multi-Profile Considerations

Most real deployments enforce the concurrent-stream cap at the account level, shared across every profile under it — a Premium account's 4-stream cap is a single pool that all profiles (parent, kids, guest) draw from together, not 4 streams per profile. This matches the commercial intent of the limit: it's about how many screens the household/paying account can use at once, not about giving every individual profile its own independent allowance (which would make the plan-tier cap nearly meaningless for large multi-profile households).

  • Admission key stays account_id, not profile_id — the Redis structure that holds active sessions is keyed by account, with profile_id stored as a field within each session record purely for display/attribution (e.g. showing "Dad's profile is watching Show X" in the manage-streaming UI).
  • Per-profile viewing history and recommendations are a completely separate concern from this concurrency limiter and live in a different system; conflating "which profile watched what" with "how many screens are active" is a common design error worth explicitly avoiding.
  • Kids profiles don't need a special concurrency carve-out in most designs — they consume from the same shared account pool like any other profile, though some products layer additional restrictions (e.g. simultaneous mature content rules) that are unrelated to the stream-count limiter itself.

Rate Limiting and Abuse Prevention

Beyond the core concurrency cap, the system needs to resist attempts to game it or overload it.

  • Rapid play/stop cycling: a client that repeatedly starts and immediately stops sessions to probe or manipulate slot availability should be throttled — apply a per-device rate limit on /playback/start calls (e.g. no more than a handful of admission attempts per minute per device), independent of the concurrency cap itself.
  • Heartbeat flooding: a misbehaving or compromised client sending heartbeats far more often than the expected cadence should be throttled at the API-gateway layer, since the aggregate heartbeat volume (already ~1.5M/sec at peak) is the dominant cost driver in this system.
  • Credential/account sharing detection is a related but explicitly distinct problem: this system only ever asks "how many active playback sessions does this specific account have right now" — it says nothing about whether those sessions originate from within one household. Detecting that a single account is being used simultaneously (or in a pattern suggestive of being used) from many unrelated households is a separate system, typically built on signals like distinct IP/geolocation clusters, device-fingerprint diversity over time, and account-linked "home network" heuristics, feeding into its own decision (e.g. prompting a household verification step). It's worth mentioning this distinction proactively in an interview, since candidates are often expected to know where this system's responsibility ends.

Security, Privacy and Permissions

  • Session identity binding: a session's stop or heartbeat call must be authenticated as belonging to the same account (and ideally the same device credential) that created it — otherwise one device could maliciously evict another account's session or forge heartbeats to keep a stale session alive.
  • Minimizing PII in the hot store: the live Redis session record needs just enough to render the manage-streaming UI (device type, rough location, content title) — avoid storing raw IP addresses or precise geolocation in the hot path; store a coarse, already-resolved region/country and keep anything more sensitive only in the access-controlled durable log.
  • Authorization on the sessions-list and stop endpoints: only the authenticated account owner (or a profile with sufficient permission) can view or remotely stop another session on the account — a guest/kids profile shouldn't necessarily be able to kick the account owner's own stream.
  • Transport security: TLS on every client-to-service call; internal service-to-Redis traffic on a private network segment with its own access controls, since this store is a business-critical enforcement path.
  • Abuse resistance: the eviction flow (a device forcing another session to stop) must itself be authenticated and rate-limited, so it can't be used as a denial-of-service vector against a household's other devices.

Load Balancing

Load balancing appears at a few independent layers:

  1. Standard L7 load balancing across stateless Session Admission Service instances, health-checked, in front of the Redis cluster.
  2. Consistent hashing at the client/proxy layer routes each account's requests to the correct Redis shard directly, avoiding an extra service-side routing hop wherever the topology allows it.
  3. Heartbeat traffic in particular benefits from being routed as close to the originating region as possible (see multi-region section) since it's high-volume and latency-insensitive individually, but sensitive in aggregate to unnecessary cross-region hops.

Scaling to Multiple Regions

  • Pin each account's session state to a "home" region — the region nearest its typical usage — so the vast majority of admission/heartbeat traffic for that account never crosses a region boundary; this keeps the sub-millisecond latency budget achievable.
  • Cross-region replication of the live session store exists for disaster recovery/failover, not for serving live traffic cross-region — an account's session check should always be answered locally in steady state.
  • The rare cross-region case (e.g. a traveler streaming from a different continent while a device at home is also active) still routes to the account's home-region shard rather than creating a second, regional source of truth — consistency of the count matters more here than shaving milliseconds off an already-uncommon scenario.
  • The durable session-history log can replicate asynchronously, multi-region, since analytics/billing tolerate eventual consistency far better than the live admission path does.

Consistency vs. Availability: Fail Open or Fail Closed?

If the session store is briefly unreachable, the system faces a genuine trade-off. Fail closed (reject all new Play requests until the store recovers) guarantees the concurrency cap is never violated, but turns an infrastructure blip into a total playback outage for affected accounts — unacceptable for a core, revenue-generating product surface. Fail open (admit playback without a successful admission check during the outage) keeps the product working, at the cost of temporarily allowing an account to exceed its plan's cap for the duration of the incident. In practice, fail open is the right default: a brief window where a handful of accounts stream one extra concurrent session during a rare infrastructure incident is a negligible business cost compared to blocking all playback account-wide; the outage is also, by construction, short-lived and rare, while a fail-closed policy would turn every future Redis hiccup into a customer-facing incident on the single most core feature of the product (watching video at all).

Interview tip
State this trade-off explicitly and justify the direction: "I'd fail open here because the downside of over-admitting for a few minutes during a rare outage is a small, recoverable business cost, while the downside of fail-closed is blocking every paying customer from watching anything at all — that asymmetry is what should decide it, not a default reflex toward strict correctness."

Monitoring, Logging and Analytics

  • Session-store latency (p50/p99/p999): the admission check's latency budget is razor-thin relative to overall playback-start time, so any Redis-side latency regression needs to alert quickly, before it becomes a customer-visible playback-start delay.
  • Admission-rejection rate, broken out by plan tier: a sustained spike in Standard-tier rejections, for instance, is a strong, directly actionable signal — both an indicator of real user demand for more concurrent streams, and a leading indicator for plan-tier upgrade opportunities.
  • Orphaned-session cleanup effectiveness: track how many sessions are reclaimed via clean Stop vs. TTL expiry vs. the background defense-in-depth sweep — a rising share of TTL-expiry reclamations relative to clean stops can indicate a client-side bug (e.g. an app failing to send Stop on backgrounding) worth fixing upstream.
  • Business-metric dashboards on plan-tier upgrade conversions triggered by hitting the limit: correlate an account seeing the over-limit picker with a subsequent plan upgrade within some window — this is one of the most direct, quantifiable links between this specific engineering system and revenue, and product teams will want it front and center.
  • Heartbeat volume and cadence drift: monitor actual heartbeat intervals against the configured cadence to catch client-side regressions (e.g. an app version sending heartbeats too infrequently, silently increasing false-expiry risk).
  • Fail-open incident tracking: whenever the system falls back to fail-open mode, log and alert on it distinctly, and reconcile after recovery how many accounts (if any) briefly exceeded their cap, for both operational review and, if needed, later analytics correction.

Common Interview Questions

Grouped by theme — expect an interviewer to pick several of these as "and then what?" follow-ups on whatever you draw first.

Core Concept and Scoping

What's the difference between "logged in on a device" and "an active stream," and why does that distinction matter?
Being logged in is unlimited and persistent — a session token on a device with no time bound. An active stream is a transient, live playback state that exists only while video is actually running. The plan-tier cap applies exclusively to the latter; a design that tracks logged-in device count instead would incorrectly block a household with many signed-in but mostly idle devices.
Is the limit per profile or per account?
Per account, shared across every profile under it. The cap represents "how many screens can this paying account use at once," not an independent allowance per profile — the Redis key is keyed by account_id, with profile_id stored only as metadata within each session.
Does casting to a TV count as one stream or two?
Treat it as a single active session attributed to the receiving/playing device, since that's what's actually decoding and displaying video; the casting sender is just a remote control in this model. This should be stated as an explicit assumption, since reasonable products differ on it.

Concurrency and Correctness

How do you guarantee two simultaneous Play requests never both get admitted when only one slot is free?
A single atomic operation (a Redis Lua script, or an equivalent transaction/CAS) performs the read-count, compare-to-cap, and write-new-session steps as one indivisible unit against the account's key. Because Redis executes a script serially per key, the second request's script always observes the first request's completed write — there's no window for a stale read.
Why not just use a distributed lock instead of a Lua script?
A distributed lock works but adds an extra dependency, round trips, and lock-timeout failure modes for a problem Redis already solves natively via single-threaded-per-key script execution — it's unnecessary complexity when the atomic-script approach gives the same correctness guarantee more cheaply.
How would you test the atomic admission logic under real concurrency?
Fire a burst of simultaneous Play requests (well beyond the cap) from a test harness against a single account and assert that exactly max_concurrent_streams are admitted regardless of arrival order or timing jitter, repeated across many trials to catch any rare race; also chaos-test with induced network delay between the service and Redis to widen any latent race window.

Heartbeat, TTL and Disconnects

How do you tune the heartbeat interval and TTL?
TTL should be roughly 3x the heartbeat interval (e.g. 90s TTL against a 25-30s heartbeat), so one or two missed beats from ordinary network jitter don't kill a session, while a genuinely dead session is still reclaimed within about two minutes. Tightening the ratio reduces slot-reclamation delay at the cost of more false expirations; loosening it does the opposite.
What happens if a player crashes without ever sending a stop signal?
Nothing extra needs to happen at the moment of the crash — the session simply stops receiving heartbeats, its TTL is never renewed again, and Redis's native key/field expiry removes it automatically once the TTL lapses, freeing the slot without any explicit cleanup logic or manual intervention.
Why not just delete the session immediately on the first missed heartbeat?
A single missed heartbeat is extremely common from ordinary transient network conditions and doesn't mean the session is actually dead. Deleting immediately would kick users off constantly over minor connectivity blips; the TTL grace period exists precisely to absorb that noise while still bounding worst-case reclamation time if the disconnect is permanent.

Over-Limit UX

What should happen when a 5th stream tries to start on a 4-stream Premium plan?
The recommended default is to reject the new stream with a 409-style response that includes the current active sessions, and let the client prompt the user to pick one to stop before retrying — giving the person control rather than silently blocking or silently evicting someone.
Why not just auto-evict the oldest or least-recently-active session automatically?
It's simpler and fully automatic, but it silently interrupts whoever's session gets picked, with no warning and no chance to object — a real source of household friction (someone's show cutting out mid-episode for no visible reason). User-chooses keeps that decision with a person and surfaces useful information instead of a confusing failure.
What if the client can't render an interactive picker (e.g. a very old app version)?
Fall back to a plain block with a clear error message telling the user they're at their stream limit and to stop a session elsewhere manually — the API's 409 response already carries everything a richer client needs, so older clients simply degrade to using less of that payload.

Reliability and Trade-Offs

Redis is unreachable for a few minutes — what happens to playback across the whole platform?
Fail open: admit playback without a successful admission check during the outage, rather than fail closed and block all playback account-wide. The business cost of a brief, rare over-admission window is far smaller than turning an infrastructure blip into a customer-facing "you can't watch anything" incident on the platform's core feature.
How would you reconcile accounts that briefly exceeded their cap during a fail-open incident?
Log every fail-open admission distinctly during the incident window, and run a post-incident reconciliation job against the durable session-history log to identify any accounts that exceeded their cap, for operational review — this is an acceptable, boundable cost, not something requiring real-time correction.
Why shard the session store by account_id instead of, say, by device_id or a random hash?
Every admission decision needs a consistent, atomic view of all of one account's sessions at once. Sharding by account_id guarantees all of an account's session data lives on one shard, so the check-and-increment logic never needs cross-shard coordination or a distributed transaction.

Related Problems and Scope Boundaries

How is this different from detecting account/credential sharing across households?
This system only answers "how many active playback sessions does this account have right now" — a purely technical, real-time counting problem. Whether those sessions represent one household or several unrelated ones is a separate, much fuzzier problem, typically solved with IP/geolocation clustering, device-fingerprint diversity analysis over time, and household-verification heuristics feeding a completely different decision pipeline.
Why does this system matter commercially, not just technically?
Unrestrained account sharing was estimated to cost streaming platforms on the order of billions of dollars a year (commonly cited estimates put 2019 losses around $9B, projected toward roughly $12.5B) — plan-tier concurrent-stream limits (1/2/4) are a direct, enforceable commercial lever, and this admission-control system is the mechanism that actually makes that tiering real rather than aspirational.
Do offline downloads count against the concurrent-stream limit?
Typically no — there's no live connection to monitor once content is downloaded, so it falls outside this system's scope entirely; a separate, usually more generous, cap on simultaneous authorized offline-download devices is a different, related feature with its own rules.

Key Takeaways

Remember
Get the core distinction right first: logged-in devices are unlimited, only concurrently active playback sessions are capped — a design that conflates the two is wrong from the first box drawn. The admission check must be a single atomic operation (a Redis Lua script or equivalent), not a separate read-then-write, or it will silently over-admit under concurrent load — this is the load-bearing correctness property of the whole system. Heartbeat plus TTL is what turns "a crashed player" from a permanently stuck slot into a bounded, self-healing recovery, and the TTL-to-heartbeat ratio is the central tuning knob balancing false-expiry risk against slot-reclamation delay. The over-limit UX is a real product decision, not an afterthought — user-chooses is the real-world default because it keeps a person in control instead of silently blocking or silently evicting. And when the store is briefly unreachable, fail open: a small, rare over-admission cost beats blocking all playback for every affected account. Finally, keep this system's scope tight — it enforces a technical concurrency cap, and is explicitly not the system that detects credential/household sharing, even though both serve the same underlying business goal.
