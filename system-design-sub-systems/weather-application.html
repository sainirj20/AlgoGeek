SYSTEM DESIGN

Developing a Weather Application

A complete, interview-ready design walkthrough for a weather app like Weather.com / AccuWeather / Apple Weather: requirements, capacity estimation, geospatial bucketing, caching & TTL strategy, upstream-provider fault tolerance, severe weather alert fan-out, data model, sharding, replication, security & cost, and follow-up interview questions.

Problem Statement

Design a weather application that serves current conditions, multi-day forecasts, severe weather alerts, and historical weather lookups to a very large user base. The service does not own any weather stations, radar installations, or satellites — it ingests data from one or more external upstream providers (e.g. NOAA / the National Weather Service, a commercial provider in the OpenWeatherMap/AccuWeather mold, or a fictional "WeatherCorp" feed used for this write-up) and re-serves that data to a much larger read audience.

Why is this fundamentally a caching problem, not a sensor-network problem?

It's tempting to reach for IoT/sensor-network framing ("millions of weather stations streaming telemetry"), but that's the wrong mental model here: we are not Doppler radar or NOAA's observation network. Precisely because the upstream provider already does the hard meteorological work (numerical weather prediction, radar processing, station aggregation) and publishes it as a rate-limited, metered API, our system's entire job is to stand between a huge, bursty read audience and a small, expensive, slow-moving data source — and to do it without ever showing an error, since "weather app is down" is worst exactly when a storm is approaching and everyone is checking at once. This makes the design far closer in spirit to a CDN/cache-offload problem (absorbing read amplification behind a TTL'd cache) than to a write-heavy ingestion problem.

Why do people check a weather app?

  • Daily planning: "do I need a jacket / umbrella today," commute and travel decisions.
  • Safety: severe weather alerts (tornado warnings, flash floods, hurricanes) that can be life-or-death and time-critical.
  • Repeated, habitual checking — the same handful of nearby locations, checked many times a day by many nearby people, which is exactly the read-amplification pattern the design must exploit.

Clarifying Questions to Ask the Interviewer

Always clarify scope before designing. A strong candidate spends the first few minutes narrowing the problem rather than assuming defaults.

  1. Do we own any sensors/radar, or do we exclusively ingest from third-party upstream provider(s)? (We'll assume the latter throughout.)
  2. How many upstream providers are there, and what are their rate limits and pricing model (per-call cost, calls/minute cap)?
  3. What data-freshness / staleness window is acceptable for current conditions vs. forecasts?
  4. Do we need severe weather push notifications, and if so, what's the target delivery latency?
  5. Do we need historical weather lookup, and how far back should it go?
  6. Do users query by exact lat/long, city name, or zip/postal code — and do we need location search/autocomplete?
  7. Single-country product (e.g. US-only, backed by NWS) or global, multi-provider?
  8. Do we need radar/precipitation map imagery, or just numeric conditions/forecasts?
  9. How many favorite/saved locations per user, and do we push alerts for all of them or just the user's current location?
  10. Is strong consistency required anywhere, or is eventual consistency acceptable everywhere (as it usually is for weather)?
Interview tip
State reasonable assumptions out loud and keep moving: "I'll assume a single commercial upstream provider with a hard rate limit and per-call cost, a 10–15 minute acceptable staleness window for current conditions, and that severe weather alerts are a hard requirement since they're the headline non-functional driver of this whole design." This shows judgment, not indecision.

Requirements and Goals

Functional Requirements

  1. Current conditions for a location, specified by lat/long, city name, or zip/postal code.
  2. Multi-day forecast: hourly (next ~48 hours) and daily (next ~7–10 days).
  3. Severe weather alerts, delivered as push notifications to affected/subscribed users.
  4. Historical weather data lookup for a location and date/date-range.
  5. Radar / precipitation map data (tile imagery or vector overlays for a map view).
  6. Location search / autocomplete (city name, zip/postal code, "current location").
  7. Per-user unit preference (Celsius / Fahrenheit), applied consistently across all responses.
  8. Favoriting / saving multiple locations per user (e.g. "Home," "Work," "Mom's house").

Non-Functional Requirements

  1. High read availability (99.99%+): people check weather constantly, and the worst possible moment to be down is during a severe weather event — exactly when read volume peaks.
  2. Low latency: sub-200ms for cached current-conditions responses; forecast responses should feel similarly instant.
  3. The external-provider dependency is the actual bottleneck: most third-party weather APIs impose strict rate limits and per-call costs — the system must be designed around minimizing upstream calls, not around our own compute capacity.
  4. Eventual consistency is fine everywhere: weather data is inherently a few minutes stale from the source already (satellite/radar processing lag, model run cadence), so there is no correctness reason to chase strong consistency.
  5. Massive read amplification: millions of users checking the same handful of nearby grid cells must collapse into a tiny number of actual upstream calls.
  6. Horizontal scalability on the read path, decoupled from the (much lower-volume, schedule-driven) ingestion path.

Extended / Out-of-Scope

We'll go deep on geospatial bucketing, caching/TTL strategy, upstream fault tolerance, and severe weather alert fan-out — the core of what makes this problem interesting — and touch on partitioning, security, and cost. We explicitly call out, but don't design, the internals of a numerical weather prediction model, radar-imagery rendering pipeline, or a full push-notification platform (assume a managed provider such as FCM/APNs sits underneath our Notification Pipeline).

Capacity Estimation and Constraints

This system is dominated by two facts: read traffic vastly exceeds anything the upstream provider can or will serve directly, and read traffic is extremely concentrated (millions of users collapse onto a small number of shared grid cells). The capacity math below is really a "how much can caching offload from an expensive, rate-limited upstream" argument — the same shape as a Redis/CDN cache-offload calculation, just applied to a geospatial key instead of a URL or a scoreboard.

Traffic Estimates — Client-Facing Read Volume

Assumption 50 million daily active users (DAU); average 4 checks/user/day (morning, midday, evening, plus ad-hoc)
Requests/day = 50M × 4 = 200 million
Average QPS = 200,000,000 ÷ 86,400 ≈ 2,315 requests/sec
Normal-day peak (commute/morning/evening bursts, ≈5× average) ≈ 11,500 QPS

Severe Weather Event Surge — the "Hurricane Hitting a Metro" Case

Assumption A hurricane approaches a metro area of 20 million residents; 40% check the app within a 1-hour landfall-approach window
Surge requests = 0.40 × 20,000,000 = 8 million checks in that hour
Surge QPS = 8,000,000 ÷ 3,600 ≈ 2,220 requests/sec, layered on top of the system-wide peak
System-wide peak during the event ≈ 11,500 + 2,220 ≈ 13,700 QPS — and if several regions have concurrent events (e.g. a hurricane on the coast and severe storms in the Midwest), design headroom for ≈20,000 peak QPS system-wide

The critical detail: that 2,220 QPS surge is not spread evenly — it lands on the few hundred grid cells covering one metro area, and disproportionately on the densest cells within it. That concentration is exactly what a per-geocell cache is built to absorb.

Geocell Sizing and the Upstream Call Budget (the Core Argument)

Choose a grid-cell resolution of roughly 5×5 km (geohash length 5, ≈4.9 × 4.89 km — see the geospatial bucketing deep dive below for why). Assume roughly 500,000 distinct geocells receive at least one query on a given day globally (this covers essentially every populated area at 5 km resolution). Assume a cache/refresh TTL of 12 minutes, i.e. 1,440 ÷ 12 = 120 refresh windows per day.

Worst-case upstream calls (every active cell queried continuously) Upstream calls/day ≤ 500,000 cells × 120 refresh windows/day = 60,000,000 calls/day
This worst-case bound alone is already 3.3× less than the 200M raw client requests/day — i.e. even in the pathological case where every cell is hot all day, caching still collapses read volume by 3.3:1
Realistic upstream calls (long tail is queried, not continuously hot) ≈50,000 "always hot" cells refresh the full 120 times/day = 6,000,000 calls
≈450,000 long-tail cells are queried only occasionally — averaging ≈5 refreshes/day each = 2,250,000 calls
Realistic total ≈ 8.25 million upstream calls/day
Overall offload ratio = 200,000,000 ÷ 8,250,000 ≈ 24:1 — every genuine upstream call answers roughly 24 client requests on average across the whole system

Now look at a single hot cell during the hurricane surge above: assume the top 20 densest cells in the affected metro absorb half the 2,220 QPS surge, i.e. ≈1,110 QPS ÷ 20 cells ≈ 56 requests/sec sustained per cell.

Hot-cell offload ratio during the event Requests served per upstream refresh = 56 req/sec × 720 sec (12-min TTL window) ≈ 40,300 requests
Offload ratio for that single hot cell ≈ 40,300:1 — one upstream call answers over 40,000 user requests during the surge

This is the same shape of argument as a hot-key/cache-offload calculation for any read-heavy system: the busier a key gets, the better the cache's offload ratio gets, because the number of upstream refreshes per key is bounded by the TTL, not by request volume.

Cache Memory Estimate

Cache sizing Payload per geocell (current conditions + 48h hourly + 10-day daily forecast, compressed JSON) ≈ 5 KB
500,000 active geocells × 5 KB ≈ 2.5 GB
Even caching every ∼5 km cell covering Earth's populated land area (≈6 million cells) × 5 KB ≈ 30 GB

Either number is tiny — this is the opposite problem from most caching case studies: the working set is small, so the entire hot dataset fits comfortably in a modest Redis Cluster with room to spare; the challenge is upstream call volume and hot-cell concentration, not memory.

Bandwidth Estimates

Bandwidth Inbound (ingestion ← upstream): 8.25M calls/day × ≈2 KB response ≈ 16.5 GB/day ≈ 190 KB/sec average
Outbound (clients ← us): 200M requests/day × ≈3 KB average response ≈ 600 GB/day ≈ 6.9 MB/sec average, with peaks of ≈35–40 MB/sec during a severe weather surge

Historical Data Storage Estimate

Assumption 2 million geocells with historical coverage; hourly observations retained for 10 years
Records/cell = 24 × 365 × 10 = 87,600
Total records = 2,000,000 × 87,600 ≈ 175.2 billion rows
Record size ≈ 200 bytes (geocell_id, timestamp, temp, humidity, wind, pressure, precip, condition_code, source)
Raw storage ≈ 175.2B × 200 bytes ≈ 35 TB; with 3× replication ≈ 105 TB
Time-series columnar compression (delta/dictionary encoding, typically 5–8×) brings the effective on-disk footprint down to roughly 15–20 TB

Data Model and Database Choice

Nature of the Data

  • A small number of distinct geocells (hundreds of thousands to low millions), each with a tiny, frequently-refreshed "current state" payload.
  • A much larger, append-only historical time series per geocell — classic time-series access pattern (write once, range-scan by time).
  • A comparatively small amount of user data (accounts, favorites, alert subscriptions) with real relational structure.
  • The read path is a pure key lookup by geocell_id (plus a time range for forecast/history) — no joins on the hot path.

SQL vs. NoSQL — the Recommended Hybrid

current_conditions and forecast_data are simple, extremely hot, geocell-keyed lookups — a natural fit for a key-value/wide-column store (Redis as the cache tier, backed by a wide-column store such as Cassandra/DynamoDB as the durable "source of truth for cache refill"). historical_weather is a textbook time-series workload (append-mostly, range-scanned by time) and belongs in a purpose-built time-series store (e.g. a Cassandra-style wide-column store partitioned by geocell+date, or a dedicated TSDB). user_favorite_locations and alert_subscriptions have genuine relational shape (user → many locations/subscriptions) and modest volume, so a conventional relational database (Postgres/MySQL) is the right, boring choice there — there is no benefit to forcing everything into one storage paradigm.

Interview tip
Good framing: "the bulk, hot, geospatially-keyed data (current conditions, forecasts, history) goes in NoSQL/time-series stores optimized for that access pattern; the comparatively small, relationship-heavy user data (favorites, subscriptions) goes in SQL." This mirrors the SQL-for-control-plane / NoSQL-for-data-plane split used elsewhere in this series, just drawn along a different boundary.

High-Level Design

Clients talk to a CDN / API Gateway first, which caches semi-static forecast responses at the edge for the busiest locations. The Weather Service is a stateless application tier that checks a per-geocell Redis cache; on a miss, it calls a Forecast Aggregator that reads the durable store's last-known-good value (never a live upstream call inline with a user request) and repopulates the cache. Completely decoupled from user traffic, a Forecast Ingestion Service polls the upstream provider(s) on a fixed schedule, normalizes the payload into our internal schema, and writes it into both the durable store and (for hot cells) directly into the cache. An Alerting Service consumes the same upstream provider's severe-weather feed and fans out push notifications through a Notification Pipeline. Analytics consumes lightweight, fire-and-forget events from both the Weather Service (cache hit/miss) and the Ingestion Service (upstream call volume and cost) to drive pre-warming and capacity decisions.

Figure 1. High-level architecture — the client read path (CDN → Weather Service → Redis → Aggregator → Durable Store) is fully decoupled from the scheduled ingestion path (Ingestion Service → Upstream Provider), which is the only component that ever calls the paid, rate-limited upstream API. The Alerting path shares the same upstream feed but fans out independently.

Key Design Principles Reflected in the Diagram

  • Only the Ingestion Service (and, rarely, the Aggregator for a brand-new "cold" cell) ever calls the upstream provider — user request volume never directly drives upstream call volume, which is the entire point of the design.
  • The read path favors availability over freshness: a genuine cache miss falls back to the durable store's last-known-good value, never to a synchronous live upstream call blocking a user request.
  • Alerts and analytics are decoupled side paths that never sit on the critical path of a conditions/forecast read.
  • Multiple layers absorb load before touching the durable store: CDN edge cache → Redis cache → durable store, each layer shedding the vast majority of traffic.

Deep Dive — Geospatial Bucketing

Weather forecasts are not naturally a function of exact coordinates — upstream providers publish forecasts per grid cell (their numerical weather models run on a grid, e.g. NOAA's NDFD grid at ≈2.5 km resolution), not per infinitely-precise lat/long. Two users 50 meters apart get, and should get, the identical forecast. Bucketing our own data the same way is therefore not just a caching trick — it mirrors how the source data is actually produced, and it's exactly what makes caching effective: many nearby users round to the same cell and share one cache entry.

Geohash vs. S2 vs. H3

SchemeCell shapeNotes
GeohashRectangular, variable aspect ratio by latitudeSimple, human-readable string prefix; easy to shard by prefix; cells distort (non-square) away from the equator
Google S2Roughly square, hierarchicalProjects the sphere onto a cube face, giving more uniform cell area globally; used by many production geo-indexing systems
Uber H3Hexagonal, hierarchicalHexagons have uniform adjacency (6 equidistant neighbors, unlike a square grid's edge/corner distinction) — convenient for "expand outward by one ring" queries such as radar tiles or nearby-cell blending

Recommendation: geohash length 5 (≈4.9 × 4.89 km) as the primary key for its simplicity and prefix-shardability (see partitioning below); S2 or H3 are equally defensible choices and are preferable if the interviewer pushes on cell-area uniformity near the poles or wants clean "k-ring" neighbor expansion for radar/precipitation overlays.

Figure 2. Multiple nearby users round to the same grid cell and share one cached response; a user near a cell boundary is still assigned deterministically by the encoding function, not by distance to a centroid.

Mapping a User's Precise Location to a Cell

  1. Client resolves a location (GPS lat/long, or a geocoded city/zip lookup via the locations table) to a precise coordinate.
  2. Server encodes that coordinate at the chosen precision (geohash-5 / S2 level ≈12) to get a deterministic geocell_id — this is a pure function, no lookup required.
  3. All reads and cache keys use geocell_id, never the raw coordinate — this is what collapses read amplification.
  4. For map/radar views spanning multiple cells, expand outward using neighbor lookup (geohash neighbor function, or an H3 k-ring) rather than re-encoding many individual points.

Deep Dive — Cache-Refill and TTL Strategy

The cache-aside pattern is standard: the Weather Service checks Redis first; on a hit, it returns immediately (sub-200ms target); on a miss, it goes through the Forecast Aggregator to the durable store, repopulates Redis, and resets the TTL. The interesting design decision is the TTL value itself and how refills are triggered.

Why 10–15 Minutes?

  • Freshness-adequate: most upstream providers themselves only update current-conditions and short-range forecasts every 10–15 minutes (bounded by their own model/observation cadence) — caching for longer than the source refreshes doesn't cost any real freshness.
  • Effective at collapsing read amplification: as shown in the capacity math above, a 12-minute TTL turns tens of thousands of requests against one hot cell into a single upstream call per window — the longer the TTL, the better the offload ratio, up to the point where it stops matching the source's real update cadence.
  • Short enough that severe weather still updates promptly: a rapidly-evolving storm's conditions won't be stale for more than one TTL window, and severe alerts bypass the cache/TTL cycle entirely via the dedicated Alerting path (below).
Figure 3. The cache-refill cycle: a write resets the TTL clock; reads are served from cache for the whole window; on expiry, only the next incoming request (coalesced via single-flight so concurrent requests don't all stampede the durable store) triggers a refill.

Request Coalescing (Single-Flight) to Prevent a Thundering Herd

When a hot cell's TTL expires during a traffic surge, dozens of requests can arrive within milliseconds of each other, all seeing a miss simultaneously. Without protection, all of them would hit the durable store (or worse, trigger duplicate upstream calls) at once. The standard fix is request coalescing / single-flight: the first request to see a miss for a given geocell_id acquires a short-lived lock (or registers itself as the "in-flight" fetcher) and performs the refill; every other concurrent request for that same key waits on the in-flight result and receives it once it completes, instead of independently re-fetching. This is the same pattern used by any high-traffic cache-aside system to protect the layer behind the cache.

Deep Dive — Forecast Ingestion, Rate Limits, and Fault Tolerance

The Forecast Ingestion Service is the only component that talks to the upstream provider(s), which makes it the natural place to enforce rate-limit discipline and failure isolation. It runs on a schedule (e.g. every 10–15 minutes per active cell, prioritized by traffic), normalizes each provider's proprietary response into our internal schema (unifying condition codes, units, and field names across providers), and writes the result into the durable store and, for currently-hot cells, directly into Redis.

Circuit Breaker Against a Failing or Rate-Limited Upstream

The single most important behavioral rule in this whole design: never show an error because the upstream provider is unavailable or rate-limiting us — always serve the last-known-good value with a visible age/staleness indicator. A circuit breaker around every upstream call enforces this cleanly.

Figure 4. Circuit breaker around every upstream call: a healthy provider (CLOSED) trips to OPEN on sustained errors/rate-limit responses — during which the cache and durable store keep serving their last-known-good values with a staleness indicator — then periodically probes via HALF-OPEN before fully recovering.

Additional Resilience Techniques

  • Secondary provider fallback: if the primary provider's circuit is open, route that region's ingestion to a secondary upstream (e.g. fail over from a commercial provider to NOAA/NWS for US locations) rather than going dark.
  • Provider reconciliation: when two providers disagree meaningfully (e.g. temperature differs by more than a few degrees, or precipitation type differs), prefer the higher-historical-accuracy source for that region, or blend/average for less consequential fields, and flag large disagreements for monitoring rather than silently picking one.
  • Every response carries an is_stale flag and an as_of_age_seconds field so the client can render "conditions as of 42 minutes ago" instead of presenting stale data as if it were fresh.
  • Rate-limit-aware scheduling: the Ingestion Service's poll scheduler is itself token-bucketed against the upstream's published rate limit, and prioritizes hot/dense cells over long-tail cells when budget is constrained.

Deep Dive — Severe Weather Alerting and Fan-Out

Severe weather alerts (tornado warnings, hurricane warnings, flash flood warnings) cannot wait for the normal 10–15 minute refresh cycle — they need to reach potentially millions of affected users within seconds of being issued. This is architecturally a broadcast/fan-out problem, not a per-request read problem.

Figure 5. Alert fan-out: an incoming CAP (Common Alerting Protocol) alert is mapped from its affected polygon to the set of overlapping geocells, resolved against a geocell-to-subscriber reverse index, and fanned out across sharded workers to push providers — the same fan-out-on-write shape used for broadcast notifications at scale.

How Fan-Out Works

  1. The upstream provider's alert feed (modeled on NOAA's CAP — Common Alerting Protocol — format) publishes an alert with a geographic polygon (or a county/zone FIPS code) and a severity level.
  2. The Alerting Service intersects that polygon against our geocell grid to get the affected cell set — typically a few dozen to a few hundred cells for a metro-scale event.
  3. For each affected cell, look up subscribed device tokens (users who favorited a location in that cell, or who have location-based alerting enabled) via the geocell-to-subscriber reverse index — this index is the key data structure that makes fan-out fast; without it, we'd have to scan every user.
  4. Fan out push jobs across many worker shards (partitioned by device-token hash) so no single worker/queue is a bottleneck for a metro-wide alert.
  5. Push through a managed provider (APNs/FCM); track delivery latency percentiles as a first-class SLO (see monitoring below), since this is the one place in the whole design where seconds genuinely matter.

Data Partitioning and Replication

Shard by Geocell Prefix — the Uber Quadtree Analogy

Both the Redis cache and the durable store are sharded by geocell_id prefix. This deliberately echoes how Uber's geospatial indexing (originally a quadtree over S2 cells, now largely H3-based) buckets driver and rider locations: nearby entities land in the same or adjacent index buckets, which makes proximity queries efficient and lets a dense, high-traffic region be subdivided further without touching the rest of the keyspace. In our system, prefix-sharding gives the same two benefits: nearby cells (useful for multi-cell radar/map queries) tend to land on the same or adjacent shards, and a densely-queried metro area can be given its own dedicated shard capacity without re-architecting the global partitioning scheme.

Hash-based sharding (hash the full geocell_id, not just its prefix) is the safer default for the durable store, since it spreads load independently of any real-world clustering in the keyspace; use consistent hashing so a shard add/remove only moves a bounded fraction of keys. Prefix-based sharding is preferred specifically for the cache tier and for any component that benefits from co-locating nearby cells (radar tiling, neighbor-expansion queries).

The Hot-Cell Problem

A major weather event concentrated over a densely-populated area (a hurricane approaching New York City, for example) can drive one shard's traffic far above every neighboring shard's — the capacity math above showed a single hot cell absorbing tens of thousands of requests per TTL window. Left unmitigated, this can saturate a single cache node or database partition even while the rest of the cluster sits idle.

Figure 6. When traffic-monitoring detects a hot cell (or cluster of cells) far above normal, four mitigations fire in parallel: dedicated cache capacity for the affected cells, added read-replica fan-out, ingestion pre-warming ahead of the forecast/storm cone, and short-TTL CDN edge caching with request coalescing.

Mitigations, in Detail

  • Dedicated / pinned cache capacity: route known hot cells (identified ahead of time from a forecast cone, e.g. NOAA's hurricane "cone of uncertainty") to isolated Redis nodes so their load can't degrade the shared cluster.
  • Read-replica fan-out: dynamically add read replicas for the affected shard, so read traffic scales horizontally without touching write/refresh capacity.
  • Pre-warming ahead of the event: once a storm's forecast cone is known, proactively refresh and pin the cells it covers before traffic actually spikes, rather than reacting only after a stampede of misses.
  • CDN edge caching + request coalescing: absorb the very largest spikes before they reach our infrastructure at all, and ensure that even a burst of near-simultaneous misses collapses into one origin fetch (see single-flight, above).

Cache and Durable-Store Replication

  • Each Redis shard is replicated (primary + at least one replica) across availability zones; a replica promotion on node failure is instant enough that clients see, at worst, a brief latency bump — never an outage.
  • The durable store is replicated 3× across AZs (and, for multi-region deployments, asynchronously across regions) purely for durability and read scaling — there is no write-path correctness requirement here as strict as, say, a payment ledger, so asynchronous replication is an easy, defensible choice.
  • Because the read path already tolerates staleness by design, cache/store replication failures degrade gracefully: a replica lagging by a few seconds, or even a full replica failover, is invisible to the "last-known-good with an age indicator" contract the API already makes.

Monitoring, Logging, and Analytics

  • Cache hit ratio per geocell: the single most important operational metric — a sustained drop signals either a TTL misconfiguration, a cold-start after deploy, or an emerging hot-cell event worth pre-warming for.
  • Upstream API cost/quota tracking: real-time dashboards of calls made vs. the provider's rate-limit ceiling and the running dollar cost, broken out per provider and per region, so a runaway ingestion bug (or an unexpectedly popular new region) is caught before it blows through a monthly quota.
  • Alert-delivery latency during severe weather: track p50/p95/p99 time from "alert ingested" to "push delivered," with a hard SLO (e.g. p95 < 60 seconds) — this is the one latency number in the whole system that genuinely has life-safety stakes.
  • Most-requested locations: a rolling top-N feeds pre-warming decisions directly — if a location is trending (e.g. a wildfire or a storm making news), proactively refresh and pin it ahead of the traffic surge rather than reacting to it.
  • Staleness distribution: track what fraction of served responses are marked is_stale and their age distribution — this is the direct signal for whether the circuit-breaker fallback path is being exercised more than expected.
  • Provider disagreement rate: when running multiple upstream providers, track how often and by how much they disagree, to catch a provider quietly degrading in quality before users notice.

Security and Cost Considerations

  • Protect the upstream API key: the upstream provider's key is a paid, rate-limited, high-value credential — it lives only inside the Forecast Ingestion Service (never shipped to clients, never exposed through our own public API), stored in a secrets manager with rotation.
  • Rate-limit our own public-facing API per API key / per client, independent of the upstream's limits — this is what actually protects the expensive upstream dependency from abuse: a malicious or buggy client hammering our endpoint should never be able to translate 1:1 into upstream calls, and thanks to the cache-refill design, it structurally can't (a flood of requests for the same cell just hits the cache).
  • Cost attribution: tag ingestion calls and cache-refill events with the triggering region/tenant (if the API is offered to third-party integrators) so upstream API spend can be attributed and, if needed, billed back or capped per integrator.
  • Input validation: bound-check lat/long ranges, reject absurd values, and normalize location queries before geocoding to avoid wasted lookups against the search index.
  • Transport security: TLS everywhere; device push tokens and any PII in alert_subscriptions encrypted at rest.
  • Abuse via scraping: a public "get forecast for every geocell" scraping campaign would be indistinguishable from legitimate hot-cell traffic to the cache (a good thing — it just gets served from cache) but could still be used to reconstruct the full grid; apply standard per-key rate limiting and anomaly detection on request patterns as an extra layer.

Load Balancing

A load-balancing layer sits at three points, same as most read-heavy web-facing systems:

  1. Between clients and the CDN/API Gateway (typically DNS/anycast-based).
  2. Between the Weather Service fleet and the Redis cache tier — routed by consistent hashing on geocell_id so a given cell's traffic reliably lands on the shard that holds it.
  3. Between the Weather Service and the durable store's shards, similarly routed by geocell_id.

Start with simple round-robin/consistent-hash routing; if hot-cell events show up as uneven load on specific nodes despite the mitigations above, evolve to a latency-weighted strategy so the balancer itself reacts to a node under pressure, not just to raw connection count.

Scaling to Multiple Regions

  • Run each region active-active with its own Weather Service fleet, cache cluster, and durable-store replica set, so reads are always served from the region closest to the requester for the lowest latency (Geo-DNS or anycast routing).
  • Ingestion can also be regionalized: use NOAA/NWS as the primary upstream for US locations and a global commercial provider elsewhere, with the normalization layer in the Ingestion Service reconciling both into one internal schema.
  • Replicate the durable store across regions asynchronously; a new observation written in one region propagating to others within a few seconds is a non-issue, since forecasts for a US city are read almost exclusively from the US region anyway.
  • Run the Alerting Service per-region against that region's own upstream alert feed, since severe weather alerts are inherently local — there's no reason a hurricane warning for Florida needs to route through an unrelated region's infrastructure.
  • Analytics can roll up per-region metrics into a global dashboard on a slower, asynchronous cadence — there's no correctness reason for cross-region analytics aggregation to be synchronous.

CAP Theorem Lens

This system leans almost entirely toward availability + partition tolerance (AP), far more so than a typical CRUD system: there is essentially no operation in this design where showing slightly-stale data is worse than showing an error or nothing at all — that's true for current conditions, forecasts, and even (within a bounded, monitored latency budget) severe alerts. The one place a stricter guarantee matters is the alert-subscription write path (a user's subscription must reliably be recorded before the next event, or they silently miss a life-safety notification) — that piece alone benefits from a conventional ACID-backed relational store, exactly as discussed in the data model section.

Common Interview Questions

These are organized by theme — use them to rehearse, or expect a real interview to pick a handful as "and then what?" follow-ups on whatever you present first.

Geospatial Design

Why bucket weather data by geohash/grid-cell instead of exact lat/long coordinates?
Two reasons, both load-bearing: upstream providers themselves publish forecasts per grid cell (their models run on a grid, not per infinitely-precise point), so bucketing mirrors the source data; and it's what makes caching effective at all — many nearby users round to the same cell and share one cache entry, instead of each generating a distinct, uncacheable key.
How do you handle a user who is exactly on the boundary between two grid cells?
The encoding function (geohash/S2) deterministically assigns any coordinate to exactly one containing cell — there's no ambiguity to resolve at read time. Since cells are ≈5 km wide and weather doesn't change discontinuously at an arbitrary grid line (the underlying model itself is smoothed at that resolution), the boundary effect is negligible; if a product wants smoother transitions, blend the nearest 2–4 cells with inverse-distance weighting, but this is rarely worth the added complexity.
Geohash, S2, or H3 — how would you choose, and does it matter?
Geohash is simplest and prefix-shardable; S2 gives more uniform cell area globally (geohash cells distort away from the equator); H3's hexagons give uniform adjacency, which is convenient for radar/neighbor-expansion queries. Any of the three is defensible — state the trade-off and pick one rather than treating it as a solved/unsolved binary.

Caching and Freshness

How do you choose the cache TTL, and what's the trade-off?
Match it to the upstream provider's own update cadence (typically 10–15 minutes) — caching longer than the source refreshes costs nothing in real freshness, while a shorter TTL just burns upstream call budget for no benefit. The trade-off is entirely about upstream cost/rate-limit headroom vs. how current the data feels, not about correctness.
How do you test that stale data is never worse than no data?
Chaos-test the ingestion path in staging by killing the mocked upstream provider and asserting the public API never returns a 5xx and always returns a payload with correct is_stale/as_of_age_seconds metadata; add contract tests that fail the build if any response path can omit the staleness fields; alert in production on the fraction of stale responses served, with a target ceiling.
How would you design the cache-refill algorithm to avoid a thundering herd on TTL expiry?
Single-flight / request coalescing: the first request to see a miss for a given geocell acquires the refill, and every concurrent request for that same key waits on and shares that one result instead of independently re-fetching.
What's the right consistency model here, and how does it differ from something like the URL shortener?
Almost pure AP: unlike a URL shortener's key-generation path (which must never double-issue a key), there is no operation here where strong consistency is required for correctness — weather data is inherently a few minutes stale from the source already. The one exception is the alert-subscription write path, which benefits from ACID guarantees so a user's opt-in is never silently lost.

Scaling and the Upstream Dependency

What happens during a hurricane when millions of users in one metro all query at once (the hot-cell problem)?
The CDN edge cache and Redis absorb the overwhelming majority of it, since all those users collapse onto a few hundred shared geocells; for the small number of cells that still run hot, dedicated pinned cache capacity, added read-replica fan-out, and ingestion pre-warming ahead of the forecast cone keep any single shard from becoming a bottleneck.
How do you handle the upstream provider being down?
A circuit breaker trips after sustained failures, at which point the system serves the durable store's last-known-good value (with an age indicator) for every affected cell and stops calling upstream until a cooldown-gated half-open probe succeeds; if a secondary provider is configured, ingestion for that region fails over to it.
How do you keep costs down against a rate-limited, paid upstream API?
The cache-refill design bounds upstream calls to roughly (active cells) × (day length ÷ TTL), completely decoupled from user request volume — the capacity estimation above shows this collapses 200 million daily client requests into roughly 8 million upstream calls, a ≈24:1 offload ratio system-wide and far higher for any individual hot cell.
How would you support multiple weather data providers and reconcile conflicting forecasts?
A normalization layer in the Ingestion Service maps every provider's proprietary schema into one internal representation; when providers disagree meaningfully, apply a per-region "preferred source" policy or a blending rule for less consequential fields, and emit a monitored disagreement-rate metric so systematic quality drift in either provider is caught early.
How do you handle historical data storage growth?
Partition by geocell + date so old partitions can be independently compacted, downsampled (e.g. keep hourly granularity for 2 years, then roll up to daily aggregates beyond that), or moved to cold storage; time-series columnar compression alone typically cuts the effective footprint 5–8×.

Alerting

How do you push severe weather alerts to potentially millions of affected users quickly?
A dedicated fan-out pipeline, separate from the normal read path: map the alert's affected polygon to overlapping geocells, resolve subscribers via a geocell-to-subscriber reverse index, and fan out across sharded push workers to APNs/FCM — with a hard delivery-latency SLO (e.g. p95 under 60 seconds) tracked as a first-class metric.
What if a user is subscribed to a location far from where the alert's polygon technically ends?
Buffer the affected-cell computation by one ring of neighboring cells beyond the literal polygon boundary before resolving subscribers — erring toward over-notifying near a hard geographic edge is the safer failure mode for a life-safety alert.

Product and API Design

How would you implement location search/autocomplete for city names and zip codes?
A separate, denormalized locations search index (prefix/full-text search on display name and postal code) that resolves a user's query to a location_id and its geocell_id — kept independent from the weather data tables since it's a different access pattern (text search, not time-keyed lookup) and changes far less often.
How would you handle unit conversion (Celsius/Fahrenheit) — server-side or client-side?
Store and cache everything in one canonical unit (metric) internally so cached payloads are unit-agnostic and shareable across users regardless of preference; convert to the requesting user's preferred unit at the API response layer, which is cheap, stateless, and keeps the cache from fragmenting by unit preference.
How would you support radar/precipitation map data efficiently?
Treat rendered map tiles as their own cacheable, geocell-adjacent artifact (often literally supplied as pre-rendered tiles by the upstream provider or a map-tile CDN) rather than trying to compute them per request; cache at the CDN edge with the same TTL discipline as other forecast data, and use a hexagonal/H3-style neighbor expansion if blending several cells' data into one continuous overlay.

Extensions

How would you extend this design to support minute-by-minute "nowcasting" (e.g. "rain starting in 10 minutes")?
Nowcasting typically comes from a different upstream feed (short-range radar extrapolation, refreshed far more often than the 10–15 minute forecast cadence) — add it as its own ingestion stream with its own, much shorter TTL, scoped to a finer grid resolution near the user's precise location, without changing the TTL/caching strategy for the rest of the system.
How would you decide which geocells to proactively pre-warm versus lazily refresh on next request?
Rank cells by a rolling popularity score from the Analytics pipeline (most-requested locations) plus any known upcoming event (a forecast cone, a trending news event); pre-warm the top tier on a tight schedule and leave the long tail on lazy, on-demand refresh — this is exactly the "hot vs. long-tail" split used in the capacity estimation above.
How would you support a user with many favorited locations, each potentially subscribed to alerts?
Fan the subscription out per favorited location at write time (one row per user+location in alert_subscriptions) rather than trying to evaluate a user's full favorites list at alert time — this keeps the hot alert fan-out path a simple reverse-index lookup instead of a fan-out-on-read scan of every user's favorites.

Key Takeaways

Remember
This is a read-heavy caching and data-freshness problem, not a sensor-network problem — the app doesn't own weather stations, it stands between a huge read audience and a small, expensive, rate-limited upstream provider. Every major design decision follows from that framing: bucket by geocell (not exact coordinate) because that's both how the source data is shaped and what makes caching effective; choose a TTL that matches the upstream's own refresh cadence, since fresher-than-source caching buys nothing; and treat "never show an error for an upstream outage" as a hard requirement, not a nice-to-have — always serve last-known-good with a visible age indicator. The capacity math (≈24:1 system-wide offload, ≈40,000:1 for a single hot cell during a severe event) is the same shape of argument as any cache-offload calculation, just keyed by geospatial grid cell instead of a URL or an object ID. Keep severe weather alerting on its own dedicated, low-latency fan-out path, fully decoupled from the normal TTL cycle, since it's the one place in this design where seconds have real safety stakes.
