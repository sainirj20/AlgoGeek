SYSTEM DESIGN

Designing a User Login and Authentication System

A complete, interview-ready design walkthrough for a user login and authentication system for a website: requirements and precise capacity estimation, API & data model, high-level architecture, deep dives into password storage, session management (stateful vs. JWT), OAuth2/OIDC social login, MFA (TOTP/WebAuthn), rate limiting & brute-force defense, sharding & replication, security hardening, monitoring/anomaly detection, and a bank of 20 follow-up interview questions.

Problem Statement

Design a login and authentication system for a website that lets users register with an email/username and password (or via a third-party identity provider like Google or GitHub), log in and out, stay signed in across visits ("remember me"), reset a forgotten password, optionally enable multi-factor authentication, and have their account automatically protected against automated guessing and credential-stuffing attacks. Nearly every other feature of the product — profile pages, checkout, messaging, admin tools — sits behind this system, so it is on the critical path of the entire application, not an isolated feature.

Why does this problem matter in an interview?

Authentication is deceptively "solved" — most candidates have used a login form thousands of times, which tempts them to describe only the happy path (check password, set a cookie, done). A strong candidate instead treats this as fundamentally a security design problem first and a CRUD problem second: every design decision (how passwords are hashed, how sessions are represented, how errors are worded, how rate limits are shaped) has to be justified against a specific attack it defends against — credential stuffing, session hijacking, timing side-channels, CSRF, account enumeration — not just against "does it work."

What makes this different from a typical data-heavy system design question?

  • The dominant non-functional requirement is security, not throughput or storage — this is unusual among "classic" system design questions and should visibly reshape the whole conversation.
  • Correctness constraints (unique emails, atomic failed-login counters, exactly-once password updates) push this toward strongly-consistent storage, unlike read-heavy, eventually-consistent systems such as a URL shortener.
  • The traffic pattern is spiky and adversarial: legitimate demand has daily/weekly cycles and occasional mass-relogin surges, while illegitimate demand (credential-stuffing bots) is adversarially adaptive and tries to blend in with the legitimate traffic shape.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope before drawing any boxes — a strong candidate states reasonable defaults out loud rather than waiting for every answer.

  1. What's the expected scale — registered users, daily active users, and peak login rate?
  2. Is social/OAuth login (Google, GitHub, Apple) in scope, or password-only?
  3. Is multi-factor authentication required, and if so which factors (TOTP, SMS, email OTP, WebAuthn/passkeys)?
  4. What compliance regime applies (GDPR, SOC 2, PCI-adjacent) — does that constrain data retention or audit logging?
  5. Is this a single web app, or do we also need to support native mobile clients and third-party API consumers (which changes how tokens should be delivered — cookies vs. bearer tokens)?
  6. Do we need single sign-on (SSO) across multiple first-party products, or is this authentication scoped to one site?
  7. What's the acceptable latency budget for login — is sub-200 ms end-to-end a hard requirement?
  8. Should we assume a single region initially, or must the design support multi-region active-active from day one?
  9. Is there an existing user base to migrate, and does it constrain the password-hashing algorithm we can assume for old records?
Interview tip
A good opening line: "I'll assume 50 million registered users, 5 million DAU, password-plus-optional-MFA as the baseline with OAuth2 social login and WebAuthn as an upgrade path, and that security dominates every trade-off here — I'll call out the couple of places where availability and strict security pull in different directions." This signals judgment without waiting to be spoon-fed every requirement.

Requirements and Goals

Functional Requirements

  1. Registration — sign up with email/username + password; optional social/OAuth registration (Google, GitHub, etc.).
  2. Email verification — a newly registered email must be confirmed via a single-use link before the account is treated as fully trusted (e.g. before password reset can target it).
  3. Login — authenticate with email/username + password, or via a linked OAuth identity provider.
  4. Logout — end the current session; also support "log out of all devices."
  5. Session management — keep a user signed in across requests and, if selected, across browser restarts ("remember me").
  6. Password reset / forgot password — a self-service flow that emails a single-use, time-boxed reset link.
  7. Password change — an authenticated user can change their password, given their current password.
  8. Multi-factor authentication — optional second factor via TOTP, SMS/email OTP, or WebAuthn/passkeys.
  9. Account lockout — temporarily lock or challenge an account after repeated failed login attempts.
  10. Account deletion / deactivation — a user can deactivate (recoverable) or permanently delete (subject to compliance holds) their account.

Non-Functional Requirements

  1. Security is the dominant concern: the system must resist credential stuffing, brute-force guessing, session hijacking, CSRF, and timing side-channel attacks. Every other requirement is secondary to this one.
  2. High availability: authentication is on the critical path of every other feature — an auth outage is a total product outage, not a degraded experience.
  3. Low latency: target sub-200 ms p99 for login, well under 50 ms for token/session validation on every subsequent request.
  4. Scalability: millions of registered users, with sharply spiky traffic — e.g. a "morning login surge" or a flood of re-logins after an incident forces mass session invalidation.
  5. Auditability: every authentication-relevant event (login, logout, password change, MFA enrollment, lockout) must be durably logged for security review and compliance.
  6. Durability: a credential, once written, must never be silently lost — unlike session state, which is allowed to be lossy.

Extended / Out-of-Scope

We go deep on registration/login/session/MFA/password-reset, the credential store, and abuse prevention. We explicitly call out — but don't design in depth — full SSO/SAML federation across unrelated products, a general-purpose fraud/risk-scoring ML platform, and legal/compliance workflow automation (e.g. GDPR erasure request tooling beyond the basic delete/deactivate API), since each is a substantial system of its own.

Capacity Estimation and Constraints

Unlike read-heavy systems where capacity is dominated by storage and bandwidth, an auth system's capacity story has a subtlety most candidates miss: the CPU cost of password verification is itself a first-class capacity input, because a secure password hash is deliberately slow. We derive traffic, storage, and — critically — hashing compute footprint below.

Assumptions used for the math below

AssumptionValue
Registered users50,000,000
Daily active users (DAU)5,000,000 (10% of registered)
Avg. password/MFA logins per DAU per day1.3 (multi-device, expired sessions)
Avg. active session duration before idling20 minutes (1,200 s)
Access token TTL15 minutes (900 s)
Normal daily peak-to-average multiplier5× (commute-hour clustering)
Password verify cost (bcrypt cost-factor 12 / tuned Argon2id)≈250 ms CPU-bound per verify
MFA adoption15% of registered users

Login Traffic (Average and Normal Peak)

Derivation Logins/day = 5,000,000 DAU × 1.3 = 6,500,000 logins/day
Average login QPS = 6,500,000 ÷ 86,400s ≈ 75 QPS
Normal peak QPS (5× during commute-hour clustering) = 75 × 5 ≈ 375 QPS

The "Morning Login Surge" — an Extreme Spike, Not Just a Normal Peak

The scenario this section is named for is not the ordinary daily peak above — it's a thundering herd: an overnight session-store outage, a forced mass logout after a security incident, or a viral event drives a large fraction of DAU to re-authenticate within a tight window, all at once.

Surge derivation Assume 25% of DAU (1,250,000 users) attempt to log in within a 10-minute (600s) recovery window
Surge QPS = 1,250,000 ÷ 600s ≈ 2,083 QPS
Design target: provision for ≈3,000 QPS burst headroom — roughly 40× average traffic

This >40× elastic range between steady-state (~75 QPS) and worst-case surge (~3,000 QPS) is why the Auth Service tier must autoscale horizontally rather than be provisioned for a fixed peak — and why rate limiting must be able to distinguish "legitimate thundering herd" from "credential-stuffing botnet" so it throttles the latter without locking out the former (see Rate Limiting below).

The Hidden Capacity Cost of Password Hashing

Because a secure password hash (bcrypt/Argon2id) is deliberately CPU/memory-hard and effectively single-threaded per verification, sustained login QPS translates directly into a compute footprint — a subtlety that's easy to miss if you only think about hashing as a security knob.

Derivation Concurrent verify operations in flight at surge = surge QPS × verify latency
= 2,500 QPS × 0.25s ≈ 625 concurrent hash computations
Throughput per core ≈ 1 ÷ 0.25s = 4 verifies/sec/vCPU (hashing doesn't parallelize within one operation)
Dedicated compute needed = 2,500 ÷ 4 ≈ 625 vCPU-equivalents, just for password verification, before any I/O handling
Interview tip
Doubling the hash cost factor (to keep pace with attacker hardware getting faster) roughly halves verify throughput per core, which roughly doubles the compute bill at a fixed QPS target. This is exactly why cost-factor tuning is a deliberate, periodically-revisited trade-off between security margin and infrastructure spend — a cost factor calibrated in 2015 is meaningfully too weak by 2026 hardware standards, and a senior candidate should say so unprompted.

Token Refresh Traffic and Concurrent Sessions

Derivation Concurrent active sessions ≈ (logins/day × avg session duration) ÷ 86,400s
= (6,500,000 × 1,200) ÷ 86,400 ≈ 90,278 concurrent sessions
Refresh QPS ≈ concurrent sessions ÷ access-token TTL = 90,278 ÷ 900s ≈ 100 QPS (steady-state)

Refresh calls are cheap relative to logins — they verify a stored token hash, not a slow password hash — but they run at comparable volume and share the same latency budget, so they must be capacity-planned separately, not assumed to be "free" just because they don't touch the password hasher.

Audit volume dwarfs every other table by two orders of magnitude — exactly why it's streamed through Kafka into a columnar/cold analytics store rather than left to grow unbounded inside the transactional primary database (see Monitoring, Logging and Analytics below).

Session / Redis Sizing

Derivation 90,278 concurrent sessions × ≈1 KB/session (user_id, device info, ip, mfa_verified flag, TTL)
≈ 90 MB of live session state

Even with a generous multiple for refresh-token hash caching and rate-limit counters, this comfortably fits in a small Redis Cluster (e.g. 3 primary shards × 2 replicas each), with enormous headroom — unlike a read-heavy caching problem, auth session data is small per record and inherently short-lived (TTL-bounded), so the store is sized for latency and availability, not raw capacity.

System / API Design

A REST API over HTTPS, with tokens delivered either as httpOnly cookies (first-party web) or as JSON bearer tokens (native/mobile and third-party API consumers) depending on client type.

Register

POST /api/v1/auth/register

Request body:
{
  "email": string,           // required
  "username": string,        // optional
  "password": string         // required, min length per NIST 800-63B (see Security section)
}

Response 201 Created:
{ "user_id": "u_9f8c...", "email_verification_sent": true }

Errors: 400 weak/breached password · 409 email already registered (see enumeration note below) · 429 rate-limited

Login

POST /api/v1/auth/login

Request body:
{
  "identifier": string,      // email or username
  "password": string,
  "remember_me": boolean     // optional, extends refresh-token TTL
}

Response 200 (no MFA enrolled):
{ "access_token": "...", "refresh_token": "...", "expires_in": 900 }

Response 200 (MFA required):
{ "mfa_required": true, "mfa_challenge_token": "...", "methods": ["totp", "webauthn"] }

Errors: 401 invalid credentials (identical message for wrong password AND unknown user)
        423 account locked · 429 rate-limited · 403 CAPTCHA required

MFA Challenge Verification

POST /api/v1/auth/mfa/verify

Request body: { "mfa_challenge_token": "...", "code": "123456" }
Response 200: { "access_token": "...", "refresh_token": "...", "expires_in": 900 }
Errors: 401 invalid code · 429 too many attempts (see MFA deep dive)

Token Refresh

POST /api/v1/auth/token/refresh

Request body: { "refresh_token": "..." }   // or via httpOnly cookie
Response 200: { "access_token": "...", "refresh_token": "...", "expires_in": 900 }  // refresh token rotated
Errors: 401 invalid/expired/revoked refresh token → client must show the login screen

Logout / Logout Everywhere

POST /api/v1/auth/logout             // revokes only the current refresh token
POST /api/v1/auth/logout-all         // revokes every refresh token for this user_id
Auth: valid access token required for both
Response 200: { "status": "logged_out" }

Forgot / Reset Password

POST /api/v1/auth/password/forgot
Request: { "email": string }
Response 200 (ALWAYS, regardless of whether the email exists — see Security section):
{ "message": "If that email is registered, a reset link has been sent." }

POST /api/v1/auth/password/reset
Request: { "reset_token": string, "new_password": string }
Response 200: { "status": "password_updated" }
Errors: 400 invalid/expired/already-used token · 400 weak/breached password

Social Login (OAuth2 / OIDC)

GET /api/v1/auth/oauth/{provider}/authorize   → 302 redirect to the provider's consent screen
GET /api/v1/auth/oauth/{provider}/callback    → exchanges the code, links/creates the local account,
                                                  issues our own access/refresh tokens (see OAuth deep dive)

Account Management

POST   /api/v1/auth/password/change   Auth required: { "current_password": ..., "new_password": ... }
POST   /api/v1/auth/mfa/totp/enroll   Auth required → { "secret": ..., "qr_code_url": ..., "backup_codes": [...] }
POST   /api/v1/auth/mfa/totp/confirm  Auth required: { "code": "123456" } → enables MFA
DELETE /api/v1/account                Auth required → deactivates (soft) or queues permanent deletion
Interview tip
Notice every error response above is deliberately vague about why a request failed whenever the honest answer would leak whether an account exists. That's not an oversight — it's the account-enumeration defense discussed in depth in the Security section, and interviewers frequently probe exactly this.

Data Model and Database Choice

Nature of the Data

  • Comparatively low volume next to a URL shortener or a feed system — tens of millions of users, not tens of billions of objects.
  • Correctness constraints dominate: an email must be unique, a failed-login counter must increment atomically, a password update must never be partially applied.
  • Strong relationships exist between tables (a user has many credentials, many refresh tokens, many audit events) — real foreign keys and referential integrity matter here.
  • The hottest read is a simple key lookup (find a user by email at login time), but it must be backed by strict uniqueness guarantees, unlike a URL shortener's simple, loosely-constrained key-value access.

These properties — strong consistency requirements, real relationships, and moderate (not extreme) volume — favor a sharded relational (or NewSQL) store for the durable user/credential/audit data, in contrast to the NoSQL-first recommendation you'd make for a pure high-volume key-value workload. Session and refresh-token hot state, by contrast, is kept in Redis rather than the primary store (see Data Partitioning below) — this system deliberately uses two different storage tiers for two different consistency/durability profiles.

Where did the "sessions" table go?
There is deliberately no durable sessions SQL table in this design. Ephemeral session/access-token validity lives entirely in Redis (or is implicit in a stateless JWT's signature), while the one thing that truly must survive a cache flush — the ability to revoke a login before it naturally expires — is captured durably in refresh_tokens instead. See the Session Management deep dive for the full reasoning.

High-Level Design

Clients (web, mobile, third-party API consumers) hit an API Gateway that terminates TLS, enforces global/per-IP rate limits, and forwards to a load balancer in front of a horizontally-autoscaled, stateless Auth Service fleet. The Auth Service talks to Redis for session/refresh-token/rate-limit state, to a sharded and replicated Primary DB for durable user/credential/audit data, and to a separate MFA Service for TOTP/SMS/WebAuthn verification. Social login redirects the client out to an external identity provider and back via an OAuth2 callback. Every auth-relevant event is fired asynchronously to Kafka, which feeds an Analytics/SIEM pipeline for anomaly detection and compliance audit — fully decoupled from the login latency budget.

Figure 1. High-level topology — Client and API Gateway (TLS, WAF, global rate limiting) front a horizontally autoscaled, stateless Auth Service, which fans out to Redis (sessions, refresh tokens, rate-limit counters), a sharded/replicated Primary DB, and an MFA Service. An async Kafka → Analytics/SIEM pipeline carries audit events off the critical path. Social login redirects the client to an external IdP and back via an OAuth2 callback.

Key Design Principles Reflected in the Diagram

  • Stateless Auth Service: no server holds session affinity in memory, so any instance can handle any request — horizontal scaling and load balancing are trivial.
  • Two storage tiers with two different jobs: Redis for fast, ephemeral, TTL-bounded session/token state; the Primary DB for durable, strongly-consistent credential and audit data.
  • Everything not strictly needed to answer "is this login valid?" (audit logging, anomaly detection) is pushed off the critical path and handled asynchronously.
  • Defense in depth before ever reaching the database: WAF/rate limiting at the gateway → in-memory/Redis rate-limit counters → the credential store itself, each layer absorbing abusive traffic before it reaches the next.

Deep Dive — Login Request Flow

This is the sequence every single login traverses, and it's where the two most important LLD details live: a constant-time comparison for the password check, and a deliberately generic error that never distinguishes "wrong password" from "no such account."

Figure 2. Login request flow — every step up through the constant-time hash comparison is identical whether or not the account exists; only after step 5 does the flow branch, and even then the client-visible response in step 7 is worded and shaped identically on failure regardless of which branch was taken.

Login Algorithm (Pseudocode)

function login(identifier, password):
    user = lookupUserByEmailOrUsername(identifier)   // may be null
    credential = user ? fetchPasswordCredential(user.user_id) : null

    // Always run a verify, even for a non-existent user, against a fixed
    // dummy hash of the same algorithm/params — this equalizes latency
    // so response TIME does not leak whether the account exists.
    hashToCompare = credential ? credential.password_hash : DUMMY_HASH
    matched = constantTimeVerify(password, hashToCompare)   // e.g. Argon2id/bcrypt "verify"

    if user is null or not matched or user.status != 'active':
        recordFailedAttempt(identifier, sourceIp)   // Redis counters, see Rate Limiting
        logEvent('login_failure', user?.user_id, sourceIp)
        return genericError(401, "Invalid email or password")   // identical message, identical shape

    resetFailedAttempts(user.user_id)
    if user.mfa_enabled:
        return issueMfaChallenge(user.user_id)
    session = createSession(user.user_id)             // Redis + refresh_tokens row
    logEvent('login_success', user.user_id, sourceIp)
    return { access_token, refresh_token }

Two details are load-bearing, not stylistic: (1) constantTimeVerify uses a comparison whose execution time doesn't depend on where the inputs first differ (bcrypt/Argon2id's own comparison primitives already do this internally for the final hash comparison), which defeats a timing attack that could otherwise recover a hash byte-by-byte from response latency; and (2) running the hash step even when no user was found keeps the overall request latency statistically indistinguishable between "wrong password" and "no such account," closing a side channel that a generic error message alone doesn't close.

Deep Dive — Password Storage and Hashing

Why Not Plain SHA-256 (or MD5)?

General-purpose cryptographic hashes like SHA-256 are designed to be fast — that's a virtue for checksumming a file, and a liability for password storage. Modern GPUs and ASICs can compute billions of SHA-256 hashes per second, so a stolen table of salted SHA-256 hashes can be brute-forced (or dictionary-attacked) at enormous speed. What you actually want is a hash function that is deliberately slow and expensive to compute, so an attacker who steals the hash table still can't afford to test more than a small number of candidate passwords per second per dollar of hardware.

Adaptive, Memory-Hard Hash Functions

AlgorithmHardnessNotes
bcryptCPU-hard, tunable cost factor (work factor 2n)Battle-tested since 1999, available in virtually every language; not memory-hard, so somewhat more GPU-parallelizable than Argon2id.
scryptMemory-hard + CPU-hardGood GPU/ASIC resistance; more complex parameter tuning than bcrypt or Argon2id.
Argon2id (recommended)Memory-hard + CPU-hard, side-channel resistant hybrid modeWinner of the 2015 Password Hashing Competition; current OWASP-recommended default (e.g. m=19 MiB, t=2, p=1, or m=64 MiB with correspondingly lower iterations depending on server memory budget).

Recommendation: Argon2id as the default for new credentials, with bcrypt (cost factor 12+) as an acceptable, more universally-supported fallback where Argon2id libraries aren't available. Either choice must be paired with:

  • A unique, random salt per user (bcrypt/Argon2id generate and store this automatically) — defeats precomputed rainbow-table attacks and ensures two users with the same password never produce the same stored hash.
  • A pepper — an additional application-wide secret (not stored in the database) mixed into the hash input, typically held in a KMS/HSM/secrets manager. A pepper means a database leak alone is not enough to offline-crack passwords; the attacker also needs the application's secret store, a materially higher bar.

Migrating Password-Hashing Algorithms Without Forcing a Mass Reset

Storing the algorithm name and parameters alongside each hash (the PHC string format, e.g. $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>) enables lazy migration: verify the submitted password against whichever algorithm/params are recorded for that row; if it succeeds and the recorded algorithm is outdated (or the cost factor is below the current minimum), re-hash the plaintext password with the new algorithm/params and overwrite the stored value — all inside the same successful-login transaction. Users who don't log in for a long time simply migrate later, the first time they do; no bulk forced reset, no downtime, and it costs nothing extra since you already have the plaintext password in memory at exactly the moment it's verified.

Deep Dive — Session Management: Stateful Sessions vs. Stateless JWTs

This is the single most consequential architectural choice in the whole design, and it's a genuine trade-off — state it explicitly rather than presenting one option as obviously correct.

Recommended Hybrid, and Why

Use a short-lived, stateless JWT access token (~15 minutes, signed asymmetrically with RS256/EdDSA so any downstream service can verify with only the public key) for the hot path of ordinary API calls, paired with a long-lived, stateful, opaque refresh token (~30 days, hashed and stored server-side in refresh_tokens) used only to mint new access tokens. This gets the best of both: the vast majority of requests (regular API calls) pay zero store round-trip cost and scale horizontally for free, while the one operation that needs true revocability (killing a session before its natural expiry) is anchored in a real, server-checkable record. The "JWT can't be revoked" problem is solved by keeping the JWT's blast radius small (15 minutes) and putting all revocation authority in the refresh token instead.

Figure 3. Access/refresh token lifecycle — short-lived JWTs are verified locally with no store round-trip; refresh calls rotate the refresh token and detect reuse (a stolen, already-used refresh token immediately revokes the whole family); logout (device or all-devices) revokes the durable refresh-token record(s), bounding how long a stolen credential can be used after the fact.

Token Refresh Algorithm (Pseudocode)

function refresh(oldRefreshToken):
    hash = sha256(oldRefreshToken)
    row = refreshTokens.findByHash(hash)

    if row is null:
        return error(401, "invalid_token")

    if row.revoked:
        // Reuse of an already-rotated token is a strong signal of theft:
        // someone else has a copy of a token we already superseded.
        revokeAllTokensForUser(row.user_id)   // kill the whole family
        logEvent('refresh_token_reuse_detected', row.user_id)
        return error(401, "reuse_detected_relogin_required")

    if row.expires_at < now():
        return error(401, "expired_token")

    newRefresh = generateOpaqueToken()
    insertRow(refreshTokens, { user_id: row.user_id, token_hash: sha256(newRefresh),
                               issued_at: now(), expires_at: now() + REFRESH_TTL })
    markRevoked(row, replaced_by = newRefresh.token_id)

    newAccess = signJwt({ sub: row.user_id, exp: now() + ACCESS_TTL })
    return { access_token: newAccess, refresh_token: newRefresh }

Deep Dive — OAuth2 / OIDC Social Login

Social login is delegated authentication: an external identity provider (Google, GitHub, Apple, ...) vouches for the user's identity, and our Auth Service maps that vouched identity onto our own users/auth_credentials tables via the OAuth2 authorization code flow (with PKCE), never trusting the IdP's own tokens as our session credential.

Figure 4. OAuth2 authorization-code flow for social login — the IdP's own tokens (step 7) are validated and then discarded as a session credential; only after step 8 links the identity to a local auth_credentials row does the Auth Service mint its own tokens (step 9).

Mapping External Identities onto the Local User Table

  • On first callback for a given (provider, provider_user_id) pair: if the IdP-supplied, verified email matches an existing local account, link the new auth_credentials row to that user (with an explicit confirmation step if the local account's email isn't itself verified, to avoid an attacker linking an account they don't own); otherwise create a new user.
  • The state parameter is itself a CSRF defense for the OAuth handshake specifically — the Auth Service generates and stores it before redirecting, and rejects the callback if the returned state doesn't match.
  • PKCE (Proof Key for Code Exchange) protects the code-exchange step even for public clients (mobile/SPA) that can't safely hold a client secret.
  • A user's IdP-issued access/ID tokens are never stored as our own session credential — they're used once, at the callback, purely to establish identity and populate the local profile.

Deep Dive — Multi-Factor Authentication

MFA adds a second, independent proof of identity — "something you have" (an authenticator app, a phone, a hardware key) on top of "something you know" (the password) — so a leaked password alone is no longer sufficient to take over an account.

Figure 5. MFA enrollment (top, one-time) and verification (bottom, every login) — TOTP per RFC 6238: a 6-digit code derived from a shared secret and the current 30-second time-step, compared with a small drift window to tolerate clock skew.

TOTP (RFC 6238) in Detail

TOTP = HOTP (RFC 4226, an HMAC-based one-time password over a counter) with the counter replaced by floor(unix_time / 30). Concretely: code = Truncate(HMAC-SHA1(secret, time_counter)) mod 10^6, zero-padded to 6 digits. Because clocks drift, the server checks the current time-step and typically ±1 step (i.e. up to 30 seconds of drift each direction) — widening this window trades security margin (a slightly larger brute-force window per code) for user tolerance of clock skew, so it should stay narrow.

Backup Codes and WebAuthn / Passkeys

  • Backup codes are single-use recovery codes generated at enrollment (e.g. 8–10 codes) for when a user loses their authenticator device. Each code has fairly low entropy individually, so each one must be hashed at rest with the same rigor as a password, not stored in plaintext.
  • WebAuthn/passkeys are the strongest modern option: a public/private keypair is generated per site inside a hardware or platform authenticator (a phone's secure enclave, a security key); the private key never leaves the device, and the server only ever stores a public key. This is phishing-resistant by construction — the credential is cryptographically bound to the site's origin, so a lookalike phishing domain simply cannot obtain a valid signature — and it removes shared secrets from the server entirely, unlike TOTP (where the server does hold a secret capable of generating valid codes) or passwords (where the server holds a hash of the actual secret).

Deep Dive — Password Reset Flow

The forgot-password flow is a favorite interview probe because it's easy to get subtly wrong in ways that leak account existence or leave a long-lived, reusable secret lying around.

Figure 6. Password-reset flow — the initial response never reveals whether the email exists; the reset token is single-use, time-boxed to 30 minutes, and only its hash is ever stored; a successful reset revokes every existing session, closing the door on an attacker who had already hijacked one.

Password-Reset Token Algorithm (Pseudocode)

function requestPasswordReset(email):
    user = lookupUserByEmail(email)     // may be null
    if user is not null:
        rawToken = randomBytes(32)                       // 256 bits of entropy
        tokenHash = sha256(rawToken)
        insertRow(passwordResetTokens, { user_id: user.user_id, token_hash: tokenHash,
                                          expires_at: now() + 30_MINUTES, used_at: null })
        sendEmail(user.email, resetLinkContaining(rawToken))   // raw token leaves the server only in this email
    // Identical response either way — do not reveal whether the account exists
    return { message: "If that email is registered, a reset link has been sent." }

function resetPassword(rawToken, newPassword):
    tokenHash = sha256(rawToken)
    row = passwordResetTokens.findByHash(tokenHash)
    if row is null or row.used_at is not null or row.expires_at < now():
        return error(400, "invalid_or_expired_token")
    if isWeakOrBreached(newPassword):                     // length + HIBP k-anonymity check
        return error(400, "password_not_acceptable")

    updateCredential(row.user_id, hash: hashPassword(newPassword))
    markUsed(row)                                          // single-use, enforced by used_at
    revokeAllSessions(row.user_id)                          // kill any session an attacker may hold
    sendEmail(row.user_id.email, "Your password was changed")
    return { status: "password_updated" }

Data Partitioning and Replication

Sharding by user_id

Shard users, auth_credentials, refresh_tokens (durable copy), mfa_secrets, and login_history by hash(user_id) using consistent hashing across a set of logical shards mapped onto physical nodes (e.g. via a Vitess-style topology or a sharding proxy). Nearly every access pattern after the initial login lookup is naturally keyed by user_id, so this is the right primary partition key for the bulk of the schema.

The Login-by-Email Problem: a Global Secondary Index

Login itself arrives keyed by email or username, not user_id — so a pure hash(user_id) shard map can't answer "which shard holds this email" without an extra hop. Two options:

  • Dedicated email→user_id index (recommended): maintain a small, heavily-cached lookup structure (a compact table or dedicated service) mapping normalized_email → user_id, kept mostly resident in Redis given how hot and small it is — every login and every registration-uniqueness check hits it. This decouples "how do we shard everything else" from "how do people log in," and lets this specific hot path be optimized (and monitored) independently.
  • Shard credentials by hash(email) instead: routes the login-time credential fetch directly to the correct shard with no extra hop, at the cost of needing a second, user_id-based index for every other service that references users by ID.

The dedicated index is the more common production pattern, precisely because this lookup is hot enough to deserve first-class caching regardless of how the rest of the schema is sharded.

Why Sessions and Refresh Tokens Live in Redis, Not the Sharded Primary Store

  • Ephemeral by nature: Redis expires keys natively via TTL, with no cleanup cron needed — session state that outlives its TTL should simply cease to exist.
  • Extreme QPS, low-latency, pure key lookup: this access pattern must not compete for capacity with the credential store's transactional workload.
  • Fundamentally different durability requirement: losing session state just forces a re-login (recoverable, low-cost); losing a credential or a uniqueness constraint would be a serious correctness/security bug. Two different durability profiles justify two different storage tiers.

Replication

  • Primary DB: synchronous or semi-synchronous replication within a region for credential writes (registration, password change) — losing a just-written password change is unacceptable — with asynchronous cross-region replication for disaster recovery.
  • Redis: primary + replica per shard for availability; asynchronous replication is acceptable here since a lost session simply forces re-login rather than causing data loss.
  • Read replicas absorb read-heavy paths (profile lookups, admin dashboards) so they don't compete with the primary's write-heavy credential/session workload.

Rate Limiting and Brute-Force Protection

Without controls, a single attacker (or, more realistically, a botnet with a huge rotating IP pool) can attempt millions of password guesses against millions of accounts.

  • Per-IP rate limits (coarse): catch a single-source brute-force attempt, enforced at the API Gateway so rejected requests never reach the Auth Service.
  • Per-account rate limits (essential): track failed attempts keyed by user_id/email in Redis, independent of source IP — this is what actually stops credential stuffing, since those attacks intentionally spread requests across huge IP pools specifically to evade per-IP limits.
  • Exponential backoff: after a threshold of failures (e.g. 3), require an increasing delay before the next attempt on that account is accepted (1s, 2s, 4s, 8s, ...).
  • Progressive, temporary lockout (e.g. 15 minutes after N failures), not permanent — a permanent lock on repeated failure creates a trivial denial-of-service vector where an attacker deliberately fails logins to lock a legitimate user out indefinitely.
  • CAPTCHA escalation: after M suspicious attempts, require a CAPTCHA or proof-of-work challenge before accepting further attempts — raises automation cost while leaving most human users unaffected.

Credential-Stuffing Detection via Breach Corpus Checking

Beyond rate limiting, proactively check candidate passwords against known-breached-password corpora using the Have I Been Pwned (HIBP) Pwned Passwords k-anonymity API pattern: SHA-1 hash the candidate password, send only the first 5 hex characters of that hash to the API, and receive back every known-breached suffix sharing that prefix; the client (or server) then checks locally whether the full hash is among them. The full password (and even its full hash) is never transmitted to the third-party service, yet the check against hundreds of millions of breached credentials is still possible. Run this check at registration, password change, and password reset — never silently at login, since that would require re-hashing on every login for no security gain.

HIBP k-anonymity request shape candidate = "Tr0ub4dor&3"
sha1_hex = SHA1(candidate) → e.g. "F2B14F901..." (40 hex chars)
send GET /range/{first 5 chars} → API returns all matching suffixes + breach counts
reject if the remaining 35 chars appear in the returned set

Security, Privacy, and Permissions

  • HTTPS everywhere, with HSTS enabled, so no authentication traffic (or session cookie) is ever eligible to travel in plaintext.
  • Secure, httpOnly, sameSite cookies for any cookie-delivered token — httpOnly blocks JavaScript (and therefore XSS) from reading it, secure blocks it from ever being sent over plain HTTP, sameSite=Lax/Strict blocks it from being auto-attached to most cross-site requests.
  • CSRF tokens are required specifically because browsers auto-attach cookies to requests — a synchronizer token or double-submit cookie proves the request originated from our own page. Bearer tokens sent explicitly via an Authorization header are not auto-attached by the browser, so they sidestep classic CSRF — a genuine trade-off in favor of the JWT/bearer model, at the cost of needing somewhere safe (not localStorage) to keep the token from XSS.
  • XSS mitigation: a strict Content-Security-Policy, consistent output encoding, and — as above — keeping any long-lived token out of localStorage/JS-readable storage where a single XSS bug could exfiltrate it wholesale.
  • Password rules — favor NIST SP 800-63B over legacy complexity rules: require a reasonable minimum length (e.g. 8–12 characters), allow long passphrases (up to 64+ characters), and do not force arbitrary composition rules ("must contain a symbol") or periodic rotation without cause — both are shown to push users toward predictable patterns (Password1!) rather than genuinely stronger secrets. Screen against breach corpora (see above) instead; that's a far higher-signal check than composition rules.
  • Account-enumeration prevention: identical response messages and near-identical response latency for "wrong password" and "no such account" (see the login algorithm above); identical registration response whether or not an email is already taken (e.g. "if this email isn't already registered, we've sent a verification link").
  • Secure password-reset flow: single-use, time-boxed tokens, sent only to the verified email already on file — recapped in full in the dedicated deep dive above.

Monitoring, Logging, and Analytics

Every auth-relevant event fans out asynchronously to Kafka and into a security analytics/SIEM pipeline, fully decoupled from the login latency budget (per the capacity math above, this pipeline handles roughly 10M events/day at steady state).

  • Failed-login-rate alerting: page on-call when the global (or per-account, or per-IP) failed-login rate spikes well above its historical baseline — an early, high-signal indicator of a credential-stuffing campaign in progress.
  • "Impossible travel" / geographic-anomaly detection: flag a login when the implied travel speed between it and the account's last known login location is physically infeasible (e.g. Mumbai at 10:00, then São Paulo at 10:20 implies ~14,000 km in 20 minutes) — a strong signal of a stolen credential or hijacked session, triggering a step-up MFA challenge or a temporary hold rather than an outright block.
  • New-device / new-location notifications: email the user whenever a login succeeds from a device or location fingerprint not seen before, giving them an independent channel to notice an account takeover even if the attacker doesn't trip any automated rule.
  • Immutable audit trail (the login_history table) for compliance review — every login, logout, password change, MFA enrollment, and lockout, retained per the retention policy and partitioned by month.
  • Security dashboards aggregating login success/failure rates, MFA adoption, lockout counts, and breach-password-hit rate over time, feeding back into product and security prioritization.

Load Balancing

Load balancing sits at three points: clients ↔ Auth Service, Auth Service ↔ Redis, and Auth Service ↔ sharded Primary DB. Start with round-robin (or least-connections) with health-check-based draining — cheap, and it automatically routes around a failing instance. Because this design deliberately avoids server-held session affinity (sessions live in Redis, not in any one app server's memory), no sticky sessions are required — any Auth Service instance can serve any request, which is exactly what makes horizontal autoscaling for the "morning login surge" tractable in the first place.

Scaling to Multiple Regions

  • Run each region active-active with its own Auth Service tier, Redis cluster, and DB replica set; route users to the nearest region via Geo-DNS or anycast for lowest latency.
  • Credential writes (registration, password change) replicate synchronously/quorum within a region and asynchronously cross-region — correctness of the source of truth is prioritized over instant multi-region read-your-writes for this data.

The Hard Problem: Multi-Region Session Consistency

The interesting trade-off is what happens to a session/refresh-token when a user's next request lands in a different region than the one that issued it:

ApproachTrade-off
Sticky-to-home-regionSimplest — a session is only valid in its issuing region; a request elsewhere is proxied back or forces re-auth. Adds latency for a genuinely roaming user, but no replication-lag correctness risk.
Globally-replicated session storeWorks from anywhere immediately, but async replication leaves a bounded window where a just-issued/just-rotated token isn't yet visible in another region — risking a spurious "invalid token" if the user's very next request lands elsewhere before replication catches up.
Region-hint embedded in the token (recommended middle ground)The token itself carries a home-region hint so routing can prefer the issuing region for validation, while still allowing failover to a replica if that region is down — bounded staleness without full global synchronous replication.

If Redis goes down: degrade, don't hard-fail
With the JWT-access + server-validated-refresh hybrid, a Redis outage does not invalidate already-issued access tokens — they verify locally by signature. What breaks: (1) token refresh, since validating a refresh token needs the store — mitigate by falling back to the durable DB copy of token hashes at higher latency rather than an unconditional failure; (2) revocation checks briefly become less enforceable mid-outage — an explicit, named trade-off, not an accident; (3) new logins may be rate-limited more conservatively if Redis-backed counters are unavailable. Net effect: users mid-session keep working until their 15-minute access token naturally expires, at which point they're forced to re-login — a bounded blast radius rather than a full outage.

CAP Theorem Lens

Favor strict consistency for credential writes and uniqueness constraints (two accounts must never silently collide on the same email; a password update must never be partially applied). Favor availability for session/token validation reads on the hot path (a slightly stale "is this still valid" check against a replica beats blocking every API call in the product on synchronous cross-region consistency) — but with one explicit, named exception: a just-revoked session must become invalid within a bounded, short window, not an indefinite one, since availability-over-consistency taken too far here has a real security cost, not just a UX one.

Common Interview Questions

These are organized by theme — use them to rehearse, or expect a real interview to pick 3–5 as "and then what?" follow-ups on whatever you presented.

Password Storage and Cryptography

Why use bcrypt/Argon2id instead of SHA-256 for storing passwords?
SHA-256 is deliberately fast, which is exactly wrong for password storage — billions of guesses/sec are feasible on modern GPUs against a stolen table. bcrypt/Argon2id are deliberately slow and (for Argon2id) memory-hard, so brute-forcing a stolen hash table is computationally and financially expensive even at scale.
Why does a timing-safe (constant-time) comparison matter for authentication?
A naive byte-by-byte comparison that returns early on the first mismatch leaks information through response time — an attacker can recover a secret one byte at a time by measuring which candidate takes marginally longer. A constant-time comparison (and, at the login-flow level, always doing a hash computation even for unknown users) removes that timing side-channel.
How would you migrate users from an old password-hashing algorithm to a new one without forcing a mass password reset?
Store the algorithm/params alongside each hash (PHC string format) and migrate lazily: verify with the recorded algorithm at login, and if it succeeds and the algorithm is outdated, re-hash with the new algorithm using the plaintext you already have in memory at that moment, then overwrite the stored value. No bulk reset, no downtime.
Why add a pepper in addition to a per-user salt?
A salt defeats rainbow tables and cross-user pattern matching but lives right next to the hash in the same database. A pepper is a secret held outside the database (in a KMS/HSM), so a database-only leak isn't sufficient to offline-crack the hashes — the attacker also needs the application's separate secret store.

Sessions, Tokens, and Revocation

JWTs vs. server-side session cookies — what are the real trade-offs?
JWTs verify locally (fast, no store round-trip, trivially horizontally scalable) but can't be revoked before their natural expiry without extra machinery. Server-side sessions revoke instantly but need a shared, available store on every request. The common resolution is the hybrid used here: short-lived JWT access token + stateful, revocable refresh token.
How do you revoke a JWT before it naturally expires?
You generally can't revoke the signature itself, so you minimize the blast radius instead: keep access-token TTLs short (~15 min) and put all real revocation authority in the paired refresh token, which is checked against a server-side store on every refresh. A pure blocklist of revoked JWT IDs is an alternative but reintroduces a store lookup on every request, defeating the point of using JWTs at all.
How would you implement "log out of all devices"?
Iterate and revoke every row in refresh_tokens for that user_id (the table is indexed by user_id for exactly this). Any already-issued access token for another device still works until its short TTL naturally expires, then that device's next refresh attempt is rejected, forcing re-login.
What happens to already-issued access tokens if Redis goes down?
Nothing — they verify by signature alone, with no dependency on Redis. Only refresh calls and revocation enforcement are affected during the outage, which is a deliberate, bounded degradation rather than a full authentication outage.

Attacks and Abuse Prevention

How do you prevent credential stuffing specifically (as opposed to simple brute force)?
Credential stuffing spreads requests across huge, rotating IP pools specifically to evade per-IP limits, so per-account rate limiting (keyed by user_id/email, independent of source IP) is the primary defense, combined with breach-corpus checking (HIBP k-anonymity) so previously-leaked passwords are rejected proactively rather than only after they're tried.
Why should "wrong password" and "user not found" return the same generic error message?
A distinguishable response lets an attacker enumerate which emails have accounts at all, which is valuable reconnaissance for a targeted attack (phishing, credential stuffing against a known-valid email). Returning an identical message — and running the same hash-verification work either way to equalize timing — removes that signal entirely.
How do you design account lockout without creating a denial-of-service vector against legitimate users?
Use progressive, temporary lockouts (e.g. 15 minutes) rather than permanent ones, and prefer exponential backoff over hard lockout where possible — both let a legitimate user recover on their own without support intervention, while still meaningfully slowing an attacker.
How would you detect account takeover after the fact, not just block it at login time?
Impossible-travel/geo-anomaly detection on the login_history stream, new-device/new-location email notifications, and monitoring for post-login behavior anomalies (e.g. a sudden password change or MFA disablement immediately after a login from a new location) — all fed by the same Kafka audit pipeline used for compliance logging.
How do you securely implement the "forgot password" flow end-to-end?
Always return an identical response regardless of whether the email exists; generate a high-entropy random token and store only its hash with a short (~30 min) expiry and single-use enforcement; email the raw token only to the verified address on file; and revoke all existing sessions once the password is actually changed.

MFA and Modern Authentication

How do WebAuthn/passkeys improve on passwords, and even on TOTP?
WebAuthn uses per-site public/private keypairs generated in a hardware/platform authenticator; the private key never leaves the device and the server only ever stores a public key. It's phishing-resistant by construction (the credential is bound to the origin), and unlike TOTP, the server never holds a secret capable of generating a valid proof on its own.
Why does TOTP need a time-synchronization tolerance window, and what's the security cost of widening it?
Client and server clocks drift, so the server typically accepts the current 30-second time-step and one step on either side. Widening this window tolerates more drift but also widens the effective brute-force window per submitted code, so it should be kept as narrow as user experience allows.
How would you let a user recover access if they lose their MFA device and their backup codes?
A deliberately slower, higher-friction identity-verification path (e.g. manual support review, a cooling-off period, re-verification against other known account signals) — explicitly not a fast self-service reset, since a fast path here would just become the attacker's preferred way to bypass MFA entirely.

Scaling and Operations

How would you design rate limiting for the login endpoint?
Layered: coarse per-IP limits at the API Gateway, finer per-account limits in Redis with exponential backoff, progressive (non-permanent) lockout past a threshold, and CAPTCHA escalation for accounts/IPs that look automated — each layer catching a different attack shape.
How would you scale the login path for a sudden 30× traffic spike (e.g. after a regional outage)?
Horizontal autoscaling of the stateless Auth Service fleet (no session affinity to worry about), pre-provisioned headroom informed by the surge math (see Capacity Estimation), and rate limiting tuned to distinguish a legitimate mass re-login from a credential-stuffing botnet riding the same spike.
How do you keep sessions consistent across multiple regions?
Either keep a session sticky to its issuing region (simplest, adds latency for roaming users), fully replicate the session store globally (best UX, introduces a bounded staleness window), or embed a region hint in the token itself so validation prefers the issuing region while still allowing failover — a genuine trade-off, not a solved problem.
How would you roll out a breaking change to the token format without logging out every active user?
Version the token (e.g. a "kid"/version claim), accept both old and new formats during a transition window, and let old tokens simply expire naturally on their existing TTL rather than force-invalidating them — new logins and refreshes pick up the new format automatically.

Key Takeaways

Remember
Treat this as a security design problem first, not a CRUD problem with a login form on top — every choice (hash algorithm, token model, error wording, rate-limit shape) should be traceable to a specific attack it defends against. Use adaptive, slow, salted (and peppered) password hashing — never a fast general-purpose hash. Prefer a hybrid session model: short-lived stateless JWTs for the hot path, paired with a stateful, rotating refresh token for the one operation that genuinely needs revocability. Make timing and error messages indistinguishable between "wrong password" and "unknown account" — enumeration defense is a first-class requirement, not an afterthought. Size compute for the deliberately expensive password hash, not just for network I/O — the capacity math changes depending on your cost-factor choice. Push everything not required to answer "is this login valid right now" (audit logging, anomaly detection, notifications) onto an asynchronous path, exactly as a read-heavy system pushes analytics off its hot path.
