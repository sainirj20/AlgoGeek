SYSTEM DESIGN

Price Alert System (Amazon / Stock Prices)

A complete, interview-ready design walkthrough for a threshold-based price alert system covering both e-commerce (Amazon-style) product prices and stock/ticker prices behind one shared evaluation core: requirements, capacity estimation, API design, data model, high-level architecture, efficient per-product rule indexing, hysteresis/debounce, hot-ticker sub-sharding, historical time-series storage, partitioning, complex conditions, security, and follow-up interview questions.

Problem Statement

Design a price alert system that lets a user say "tell me when this crosses a price I care about" for either of two variants that share one evaluation core: (1) e-commerce — "notify me when this product drops below $49.99," or "drops by 20% from what I paid," and (2) stocks/tickers — "notify me when TSLA crosses $250," or "drops 5% below its 30-day high." A user creates one or more alert rules on a product (SKU/ASIN) or a ticker symbol; the system continuously watches the relevant price stream, evaluates every active rule against every incoming price update for its target, and when a rule's condition becomes true, delivers a notification through the user's preferred channel. Alerts can be one-shot (fire once, then deactivate) or repeating (re-arm and can fire again later).

Why does this problem matter in an interview?

It looks like a simple CRUD-plus-cron problem at first glance, but it hides several classic, individually-hard sub-problems: two very different ingestion cadences feeding one pipeline (periodic polling/scraping vs. a continuous streaming feed), a rule-evaluation step that must not become an O(n) scan when a single product or ticker can carry millions of rules, a debouncing problem (a price oscillating around a threshold must not spam the user), and a time-series storage problem at the scale of billions of points retained for years. A strong candidate treats "how do we evaluate a price tick against millions of rules without scanning all of them" as the load-bearing question — not "how do we build a scraper" or "how do we send an email."

Why one shared evaluation core for two very different variants?

  • Both variants reduce to the same abstraction: a stream of (target_id, price, timestamp) updates, a per-target set of active rules keyed by threshold/condition, and a notify-on-match step. Building two independent systems would duplicate the hardest part twice.
  • The two variants differ only at the edges: how a price update is produced (poll/scrape vs. streaming feed) and how "fresh enough" is defined (minutes/hours vs. seconds) — everything from the event stream onward (evaluation, indexing, hysteresis, notification) is identical code.
  • New target types (e.g. crypto, real estate listings, flight fares) become a third ingestion adapter feeding the same stream, not a third system.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope before drawing boxes.

  1. Are we designing for e-commerce price drops (Amazon-style), stock/ticker prices, or both behind one shared evaluation core?
  2. What freshness is actually required — near-real-time (seconds) for stocks, or is minutes-to-hours acceptable for e-commerce given polling/scraping cost?
  3. Do alerts fire once and deactivate, or can a user ask to be notified every time the condition becomes true again (repeating, with some re-arm rule)?
  4. Do we need to support complex conditions ("5% below the 30-day high," "back in stock"), or is a simple absolute threshold cross enough for v1?
  5. Is there a first-party product/pricing API we can call, or do we need to scrape when no API exists or its rate limits are too restrictive (e-commerce specifically)?
  6. How many years of historical price history must we retain, and do we need to power charts or "N-day high" style conditions off it?
  7. Do we need multi-channel notification (email/SMS/push), or is a single channel enough at launch — can we assume an existing notification service handles final delivery?
  8. Should we cap how many alerts a single user can create, and how many total rules a single product/ticker can attract?
  9. Single region to start, or does the design need to anticipate multiple exchanges/marketplaces and users spread globally from day one?
  10. Is silently missing a trigger acceptable in extreme scenarios (e.g. a brief outage), or is that treated as a functional bug that needs a reconciliation backstop?
Interview tip
Don't stall waiting for every answer — state a reasonable assumption out loud ("I'll design one shared core: ingestion → stream → evaluation → notification, and call out where the two variants diverge, rather than building two independent systems") and keep moving. Explicitly naming the shared abstraction early is exactly the kind of framing interviewers reward.

Requirements and Goals

Functional Requirements

  1. A user creates an alert rule on a product or ticker: a threshold price, a direction (above/below), or a percent-change condition, optionally relative to a reference value (30-day high, price-at-creation).
  2. The system continuously watches the relevant price stream and evaluates every active rule against every price update for its target.
  3. When a rule's condition is met, notify the user through their preferred channel (email/SMS/push).
  4. Support both one-shot alerts (fire once, then deactivate) and repeating alerts (re-arm after a cooldown / after the condition becomes false again by some margin).
  5. Users can list, edit, pause, and cancel their own alert rules.
  6. Support complex, composed conditions — e.g. "5% below the 30-day high" (stocks), "back in stock" (e-commerce) — without a bespoke pipeline per condition type.
  7. Provide a queryable price history (for charts and for reference-value conditions like "N-day high") spanning years.
  8. Scale to millions of independently tracked products/tickers, each with its own, wildly-varying-in-size set of rules.

Non-Functional Requirements

  1. Near-real-time freshness for stocks: a price crossing a threshold should trigger a notification within a few seconds end-to-end.
  2. Reasonably fresh for e-commerce: minutes to a few hours is acceptable — retail prices don't change every second, and polling/scraping every product every second has real cost and would be abusive to the source.
  3. Horizontal scalability to millions of tracked products/tickers and hundreds of millions of concurrently active alert rules.
  4. Correctness first: never silently miss a trigger — a missed price-drop alert is a functional bug, not a minor UX annoyance, and needs a reconciliation backstop, not just hope.
  5. No alert storms: avoid duplicate/spam notifications when a price "flaps" back and forth across a threshold (hysteresis/debounce is a first-class requirement, not a nice-to-have).
  6. High write throughput on ingestion, decoupled from the read-heavy evaluation and notification paths, so a Black-Friday price-drop wave or an earnings-day volatility spike never blocks either.
  7. Durable, long-retention historical storage that still answers time-range queries fast enough for charting and "N-day high/low" conditions, at billions-of-points scale.

Extended / Out of Scope

We'll go deep on ingestion, efficient per-target rule indexing, hysteresis/debounce, hot-key sub-sharding, historical time-series storage, and partitioning. We call out but don't build the internals of a full charting UI, anti-bot/scraping-legality infrastructure, or a general strategy-backtesting engine on top of the historical price data — real products, but layered on top of this core.

Capacity Estimation and Constraints

State assumptions explicitly and let them drive every downstream decision. Because the two variants have very different traffic shapes, we size each separately, then combine at the stream/storage layer.

Notice the two ingestion endpoints normalize into the identical downstream shape — { target_id, price, timestamp, [in_stock] }. Data Model and Database Choice

Nature of the Data

  • Alert rules: hundreds of millions of rows, read-heavy on "give me all active rules for target X" (the evaluation hot path), write-light relative to reads (rules are created/paused/cancelled far less often than they're evaluated against incoming ticks).
  • Price history: an extremely write-heavy, append-only time series, queried almost exclusively by time range, never updated in place — the textbook case for a wide-column/time-series store over a relational database.
  • Hot cache: the current price and a recent rolling window (e.g. 30–90 days) per popular target, so the overwhelming majority of "is this a new 30-day high" checks never touch the underlying time-series store at all.

Rule Store: Wide-Column, Keyed by target_id, Denormalized for "My Alerts"

The evaluation access pattern ("all active rules for this target_id, sorted by threshold") wants rules physically co-located and pre-sorted per target — a wide-column store (e.g. Cassandra/Bigtable/DynamoDB) partitioned by target_id with rule_id as a clustering key is the natural fit, and it's exactly what lets the per-target sorted-threshold structure in the next section live cheaply in memory per partition. But the "list/cancel my alerts" UI access pattern needs the opposite key (user_id) — rather than forcing a scatter-gather query across every target-partitioned shard, we denormalize into a second, user_id-keyed table that's a thin index back to the canonical rows.

Relational (single Postgres-style table)Wide-column, target_id-keyed (chosen)
Evaluation hot-path readIndex scan on target_id — fine at small scale, degrades as hot-key skew growsWhole partition for a target_id is co-located and pre-sortable in memory
Horizontal scale to 300M+ rulesNeeds manual sharding on top of a relational engineNative horizontal partitioning
"My alerts" by user_idTrivial secondary indexNeeds a denormalized second table (accepted trade-off)
Hot-key skew (millions of rules on one target_id)One shard/partition becomes a hotspotSame risk, but sub-shardable — see Hot-Ticker Sub-Sharding

Price History: Time-Series Store, Not Relational

Billions of points/day, append-only, queried by contiguous time range — a wide-column or purpose-built time-series store (Cassandra/Bigtable/HBase-style, or a TSDB such as InfluxDB/TimescaleDB) partitioned by (target_id, time-bucket) lets a "last 30 days for TSLA" query become a small, contiguous range scan instead of an index-wide search. A hot-range cache (Redis) sits in front, holding a rolling recent window per popular target so the vast majority of reads never reach the time-series store — detailed in the Historical Storage deep dive below.

High-Level Design

Two ingestion adapters — a Data Collection Service that polls or scrapes e-commerce product pages (more frequently for popular products, via a product API where available or a scraper where API rate limits are insufficient) and a Market Data Feed client that receives a continuous stream of stock ticks — both normalize their updates and publish them onto a single price-updates Kafka topic, partitioned by target_id. An Alert Evaluation Service consumes that stream, looks up the active rules for the incoming target_id from the Rule Store (using the sorted-threshold index described in the next section), consults the Price History + Hot-Range Cache for any reference-value conditions (30-day high, etc.), and checks each rule's threshold/direction/percent-change condition. Any rule whose condition is met is published to a triggered-alerts Kafka topic, which a Notification Service drains and dispatches to the user's preferred channel — reusing the priority-queue, rate-limiting, and fan-out patterns of a dedicated notification service rather than re-inventing delivery.

Figure 1. High-level architecture — two ingestion adapters feed one Kafka price-updates topic; the Alert Evaluation Service checks rules against a target_id-sharded Rule Store plus a Price History / Hot-Range Cache, and publishes matches to a triggered-alerts topic that a Notification Service fans out across channels.

Key Design Principles Reflected in the Diagram

  • One event shape, two producers: the price-updates topic doesn't know or care whether an event came from a scraper sweep or a live tick — everything downstream is variant-agnostic.
  • Evaluation never scans "all rules" — it only ever asks the Rule Store for the (small, sorted) slice of rules relevant to the target_id on the event it just received.
  • Kafka decouples "detected a trigger" from "delivered a notification" — the Notification Service scales and fails independently of ingestion and evaluation.
  • The Price History + Hot-Range Cache is consulted, not scanned, on the hot path — only reference-value condition types (30-day high, etc.) touch it at all, and almost always via the cache, not the cold store.

Deep Dive — Efficient Rule Indexing per Product

The naive design stores each target's rules as an unordered list and, on every price tick, scans all N of them to check whether any threshold was crossed. For the median product or ticker with a handful of rules this is fine — but for a hot target carrying millions of rules, an O(n) scan on every single tick (and ticks can arrive many times per second for an actively-traded stock) is a non-starter.

Sorted-Threshold Structure, One Per (target_id, direction)

Instead, keep the rules for a given target_id in two sorted structures (a balanced tree, skip list, or sorted array with binary-search insert) — one for "notify below X" rules ordered ascending by threshold, one for "notify above X" rules ordered ascending by threshold. On a price update from old_price to new_price, we only ever need to find the rules whose threshold lies in the "crossing range" the price just moved through:

Crossing-range query Falling price (new_price < old_price): probe the "below" structure for thresholds in (new_price, old_price]
Rising price (new_price > old_price): probe the "above" structure for thresholds in [old_price, new_price)
Cost: O(log n) to find the range boundary + O(k) to walk the k matched rules — not O(n) over every rule watching the target

Percent-change / N-day-high-relative rules can't be pre-sorted by a fixed absolute threshold, since the trigger price itself is derived and moves whenever the reference value changes (e.g. a new 30-day high is set). We handle this by recomputing each such rule's effective absolute threshold whenever its reference value changes and re-inserting it into the same sorted structure — covered further in Feature-Specific Logic below — so the hot-path evaluation cost stays O(log n + k) regardless of condition type.

Figure 2. Crossing-range query on the sorted-threshold structure: a price drop from $242 to $228 only touches the 3 rules whose threshold falls in the crossing band — O(log n + k), never a full scan of every rule on the target.

Deep Dive — Hysteresis / Debounce to Prevent Alert Storms on Flapping Prices

A price hovering right at a threshold — a stock bouncing between $49.98 and $50.02, or a retailer's dynamic pricing engine nudging a price a few cents around a round number — would otherwise trigger, clear, and re-trigger repeatedly within seconds: an alert storm that spams the user and wastes evaluation and notification capacity on noise, not signal.

Per-Rule State Machine: ARMED → TRIGGERED → COOLDOWN

Each rule carries a small state machine rather than being purely stateless. In ARMED, the rule is live in the sorted-threshold structure and eligible to fire. When its condition is met, it moves to TRIGGERED: a notification is published, and last_triggered_at is recorded. For a one-shot alert, TRIGGERED is terminal — the rule deactivates. For a repeating alert, TRIGGERED transitions into COOLDOWN for a configurable minimum interval (e.g. 30 minutes), during which no re-fire is possible regardless of further price movement. The rule only returns to ARMED once both the cooldown interval has elapsed and a hysteresis "reset" condition is satisfied.

Hysteresis Band — Why a Single Reset Point Isn't Enough

If re-arming happened the instant the price ticked back over the original threshold, a price sitting exactly at the boundary would still flap the state machine every tick. Instead, the reset condition uses a band offset from the original threshold — e.g. a rule that triggers when price drops below $50 only re-arms once price rises back above $51 (a 2% band), not the moment it crosses $50.00 again. This is the same hysteresis technique used in thermostats and Schmitt-trigger circuits, applied to a price series instead of a temperature or voltage signal.

Figure 3. Per-rule state machine with hysteresis: TRIGGERED → COOLDOWN → ARMED requires both a minimum time interval and a price move back past a reset band, not just a single boundary re-cross — this is what stops a flapping price from causing an alert storm.

Deep Dive — Hot-Ticker Sub-Sharding

A small number of targets attract a wildly disproportionate share of rules: a viral flash-sale item or a heavily-watched mega-cap stock during earnings season can carry millions of alert rules, while the median tracked item has a handful. A single partition/evaluator responsible for that one hot key becomes a bottleneck — even with the O(log n + k) sorted-threshold structure, the working set (millions of rules) can be too large to evaluate against a high tick rate on one core, and it also skews that shard's memory footprint far beyond its neighbors.

Detecting and Sub-Sharding a Hot Key

A background monitor tracks rule count per target_id (see Monitoring, Logging and Analytics below). When a target_id crosses a configured hot threshold (e.g. >100,000 rules), its rule set is sub-sharded across a dedicated pool of parallel workers — for example, by hashing rule_id or bucketing by threshold-range into 16–64 sub-shards, each holding its own independent sorted-threshold structure over a slice of the rules. A single incoming price tick for that hot target is fanned out to every sub-shard worker in parallel (not processed sequentially by one worker); each worker independently runs its own crossing-range query over its slice, and a lightweight aggregator merges the union of triggered rule_ids before publishing to the triggered-alerts topic. If a key's rule count later drops back below a lower threshold (e.g. interest fades once a deal ends), the sub-shards are merged back down to avoid keeping idle worker capacity provisioned indefinitely — with its own hysteresis so the system doesn't thrash between sharded and unsharded on small fluctuations.

Figure 4. Hot-ticker sub-sharding: a target's rule set is split across a pool of parallel workers once it crosses a rule-count threshold, so evaluating a single tick against millions of rules stays parallel rather than a serial bottleneck on one partition.

Deep Dive — Historical Price Storage and Time-Range Queries

Billions of price points must be retained for years — for user-facing charts and for reference-value conditions like "30-day high" — while still answering time-range queries fast, and the overwhelming majority of query traffic is for recent, popular data.

Time-Series Schema

The price_history table is partitioned by (target_id, time-bucket) — e.g. one partition per (product_id/ticker, day) — with individual price points as clustered columns ordered by timestamp within the partition. A "last 30 days for TSLA" query becomes a small, contiguous range scan over roughly 30 partitions rather than an index-wide search across billions of rows.

Hot-Range Cache

For popular, actively-alerted targets, Redis holds a rolling recent window (e.g. the last 30–90 days, or an OHLC-bar rollup of it) so the "is this a new 30-day high" check on every tick almost never touches the underlying time-series store — only a cache miss (a cold or rarely-watched item) falls through to it.

Downsampling and Compaction

Raw per-tick data is valuable only for a limited retention window (e.g. 7–30 days); a background compaction job then rolls it up into 1-minute, 1-hour, and 1-day OHLC bars for long-term retention. This keeps storage growth bounded (rather than the raw 84 TB/year from the capacity estimate compounding indefinitely) while still supporting "N-day/month/year high" conditions and charting at coarser granularity for older history.

Figure 5. Historical price storage: writes fan out to a partitioned time-series store and a Redis hot-range cache; reads hit the cache first (the common case for popular targets), falling back to the cold store only on a miss; a background job compacts raw ticks into coarser bars for long-term retention.

Data Partitioning and Replication

The guiding principle throughout: co-locate a target's price stream, its rule store partition, and its evaluation worker, so a price tick and the rules it must be checked against always land on the same shard with no cross-shard coordination — with the hot-key sub-sharding layer from the previous deep dive as the deliberate exception for targets that outgrow a single shard.

  • price-updates topic is partitioned by hash(target_id), so all updates for one product/ticker are strictly ordered on the same partition.
  • alert_rules is sharded by the same target_id in the Rule Store, so the Alert Evaluation Service instance consuming a given price-updates partition can hold that partition's rule set in memory without a network hop — the same hashing scheme is used on both sides deliberately.
  • triggered-alerts topic is instead partitioned by user_id, so the Notification Service (and any per-user rate limiting downstream) sees one user's triggered alerts in order, regardless of which targets they came from.

Feature-Specific Logic: Supporting Complex Conditions

Every "complex" condition reduces to the same two-part pattern: (a) maintain a derived/rolling reference value incrementally, and (b) run a plain threshold check against that reference using the exact same sorted-threshold indexing and hysteresis machinery already built — new condition types are additive, never a redesign.

"5% Below the 30-Day High"

Maintain a rolling 30-day high per target as a reference value, updated incrementally from the Hot-Range Cache whenever a new price point arrives (a sliding-window maximum, or simply re-derived from the cached rollup bars). Whenever that reference value changes — i.e. a new 30-day high is set — recompute the effective absolute threshold for every PCT_DROP_FROM_N_DAY_HIGH rule on that target (threshold = reference × (1 − pct/100)) and re-insert it at its new position in the sorted-threshold structure from the Rule Indexing deep dive. Evaluation on every subsequent tick is then an ordinary absolute-threshold crossing-range check, unaware that the threshold is conceptually "dynamic."

"Back in Stock"

Modeled as a distinct condition_type on the same target_id-keyed rule, evaluated off the in_stock boolean carried on each e-commerce price-update event rather than the price value at all. It's a boundary-crossing detector (false → true) that reuses the identical ARMED/TRIGGERED/COOLDOWN state machine from the Hysteresis deep dive — no bespoke pipeline needed, just a different field on the incoming event and a boolean instead of a numeric comparison.

Composed / Multi-Condition Alerts

A rule requiring more than one simultaneous condition (e.g. "below $250 AND back in stock") is represented as a small AND-group of sibling rule rows sharing a group_id; each sibling is independently ARMED/TRIGGERED against the same indexing and hysteresis machinery, and the group only actually notifies once every sibling in the group is simultaneously TRIGGERED — keeping the per-condition evaluation logic completely unchanged and pushing the composition logic to a thin layer above it.

Rate Limiting and Abuse Prevention

  • Per-user alert-creation caps: a maximum number of active rules per user (e.g. 200, tiered by account type), enforced at alert-creation time, to bound both storage growth and worst-case fan-out from any single user.
  • Per-user notification caps as a backstop: even with hysteresis correctly debouncing a single rule, cap total triggered notifications per user per day as a defense-in-depth measure against a misconfigured or unexpectedly volatile rule.
  • Politeness limits on the e-commerce collector: rate-limit and back off against the source site, rotate collection to respect the target site's own limits, and honor robots.txt and API terms of service where a first-party API isn't available — the collector must never itself become a source of abusive traffic against the marketplace it's reading from.
  • Abuse of the create-alert API itself: rate-limit alert creation per account/IP to prevent bulk/bot-created rules on a single target (e.g. an attempt to inflate a visible "N people are watching this" counter, if that's ever surfaced as a feature).

Security, Privacy and Permissions

  • Ownership checks on every alert operation: a user can only view, edit, pause, or cancel alert rules where rule_id resolves to their own user_id — enforced at the API layer before any datastore call, not left to a client-side check.
  • No PII in evaluation/price logs: the Alert Evaluation Service's operational logs reference rule_id and target_id only; a user's email address or phone number is never written to a general-purpose log, only to the access-controlled alert/notification-preference store.
  • Transport and credential security: TLS everywhere; authenticated/signed connections to the market-data feed provider and between the e-commerce collector and its internal ingestion endpoint; provider API keys and feed credentials live in a secrets manager, rotated regularly, never logged.
  • Market-data licensing: many market-data providers impose redistribution/display restrictions on raw tick data (e.g. delayed-quote requirements for non-professional users, limits on caching/re-serving data to end users) — flag this as a real compliance constraint on the Hot-Range Cache and history API design, even though the full legal review is out of scope for this exercise.

Load Balancing

  1. Standard L7 load balancer, health-checked, in front of the user-facing alerts CRUD API.
  2. Kafka consumer-group rebalancing handles load distribution across Alert Evaluation Service instances natively as the fleet scales up/down with partition count.
  3. A load-aware balancer across the hot-key sub-shard worker pool (Deep Dive: Hot-Ticker Sub-Sharding), since a uniform hash split doesn't guarantee uniform tick-processing cost across sub-shards if rules within the hot target are themselves unevenly clustered by threshold.

Scaling to Multiple Regions

  • The stock variant is inherently tied to specific exchanges and their trading hours — run the Market Data Feed ingestion and its Alert Evaluation Service instances near the exchange/feed provider's region to minimize feed latency, since that latency is the dominant cost for the near-real-time NFR.
  • The e-commerce collector is regionalized per marketplace (amazon.com vs. amazon.co.uk have different catalogs, currencies, and prices) — each marketplace's collector and its price-updates partitions live in the region closest to that marketplace.
  • The Rule Store replicates globally for durability, but evaluation ownership for a given target_id is pinned to the region that owns its canonical price feed, avoiding cross-region coordination on the hot evaluation path.
  • Notification dispatch happens in the user's home region, reusing the same home-region-pinning pattern a dedicated notification service already uses for its own rate-limit counters.

CAP Theorem Lens

Favor availability (AP) for price-history reads and chart queries — a slightly stale chart or a cache serving a few-seconds-old rolling high is far better than blocking evaluation on a consistency check. Favor consistency for the rule store's status transitions specifically (ARMED/TRIGGERED/COOLDOWN) — a race that lets the same rule fire twice because two replicas both believed it was still ARMED is exactly the duplicate-notification bug the idempotent-dispatch dedup key exists to catch as a second line of defense, but getting the state transition itself consistent is the cheaper fix.

Monitoring, Logging and Analytics

  • Evaluation lag: time from a price tick's observed_at/exchange timestamp to the moment a matching alert is published to the triggered-alerts topic — the single most important SLO metric, dashboarded p50/p99 separately for the stock and e-commerce variants given their very different freshness targets.
  • Missed-trigger reconciliation sweep: a scheduled batch job that re-scans recent price history (e.g. the last 24 hours) against currently-active rules and compares against what the streaming evaluator actually fired, surfacing any gap for investigation — a correctness backstop, not the primary evaluation path.
  • Notification delivery success rate: per-channel (email/SMS/push) delivery and failure rates, reusing the delivery-tracking infrastructure of a dedicated notification service rather than building a parallel one.
  • Per-target rule-count skew monitoring: continuously track the rule-count distribution across all tracked targets so the hot-key detector can proactively sub-shard a rising target before it becomes a latency bottleneck, rather than reacting after a p99 spike.
  • Ingestion health: collector success/failure rate per source site (e-commerce) and feed connection uptime/tick-gap detection (stocks), since a silent ingestion failure is functionally identical to a missed trigger from the user's point of view.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as "and then what?" follow-ups on whatever you draw first.

Efficiency and Indexing

How do you avoid an O(n) scan of every alert rule on every price update?
Keep rules for each target_id in a sorted structure keyed by threshold, split by direction (below/above). A price update only needs a crossing-range query — the rules whose threshold lies between the old and new price — which costs O(log n) to find the boundary plus O(k) for the k rules actually crossed, not O(n) over every rule watching the target.
Why keep separate sorted structures for "below" and "above" rules instead of one?
A falling price only ever needs to probe the "below" structure for the range (new_price, old_price], and a rising price only the "above" structure for [old_price, new_price) — splitting by direction avoids touching irrelevant rules and keeps the range query's direction unambiguous.
How do percent-change or N-day-high-relative rules fit into a threshold-sorted structure if their "threshold" isn't fixed?
Recompute the rule's effective absolute threshold whenever its reference value changes (e.g. a new 30-day high is set) and re-insert it into the same sorted structure at its new position — evaluation on every subsequent tick is then an ordinary absolute-threshold check.

Hysteresis and Notification Quality

Why do you need hysteresis/debounce at all — why not just re-fire every time the price crosses back?
A price hovering right at a boundary would trigger, clear, and re-trigger repeatedly within seconds — an alert storm that spams the user and wastes evaluation and notification capacity on noise rather than a genuinely new signal.
Walk me through the state machine for a repeating alert.
ARMED (eligible to fire) → TRIGGERED (condition met, notification sent) → COOLDOWN (a fixed minimum interval where no re-fire is possible) → back to ARMED, but only once the cooldown has elapsed AND the price has crossed back past a hysteresis reset band, not the instant it re-crosses the original threshold.
What's the difference in state-machine handling between a one-shot and a repeating alert?
A one-shot alert's TRIGGERED state is terminal — the rule deactivates and is removed from the sorted structure. A repeating alert instead transitions from TRIGGERED into COOLDOWN and can return to ARMED later.

Stock-Specific and Data Quality

How do you handle a flash crash or an exchange trading halt?
Apply circuit-breaker sanity checks that reject or quarantine ticks outside a plausible bound, and respect the exchange's own trading-halt signals, so the evaluator doesn't fire a storm of alerts off momentarily bad-quality or halted-market data.
What happens if the primary market-data feed goes down?
Fail over to a secondary data provider (accepting some difference in latency/format), and mark affected tickers as degraded/stale in the interim rather than silently continuing to serve an old price as current.
How do you keep evaluation lag low when tick volume spikes 10× on earnings day?
The message queue absorbs the burst so ingestion never blocks; the Alert Evaluation Service scales horizontally per partition; and any specific ticker whose rule count has grown large is already (or gets) hot-key sub-sharded, so a volume spike on one symbol doesn't serially bottleneck its evaluation.

Reliability and Correctness

How do you guarantee you never silently miss a trigger?
The price stream is durable and replayable (Kafka retention), evaluation lag is dashboarded and alerted on, and a periodic reconciliation sweep job re-scans recent price history against active rules to catch anything the streaming path might have missed during an outage window.
How do you avoid double-notifying a user given at-least-once delivery?
Dedup on a composite key — rule_id + trigger_price + day — at the notification-dispatch step, so a Kafka redelivery or a reprocessing run is recognized as the same logical trigger event and treated as a no-op rather than resent.
What happens if the Alert Evaluation Service crashes mid-batch?
Kafka consumer offsets are committed only after a batch's evaluation and publish steps both succeed, so a restart safely re-processes the same batch — correctness relies on the idempotent-dispatch dedup key downstream, not on the consumer never re-processing anything.

Hot Keys and Scaling

What do you do when a single ticker or a viral deal item has millions of rules?
Detect the hot key once its rule count crosses a threshold and sub-shard its rule set across a dedicated pool of parallel workers; a price tick for that target is fanned out to every sub-shard worker simultaneously, and a lightweight aggregator merges the union of triggered rules.
How do you decide when to sub-shard a key and when to merge it back?
Use a rule-count threshold with its own hysteresis — e.g. sub-shard above 100K rules, merge back only below 20K — so a target hovering right around the boundary doesn't thrash between sharded and unsharded configurations.

Historical Storage

Why not store every raw tick forever?
Raw-tick storage growth is unbounded (tens of terabytes per year at this scale) and most of it is never queried again at full resolution; a background job downsamples data older than a retention window into 1-minute/1-hour/1-day OHLC bars, keeping storage bounded while still supporting long-range charting and reference-value conditions.
How does the "30-day high" check stay fast if it needs a month of history on every tick?
A Redis hot-range cache maintains the rolling reference value incrementally for popular/actively-alerted targets, so the check almost always hits the cache; only a cold or rarely-watched target falls through to the underlying time-series store.

Product and Feature Design

How would you support "notify me when this item is back in stock" using the same infrastructure?
Model it as a boolean-crossing condition type (false → true) driven off the in_stock flag carried on each e-commerce price-update event, reusing the identical target_id-keyed evaluation path and ARMED/TRIGGERED/COOLDOWN state machine already built for price thresholds — no separate pipeline required.

Key Takeaways

Remember
Two very different ingestion cadences — poll/scrape for e-commerce, continuous streaming for stocks — converge on one shared abstraction (a stream of target_id/price/timestamp updates); state that convergence explicitly, since it's what makes "one system, two variants" a real claim rather than a slide. The entire design's efficiency hinges on never scanning all of a target's rules: a sorted-threshold structure per (target_id, direction) turns evaluation into a crossing-range query, O(log n + k), and hot-key sub-sharding is the escape hatch for the handful of targets where even that isn't enough. Hysteresis/debounce (a state machine plus a reset band, not just a single boundary) is what stands between "useful alert" and "alert storm" on a flapping price. Historical storage is a time-series problem, not a relational one — partition by (target_id, time-bucket), cache the hot recent range, and downsample the rest. And because Kafka is at-least-once, idempotent dispatch (dedup by rule_id + trigger_price + day) has to live in the data model, not in broker configuration.
