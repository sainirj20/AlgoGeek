SYSTEM DESIGN

Designing a Notification Service at Scale

A complete, interview-ready design walkthrough: requirements, capacity estimation, API & event schema, data model, priority-queue architecture, rate limiting & preference gating, Kafka fan-out to pluggable channel handlers, retry/DLQ, sharding & replication, security, and follow-up interview questions.

Problem Statement

Design a notification service that lets many upstream producer services — an order-service, an OTP-service, a marketing-service, and others — say "please notify user X about event Y" without knowing or caring how the message actually reaches the user. The service must classify each request by urgency, gate it against per-user rate limits and channel/timing preferences, and fan the approved request out to one or more delivery channels — in-app, email, and SMS today, with new channels (e.g. push) pluggable in later without touching existing code. It must be multi-tenant (SaaS): many independent client companies can plug their own producer services into the same deployment. Above all, a time-critical transactional message (a login OTP) must never be delayed behind a bulk promotional blast.

Why does this problem matter in an interview?

It combines several classic sub-problems that are individually easy but jointly demanding: priority scheduling under contention, rate limiting with race-safe counters, at-least-once delivery made idempotent, a pluggable/extensible handler architecture, and multi-tenant isolation. A strong candidate treats prioritization as the load-bearing requirement — everything else (rate limiting, preferences, retries) is designed so it can never block the notify-user-of-OTP path.

Why build one shared service instead of letting each team roll its own?

  • One place to enforce the 5-notifications-per-user-per-day cap and channel/quiet-hours preferences consistently, instead of every producer team reinventing (or forgetting) it.
  • One place to add a new channel (push, WhatsApp) — every existing producer benefits without any of them redeploying.
  • One place to build retry/backoff, dead-lettering, delivery tracking, and observability, instead of duplicating that plumbing per team.
  • SaaS-ready: a single deployment can serve many client companies (tenants), each with isolated preferences, quotas, and templates.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope before drawing boxes.

  1. What channels must we support at launch, and do we need to add new ones (e.g. push) without redeploying existing channel handlers?
  2. Is this single-tenant or a true multi-tenant SaaS serving many independent client companies?
  3. Is the 5-notifications-per-user-per-day cap a blanket limit across all priority classes, or does it exempt transactional messages like OTP and order updates?
  4. Do we need templated messages with variable substitution, and scheduling a notification for future delivery?
  5. What's the acceptable latency for an OTP notification, end to end (sub-second? a couple of seconds)?
  6. Do the downstream SMS/email providers impose their own rate limits we must respect?
  7. Do we need delivery receipts and read receipts, particularly for in-app notifications?
  8. Do users need per-channel unsubscribe/opt-out, and does that override transactional sends too?
  9. What consistency do we need on the rate-limit counter under concurrent requests for the same user?
  10. Single region to start, or does the design need to anticipate multi-region from day one?
Interview tip
Don't stall waiting for every answer — state a reasonable assumption out loud ("I'll assume the 5/day cap applies to promotional and bulk traffic only, since silently dropping an OTP or order-shipped notice would be a functional bug, not just an inconvenience") and keep moving. This is exactly the kind of judgment call interviewers want to see.

Requirements and Goals

Functional Requirements

  1. Accept a notification request from a producer service and deliver it to the target user via in-app, email, and/or SMS.
  2. Classify every request into one of four priority classes — OTP (highest), Order Update, Promotion, and Bulk/Other (lowest) — and schedule delivery accordingly.
  3. Enforce a rate limit of no more than 5 notifications per user per day.
  4. Respect per-user preferences: channel preference (SMS, email, or all channels) and a time-of-day ("quiet hours") preference specifically for promotional messages.
  5. Support templated notifications with variable substitution (e.g. "Your order #{order_id} has shipped").
  6. Support scheduling a notification for future delivery (e.g. a reminder 24 hours from now).
  7. Retry failed deliveries with backoff, and guarantee idempotent delivery — a retry must never cause a duplicate send.
  8. Support per-channel unsubscribe / opt-out.
  9. Support delivery receipts and read receipts for in-app notifications.
  10. Be pluggable: new channel handlers can be added (or swapped) without touching existing handler code, and be multi-tenant: isolate configuration, quotas, and templates per client company.

Non-Functional Requirements

  1. Low latency specifically for high-priority traffic: an OTP must reach the user in near real time even while the system is absorbing a huge promotional campaign — this is the entire reason for the priority-queue design.
  2. High throughput: a single marketing campaign can fan out to tens of millions of users in a short window.
  3. Durability for transactional messages: an OTP or order-update notification must never be silently dropped, even under load or partial outage.
  4. At-least-once delivery with idempotency: Kafka and retries mean a message can be processed more than once; the system must guarantee it's never delivered to the user more than once.
  5. Eventual consistency is acceptable for low-priority/bulk traffic — a promotional message arriving a few seconds (or minutes, under extreme load) late is a non-issue.
  6. Horizontal scalability of ingestion, the priority handler, and each channel handler independently, since their load profiles differ enormously.
  7. Pluggability as a first-class architectural property, not an afterthought — adding a channel must be a purely additive change.

Extended / Out-of-Scope

We'll go deep on ingestion, prioritization, rate limiting/preferences, Kafka fan-out, channel handlers, retry/DLQ, and delivery tracking. We call out but don't build the internals of a full template-authoring UI, a campaign-management console, or an ML-based send-time optimizer — real products, but layered on top of this core.

Data Model and Database Choice

Nature of the Data

  • Hundreds of millions of small records per day (notification_log), each a simple row with no complex joins on the hot path.

  • Extremely read/write heavy on a narrow key, at huge scale — the textbook case for a wide-column NoSQL store over a relational database for the bulk data plane.

Cassandra + Redis — Why Both, Not Just One

Redis gives sub-millisecond atomic counters (INCR) and a fast preference cache — exactly what the Priority Handler needs on every single request's hot path. But Redis alone is not durable enough to be the system of record: an eviction, a restart, or a cache flush must never silently reset a user's rate-limit count or lose their preferences. Cassandra is the durable, horizontally-shardable source of truth for preferences and the full delivery log (analytics, "your notifications" history, audit); it's also write-heavy-friendly and TTL-native, which the rate-limit counters and delivery log both benefit from. The pattern is: Redis for the read/write-hot, latency-critical path; Cassandra for everything that must survive a cache failure and everything analytical.

Interview tip
If pushed on "why not just Cassandra everywhere": Cassandra can serve the counter workload, but a single atomic INCR-and-check under heavy concurrent contention is a better fit for Redis's in-memory, single-threaded-per-key execution model — it avoids the read-modify-write race a naive Cassandra counter update could hit under high QPS from the same user (e.g. a burst of retries).

High-Level Design

Producer services (order-service, OTP-service, marketing-service, and any future tenant integration) publish "notify user X of event Y" requests. A Notification Consumer classifies every incoming request into one of four priority queues. A Priority Handler drains those queues — highest priority first, with starvation-safe scheduling — and for each notification consults a rate-limiting and user-preference check backed by Cassandra + Redis. If the notification passes, the Priority Handler publishes it to Kafka, which fans out to three pluggable channel handlers (in-app, email, SMS) and to a Tracker that records delivery outcomes back into the same Cassandra + Redis store.

Figure 1. High-level architecture — four priority queues feed a Priority Handler gated on rate limiting + user preference (Cassandra + Redis), which publishes to Kafka; Kafka fans out to in-app/email/SMS handlers and a Tracker that writes delivery outcomes back into the same store.

Key Design Principles Reflected in the Diagram

  • Prioritization happens before any expensive work: classification into 4 queues is the very first thing that happens, so an OTP is already on the fast lane before rate-limiting or preference logic even runs.
  • The rate-limit/preference gate is a single choke point — every notification, regardless of priority, passes through it exactly once, which is what keeps the 5/day guarantee and preference model consistent system-wide.
  • Kafka decouples "decided to send" from "actually delivered" — channel handlers and the Tracker scale and fail independently of the ingestion/priority tier.
  • Pluggability is structural, not incidental: each channel handler is an independent consumer group off the same topic; adding push notifications means adding a new consumer group, not modifying in-app/email/SMS.

Deep Dive — Priority Queue Ingestion and Scheduling

The Notification Consumer maps every incoming event_type to a priority class via a simple, tenant-configurable lookup table (e.g. OTP_* → P1, ORDER_* → P2, PROMO_* → P3, everything else → P4), then writes the request onto that priority's queue (implemented as a dedicated Kafka topic — see "Data Partitioning and Replication" below for why topics-per-priority beats one topic with a priority field).

Why 4 Separate Queues Instead of One Queue with a Priority Field?

A single queue with an in-band priority field still forces every consumer to read messages roughly in arrival order (or requires an expensive re-sort/priority-heap on the consumer side), and a burst of low-priority traffic still occupies queue capacity, partitions, and consumer-group throughput that high-priority traffic needs. Separate queues give physical isolation: a promotional flood fills up the P3/P4 queues and their dedicated consumers, while P1 (OTP) has its own queue, its own partitions, and effectively its own throughput budget that nothing else can consume. This is the single most important architectural decision in the whole system.

Scheduling Algorithm — Weighted, Starvation-Safe Draining

A naive strict-priority scheduler (always fully drain P1, then P2, then P3, then P4) guarantees OTP never waits, but can starve P4 indefinitely during a sustained P1/P2 load. The Priority Handler instead uses weighted round-robin with aging: each scheduling round it pulls up to a weighted quota from each queue (e.g. 8:4:2:1 for P1:P2:P3:P4), so every priority class makes guaranteed forward progress every round, while P1 still gets by far the largest share. On top of that, any message that has waited longer than a bounded threshold (e.g. 30 seconds) is promoted one priority level, so a pathological, sustained P1/P2 flood can't starve P4 forever — it just guarantees an upper bound on P4 latency instead of true starvation.

Figure 2. Weighted round-robin priority scheduling: each round pulls a weighted share (8:4:2:1) from each queue so P1 dominates without starving P2–P4; aging escalates a message that has waited too long.

Deep Dive — Rate Limiting and User Preference Gate

Every notification that survives the priority queues passes through exactly one gate before it's allowed to reach Kafka: rate limiting, then preference checks.

Rate Limiting — Fixed Window Counter in Redis

We use a fixed window counter keyed by rl:{tenant_id}:{user_id}:{yyyy-mm-dd} (the user's local calendar day, not UTC — see the "quiet hours" discussion below for why timezone matters here too). Redis's INCR is atomic, so two concurrent requests for the same user can never both read-then-write a stale count — the increment itself is the check-and-increment, eliminating the classic read-modify-write race. The key carries a 24–48 hour TTL so it self-expires without any cleanup job. A sliding-window log or sliding-window counter would be smoother at the boundary (no "reset cliff" at midnight) but costs more memory and complexity per user; for a simple daily cap like 5/day, a fixed window is the pragmatic, defensible choice — call this trade-off out explicitly if asked.

Scope of the cap: we exempt P1 (OTP) entirely from the 5/day cap — an OTP is a security-critical, user-initiated action, not spam, and must never be silently dropped by a counter. P2 (order updates) is tracked in a separate, generous counter mostly as an abuse backstop. The 5/day figure is really aimed at P3/P4 (promotional and bulk) traffic; state this scoping decision explicitly, since a literal reading of "5 notifications per user per day" would otherwise block a legitimate 2FA code on a busy shopping day.

User Preference Check

After the rate-limit check passes, the Priority Handler reads the cached preference record (Redis, backed by Cassandra) for the user: channel opt-in flags (SMS/email/in-app/all) and, for P3 (promotional) traffic specifically, a quiet-hours window in the user's own timezone. If the current local time falls inside quiet hours, a promotional notification is deferred (re-enqueued with a computed schedule_at at the end of quiet hours) rather than dropped. Quiet hours are intentionally scoped to promotional traffic only — an OTP or order update is never held back for "quiet hours," since deferring a security code defeats its purpose.

Figure 3. Rate-limiting mechanism: an atomic Redis INCR against a per-user, per-day key (TTL 24h) decides pass/fail in one round trip, with an async write-behind to Cassandra for durable audit; P1/OTP bypasses this cap entirely.

Deep Dive — Kafka Fan-Out and Pluggable Channel Handlers

Once a notification clears the gate, the Priority Handler publishes it to a single notifications.approved Kafka topic, partitioned by user_id so all of one user's messages stay in relative order. Each channel handler runs as its own Kafka consumer group reading the same topic independently — this is what makes the "pluggable" requirement real rather than aspirational.

Adding a New Channel Without Redeploying Existing Handlers

To add push notifications: stand up a new push-Handler service, register it as a new consumer group on the existing notifications.approved topic, and add a routing rule so channel_hint/preferences can select it. The in-app, email, and SMS handlers never see a code change, a redeploy, or even a config reload — they're reading the same topic through their own, unrelated consumer-group offsets. This is the direct payoff of "channel handler = independent consumer group," not a special extension mechanism bolted on afterward.

Template Rendering

Each handler fetches the template by (tenant_id, template_id, locale), validates that every variable used in the request matches the template's declared variables_schema, and performs simple {{variable}} substitution — deliberately not a general-purpose templating/scripting language, to close off injection risk (see "Security" below). Rendered output is channel-specific: SMS truncates/segments for length, email renders an HTML + plain-text pair, in-app produces a structured payload (title, body, deep link, icon) for the inbox/feed UI.

Deep Dive — Retry, Backoff, and Dead-Letter Queue

Every channel handler call to an external provider (or internal in-app write) can fail transiently. Failures are retried with exponential backoff (e.g. 1s → 2s → 4s → 8s → 16s, capped at 5 attempts). If retries are exhausted, a circuit breaker opens for that provider and traffic fails over to a configured backup vendor (e.g. a secondary SMS aggregator); only if the backup also fails does the notification land in a Dead-Letter Queue (DLQ) for alerting and possible manual/scheduled reprocessing.

Figure 4. Retry / DLQ flow for a failing channel provider: exponential backoff, then circuit-breaker failover to a backup vendor, then a Dead Letter Queue with alerting and idempotent replay.

Deep Dive — Delivery Tracking, Idempotency, and the Send Sequence

Kafka's at-least-once semantics mean the same message can be delivered to a channel handler more than once (consumer restart, rebalance, retry). The system is made idempotent at the storage layer, not by trying to make Kafka exactly-once: notification_log has a unique constraint on idempotency_key, and a channel handler performs a conditional "claim" write (insert-if-absent) before calling the provider. If the claim fails because the row already exists and is already SENT/DELIVERED, the handler treats the message as a no-op duplicate and acknowledges it without calling the provider again. This — not Kafka configuration — is what actually prevents a double SMS from a redelivered message.

The Tracker consumes the same notifications.approved topic (its own consumer group) purely to observe outcomes: it correlates provider webhooks/callbacks (delivery receipts) and in-app read events back to the notification_id, and writes the final status into Cassandra + Redis. In-app read receipts arrive as a small event from the client ("user opened notification N") that the Tracker folds into the same status field.

Figure 5. The end-to-end send sequence — classification and the rate-limit/preference gate (steps 2–5) are the only strictly-ordered, synchronous-feeling steps; everything from step 6 onward is async and independently scalable.

Data Partitioning and Replication

Sharding decisions follow the same principle throughout: keep everything for one user together for correctness (ordering, rate-limit atomicity), and keep priority classes physically separated for isolation.

  • Rate-limit counters and preferences are sharded by user_id (consistent hashing in both Redis Cluster and Cassandra) so every check for a given user always lands on the same shard/replica set — no cross-shard coordination needed for a single user's counter.
  • Ingestion topics are one Kafka topic per priority class (notifications.otp, notifications.order_update, notifications.promotion, notifications.bulk), each with its own partitions and consumer lag. This is why a promotional flood can never delay an OTP: the OTP consumer only ever reads notifications.otp, whose partitions and throughput are completely untouched by whatever is happening in notifications.bulk.
  • The post-gate fan-out topic (notifications.approved) is partitioned by user_id instead, so all of one user's approved notifications preserve relative order across channels, while each channel handler's consumer group independently reads every partition.

Rate Limiting and Abuse Prevention

Beyond the per-user 5/day cap, the system needs tenant-level and producer-level abuse controls, since this is a shared, multi-tenant service.

  • Per-tenant ingestion quota enforced at the API gateway (token-bucket per tenant_id), so one client company's misbehaving or compromised producer service can't starve every other tenant's ingestion capacity.
  • Per-producer-service authentication (API key or mTLS) so requests are always attributable, and a specific misbehaving integration can be throttled or disabled without affecting the rest of its tenant.
  • Burst shedding under extreme load: if ingestion capacity is genuinely exceeded, shed P4 first, then P3, protecting P1/P2 — the priority queues make this a natural, already-built-in policy rather than a special case.
  • 429-equivalent responses with backpressure: a tenant exceeding quota gets a fast, clear rejection at the edge rather than an accepted-then-silently-dropped request.

Security, Privacy and Multi-Tenant Isolation

  • No PII in logs: application/operational logs reference user_id and notification_id only; phone numbers, email addresses, and rendered message bodies are never written to general-purpose logs — only to the access-controlled notification_log store, and even there, contact details are masked/tokenized where the log's purpose doesn't require them in the clear.
  • Template injection prevention: templates support only declared, schema-validated {{variable}} substitution — never string concatenation into a script/expression engine. Rendered output is HTML/attribute-escaped for email and in-app to prevent stored XSS, and template IDs are scoped per tenant so one tenant can never reference (or overwrite) another tenant's template.
  • Multi-tenant isolation: every table is keyed by tenant_id as the leading partition key element, so a query or a bug can't cross tenant boundaries by construction; rate limits, quiet hours, and quotas are configured per tenant.
  • Transport security: TLS everywhere; mTLS between producer services and the ingestion API; provider (SMS/email vendor) credentials stored in a secrets manager, rotated regularly, and never logged.
  • Abuse of the notification channel itself: the rate limiter is also the primary defense against using the service to spam a user (e.g. a compromised producer trying to harass a target user with repeated messages) — this is a security property of the rate-limit gate, not just a UX one.

Load Balancing

Load balancing shows up at several independent layers:

  1. Between producer services and the ingestion API (standard L7 load balancer, health-checked).
  2. Across Kafka partitions/consumer-group members for the Priority Handler and each channel handler — Kafka's own consumer-group rebalancing handles this natively as instances scale up/down.
  3. Across a pool of SMS numbers / email sending domains, so no single provider account absorbs more than its rate limit while others sit idle.

Start with round-robin at the API tier; for the provider pools specifically, use a rate-aware balancer that actively tracks each account's remaining quota rather than blind round-robin, since provider throttling is the real bottleneck (see capacity estimation above).

Scaling to Multiple Regions

  • Run each region active-active, and co-locate the Notification Consumer + Priority Handler with the region the requesting producer/user is closest to — OTP latency is the metric this design cares most about, and network round-trips to a distant region are exactly the kind of tax that requirement can't absorb.
  • Cassandra multi-DC replication keeps preferences and rate-limit backstops available locally in each region; use LOCAL_QUORUM for low-latency reads/writes within a region, with cross-region replication happening asynchronously.
  • Rate-limit counters need a explicit choice: either pin each user to a "home" region for their counter (simplest, avoids cross-region coordination, at the cost of a slower failover path if that region is down), or accept eventually-consistent global counters (simpler failover, but a user could theoretically exceed 5/day by a small margin if requests land in two regions in the same window). For most products, home-region pinning is the pragmatic default.
  • Kafka runs as regional clusters with MirrorMaker (or an equivalent) replicating the approved-notifications stream cross-region only where a channel handler must run centrally (e.g. a single SMS provider relationship) — not on the OTP-latency-critical path.

CAP Theorem Lens

Favor availability (AP) for preference reads and the delivery log — a slightly stale preference or a delayed analytics write is far better than blocking a send. Favor consistency for the rate-limit counter specifically — a single atomic INCR per key gives us strong, race-free consistency exactly where it matters (never letting a user silently exceed the cap due to a race), without paying a distributed-consensus cost across the whole system.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as "and then what?" follow-ups on whatever you draw first.

Prioritization and Scheduling

Why 4 separate priority queues instead of one queue with a priority field?
A shared queue still lets low-priority volume consume shared partitions/consumer throughput and forces either in-order processing or an expensive re-sort. Separate topics give physical isolation: a promotional flood can only ever back up its own topic and consumers, never touch OTP's dedicated capacity.
How do you prevent low-priority notifications from starving forever?
Weighted round-robin guarantees every priority a bounded share every scheduling round (not zero), and an aging rule promotes any message that's waited past a threshold (e.g. 30s) up one priority level, giving a hard upper bound on worst-case wait instead of indefinite starvation.
How do you test that OTP still arrives fast during a huge promotional campaign?
Load-test by injecting a synthetic P4 flood at several multiples of peak while continuously measuring P1 end-to-end latency (p50/p99) from a separate control-plane probe; alert if P1 p99 degrades at all, since a well-isolated design should show flat OTP latency regardless of P3/P4 volume.

Rate Limiting and Preferences

How does the rate limiter avoid a race condition across concurrent requests for the same user?
Redis's INCR is atomic and single-threaded per key — there's no separate read-then-write step for a caller to race against. Two concurrent requests both get a correct, distinct post-increment value; whichever pushes the count past 5 is the one rejected.
Why Cassandra + Redis together instead of just one?
Redis gives the sub-millisecond atomic counters and cache hits the hot path needs; Cassandra is the durable, horizontally-shardable system of record so a Redis eviction/restart never silently loses preferences or resets a rate-limit count, and so analytics/history queries have somewhere durable to run against.
Does the 5/day rate limit apply to OTP too?
No — OTP is a security-critical, user-initiated action, not spam, and is exempt from the cap by design (a separate, generous safety backstop can still exist to catch genuine abuse). The cap is really aimed at promotional/bulk traffic; state this scoping decision explicitly rather than applying it uniformly.
How do you handle a user's timezone for quiet hours?
Store an IANA timezone (e.g. America/Los_Angeles) alongside the quiet-hours start/end on the preference record, and evaluate "is it currently quiet hours" in that timezone at send time, not in UTC or the server's local time — and re-enqueue with a computed schedule_at for the end of quiet hours rather than dropping the message.

Delivery, Idempotency and Reliability

How do you make delivery idempotent given Kafka's at-least-once semantics?
A unique constraint on idempotency_key in notification_log plus a conditional "claim" insert before calling the provider. A redelivered message fails the claim (row already SENT/DELIVERED) and is acknowledged as a no-op rather than resent — the guarantee lives in the datastore, not in Kafka configuration.
What happens if the SMS provider is down?
Exponential backoff retries, then a circuit breaker opens and traffic fails over to a backup SMS vendor; if the backup also fails, the message lands in a Dead Letter Queue with alerting and idempotent scheduled replay — it's never silently dropped.
How would you add a new channel (push notifications) without redeploying existing handlers?
Stand up a push-Handler as a new, independent Kafka consumer group on the same notifications.approved topic, and add a routing/preference rule for it. Existing in-app/email/SMS handlers read the same topic through unrelated consumer-group offsets and need zero code change or redeploy.
How do delivery receipts and read receipts work for in-app notifications?
Delivery receipt = the in-app Handler's successful write to the user's inbox/feed store, which the Tracker records as DELIVERED. Read receipt = a small client-emitted event ("user opened notification N") that the Tracker folds into the same notification_log row as a READ status/timestamp.
What's the replay strategy for messages sitting in the Dead Letter Queue?
A scheduled reprocessing job re-publishes DLQ entries (reusing the same idempotency_key, so it's safe even if the original attempt partially succeeded) once the provider/circuit breaker has recovered, with a cap on total replay attempts before requiring manual review.

Multi-Tenancy and Product

How do you isolate different client companies (tenants) using the same service?
tenant_id is the leading partition-key element on every table (preferences, rate limits, delivery log, templates), so a query or bug can't cross tenant boundaries by construction. Quotas, rate-limit configs, and templates are all scoped per tenant, and per-tenant API credentials attribute every request.
How would you support a tenant-specific rate limit or priority mapping instead of one global policy?
Store the priority-classification rules and the per-day cap as tenant-scoped configuration (loaded/cached by the Notification Consumer and Priority Handler), rather than hardcoding "OTP = P1" globally — the event_type-to-priority table and the numeric cap both become per-tenant lookups.
A noisy tenant is sending an enormous campaign — how do you stop it from degrading service for every other tenant?
Per-tenant quota enforced at the API gateway, independent of the global priority-queue budget; combined with the fact that a legitimate huge campaign should already be classified P3/P4 and thus isolated from every other tenant's P1/P2 traffic by the topic-per-priority design.

Scaling and Operations

How do you scale Kafka partitions as the user base grows 10×?
Increase partition count on the approved-fan-out topic (partitioned by user_id, so this redistributes cleanly with a standard partition-reassignment tool) and scale each channel handler's consumer group up to match; the priority-topic side scales similarly, independently per priority class based on its own volume growth.
How would you detect and alert on an OTP p99 latency regression before customers complain?
Emit end-to-end latency (classification → gate → Kafka publish → handler ack) tagged by priority class, dashboard P1 p99 specifically, and alert on any sustained increase — since a healthy design should show P1 latency essentially flat regardless of P3/P4 load, any drift is a strong signal of a scheduling or gate regression.
How do you prevent template injection attacks?
Templates only support declared, schema-validated {{variable}} substitution — never string concatenation into a script/expression engine — and rendered output is escaped per channel (HTML-escaped for email/in-app) to block stored XSS; template IDs are tenant-scoped so one tenant can't reference or overwrite another's template.

Key Takeaways

Remember
Prioritization is the design's spine, not a feature bolted on afterward: four physically-separated priority queues, weighted scheduling with aging, and a single rate-limit/preference gate are what guarantee an OTP is never delayed behind a bulk campaign — state that causal chain explicitly. Rate limiting must be atomic (Redis INCR) to be race-free, and durable (Cassandra) to survive a cache failure; know why you need both, not just one. Kafka's at-least-once delivery means idempotency has to live in your data model (a unique idempotency_key and a conditional claim write), not in broker configuration. Pluggability is proven by consumer-group independence, not by promises — a new channel handler should require zero changes to existing ones. And because this is a shared, multi-tenant service, tenant_id needs to be the leading key on every table from day one, not retrofitted later.
