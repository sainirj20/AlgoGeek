SYSTEM DESIGN

Photo Sharing Platform (Flickr / Google Photos)

A complete, interview-ready design walkthrough: requirements, capacity estimation, chunked/resumable upload & API design, the blob-store-plus-metadata data model, an asynchronous processing pipeline for thumbnails/transcoding/ML inference, content-hash and perceptual-hash deduplication, face clustering, storage tiering for cost efficiency, sharding & replication, security/privacy, and follow-up interview questions.

Problem Statement

Design a photo and video sharing platform that lets hundreds of millions of users upload media from their phone or desktop, stores it durably (effectively forever), organizes it into albums, lets users share a single photo or an entire album with fine-grained visibility — private, public, or link-based — and makes an enormous personal (and, for public content, global) library searchable by date, location, the people in the photo, or the objects and scenes it contains, without the user ever manually tagging anything. The platform should also proactively resurface the past: an "On this day" reminder, an auto-generated trip or event album, a highlight reel — all computed by machine learning over the user's own library. It must do all of this at a scale of billions of photos and videos and hundreds of petabytes moving toward exabytes of storage, while treating data loss as essentially unacceptable.

This brief deliberately spans two real products with different centers of gravity: Flickr, built around public sharing, community, and photographer-oriented features (RAW support, licensing, groups); and Google Photos, built around personal backup-first storage and a "media intelligence platform" that understands the content of every photo well enough to search it, curate it, and act on it without the user doing any organizing work themselves. A strong design supports both postures with the same core architecture, differing mainly in default visibility and how aggressively ML features are surfaced.

Why does this problem matter in an interview?

It forces you to reconcile several things that pull in different directions: photo/video bytes are large, immutable, and cheap to store per-byte at scale, but the metadata about them is small, highly mutable, and needs strong consistency for things like album membership and sharing permissions. Processing every upload with ML (face/object detection, transcoding) is expensive and slow, yet the user expects the app to say "uploaded" almost instantly. Two photos can be exact-duplicate bytes (worth deduplicating hard) or near-duplicate burst shots (visually similar, but not byte-identical, and shouldn't be silently merged). A good candidate treats "never put image bytes in the relational database" and "upload confirmation is decoupled from the real, asynchronous processing" as the two load-bearing architectural decisions, and builds everything else — dedup, search, Memories, tiering — on top of that split.

Why build one shared platform instead of point solutions per feature?

  • One place to enforce the visibility/permission model consistently — a private photo must be private everywhere: in search results, in Memories, in the API, in a face cluster suggestion — not just hidden in one UI surface.
  • One ingestion and processing pipeline reused across every source — mobile auto-backup, web upload, desktop sync client, API partners — so thumbnailing, transcoding, dedup, and ML tagging behave identically regardless of how a photo arrived.
  • One place to realize deduplication savings and storage-tiering savings across the entire corpus, instead of every client or feature team reinventing its own (worse) version.
  • One place to build durability, replication, and disaster recovery once, to a very high bar, rather than per-feature teams re-deriving "how many nines do we need" independently.

Clarifying Questions to Ask the Interviewer

Spend the first few minutes narrowing scope — this problem has more legitimate "it depends" branches than most.

  1. Is this closer to Flickr's public-sharing/community model, or Google Photos' personal-backup-first model? That single answer changes default visibility, the importance of a public search/discovery surface, and how central ML features are to the core experience.
  2. Do we need to support video, not just photos? If so, what's the maximum length/resolution, and do we need adaptive-bitrate streaming for playback?
  3. Are face recognition/clustering and object/scene tagging in scope for this session, or should I treat them as a deep dive I flag but don't fully design?
  4. Is mobile auto-backup (silent background upload of the camera roll) a requirement, including behavior on cellular vs. Wi-Fi-only, and battery/network-aware throttling?
  5. Is there a storage budget or tiered quota model (e.g. a free tier with a cap, a paid tier with more/unlimited storage), and does that change our tiering strategy?
  6. Do we need to support original-quality, uncompressed storage of every byte forever, or is a "storage saver" (server-side re-encoded, slightly compressed) tier acceptable as a user-selectable option?
  7. Do we need RAW file support for professional photographers (large, uncompressed camera-sensor files), and does that imply a different processing path than a phone JPEG/HEIC?
  8. What's the deletion model — is there a trash/recycle-bin window (e.g. 30 days) before permanent, unrecoverable deletion, and do backups/replicas need to honor that same window?
  9. Do users need collaborative/shared albums where multiple people can contribute photos, or is sharing strictly "owner shares read-only access"?
  10. Single region to start, or should the design anticipate multi-region and data-residency constraints (e.g. EU biometric/face data staying in-region) from day one?
Interview tip
Don't wait for every answer before drawing anything. State a reasonable default out loud — "I'll design this as personal-backup-first like Google Photos, with private-by-default visibility, and treat public Flickr-style community/discovery features as an additive layer on the same sharing primitives" — and keep moving. Naming the assumption and its consequence is exactly the signal interviewers are listening for.

Requirements and Goals

Functional Requirements

  1. Upload, store, and serve photos and videos from mobile, web, and desktop clients, including large RAW and video files.
  2. Organize media into albums; support adding a photo to multiple albums without duplicating the underlying bytes.
  3. Share a single photo or an entire album with fine-grained visibility: private (owner only), public (anyone, discoverable/searchable), or link-based (anyone with the link, not otherwise discoverable).
  4. Search the user's library (and, for public content, the global corpus) by date taken, location, the people recognized in the photo, and objects/scenes detected in the photo (e.g. "beach", "dog", "birthday cake").
  5. Support silent, automatic mobile backup of the device's camera roll, resumable across app restarts and network drops.
  6. Deduplicate exact-byte-identical uploads (e.g. the same photo re-imported from two devices, or a screenshot forwarded and re-saved) so it is stored once, not once per upload.
  7. Proactively surface ML-curated "Memories" — on-this-day reminders, auto-generated trip/event albums, highlight reels — without any manual curation from the user.
  8. Support face clustering (grouping photos of the same person together) as an explicit, opt-in feature, and let the user label a cluster with a name to make it searchable.
  9. Support a trash/recycle-bin window before permanent deletion, and a full-library export for data portability.
  10. Support collaborative/shared albums where invited contributors can add their own photos alongside the owner's.

Non-Functional Requirements

  1. Durability approaching 11 nines (99.999999999%) for stored originals — losing a user's only copy of an irreplaceable photo is treated as one of the worst possible failure modes of this system, not an ordinary bug.
  2. High availability (≥99.9%) for both the upload path and the read/serving path, since both backup (write) and browsing/sharing (read) are core, always-on use cases.
  3. Low-latency serving via a CDN — opening the app or a shared album should render thumbnails in well under a second, regardless of where in the world the viewer is.
  4. Support for very large individual files — multi-hundred-megabyte RAW photos and multi-gigabyte videos — without the upload path assuming "a photo is a few megabytes."
  5. Massive scale: the design must reason in the range of billions of photos/videos and hundreds of petabytes moving toward exabytes of storage, not millions of rows and terabytes.
  6. Cost-efficient storage: most bytes, once uploaded, are viewed a handful of times and then almost never again — the design must exploit that access pattern aggressively via tiering rather than treating every byte as equally "hot" forever.
  7. Strong consistency for ownership/permission-relevant metadata writes (a photo's owner, an album's membership, a share's visibility) — the user who just added a photo to a private album must see it there immediately, and a permission change must take effect everywhere at once, not eventually.
  8. Eventual consistency is acceptable for ML/social features — a face cluster taking a few minutes to pick up a brand-new photo, or a Memories feed lagging behind the very latest upload by an hour, is a non-issue.
  9. Horizontal scalability of upload ingestion, each stage of the async processing pipeline, and search/serving independently, since their load profiles and growth rates differ enormously.

Extended / Out-of-Scope

We'll go deep on chunked/resumable upload, content-hash and perceptual-hash deduplication, the asynchronous processing pipeline (thumbnails, transcoding, ML inference), face clustering, storage tiering, data modeling, and partitioning/replication. We call out but don't build the internals of a full photo-editing suite, the ranking model that scores candidate Memories (we describe its inputs, not its training), or a subscription-billing engine for storage quotas — real product surfaces, but layered on top of this core.

Capacity Estimation and Constraints

State assumptions explicitly and let them drive every downstream decision — this problem's numbers span many orders of magnitude, so the estimation itself is a large part of demonstrating seniority.

Total uploads/month ≈ 500,000,000 × 20 = 10 billion photos/month
Uploads/day ≈ 10,000,000,000 ÷ 30 ≈ 333 million/day

Holiday/New Year's-style spikes can run 5–10× steady-state peak for a few hours; design ingestion headroom for ≥30,000/sec short bursts, not just the 15,000/sec steady peak

Storage Growth

Raw ingest Daily raw photo bytes ≈ 333,000,000 × 3 MB ≈ 1,000,000 GB = 1,000 TB ≈ 1 PB/day (photos alone)
Annual raw ingest ≈ 1 PB × 365 ≈ 365 PB/year, before video and before any storage-overhead factor
With erasure coding for durability (≈1.4× overhead, vs. ≈3× for full triplication — see "Storage Tiering" below) ≈ ≈511 PB/year of actual stored bytes just from new photo ingest
Add the ≈1.33 PB/day video stream (×365 × 1.4 ≈ ≈680 PB/year at RF-equivalent) and total new stored bytes/year lands in the ≈1.2 exabyte/year range — and this compounds year over year as the user base and per-user library both grow
Derived-asset ("thumbnail fan-out") multiplier Each original photo generates ≈5–6 derived variants: a ≈150px thumbnail (≈8 KB), a ≈320px small (≈25 KB), an ≈800px medium (≈120 KB), a ≈1600px large (≈350 KB), and a modern re-encode (WebP/AVIF, ≈250 KB) for bandwidth-efficient serving
Combined derived bytes per original ≈ 750 KB — roughly 25% of a 3 MB original, i.e. derived assets add ≈20–25% on top of original-photo storage, not a multiple of it
But the object count the pipeline must create, store, and serve is ≈6× the original count — the processing pipeline and metadata store must be sized for object-count fan-out even though the byte-count overhead is modest
Video adds more: adaptive-bitrate renditions (240p/480p/720p/1080p) plus HLS/DASH segment manifests typically add ≈1.5–3× the original video's bytes across all renditions combined

Read Traffic Is Heavily Skewed Toward Reads

Read:write ratio Assume each of the 500M MAU views ≈40 photos/day on average across their own library, shared albums, and the Memories feed
Total views/day ≈ 500,000,000 × 40 = 20 billion views/day, vs. ≈333 million uploads/day
Blended read:write ratio ≈ 60:1 — and a single viral shared album can push the ratio for that one album's storage key into the thousands-to-one range for a few hours
Design conclusion: the serving path (CDN + thumbnail cache) is the dominant traffic driver, not the upload path — optimize read latency and cache hit ratio first

Metadata and Face-Index Sizing

Photo metadata corpus Assume the average user accumulates ≈3,000 photos over a multi-year account lifetime → total corpus ≈ 500,000,000 × 3,000 ≈ 1.5 trillion photo metadata rows (this is the same order of magnitude Google has publicly cited for Google Photos' real corpus size)
At ≈500 bytes/row (photo_id, owner_id, storage_key, content_hash, taken_at, uploaded_at, lat/lng, exif pointer, dimensions) ≈ 750 TB raw metadata
×3 replication ≈ 2.25 PB — large, but tractable for a horizontally sharded store, in sharp contrast to the multi-exabyte blob tier
Face embeddings Assume ≈50% of photos contain at least one face, averaging ≈1.3 faces per such photo → ≈1.5T × 0.5 × 1.3 ≈ ≈975 billion face embeddings at full corpus scale
A raw 512-dimension float32 embedding is ≈2 KB → naively ≈1.95 exabytes just for embeddings — clearly untenable
Quantizing to int8 (≈512 bytes) or product-quantizing to ≈64–128 bytes cuts this by 4–16×, landing in the ≈60–250 PB range — still large, which is exactly why face search is built as per-user nearest-neighbor indexes (see the face-clustering deep dive) rather than one global index

System / API Design

Clients talk to the platform through a small set of versioned APIs: a chunked, resumable upload flow; album and sharing management; and search. Every field needed for dedup, ownership, and rendering travels with the request so downstream stages never need an extra round trip just to know what they're looking at.

Interview tip
Call out client_content_hash explicitly as an optimization, not a requirement: if the client can cheaply hash the file before sending a single byte, and the server already has that hash, the upload can be skipped entirely — saving bandwidth on the client's most constrained resource (mobile data) as well as server ingest capacity. Make clear the server still verifies/recomputes the hash server-side once bytes do arrive, so a malicious or buggy client can never claim a false dedup hit.

Data Model and Database Choice

Nature of the Data

  • Two fundamentally different kinds of data live in this system, and conflating them is the single most common design mistake: large, immutable binary bytes (the photo/video itself and its derived variants) and small, highly mutable structured metadata (who owns it, what album it's in, who it's shared with, what's in it).
  • The metadata is a textbook relational/structured workload: strong consistency matters (album membership, ownership, permissions), records are small (a few hundred bytes), and there are meaningful relationships (a photo belongs to a user, can belong to many albums, can have many shares and many detected faces).
  • The bytes are the textbook object-storage workload: write-once/read-many, no need for in-place mutation, and enormous in aggregate volume relative to record count.

Never Put Image Bytes in the Relational Database

Photo and video bytes go into a distributed, erasure-coded blob/object store (an S3- or GFS-style system) — never into the metadata database as a BLOB column. The metadata database stores only a storage_key pointer and the descriptive fields around it (owner, timestamps, location, EXIF, content hash). This keeps the metadata store small enough to serve low-latency, highly consistent reads and writes, while the blob store — purpose-built for exactly this access pattern — handles the actual bytes at petabyte-to-exabyte scale with its own replication/erasure-coding, tiering, and CDN-origin behavior.

Historical grounding: Flickr's classic architecture
Flickr's original production architecture is a clean, real-world instance of exactly this split, and worth citing directly in an interview. ServerIron load balancers fronted a tier of PHP application servers; Squid caching servers sat in front of NetApp filers, which is where the actual photo bytes lived. The application servers talked to storage through a "storage manager" abstraction layer rather than touching filers directly, so the storage backend could evolve independently of application code. Metadata lived in master-master MySQL shards, with a separate, small "shard lookup" database telling the app which shard a given user's data lived on — and a Memcached cluster absorbed the read-heavy metadata load. The guiding principle, in Flickr engineers' own words, was "share nothing": nothing except the photo bytes themselves lives outside the database — every other piece of state about a photo is a database row. That's the same core split this design uses, just with newer building blocks (an object store instead of NetApp filers, a modern message queue instead of ad hoc PHP job dispatch).

Choosing the Metadata Store

The strongly-consistent, relationship-heavy core — users, photos, albums, album membership, shares — is sharded by user_id (see "Data Partitioning and Replication" below) across a relational engine (sharded PostgreSQL/MySQL, or a distributed SQL system like Spanner/CockroachDB if cross-shard transactions are needed for shared albums). This gives us real transactions for "add this photo to this album" and immediate-read-your-own-write consistency for the owner. Search-adjacent, eventually-consistent data — face embeddings, object/scene tags, the search index itself — lives in a separate system (a vector/ANN index plus a text/attribute search engine like Elasticsearch) that's allowed to lag the metadata store by seconds to minutes without violating any correctness requirement.

High-Level Design

A client (mobile auto-backup, web upload, or desktop sync) sends a photo through the chunked Upload Service. Once all chunks land, the service computes/verifies a content hash and checks it against a dedup index. A genuinely new photo is committed to blob storage; the metadata database gets a new row immediately, and the client receives an upload confirmation right then — before any of the expensive processing below has even started. The Upload Service publishes a "photo_uploaded" event to a queue, which fans out to independent worker pools: thumbnail generation, video transcoding, and ML inference (face/object detection). Each worker pool writes its output back into the metadata database and the search index. Reads — browsing a library, opening a shared album — are served through a CDN sitting in front of the blob store, so the vast majority of traffic never even reaches origin.

Figure 1. High-level architecture — upload confirmation happens as soon as bytes land and a metadata row is committed; thumbnailing, transcoding, and ML inference all run asynchronously afterward via independent consumer groups off the same event.

Key Design Principles Reflected in the Diagram

  • Perceived latency is decoupled from real processing: the client gets "uploaded" the moment bytes are durably stored and a metadata row exists — not after thumbnails, transcodes, and ML tags are ready. This is the single most important UX-facing architectural decision.
  • The dedup check happens before any bytes are durably committed as a "new" object — a hit means we skip storage and processing entirely and just add a reference, which is where most of the cost savings in this design come from.
  • The queue decouples "stored" from "understood": thumbnail, transcode, and ML workers scale and fail completely independently of the upload path and of each other.
  • Reads never touch the write path: the CDN in front of blob storage absorbs the ~60:1 read-skewed traffic without involving the Upload Service, the queue, or the metadata database's write capacity at all.

Deep Dive — Resumable Chunked Upload and Content-Hash Deduplication

Mobile networks drop; app processes get killed mid-upload; a multi-gigabyte video simply takes a long time. The upload protocol has to assume interruption is normal, not exceptional — the same problem the open tus.io resumable-upload protocol solves, and a reasonable design to reference by name in an interview.

Chunked, Resumable Upload Sequence

  1. Client calls POST /v1/uploads/init with file metadata (size, content type, optionally a client-computed hash). Server allocates an upload_id and a chunk size (e.g. 8 MB).
  2. Client uploads chunks in sequence via PUT /v1/uploads/{upload_id}/chunks/{chunk_index}; each chunk is durably persisted (to a staging area in blob storage) and acknowledged before the client advances.
  3. On any interruption (app kill, network loss, backgrounding), the client later calls GET /v1/uploads/{upload_id}/status to learn exactly which chunks the server already has, and resumes from the first missing chunk — it never re-sends bytes the server already durably holds.
  4. Once every chunk is present, the client calls POST /v1/uploads/{upload_id}/complete. The server reconstitutes the full object, computes a cryptographic content hash (SHA-256) over the final bytes, and only now performs the dedup check and object finalization.

Content-Hash Deduplication

The server maintains a dedup index mapping content_hash → storage_key, scoped primarily per-user (so a user re-importing the same photo from two devices, or a screenshot they forwarded and re-saved, is deduplicated within their own library) and optionally consulted platform-wide purely for storage efficiency — never for content matching or cross-user visibility. A platform-wide hit only ever causes the new metadata row to reference the same underlying, reference-counted blob; it never grants the new uploader any visibility into who else has that hash, and the dedup index itself stores no information beyond the hash and a reference count. If a client pre-computed and sent client_content_hash at /uploads/init, a server-side hit there can skip the chunk-upload phase entirely — the biggest possible bandwidth win, since no bytes cross the network at all — but the server still recomputes the hash from whatever bytes do arrive before ever trusting a claimed dedup match, so a buggy or malicious client can't spoof a hit.

On a miss, the object is committed to blob storage under a fresh storage_key, the content hash is inserted into the dedup index with reference count 1, and a new photos row is written pointing at it. On a hit, no bytes are written to blob storage at all — the existing object's reference count is incremented and a new, independent photos row is written pointing at the same storage_key (each user's row carries its own ownership, album membership, and permissions, entirely independent of any other row that happens to reference the same bytes).

Deep Dive — Asynchronous Processing Pipeline

Once an upload is confirmed, the real work — making the photo browsable, playable, and searchable — happens off the critical path. The photo_uploaded event fans out to three independently scaling worker pools, each its own consumer group reading the same event stream.

Thumbnail Generation

Generates the ≈5–6 derived size/format variants described in the capacity estimation (thumbnail, small, medium, large, modern-format re-encode). These are generated eagerly, right after upload, rather than on first view, because browsing a library is the platform's single most frequent operation — paying the generation cost once at upload time is far cheaper in aggregate than paying an on-demand generation cost (and its latency) on every first view, especially given the ≈60:1 read:write ratio.

Video Transcoding

Produces adaptive-bitrate renditions (240p/480p/720p/1080p, plus a poster-frame thumbnail) and packages them for HLS/DASH streaming playback. This is the most compute-intensive stage per object and typically the pipeline's bottleneck under video-heavy load — its worker pool is scaled and provisioned (including GPU/hardware-encoder instances) independently of the much cheaper thumbnail and ML stages.

ML Inference

Runs face detection (bounding boxes + embeddings, feeding the face-clustering deep dive below), object/scene classification (feeding text search — "beach", "dog", "birthday cake"), and optionally on-image text extraction (OCR, for photos of documents/signs/whiteboards). Results are written to the metadata database (as tags) and to the search index; none of this blocks the upload confirmation or even the thumbnail/transcode stages — a photo is fully browsable before it's fully searchable, and that gap (seconds to low minutes under normal load) is an explicitly accepted eventual-consistency trade-off.

Deep Dive — Face Clustering and Searchability

Face clustering is what makes "show me photos of Mom" possible without the user ever tagging a single photo — and it's also the deep dive with the sharpest privacy constraints, since face data is biometric data under regulations like GDPR (EU) and BIPA (Illinois).

Pipeline: Detect → Embed → Cluster → Label

  1. The ML Inference worker runs a face-detection model over each photo, producing a bounding box per detected face.
  2. For each detected face, a separate embedding model produces a fixed-length vector (e.g. 512 dimensions) such that embeddings of the same person's face, across different photos, lighting, and angles, land close together in vector space.
  3. The new embedding is compared, via approximate nearest-neighbor (ANN) search, against the existing embeddings in that user's own library only — never against other users' libraries — to decide whether it belongs to an existing cluster or should seed a new one.
  4. Clustering runs incrementally (a streaming/online clustering approach, since new photos keep arriving continuously) rather than as a from-scratch batch job over the whole library on every upload.
  5. Clusters are anonymous ("Person 1", "Person 2" …) until the user optionally labels one with a name; only then does that label become searchable text for that user.

Why Per-User, Not One Global Index

Clustering within a single user's library keeps the ANN search space small (thousands to tens of thousands of faces per user, not hundreds of billions platform-wide), keeps the feature meaningfully privacy-preserving (a user's face graph is never merged with anyone else's without separate, explicit consent), and matches the actual product need — "who is this, among the people in my photos" — rather than "identify this person globally," which is a different, far more sensitive capability this design deliberately does not build.

Interview tip
Lead with consent, not the model: "Face clustering is opt-in. If a user hasn't enabled it, no face embeddings are computed or stored for their library at all — not computed-and-hidden, simply not computed." Interviewers probing this feature are usually listening for exactly this distinction, since "we compute it but don't show it" is not the same privacy posture as "we don't compute it."

Deep Dive — Storage Tiering for Cost Efficiency

Most photo bytes are viewed a handful of times in the days after upload and then almost never again — but "almost never" is not "never," and durability requirements don't relax just because access frequency does. Tiering exploits this access-pattern skew for cost, while access-frequency-driven lifecycle rules (not manual decisions) move data between tiers automatically.

TierTypical age / access patternRetrieval latencyRelative cost per GB
HotJust uploaded, actively viewed/sharedMilliseconds (CDN-cached, SSD-backed origin)Highest
WarmWeeks to months old, occasional accessTens of ms (standard HDD-backed object storage)Medium
ColdOld, rarely accessedSeconds to low minutesLow
ArchiveVery old originals, essentially never re-accessedMinutes to hours (batch rehydration)Lowest

Two important refinements make this practical rather than user-hostile: first, thumbnails always stay hot (CDN-cached) regardless of which tier the original has been demoted to — scrolling a library only ever needs cheap thumbnail bytes, so tiering the multi-megabyte original down to archive doesn't degrade the everyday browsing experience at all; the slow retrieval path is only ever hit on an explicit full-resolution download or print request. Second, durability applies uniformly across every tier — erasure coding (e.g. a 10-data-plus-4-parity Reed–Solomon scheme, ≈1.4× storage overhead) rather than full 3× replication is what keeps the ≈11-nines durability target affordable at exabyte scale; tiering changes retrieval latency and cost, never the durability guarantee.

Data Partitioning and Replication

Two very different sharding strategies coexist, matched to two very different kinds of data.

  • Metadata (photos, albums, faces, tags) is sharded by owner_id (consistent hashing) so every table for one user's entire library lands on the same shard/replica set — browsing a library, listing an album, or running a per-user face-cluster ANN search never requires cross-shard coordination.
  • Blob storage is inherently distributed already, independent of user sharding — each object is erasure-coded across many nodes/racks/availability zones purely based on the object store's own placement policy, not on which user owns it.
  • The search index is sharded independently of the metadata store — often by a different key entirely (e.g. geographic region for public-photo discovery, or simply its own consistent-hash ring over embedding/tag IDs) — because search needs to answer both "search within my library" and, for public content, "search across many users' public photos," which the user-sharded metadata store isn't shaped for.

Feature-Specific Logic: Near-Duplicate Detection for Burst Photos

Content-hash dedup (above) only catches byte-identical files. A burst of five nearly identical shots taken half a second apart — the classic "which one has everyone's eyes open" sequence — are all different bytes and would all get distinct cryptographic hashes, even though they're visually almost the same photo. Catching that requires a different tool: perceptual hashing.

How Perceptual Hashing Works

  1. Downscale the image to a small, fixed grid (e.g. 8×8 or 32×32 pixels) and convert to grayscale, discarding fine detail and noise.
  2. Compute a frequency-domain transform (a discrete cosine transform, DCT, is the classic choice) over that small grid, and keep only the low-frequency components — the coarse shape/luminance structure of the image, which is what survives minor exposure/framing differences between burst shots.
  3. Produce a fixed-length bit string (the perceptual hash) by thresholding those components against their median.
  4. Compare two images' perceptual hashes with a Hamming distance (count of differing bits): a small distance means visually similar images, even though their raw bytes and cryptographic hashes are completely unrelated.

Photos whose perceptual hashes fall within a small Hamming-distance threshold of each other, and whose taken_at timestamps are within a short window (e.g. a few seconds), are grouped into a "burst stack." This powers a UX suggestion — "these 5 photos look similar, want to keep just the best one?" — rather than an automatic storage action: near-duplicates are still visually distinct, independently valuable photos, and the system never deletes or merges them without explicit user confirmation. This is a deliberately different mechanism from content-hash dedup: one is a hard, lossless storage optimization for identical bytes; the other is a soft, human-in-the-loop suggestion for similar-but-distinct content.

Content hash (SHA-256)Perceptual hash
CatchesByte-identical files onlyVisually similar but byte-different files
Sensitivity to changeOne bit different → completely different hashSmall edits/framing differences → small Hamming distance
Action on matchAutomatic, lossless dedup (skip storage)Surface a suggestion; user decides whether to act
Typical use hereRe-imports, re-shared identical filesBurst-mode shots, minor re-edits/re-exports

Rate Limiting and Abuse Prevention

  • Per-account upload quota (token bucket) to prevent a compromised or scripted account from hammering ingestion capacity, layered on top of any storage-quota limit tied to the user's plan.
  • Anomalous upload-velocity detection: a sudden burst far outside a user's historical pattern (e.g. thousands of uploads in minutes from an account that normally uploads a handful a day) triggers step-up verification (CAPTCHA, re-authentication) rather than an outright block, to avoid punishing a legitimate bulk import.
  • Scraping protection on public shares: public and link-based albums are rate-limited per viewer/IP, with anomalous crawl-pattern detection (sequential ID enumeration, unusually high fetch rates) throttled or challenged, since a Flickr-style public gallery is an explicit scraping target.
  • Mandatory content-safety scanning at ingestion: every uploaded photo/video is checked against known-illegal-content hash databases (industry hash-matching services such as PhotoDNA, cross-referenced with organizations like NCMEC) as part of the pipeline, independent of and prior to any user-visible processing — this is a legal and ethical requirement for any platform storing user-uploaded images, not an optional hardening feature.
  • Public-share indexing controls: owners of public content can opt out of search-engine indexing (a per-share robots/no-index directive), separate from the platform's own internal search, which always respects the visibility model regardless of this setting.

Security, Privacy and Permissions

  • Tri-state visibility model: every photo and album is private (owner only, the default), public (discoverable and searchable by anyone), or link (accessible only to someone with the specific share URL, not otherwise discoverable) — enforced as a real access-control check on every read path (API, search, Memories, face-cluster suggestions), not a UI-only filter.
  • Face-recognition consent: face detection/embedding computation only runs for users who have explicitly opted in; the opt-in is per-user and revocable, and revoking it deletes the stored embeddings, not just hides the feature.
  • Geo-tag stripping on public/link shares: a photo's precise lat/lng EXIF data is stripped by default when shared publicly or via link (configurable per-share), since a home address embedded in a casually shared vacation photo is a well-known real-world privacy leak; the original, unstripped metadata is retained in the owner's private copy.
  • Encryption everywhere: TLS in transit for every client-facing and internal call; encryption at rest for both blob storage and the metadata database; provider/API credentials in a secrets manager, rotated regularly.
  • Revocable share links: a link-based share can be revoked or set to expire, immediately invalidating access for anyone still holding the URL — enforced by checking share validity on every request, not by an unguessable-URL-as-security model alone.
  • Audit trail for permission changes: changes to a photo's or album's visibility are logged (who changed what, when), since "who could see this photo, and when" is a real support and compliance question users and regulators both ask.

Load Balancing

Load balancing shows up at several independent layers, and the biggest lever is keeping the very different byte profiles of "upload a 2 GB video" and "fetch a 20 KB thumbnail" from competing for the same connection pools:

  1. A dedicated ingestion tier (L7 load balancer, health-checked) for the chunked Upload Service, sized and tuned for large-body, long-lived connections — kept separate from the lightweight metadata/API tier so one doesn't starve the other.
  2. The CDN is the primary load-balancing layer for reads: the overwhelming majority of the ≈60:1 read-skewed traffic never reaches origin at all, resolving from edge caches close to the viewer.
  3. Worker-pool consumers (thumbnail, transcode, ML inference) scale horizontally behind the processing queue, each pool's instance count driven by its own queue depth rather than a shared, one-size-fits-all autoscaling policy.
  4. Blob storage nodes are load-balanced via the object store's own consistent-hashing placement, so a single "hot" object (e.g. from a viral share) doesn't overload one physical node — the CDN cache in front of it absorbs the read amplification before it would ever matter.

Scaling to Multiple Regions

  • Assign each user a home region (data residency and latency both favor this) where their metadata shard and primary blob replicas live; the Upload Service and read APIs route to the region closest to the requesting client, falling back to the user's home region for writes that need strong consistency.
  • The CDN is inherently global — edge PoPs cache derived assets (thumbnails, transcoded renditions) regardless of which region the origin blob lives in, so viewers anywhere get low-latency reads without the metadata/home-region question ever being relevant to them.
  • Blob storage replicates cross-region asynchronously for disaster recovery on top of its intra-region erasure coding — losing an entire region should still not lose a single photo.
  • Face embeddings and other biometric-adjacent data respect data-residency law (e.g. EU users' face data staying within EU infrastructure) — this is a hard constraint from regulation, not a performance optimization, and needs to be designed in from day one rather than retrofitted.
  • Collaborative/shared albums spanning users in different home regions are the one place this gets genuinely harder: either designate a "home region" for the album itself (simplest, mirrors the per-user rate-limit-counter pinning trade-off notification-style systems make, at the cost of extra latency for contributors outside that region) or accept asynchronous, eventually-consistent replication of album membership across regions. For most products, album-level home-region pinning is the pragmatic default.

CAP Theorem Lens

Favor availability (AP) for search, Memories, and face-cluster suggestions — a stale search index or a Memories feed that hasn't picked up this morning's upload yet is a non-issue. Favor consistency (CP) for ownership, album membership, and visibility changes — a user who just made a photo private must see it as private everywhere immediately, and there is no acceptable "eventually private." The blob store itself sits outside this trade-off entirely: once written, an object's bytes are immutable, so there's no write-conflict to resolve, only replication lag to manage.

Monitoring, Logging and Analytics

  • Upload success/failure rate, broken out by client platform and network type, to catch a regression in the resumable-upload path before it shows up as a spike in support tickets.
  • Transcoding backlog depth (queue depth and oldest-message age per worker pool) as the primary signal for autoscaling and for alerting on a stuck or under-provisioned pool.
  • Dedup savings percentage — bytes avoided via content-hash hits as a fraction of raw ingest — tracked over time as a direct measure of the dedup system earning its complexity.
  • CDN cache hit ratio, since it's the dominant lever on both read latency and blob-storage read cost given the ≈60:1 read:write ratio; a drop is often the earliest signal of a cache-invalidation bug or a shift in traffic pattern.
  • ML inference queue latency (p50/p99 time from upload to face/object tags becoming available), monitored against the eventual-consistency SLA the product has committed to for search/Memories freshness.
  • Storage cost per GB by tier, tracked against the tiering lifecycle policy's actual realized savings, to validate that the hot/warm/cold/archive thresholds are still well-tuned as access patterns evolve.

Common Interview Questions

Grouped by theme — expect a real interview to pick several of these as "and then what?" follow-ups on whatever you draw first.

Deduplication and Storage Efficiency

How does deduplication work at billions-of-photos scale, and does it compromise privacy?
A content hash (SHA-256) is computed over the final uploaded bytes and checked against a hash→storage_key index. A hit references the existing, reference-counted blob instead of storing new bytes; a miss commits a new object and registers its hash. Scoping the index per-user avoids any privacy concern by construction; a platform-wide index used purely for storage efficiency only ever reveals "this hash already exists," never who else uploaded it.
Why not just rely on content-hash dedup for everything, including burst-mode near-duplicate shots?
A cryptographic hash changes completely with even a single differing bit, so visually near-identical burst shots (different exposure, tiny framing shift) hash completely differently and would never dedup. That's a separate problem — perceptual hashing with a Hamming-distance threshold — and a deliberately soft, user-confirmed suggestion rather than an automatic storage action, since near-duplicates are still distinct, independently valuable photos.
Why compute the hash client-side before uploading, if the server recomputes it anyway?
A server-side hit on a client-supplied hash can skip the entire chunk-upload phase, saving the user's most constrained resource (mobile bandwidth) and server ingest capacity entirely. The server still recomputes the hash from whatever bytes do arrive before trusting any claimed match, so a buggy or malicious client can never spoof a dedup hit and cause data loss or cross-reference someone else's content.
What's the storage-cost trade-off between erasure coding and full replication?
Full 3× replication triples storage cost for a given durability level. A Reed–Solomon erasure-coding scheme (e.g. 10 data shards + 4 parity shards) achieves comparable or better durability at roughly 1.4× overhead instead of 3×, at the cost of more compute-intensive reconstruction when shards are lost — a good trade at exabyte scale where the overhead multiplier dominates total cost.

Search, Faces, and ML

How does face clustering scale to hundreds of billions of faces across the whole platform?
It doesn't run as one global index — each user's face embeddings are clustered and searched only within that user's own per-user ANN index (thousands to tens of thousands of faces), which keeps both the search space and the privacy blast radius small. The platform-wide face count is large, but it's sharded by owner_id exactly like the rest of the metadata, so no single index ever needs to hold more than one user's faces.
Is face recognition on by default?
No — it's strictly opt-in per user. If a user hasn't enabled it, no face embeddings are computed or stored for their library at all, not merely hidden from the UI. Revoking consent deletes the stored embeddings rather than just disabling the feature's visibility.
How would you rank candidate "Memories" to surface?
Combine signals available from the pipeline already built: recency milestones (same date, N years ago), detected trip/event clusters (a burst of photos sharing a tight time window and nearby GPS coordinates), presence of labeled face clusters the user engages with often, and past engagement with similar surfaced memories as an implicit feedback signal — then apply frequency/diversity caps so the feed doesn't repeat the same event constantly.
A photo is fully browsable moments after upload but not yet searchable by its contents — is that acceptable?
Yes, and it should be called out explicitly as a deliberate eventual-consistency trade-off: thumbnailing is cheap and fast, while face/object ML inference is comparatively expensive and can lag by seconds to low minutes under normal load. Nothing in the requirements demands search-on-upload; it demands upload confirmation to feel instant, which the design achieves by never blocking on ML inference.

Sharing, Privacy, and Abuse

How do you prevent a public shared album from being scraped in bulk?
Rate-limit public/link-share access per viewer/IP, detect anomalous crawl patterns (sequential ID enumeration, abnormally high fetch rates) and challenge or throttle them, and keep link-based shares unguessable and independently revocable/expiring so access can be cut off without touching the album's other visibility settings.
What happens to a photo's GPS location when it's shared publicly?
By default, precise lat/lng EXIF data is stripped from the version served on a public or link share — the owner's private copy retains full, unstripped metadata. This is configurable per share, but the safe default assumes the sharer didn't intend to publish their exact location.
What legal/safety scanning is mandatory on every upload?
Every uploaded photo and video is checked against known-illegal-content hash-matching databases (industry services like PhotoDNA, cross-referenced against organizations such as NCMEC) as a pipeline stage independent of and prior to user-visible processing. This is a baseline legal/ethical requirement for any platform that stores user-uploaded images, not an optional feature to trade off against cost.
How is a private photo kept private across every feature — search, Memories, face clusters?
Visibility is enforced as an access-control check on every read path, not a UI-only filter: the search index, the Memories ranking service, and face-cluster suggestions all filter by the same visibility field on the underlying photos table, so there's exactly one source of truth for "who can see this," checked consistently everywhere it's read.

Reliability, Scaling, and Architecture History

Walk me through Flickr's classic, real-world production architecture — why is it relevant here?
Flickr fronted PHP application servers with ServerIron load balancers and Squid caches, stored photo bytes on NetApp filers accessed through a "storage manager" abstraction, and kept all other state — ownership, albums, tags, permissions — in master-master MySQL shards plus a small shard-lookup database, with Memcached absorbing read load. Their stated principle was "share nothing": nothing but the photo bytes themselves lives outside the database. It's directly relevant because it's the same bytes/metadata split this design uses, just implemented with the tools available at the time rather than a modern object store and message queue.
Why should image bytes never be stored in the relational database?
Large binary blobs bloat the database's storage footprint, slow down backups/replication, and don't benefit from anything a relational engine is good at (joins, transactions, indexes on structured fields). An object store is purpose-built for exactly this access pattern (write-once, read-many, huge aggregate volume) and can be tiered/replicated/erasure-coded on its own terms, while the database stays small and fast enough to serve latency-sensitive metadata queries.
How would you design the resumable upload protocol so it survives an app crash mid-upload?
Each chunk is durably persisted and acknowledged individually before the client advances; the client never has to hold more than one chunk's worth of "in-flight, unconfirmed" state. After any interruption, the client asks the server which chunks it already has and resumes from the first gap — it never needs to restart the whole file, and the server never needs to guess what the client has versus hasn't sent.
Why generate all thumbnail sizes eagerly at upload time instead of on first view?
The read:write ratio is roughly 60:1 and library browsing is the platform's single most frequent operation, so paying the (cheap, parallelizable) generation cost once per photo up front is far less total cost and latency than paying an on-demand generation cost, and its latency, on every first view across potentially dozens of viewers.
How do you support a full account data export (data portability)?
Because metadata is sharded by owner_id, a single user's complete library — every photo/video's storage_key, all albums, all tags, all face-cluster labels — can be read from one shard/replica set without a platform-wide scan. An export job streams each object from blob storage alongside its metadata into an archive, which can run as a background, rate-limited task per user rather than requiring any special-cased infrastructure.
A single shared album suddenly goes viral — what actually breaks first, and how do you protect it?
Read amplification is absorbed almost entirely by the CDN cache in front of blob storage, since thumbnails for that album's photos are already cached at the edge. The more interesting risk is write-side: if many contributors are adding photos to the same album concurrently, a single hot album_photos partition can become a contention point; modeling additions as an append-only activity log rather than synchronous updates to one row avoids that hotspot.

Key Takeaways

Remember
The entire design rests on two decisions, and everything else is built on top of them: image/video bytes never touch the relational database — they live in erasure-coded object storage, referenced by a metadata row that carries only a pointer — and upload confirmation is decoupled from real processing, so the user sees "uploaded" the instant bytes are durable, while thumbnailing, transcoding, and ML inference catch up asynchronously afterward. Deduplication has two distinct tools solving two distinct problems: content hashing for exact-byte matches (a hard, automatic storage optimization) and perceptual hashing for near-duplicate burst shots (a soft, human-confirmed suggestion) — know which one you're being asked about. Face clustering must be opt-in and scoped per-user, both for tractable ANN search at scale and because face data is biometric data under real regulation. And because most bytes are viewed a handful of times and then almost never again, storage tiering driven by access recency — never touching the durability guarantee itself — is what keeps the "store everything, forever" promise affordable at exabyte scale.
