SYSTEM DESIGN

Designing Uber Backend

A complete, interview-ready design walkthrough for a ride-hailing dispatch backend comparable to Uber, Lyft, or Ola: requirements and capacity estimation, system/client APIs, high-level architecture, a deep dive into the Location Service and its quadtree/geo-tile spatial indexing scheme, low-level classes and the Mercator tile-math formula, database schema and sharding (including online tile re-sharding via dual-write), feature-specific logic for nearby-cab discovery and trip lifecycle management, replication and fault tolerance, monitoring/analytics/notifications, and a bank of follow-up interview questions.

Problem Statement & Scope

Design the backend for a ride-hailing dispatch system comparable to Uber, Lyft, or Ola. A rider opens the app, sees nearby available cabs on a map, requests a ride, and is shown an ETA and estimated cost before/while a driver is matched and dispatched.

In scope (deep design)

  • Nearby-cab discovery (real-time geospatial search over moving drivers)
  • Cab booking / trip request and lifecycle management
  • ETA and cost computation
  • Driver location ingestion at scale (constant GPS pings)
  • Supporting analytics (Kafka → Spark → Hadoop pipeline) that feeds back into geo-partition tuning, fraud detection, and profiling

Explicitly out of scope, but shown as pluggable hooks

Two capabilities are explicitly out of scope for deep design per the source requirements, but the design still shows exactly where they hook in, so an interviewer can see the boundary was a deliberate choice rather than an omission:

  • Payment flow — Cab Request Service makes a call out to a Payments component when a trip is set up/completed (charge on completion, refund on cancellation), but the internals of the payment gateway, PCI compliance, and wallet/card handling are not designed here. Treated as a black-box downstream dependency invoked from Trip Service on COMPLETED.
  • Notification Service — a consumer sits on the same Kafka topics (trip assigned, driver arriving, trip complete) to push SMS/push notifications, but push infrastructure, templating, and delivery guarantees are not designed here. See the Monitoring, Logging & Analytics section for the hook sketch.
Why the Location Service is the centerpiece
The centerpiece of this design is the Location Service and its geospatial indexing scheme (quadtree / geo-tile sharding), since that is what makes “nearby cabs” tractable at planet scale. Nearly every interesting decision in this walkthrough — the capacity math, the choice of Cassandra + Redis over a single store, the sharding scheme, the boundary-expansion logic, even the fraud-detection signals — ultimately traces back to how that service encodes coordinates into shard keys.

Non-Functional Requirements

Assumptions & Constraints

  • Driver GPS ping interval: every 5–10 seconds (assume uniform, average 7.5s) over a persistent WebSocket connection established through the API Gateway.
  • Payments and Notifications are out of scope for deep design — treated as external calls/consumers.
  • This is a single global system operating across multiple cities, each of which may be configured with a different zoom level for its geospatial grid depending on cab density (e.g., zoom 10 for a dense metro, zoom 8 for a newly launched low-density market).
  • Maps/roads/ETA data comes from an external provider (Google Maps), accessed only through an internal Map Service abstraction (so the provider could be swapped later).
  • Drivers and riders are both mobile-app clients; all traffic enters through a single API Gateway.
  • Cab matching is 1 driver : 1 active trip at a time (no ride-pooling in this scope).

Capacity Estimation and Constraints

Always state assumptions explicitly, then derive numbers — interviewers care about the method, not decimal precision. This section derives location-update write throughput, getNearByCabs read throughput, Cassandra storage for location history, and the quadtree/geo-tile shard-count math, in that order, because each stresses a different part of the Location Service.

Location-update write QPS

Derivation QPS = active_drivers / avg_ping_interval
= 5,000,000 / 7.5s
≈ 666,667 writes/sec (≈667K WPS sustained, globally)

This is a sustained, not spiky, load — drivers ping continuously regardless of rider demand — though the number of active drivers itself has a diurnal curve (more drivers online during commute/evening peaks), so provision for roughly 1M WPS at peak (≈1.5×).

getNearByCabs read QPS

Derivation calls/day = 10,000,000 requests/day × 4 refreshes/request = 40,000,000 calls/day
avg QPS = 40,000,000 / 86,400s ≈ 463 QPS (average)
peak QPS = 463 × 8 ≈ 3,700 QPS (peak, rush hour)

At the ≈200ms p99 target, this is comfortably servable from Redis-backed tile lookups (in-memory set reads), not from Cassandra directly.

Cassandra storage for driver location history

Derivation pings/day/driver = 86,400s / 7.5s ≈ 11,520 pings/day
total pings/day = 5,000,000 drivers × 11,520 ≈ 57.6 billion pings/day
raw bytes/day = 57.6B × 100 bytes ≈ 5.76 TB/day
30-day raw total = 5.76 TB × 30 ≈ 172.8 TB
with RF = 3 ≈ 518 TB cluster storage for location history alone
Compression and retention caveat
In practice, Cassandra's SSTable compression (typically 2–4×) brings physical disk usage down to roughly 130–260 TB, and older data (>30 days) should be down-sampled or rolled off to cold storage / deleted rather than retained at full fidelity — raw per-second-ish location pings have little value beyond the recent window except in aggregate (analytics already extracts what it needs via the Kafka → Spark → Hadoop pipeline). Current-location footprint in Redis is tiny by comparison: 5M drivers × ≈100 bytes (driverID, lat/long, tileId, TTL metadata) ≈ 500 MB, trivially fitting in a Redis cluster with room for replicas.

Quadtree / geo-tile shard counts

Derivation tiles_at_zoom(z) = 4^z
zoom 10 (metro) → 4^10 = 1,048,576 possible tiles worldwide
zoom 8 (low-density) → 4^8 = 65,536 possible tiles worldwide

Note this is not “1M physical database shards” — most of the planet's surface (oceans, poles, unpopulated land) has zero driver activity, so tile addressing is sparse: a directory/routing layer maps only active tile prefixes to a physical Cassandra/Redis shard. Empty tiles resolve instantly to “no cabs” without owning a dedicated shard. A single physical shard commonly backs many low-traffic tiles that are colocated by hashing, while a genuinely hot tile (e.g., downtown SF at zoom 10) may get its own dedicated shard or even be split further if it becomes a hotspot (see Data Sharding).

How exponential is this? The zoom-24 illustration
As a reference point on how exponential this scale is: zoom level 24 yields ≈2.3 meter square tiles — i.e., going from zoom 10 to zoom 24 (14 more levels) shrinks tile size by roughly 4^14 ≈ 268 million× in area. This is why zoom level is chosen per market based on cab density rather than using one global fixed resolution: a low-density market wastes shard/index overhead at zoom 10, while a dense metro would suffer from too many cabs per tile at zoom 8 (ambiguous, slow-to-rank candidate sets).

High-Level Design

Every request enters through a single API Gateway that terminates SSL, authenticates/authorizes, serves static assets via CDN, applies rate limiting, and wraps backend calls with a circuit breaker + timeout, plus load balancing across service instances. From there, traffic fans out into a profile plane (User/Driver Service), a dispatch/geo plane centered on the Location Service, and an analytics plane fed entirely off Kafka.

Component walkthrough

  1. API Gateway — single entry point for both rider and driver apps; SSL termination, authN/Z, CDN static assets, rate limiting, circuit breaker + timeout, load balancing.
  2. User Service and Driver Service are symmetric: each owns signup/login/profile/history for its entity, backed by MySQL (source of truth, ACID) with a Redis cache in front for hot reads; MySQL is also queried directly for ad-hoc SQL analytics.
  3. Cab Request Service is the orchestrator a rider hits to request a cab. It talks to Location Service (via Cab Finder) to find nearby cabs, to Trip Service to persist trip state, and to Payments (out of scope) once a trip is set up/completed.
  4. Location Service is the geospatial core: drivers hold a persistent WebSocket connection (through the API Gateway) and push GPS coordinates every 5–10s. A horizontally scaled pool of WebSocket Handlers receives these pings. A WebSocket Manager coordinates the pool and stores in Redis which handler/connection is bound to which driver, so any handler node can route a message to the correct driver regardless of which node physically holds that socket. Handlers forward each ping to Location Service, which (a) persists updated location + route info to Cassandra (durable history, chosen for high write throughput) and Redis (hot “current location” / tile membership), (b) calls Map Service to resolve the “segment info” (which geo-tile/road-segment the coordinate falls in), and (c) emits the ping to Kafka for downstream analytics.
  5. Map Service wraps the external Google Maps API for segment/road lookups and is reused later by Cab Finder for ETA computation using roads data.
  6. Cab Finder (subcomponent invoked by Cab Request Service) calls Location Service.getNearByCabs, ranks candidates by real ETA (not straight-line distance) via Map Service, and picks the best match. It emits two analytics events to Kafka: “cab found + ETA” and “no cab found.”
  7. Trip Service manages trip state: active trips live in MySQL; a Trip Archiver cron migrates completed/cancelled trips into a Cassandra trip_history store on a schedule. Trip Service serves getTripHistory by querying MySQL (active) and Cassandra (archived) and merging results. Payments (out of scope for deep design) is invoked by Cab Request Service/Trip Service at trip completion.
  8. Analytics pipeline: Kafka fans out to (a) a driver feedback consumer listening for “trip complete” events, (b) a Notification Service consumer (out of scope, hook only), and (c) Spark Streaming, which pushes raw events into Hadoop. A batch Spark ML job runs over Hadoop's accumulated data producing: Maps/segment optimization (feeds back into geo-tile tuning), User/Driver profiling, and Fraud detection.

Low-Level Design

The classes below sketch how the API-level contract (saveDriverLocation / getNearByCabs) is actually implemented on top of the quadtree encoding, Redis tile sets, and Cassandra history table.

Core classes / interfaces

class DriverLocationPing {
  String driverId;
  double lat;
  double lon;
  long timestamp;
  String segmentInfo; // resolved via Map Service
}
interface QuadrantIndex {
  // Encodes a coordinate into a shard/tile identifier at a given zoom level.
  // Returns either a prefix string (e.g. "ADBC") or an equivalent (x, y, zoom) tuple.
  String encode(double lat, double lon, int zoom);

  // Returns the (up to) 8 neighboring tileIds around a tile, used for
  // boundary expansion when a query's home tile has too few cabs.
  List<String> neighbors(String tileId);
}
class LocationService {
  void saveDriverLocation(String driverId, double lat, double lon, long timestamp) {
    String tileId = quadrantIndex.encode(lat, lon, zoomFor(driverId's region));
    cassandra.insert(driver_location_history, driverId, lat, lon, timestamp, tileId);
    redis.set("current_loc:" + driverId, {lat, lon, tileId}, ttl = pingInterval * 3);
    redis.sadd("tile:" + tileId + ":cabs", driverId);
    String segmentInfo = mapService.getSegmentInfo(lat, lon);
    kafka.publish("location.ping", {driverId, lat, lon, timestamp, tileId, segmentInfo});
  }

  List<Cab> getNearByCabs(double lat, double lon) {
    int zoom = zoomForRegion(lat, lon); // e.g. 10 metro, 8 low-density
    String tileId = quadrantIndex.encode(lat, lon, zoom);
    Set<String> driverIds = redis.smembers("tile:" + tileId + ":cabs");

    if (driverIds.size() < MIN_CANDIDATES) {
      for (String nbr : quadrantIndex.neighbors(tileId)) {
        driverIds.addAll(redis.smembers("tile:" + nbr + ":cabs"));
      }
    }
    return hydrateAndFilterOnline(driverIds);
  }
}
class CabFinder {
  Cab findBestCab(double riderLat, double riderLon) {
    List<Cab> candidates = locationService.getNearByCabs(riderLat, riderLon);
    if (candidates.isEmpty()) {
      kafka.publish("cab_finder.no_cab_found", {riderLat, riderLon, ts: now()});
      return null;
    }
    for (Cab c : candidates) {
      c.eta = mapService.getETA(c.lat, c.lon, riderLat, riderLon); // roads data, not haversine
    }
    Cab best = min(candidates, by = c -> c.eta);
    kafka.publish("cab_finder.cab_found", {driverId: best.driverId, eta: best.eta, ts: now()});
    return best;
  }
}

  Trip requestCab(String userId, double pLat, double pLon, double dLat, double dLon) { ... }

  }

class TripArchiverJob {
  // Scheduled cron (e.g. hourly): moves COMPLETED/CANCELLED trips older than N hours
  // from MySQL `trips` (active) into Cassandra `trip_history`, then deletes/archives
  // the MySQL row to keep the active-trips table small and fast.
  void run() {
    List<Trip> done = mysql.query("SELECT * FROM trips WHERE status IN (COMPLETED, CANCELLED) AND completedAt < NOW() - INTERVAL N HOUR");
    cassandra.batchInsert(trip_history, done);
    mysql.deleteBatch(done.ids);
  }
}

Mercator tile-math (verbatim, as given in source notes)

Used by QuadrantIndex.encode() to convert a lat/long into pixel/tile coordinates at a given zoom level (standard Web Mercator / Bing Maps tile system formula):

Formula sinLatitude = sin(latitude * PI / 180)
pixelX = ((longitude + 180) / 360) * tileSize * 2^zoom
pixelY = (0.5 - ln((1 + sinLatitude) / (1 - sinLatitude)) / (4 * PI)) * tileSize * 2^zoom
  • longitude maps linearly into pixelX — the world is evenly divided east-to-west.
  • latitude is not linear — the log term is the Mercator projection's latitude-warping function, which stretches tiles near the poles so that on-screen tile density visually matches the projection (the same reason Greenland looks huge on a Mercator map).
  • Both terms are scaled by tileSize * 2^zoom — this is what makes the grid exponentially finer as zoom increases: doubling zoom doubles resolution along each axis (2^zoom), and total tile count grows as 4^zoom (see Capacity Estimation).
  • At zoom level 24, this produces roughly 2.3 meter square tiles — illustrating that the zoom-to-tile-size relationship is exponential, not linear; going from a coarse metro zoom (10) to zoom 24 shrinks tiles by many orders of magnitude.

getNearByCabs pseudocode (boundary expansion)

function getNearByCabs(lat, long):
  zoom = configuredZoomForRegion(lat, long) // e.g. 10 metro, 8 low-density
  tileId = QuadrantIndex.encode(lat, long, zoom)
  cabs = Redis.SMEMBERS("tile:" + tileId + ":cabs")

  if size(cabs) < MIN_CANDIDATES_THRESHOLD:
    for neighborTileId in QuadrantIndex.neighbors(tileId): // up to 8 surrounding tiles
      cabs = cabs UNION Redis.SMEMBERS("tile:" + neighborTileId + ":cabs")

  candidates = hydrate(cabs) // fetch lat/long/status from Redis
  candidates = filter(candidates, status == ONLINE)
  return candidates // Cab Finder subsequently ranks these by real ETA, not raw distance

Data Sharding

The Location Service's shard key is not an afterthought — it is the quadtree encoding described in Low-Level Design. This section spells out the two equivalent ways to name a tile, how zoom level is chosen per market, how the Trip database is sharded separately, and how a tile is split online without ever stopping writes.

Quadtree prefix naming (as given)

The world map is recursively divided into 4 sub-quadrants. Top level:

World
├── AA
├── AB
├── AC
└── AD

Busier quadrants are subdivided further based on usage/density. E.g., AD splits into:

AD
├── ADA
├── ADB
├── ADC
└── ADD

Each additional character narrows the search into one of 4 children of the current tile — a simple prefix string that doubles as both a spatial index and a shard key: the database is sharded by quadrant-name prefix. A query first walks/matches the prefix to determine which quadrant(s) a coordinate falls into, then queries only that shard (plus neighboring shards for boundary cases, per the getNearByCabs pseudocode) instead of scanning the whole world.

Figure 3. Quadtree recursive split: the world divides into AA/AB/AC/AD; the busiest quadrant, AD, is further split into ADA/ADB/ADC/ADD, and so on — each extra character is one more level of the same base-4 encoding.

Numeric (x, y) @ zoom grid — equivalent representation

The same idea expressed numerically: at zoom level z there are 2^z × 2^z tiles per axis (4^z total). A coordinate resolves to an integer tile address (x, y) at that zoom level via the Mercator pixel formula above, then tileX = floor(pixelX / tileSize), tileY = floor(pixelY / tileSize). (x, y, zoom) and the AA/AB/AC/ADA… prefix string are two encodings of the identical quadtree node — the prefix string form is just a base-4 encoding of interleaved (x, y) bits, useful for range queries and human-readable shard naming; the (x, y, zoom) form is useful for neighbor math (x±1, y±1).

Trip DB sharding

Trip (MySQL) is sharded by tripID hash (or userID hash if user-centric access patterns dominate, e.g. “show me my trips” without a cross-shard fan-out). Cassandra trip_history is naturally partitioned by userID/tripID as its partition key, giving even distribution and locality for history reads.

Re-sharding a growing tile

When a previously low-density area (zoom 8) grows and needs finer resolution (zoom 9 or 10):

  1. Detect via the Maps/Segment optimization analytics output that a tile is approaching a cab-density threshold that degrades getNearByCabs candidate-set quality.
  2. Split the tile into its 4 (or 16) children at the new zoom level, computing each driver's new child-tile membership from its last known (lat, long).
  3. Dual-write during migration: new pings write to both old (coarse) and new (fine) tile keys; reads continue against the old tile key until backfill/verification completes, then reads cut over atomically.
  4. Retire the old coarse tile's Redis set and Cassandra shard mapping once cutover is confirmed, updating the routing/directory layer that maps tile-prefix → physical shard.

This mirrors standard shard-splitting playbooks (dual-write + cutover) rather than a stop-the-world migration, so in-flight location pings are never dropped mid-split.

Figure 4. Tile re-sharding via dual-write: a hot coarse tile (AD) splits into 4 fine children (ADA–ADD); new pings dual-write to both generations during backfill, then reads cut over atomically and the old shard mapping is retired.

Feature-Specific Logic

Nearby-cab algorithm

  1. Resolve the requesting coordinate to its tile at the region's configured zoom level (QuadrantIndex.encode).
  2. Read tile:{tileId}:cabs from Redis (fast, in-memory set of driverIDs currently in that tile).
  3. If the candidate count is below a minimum threshold, expand to the up-to-8 neighboring tiles (QuadrantIndex.neighbors) and union their cab sets — this handles the boundary case where the rider is near a tile edge and genuinely-close cabs sit just across the line.
  4. Hydrate candidate driver records (current lat/long, status) and filter to online/available.
  5. Pass candidates to Cab Finder, which re-ranks by real ETA (via Map Service → Google Maps roads data), not straight-line/haversine distance — a cab 400m away by straight line but blocked by a one-way system or river can easily have a worse ETA than one 900m away on a direct route.
Figure 5. Boundary expansion: the rider's coordinate resolves to a home tile; if that tile's tile:cabs set is below MIN_CANDIDATES_THRESHOLD, up to 8 neighboring tiles are unioned in before Cab Finder ranks the combined set by real ETA.

Cab Finder matching/ranking & analytics outcomes

  • Cab Finder calls getNearByCabs, computes ETA per candidate, and selects the minimum-ETA driver (ties broken by rating or idle time, as a further refinement).
  • Two named analytics events are emitted to Kafka:
    • cab_found (with ETA) — feeds dashboards on match quality, average ETA per tile/city, and (upstream) surge-pricing signals (persistently low ETA/high supply vs. persistently high ETA/low supply).
    • no_cab_found — a strong signal for tile-level supply shortages; aggregated over time this drives both surge pricing decisions and geo-expansion/tile-tuning decisions, e.g. flagging a tile that consistently returns “no cab found” as needing either more driver incentives or a coarser tile (fewer, larger tiles reduce false negatives in genuinely sparse areas).

Driver-location ingestion pipeline

Driver (WS ping, 5–10s) → API Gateway → WebSocket Handler (pool) → [lookup handler binding via WebSocket Manager/Redis if re-routing needed] → Location Service.saveDriverLocation → {Cassandra (durable history) + Redis (current loc + tile set)} + Map Service (segment info) + Kafka (fan-out for analytics).

Because the WebSocket Handler pool is stateless (any handler can look up any driver's binding via Redis), the ping path tolerates individual handler-node failures with just a client reconnect — no ping is silently dropped into a dead node.

Figure 6. Driver-location ingestion pipeline: a stateless WebSocket Handler pool forwards each ping to Location Service, which writes durably to Cassandra, updates the hot Redis tile set, calls Map Service for segment info, and fans the event out to Kafka — all off the critical path of the next ping.

Trip lifecycle state machine

Figure 7. Trip lifecycle: REQUESTED → DRIVER_ASSIGNED → ARRIVED → IN_PROGRESS → COMPLETED, with a CANCELLED branch reachable from any state prior to IN_PROGRESS.
  • REQUESTED: rider hit requestCab; Cab Finder is searching.
  • DRIVER_ASSIGNED: Cab Finder matched a driver; rider notified (hook to Notification Service) with ETA.
  • ARRIVED: driver's live location tile matches pickup tile within tolerance (or driver explicitly marks arrival).
  • IN_PROGRESS: trip started; Payments pre-auth may occur here (out of scope detail).
  • COMPLETED / CANCELLED: terminal; triggers Payments capture (if completed) and a trip_complete Kafka event consumed by the driver-feedback service and Notification Service.

Trip Archiver cron

Runs on a schedule (e.g., hourly), selects Trip rows in a terminal state older than a retention threshold, batch-inserts them into Cassandra trip_history, and removes/archives them from the MySQL active table — keeping the hot Trip table small (fast writes/reads for in-flight trips) while preserving full history for getTripHistory via a MySQL + Cassandra merge read.

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design. Answers are grouped by theme below rather than left as one-line prompts, so you can rehearse how you'd actually talk through each follow-up out loud.

Geo-Indexing & Sharding

How do you handle a tile at a zoom level that suddenly needs to be split online without dropping in-flight location pings?
Use a dual-write migration: new pings write to both the old coarse tile key and the new fine child-tile keys computed from the driver's last known coordinate; reads stay on the old key until backfill is verified, then cut over atomically and retire the old key. No stop-the-world lock is needed.
How would you extend getNearByCabs to account for real road distance/ETA rather than tile proximity?
Tile lookup is only a cheap candidate-generation step; the actual ranking happens in Cab Finder, which calls Map Service (Google Maps roads data) to get a real driving ETA per candidate and sorts by that instead of raw distance, as described in Low-Level Design and Feature-Specific Logic.
How do you choose the zoom level for a new city, and can it change over time?
Zoom level is a per-region config picked from initial expected cab density (start conservative, e.g. zoom 8) and revisited using the Maps/Segment optimization analytics output — if no_cab_found/candidate-set-quality metrics indicate the grid is too coarse as the city grows, the region is migrated to a finer zoom via the re-sharding process in Data Sharding.
How would you detect and rebalance a “hot” physical shard that backs multiple sparse tiles but one of them suddenly spikes?
Per-tile write/read metrics (see Monitoring, Logging & Analytics) detect the imbalance; the directory/routing layer that maps tile-prefix → physical shard can migrate just the hot tile's key range to its own dedicated shard, independent of resharding to a finer zoom level.

Matching, Consistency & Fault Tolerance

How do you prevent two passengers from both being matched to the same driver in a race condition?
Driver assignment must be an atomic compare-and-set (e.g., a conditional update on Driver.status from online to on-trip, or a distributed lock keyed by driverID) inside Trip Service's MySQL transaction; the first assignment wins and the loser's Cab Finder falls back to the next-best candidate.
Why Cassandra for location data instead of just Redis or just MySQL?
Redis alone isn't durable/queryable for historical range scans and risks losing recent-but-not-yet-flushed data on failover; MySQL can't sustain ≈667K+ writes/sec at this scale with acceptable latency. Cassandra's append-only, tunable-consistency write path is built for exactly this throughput, while Redis stays as the low-latency “current state” cache on top.
What happens if the WebSocket Manager's Redis binding table becomes unavailable?
Drivers re-ping every 5–10s regardless, so a handler can simply re-register the binding on the next ping; worst case is a few seconds of “who owns this driver's socket” ambiguity, not data loss — consistent with the eventual-consistency NFR for location.
How do you scale the WebSocket Handler tier as fleet size grows?
Handlers are stateless and horizontally scalable behind the API Gateway's load balancer; the only shared state is the Redis binding table, so adding handler nodes is a simple capacity change, not a re-architecture.
What's the failure mode if Map Service/Google Maps is down or slow?
Wrapped in a circuit breaker with timeout (per the API Gateway pattern); on trip it falls back to a straight-line-distance-based rough ETA/cost estimate rather than blocking the booking flow entirely, trading accuracy for availability.
How do you keep the Kafka-based analytics pipeline from becoming a single point of failure for core booking flow?
Kafka publishing from Location Service/Cab Finder/Trip Service is fire-and-forget/async and off the critical path of saveDriverLocation, getNearByCabs, and trip state transitions — a Kafka outage degrades analytics/fraud/notifications freshness but does not block booking or dispatch.

Extensions & Edge Cases

How would surge pricing plug into this design?
The cab_found/no_cab_found ratio per tile is exactly the signal surge pricing needs — a pricing service consuming the same Kafka events can compute a per-tile demand/supply multiplier and Cab Request Service applies it when computing fareEstimate.
How do you detect and mitigate GPS spoofing/fraud?
Flag implausible speed/teleportation between consecutive driver_location_history rows (distance/time > physically possible), cross-check against Map Service road segments (is the driver even on a road), and feed these signals into the batch Fraud detection job; repeated violations suspend the driver account pending review.
How would you support ride-pooling/shared rides on top of this design?
Cab Finder's matching logic would need to consider multiple active requests against a single driver's route (via Map Service) instead of 1:1 matching, and Trip Service's state machine would need a multi-passenger trip variant — a meaningfully larger scope change, but the geo-index and ingestion pipeline are unaffected.
How is getTripHistory kept fast if it has to query two databases (MySQL + Cassandra)?
Most history requests skew toward recent trips, which are still in MySQL or have just been archived; Trip Service can query MySQL and Cassandra in parallel and merge/sort results, and cache the merged page in Redis for a short TTL for repeat pagination requests.
How would you extend this design to support multiple vehicle types (e.g., sedan, SUV, auto) in the same city?
Add vehicleType as a filter dimension in the tile:{tileId}:cabs set (e.g., separate sets per type, or a type field on hydrated candidates) so getNearByCabs/Cab Finder can filter/rank within a requested vehicle class without changing the underlying quadtree/geo-tile indexing scheme.

Key Takeaways

Remember
Everything in this design radiates outward from one decision: how a (lat, long) coordinate becomes a shard key. The quadtree/geo-tile prefix (AA/AB/AC/AD…) and the numeric (x, y, zoom) grid are the same encoding viewed two ways, both derived from the standard Web Mercator pixel formula — and that single encoding is what makes tiles a spatial index, a Redis key, and a Cassandra/physical shard boundary all at once. Zoom level is a per-market dial, not a global constant: dense metros need fine tiles to disambiguate candidates, sparse markets need coarse tiles to avoid empty results, and a tile that outgrows its zoom level is split online via dual-write, never a stop-the-world migration. Consistency requirements split cleanly along the same line as the NFRs — eventually-consistent, AP-leaning Cassandra/Redis for driver location (a few stale seconds is fine), strongly-consistent ACID MySQL for trip/booking state (never double-assign a driver). getNearByCabs is deliberately a two-step process: a cheap Redis tile lookup for candidate generation, then Cab Finder re-ranking by real Map-Service ETA, because straight-line distance is a poor proxy for actual arrival time. And the cab_found/no_cab_found signal, emitted on literally every dispatch attempt, quietly powers three different downstream systems — surge pricing, geo-expansion tuning, and fraud detection — for free, because the whole pipeline was built Kafka-first from the start.
