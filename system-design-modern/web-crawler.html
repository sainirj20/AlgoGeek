SYSTEM DESIGN

Design a Web Crawler

A complete, interview-ready design walkthrough for a large-scale Web Crawler: requirements and capacity estimation, the worker-thread crawl-loop contract, data model, high-level architecture, a Mercator-style priority/politeness-aware URL Frontier, fetching & DNS & rendering internals, deduplication & URL filtering, distributed crawling with consistent hashing, partitioning, fault tolerance, and a bank of follow-up interview questions.

A note on sources
This design synthesizes two ground-truth sources: (1) the classic "Design a Web Crawler" reference write-up (used for requirements rigor, the 15-billion-page/4-week capacity estimation, and the checksum-store sizing), and (2) a pair of hand-drawn whiteboard diagrams — a bare-minimum component wiring diagram, and a Mercator-style URL Frontier internals diagram — reproduced faithfully below as the High-Level Design and Low-Level Design figures.

Problem Statement

Design a Web Crawler: a system that systematically browses the World Wide Web, downloads documents, and stores/indexes them at massive scale — while staying extensible enough that new media types (images, video, audio) and new network protocols (FTP, and beyond) can be added later without redesigning the core. Web crawlers are also known as spiders, robots, worms, and walkers. Search engines are the canonical use case: a fresh, comprehensive index depends entirely on how well the underlying crawl keeps up with a Web that is both enormous and constantly changing.

The same core machinery also underlies several adjacent use cases, worth naming to an interviewer to show you understand the problem's breadth:

  • Testing pages and links for valid syntax and structure.
  • Monitoring sites to detect when their structure or content changes.
  • Maintaining mirror sites for popular destinations.
  • Scanning for copyright infringement across the Web.
  • Building a special-purpose index — e.g. one with deep understanding of content buried inside multimedia files.

Clarifying Questions to Ask the Interviewer

This problem is deceptively open-ended. The scope decisions below change the entire shape of the design, so surface them explicitly in the first few minutes rather than silently assuming.

  1. Is this crawler for HTML pages only, or must it also fetch and store other media types (images, audio, video)? (We'll assume HTML-only to start, but keep the parsing/processing layer modular per MIME type.)
  2. What protocols must it support — HTTP only, or also FTP and others? (We'll assume HTTP only initially, with the protocol module pluggable for later extension.)
  3. What scale are we targeting, and over what time window? (We'll assume roughly 1 billion websites yielding an upper bound of 15 billion distinct pages, crawled within 4 weeks.)
  4. How should the crawler handle robots.txt and politeness — is respecting the Robots Exclusion Protocol a hard requirement?
  5. How often must already-crawled pages be refreshed — is there a freshness SLA for fast-changing content like news homepages, versus mostly-static reference pages?
  6. Does this run on a single datacenter, or must it be distributed across multiple machines/regions from day one?
  7. Do we need near-real-time crawling for a subset of "hot" URLs, or is a multi-week batch-style crawl acceptable for the whole corpus?
  8. Is strict avoidance of duplicate content (mirrors, syndicated articles) required, or is some redundant storage acceptable?
  9. Do we need to defend against crawler traps and adversarial content (infinite URL generators, spam)?
  10. Is there a requirement to expose crawl results (raw HTML, extracted text, a search index) to a downstream consumer, or does this system's scope end at durable storage?
Interview tip
Don't wait for every answer before moving on — state a reasonable assumption out loud ("I'll assume HTML-only over HTTP, ~15 billion pages in 4 weeks, and that we must honor robots.txt") and keep going. Interviewers are grading whether you can scope a genuinely open-ended problem, not whether you guessed their exact numbers.

Requirements and Goals

Functional Requirements

  1. Given a set of seed URLs, systematically discover and download reachable pages across the Web.
  2. Extract outbound links from each downloaded page and feed newly-discovered URLs back into the crawl.
  3. Respect the Robots Exclusion Protocol (robots.txt) for every host before downloading any real content from it.
  4. Avoid downloading/processing the same document more than once (document dedupe), and avoid re-enqueuing a URL already seen (URL dedupe).
  5. Store downloaded documents and their metadata durably so downstream systems (indexing, search) can consume them.
  6. (Extended) Recrawl previously-downloaded pages on a freshness/priority-driven schedule.
  7. (Extended) Support path-ascending crawling to discover isolated resources that have no inbound link.

Non-Functional Requirements

  1. Scalability: the service must scale horizontally to fetch hundreds of millions to tens of billions of documents — no single server can carry this workload.
  2. Extensibility: new media types and new network protocols must be addable as modular units, without redesigning the frontier, dedupe, or storage layers.
  3. Politeness: the crawler must never overload a single host, and must never have more than one open connection to a given host at a time.
  4. Throughput: must sustain the fetch rate implied by the corpus size and time budget (see Capacity Estimation below).
  5. Fault tolerance: a multi-week crawl must survive individual server failures without losing meaningful progress.
  6. Robustness against traps: must not get stuck indefinitely on crawler traps or adversarially-generated infinite URL spaces.

Extended / Out-of-Scope

We go deep on the frontier, fetch, dedupe, partitioning, and fault-tolerance core — the parts that make this problem hard. We explicitly call out, but don't build, the internals of a full-text search index/ranking system, an ML-based content or spam classifier, or a headless browser's JavaScript execution engine, since each is a substantial sub-system in its own right.

System / API Design

A web crawler doesn't expose a public request/response API to end users the way a consumer-facing service does — its real "interface" is the contract every worker thread follows on each iteration of its crawl loop. Getting that contract right (and keeping each step modular/extensible) is the actual API design problem here.

WORKER THREAD LOOP (runs continuously on each of N worker threads):

loop:
  url = URLFrontier.dequeue()            // pick next URL, respecting priority + politeness
  if url is null: sleep(); continue

  host = canonicalHost(url)
  ip    = DNSResolver.resolve(host)       // cached — see Deep Dive: Fetching, DNS, Rendering

  if not RobotsCache.isAllowed(host, url):
      continue                            // Robots Exclusion Protocol check, cached per host

  conn = ProtocolModule.connect(ip, url)   // HTTP today; pluggable per URL scheme
  dis  = conn.downloadInto(DocumentInputStream)  // <64KB in memory, else backing file

  if DocumentDedupe.isDuplicate(checksum64(dis)):  // ~120 GB checksum store
      continue                                      // seen this content before under a different URL

  Datastore.store(url, dis, metadata)
  extractedLinks = Extractor.parse(dis)   // MIME-specific processing module (HTML today)

  for link in extractedLinks:
      absUrl = normalize(link, baseUrl=url)
      if not UrlFilter.allowed(absUrl):
          continue                         // domain / prefix / protocol blacklist
      if UrlDedupe.seen(checksum32(absUrl)):  // ~60 GB checksum store / Bloom filter
          continue
      URLFrontier.enqueue(absUrl)

  goto loop
Interview tip
Walk the interviewer through this loop step by step — pick URL → DNS resolve → connect/download → parse → extract new URLs → dedupe → store — before drawing any boxes. Every subsequent deep dive in this design is really just "how do we make one step of this loop scale/behave correctly."

High-Level Design

A bare-minimum crawler needs at least these components: a URL Frontier to hold and prioritize what to crawl next, an HTTP Fetcher to retrieve pages, an Extractor to pull links out of downloaded documents, a Duplicate Eliminator so the same content isn't processed twice, and a Datastore to durably hold what's been downloaded. Figure 1 wires these together into two cooperating loops: a crawl-management loop (which URL do we work on next?) and a fetch-execution loop (actually go get it), decoupled by a Response Queue so a slow parse never blocks a fast fetch.

Figure 1. High-level design — the crawl-management loop (Seed URLs → URL Frontier → URL Loader → URL Filter → URL Extractor → back to URL Frontier) runs alongside the fetch-execution loop (Fetcher + Renderer pool ↔ DNS Resolver ↔ Internet, writing to Redis and Storage), decoupled by a Response Queue that fans out to the URL Extractor and Duplicate Detection.

Low-Level Design — Mercator-Style URL Frontier Internals (Priority + Politeness)

The URL Frontier from the High-Level Design isn't a single FIFO queue — at this scale it must satisfy two independent, sometimes-competing goals simultaneously: crawl the most important/freshest URLs first (priority), and never send back-to-back requests to the same host (politeness). The Mercator crawler's classic answer, adopted by essentially every production crawler since, is to split the frontier into two queue tiers connected by a router and a heap-based selector.

Figure 2. Mercator-style URL Frontier internals — a Prioritizer assigns each URL to one of F front queues (priority/recrawl/freshness tier); a Back Queue Router drains the front queues and routes each URL into one of B back queues, keyed by host; a Back Queue Selector pulls the next-ready back queue via a min-heap keyed by next-allowed-fetch-time and hands it to the Fetcher + Renderer thread pool.

Every URL for a given host always routes to the same back queue, which is exactly what makes "one queue per host, one thread per queue" a structural guarantee rather than a policy someone could forget to enforce.

Deep Dive — URL Frontier Internals: Prioritizer, Front Queues, and Back Queues

Figure 2 solves two orthogonal problems with two separate queue tiers — collapsing them into a single queue would break one or the other.

Front Queues — Priority, Recrawl Cadence, and Freshness

The Prioritizer looks at signals like a page's importance, how often it has historically changed, and how "fresh" its content category needs to be (a news homepage vs. a static reference page), and assigns each URL to one of F front queues. Front queue 1 might hold "recrawl within the hour" URLs; front queue F might hold "recrawl within a month" URLs. This tier answers exactly one question — of everything we could crawl next, what matters most right now? — and says nothing about which host a URL belongs to.

Back Queues — One Queue, One Host, One Thread

The Back Queue Router pulls URLs out of the front queues (biased toward higher-priority ones, but not exclusively — a pure priority order would starve low-priority queues forever) and routes each URL into exactly one of B back queues, keyed by canonical hostname. This is the politeness mechanism: because every URL for a given host always lands in the same back queue, and each back queue is drained by exactly one worker thread, it is structurally impossible for two threads to hit the same host concurrently — the invariant holds by construction, not by a runtime check that could be missed under load.

Why a Min-Heap Instead of Round Robin?

A naive round robin over the B back queues would frequently select a queue whose host was fetched moments ago, violating the minimum inter-request delay for that host. Instead, the Back Queue Selector maintains a min-heap of size B, keyed by each queue's next_allowed_fetch_time. Popping the heap's minimum always yields the queue that has waited longest since its last fetch (and is past its politeness delay); after a fetch, that queue's next-allowed time is recomputed and pushed back onto the heap. This gives O(log B) selection while guaranteeing every host-level delay is honored — a guarantee round robin cannot make once queue occupancy becomes uneven.

Interview tip
If asked "why not skip the front-queue tier and just have one queue per host?" — because priority and politeness are genuinely different axes. Without front queues, a flood of low-priority URLs from one prolific host could crowd out high-priority URLs from a host that only just became reachable. The two-tier design lets you reason about "what to crawl next" and "how not to overload a host" independently.

Deep Dive — Fetching, DNS Resolution, and Rendering

Once a URL is selected, the worker thread hands it to a protocol-specific fetcher module, which resolves the host, opens a connection, and streams the response into a reusable, per-thread abstraction called a Document Input Stream (DIS) — so every downstream processing module can re-read the same content without triggering a second download.

Figure 3. Fetch pipeline — the protocol module checks a per-host robots.txt cache and a cached DNS resolver before downloading into a per-thread Document Input Stream; documents under 64 KB stay in memory, larger ones spill to a backing file, and every MIME-specific processing module re-reads the same DIS instead of re-downloading.

HTTP Fetcher Module and robots.txt Caching

Courteous crawlers fetch a host's robots.txt before downloading anything else from it. Re-fetching that file on every single request would double the request volume against every host for no benefit, so the HTTP protocol module keeps a fixed-size cache mapping hostnames to their parsed robots exclusion rules.

DNS Resolution — Cache It, or It Becomes the Bottleneck

At roughly 6,200 pages/sec sustained, an uncached DNS lookup on every fetch would saturate any resolver long before the fetch layer itself became the limiting factor (see Bottlenecks below). A local caching DNS server converts the overwhelming majority of lookups — anything for a host already seen this crawl — into an in-memory hit instead of a network round trip.

Document Input Stream (DIS) — Download Once, Read Many Times

Because the same downloaded document may need to be processed by several different modules (link extraction, MIME-specific processing, dedupe checksumming), the crawler wraps every download in a Document Input Stream: documents 64 KB or smaller are cached entirely in memory, while larger documents are temporarily written to a backing file. Each worker thread reuses one DIS instance across documents, so every processing module can re-read the same content without ever triggering a second network fetch.

Deep Dive — Politeness, Duplicate Detection, and URL Filtering

Politeness Is Structural, Not a Runtime Check

Per-host politeness isn't enforced by a rate-limiter bolted on afterward — it falls directly out of the back-queue-per-host design (Figure 2): since exactly one back queue holds a given host's URLs and exactly one thread drains that queue, only one connection to that host can ever be open at a time, and the min-heap selector enforces the minimum delay between requests.

Document Dedupe — 64-bit Checksum Against a ~120 GB Store

Many documents are reachable under multiple different URLs, or mirrored across servers — without a check, a crawler will download the same content repeatedly. After download, the crawler computes a 64-bit checksum (MD5/SHA, truncated) of the document and compares it against a store of all previously-seen checksums (≈120 GB for 15 billion documents). A hit means "discard, we've already stored this content under a different URL."

URL Dedupe — Bloom Filter Over a ~60 GB Checksum Space

Before a newly-extracted URL is even allowed back into the Frontier, it's checked against a store of all previously-seen URL checksums (≈60 GB for 15 billion URLs, 4 bytes each). To avoid the cost of a full lookup on every single extracted link, this set is commonly implemented as a Bloom filter — a compact, probabilistic membership structure where a "no" answer is 100% certain, but a "yes" answer only means "probably present."

The Bloom filter trade-off is not what you'd expect
A false positive on the URL-seen Bloom filter does not mean a duplicate slips through and gets crawled twice. It means the opposite: a brand-new, never-before-seen URL gets incorrectly classified as "already seen," is silently dropped, and is never added to the Frontier at all — the crawler simply never learns that page exists. The mitigation is a larger bit vector (lower false-positive rate), not a secondary duplicate check.

URL Filtering

Before a URL is enqueued, it also passes through a user-supplied URL filter that restricts crawling by domain, path prefix, or protocol — the mechanism used to blacklist entire sites the crawler should ignore (spam farms, known crawler traps, disallowed domains).

Deep Dive — Distributed Crawling, Consistent Hashing, and Crawler Traps

Consistent Hashing Across Crawl Servers

URLs are distributed across crawl servers by hashing the canonical hostname, so that every URL for a given host is handled by the same server (which is also what lets that server co-locate the host's frontier entries with its checksum-store shard — see Data Partitioning below). Using a plain modulo hash would mean that adding or removing even one server reshuffles almost every host's assignment. Consistent hashing avoids that: servers are placed on a hash ring, and only the range owned by the failing/joining server needs to move.

Figure 4. Consistent hashing across crawl servers — hostnames hash to points on the ring and are owned by the next server clockwise. When S3 fails, only the hostnames between S2 and S3 (its arc) reassign to S4; every other server's assignment is untouched.

Checkpointing for Restart-Ability

Every crawl server performs regular checkpointing of its FIFO frontier queues to disk, and periodically dumps a snapshot of everything it holds to a remote server. If a server dies, consistent hashing shifts its load elsewhere, and a replacement can rebuild from the last snapshot rather than needing to re-derive the entire crawl state from scratch.

Crawler Traps

A crawler trap is a URL or set of URLs that causes a crawler to crawl indefinitely. Some are unintentional — a symbolic link within a file system can create a cycle that looks like an endless chain of new pages. Others are introduced deliberately: dynamically-generated infinite webs of documents, sometimes built as anti-spam traps to catch email-harvesting bots, and sometimes built purely to consume search-engine crawler budget and boost a site's perceived ranking. Mitigate with hard limits: max crawl depth per host, and a cap on total pages fetched per host, both tracked via the depth field on each frontier entry.

Data Partitioning and Sharding

The crawler deals with three kinds of data: (1) URLs still to visit, (2) URL checksums for dedupe, and (3) document checksums for dedupe. Since URLs are already distributed by hostname (Deep Dive: Distributed Crawling above), all three data sets for a given host are stored together on the same shard — a host's pending URLs, its URL checksums, and its document checksums never need a cross-shard lookup. When consistent hashing redistributes load after a node failure or addition, all three co-located data sets move together as a unit.

Replication and Fault Tolerance

Each crawl server checkpoints periodically and dumps a snapshot of all the data it holds to a remote server. If a server goes down, a replacement is brought up and rebuilds its state from the last snapshot rather than from an empty start, while consistent hashing shifts new load away from the failed node in the meantime. This bounds the "blast radius" of any single failure to whatever changed since the last checkpoint, not the entire multi-week crawl.

Feature-Specific Logic

  • Path-ascending crawling: helps discover isolated resources that have no inbound link. Given a seed URL like http://foo.com/a/b/page.html, the crawler additionally attempts to crawl /a/b/, /a/, and /.
  • BFS by default, DFS within a host as an optimization: breadth-first search is the default traversal strategy, but once a connection to a given host is already open, the crawler may DFS the remaining URLs on that host to avoid the handshake overhead of reopening the connection repeatedly.
  • Extensible MIME-type processing modules: the Extractor invokes the processing module registered for a document's MIME type; adding a new media type (image, video, audio) later means registering a new module, not redesigning the pipeline.

Security, Privacy and Permissions

  • Robots Exclusion Protocol compliance is the primary "permission" mechanism on the Web — a courteous crawler always fetches and honors a host's robots.txt before downloading any real content, and caches the parsed rules per host.
  • Rate limiting per host (enforced structurally via the back-queue-per-host + min-heap design) avoids the crawler being mistaken for — or effectively behaving like — a distributed denial-of-service attack against any single host.
  • User-supplied URL filter blacklists let operators exclude entire domains, path prefixes, or protocols from being crawled at all.

Load Balancing

Distribute crawl servers via the same consistent-hashing ring used for host assignment (Figure 4), so adding or removing capacity only reshuffles a bounded slice of hosts. Within a single crawl server, distribute worker threads evenly across its assigned back queues, so no one thread becomes a bottleneck while others sit idle waiting on their heap turn.

Scaling to Multiple Regions

Run regional crawl clusters physically closer to their target hosts to cut fetch latency (a crawl server in the same region as the hosts it's fetching sees materially lower round-trip time than one crawling cross-continent). Share or asynchronously replicate the URL-seen and document-checksum indexes across regions so two regions never redundantly crawl and store the same content, while accepting a short propagation delay as a reasonable trade-off given the corpus is already only refreshed on a multi-week cadence.

Monitoring, Logging and Analytics

  • Crawl rate vs. target: track pages fetched/sec against the ≈6,200 pages/sec target derived in Capacity Estimation, and alarm on sustained deviation.
  • Per-host politeness-violation alarms: detect any host receiving requests faster than its configured minimum delay — a sign the back-queue invariant has been broken somewhere.
  • Frontier queue depth: monitor per front-queue and per back-queue depth; a queue that only grows and never drains signals either a capacity shortfall or a trap.
  • Storage growth rate vs. the 2.14 PB budget: track actual bytes stored/day against the capacity-estimation plan so the storage tier is provisioned ahead of, not behind, real growth.
  • Crawler-trap detection heuristics: alert when a single host's crawl depth or page count blows past expected norms, which is exactly the trap-detection signal described above.

BFS vs. DFS Trade-Off

Breadth-first search is the safer default: it spreads fetches across many hosts naturally, which plays well with politeness constraints and avoids getting stuck deep inside one site. Depth-first search within an already-connected host is a narrow, deliberate optimization — it saves reopening a connection/handshake for the next URL on the same host — but used as a global strategy it risks exactly the crawler-trap and single-host-monopolization failure modes described above.

Two properties of the Web itself are what make this whole problem hard, independent of any implementation choice: its large volume (the crawler can only ever download a fraction of it at any moment, so prioritization is mandatory, not optional) and its high rate of change (by the time the last page of a site is downloaded, an earlier page may have already changed — freshness is a moving target, not a one-time achievement).

Common Interview Questions

Interviewers love pressure-testing one component at a time. Expect a real interview to pick 3–5 of these as "and then what?" follow-ups.

Scaling and Performance

How would you crawl 15 billion pages in 4 weeks without DNS resolution becoming the bottleneck?
Cache DNS lookups locally (Deep Dive: Fetching, DNS Resolution). At ≈6,200 pages/sec sustained, an uncached resolver would be overwhelmed long before the fetch layer itself became the limit — a local caching resolver turns repeated-host lookups into in-memory hits.
A single popular host has millions of pages queued — how do you avoid hammering it?
The back-queue-per-host design plus the min-heap keyed by next-allowed-fetch-time in the Back Queue Selector (Figure 2) — only one queue, and thus one connection, is ever active against that host at a time, with an enforced minimum delay between requests.
How would you reduce the ≈2.14 PB storage footprint?
Compress stored HTML (text typically compresses 5–10×), store only extracted structured data instead of raw bytes for some content types, and tier cold/rarely-revisited pages to cheaper storage classes.
What would you change if the target grew from 15 billion to 150 billion pages?
Widen the partitioning (more crawl servers, larger F/B queue counts), and re-check whether 8-byte/4-byte checksums still give an acceptably low collision rate at 10× the corpus size before assuming the same schema scales unchanged.

Correctness and Deduplication

Why use two separate checksum stores (document vs. URL) instead of one?
They answer different questions at different pipeline stages — document checksum dedupes by content after download (≈120 GB), URL checksum dedupes by identity before ever downloading (≈60 GB). Collapsing them would mean either re-downloading known duplicate content, or losing the ability to detect the same document living behind two different URLs.
What actually happens when the URL-seen Bloom filter produces a false positive?
Not a duplicate slipping through — the opposite. A brand-new URL gets misclassified as "already seen" and is silently never added to the Frontier, so that page is simply never crawled. The fix is a larger bit vector, not a secondary dedupe pass.
How would you dedupe near-identical pages (same article, different ad slots) that don't share an exact checksum?
A byte-level checksum only catches exact duplicates. Near-duplicate detection needs a similarity technique such as shingling or SimHash over normalized content, at the cost of extra CPU per page — a legitimate extension beyond the bare-minimum dedupe design.
Should URL normalization happen before or after the URL dedupe check?
Before. Normalize query-parameter ordering, trailing slashes, and default ports first, then checksum — otherwise cosmetically different URLs pointing at the same resource each look "new" and both get crawled and stored.

Politeness, Distribution, and Fault Tolerance

How does the design guarantee only one thread ever hits a given host at a time?
Each back queue holds URLs for exactly one host, and each back queue is drained by exactly one worker thread — one queue per thread, one host per queue, by construction (Figure 2).
A crawl server holding 5% of the frontier crashes — what happens?
Consistent hashing reassigns only that server's arc on the ring to its clockwise neighbor (Figure 4); the neighbor rebuilds that slice from the last on-disk or remote checkpoint rather than needing to re-derive the entire crawl state.
How would you restart a multi-week crawl after a full datacenter power loss?
Regular checkpointing of the FIFO frontier queues to disk, plus periodic snapshot dumps to a remote server — restart from the latest checkpoint rather than reseeding the entire crawl from scratch.
How would you detect a crawler trap before it consumes a disproportionate share of the fetch budget?
Track max-depth and max-pages-per-host counters per host (the frontier entry's depth field); a host that keeps generating "new" URLs indefinitely past a sane threshold is very likely a trap — intentional or an unintentional symlink cycle — and gets throttled or blacklisted.

Extensions and Product

How would you extend the crawler to index images and video, not just HTML?
The MIME-specific processing-module design (Figure 3) is already built for this — register a new Image or Video processing module for those content types; the Extractor, Frontier, and dedupe machinery are unchanged.
How would you support near-real-time recrawling of a fast-changing news homepage vs. a mostly-static reference page?
The Prioritizer assigns front-queue tier by expected recrawl/freshness need — a news homepage lands in a high-priority, short-interval front queue, while a static page lands in a long-interval one (Deep Dive: URL Frontier Internals).
How would you add FTP support alongside HTTP without a redesign?
The worker thread already selects a protocol module based on the URL's scheme (an explicit Non-Functional Requirement) — add an FTP protocol module alongside the HTTP one; everything downstream (DIS, Extractor, Dedupe) is protocol-agnostic.
How would you let an operator scope a crawl to "only this domain's /docs subdirectory"?
Express it as a URL Filter policy scoped to that path prefix; combine with path-ascending crawling if isolated resources within that subdirectory (with no inbound link) also need to be discovered.

Reliability and Operations

How do you know politeness is being violated against a host in production before that host's admin emails you?
Alarm on per-host request-rate metrics exceeding the configured minimum-delay policy (Monitoring, Logging and Analytics) rather than waiting for an abuse complaint.
Frontier queue depth is growing faster than the fetch rate can drain it — what do you do?
Treat it as a monitored signal that either the corpus estimate was too low or a spike in outbound links (a trap, or a genuinely large new site) needs investigation, rather than blindly adding more fetch capacity.

Key Takeaways

Remember
Start with the two numbers that drive everything else: ≈6,200 pages/sec sustained and ≈2.14 PB of storage, derived from a 15-billion-page, 4-week target. The Mercator-style two-tier frontier (front queues for priority/freshness, back queues for per-host politeness, a heap-based selector tying them together) is the single most important piece of machinery in this design — know it well enough to draw it from memory. Dedupe happens at two distinct layers for two distinct reasons (URL checksum before download, document checksum after), and the Bloom filter's failure mode is counter-intuitive — a false positive means a page is silently never crawled, not that a duplicate slips through. Consistent hashing plus regular checkpointing is what makes a multi-week, many-server crawl survivable when (not if) individual servers fail. And the two properties that make crawling fundamentally hard — the Web's sheer volume and its constant rate of change — are exactly what the Prioritizer and front-queue tiering exist to manage.
