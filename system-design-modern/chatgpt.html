SYSTEM DESIGN

Designing ChatGPT

A complete, interview-ready design walkthrough for a large-scale conversational AI chat product (ChatGPT-style): users send messages and receive token-streamed AI responses, conversations persist and can be resumed across devices, users juggle multiple threads, and the model can optionally call tools (web browsing, code execution) or read uploaded files/images mid-conversation. We cover requirements and capacity estimation, high-level architecture, API and low-level design, database schema, sharding, a feature-specific deep dive (conversation branching), replication and fault tolerance, caching, monitoring, security, and a bank of follow-up interview questions. The thread running through every section is that this system has two very differently-shaped scaling problems living under one roof — a fairly ordinary, read-heavy web/data tier (conversations, messages, quotas) that scales the way any large CRUD system does, sharded by user_id/conversation_id and read-replicated — and a GPU-bound, autoregressive token-generation tier where the scarce resource isn't request throughput but GPU memory and GPU-seconds, and where the central efficiency idea, continuous batching, has no real analogue in ordinary web-tier scaling.

Problem Statement & Scope

Design a large-scale conversational AI chat product, similar to ChatGPT, that lets users:

  • Send a message and receive an AI-generated response, streamed back token-by-token rather than delivered all at once.
  • Create, list, rename, and delete conversations, with history that persists and can be resumed later, from any device.
  • Maintain multiple conversation threads per user, each an independent context.
  • Regenerate a response, or edit an earlier message and continue from there — both of which fork the conversation rather than simply appending to it.
  • Carry on very long conversations that exceed the model's fixed context window, without the product breaking or silently forgetting everything.
  • Optionally let the model use tools — web search/browsing, a code interpreter, retrieval over an uploaded file — deciding for itself, mid-generation, when a tool call is useful.
  • Accept multi-modal input: text plus images or file uploads as part of a single message.

In scope

The request/response chat path end-to-end: session and conversation management, the streaming protocol, the inference-serving layer's efficiency techniques (continuous batching, KV-cache management), conversation branching/forking, context-window management, tool-calling/RAG at a conceptual level, moderation, caching, sharding, replication, and monitoring.

Out of scope (acknowledged, not designed in depth)

The internals of model training/fine-tuning, the exact transformer architecture or weights of any specific model, proprietary details of any real company's fleet size or scheduler, and the UI/client rendering layer. We treat "the model" as a black-box autoregressive token generator with well-known public serving characteristics (KV cache grows with sequence length, decoding is sequential per request, batching many requests together is what makes a GPU efficient) — these are the constraints the design must satisfy, not internals we re-derive from first principles.

Key design tension
Autoregressive decoding is inherently sequential per request: token N cannot be computed until token N−1 exists, so a single user's generation cannot be parallelized away by throwing more machines at it. The only lever that makes a GPU efficient is packing many different users' in-flight generations onto the same batched matrix-multiply step — continuous (iteration-level) batching. That single fact reframes almost every later decision in this design: capacity planning is a GPU-memory-and-throughput problem before it is a request-count problem, replication of "state mid-generation" is fundamentally harder than replicating a database row (KV cache lives in GPU HBM, not on durable storage), and the true bottleneck resource is GPU capacity, not application-server count.

Non-Functional Requirements

These are the constraints that actually shape the architecture.

  • Low time-to-first-token (TTFT). The single most user-visible latency metric is how quickly the first token appears after the user hits send — not total response time. TTFT is dominated by queueing for a free GPU batch slot and the "prefill" pass over the prompt, and is tracked and budgeted separately from steady-state decode speed.
  • Sustained token-streaming throughput. Once generation starts, tokens must keep arriving at a steady, human-readable cadence (roughly reading speed or faster) for the duration of a potentially long response, without stalling mid-stream.
  • Very high read/write volume on conversation history at global scale. Listing conversations, fetching history, and appending new turns is an enormous, read-heavy OLTP workload — the kind of workload OpenAI's own engineering blog has described running through a single logical PostgreSQL primary with nearly 50 globally distributed read replicas at hundreds-of-millions-of-users scale, precisely because it's read-heavy and horizontally cacheable, not because it's small.
  • Strict safety/content-moderation guarantees. Both the user's input and the model's output must be checked against a moderation policy, including the ability to abort a response mid-stream if it starts drifting into disallowed content — a purely "check once at the end" model is not acceptable for a streaming product.
  • GPU capacity is the primary scaling bottleneck — not just a typical web-tier scaling problem. Unlike stateless web servers, GPU inference nodes are expensive, power/cooling-constrained, and have long procurement lead times; "add more instances" is not a free, instantaneous lever the way it is for the API/chat-session tier.
  • Multi-region availability. The stateless web/session tier should run active-active across regions; GPU inference capacity, being the scarce and costly resource, may not be symmetrically available in every region (see Replication and Fault Tolerance).
  • Cost-per-token efficiency. Because inference cost scales directly with tokens generated, GPU utilization (via batching, caching, and right-sized routing) is a first-class design goal, not an afterthought optimization.

Capacity Estimation and Constraints

Given assumptions (illustrative, for this exercise — not a claim about any specific product's actual current traffic): we anchor the order of magnitude on the real, publicly cited figure of 800 million ChatGPT users from OpenAI's own engineering blog, and assume ≈150M of those are daily active (a plausible DAU/registered ratio for a widely used consumer product), each sending ≈6 messages/day.

Message & token volume

Assumption DAU = 150M; messages/user/day ≈ 6 → user messages/day ≈ 150M × 6 = 900M/day
Each user message produces exactly one streamed assistant response → ≈900M responses/day
Assume ≈600 output tokens/response on average (mix of short answers and longer reasoning/code) → total output tokens/day ≈ 900M × 600 = 540B tokens/day

Throughput (tokens/sec) — the number that actually sizes the GPU fleet

Calculation Average tokens/sec = 540B ÷ 86,400s ≈ 6.25M tokens/sec sustained average
Peak concentration (assumption): ≈3× average during peak daytime hours (a broad, continuous, globally-overlapping peak, not a single scheduled instant like a market open) → ≈18.75M tokens/sec ≈ 19M tokens/sec at peak

GPU replicas needed at peak

Assumption, informed by public benchmarks Independent vLLM benchmarks report ≈5,700 tokens/sec aggregate decode throughput on a single H100 GPU under continuous batching for a mid-size open model — we round down to ≈5,000 tokens/sec/GPU as a conservative, illustrative "GPU-equivalent" unit (a production frontier model is larger and spans many GPUs per replica via tensor/pipeline parallelism, so this is a unit of accounting, not a literal single chip).
Assume one serving replica = 8 GPUs (a tensor-parallel shard of one model copy) → replica aggregate throughput ≈ 8 × 5,000 = 40,000 tokens/sec/replica
Result Replicas needed at peak = 19,000,000 ÷ 40,000 ≈ 475 replicas → ≈475 × 8 ≈ 3,800 GPUs
+ ≈25% headroom (failover, uneven request-length variance) ≈ 4,750–5,000 GPUs for decode capacity alone, at this illustrative scale
(This excludes separate prefill-optimized capacity, multiple model sizes/tiers, fine-tuning, and evaluation traffic — a real fleet serving hundreds of millions of users across several model tiers is a materially larger, multi-tier number. This is an order-of-magnitude illustration of the reasoning, not a claim about any company's actual fleet size.)

Concurrent open streaming connections (Little's Law)

Calculation Peak responses/sec = peak tokens/sec ÷ avg tokens/response = 19,000,000 ÷ 600 ≈ 31,700 responses/sec
Assume a response takes ≈12s to fully stream end-to-end (queueing + prefill + decode)
Concurrent in-flight generations ≈ 31,700 × 12 ≈ 380,000 concurrent streaming connections at absolute peak

That ≈380k figure matters beyond GPU sizing: it also sizes a stateful streaming-gateway tier that has to hold hundreds of thousands of long-lived SSE/WebSocket connections open simultaneously — a fundamentally different capacity problem than a typical request/response API tier that closes each connection in milliseconds.

Storage growth (conversation history)

Calculation Message row ≈1.5 KB (role, text, token counts, metadata; images/files stored separately in blob storage, referenced by pointer, never inline)
Rows/day (user + assistant turns) = 900M × 2 = 1.8B rows/day
Raw storage/day = 1.8B × 1.5 KB ≈ 2.7 TB/day → + secondary indexes (≈40%) ≈ 3.8 TB/day
× 365 days/year ≈ 1.4 PB/year raw+idx → × 3 replicas (durability/read-scale) ≈ 4.1 PB/year provisioned

This lands in the same shape OpenAI's own "Scaling PostgreSQL to power 800 million ChatGPT users" engineering post describes: a read-heavy conversation/account metadata workload served off a single logical primary with dozens of read replicas, low double-digit-millisecond p99 latency, and the shardable, write-heavy pieces migrated off to a separately-sharded store — exactly the split this design's Data Sharding section reasons through independently below.

Takeaway
The conversation/data tier (≈900M messages/day, ≈4 PB/year) is a large but conventional, read-heavy OLTP scaling problem: the playbook is replicas, caching, and sharding, and it is well understood. The inference tier (≈19M tokens/sec peak, ≈5,000 GPUs, ≈380k concurrent streams) is GPU-capacity-bound: the engineering effort goes into continuous batching, KV-cache memory management, and prefix caching, and the scarce resource (GPUs) cannot be conjured on-demand the way a stateless web server can. These are two different problems on two different cost curves — see Data Sharding and Partitioning.

High-Level Design

Services

Architecture overview

The diagram below turns the service list into a wiring diagram. A message enters through the API Gateway, is loaded into context by the Chat/Session Service (pulling prior turns from the Conversation Store), passes through the input-side Moderation filter, and is handed to the Inference Orchestrator, which routes it onto a GPU replica running continuous batching. The Tool-Use/RAG subsystem can be invoked mid-generation by the model itself. Output passes back through a second Moderation check before being streamed to the client over SSE/WebSocket.

Figure 1. Service topology: a request flows straight down through session assembly, input moderation, and the orchestrator into the GPU cluster's continuous-batching model-serving layer, with the Tool-Use/RAG subsystem invocable mid-generation and output moderation gating the stream before it reaches the Streaming Gateway and, ultimately, the client.

Data flow: sending a message and streaming the response

  1. Client → Gateway → Chat/Session Service: new user message, conversation_id (or none, for a new conversation).
  2. Chat/Session Service loads the active branch of prior turns from the Conversation Store (walking parent pointers — see Feature-Specific Logic) and assembles the prompt, applying context-window management if needed (see Low-Level Design).
  3. Input Moderation classifies the assembled prompt; a violation short-circuits here, before any GPU is touched.
  4. Orchestrator selects a GPU replica (by model, queue depth, KV-cache headroom) and admits the request into that replica's continuously-batched decode loop.
  5. The GPU cluster streams decoded tokens back as they're produced; if the model emits a tool-call, the Orchestrator pauses that sequence, the Tool-Use/RAG subsystem executes the call, and the result is appended back into context before decoding resumes (see Low-Level Design and Security Considerations).
  6. Output Moderation classifies the growing response incrementally; on a violation, generation is aborted mid-stream and a policy message is substituted.
  7. Streaming Gateway relays each token to the client over SSE/WebSocket as it clears moderation.
  8. On completion, the full assistant message is persisted to the Conversation Store (async, off the token-delivery critical path), and usage quota is decremented.

Conventions: JSON over HTTPS (REST) for control-plane operations; the message-send endpoint streams its response via Server-Sent Events. Every request carries a bearer access token; conversation/message identifiers are opaque, sortable IDs.

→ 200 OK, text/event-stream   // same streaming contract as above; creates a new

Idempotent, cacheable reads (conversation list, history) are served from read replicas/cache, never from a path that also holds a GPU slot (see Caching Strategy).

Low-Level Design (Deep Dive)

7.1 Autoregressive decoding and the KV cache

A transformer generates one token at a time: each new token's prediction depends on attending over every previous token in the sequence. Recomputing attention over the whole prefix at every single step would be quadratically wasteful, so inference engines cache the Key and Value projections for every previous token — the KV cache — and each decode step only computes attention for the one new token against that cache. This is why decoding is inherently sequential per request (token N needs token N−1's KV entries to exist) and why the KV cache, not raw FLOPs, is very often the resource that actually limits how many concurrent conversations one GPU can serve.

Illustrative KV-cache footprint (not any specific proprietary model) For a model with 32 layers, hidden size 4096, running in fp16: bytes/token = 2 (K and V) × 32 layers × 4096 × 2 bytes ≈ 524,288 bytes ≈ 0.5 MB/token
An 8K-token conversation → ≈8,000 × 0.5 MB ≈ 4 GB of KV cache for that one sequence alone
An 80 GB GPU minus ≈14 GB of fp16 model weights leaves ≈60 GB — naively reserving the full 8K-token worst case per sequence caps concurrency at ≈60÷4 ≈ 15 sequences, regardless of how short most conversations actually are.

That naive bound is exactly the problem PagedAttention (the technique behind vLLM) targets: instead of reserving one contiguous, worst-case-sized block of GPU memory per sequence up front, it allocates KV cache in small fixed-size, non-contiguous pages — the same idea operating systems use for virtual memory — and grows a sequence's allocation only as it actually generates tokens. Early naive/contiguous allocators were measured wasting 60–80% of KV-cache memory to fragmentation and over-reservation; near-zero-waste paging is what lets far more real (mostly-short) conversations share the same GPU concurrently than the worst-case arithmetic above would suggest.

7.2 Continuous batching — the central serving-efficiency idea

Naive ("static" or request-level) batching groups a fixed set of requests together and doesn't return control until every request in that batch has finished — so a batch of 4 requests where 3 are short and 1 is long leaves the GPU computing on 3 already-finished, padded-out slots for however long the 4th keeps going. Continuous (iteration-level) batching re-evaluates batch membership at every single decode step: the moment a sequence finishes, its slot is immediately backfilled with the next queued request, rather than waiting for the whole batch to drain.

Figure 2. Continuous batching: in static batching (top), three short requests finish early but their GPU slots sit idle until the longest request in the group also finishes. In continuous batching (bottom), each finished slot is backfilled with the next queued request at the very next decode step — the GPU is never left waiting on the slowest sequence in an arbitrary group.

Independent benchmarks of continuous batching (e.g., Anyscale's evaluation of the technique) report throughput improvements on the order of 10–20× over naive static batching at the same latency budget, and pushing GPU utilization from the 30–40% range up past 80% — which is precisely why this, not simply "add more GPUs," is the first lever engineers reach for when GPU capacity is the constrained resource (see Capacity Estimation).

7.3 Context-window management: what happens when a conversation outgrows the model

Every model has a fixed maximum context window (measured in tokens). A long-running conversation will eventually exceed it. Two complementary techniques:

  • Sliding-window truncation. Drop the oldest turns once the assembled prompt would exceed the limit, always keeping the system prompt and the most recent N turns. Simple and cheap, but loses anything earlier verbatim — acceptable for short-lived task conversations, poor for long-running ones with important early context.
  • Rolling summarization. Periodically (e.g., every time the window would overflow), an auxiliary summarization pass compresses the oldest chunk of turns into a short synthetic "memory" system message, which replaces the raw turns in the assembled prompt while the raw turns remain in the Conversation Store for display/history. This trades a small amount of fidelity (summarization is lossy and can under-weight details that later turn out to matter) for effectively unbounded conversation length.

In practice, production systems combine both: keep the most recent turns verbatim (sliding window) and fold everything older into a periodically-refreshed summary, cached so it isn't recomputed on every single new turn (see Caching Strategy).

Why parent_message_id is the single most important column in this schema: it is what turns "conversation history" from a flat append-only log into a tree, which is the data structure regenerate/edit-and-fork actually requires (see Feature-Specific Logic Deep Dive).

Data Sharding and Partitioning

Like the capacity numbers above already hinted, this system has two independent scaling axes that must not be conflated.

Axis 1 — conversation data, sharded by user_id (or conversation_id)

Shard key: user_id. A user's conversations and messages are co-located on one shard, so listing a user's conversations or loading one conversation's full branch history never fans out across shards. For products where multiple users collaborate inside one shared conversation (e.g., an enterprise workspace thread), conversation_id is the better key — the trade-off is that a single user's "list my conversations" query then has to fan out across whichever shards hold their various conversations, so the right choice depends on which access pattern (per-user history vs. per-conversation collaboration) dominates.

Hot-conversation considerations. Two conversation shapes stress this axis specifically: a single conversation that runs to an enormous number of turns (an extremely long-lived chat), and a conversation shared publicly and read by a large, bursty audience (a "viral" shared link). Both are handled the same way as any other hot-key problem — read replicas and a caching layer absorb the read fan-out (see Caching Strategy) — but an unusually long conversation additionally interacts with context-window management (Section 7.3): past some length, the summarization pass isn't just a token-budget optimization, it's what keeps loading that conversation's context from becoming its own latency problem.

Axis 2 — GPU inference capacity: a pooled resource, not shardable data

The GPU fleet has no natural shard key at all. There is no per-user or per-conversation partition of "compute" the way there is a partition of rows — any user's request can, in principle, land on any GPU replica that has a free continuous-batching slot and enough KV-cache memory headroom for that request's context length. The Inference Orchestrator's routing decision is a bin-packing / load-balancing problem (which replica has queue depth and memory to spare right now), not a hashing problem (which shard owns this key).

Figure 3. The dual scaling axis: conversation data shards by user_id (or conversation_id) and scales with more shards/replicas — a storage-cost problem. GPU inference capacity is a pooled resource routed by queue depth and memory headroom, with no shard key at all — a capacity-constrained compute problem with its own, much slower-moving cost curve.

Feature-Specific Logic (Deep Dive)

We work through regenerate / edit-and-fork end-to-end, because it's the one feature that forces a real data-modeling decision: conversation history cannot be a flat, append-only list.

10.1 Why a flat list breaks

If messages were simply appended in order, "edit an earlier message" and "regenerate this response" would have no honest representation: either you destructively overwrite history (losing the original, which users very visibly rely on being able to go back to), or you bolt on ad-hoc "edited_from" pointers that don't compose when a user edits, then edits again, then also regenerates a sibling response. The clean fix is to make messages a tree: every message (except the root) has exactly one parent_message_id, and both "regenerate" and "edit" are the same primitive operation — insert a new sibling under an existing parent — just applied at a different node.

10.2 The tree, the active branch, and the pointer that ties them together

  • Regenerate a response = insert a new assistant message as a sibling of the existing assistant message, both children of the same user-message parent.
  • Edit a prior user message = insert a new user message as a sibling of the original, both children of the same preceding-assistant-message parent; whatever the model generates next hangs off the new user message, starting a fresh sub-tree.
  • Neither operation ever deletes anything. The original branch stays fully reachable — that's what lets the UI offer a "< 1 of 2 >" switcher between sibling responses.
  • conversations.active_leaf_message_id is the single pointer that says "this is the tip of the branch currently being displayed and continued." Every new message anywhere in the tree updates this pointer to itself. Switching branches (the POST /v1/conversations/{id}/active-branch endpoint) is just a pointer update — no data is copied or moved.
  • To reconstruct the linear prompt sent to the model for the next turn, walk parent_message_id from active_leaf_message_id back to the root, then reverse it. This is exactly the sequence that feeds into context-window management (Section 7.3).
Figure 4. The message tree: editing msg3 creates sibling msg3′ without deleting the original; regenerating creates sibling msg4′ the same way. The conversation's single active_leaf_message_id pointer names the tip of the branch currently in view — switching branches is a pointer update, and walking parent pointers from that leaf back to the root reconstructs the linear prompt for the next turn.

Replication and Fault Tolerance

  • A GPU node fails mid-generation. The KV cache for an in-flight sequence lives only in that GPU's HBM — it is not durable and is far too large and too fast-changing to synchronously replicate across nodes the way a database row is. The realistic recovery path is not "failover the live GPU state," it's: the orchestrator detects the broken stream (heartbeat/lease timeout), the client/gateway has already received and can keep the tokens streamed so far, and the request is retried by re-running the prefill on a healthy replica using the partial output plus original prompt as the new input — i.e., resume from the last flushed chunk, not from raw in-memory GPU state. This is why request handling upstream of the GPU cluster must be idempotent (a retried generation must not double-append to the conversation).
  • Conversation-store replication. Once a message is fully generated, persisting it follows an ordinary durable-write pattern: synchronous/quorum replication for the write path, with read traffic (history, listing) served from read replicas — the same pattern OpenAI's own engineering blog describes running at hundreds-of-millions-of-users scale off a single logical primary plus dozens of geo-distributed read replicas. Individual in-flight streamed tokens are not fsynced one at a time; only the completed message is durably committed, trading a small durability window (a crash mid-stream loses at most one incomplete message, which the client can simply re-request) for not paying a disk round-trip per token.
  • Multi-region: the stateless tiers can be active-active; GPU capacity is the sticky constraint. The API gateway, chat/session service, and moderation tier are ordinary stateless services and can run active-active across regions behind a global load balancer. GPU inference capacity cannot be treated the same way: GPUs are expensive, power/cooling-constrained, and typically provisioned per region well ahead of time, so failing an entire region's inference traffic over to another region requires either pre-provisioned spare GPU headroom there (costly, and not always fully available) or graceful degradation — e.g., routing to a smaller/faster fallback model, queuing with a visible wait, or admission-controlled throttling — rather than the instant, symmetric failover a stateless web tier enjoys.
  • Retry-with-backoff, made safe by idempotency. A client retry after a dropped stream carries the same client-generated request key; the server can distinguish "this generation already completed, replay the stored result" from "this generation is still in flight, don't start a second one" from "this genuinely never started, begin it now" — the same idempotency discipline used to keep any retried write safe.

Caching Strategy

Guiding rule: cache anything expensive-and-safe-to-reuse; never cache the moderation decision or quota counters as if they were static facts.

DataCache?Rationale / invalidation
KV cache for a shared prefix (system prompt, few-shot preamble, a popular custom assistant's instructions)Yes — prefix/prompt cachingReuses previously-computed Key/Value tensors for an exact-match prefix instead of recomputing them for every request that shares it. Reported real-world impact from major providers' prompt-caching features is substantial — up to roughly 50–90% latency and cost reduction on cache hits for long, repeated prefixes — which is exactly why a widely-shared system prompt is worth caching aggressively.
Frequent tool results (repeated web-search queries, common code-execution snippets)Yes, short TTLAvoids redundant external calls, but the web changes: a short TTL (minutes, not hours) bounds staleness risk for anything time-sensitive.
Conversation summaries (from context-window management)Yes, invalidated on new turns past the summarized boundaryRecomputing a summary of the same 200 older turns on every new message would be pure waste; cache it and only re-summarize when the window boundary moves.
Conversation list / history readsYes, populated async, served from replicas/cacheThe overwhelming majority of traffic (listing, scrollback) is read-only and tolerant of being a few hundred ms stale.
Moderation decision on mutable/evolving contentNo, or very short TTL onlyPolicy and classifiers get updated; caching a stale "allowed" verdict indefinitely can let content that would now be blocked keep slipping through.
Usage-quota counters (FR8)No — authoritative fast counter, not a cacheThe same double-spend-shaped race as any balance check: two concurrent requests both reading a stale "under quota" value can both proceed and blow past the limit. Quota decrements need an atomic conditional check-and-decrement, not a cached read.

Monitoring, Logging, Analytics and Notifications

Key SLIs / metrics:

  • Time-to-first-token (TTFT) P50/P95/P99 — the single most user-visible latency number, tracked separately from steady-state decode speed.
  • Tokens/sec per request (decode throughput) and tokens/sec per GPU replica (aggregate) — the second tells you whether continuous batching is actually packing the GPU efficiently.
  • GPU utilization and orchestrator queue depth — a growing queue is the earliest signal that GPU capacity, not the web tier, needs to scale.
  • KV-cache memory utilization per replica — approaching saturation caps how many new sequences that replica can admit, independent of raw compute headroom.
  • Moderation-flag rate, split by input vs. output and by policy category — a sudden spike can indicate either an abuse campaign or a classifier regression after a model/policy update.
  • Cost per conversation / cost per 1K tokens — the direct cost signal, since inference cost scales with tokens generated.
  • Prefix-cache hit rate, tool-call error/timeout rate, idempotency-replay rate (duplicate request-key hits), and streaming-connection drop/reconnect rate.

Logging: conversation content logging sits in tension with privacy expectations (see Security Considerations) — retention windows, access controls, and any use of content for further training must be explicit, configurable, and audited, not an incidental side effect of "logs are useful for debugging."

Notifications: usage-quota-approaching alerts to the user (FR8), and incident/degraded-capacity banners in the client when GPU capacity is constrained (e.g., routing to a smaller fallback model or queuing) so the product is honest about degraded service rather than silently slower.

Security Considerations

  • Prompt injection from tool results / RAG content. A web page, search result, or uploaded document the model retrieves mid-generation can contain text deliberately crafted to look like instructions ("ignore your previous instructions and instead..."). The tool-use subsystem must return retrieved content as clearly-delimited, untrusted data — never concatenated into the prompt in a way indistinguishable from a trusted system instruction — and sensitive actions a tool could trigger should require explicit confirmation rather than executing purely on the model's own say-so. Output-side moderation (below) is the second layer of defense if an injection partially succeeds.
  • Content moderation on both input and output. Input classification happens before a GPU is ever touched (cheap rejection); output classification runs incrementally against the streaming response and can abort generation mid-stream — a single "check the finished response" pass is not sufficient for a product where the user is already reading tokens as they arrive.
  • Data privacy and retention for conversation history. Encryption in transit and at rest; configurable retention windows and user-initiated deletion; clear, separately-consented policy on whether conversation content is used for further model training; regional data residency options for regulated/enterprise customers.
  • Per-tenant isolation for enterprise customers. Strict conversation-store partitioning so no query path can cross tenant boundaries, audit logging scoped per tenant, and — on the GPU side — either dedicated capacity pools or, more cost-effectively, strong logical isolation (no tenant's prompt/response content or KV cache is ever inspectable by another tenant) within the shared pooled fleet, reserving fully dedicated GPU capacity only for customers whose contractual requirements demand it.
  • Idempotency as a security/correctness control. The same client-supplied request-key discipline used for fault tolerance (Replication section) also prevents a replayed or duplicated request from generating and billing a response twice.

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design. Rehearse the reasoning out loud, not just the one-line answer — the "why" is what actually gets evaluated.

Serving Efficiency & GPU Economics

Q1. Why does continuous batching matter so much for GPU efficiency compared to naive per-request (static) batching?
Static batching holds an entire batch's GPU slots hostage to whichever request in the group finishes last — three short requests finish and then sit idle, padded, waiting for a fourth, long one. Continuous (iteration-level) batching re-checks batch membership at every decode step and immediately backfills a finished slot with the next queued request, so the GPU is never idle waiting on an arbitrary group's slowest member. Reported real-world gains are on the order of 10–20× throughput at the same latency budget, which is the difference between needing thousands of GPUs and needing tens of thousands for the same traffic.
Q2. Why is GPU capacity described as the true bottleneck resource here, rather than the usual "just add more app servers" web-scale story?
A stateless web server is cheap, fungible, and can be spun up in seconds by an autoscaler; a GPU is expensive, power/cooling-constrained, often has a multi-month procurement lead time, and its useful capacity per unit depends on model size, batch efficiency, and KV-cache memory headroom rather than a simple CPU/RAM ratio. You cannot "autoscale" your way out of a GPU shortage the way you can for a web tier — capacity planning has to happen far ahead of demand, and every efficiency technique (batching, caching, quantization) directly multiplies how much traffic your existing GPU fleet can serve, which matters far more here than in a typical horizontally-scaled service.
Q3. Why not just cache the KV cache across requests the way you'd cache a database read?
You can, but only for the part of the sequence that's an exact, shared prefix across requests (a common system prompt, a repeated few-shot preamble) — that's exactly what prefix/prompt caching does, and it's a large win because that shared prefix's Key/Value tensors are identical for every request that includes it. What you cannot do is cache the KV cache for the user-specific, ever-growing suffix of a conversation the way you'd cache a stable read: it's enormous (hundreds of KB to several MB per thousand tokens), changes every single turn, and lives in GPU HBM rather than a cache tier built for that access pattern.
Q4. A single very popular system prompt (e.g., a shared custom assistant configuration) is reused by millions of conversations — how do you exploit that?
Route requests that share that exact prefix so they're likely to land on GPU replicas that already have its KV cache resident (affinity routing), and rely on the serving engine's prefix-caching layer to recognize the exact-match prefix and skip recomputing its Key/Value tensors entirely, paying only for the unique, per-conversation suffix. This turns what would be millions of redundant prefill passes over the identical prompt into effectively one, at the cost of some routing complexity to keep "hot prefix" traffic concentrated rather than spread evenly (which would minimize cache hit rate).

Data Model, Branching & Fault Tolerance

Q5. How would you design conversation branching so a user can edit an earlier message or regenerate a response without losing the original?
Model messages as a tree via parent_message_id rather than a flat list. Both "regenerate" and "edit" become the same operation — insert a new sibling under an existing parent — applied at different nodes, and neither ever deletes the original. A single active_leaf_message_id pointer on the conversation names which branch is currently in view; switching branches is just a pointer update, and reconstructing the linear prompt for the model is a walk from that leaf back to the root via parent pointers.
Q6. A conversation grows past the model's context window in the middle of a long chat — what actually happens?
Two complementary mechanisms: a sliding window keeps the most recent turns verbatim and drops the oldest ones from the assembled prompt (cheap but lossy), and a rolling summarization pass periodically compresses everything older than the window boundary into a short synthetic system message that stands in for the raw turns in the prompt, while the raw turns remain in storage for history/display. Production systems combine both, and cache the summary so it isn't recomputed on every subsequent turn.
Q7. A GPU node crashes 40% of the way through streaming a response to a user — what does the client see, and how do you recover?
The client keeps whatever tokens it already received; the orchestrator detects the broken stream via a heartbeat/lease timeout and retries the request on a healthy replica, re-running prefill with the original prompt plus (if the design chooses to preserve it) the partial output as additional context, rather than attempting to resurrect the crashed GPU's in-memory KV cache — that state simply isn't durable or cheaply replicable. The retry must carry the same idempotency key as the original request so the conversation store never ends up with a duplicated or double-appended assistant message.
Q8. Why shard conversation/message data by user_id or conversation_id, and what happens with one abnormally large/hot conversation?
user_id co-locates a user's own conversations so their most common operation — "list my chats," "load my history" — never fans out across shards; conversation_id is the better key when multiple users collaborate inside one shared thread, at the cost of a per-user listing query needing to fan out. An abnormally large conversation (extremely long-running, or a viral public share) is handled like any hot key — read replicas and caching absorb the read fan-out — but its length also forces context-window summarization sooner, which is as much a latency safeguard for loading that conversation as it is a token-budget one.

Safety, Cost & Extensions

Q9. A web-browsing tool call returns a page that contains hidden instructions telling the model to ignore its system prompt — how do you defend against that?
Treat every tool result as untrusted data, clearly delimited from trusted instructions in the assembled prompt, never concatenated in a way that lets retrieved text masquerade as a system directive. Sensitive actions a tool call could trigger (sending data somewhere, making a purchase, executing risky code) should require an explicit confirmation step rather than firing purely on the model's own decision, and output moderation remains a second, independent check that can still catch a response that was steered off course despite the input-side safeguards.
Q10. How do you moderate a response that's already streaming to the user when the model starts producing disallowed content halfway through?
Output moderation runs incrementally against the growing response, not just once at the end, so it can catch a policy violation mid-stream. When it does, generation is aborted on the GPU side, the streaming gateway stops relaying further tokens (and can retract/replace what's already been shown, depending on product policy), and the incomplete message is stored with a status like ABORTED_MODERATION rather than silently marked complete.
Q11. An enterprise customer wants a guarantee that their conversations never share GPU capacity or storage with any other tenant — how do you accommodate that without giving every enterprise customer their own idle GPU fleet?
For storage, strict per-tenant partitioning with no shared query path already gives that guarantee cheaply. For GPU capacity, the pragmatic middle ground is strong logical isolation within the shared pooled fleet by default (no tenant's content or KV cache is ever inspectable cross-tenant), reserving genuinely dedicated GPU capacity only for the subset of customers whose contracts specifically require physical isolation — because dedicating idle GPU capacity per tenant at scale is exactly the kind of cost that made pooling the whole point of the fleet in the first place.
Q12. How would you extend this design to support multi-modal input (e.g., an uploaded image) without changing the core message/conversation data model?
The message row stays a thin pointer: an attachments reference to an object-storage location, not the binary content inline, keeping the messages table's row size and replication cost unaffected by upload size. The image is fetched by the inference path when assembling that turn's input for a multi-modal-capable model, and treated like any other attachment for retention/deletion policy; the tree/branching model in Section 10 is entirely orthogonal to what a message's content contains, so it needs no change.

Key Takeaways

Remember
This design has two genuinely different systems sharing one product surface, and conflating them is the most common mistake. The conversation/data tier (conversations, messages, quotas) is a large but conventional, read-heavy OLTP problem: shard by user_id/conversation_id, lean on read replicas and caching, and model messages as a tree (via parent_message_id and a single active_leaf_message_id pointer) so regenerate and edit-and-fork are the same primitive operation instead of a destructive overwrite. The inference tier is GPU-capacity-bound: autoregressive decoding is inherently sequential per request, so continuous batching — packing many users' in-flight generations onto shared GPU steps and immediately backfilling any slot that finishes — is the load-bearing efficiency idea, backed by KV-cache memory management (paged, non-contiguous allocation) that decides how many real conversations actually fit on one GPU. Because GPU nodes are expensive, capacity-constrained, and not durably replicable mid-generation the way a database row is, fault tolerance here means idempotent retry-from-last-flushed-chunk rather than live failover, and multi-region design means the stateless tiers go active-active while GPU capacity, the truly scarce resource, gets graceful degradation instead of instant symmetric failover.
