SYSTEM DESIGN

Designing WhatsApp

A complete, interview-ready design walkthrough for a WhatsApp-style messaging system: requirements and capacity estimation, system/client APIs, high-level architecture, deep dives into message delivery, presence and group fan-out, a full audio/video calling subsystem (signaling, NAT traversal, SFU topology), end-to-end encryption via the Signal Protocol, database schema and sharding, caching, replication and fault tolerance, load balancing, security, monitoring, key trade-offs, and a bank of follow-up interview questions.

Problem Statement & Scope

Design a messaging system like WhatsApp that supports real-time 1:1 and group text chat, media sharing, delivery/read receipts, presence ("last seen"), and 1:1 and group audio/video calling, at a scale of hundreds of millions of daily active users. This is one of the most common "chat + real-time communication" interview questions, and it rewards candidates who recognize early that it is really two sub-systems glued together: a store-and-forward messaging system, and a real-time media (RTC) system for calls. Interviewers frequently probe both halves, plus how they share infrastructure — auth, presence, push notifications.

It's worth stating up front why this problem is such a durable interview favorite: WhatsApp itself is a famous existence proof that a tiny engineering team can run this kind of system at planet scale. When Facebook acquired WhatsApp for roughly $19 billion in February 2014, the company was reportedly operating the service with around 50 engineers total, serving a user base already in the hundreds of millions — a ratio that only worked because of deliberate architectural choices (Erlang, FreeBSD, and a thin feature set) that this walkthrough revisits throughout, especially in the capacity-estimation and fault-tolerance sections below.

In scope

A focused design covers the following capabilities end-to-end:

  • 1-on-1 text chat, with offline delivery
  • Group text chat (create/add/remove members, broadcast)
  • Image / video / document / voice-note sharing
  • Delivery receipts (sent / delivered / read — the "ticks") and typing indicators
  • Presence: online / last-seen, using a heartbeat
  • 1-on-1 audio and video calling
  • Group audio/video calling (small groups, e.g., ≤ 8 participants a la WhatsApp/Zoom)
  • End-to-end encryption of messages and calls

Out of scope (mention to interviewer, don't over-invest)

Call these out explicitly so the interviewer knows you understand the boundary, then move on without designing them:

  • Payments / Status (stories) / Business API / Channels — call out as extensions if time permits
  • Large-scale webinar/broadcast video (that's closer to a Zoom-webinar or live-streaming design)

Functional Requirements

These are the concrete, testable behaviors the system must support. State them explicitly at the start of an interview so both you and the interviewer are anchored to the same scope before any boxes get drawn.

  1. Users can send and receive 1:1 text messages in near real time.
  2. Users can create groups and send messages that are broadcast to all members.
  3. Users can send images, videos, voice notes, and documents.
  4. Sender sees delivery state: sent (single tick), delivered (double tick), read (blue tick).
  5. Users can see whether a contact is online, and if not, their last-seen timestamp.
  6. Offline users receive queued messages when they reconnect, and a push notification while offline.
  7. Users can place 1:1 audio or video calls to a contact, with ringing, accept/reject/busy states.
  8. Users can start/join a group audio or video call.
  9. Chat history persists and syncs across a user's devices.
  10. Messages and calls are end-to-end encrypted so even the service provider cannot read them.

Non-Functional Requirements

The non-functional requirements are where this design diverges most sharply from a typical CRUD system: messaging and calling have almost opposite tolerance for loss versus latency, and that tension shapes nearly every architectural decision that follows.

  • Low latency: message delivery to an online recipient should feel instantaneous (low hundreds of ms domestically; a few seconds is acceptable across continents, bounded by speed-of-light propagation delay on long fiber routes).
  • No message loss: text messages must not be lost even if the recipient is offline or a server crashes mid-flight — durability trumps latency for text.
  • Real-time media can drop frames: for audio/video calls, some packet loss is acceptable (concealed by jitter buffers/codecs); consistent low latency matters more than perfect delivery.
  • High availability: target 99.9%+ for messaging; a chat server dying should not lose messages, only force a client reconnect.
  • Eventual, per-user consistency: each user should see a consistent, monotonically ordered view of their own conversation, but strict global ordering across all users is not required.
  • Scalability: system must scale horizontally to hundreds of millions of concurrent connections and tens of billions of messages/day.
  • Security & privacy: end-to-end encryption; the server should not be able to read message content or decode call media.
  • Multi-device support: same account usable from phone + linked web/desktop clients, with history sync.

Working assumptions (state these out loud in an interview)

A strong candidate narrates these assumptions rather than silently baking them in:

  • Video/audio calls are real-time — some packet loss and minor quality degradation is OK.
  • Text messages: data loss is NOT acceptable; a 1–2 second delay is fine, and depends on distance (international routes can add multiple seconds due to physical distance / speed of light + extra hops).
  • Clients are "smart": they cache sent/unsent/failed messages locally, retry, and transcode media to a standard format/resolution before upload.
  • A client that doesn't support a codec/transcoder (e.g., a browser-based client) falls back to a server-side transcoding path.

Capacity Estimation and Constraints

Always state assumptions explicitly, then derive numbers — interviewers care about the method, not decimal precision. This section walks through messaging load, the connection/server fleet, media storage, and audio/video calling capacity separately, because each stresses a different part of the system.

Messaging load

Assume 500 million daily active users (DAU), each sending ≈40 messages/day on average.

Assumption Total messages/day = 500M users × 40 msgs = 20 billion messages/day
Avg message size ≈ 100 bytes (text + small metadata)
Storage/day = 20B × 100 bytes ≈ 2 TB/day
Storage/5 years = 2TB × 365 × 5 ≈ 3.6 PB (before replication/compression)
Incoming bandwidth = 2TB ÷ 86,400 sec ≈ 25 MB/s
Outgoing bandwidth ≈ 25 MB/s (every message fans out to ≥ 1 recipient)

Add roughly 3× for replication (three copies for durability) and this becomes ≈10.8 PB of physical storage over five years — still very manageable once sharded across a wide-column store (see Data Sharding, below).

Real-world scale check
The 20-billion-messages/day figure above is a deliberately round, teachable baseline — it's worth knowing where WhatsApp's real traffic actually landed, because interviewers sometimes ask you to sanity-check an estimate against reality. WhatsApp's own leadership reported roughly 50 billion messages/day in early 2014 (around the time of the Facebook acquisition), growing to about 65 billion/day by 2018, and then — per a public statement from WhatsApp head Will Cathcart — to roughly 100 billion messages/day by late 2020. The real production system has run at 5× or more of the baseline this walkthrough uses, a good reminder to present your numbers as order-of-magnitude assumptions rather than invented facts.

Connections & chat server fleet

Plan for up to 500M concurrent long-lived connections (WebSocket/TCP) at peak.

Assumption Assume 1 modern server can hold ≈50K–500K concurrent connections
(real systems tune the OS heavily — WhatsApp historically tuned FreeBSD to 2M+ conns/box)
Conservative (50K/box): 500M ÷ 50K ≈ 10,000 chat servers
Aggressive (1M/box): 500M ÷ 1M ≈ 500 chat servers

This spread is the classic "vertical vs. horizontal" scaling trade-off — see Key Trade-offs & Alternatives Considered below, and follow-up question 2 under Messaging depth.

Real-world scale check
This isn't just theoretical. WhatsApp's engineers publicly described tuning FreeBSD — chosen partly because its kqueue event-notification mechanism outperformed Linux's epoll for this exact workload at the time — to sustain upwards of 2 million concurrent connections on a single box, roughly 20–40× the "aggressive" end of the 50K–1M/box range this section assumes. Combined with Erlang's lightweight, per-connection process model (Erlang was originally built by Ericsson for telecom switches, where holding millions of simultaneous, mostly-idle connections is exactly the workload it was designed for), a fleet sized in the hundreds — not tens of thousands — of boxes was reportedly sufficient for hundreds of millions of users. The interview takeaway: always state your per-box assumption out loud, because it swings your fleet-size estimate by more than an order of magnitude, and the "right" answer depends entirely on how much OS/runtime tuning investment a team is willing to make.

Media (images/video/voice notes)

Assume 10% of the 20B daily messages carry media, averaging 300 KB (a mix of images, short voice notes, and video clips).

Assumption Media messages/day = 20B × 10% = 2 billion
Media storage/day = 2B × 300KB ≈ 600 TB/day (raw, before dedup/compression)
Media bandwidth = 600TB ÷ 86,400s ≈ 7 GB/s ingress to blob storage / CDN

Media is stored once in a blob store + CDN and referenced by a UID in the message payload (not inlined) — this keeps the chat-message hot path small and fast.

Audio / video calling

Calling capacity needs a different model: concurrency, not daily totals, is what sizes the real-time media/relay fleet.

Assumption 500M DAU, 10% place ≥ 1 call/day => 50M calls/day
Avg call duration = 3 minutes; peak-hour share of daily traffic = 15% (typical diurnal peak factor)
Peak calls initiated/sec: 50M × 15% ÷ 3600s ≈ 2,080 calls/sec initiated at peak
Peak CONCURRENT 1:1 calls (Little's Law: L = λ × W):
2,080 calls/sec × 180 sec avg duration ≈ 375,000 concurrent 1:1 calls at peak
Bandwidth per call leg (adaptive, standard quality): audio ≈ 24–64 kbps (Opus), video ≈ 500 kbps–1 Mbps (VP8/H.264) per direction
Most calls connect P2P directly (ICE succeeds); assume ≈25–30% require a TURN relay (symmetric NAT / restrictive firewalls):
Relayed concurrent calls = 375,000 × 30% ≈ 112,500 calls
Server bandwidth/relayed call (2 legs × in+out × ≈700kbps avg) ≈ 2.8 Mbps
Total TURN relay bandwidth = 112,500 × 2.8 Mbps ≈ 315 Gbps sustained at peak

This is the number that justifies why WebRTC systems fight hard to make P2P (via STUN/ICE) succeed as often as possible — every percentage point pushed off TURN relay saves real, very expensive, server bandwidth (see Detailed Design — Audio/Video Calling, below).

Real-world detail
The 24–64 kbps audio figure above isn't arbitrary — it matches the real Opus codec, which WhatsApp calling actually uses. Opus is royalty-free (important at billions-of-users scale, where per-user codec licensing would be a real cost line item), was purpose-built for low-latency voice-over-IP, and produces speech-quality audio at a fraction of the bitrate of older codecs like MP3. WhatsApp's calling stack also reportedly borrows pieces of the open-source WebRTC voice engine — acoustic echo cancellation, automatic gain control, and noise suppression — rather than reinventing them, a good example of building on proven RTC building blocks instead of a from-scratch media stack.

High-Level Design

Two planes share the same auth/identity layer but are otherwise mostly independent: a Messaging plane (store-and-forward) and a Calling plane (real-time media, mostly not touching application servers once a call is set up). Keeping this split explicit in your head — and on the whiteboard — is the single most useful framing device for this problem, because it explains almost every subsequent design decision: why messaging optimizes for durability and calling optimizes for latency, why calling needs STUN/TURN and messaging doesn't, and why both still share identity, key management, and push notifications.

Detailed Design — Messaging

This section walks the message from the moment a client hits "send" through delivery, receipts, presence, offline queuing, group fan-out, and media handling. Each subsection maps to one concrete design decision an interviewer is likely to probe.

Delivering messages: push vs. pull

A client can either poll the server (pull) or keep a connection open and let the server push (push). Pull wastes resources (mostly-empty polls) and adds latency; push (WebSocket / HTTP long-polling) gives near-instant delivery and no wasted polling, at the cost of holding one open connection per active user. WhatsApp/Messenger-style systems use push as the primary path, and pull only as a fallback/catch-up mechanism for reconnecting or new devices.

Connection routing

Each chat server keeps an in-memory hash table: UserID → connection object. A software load balancer / connection directory maps UserID → which physical chat server currently owns that user's socket (since a user can reconnect to any server behind the LB). To deliver a message, the sender's server looks up the recipient's owning server (via the directory, often backed by a fast in-memory store like Redis) and forwards the message to it over an internal RPC; that server then writes it to the live socket.

Delivery state machine — the "ticks"

The tick progression is one of the most user-visible parts of the whole design, and it's a clean three-state machine driven entirely by acknowledgments flowing back through the server.

StateTriggerClient visual
SENT (single tick)Server receives the message from sender and durably ACKs it✓
DELIVERED (double tick)Recipient device receives the message and sends a RECEIVE_ACK back to the server, which relays it to the sender✓✓
READ (blue double tick)Recipient opens the conversation and sends a READ_ACK✓✓ (blue)
Figure 2. The delivery-state machine: each transition is driven by an acknowledgment flowing back through the server, not by the server unilaterally guessing state.

Read receipts are a per-user, per-message setting — the client also needs to let users disable read receipts, which turns off blue ticks bidirectionally.

Presence / last-seen

Clients send a lightweight heartbeat on an interval (e.g., every 25–30s) over the open socket. The chat server updates an in-memory + periodically persisted "last active timestamp" for that user. On disconnect (socket close/timeout), the server flips the user to offline and stamps the last-seen time. To avoid a storm of status broadcasts at 500M-user scale:

  • Clients pull the current status of their contacts once on app start, not continuously.
  • Status changes are broadcast only to users actually viewing/interested in that contact (e.g., open chat, contact list on screen), with a short debounce (a user going offline for 2 seconds and back shouldn't spam a status change).
  • Stale offline status is acceptable for a few seconds — this is an explicit availability/consistency trade-off.

Offline delivery

Offline delivery is what actually guarantees the "no message loss" non-functional requirement — the server, not the recipient's device, is the durable source of truth.

  1. User1 sends a message addressed to User3.
  2. User3's owning chat server has no live socket for User3 (offline) → message is durably written to the Message Store, marked PENDING for User3, and (optionally) a push notification is triggered.
  3. When User3 reconnects, their client (or the server, proactively) triggers a pull of pending messages since their last known message id/sequence.
  4. Server returns queued messages in order; client ACKs; ticks now progress to DELIVERED, then READ.

Group messaging

Group chat reuses the same delivery machinery per-recipient, with a dedicated Group Handler resolving membership up front.

  1. Client sends {message, group_id} to its chat server.
  2. The Group Handler resolves group_id → member list (from the Group/Member DB, cached).
  3. For each member, the handler finds their owning chat server (via the connection directory) and forwards the message; each server delivers to online members and persists for offline ones.
  4. Delivery/read receipts in groups are aggregated (e.g., "read by N of M") rather than one tick per recipient shown inline, to keep the UI and the write load manageable.

Group chat objects are modeled separately (GroupChatID, member list, admins) and stored partitioned by GroupChatID so all messages/metadata for a group co-locate.

Media messages

Media never travels inline with the chat message — it flows through a dedicated upload/transcode path and is referenced by a small UID, keeping the hot messaging path lightweight.

  1. Client transcodes locally to a standard format/resolution where possible (saves bandwidth, normalizes playback).
  2. Client uploads the media blob to the Media Service, which stores it in object storage and returns a media UID + CDN URL.
  3. The actual chat message only carries the UID/thumbnail/small metadata — not the raw bytes — keeping the hot messaging path lightweight.
  4. Recipient's client fetches the full media from the CDN using the UID, lazily / on demand.
  5. If the client can't transcode (e.g., a thin/browser client), the server-side Media Service transcodes HD → standard quality on upload.

Detailed Design — Audio/Video Calling

Calling is the second half of the system, and it is architecturally almost a mirror image of messaging: instead of durably storing and forwarding small payloads, it tries to get out of the data path entirely as fast as possible and hand control to a direct connection between the two devices.

Why calling is architecturally different from chat

Text messages are small, must not be lost, and can tolerate a store-and-forward hop through the server. Call media is large, continuous, latency-critical, and can tolerate loss (a lost video frame is just briefly ugly). So calling optimizes for the lowest possible round-trip media path — ideally peer-to-peer — and uses the server only for signaling and, when unavoidable, relaying.

Call setup / signaling flow (1:1)

The signaling exchange is entirely out-of-band from the eventual media path — its only job is to help two clients discover each other's network reachability and agree on codecs before handing off to a direct connection.

  1. Caller sends callInitiate to the Signaling/Ring service with the callee id and an SDP offer (codecs, media capabilities) plus its discovered candidate addresses.
  2. Ring service pushes a RINGING event to the callee's owning chat/signaling connection (same connection-directory mechanism as messaging) and, if the callee's app isn't foregrounded, a high-priority push notification (VoIP push) to wake it.
  3. Callee's client gathers its own ICE candidates (host, server-reflexive via STUN, relay via TURN) and returns an SDP answer + candidates if accepted.
  4. Both sides run ICE connectivity checks across candidate pairs; the best-working pair is selected (direct P2P if possible, else relayed through TURN).
  5. Media flows directly between clients (SRTP) once a path is established; the signaling server drops out of the media path entirely for a successful P2P call.
  6. Either side can hang up, or the call can time out (no answer) / be rejected / return busy — all communicated back over the signaling channel.
Figure 3. 1:1 call setup: signaling exchanges SDP/ICE through the Ring Service, then media (SRTP) establishes directly between caller and callee once ICE connectivity checks succeed.

NAT traversal: STUN, TURN, ICE

Almost every real device sits behind some form of NAT, so a client cannot simply hand its local IP address to a peer and expect a connection — NAT traversal machinery is what makes P2P calling possible at all.

MechanismRole
STUNLightweight server that tells a client its public IP:port as seen from the internet, so it can share a usable address with the peer (works when NAT is a simple cone NAT).
TURNA relay server that forwards media when a direct path can't be established (symmetric NAT, restrictive corporate firewalls). Correct but expensive — it consumes real bandwidth for every relayed byte, in both directions, for the whole call.
ICEThe overall framework: gather candidates (host / STUN / TURN), exchange them via signaling, try pairs in priority order (direct first), and pick the best working path.

During the call, clients keep sending bandwidth/quality telemetry to the ring/media service; video quality (resolution/bitrate) is renegotiated up or down mid-call based on measured loss/RTT/jitter — this is why a video call sometimes visibly drops to a lower resolution under poor network conditions instead of freezing or disconnecting.

Media topology: P2P vs. SFU vs. MCU

Once more than two participants are on a call, the question of who forwards media to whom becomes the central design decision, with three well-known topologies trading off server cost, latency, and client bandwidth very differently.

TopologyHow it worksBest forTrade-off
Mesh / P2PEvery participant connects directly to every other participant1:1 calls, or very small groups (2–4)Zero server media cost and lowest latency, but each client's upload bandwidth scales with (N-1) — breaks down fast as group size grows
SFU (Selective Forwarding Unit)Each client sends one stream up to the SFU; the SFU forwards (does not decode/re-encode) copies to every other participantSmall/medium group calls (WhatsApp/Zoom-style, up to ≈8–50)Server needs bandwidth, but not heavy CPU (no transcoding); scales much better than mesh; still N-1 download streams per client unless simulcast/selective relay is used
MCU (Multipoint Control Unit)Server decodes every incoming stream, composites/mixes into a single combined stream, and sends one stream per participantLegacy conferencing, thin clients, recording/composited layoutsVery CPU-heavy (decode+composite+encode per participant) and adds latency; simplifies the client though
Figure 4. Media topology comparison: mesh scales media cost with N-1 per client, an SFU relays without transcoding, and an MCU trades heavy server CPU for a simpler client.

WhatsApp/Zoom-style group calls use an SFU: each participant uploads once; the SFU relays; each client downloads N-1 streams (mitigated with simulcast — clients send multiple quality layers and the SFU forwards only what a given receiver's bandwidth allows, plus "active speaker" logic that only forwards video for the last few speakers instead of every tile in a large call).

Group video call flow

  1. First participant to start a group call creates a "call room" on a chosen SFU node (ring service picks based on region/load).
  2. Each subsequent joiner is signaled the SFU node/address to connect their media to; signaling still flows through the ring service for join/leave/mute events.
  3. SFU forwards each participant's audio/video to every other participant; clients render tiles.
  4. SFU (or client, via simulcast) adapts per-recipient quality to that recipient's real-time bandwidth — a participant on poor Wi-Fi gets a lower-res stream without affecting others.
  5. If a participant's connection drops, the SFU stops forwarding their stream and signals a participant-left event; others are unaffected (no single point of mesh failure).

Call edge cases to mention in an interview

  • Ringing timeout — auto-cancel and notify caller after N seconds of no answer.
  • Busy / declined — immediate signal back, optionally offer to leave a voice message / send a text.
  • Simultaneous call collision — both users call each other at once; deterministic tie-break (e.g., lower user id "wins" and the other call is auto-declined).
  • Network handoff mid-call — Wi-Fi ↔ cellular switch; ICE restart re-negotiates a path without tearing down the whole call.
  • Missed call notification — stored + pushed like an offline message.

End-to-End Encryption

Both chat and calls are end-to-end encrypted using a Signal-Protocol-style scheme: the server relays ciphertext and call media (SRTP) but cannot decrypt either. This is not just "a" protocol inspired by Signal — it is worth naming explicitly in an interview, because it is one of the most concrete, verifiable facts about how WhatsApp's real production system actually works.

Real-world detail
In November 2014, Open Whisper Systems (the organization behind the Signal messenger, later reorganized as the Signal Foundation) announced a partnership with WhatsApp to integrate the actual Signal Protocol — the same X3DH + Double Ratchet design described below — into every WhatsApp client. The rollout was staged: Android first, then other platforms and group/media messages. On April 5, 2016, WhatsApp and Open Whisper Systems jointly announced the rollout was complete across every client platform and every form of communication — individual chats, group chats, attachments, voice notes, and voice calls — putting well over a billion monthly users on the Signal Protocol at once, likely the largest single deployment of end-to-end encryption in consumer software history at that time.

Session bootstrap — X3DH

  • Each device generates and uploads to the Key Service: a long-term Identity Key (IK), a medium-term Signed Pre-Key (SPK), and a batch of one-time Pre-Keys (OPKs) — all using elliptic-curve cryptography (e.g., Curve25519).
  • To start a session, the sender fetches the recipient's key bundle from the server and performs a handful of Diffie-Hellman computations (combining identity + ephemeral + pre-keys) to derive a shared secret — all without either party being online at the same time.

Ongoing messages — Double Ratchet

  • A Diffie-Hellman ratchet advances a "root key" whenever a new message round-trip introduces a fresh DH exchange.
  • A symmetric-key (hash) ratchet derives a unique per-message key from the current chain key, then advances the chain — so every single message uses a distinct key.
  • Result: forward secrecy (compromising a later key doesn't expose earlier messages) and post-compromise security (the session self-heals as new DH ratchet steps occur).
Figure 5. Simplified session bootstrap and Double Ratchet: X3DH establishes a shared root key using pre-published key bundles, then a hash ratchet derives one unique key per message on each side while the server only ever relays opaque ciphertext.

Calls

Call media uses SRTP with keys derived via a similar DH exchange carried over the (already encrypted-in-transit) signaling channel, so the server — including any TURN relay it operates — only ever sees encrypted media bytes to forward.

Group chat encryption

Group messaging typically uses a "sender key" scheme: each member generates a symmetric sender key and distributes it 1:1 (encrypted) to every other member via their pairwise sessions; subsequent group messages are encrypted once with the sender key rather than once per recipient, which is far cheaper at scale.

Database Schema

The schema splits cleanly into two very different workloads: a durable message store optimized for high write-rate and range scans, and relational metadata (users, groups, devices, keys) that is small and changes rarely. Trying to force both into the same storage engine is a common interview misstep worth calling out explicitly.

Messages (wide-column store — e.g., HBase/Bigtable/Cassandra-style)

Rationale: we need very fast small writes (every message is an insert) and fast sequential range reads ("give me the last 50 messages of this conversation"). A row-store RDBMS or a document NoSQL store forces either a slow row read/write per message or extra index maintenance; a wide-column store buffers writes in memory and flushes in bulk, and is built to scan ranges by key prefix efficiently.

Message ordering

A single server-received timestamp is NOT sufficient to order messages consistently for both participants, because two messages sent "simultaneously" in each direction can be delivered to the two users in different orders relative to their own send. The fix: keep a separate, monotonically increasing sequence number per recipient. Each user then sees a consistent, strictly increasing order of the messages addressed to them — the two users' views of the same conversation are internally consistent even if not byte-identical in global order.

Data Sharding

Sharding is the single decision that most determines whether "fetch my recent chat history" stays a fast, single-node operation or turns into an expensive scatter-gather across the cluster — and the right axis to shard on follows directly from the read pattern, not from where data happens to be generated.

Shard by UserID (chosen approach)

Hash(UserID) → shard, so all of a user's conversations/messages live on one logical shard.

Assumption ≈3.6 PB of 5-year message history, ≈4 TB per shard
Number of shards ≈ 3.6 PB ÷ 4 TB ≈ 900 shards — round to 1,000 for headroom

This makes "fetch my recent chat history" a single-shard operation — fast. Start with more logical shards than physical machines (e.g., 1,000 logical shards on a handful of physical boxes) and remap logical→physical as data grows, without having to re-hash user IDs later.

Figure 6. Sharding by UserID: hash(UserID) selects one physical shard, and all of that user's conversations and group memberships co-locate there, making "load my recent chats" a single-shard read.

Why not shard by MessageID

If a single conversation's messages are scattered across shards by message id, fetching a contiguous range of a conversation's history requires fanning out to many shards and merging — exactly the operation we do most often, so this is the wrong axis to shard on for a messaging system (contrast with Twitter's TweetID sharding — a different access pattern, covered in the companion Facebook/Twitter feed design).

Group chats

Stored in a separate table/keyspace partitioned by GroupChatID, since a group's messages are most often accessed together and a group's member list must be resolved as a unit for fan-out.

Caching

Caching in this system leans heavily on the fact that conversations are already co-located by the sharding scheme above, which makes cache placement and invalidation almost trivial compared to a system with cross-shard access patterns.

  • Cache the last ≈15 messages of the last ≈5 open conversations per active user — covers the "user just opened the app" hot path.
  • Because messages for a user are shard-co-located, that user's cache also naturally lives on one cache node — simplifies invalidation.
  • Presence/last-seen is itself effectively an in-memory cache (kept in the chat server / a fast store like Redis), rarely hitting durable storage.
  • Media is cached at the CDN edge, not in the application cache tier.

Replication and Fault Tolerance

Failure handling differs sharply between the two planes: messaging failure recovery leans on durable storage and client reconnect, while calling failure recovery leans on the fact that in-flight media can simply be lost and re-established without violating any correctness guarantee.

Chat server failure

Chat servers hold live TCP/WebSocket connections — failing over an established TCP connection to another box is impractical. Instead: clients detect the drop and automatically reconnect (with jittered backoff) to any healthy server via the load balancer; on reconnect the client pulls anything it missed since its last known message id. Any message that was accepted by the server before it died is durable in the Message Store, so nothing is lost — only a brief reconnect blip is visible.

Message durability

Never keep only one copy of a user's messages. Replicate each shard (e.g., 3-way replication across racks/AZs) or use an erasure-coding scheme (e.g., Reed-Solomon) to tolerate node/AZ loss with less storage overhead than full replication.

Calling infrastructure

  • TURN/SFU nodes are stateless per-call — if one dies mid-call, the affected call drops and clients can attempt an ICE restart / rejoin against a healthy node; it does not corrupt other calls.
  • Signaling servers are horizontally replicated behind the load balancer just like chat servers; a call in the RINGING state that loses its signaling connection can retry against another node.
  • Deploy STUN/TURN/SFU points-of-presence regionally so most call legs stay geographically close, reducing both latency and cross-region relay bandwidth cost.

Multi-region

Route users to their nearest region for chat servers and calling infra (latency); replicate message data cross-region asynchronously for disaster recovery, accepting eventual consistency for the (rare) cross-region failover case.

Load Balancing

Load balancing here is more than "spread requests evenly" — the messaging path specifically needs connection-aware routing, since a plain round-robin balancer has no way to know which physical server currently owns a given user's live socket.

  • Client → Chat servers: a connection-aware LB (or a directory service backed by Redis) maps UserID → currently-owning server, since plain round-robin would break "which box holds this user's socket" routing.
  • Chat servers → Message DB: requests are already sharded by UserID, so the DB-side LB is really just "route to the shard that owns this hash."
  • Signaling → SFU/TURN pool: assign call rooms to the least-loaded, closest-region node; rebalance new joins away from hot nodes.

Security & Abuse Prevention

Because message content is end-to-end encrypted, abuse prevention here looks meaningfully different from a typical server-side content-moderation pipeline — the server is largely blind to payloads and must rely on metadata, rate limits, and user reporting instead.

  • TLS for all client↔server transport; end-to-end encryption for message/call content on top of that (defense in depth — the transport layer protects metadata/signaling even though payload is already E2E encrypted).
  • Rate limiting per account/device on message sends and call attempts to blunt spam and robocalling.
  • Device/session revocation — linking a new device re-runs key exchange; removing a device invalidates its session and future messages simply won't decrypt for it.
  • Report/block pipeline; since content is E2E encrypted, abuse handling relies on user reports (reported message + limited context submitted voluntarily by the reporter) rather than server-side content scanning.
  • Media/link scanning happens client-side or on the sender's own device where possible, to avoid requiring server access to plaintext.

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design. The guidance below is expanded into fuller reasoning rather than a one-line prompt — use it to rehearse how you'd actually talk through each follow-up out loud.

Messaging depth

How do you support multi-device sync (same account on phone + web + desktop)?
Model each device as its own connection endpoint with its own key bundle and its own place in the connection directory, rather than treating "the user" as a single socket. When a message arrives for that user, the server fans it out to every currently-active device, not just one, and each device tracks its own per-device sequence number and ack state so its view stays internally consistent even if another device is offline or lagging. The trade-off is that group fan-out and per-message encryption both now scale with number-of-devices rather than number-of-users, which is exactly why the sender-key scheme for group chats and per-device session bootstrap in the Key/Encryption Service matter at scale.
How would you reduce the number of chat servers needed?
The lever is connections-per-box, not clever sharding, since the fleet size in this design is dominated entirely by that ratio (500 vs. 10,000 servers in the capacity estimate above). Practically, that means an event-driven runtime with cheap per-connection state (an actor model like Erlang, or an epoll/kqueue-based event loop in a language like Rust or Go) instead of a thread-per-connection model, plus OS-level tuning of file-descriptor limits and socket buffers. Fewer, bigger boxes also reduce inter-box hops and coordination overhead in the connection directory, which is a second-order win beyond the raw server count.
How do you guarantee exactly-once delivery given retries?
Push the idempotency key to the client: every send carries a client-generated client_msg_id, and the server treats a resend with the same key as a no-op rather than a new message, simply re-returning the original ack. This matters because clients will legitimately retry after a timeout even when the original send actually succeeded (an "ack that got lost," not a "message that got lost"), and without a stable idempotency key those retries would silently duplicate messages in the recipient's history.
How would you implement "message disappears after 7 days" (disappearing messages)?
Attach a TTL to the message row at write time and let the wide-column store's native TTL/compaction expire it automatically, rather than running an application-level sweep job. This is one of the reasons a wide-column store is such a good fit here beyond raw write throughput — TTL-based expiry is a first-class, low-overhead feature in stores like Cassandra/Bigtable, whereas bolting equivalent behavior onto an RDBMS would mean a recurring DELETE job competing with live write traffic.
How do you paginate very long chat histories efficiently?
Use a range scan keyed by the row key (conversation_id) with a bounded page size and a cursor equal to the last message_id the client has already seen, never an OFFSET-style "skip N rows" pagination. OFFSET pagination gets progressively slower the deeper a user scrolls because the store still has to walk past every skipped row, while a cursor keyed on a monotonic column qualifier lets the wide-column store seek directly to the right position regardless of how far back the user scrolls.

Calling depth

Why can't we just always use a TURN relay and skip P2P complexity?
Cost and latency, and the capacity estimate makes the cost concrete: at ≈375,000 peak concurrent calls, relaying all of them instead of the assumed 30% would roughly triple the ≈315 Gbps TURN bandwidth figure to something close to 1 Tbps sustained, which is an enormous, permanently-provisioned expense. On top of the raw bandwidth cost, a relay adds an extra hop's worth of round-trip latency versus a direct path, which is directly perceptible as call lag — so P2P-first with ICE is both cheaper and better for the user whenever it can succeed.
How do you handle a participant joining a large group call efficiently?
Combine simulcast with active-speaker selection: each client encodes and uploads multiple quality layers of its own video simultaneously, and the SFU forwards only the layer (and, for video specifically, only the tiles of the handful of currently active speakers) that a given receiver's bandwidth and screen layout actually need. This avoids the naive "every participant downloads full-quality video from every other participant" cost, which would make an SFU's download bandwidth scale linearly and unsustainably with group size.
How would you add call recording?
An SFU-side (or MCU-side) recorder subscribes to the call like any other participant, decrypting and writing either the composed stream or each individual stream to storage. The important thing to flag out loud is the trade-off this introduces with true end-to-end encryption: the moment a server-side component can decode media for recording, the server is no longer cryptographically blind to call content, which is exactly why WhatsApp/Signal-style apps that market themselves as E2E-encrypted generally avoid offering server-side call recording as a first-party feature.
How do you detect and react to poor network quality mid-call?
Continuous RTCP-style telemetry (packet loss, jitter, round-trip time) feeds a bitrate-adaptation control loop that steps video resolution/bitrate up or down in near real time, which is why a call visibly drops to a blockier picture instead of freezing when a network briefly degrades. If loss stays severe for long enough, the same control loop can trigger an automatic fallback from video to audio-only, trading the richer experience for keeping the call alive at all.
How would you scale to webinar-style 1-to-many broadcast (thousands of viewers)?
Treat it as a genuinely different problem rather than a bigger SFU: a single SFU forwarding unicast streams to thousands of viewers doesn't scale the way it does for an 8-50 person call, so the right architecture looks more like CDN-style live-streaming fan-out (HLS/LL-HLS) or a broadcast-tree of SFUs, trading some latency for near-unbounded viewer scale. Calling this out explicitly signals to an interviewer that you understand the SFU model has a real ceiling, not an unlimited one.

Reliability / security depth

What happens if the Key Service is compromised?
Because private keys never leave the originating device, a breach of the Key Service exposes only public keys and metadata — identity keys, signed prekeys, and one-time prekeys that were always meant to be shared — not any message content. That said, it's worth explicitly naming what metadata is still exposed even under perfect E2E encryption: who talks to whom, how often, and roughly when, since none of that is protected by the Signal Protocol itself and is a genuine, often-overlooked privacy surface.
How would you detect and mitigate spam/abuse without reading message content?
Lean entirely on behavioral and metadata signals rather than content: send-rate anomalies per account/device, unusually high fan-out to strangers who never replied, and rapid-fire messaging to many brand-new contacts in a short window are all strong spam signals that require zero visibility into plaintext. Combine that with user-driven reporting (a user voluntarily shares a flagged message and limited context with a trust-and-safety pipeline) as the fallback path for anything the behavioral signals miss.
How do you avoid a single celebrity/broadcast-list send overwhelming the system?
Treat it as the same group-fan-out problem taken to an extreme, and apply the same mitigations at a larger scale: cap broadcast-list/group size at a sane ceiling, and fan out asynchronously through a queue rather than synchronously per recipient inside the request path, so a single sender's send doesn't block on thousands of individual deliveries completing before the API call returns.
How would you support message search across a user's history?
Build a secondary search index (e.g., Elasticsearch) fed by a change-data-capture stream off the message store, keeping it clearly separate from the primary durable path so a search-index outage never affects message delivery. The subtlety worth raising unprompted is that this index has to be built and searched client-side, or over data the client itself decrypted and indexed locally, since the server-side CDC stream only ever has access to the same opaque ciphertext everything else does — "search over encrypted data" is a deep sub-topic in its own right and a good signal that you're thinking past the obvious answer.

Key Takeaways

Remember
Frame this system as two planes sharing one identity layer: a store-and-forward messaging plane that optimizes relentlessly for no data loss (durable writes, per-recipient sequence numbers, client auto-reconnect), and a real-time calling plane that optimizes for the lowest-latency media path (P2P-first via ICE, SFU for groups, tolerating packet loss). Every capacity number should visibly drive a design choice — the 500K–10,000 server spread for chat servers justifies the OS/runtime-tuning conversation, and the ≈315 Gbps TURN estimate justifies why P2P success rate is treated as a first-class metric, not an afterthought. Shard by UserID, not MessageID, because conversation history is read as a contiguous range far more often than any single message is looked up in isolation. End-to-end encryption via the real Signal Protocol (X3DH + Double Ratchet) means the server is a durable, replicated relay for ciphertext it cannot read — which in turn reshapes abuse prevention, search, and even call recording into metadata-and-behavior problems rather than content-scanning problems. Know your alternatives at every decision point (push vs. pull, wide-column vs. RDBMS, SFU vs. mesh vs. MCU, UserID vs. MessageID sharding) since "why not X instead?" is close to guaranteed as a follow-up.
