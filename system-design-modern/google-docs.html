SYSTEM DESIGN

Designing Google Docs — Real-Time Collaborative Editing

A complete, interview-ready design walkthrough: requirements, capacity estimation, the WebSocket operation contract, data model, architecture, the Jupiter model of centralized Operational Transformation, real-time transport, CRDT-assisted rich formatting, presence and offline reconciliation, sharding, fault tolerance, and follow-up interview questions.

Problem Statement

Design a real-time collaborative document editor — a system like Google Docs — where many users can open the same document and type into it simultaneously, and every collaborator's screen converges on the exact same final content. The core hard problem is concurrency: two people can press keys at nearly the same instant, each starting from the same version of the document, and the system has to reconcile both edits into one coherent, shared result without losing a single keystroke and without requiring either user to wait for the other before they can keep typing.

The experience bar is high and mostly invisible when done well: a keystroke must feel instantaneous to the person typing it (no perceptible lag, no lock icon, no "someone else is editing — please wait"), and it must show up on every other open collaborator's screen within a sub-second window. Comparable real systems include Google Docs, Sheets and Slides, Microsoft 365 co-authoring, Notion, and Figma's multiplayer canvas.

Why does this problem matter in an interview?

It is one of the few system-design prompts where the interesting problem is concurrency and correctness rather than raw scale. It rewards candidates who can reason precisely about what it means for two edits to conflict and how the system guarantees every replica converges, rather than candidates who jump straight into sharding a database.

Why is this categorically different from a typical CRUD system?

  • Most systems assume writes are naturally serialized by the client or that the last writer simply wins; here, concurrent writers are the normal case, not the exception.
  • The unit of correctness is not "the row was updated" but "every replica's document state provably converges to the same bytes," even though different clients observe events in different orders and at different times.
  • Latency requirements are asymmetric and strict: the local echo of your own keystroke must be instant, while global convergence across collaborators only needs to be fast (sub-second), not synchronous.

Clarifying Questions to Ask the Interviewer

Always narrow the problem before designing. Spend the first few minutes on scope, not on drawing boxes.

  1. Should the editor support plain-text collaboration only, or also rich formatting, tables, images, and comments?
  2. Do we need to support fully offline editing (extended periods with no network), or just brief connectivity blips?
  3. What is the expected maximum document size, and how far back does version/revision history need to reach?
  4. How many simultaneous editors do we need to support on a single document — a handful of teammates, or hundreds on a viral public doc?
  5. Are live cursor positions and collaborator presence (who's online, where they're typing) in scope for this design?
  6. Do we need granular sharing permissions (owner/editor/commenter/viewer), or is "anyone with the link can edit" acceptable for a first version?
  7. Should edits be attributed per user in history for audit and undo, or is a single merged history acceptable?
  8. Is this a single-region deployment, or does it need to support globally distributed editors with low latency everywhere?
  9. Do we need a suggestion/track-changes mode, or is direct editing the only mode in scope?
  10. What end-to-end latency budget is acceptable from one user's keystroke to another collaborator seeing it?
Interview tip
Don't stall waiting for every answer — state a reasonable assumption out loud ("I'll assume rich formatting is in scope but comments are extended-only, offline editing must be supported, and we're targeting tens of simultaneous editors per document") and keep moving. That shows judgment, not indecision.

Requirements and Goals

Functional Requirements

  1. Any number of users can open the same document and edit it concurrently; all edits must converge to one identical final document across every replica.
  2. Live cursor position and basic presence (who is currently viewing or editing) are visible to every collaborator in real time.
  3. The document keeps a version/revision history that can be inspected and, in a fuller build, restored.
  4. A client that goes offline can keep editing locally; on reconnect, its queued edits are reconciled against everything that happened while it was disconnected, with no edits silently dropped.
  5. (Extended) Documents can be shared with specific collaborators at different permission levels.
  6. (Extended) Collaborators can leave comments and use a suggestion/track-changes mode without directly mutating the canonical text.

Non-Functional Requirements

  1. Low-latency propagation of keystrokes — feels instant to the typer, near-instant to others.
  2. Strong eventual consistency — every replica converges to the same document state, regardless of the order in which operations were observed.
  3. Availability over strict consistency during a network partition — a disconnected collaborator keeps typing locally rather than being blocked; full convergence waits for reconnection.
  4. Durability — once an operation is acknowledged as committed, it must never be lost, even if the authoritative server crashes immediately afterward.
  5. Horizontal scalability — both in the number of concurrently active documents and in the number of simultaneous editors on any single hot document.

Extended / Out-of-Scope

We'll go deep on the operational-transform core — real-time edit propagation, ordering, and convergence guarantees — and touch on presence, history, and offline reconciliation. We explicitly call out, but don't build in depth, a full comment/suggestion-mode workflow (a parallel annotation layer with its own resolve/accept lifecycle) or a granular permission model (owner/editor/commenter/viewer ACLs) — both are real, sizable sub-systems in the actual product but orthogonal to the core convergence problem this design focuses on.

Capacity Estimation and Constraints

Assume a large collaborative-editing user base: hundreds of millions of documents exist, and only a small fraction of them are actively co-edited at any given moment — but the ones that are can have tens of simultaneous editors during a live session (a company all-hands notes doc, a shared classroom worksheet, a viral publicly-editable doc).

System / API Design

The write path is a persistent, bidirectional WebSocket contract rather than a request/response REST call — operations must be ordered and broadcast continuously, which a stateless HTTP call cannot do efficiently.

Submitting an Operation (Client → OT Server)

WS message, client -> server
{
  "type": "submit_op",
  "doc_id": "doc_9f3ac2e1",
  "client_id": "client_4471",
  "base_revision": 128,
  "op": [
    { "retain": 42 },
    { "insert": "collaborative " },
    { "retain": 908 }
  ]
}

Committed Operation Broadcast (Server → Every Collaborator)

WS message, server -> every connected client (including the sender)
{
  "type": "committed_op",
  "doc_id": "doc_9f3ac2e1",
  "revision": 129,
  "client_id": "client_4471",
  "op": [
    { "retain": 42 },
    { "insert": "collaborative " },
    { "retain": 908 }
  ],
  "server_ts": "2026-07-19T14:02:11.483Z"
}

Stale Revision → Catch-Up Required

WS message, server -> client (client's base_revision is behind current_revision)
{
  "type": "reject_stale_revision",
  "doc_id": "doc_9f3ac2e1",
  "client_current_base": 128,
  "server_current_revision": 131,
  "missing_ops": [
    { "revision": 129, "op": [ "..." ] },
    { "revision": 130, "op": [ "..." ] },
    { "revision": 131, "op": [ "..." ] }
  ]
}
// Client transforms its pending local op(s) against missing_ops, then resubmits with base_revision = 131

Opening a Document (REST — Snapshot + Catch-Up)

GET /api/v1/docs/{doc_id}/open

Response 200:
{
  "doc_id": "doc_9f3ac2e1",
  "snapshot_revision": 100,
  "snapshot_ref": "gs://doc-snapshots/doc_9f3ac2e1/rev-100.snap",
  "ops_since_snapshot": [ { "revision": 101, "op": ["..."] }, "...", { "revision": 128, "op": ["..."] } ],
  "current_revision": 128
}
// Client loads the snapshot, replays only the ops since that snapshot, then opens the live WebSocket at base_revision = 128
Interview tip
The base_revision field is the load-bearing piece of this whole contract — it's exactly how the server knows which already-committed operations a newly-submitted op needs to be transformed against before being assigned the next revision number.

Data Model and Database Schema

Nature of the Data

  • Two very different access patterns living side by side: a tiny, frequently-updated pointer record per document (current_revision, snapshot_ref), and a huge, append-only, sequential log of every operation ever applied.
  • The operation log is written once and never updated — a natural fit for an append-only, log-structured store — and is read sequentially by revision far more often than it is read randomly.
  • The document pointer record, by contrast, is read constantly (every open, every reconnect) and updated on every single committed operation, so it benefits from being small and cacheable in memory on the OT server that owns that document's shard.

Database Choice

The operation_log table's access pattern — append-only, partitioned by doc_id, read back sequentially by increasing revision — is the textbook case for a wide-column / log-structured store. The document pointer table is small, hot, and needs strict consistency on current_revision, since it's effectively the watermark the OT server checks on every incoming operation, which favors a strongly-consistent store co-located with (or cached in memory by) the OT server owning that shard.

High-Level Design

Clients hold open a persistent WebSocket connection into a Collaboration / OT Server tier. Each server in that tier is the single source of truth for operation ordering on whichever documents it currently holds authority over — every operation for a given doc_id is funneled through exactly one authoritative server at a time. Committed operations are appended to a durable Operation Log store, and a background process periodically compacts the log into a Snapshot, so a newly-opened document loads by fetching the latest snapshot plus a short tail of recent ops rather than replaying the document's entire history from revision zero.

Figure 1. High-level architecture — clients hold a persistent WebSocket into the Collaboration/OT Server tier, which commits ordered operations to a durable Operation Log and periodically compacts history into Snapshots for fast document loads.

Key Design Principles Reflected in the Diagram

  • Sticky, per-document authority: a document's ordering must be decided by one server at a time, so client connections for that doc are routed to whichever shard currently owns it (see Load Balancing below).
  • Durability is decoupled from serving latency: an operation is acknowledged once committed to the Operation Log, not once every collaborator has received the broadcast.
  • Snapshots are a pure performance optimization, not a correctness requirement: the log alone is always sufficient to reconstruct any revision; the snapshot just avoids replaying it in full on every open.

Low-Level Design

Walk through the moment two users type at nearly the same instant — this is the core mechanic the entire design exists to support.

Figure 2. Core concurrent-edit flow — two clients optimistically apply their own keystrokes locally; the OT server assigns a total order and transforms the second op against the first, then broadcasts both transformed ops to every collaborator so all replicas converge.
  1. User A and User B each have the document open at revision N and type at nearly the same instant.
  2. Each client optimistically applies its own keystroke to its local in-memory document immediately — the typer never waits on the network.
  3. Each client ships its operation to the OT Server as {doc_id, base_revision: N, op}.
  4. The OT server, which processes one document's incoming operations one at a time, picks whichever operation arrives first (say A's) and commits it unchanged as revision N+1.
  5. B's operation was authored against revision N but must now sit on top of revision N+1, so the server transforms B's op against A's already-committed op — producing an equivalent op that preserves B's intent while accounting for A's change — and commits it as revision N+2.
  6. The server broadcasts both committed operations to every connected collaborator, including A and B themselves.
  7. A's client applies B's transformed op on top of its own local state; B's client applies its own server-transformed op (replacing its speculative local version) plus A's op. Every client ends up with byte-identical document state, regardless of which raw keystroke physically happened first.

Deep Dive — The Jupiter Model: Centralized Operational Transformation

Google Docs' real, documented architecture is commonly referred to as the "Jupiter model," named after a 1995 collaborative system (Nichols, Curtis, Dixon, and Lamping) that first described this specific centralized-OT architecture. The key simplifying move: rather than a fully peer-to-peer OT system, where every client must be able to transform its operations against every other client's concurrent operations — a combinatorial explosion of transform-function cases as the number of simultaneous editors grows — a single central server defines the one canonical ordering of all operations for a given document.

Two Streams, Not Every Pairwise Combination

Under this model, each client only ever has to reason about two operation streams: its own pending local operations (not yet acknowledged by the server) and the stream of already-ordered operations arriving from the server. The server, symmetrically, only has to transform each client's incoming operation against server history — never against another client's operations directly, and never against another client's in-flight, not-yet-ordered operation.

Why This Collapses Complexity

In a fully peer-to-peer OT system with N simultaneous editors, a naive design needs to reason about transform interactions across pairs (and higher-order combinations) of concurrently in-flight operations from every client — complexity that grows sharply with N. Under the Jupiter model, the transform function only ever needs to handle "my pending op versus the server's next committed op(s)," a fixed, small problem regardless of how many other collaborators are connected. This is the single biggest reason the centralized model is what actually shipped in production, rather than a theoretically more symmetric peer-to-peer design.

What each client must transform againstEvery other client's concurrent operations, in every possible arrival orderOnly the server's ordered history
Transform-case growth as editor count increasesGrows sharply with the number of simultaneous editorsStays roughly constant — one client versus one server, always

Deep Dive — Real-Time Transport: WebSockets, Optimistic Local Apply, and the Op Queue

The "fast path" is what makes typing feel instant. Every keystroke is applied optimistically to the local in-memory document the moment it happens — there is no network round-trip on the critical path between a user pressing a key and the character appearing on screen. Simultaneously, the same operation is shipped over a persistent WebSocket connection to the OT server.

The OT server transforms the incoming operation against any operations that arrived concurrently (i.e. committed after the base_revision the client's operation was authored against), commits the transformed operation to the durable operation log, and fans the final, transformed operation out to every other connected collaborator on that document — who apply it to their own local copy, exactly as described in the Jupiter model above.

Figure 3. The fast path — a keystroke is applied locally and instantly, shipped over a persistent WebSocket, transformed and committed by the OT server, then fanned out to every other collaborator.

Why an Operation Queue, Not a Single In-Flight Op

A client doesn't wait for the server to acknowledge one operation before accepting the next keystroke — it maintains a small local queue of not-yet-acknowledged pending operations, so a burst of fast typing is never throttled by round-trip latency. When the server's committed-op broadcast catches up and acknowledges the oldest pending operation, it's popped off the local queue; if the server instead responds with a stale-revision rejection, the entire pending queue is transformed against the missing history and resubmitted as a batch.

Deep Dive — Rich Formatting, CRDTs, and Structural Edits

Plain-text OT transform functions (insert/delete/retain against another insert/delete/retain) are well-understood and have been formally studied in the literature. Real documents, though, are far more than a flat character stream: they have formatting runs (bold, italic, font, color) layered on top of text, embedded objects (images, tables, drawings), and comment threads anchored to a range of text that itself might move as the document is edited.

Production collaborative editors commonly split the problem: keep OT for the core linear text stream, where its transform functions are simplest and best understood, and layer CRDT-like (Conflict-free Replicated Data Type) structures on top for the more tree-shaped or set-shaped auxiliary state — formatting spans, embedded object metadata, comment anchors. A CRDT is specifically designed so replicas can apply updates in any order, or even apply the same update twice, and still converge — without needing a central authority to define one canonical ordering, which is exactly the property that's awkward to obtain for tree-shaped state out of a straight character-stream OT model.

OT vs. CRDT — Two Answers to "How Do Concurrent Edits Converge?"

DimensionOperational Transformation (OT)CRDT
CoordinationNeeds a central server (Jupiter model) or a full peer-to-peer transform matrixNone required — convergence is a mathematical property of the merge function
Best fitLinear, ordered structures — the core text streamTree/set-shaped structures — formatting spans, object metadata, comments
Server roleLoad-bearing — defines the canonical orderOptional — can relay only, without transforming anything
Typical production useGoogle Docs' core text engine (Jupiter-derived)Often combined with OT for auxiliary state, not a full replacement

The practical takeaway for an interview: don't present OT and CRDTs as competing answers to the same question — the strongest answer is that real systems combine them, using each where its guarantees are the easiest to obtain.

Deep Dive — Presence, Cursors, History, and Offline Editing

Several features here are related to, but not identical with, the core OT convergence problem, and it's worth being explicit about which ones ride on the authoritative operation log and which ones don't.

Presence and Live Cursors

Live cursor position and collaborator-presence indicators (who's viewing, who's actively typing, and where) are broadcast as lightweight, non-authoritative side-channel messages — separate from the authoritative operation log entirely. They're never committed, never need to be durable, and can be safely dropped or superseded by a newer cursor position with no correctness impact, which is exactly why they don't need to go through the same commit-then-broadcast pipeline as document text.

Version History via Snapshots

Periodic snapshots (see Feature-Specific Logic below) do double duty: they let a newly-opened document load instantly instead of replaying its entire operation history from revision zero, and they also form the natural basis for a user-facing version history feature — each retained snapshot (or a labeled subset of them) is a restorable point in time.

Offline Editing and Reconnect Reconciliation

An offline client keeps accepting local keystrokes into its optimistic local document and its local pending-operation queue exactly as it would if briefly disconnected mid-session — there's no special "offline mode" at the editing layer. On reconnect, the client replays its queued operations against the server using precisely the same OT machinery used for live concurrent edits: it resubmits with its now-stale base_revision, the server transforms the queued operations against everything committed while the client was disconnected, and broadcasts the results.

Figure 4. Offline-queue reconciliation — a disconnected client keeps buffering local edits while the server's revision keeps advancing from other collaborators; on reconnect, the queued ops are transformed against the missed history and rebased into the converged document.

The only meaningful difference between being offline for 2 seconds versus 2 hours is the size of missing_ops the server has to transform the queue against — the correctness mechanism is identical at both time scales, which is a nice validation that the core OT design generalizes rather than needing bespoke offline-specific logic.

Data Partitioning and Sharding

Shard the Collaboration/OT server tier and the Operation Log by doc_id: every operation for a given document is routed to, ordered by, and logged under exactly one shard at a time. This is the load-bearing design choice that makes a single canonical ordering per document tractable at all — it sidesteps needing any cross-shard coordination protocol for ordering, at the cost of concentrating all of one document's activity onto one shard (addressed below under Bottlenecks).

  • Hash doc_id to a shard for an even distribution across the OT server fleet.
  • A shard can hold authority for many low-activity documents simultaneously; a single very hot document effectively borrows a disproportionate share of its shard's capacity, which is why hot-document detection and rebalancing matter operationally.
  • Shard reassignment (during scale-out, failover, or rebalancing a hot doc onto its own dedicated shard) must hand off cleanly: drain in-flight ops, ensure the new shard picks up from the exact last committed revision, and only then let clients reconnect to the new owner.

Replication and Fault Tolerance

The Operation Log is the one dataset that can never lose a committed keystroke, so it's durably replicated (e.g. 3× across availability zones) before an operation is acknowledged as committed back to clients. If the OT server holding authority for a document crashes, a standby takes over: it replays the operation log from the last durable revision, reconstructs the in-memory ordering state, and resumes accepting new operations at exactly current_revision + 1 — clients reconnect, discover the new revision via the stale-revision/catch-up path (see System/API Design above), and continue seamlessly.

  • Because ordering state can be fully reconstructed from the log, the OT server itself can be treated as disposable on crash — the log, not the server process, is the actual source of truth.
  • Snapshot storage is likewise replicated, though it's a pure performance optimization: if a snapshot were ever lost, the full operation log since document creation is still sufficient (just slower) to reconstruct current state.

Feature-Specific Logic

  • Every operation carries the base_revision it was authored against; the OT server compares that to current_revision to know exactly which already-committed operations (if any) it must transform the incoming op against before assigning it the next revision number.
  • A client that has been offline or slow to flush simply resubmits with an older base_revision; the server's transform step is identical whether the concurrent operations were milliseconds old or minutes old — there's no special-cased offline path at the transform layer itself.
  • The operation log would grow without bound for a long-lived, heavily-edited document, so a background compaction job periodically materializes a full-document snapshot at some revision and lets older raw operations age out of hot storage (moved to cold storage for audit/history purposes, or dropped per retention policy).
  • Snapshot compaction cadence trades off replay cost on open (fewer, older snapshots mean more ops to replay) against compaction overhead (too-frequent snapshotting wastes storage/IO on a document nobody re-opens for a while) — a reasonable default is snapshotting every N committed operations or every T minutes of continuous editing, whichever comes first.

Security, Privacy and Permissions

  • Per-document access control: owner, editor, commenter, viewer — enforced both at the REST layer (opening/loading a document) and, critically, on every single incoming WebSocket operation, not just at initial connection time.
  • Permissions can change mid-session (an owner downgrades a collaborator from editor to viewer while they're actively connected); the OT server must re-check the caller's current permission on every submitted op and reject or disconnect if it's no longer sufficient, rather than trusting a permission check performed only when the socket was first opened.
  • Transport security: TLS on every WebSocket and REST call; operations and snapshots encrypted at rest.
  • Audit trail: since every committed operation records a client_id and timestamp, the operation log doubles as a tamper-evident audit log of exactly who changed what and when.

Load Balancing

Unlike a stateless CRUD API, routing here cannot be simple round-robin: once a document's ordering authority lives on a specific OT server (see Data Partitioning above), every client editing that document must have its WebSocket routed to that same server — otherwise two different servers could each think they're the source of truth for the same doc_id, which breaks the entire ordering guarantee. A connection-routing layer (a consistent-hashing-aware proxy, or a lookup service backed by a fast in-memory directory of doc_id → owning server) directs each client's WebSocket handshake to the correct shard. Only the initial handshake / shard-lookup step is load-balanced in the traditional sense; once connected, the client is sticky to that server for the life of the session.

Scaling to Multiple Regions

  • Place a document's authoritative OT shard in the region closest to its most active editors, to minimize the perceived typing-to-broadcast latency for the majority of that document's collaborators.
  • A collaborator connecting from a distant region still has their WebSocket routed back to the document's single authoritative shard, since ordering can't be split across regions — cross-region collaborators trade off some added latency, an explicit and acceptable cost given that the alternative (multiple simultaneous orderings) breaks correctness entirely.
  • The durable Operation Log is replicated cross-region asynchronously for disaster recovery, so a regional outage doesn't lose committed history, even though live editing on documents authoritative in that region is briefly unavailable during failover.
  • If a document's center of gravity shifts (a team relocates, or a doc goes viral in a new region), its authoritative shard can be migrated to a closer region during a low-activity window.

Monitoring, Logging and Analytics

  • Per-document operation throughput and P50/P95/P99 transform latency — the direct proxy for whether typing feels instant.
  • WebSocket connect/disconnect/reconnect rates, and offline-replay op counts — spikes here often correlate with client-side or network issues before they show up as user complaints.
  • Snapshot-compaction lag (how far behind the latest revision the newest snapshot is) — a growing lag means document-open latency is quietly getting worse for that document.
  • Per-shard hot-document detection: alert when a single doc_id's op rate or connected-editor count crosses a threshold, since that's the leading indicator of the single-shard hotspot described below.

Consistency Model, Explicitly

Favor availability on the write path from the typer's perspective: a disconnected or lagging client keeps accepting local keystrokes rather than blocking. Favor strict, centralized ordering for the one specific decision that must never be ambiguous — which operation counts as "first" on a given document at a given revision — since two servers disagreeing on that would break convergence outright.

Common Interview Questions

Beyond the core design, interviewers love to pressure-test one component at a time. Use these to rehearse, or expect a real interview to pick 3–5 as "and then what?" follow-ups.

Scaling and Performance

A single public document goes viral and thousands of people open it to watch (mostly read-only) while a handful actively edit — how do you handle the read-heavy fan-out without overloading the OT server?
Separate "read/observe" connections from "edit" connections at the transport layer; observers can be served the broadcast stream from a lightweight fan-out tier without ever touching the OT server's per-op transform path, which stays reserved for actual editors.
How would you scale the OT server tier when one document suddenly has 200 simultaneous editors instead of the usual 3?
Detect the hot document via per-shard op-rate/connection-count monitoring, and either give it a dedicated shard sized to its load or apply light backpressure/batching on the transform loop; the single-authority-per-doc constraint doesn't change, only how much capacity that one authority is given.
What's the CPU cost of the transform step as a document's total history grows into the millions of operations?
Bounded and independent of total history — an incoming op is only ever transformed against operations committed since its base_revision (typically a handful), not against the document's entire lifetime of edits; this is exactly why revision numbers matter (see Feature-Specific Logic).

Correctness and Convergence

Two operations arrive at the OT server in the same millisecond — how do you decide which one is "first"?
The server processes its incoming operation queue for a given document strictly one at a time; the point isn't fairness, it's that there is exactly one authority making that call, so every replica agrees with it by construction.
How do you prove the resulting document is actually the same on every client, not just "probably" the same?
OT transform functions are typically accompanied by formal properties (often called TP1/TP2 in the literature) guaranteeing that applying transformed operations in the server-assigned order always yields the same result regardless of a client's original local ordering; production systems also validate this with extensive property-based and fuzz testing of the transform function itself.
What happens if the transform function has a subtle bug that produces divergent state for one rare operation combination?
This is the scariest failure mode in the whole design, since it silently corrupts a shared document rather than throwing a visible error; mitigations include exhaustive transform-function test suites, periodic background consistency checks that hash-compare client and server document state, and a manual "force resync from server snapshot" recovery path.

Product and API Design

How would you support commenting without letting comments interfere with the core text OT stream?
Model comments as a separate, anchor-based auxiliary structure (a CRDT-like set keyed by a stable position reference into the text) rather than literal characters in the document body, so comment operations never need to be transformed against text insert/delete operations at all.
How would you add a "suggestion mode" / track-changes feature?
Represent a suggestion as metadata wrapping an operation (an insert/delete tagged "proposed, not yet accepted") rather than a different operation type — the underlying OT/transform machinery for ordering and convergence stays identical; only the rendering layer and an accept/reject action differ.
How do you let a user restore the document to a version from an hour ago?
Roll forward from the nearest snapshot before that point in time by replaying the retained operation log up to the target revision, then apply that reconstructed state as a new operation (a large diff) at the current revision — restoring is itself just another committed operation, never a special-cased mutation of history.

Security and Permissions

A collaborator's edit permission is revoked while they're actively typing — what should happen?
The OT server must re-validate permission on every incoming operation, not just at connection time; once revoked, subsequent operations from that client are rejected and the WebSocket can be closed, though operations already committed before the revocation remain part of history.
How do you prevent a malicious client from submitting operations for a document it was never granted access to?
Every operation submission is authenticated and authorized against that specific doc_id server-side before it's even considered for ordering or transformation — permission checks happen strictly before the op enters the transform pipeline, not after.
How would you support end-to-end encrypted documents, where even the server can't read the content?
This is fundamentally in tension with server-side OT, since the server needs to inspect operation content at least structurally to transform it correctly; real designs either accept that the OT server sees plaintext (the common, trusted-server model) or move to structural-only transforms and CRDT merges that operate on encrypted-but-structured blobs without needing to interpret their content.

Reliability and Operations

The OT server holding authority for a document crashes mid-session — what does the user experience?
A brief connection drop and reconnect; the standby replays the operation log from the last durable revision, resumes accepting ops, and clients catch up via the same stale-revision/catch-up path used for any reconnect — no data loss, just a short availability blip.
How would you detect that convergence has silently broken for some document?
Periodic background jobs that hash-compare the server's authoritative document state (reconstructed from the log) against what a sample of connected clients report as their local state, alerting on any mismatch well before a user notices garbled content.

Extensions

How would you extend this design to real-time collaborative spreadsheets, where "operations" are cell edits rather than character inserts?
The same centralized-ordering, transform-against-history model applies; the transform function changes shape (cell-range shift or formula-reference rewrite on row/column insert/delete, rather than character-offset retain/insert/delete), but the OT server, operation log, and snapshot/broadcast machinery are structurally identical.
How would you support a "presenter follows me" mode where all viewers' scroll position snaps to the presenter's cursor?
This rides entirely on the existing non-authoritative presence/cursor side-channel described above — broadcast the presenter's cursor position at a modest rate and have following clients scroll to it locally; it never touches the operation log or the transform pipeline at all.

Key Takeaways

Remember
The single defining fact about this system is that concurrent, conflicting edits are the normal case, not an edge case — every other decision (centralized ordering authority, revision numbers, transform-against-history, sharding by doc_id) flows from needing a precise, provable answer to how all replicas end up identical. The Jupiter model's big insight is collapsing peer-to-peer transform complexity down to "each client versus one server" by making a single server the canonical source of ordering — state this trade-off explicitly, since "why not full peer-to-peer OT?" is a near-guaranteed follow-up. Keep the fast path (local optimistic apply, WebSocket, transform, broadcast) narrowly focused on correctness and latency, and push presence, version history, and rich-formatting concerns onto adjacent, non-authoritative structures — side-channel presence messages, periodic snapshots, CRDT-like formatting layers — rather than overloading the core text-operation stream with all of it.
