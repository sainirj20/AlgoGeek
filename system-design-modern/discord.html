SYSTEM DESIGN

Designing Discord

A complete, interview-ready design walkthrough for a Discord-style real-time community platform covering guilds ("servers") with multiple text channels, direct messages, presence and typing indicators, and group voice/video channels: requirements and capacity estimation, high-level architecture, API and low-level design (the WebSocket gateway session lifecycle), database schema, sharding, a feature-specific deep dive on fanning a single message out to a mega-guild's connected sessions without one send blocking the system, replication and fault tolerance, caching, monitoring, security, and a bank of follow-up interview questions. The thread running through every section is that this system is really two different real-time systems sharing one product surface — a reliable, ordered WebSocket control plane (chat, presence, typing) fanned out through a pub/sub tree, and a loss-tolerant, low-jitter UDP media plane (voice/video) relayed through an SFU that never touches the message store or the gateway's event stream — plus one architectural fact that trips up most candidates: a handful of oversized guilds, not the average guild, are what actually threaten to take down the fan-out layer, so the design has to be built around the 99.9th-percentile guild, not the median one.

Problem Statement & Scope

Design a real-time community chat platform, similar to Discord, that lets users:

  • Create or join a "server" (guild) — a persistent community grouping multiple text and voice channels, joined via a shareable invite.
  • Send and receive real-time text messages in a channel, with full history and pagination, delivered to every currently connected member with sub-second latency.
  • See presence — who else in a shared guild is online, idle, or offline — updated live as members connect, disconnect, or go idle.
  • See typing indicators — a lightweight, ephemeral "user is typing…" signal scoped to one channel.
  • Exchange direct messages (DMs) with another user, outside any guild.
  • Join a voice or video channel inside a guild for real-time group voice/video (WebRTC).
  • Operate under per-guild roles and permissions — who can post, manage channels, or moderate, resolved per channel.
  • Receive a push notification for an @mention or DM while offline.

In scope

The WebSocket gateway/session layer and its event fan-out, the guild/channel/membership/role model, message persistence and history pagination, presence propagation, typing indicators, the voice-channel signaling handshake and SFU-based media relay, and the caching/sharding decisions that keep one oversized guild from degrading the platform for everyone else.

Out of scope (acknowledged, not designed in depth)

Audio/video codec internals (Opus/VP8/H.264 encoding itself), the bot/developer API platform, AutoMod/ML content-moderation internals, screen-share encoding specifics, monetization, and end-to-end encrypted voice. We treat these as adjacent systems the design must leave room for, not features to build from scratch.

Key design tension
Two facts shape almost every later decision. First, this is two different real-time systems wearing one UI: text/presence/typing is a reliable, ordered event-fan-out problem over persistent WebSocket connections, while voice/video is a loss-tolerant, latency-sensitive media-relay problem that needs an entirely different transport (UDP, SFU) — pushing voice frames through the same pub/sub pipe that carries chat events would be a fundamental mismatch. Second, guild size is wildly uneven: the overwhelming majority of guilds have a handful to a few hundred members, but a small number run into the hundreds of thousands — and a "publish this message to every member's connection" implementation that is perfectly fine at 50 members becomes a thundering-herd fan-out storm at 100,000+. The design has to be built around that long tail, not the median.

Non-Functional Requirements

  • Very low latency for real-time events. A message posted in a channel should reach every other connected member well under a second (target end-to-end p95 in the low hundreds of ms for text/typing/presence) — a human-perceived "instant messaging" bar, not "eventually shows up."
  • Extremely large individual guilds must not degrade the rest of the platform. A single guild can have hundreds of thousands of members; fanning out one message in that guild must cost work proportional to that guild's connected sessions, never contend for a resource every unrelated guild also depends on.
  • High WebSocket connection concurrency at global scale. Tens of millions of concurrent, long-lived, mostly-idle connections must be held open cheaply — per-connection footprint (memory, scheduler overhead) is the dominant cost driver of the gateway tier.
  • Message ordering within a channel. Two messages posted to the same channel must be delivered to every subscriber in one consistent order — never re-ordered within a channel, even if wall-clock ordering across unrelated channels is not guaranteed.
  • Voice/video has a fundamentally different latency/loss contract than text. Voice needs low, bounded jitter and tolerates occasional dropped packets (a dropped 20 ms audio frame is inaudible; a late retransmit is worse than useless) — the opposite trade-off from text, which must never lose a message but tolerates tens to low-hundreds of ms of delivery latency.
  • Durability of message history, but not of ephemeral signals. A message, once acknowledged, must survive a node failure. Presence and typing indicators are best-effort soft state — losing one typing event or one stale presence tick is a non-event.

Capacity Estimation and Constraints

Given assumptions (illustrative, for this exercise — not a claim about Discord's actual current traffic): ≈200M monthly active users, ≈40M DAU, ≈15M peak-concurrent WebSocket gateway sessions. That concurrency figure is deliberately grounded in the same order of magnitude as the real, cited progression on Discord's own engineering blog — 5,000,000 concurrent users on the Elixir gateway in 2017, scaled further to 11,000,000+ concurrent connections after the Rust/Rustler optimizations described in a later post — so 15M peak sits as a reasonable next step in that same trajectory, not an invented number.

Guild size distribution — the long tail that drives the design

Assumption ≈40M active guilds; the overwhelming majority (≈99%) have <500 members
≈0.1% of guilds ("mega-guilds") have 50,000–500,000+ members — illustrative long-tail, consistent with Discord publicly describing individual communities in the hundreds of thousands
A single mega-guild at 100,000 members with ≈15% concurrently online ⇒ ≈15,000 simultaneously connected sessions subscribed to that one guild

Message throughput

Calculation Assume ≈40M DAU send ≈15 messages/day on average → ≈600M messages/day
Average messages/sec = 600M ÷ 86,400s ≈ 6,900 msg/sec
Peak multiplier (evening/regional peak concentration) ×5 ≈ 35,000 msg/sec peak write rate
(Order of magnitude only — Discord's own "trillions of messages stored" figure, cited on its engineering blog, implies a multi-year sustained average consistent with a number in roughly this range.)

Fan-out cost of one message in a 100,000-member guild

Calculation Guild members = 100,000; concurrently-connected fraction ≈ 15% → 15,000 live gateway sessions subscribed to that guild
Naive fan-out: 1 message write → 15,000 individual gateway pushes, all triggered by a single publish
If those 15,000 sessions are spread across ≈75 gateway nodes (≈200 sessions/node, least-connections balanced), a pub/sub layer that delivers once per interested node instead of once per session cuts the fan-out publish cost from 15,000 to ≈75 — each node then does one cheap, in-process local broadcast to its own ≈200 attached sessions (see Feature-Specific Logic Deep Dive)

Voice/SFU bandwidth

Assumption & calculation Opus audio ≈ 64 kbps per participant's upstream; the SFU forwards (does not mix) each active speaker's stream to every other participant
A 10-person voice channel with ≈2 simultaneously-active speakers → each participant downloads ≈2 × 64 kbps ≈ 128 kbps, uploads ≈64 kbps only while actually speaking
Grounded by the real, cited figures on Discord's own engineering blog: ≈2.6M concurrent voice users served by 850+ voice servers across 13 regions/30+ datacenters, at >220 Gbps and >120M packets/sec of egress — consistent with per-participant bandwidth staying small (tens to low hundreds of kbps) while aggregate egress is dominated by participant count, not per-participant rate
Takeaway
The text/presence path (≈35,000 msg/sec peak writes, 15M concurrent WS sessions) is a fan-out-shaped problem, and the shape is lumpy, not smooth: a handful of mega-guilds contribute a wildly disproportionate share of the fan-out cost per message compared to the platform average. The voice path (≈2.6M concurrent, real cited figure) is a media-relay-shaped problem dominated by participant count and egress bandwidth, not message volume, and lives on entirely separate infrastructure (see High-Level Design and Data Sharding).

Architecture overview

The diagram below turns the service list into a wiring diagram. The API Gateway splits traffic into a WebSocket upgrade path (Gateway Service, for receiving real-time events) and a REST path (Guild/Channel Service, for CRUD and message sends). A message write triggers a change-feed event into the Pub/Sub Fan-out Layer, which delivers once per gateway node holding an interested session — each node then does a cheap local broadcast. Voice is signaled over the same WS connection but its actual media takes a completely separate UDP path straight to the SFU cluster.

Figure 1. Service topology: text/presence flows through the Gateway Service and a Pub/Sub fan-out layer that delivers once per interested gateway node, never once per session; voice/video is signaled through the same WS connection but its actual media takes a separate UDP path straight to the SFU cluster, bypassing the message store and fan-out layer entirely.

Data flow (a): Sending a text message

  1. Client → API Gateway: POST /v1/channels/{channel_id}/messages (REST, not over the WS gateway — sends are request/response, not gateway dispatch).
  2. API Gateway → Guild/Channel Service: resolve the caller's effective permission for this channel (role + per-channel overwrite).
  3. Guild/Channel Service → Message Service: permission OK → persist the message (Message Store write, partitioned by channel_id).
  4. Message Service → API Gateway → Client: 201 Created with the canonical message (a Snowflake message_id, so id order = time order).
  5. The write triggers an async change event → Pub/Sub Fan-out Layer, keyed by (guild_id, channel_id).
  6. Fan-out Layer → every Gateway node with ≥1 session subscribed to that guild/channel: one delivery per node.
  7. Each Gateway node → its own locally attached sessions: an in-process broadcast of a MESSAGE_CREATE dispatch event, no further network hop.
  8. (async) Fan-out Layer → Notification Service: if a mentioned/DM'd user has no live session, send a push notification.

Data flow (b): Joining a voice channel

  1. Client → Gateway Service (over the existing WS control connection): a Gateway op signaling "join voice channel X" (VOICE_STATE_UPDATE).
  2. Gateway Service → Voice Signaling Service: forwards the request; Voice Signaling assigns the nearest/least-loaded SFU node for that channel's region and returns connection info (SFU endpoint, ICE servers) back over the same WS connection (VOICE_SERVER_UPDATE).
  3. Client ↔ SFU node: a separate UDP connection — ICE negotiation, DTLS handshake, then SRTP media flow. This never touches the Gateway Service, the Pub/Sub Fan-out Layer, or the Message Store.
  4. SFU node → every other participant already in the channel: forwards the new participant's audio/video stream (and vice versa) — an N-way relay through the SFU, not a peer-to-peer mesh between clients.
  5. Voice Signaling Service → Presence Service: mark the user "in voice channel X" so other guild members see it live.

API Design

Conventions: JSON over HTTPS (REST) for CRUD and message send/read; a persistent WebSocket for the real-time event stream (the "Gateway"). Message/guild/channel/user IDs are Snowflakes (time-sortable 64-bit integers, see Database Schema), so pagination and ordering never need a separate timestamp index.

Gateway (WebSocket) protocol

wss://gateway.example.com/?v=10&encoding=json

← op 10 Hello        { "heartbeat_interval": 41250 }
→ op 2 Identify      { "token":"...", "intents": ["GUILDS","GUILD_MESSAGES","GUILD_PRESENCES"] }
← op 0 Dispatch      { "t":"READY", "s":0, "d": { "session_id":"...", "guilds":[...] } }

→ op 1 Heartbeat     { "d": <last_seq> }         // every heartbeat_interval
← op 11 Heartbeat ACK

← op 0 Dispatch      { "t":"MESSAGE_CREATE","s":41,"d": {...} }
← op 0 Dispatch      { "t":"TYPING_START","s":42,"d": {"channel_id","user_id"} }
← op 0 Dispatch      { "t":"PRESENCE_UPDATE","s":43,"d": {"user_id","status"} }

// reconnect after a drop:
→ op 6 Resume        { "token":"...", "session_id":"...", "seq": 43 }
← op 0 Dispatch (replay of any events with s > 43), then the live stream continues
   — or, if the session is no longer valid server-side —
← op 9 Invalid Session { "d": false }               // client must re-Identify from scratch

Every Dispatch event carries a monotonically increasing sequence number s, scoped to the session; a client tracks the last s it saw so a Resume can ask the gateway to replay only what it missed (see Low-Level Design).

Low-Level Design (Deep Dive)

7.1 Gateway session lifecycle: connect, heartbeat, and resume without losing events

A gateway connection is not stateless request/response — it is a long-lived session with server-side state (the guild interest set, the last-seen sequence number, a short replay buffer of recent dispatches) that a reconnect should ideally recover rather than rebuild from scratch.

Figure 2. Gateway session lifecycle: Hello, Identify, and Ready establish a session with a sequence number; on reconnect, Resume asks for events after the client's last-seen seq, replayed from a bounded server-side buffer — only if that buffer or session is gone does the client pay for a full re-Identify.

Why a sequence number instead of "just replay everything since you disconnected": the gateway does not know how long a client will be gone, and a session that reconnects a minute later should not force a full guild resync if nothing changed except three messages in one channel it cares about. The sequence number lets Resume ask precisely "replay events after s=41" against a short, bounded replay buffer (illustratively a few minutes). If the buffer has already rotated past that point, or the session's owning process/node is gone, the gateway cannot honestly claim to replay everything and instead sends Invalid Session — forcing a fresh Identify and a full Ready payload is strictly slower but never silently drops an event the client thinks it should have received.

7.2 Sharding a single logical guild across gateway processes at mega-guild scale

A guild is a logical pub/sub topic, but nothing says the fan-out work for one guild has to be owned by a single process. For a 500-member guild, one lightweight guild-coordinator process handling every publish and knowing every subscribed session is fine. For a 200,000-member guild with 30,000 concurrently connected sessions, the same design would mean one process holding 30,000 remote references and doing 30,000 sends for every single message — a single point of both bottleneck and failure for that one (admittedly unusual) guild.

The fix: split the guild's session-interest set across N relay shards (illustratively, one relay shard per ≈500–1,000 sessions), each independently responsible for delivering to its own slice of that guild's connected sessions. The guild-coordinator's job shrinks to "publish once to each of my N relay shards," not "publish once to every session" — the fan-out ratio the coordinator itself deals with drops from 1:30,000 to roughly 1:30–60, and each relay shard's own fan-out (1:500–1,000) is cheap, local, in-process work. This is conceptually the same problem Discord's own engineering blog describes solving with Manifold — a library that distributes a broadcast across remote nodes without requiring the sending process to call send once per destination process — and is also why very large guilds' connections are described as sharded across many separate gateway processes rather than herded onto one.

7.3 Permission resolution on the message-send hot path

Every message send and every read of channel history re-resolves the caller's effective permission for that specific channel: base permissions from the member's role(s), then any channel-level permission overwrite (allow/deny bitmask) for that role or that specific user, applied in a fixed precedence order (guild role → role overwrite → member-specific overwrite, most specific wins). This is cheap (a bitwise OR/AND over a small number of roles) but happens on every send, so the resolved bitmask for a (user, channel) pair is cached and invalidated on any role/overwrite change (see Caching Strategy) rather than recomputed from a fresh role lookup every time.

7.4 Typing indicators as pure ephemeral state

A TYPING_START event is deliberately never written to the Message Store. It is published directly to the Pub/Sub Fan-out Layer for that channel with a client-enforced ≈10-second expiry, and if the fan-out publish is dropped under load, the correct behavior is to drop it silently, not retry — a missed typing indicator is invisible to the user experience, while retrying it after the fact would show a stale, misleading signal. This is the clearest example in the whole design of a signal with intentionally weaker guarantees than a message.

Database Schema

IDs are Snowflake-style 64-bit integers (timestamp + worker/shard id + sequence), so an ID is both a globally unique key and a sortable proxy for created_at — pagination and ordering never need a separate index. guild_id is the shard key for membership/role data; channel_id is the shard key for messages (see Data Sharding).

guilds

CREATE TABLE guilds (
  guild_id BIGINT PRIMARY KEY, -- snowflake
  name VARCHAR(100) NOT NULL,
  owner_id BIGINT NOT NULL,
  region VARCHAR(16) NOT NULL, -- default voice/media region
  member_count BIGINT NOT NULL DEFAULT 0, -- approximate, async-updated
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

channels

CREATE TABLE channels (
  channel_id BIGINT PRIMARY KEY, -- snowflake
  guild_id BIGINT REFERENCES guilds(guild_id), -- NULL for a DM channel
  type VARCHAR(8) NOT NULL, -- text|voice|dm
  name VARCHAR(100),
  position INT NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_channels_guild ON channels(guild_id);

guild_members, roles & permission overwrites

CREATE TABLE guild_members (
  guild_id BIGINT NOT NULL REFERENCES guilds(guild_id),
  user_id BIGINT NOT NULL,
  nickname VARCHAR(64),
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (guild_id, user_id)
);

CREATE TABLE roles (
  role_id BIGINT PRIMARY KEY,
  guild_id BIGINT NOT NULL REFERENCES guilds(guild_id),
  name VARCHAR(64) NOT NULL,
  permissions BIGINT NOT NULL, -- bitflags: SEND_MESSAGES, MANAGE_CHANNELS, KICK, BAN, MUTE_MEMBERS, ...
  position INT NOT NULL DEFAULT 0 -- role hierarchy for precedence
);

CREATE TABLE member_roles (
  guild_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  role_id BIGINT NOT NULL REFERENCES roles(role_id),
  PRIMARY KEY (guild_id, user_id, role_id)
);

CREATE TABLE channel_permission_overwrites (
  channel_id BIGINT NOT NULL REFERENCES channels(channel_id),
  target_type VARCHAR(4) NOT NULL, -- 'role' | 'user'
  target_id BIGINT NOT NULL,
  allow BIGINT NOT NULL DEFAULT 0,
  deny BIGINT NOT NULL DEFAULT 0,
  PRIMARY KEY (channel_id, target_type, target_id)
);

messages (partitioned by channel_id, see Data Sharding)

CREATE TABLE messages (
  channel_id BIGINT NOT NULL,  -- partition key
  message_id BIGINT NOT NULL,  -- snowflake, clustering key DESC (time-sortable)
  author_id BIGINT NOT NULL,
  content TEXT,
  edited_at TIMESTAMPTZ,
  deleted BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
-- wide-column store (ScyllaDB/Cassandra-style): one partition per channel_id (+ time bucket at very high volume)

direct_message_channels

CREATE TABLE dm_channel_participants (
  channel_id BIGINT NOT NULL REFERENCES channels(channel_id),
  user_id BIGINT NOT NULL,

Data Sharding and Partitioning

Two independent partitioning decisions matter here, for two different reasons.

Message storage: partitioned by channel_id

Every message read (open a channel, page back through history) is scoped to exactly one channel_id, so co-locating a channel's messages on one partition gives natural read/write locality: a channel-open reads one partition's most recent rows, never a cross-partition scatter-gather. At very high per-channel volume this is further bucketed by a time window (e.g., one bucket per channel per N days) so a single channel's partition doesn't grow unbounded — the same channel_id + bucket partitioning Discord's own engineering blog describes using in its real message store (originally Cassandra, migrated to ScyllaDB).

The mega-guild problem: gateway fan-out, not storage, is the actual hot spot

Message storage partitioned by channel_id scales gracefully even for a busy channel in a huge guild — it's one more partition doing more writes, not fundamentally different from any other partition. The real hot spot lives one layer up, in the gateway/session fan-out: a 200,000-member guild's 30,000 concurrently connected sessions are not naturally partitioned by anything, and if the pub/sub layer treats guild_id as the only routing key, every one of those 30,000 sessions converges on whatever single process or topic owns that guild_id — a hot partition of connections, not of storage rows.

Figure 3. The mega-guild problem is a connection-fan-out hot spot, not a storage hot spot: message partitions scale the same regardless of guild size, but a single huge guild's live session fan-out must itself be sharded across relay shards to avoid one coordinator process owning tens of thousands of sends per message.

The fix mirrors Section 7.2: fan-out for one guild is itself sharded across relay shards keyed by something like hash(session_id) mod N, so a mega-guild's fan-out workload is spread across N relay shards instead of concentrating on one. A regular-sized guild doesn't need this at all — N=1 relay shard is the common case, and the sharding only kicks in once a guild's connected-session count crosses a threshold, so the added complexity is paid for only by the guilds that actually need it.

Feature-Specific Logic (Deep Dive)

10.1 Fanning one message out to a 100,000-member guild without one send blocking the system

Scenario: a message is posted in the busiest text channel of a 100,000-member guild; ≈15,000 of those members are concurrently connected right now, spread across many gateway nodes because sessions are load-balanced across the whole gateway fleet, not pinned to one node per guild.

Why pure fan-out-on-write (iterate every session and push) doesn't work at this size: a single publish that must individually address 15,000 remote sessions means the publishing process either blocks synchronously issuing 15,000 sends, or spawns 15,000 short-lived send tasks — either way it is a burst of work proportional to guild size on every single message, and a popular mega-guild channel can produce this burst many times a second.

Why pure fan-out-on-read (store the message, let each client poll/pull) doesn't work either: it destroys the "instant messaging" feel FR2 and the low-latency NFR require — polling introduces exactly the delay a WebSocket gateway exists to avoid.

The design that actually works is a hybrid, batched at the granularity of gateway nodes, not individual sessions:

  1. The Message Service does one write to the Message Store (single partition, channel_id).
  2. That write publishes exactly once to a Pub/Sub topic keyed by (guild_id, channel_id) — fan-out-on-write, but only one logical publish, not 15,000.
  3. The Pub/Sub layer maintains, per topic, the set of gateway nodes that currently have at least one session interested in it (not the set of sessions themselves) — illustratively ≈75 nodes out of the whole gateway fleet, since 15,000 sessions spread at ≈200/node land on ≈75 distinct nodes.
  4. The topic delivers the event once to each of those ≈75 nodes — the only "wide" fan-out step, and two orders of magnitude cheaper than addressing every session directly.
  5. Each of the ≈75 nodes then does a cheap, local, in-process broadcast loop over its own ≈200 attached sessions interested in that guild/channel — no network hop, no per-recipient serialization, just writing the same already-serialized bytes to each local connection's send buffer.
Figure 4. Hybrid fan-out for a mega-guild message: fan-out-on-write happens once, at the granularity of interested gateway nodes (≈75), not sessions (15,000); each node then does a cheap fan-out-on-read-style local loop over its own attached sessions.

This is fan-out-on-write at the inter-node granularity and a tight local loop within each node — conceptually the same shape as the batch message-passing Discord's own engineering blog describes building (Manifold) specifically so that a guild process calls send at most once per remote node, not once per session.

Replication and Fault Tolerance

  • Gateway node failure and session resume via sequence numbers. If a gateway node dies, every session it was holding drops. The client reconnects (to a different node, via the load balancer) and attempts Resume with its last-known session_id and seq. Because the session's in-memory state (guild interest set, replay buffer) lived on the node that just died, a Resume against a truly dead node's session will fail server-side (Invalid Session) unless that state was itself externalized/replicated — which most gateway designs deliberately do not do, because replicating every connection's transient state for the rare case of a node crash is expensive relative to just accepting a full re-Identify. The practical trade-off: a node failure costs affected clients one full guild resync (a brief "reconnecting…" state), never a lost message — messages themselves are safe in the Message Store regardless of what happens to any gateway node.
  • Message Store replication. The wide-column store (ScyllaDB/Cassandra-style) replicates each partition to multiple nodes (typically 3, across racks/AZs) with a quorum write/read consistency level — a message is not acknowledged as sent until a quorum of replicas has it, so a single node loss never loses an acknowledged message.
  • Voice SFU failover mid-call is accepted as a brief reconnect, not seamless failover. If a participant's assigned SFU node dies mid-call, there is no practical way to hand off an in-flight UDP/DTLS/SRTP session to another node without the client renegotiating — so the accepted behavior is: detect the drop (missed RTP/RTCP keepalives), the client re-runs the voice-join handshake against a newly assigned SFU node, and there is a short audio glitch. This is a deliberate scope decision: chasing seamless mid-call SFU failover is a large amount of engineering for a failure mode users already tolerate (it looks like ordinary network jitter), whereas losing a chat message would not be tolerated at all.
  • Presence and typing state are not replicated at all — they're recomputed, not recovered. If the process holding a user's presence state dies, the correct recovery is to recompute it from the still-live gateway connection state (is this user's session currently connected anywhere?), not to restore it from a durable log; there is nothing to lose that isn't trivially re-derivable.

Caching Strategy

Guiding rule: cache anything that's safe to read slightly stale for display; never let a cache become the only place authorization state lives.

Monitoring, Logging, Analytics and Notifications

  • WebSocket connection count and reconnect rate, globally and per gateway node — a spike in reconnects after a deploy or node restart is the earliest signal of a thundering-herd reconnect storm (see Follow-up Interview Questions).
  • Message fan-out latency — time from a Message Store write to dispatch being flushed to a subscriber connection, tracked at both the "delivered to gateway node" hop and the "delivered to client" hop, so a slow relay shard versus a slow individual node is distinguishable.
  • Per-guild fan-out cost distribution — not just an average, but the tail: which guilds are triggering the widest node fan-out per message, since that's precisely the mega-guild hot-spot signal from Data Sharding.
  • Voice call quality metrics — jitter, packet loss %, round-trip time, and a derived quality score per SFU node/region, so a degrading region can be flagged before users report "voice keeps cutting out."
  • Moderation/report queue depth and age — abuse reports waiting for review, an operational and trust-and-safety signal simultaneously.
  • Push notification delivery latency/success rate for offline mentions, split by APNs/FCM, since a silent failure here means a user simply never finds out they were mentioned.

Notification triggers: an @mention or DM to a user with no live gateway session (or with push-on-all-messages enabled) is picked up by the Notification Service as it consumes the same fan-out stream every gateway node consumes — it is just another subscriber, never a special-cased write path.

Security Considerations

  • Role/permission enforcement per channel, on every action. Sending a message, reading history, joining a voice channel, and every moderation action all re-resolve the caller's effective permission for that specific channel (role → role overwrite → member overwrite precedence) at the moment of the action — never trusted from a client-supplied claim, and never skipped because "they were allowed to post here five minutes ago."
  • Rate limiting to prevent message flooding/spam. Per-user, per-channel, and per-IP rate limits at the API Gateway on message sends (and on invite creation, DM initiation, and reaction adds), independent of and in addition to any content-based spam/abuse classifier.
  • Voice/video media encryption. Media is encrypted in transit via DTLS-SRTP between client and SFU (standard WebRTC transport security); the SFU can see and route packets, but end-to-end (client-to-client, SFU-blind) encryption of voice content is a materially harder, separate design (acknowledged, out of scope — see Problem Statement & Scope).
  • Abuse reporting and moderation tooling. Any member can report a message/user; reports enqueue into the Moderation/Trust & Safety Service for human or automated review, independent of the normal message-delivery path, so a report never blocks or delays delivery to other members.
  • Invite abuse controls. Invite codes support max-use counts and expirations; a compromised/leaked invite to a large guild is a realistic vector for spam-bot floods, so invite creation and redemption are both rate-limited and auditable per guild.
  • Token/session security. Gateway Identify uses a bearer token over TLS; a revoked/reset token immediately invalidates every live session authenticated with it (the Gateway Service checks token validity, not just presence, on Identify and on a periodic re-validation window).

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design. Rehearse the reasoning out loud, not just the one-line answer — the "why" is what actually gets evaluated.

Real-Time Fan-out & the Gateway

Q1. How would you fan out a single message to a 100,000-member guild without overloading the system?
Never address individual sessions from the publish path. Publish once to a (guild_id, channel_id) topic; the pub/sub layer tracks which gateway nodes hold at least one interested session (illustratively ≈75 nodes for 15,000 concurrently connected sessions) and delivers once per node, not once per session. Each node then does a cheap, local, in-process broadcast to its own ≈200 attached sessions. This turns a 15,000-wide fan-out into a ≈75-wide one at the network layer, with the remaining fan-out happening as free, local work per node.
Q2. Walk me through what happens when a client's WebSocket disconnects and reconnects — how do they avoid missing events?
Every dispatch event carries a monotonically increasing sequence number scoped to the session. On reconnect, the client sends Resume with its session_id and last-seen seq. If the gateway still has that session's state and a bounded replay buffer covering the gap, it replays only the missed events and continues the live stream — no full resync needed. If the session or buffer is gone (e.g., the owning node crashed, or too much time passed), the gateway sends Invalid Session and the client must re-Identify from scratch, paying for a full guild resync instead of silently missing events.
Q3. Why is "15M concurrent connections" a harder capacity problem than the raw message throughput number?
Connection count, not message rate, dominates the gateway tier's resource footprint: tens of millions of mostly-idle, long-lived connections each cost memory and scheduler overhead just to exist, independent of whether they ever receive a message. Message throughput (tens of thousands/sec) is comparatively small and bursty; the always-on cost of simply holding that many sockets open is the number that actually sizes the fleet.
Q4. A user in a small guild occasionally reports "losing" a typing indicator. Is that a bug?
No — typing indicators are explicitly best-effort, ephemeral signals that are dropped rather than retried under load. Retrying a stale typing event after the moment has passed would show a misleading "still typing" signal, which is worse than simply not showing it. This is a deliberate NFR distinction: a message must never be lost, but a typing indicator losing an occasional update is a non-event by design.
Q5. A gateway node restarts for a deploy. What stops every client on it from reconnecting at the exact same instant?
Client SDKs reconnect with exponential backoff and jitter rather than an immediate retry, spreading the reconnect load over a window instead of a single instant. The load balancer in front of the Gateway Service uses least-connections routing so new/resumed connections spread evenly across the remaining fleet, and each node enforces a connection-admission cap so it fails fast rather than degrading for everyone if it approaches its limit.

Voice, Media & Transport

Q6. Why does voice/video use a completely different transport and architecture (SFU/UDP) instead of the same WebSocket gateway used for text?
Text needs reliability and ordering (never lose a message, never reorder within a channel) and tolerates tens to low-hundreds of ms of delivery latency — a good fit for TCP-based WebSocket dispatch. Voice/video needs the opposite trade-off: low, bounded jitter, and it tolerates dropping a packet outright (a lost 20ms audio frame is inaudible; a late retransmit of it is worse than useless) — a good fit for UDP with no retransmission. On top of that, group voice at scale needs a media relay (SFU) rather than a peer-to-peer mesh, because P2P cost grows with the square of participants and leaks every participant's IP; routing media through server-side relays avoids both problems, which is the real, published reasoning behind Discord's own SFU-based voice architecture.
Q7. Why doesn't the SFU mix audio server-side instead of forwarding every participant's stream separately?
Forwarding (not mixing) keeps the SFU a comparatively simple, mostly-stateless relay rather than a real-time audio-encoding pipeline that would need to re-encode a mixed stream per listener at real CPU cost, at scale. It also preserves per-user volume control and muting entirely on the client, since each participant's stream arrives separately and the client decides how to combine and present them locally — a feature that would be lost if the server had already mixed everything into one stream. This forward-don't-mix design is the one Discord's own engineering blog describes for its real SFU.
Q8. An SFU node crashes mid-call for a 6-person voice channel. What happens to the participants?
There is no attempt at seamless mid-call failover of the UDP/DTLS/SRTP session — that would require the client to hold and resume cryptographic/transport state across a server it no longer has any connection to, which isn't practical. Instead, clients detect the drop via missed RTP/RTCP keepalives, and each client re-runs the voice-join signaling handshake against a freshly assigned SFU node. Users experience a short glitch that looks like ordinary network jitter, which is an accepted, deliberate trade-off against the much larger engineering cost of true seamless media failover.

Sharding, Storage & Reliability

Q9. What's your sharding strategy for message history, and why that key?
Partition by channel_id, because every history read is scoped to exactly one channel — co-locating a channel's messages on one partition gives read/write locality with no cross-partition scatter-gather. At very high volume, further bucket by a time window so one channel's partition doesn't grow unbounded. Sharding by guild_id instead would be wrong: a guild can contain many channels of wildly different activity levels, and grouping them onto one partition would recreate exactly the hot-partition problem this key choice avoids.
Q10. A single channel in a mega-guild is extremely chatty — thousands of messages a minute. Does channel_id partitioning still hold up?
At the storage layer, yes — it's simply one busier partition doing more writes, and can be split further by a finer time bucket if needed; nothing about it is fundamentally different from any other partition. The pressure from a hot mega-guild channel actually shows up one layer up, in gateway/session fan-out (see Data Sharding), which is the layer that genuinely needs its own, separate sharding fix — conflating "the channel is chatty" with "the guild's fan-out is expensive" is the mistake to avoid.
Q11. How would you track per-user unread/mention state without adding write load to the message-send hot path?
As a separate, async "read state" service — a per-user, per-channel last-read-message-id, updated when the client acknowledges reading up to a point, decoupled entirely from the message-send path. This mirrors a real Discord service (their Read States service), which was rewritten from Go to Rust specifically because it sits on a very hot, latency-sensitive path (touched on every connect, every send, every read) where garbage-collection pauses were causing periodic latency spikes; Rust's ownership model let them evict and free entries from its cache without a GC pause.
Q12. Why not just make every guild use the same N-relay-shard fan-out from day one, even small ones?
Because the extra hop (guild coordinator → N relay shards → sessions) is pure overhead for a 50-person guild that would be served just as well, and more simply, by one coordinator process talking directly to its handful of sessions. Sharding a guild's fan-out is threshold-triggered — it only activates once connected-session count for that guild crosses a size where a single coordinator would actually become a bottleneck — so the common case (the overwhelming majority of guilds) stays simple, and the complexity is paid for only by the long tail that needs it.

Key Takeaways

Remember
This design is really two systems sharing one product surface, and the biggest interview trap is treating them as one. The text/presence path is a reliable, ordered event-fan-out problem: a Gateway Service holds tens of millions of mostly-idle WebSocket connections, a Pub/Sub Fan-out Layer delivers each message once per interested gateway node rather than once per session, and every node then does a cheap local broadcast to its own attached sessions — a hybrid of fan-out-on-write and fan-out-on-read that is the only thing keeping a 100,000-member mega-guild from becoming a thundering-herd fan-out storm. The voice/video path is a completely different, loss-tolerant, low-jitter media-relay problem: an SFU forwards (never mixes) each speaker's stream over UDP, entirely bypassing the message store and the gateway's event stream after the initial signaling handshake. Layered on both: message storage shards by channel_id for read/write locality, while a single mega-guild's live fan-out has to be sharded independently, across relay shards keyed by session, because storage locality and connection-fan-out cost are two different hot-spot problems with two different fixes. None of this is "one size fits all" — it's a design that spends its complexity exactly where the long tail (a handful of oversized guilds, a handful of hot channels) actually needs it, and stays simple everywhere else.
