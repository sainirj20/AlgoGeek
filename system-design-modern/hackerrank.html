SYSTEM DESIGN

Designing HackerRank

A complete, interview-ready design walkthrough for a HackerRank-like competitive-programming and technical-hiring platform spanning three product surfaces — Practice (question library + automated judge + per-user scoreboard), Contests (time-boxed competitions with a sub-second live leaderboard for tens of thousands of concurrent participants), and Interview Sessions (live pair-programming with a shared real-time editor, audio/video, shared code execution, and session recording). Covers requirements, capacity math, high-level design, API & low-level design (including the full judge and leaderboard-scoring pseudocode), database schema, sharding & the salted-partition hot-key solution, feature-specific deep dives, replication & fault tolerance, caching, monitoring/logging/analytics/notifications, security, and a bank of 16 follow-up interview questions.

This write-up is grounded in the architecture sketched on the reference whiteboard (API Gateway → User / Practice / Contest / Scoreboard services → Kafka → analytics / post-processing / logging / notification), extended into an interview-quality design. Storage choices are kept consistent with that ground truth: MySQL for user data, Cassandra for questions/test-cases and historical contest data, S3 for submitted code, Kafka as the event backbone, an in-memory data grid (Apache Ignite / H2) for live contest state, Ehcache + Hibernate at the service layer, a dedicated code-execution sandbox service, and a post-processing pipeline for plagiarism/code-similarity detection.

Problem Statement & Scope

We are building a competitive-programming and technical-hiring platform with three distinct product surfaces that share infrastructure but have very different real-time and consistency requirements:

  1. Practice — a large library of coding questions with an automated judge. Users write code in a browser editor, submit, and get verdicts (Accepted / Wrong Answer / TLE / MLE / Runtime Error / Compile Error). A per-user scoreboard tracks solved counts, points, and streaks.
  2. Contests — time-boxed competitions over a fixed question set with a live leaderboard that updates in near real time as thousands of participants submit. Contests have a start/end time, scoring rules, and penalties. When a contest ends it becomes an immutable historical record.
  3. Interview Sessions — a live pair-programming product (like HackerRank CodePair): a shared real-time code editor, audio/video, shared code execution, interviewer/candidate roles, and session recording/playback for later review.

These three surfaces are worth stating explicitly up front because they pull the design in different directions: Practice is read-heavy and tolerant of a few seconds of staleness; Contests need a strongly consistent, sub-second scoring path under a massive finale burst; Interview Sessions need sub-150ms bidirectional sync on a persistent connection, which is architecturally closer to a real-time collaboration product than to either of the other two.

In scope

  • Submission ingestion and sandboxed execution/judging
  • Scoring (practice + contest, including penalties and tie-breaking)
  • Real-time leaderboards (contest) and eventually consistent aggregates (practice)
  • Historical archival of contests and submissions
  • Plagiarism/code-similarity detection
  • The collaborative interview surface (editor sync, A/V, shared execution, recording)
  • The supporting data / eventing / caching / observability infrastructure

Out of scope (assumed handled elsewhere or trivially)

  • Billing / subscriptions
  • Marketing site / CMS
  • The rich-text problem-authoring UI
  • Identity-provider internals (we assume OIDC/JWT is available)

We mention these only where they touch the core flows.

Functional Requirements

Practice questions + judge

  • Browse/search questions by tag, difficulty, company, acceptance rate.
  • Fetch a problem statement, constraints, sample I/O, and starter code per language.
  • Submit a solution in one of N supported languages; run against sample test cases ("Run") or the full hidden test set ("Submit").
  • Return a verdict per test case and an aggregate verdict, plus runtime/memory stats.
  • Persist every submission (code blob + verdict) and expose submission history.

Scoreboard (per-user, practice)

  • Maintain per-user aggregates: problems solved, points, acceptance rate, streak, per-tag proficiency.
  • Global and friend leaderboards (all-time / monthly).
  • Eventually consistent — a few seconds of lag after a verdict is acceptable.

Contests + live leaderboard

  • Admin configures a contest via remote config/.properties: questions[] (fixed or randomly drawn from the question DB), start_time, end_time, scoring model, penalty rules.
  • Registration; a contest becomes joinable at start_time.
  • During the contest: submit, judge, score, and reflect the participant's new rank on a live leaderboard within ≈1 second.
  • Tie-breaking by penalty/time; freeze the board in the final minutes (optional "frozen scoreboard").
  • On end_time: freeze scoring, archive to an immutable historical store, trigger plagiarism post-processing, publish final standings.

Interview sessions

  • Schedule a session (interviewer, candidate, time, question set); issue tokens/links.
  • Real-time collaborative editor: every keystroke/edit is synchronized across participants.
  • Audio/video between participants.
  • Shared code execution against the same judge/sandbox used by practice.
  • Roles: interviewer (can see private notes, rubric, all questions) vs candidate (restricted view).
  • Full session recording (code timeline + AV) and playback.
  • Presence, reconnect/resume, and post-session feedback capture.

Consistency trade-offs (explicit)

This is one of the richest parts of the design and deserves to be stated out loud rather than glossed over: different pieces of state genuinely need different consistency models, and the system is built around three named tiers.

Strong / linearizable — where correctness is money-on-the-line
Contest scoring & the live standing per participant. Two submissions to the same problem by the same user must be scored in order; a user's best_score and penalty must be a deterministic function of their accepted submissions. We use the ACID in-memory grid (Ignite/H2) with per-(contest_id, user_id) transactional updates and exactly-once scoring semantics (see Feature-Specific Logic, 10b).

Contest membership and end_time enforcement — a submission accepted at T > end_time must be rejected deterministically (server-authoritative clock).
Eventual consistency (seconds) is fine
Practice scoreboard aggregates — recomputed off Kafka; a lag of a few seconds after a verdict is invisible to users.

Analytics, difficulty calibration, participation funnels — batch/stream, minutes of lag acceptable.

Global leaderboard reads during a contest — replicas may serve slightly stale ranks; we prefer available-but-slightly-stale over unavailable (see Replication and Fault Tolerance).

Plagiarism/code-similarity — runs fully async off Kafka after the contest; not on the hot path.
Read-your-writes for the submitting user
After you submit, your own row on the leaderboard and your own submission history must reflect the result immediately, even if other users' rows are eventually consistent. This is delivered by having the scoring transaction commit to the grid and immediately push the requester's updated row/rank to their own socket, while other users' rows propagate a beat later via the delta stream.

Capacity Estimation and Constraints

Given assumptions: 15M registered users; 1.5M DAU; 200K peak concurrent during a big contest; 5 submissions/user/day; 5 KB avg code payload; 300 ms avg execution/submission; 10× peak factor.

4.1 Submission QPS

Assumption Submissions/day = DAU × subs/user/day = 1.5M × 5 = 7.5M submissions/day
Seconds/day = 86,400
Average QPS = 7.5M ÷ 86,400 ≈ 86.8 → ≈87 QPS
Peak QPS (10×) = 87 × 10 ≈ 870 QPS

Contest-finale burst (separate, worse-than-average spike): if 200K concurrent participants each fire one submission in the last 60 seconds:

Assumption Burst QPS = 200,000 ÷ 60 ≈ 3,333 submissions/s — this is the number that sizes the judge, not the 870

We design the judge for the burst and absorb the gap with a queue + autoscaling (see Low-Level Design and Feature-Specific Logic).

4.2 S3 storage for submissions (per year)

Assumption Submissions/year = 7.5M/day × 365 = 2.7375 × 109 submissions/year
Bytes/year = 2.7375e9 × 5 KB = 1.36875 × 1010 KB ≈ 13.6875 × 106 MB
≈ 13,687 GB ≈ 13.4 TB/year (raw)

S3 replicates internally, so 13.4 TB/year is the billed footprint. With compression (source code gzips ≈4:1) the effective stored payload is ≈3.4 TB/year. Over 5 years, ≈17 TB compressed — trivial for S3. The real cost driver is request count (2.7B PUTs/year), mitigated by batching small blobs and using lifecycle tiering to Glacier for submissions older than 12 months.

4.3 Cassandra storage — questions & test cases

Assumption ≈50,000 questions; statement + metadata ≈ 20 KB/question; hidden test set ≈ 1 MB/question (bundled/compressed)
Statements = 50,000 × 20 KB = 1.0 GB
Test cases = 50,000 × 1 MB = 50 GB
Subtotal ≈ 51 GB → with RF = 3 ≈ 153 GB

Small enough to fit in RAM+SSD comfortably; the design driver for Cassandra here is read fan-out and hot partitions during contests, not raw size (see Data Sharding). Large test blobs (>256 KB per row) are offloaded to S3 with Cassandra holding pointers.

4.4 MySQL — user table

Assumption users: 15M rows × ≈1 KB/row (id, handle, email, pw_hash, profile, aggregate stats) = 15 GB (→ 45 GB at RF/replicas ×3)
user_solutions_index: one row per (user, submission) reference
= 2.7375B rows/year × ≈120 B/row = 328 GB/year

The users table is tiny; user_solutions_index grows ≈330 GB/year and is the reason MySQL is sharded by user_id (see Data Sharding). We keep only an index (pointers to S3 + verdict) in MySQL — never the code itself.

4.5 Kafka throughput

Model ≈5 events per submission on the hot path (submission_received, execution_started, verdict_ready, score_updated, audit_log) plus a clickstream/analytics firehose.

Assumption Submission events (avg) = 87 QPS × 5 ≈ 435 events/s
Submission events (peak) = 870 × 5 ≈ 4,350 events/s
Contest-burst events = 3,333 × 5 ≈ 16,650 events/s (design ceiling)
Clickstream/analytics = 1.5M DAU × ≈50 events/day ÷ 86,400 ≈ 868 events/s avg (≈8,700/s at 10×)
Peak total (design) ≈ 16,650 + 8,700 ≈ ≈25K events/s
Bytes Hot-path events carry references (solution_id), not code, so ≈0.5–1 KB each; a subset carries the 5 KB payload. Take avg 1 KB/event:
Peak ingress ≈ 25,000 events/s × 1 KB ≈ 25 MB/s
With RF = 3 on the brokers ≈ 75 MB/s of disk write

Well within a modest 6–9 broker cluster. We provision ≈2–3× headroom (partitions sized for ≈50K events/s).

4.6 Bandwidth

Assumption Ingress (code): peak 870/s × 5 KB ≈ 4.35 MB/s (finale burst ≈ 16 MB/s)
Egress (leaderboard, naive polling):
200K concurrent × poll every 5 s = 40,000 reads/s
response ≈ 5 KB (top-50 + own rank window)
→ 40,000 × 5 KB = 200 MB/s egress ← the dominant cost
The number that shapes the leaderboard architecture
The 200 MB/s polling egress is the reason the live leaderboard is push-based over WebSocket/SSE with server-side diffing (send only rank deltas, ≈200 B) rather than full-page polling. That cuts egress by ≈25× to ≈8 MB/s and removes 40K QPS of read pressure from the grid entirely. This single insight is why Section 5 (High-Level Design) and Section 10a (Feature-Specific Logic) both treat "push rank deltas, never poll the authoritative standing" as a first-class architectural principle rather than an optimization bolted on later.

4.7 Code-executor sandbox fleet at peak

Assumption Per-slot throughput = 1 execution / 300 ms = 3.33 executions/s
Steady peak (870/s) → 870 ÷ 3.33 ≈ 261 concurrent execution slots
Contest burst (3,333/s) → 3,333 ÷ 3.33 ≈ 1,000 concurrent execution slots

So the judge needs ≈260 slots steady-peak and ≈1,000 slots during a contest finale. If one physical executor host runs, say, 8 isolated microVM sandboxes, that's ≈33 hosts steady and ≈125 hosts at contest peak. We add ≈50% headroom for retries, cold-start warm-pool, and multi-test-case submissions (a "submission" often runs many test cases sequentially, so real per-submission wall time can exceed 300 ms), and we smooth the burst with a bounded submission queue so we provision for the drain rate we're willing to commit to (e.g., SLA "verdict within 10 s") rather than the instantaneous arrival rate.

Architecture overview

The diagram below turns the whiteboard sketch into a wiring diagram: the API Gateway fans requests out to four services, each of which reads/writes its own storage system, with all of them emitting events onto a shared Kafka backbone that fans out to analytics, plagiarism post-processing, logging, and notifications. Note that only the Contest Service and Scoreboard Service touch the in-memory grid — that's the one piece of state in the whole system that is strongly consistent and never cached.

Figure 1. Overall topology: one API Gateway routes into four services, each with its own storage; Contest and Scoreboard also read/write the strongly consistent in-memory grid. All services emit to Kafka, which fans out to analytics, plagiarism post-processing, logging, and notifications.

Data flow: submitting a practice solution

  1. Client POST /practice/submissions with {question_id, language, code} (5 KB) → Gateway (authN, rate-limit) → Practice Service.
  2. Practice Service generates a solution_id, writes the code blob to S3 at a sharded key, writes a PENDING index row to user_solutions_index (MySQL, via User Service), and produces a submissions Kafka event (idempotency key = solution_id). Returns 202 Accepted with solution_id.
  3. Judge worker (consumer / direct RPC) pulls test cases from Cassandra, dispatches to a Code Executor sandbox, collects per-test-case results.
  4. Practice Service writes the verdict to the index row, emits verdict_ready. If ACCEPTED and first accept, emits a score_updated event.
  5. Scoreboard Service / Analytics consume score_updated and update the per-user practice aggregates (eventually consistent). Client polls GET /practice/submissions/{id} or receives a push.

Data flow: joining a live contest and submitting

  1. POST /contests/{id}/register (before start) → row in the in-memory grid keyed (contest_id, user_id) with zeroed score.
  2. At start_time the Contest Service (config-driven) exposes questions. GET /contests/{id}/questions returns the fixed set.
  3. POST /contests/{id}/submissions → Contest Service validates now < end_time using the server clock (see Security Considerations), writes blob to S3, judges via Code Executor against Cassandra test cases.
  4. On verdict, Contest Service performs an ACID transaction on the in-memory grid: update (contest_id, user_id) best-score/penalty, recompute rank bucket. This is the strongly consistent write path with exactly-once semantics keyed on solution_id.
  5. Scoreboard Service reads the grid and pushes a rank delta to subscribed clients (<1 s). It also emits contest.events to Kafka for logging/analytics.
  6. At end_time: Contest Service freezes writes, snapshots the grid to Cassandra Past-Contest DB (immutable, read-only), and emits contest.ended → post-processing runs plagiarism detection and archival.

5.4 Interview Sessions — a separate real-time plane

Because interview sessions are latency-sensitive and stateful (a live document + AV), they run on a separate real-time plane rather than the request/response services:

  • Realtime Collaboration Gateway — terminates secure WebSockets (WSS), authenticates the session token, and routes the connection to the Session Server that owns that session_id (sticky by consistent hash).
  • Session Server — the single source of truth for one session's document. It applies incoming edits, resolves concurrency (OT or CRDT — or, for a simpler v1, a server-authoritative sequenced WebSocket broadcast: every edit is stamped with a monotonically increasing sequence number and rebroadcast; clients that fall behind re-sync from a snapshot). It records the ordered edit stream for playback.
  • WebRTC SFU — audio/video handled by a Selective Forwarding Unit, delegated to a third party (Twilio / Daily / Agora). Our servers only broker signaling and access tokens; media never touches our judge plane.
  • Shared execution — "Run" in a session calls the same Code Executor as practice/contest.
  • Recording pipeline — the ordered edit stream (with timestamps) is persisted to S3 as the "code timeline"; AV is recorded by the SFU provider and its artifact URL is stored against the session. Playback replays edits against wall-clock offsets synced to the AV track.
Figure 2. Interview sessions run on a separate real-time plane: the Realtime Collaboration Gateway pins each connection to the Session Server that owns the document, which fans out to a shared Code Executor, Redis presence, S3 recording, and a third-party WebRTC SFU for A/V — media never touches the judge plane once established.

Low-Level Design

7.1 Judge / code-execution flow (sandboxing)

Isolation approach (defense in depth). Untrusted user code must never compromise a host or read another user's data. Options, strongest first:

  • Firecracker microVMs (KVM-based) — each execution in a fresh, ≈125 ms-boot micro-VM with its own kernel; strongest isolation, used by AWS Lambda. Preferred for the judge.
  • gVisor — user-space kernel intercepting syscalls; lighter than a VM, stronger than a container.
  • Docker + seccomp-bpf + AppArmor + dropped capabilities — acceptable baseline; syscall allowlist, --network=none, read-only rootfs, non-root uid, cgroup CPU/mem caps.

We run Firecracker microVMs from a warm pool (pre-booted, snapshot-restored) to hide boot latency, one submission per microVM, destroyed after use.

Figure 3. Judge sandbox defense-in-depth: an isolated network segment wraps a Firecracker microVM (or gVisor), which wraps cgroup resource limits, which wraps seccomp/AppArmor syscall restriction, around the untrusted submission process itself.

def judge(submission):
    code = s3.get(submission.solution_id)                      # blob
    tests = cassandra.get_test_cases(submission.question_id)   # ordered, may stream from S3
    lang = LANG_REGISTRY[submission.language]

    with warm_pool.acquire() as vm:                 # Firecracker microVM
        compile_res = vm.run(lang.compile_cmd, timeout=COMPILE_TIMEOUT)
        if compile_res.failed:
            return Verdict(COMPILE_ERROR, detail=truncate(compile_res.stderr))

        results = []
        for i, tc in enumerate(tests):
            r = vm.run(lang.run_cmd, stdin=tc.input,
                       timeout=problem.time_limit_ms,
                       mem_limit=problem.mem_limit_kb)

            if r.timed_out:        status = TLE
            elif r.oom:             status = MLE
            elif r.exit != 0:       status = RUNTIME_ERROR
            elif normalize(r.stdout) != normalize(tc.expected):
                                     status = WRONG_ANSWER
            else:                    status = ACCEPTED

            results.append(TestResult(i, status, r.time_ms, r.mem_kb))
            if status != ACCEPTED and problem.stop_on_first_fail:
                break

    verdict = ACCEPTED if all(x.status == ACCEPTED for x in results) else first_failure(results)
    return Verdict(verdict, per_test=results,
                    runtime_ms=max(x.time_ms for x in results))

The judge is stateless and idempotent: re-running the same solution_id yields the same verdict (fixed test set, deterministic normalization). Non-deterministic checkers (special judges) are supported via a per-problem checker binary that compares output.

7.2 Leaderboard update algorithm (scoring, ties, penalties)

Scoring model (ICPC-style, configurable per contest):

  • A problem is solved on the first accepted submission.
  • Score = number of problems solved (or sum of problem points for IOI-style).
  • Penalty = sum over solved problems of (minutes from contest start to first accept) + 20 × (rejected attempts before the accept). Rejected attempts on unsolved problems don't count.
  • Ranking: sort by score DESC, penalty ASC. Further ties broken by last_accept_time ASC, then user_id for determinism.
// Executed inside an ACID transaction on the in-memory grid, keyed (contest_id, user_id)
void applyVerdict(cid, uid, qid, verdict, submitTimeMs, solutionId) {
    Standing s = grid.get(cid, uid);        // pessimistic lock on the (cid,uid) row
    if (s.hasScored(solutionId)) return;    // exactly-once: dedupe on solution_id
    s.recordProcessed(solutionId);

    ProblemState p = s.problems.get(qid);
    if (p.solved) return;                   // already solved -> ignore later submissions

    if (verdict == ACCEPTED) {
        p.solved = true;
        int minutes = (submitTimeMs - contest.startMs) / 60000;
        p.penalty = minutes + 20 * p.rejectedAttempts;
        s.score += problemPoints(qid);
        s.penalty += p.penalty;
        s.lastAcceptMs = submitTimeMs;
    } else {
        p.rejectedAttempts++;               // counts only if problem later solved
    }

    grid.put(cid, uid, s);                  // commit
}

Rank materialization. We do not re-sort N participants on every submission. The grid maintains a sorted structure keyed by the composite (score DESC, penalty ASC, lastAccept ASC). On a standing change we do an O(log N) remove+insert. Reads of "top 50" are an O(50) scan; "around me" is a bounded window around the user's node. Absolute integer rank (1..N) is expensive to keep exact for all users, so we serve exact rank for the top-K and the requester's own bucketed rank, refreshing full absolute ranks on a short interval (e.g., every 2–5 s) — acceptable because the requirements only demand the requester's own rank be immediately correct.

7.3 Plagiarism / code-similarity pipeline (async, off Kafka)

Runs as a Kafka consumer group on contest.ended and on a sampled stream of practice submissions — never on the submit hot path.

Figure 4. Plagiarism pipeline: seven stages from ingest through report, run entirely off the hot path and scalable by cohort.
  1. INGEST: consume solution_ids for the (contest, question) cohort.
  2. FETCH: pull code blobs from S3.
  3. NORMALIZE (per language): strip comments/whitespace, rename identifiers to canonical tokens (v1, v2…), normalize literals → a token stream. This defeats renaming/reformatting-based obfuscation.
  4. FINGERPRINT (MOSS / Rabin–Karp winnowing): k-gram the token stream (e.g. k=5); hash each k-gram; select a subset via the winnowing algorithm (min hash in each sliding window) → a stable, position-anchored set of fingerprints per submission.
  5. INDEX & COMPARE: build an inverted index fingerprint → [submissions]. Similarity(A,B) = |fp(A) ∩ fp(B)| / |fp(A) ∪ fp(B)| (Jaccard). Compare only within the same (contest, question) cohort to bound the N² cost; LSH buckets prune obvious non-matches.
  6. FLAG: pairs above a threshold (e.g. 0.85), excluding shared boilerplate/starter code (subtract the starter fingerprint set), → review queue.
  7. REPORT: emit similarity report to the archive; notify admins; optionally disqualify per contest policy.

Off-hot-path, horizontally scalable by cohort, and idempotent (re-running produces the same report). Cross-contest and historical comparison run as periodic batch jobs.

The hot-partition problem, and why we salt the key
During a live contest all writes to contest_submissions naturally carry the same contest_id, which would hammer one partition (and its replica set) — recall the finale burst of 3,333 writes/s from the Capacity Estimation section. Salting/bucketing the partition key across B buckets (e.g. 64), via bucket = user_id % B, spreads that load across ≈64× more partitions/replica sets. Reads for "all submissions in this contest" fan out to B buckets and merge — acceptable because that's an admin/archival query, not the hot leaderboard read (which comes from the in-memory grid, never from Cassandra). Choose B from expected peak writers so each bucket stays under Cassandra's per-partition write ceiling. This is a named interview classic: recognize the hot-key symptom, apply the salting fix, and be explicit about which reads get more expensive as a result (the fan-out on the rare archival query) in exchange for which reads stay cheap (the live leaderboard, which never touches this table at all).
Figure 5. Salted-bucket sharding: the naive key (contest_id alone) concentrates every write from a 200K-participant finale onto one partition; salting with bucket = user_id % B spreads the same writes across B independent replica sets.

Kafka partitioning & ordering

  • submissions / verdicts / scores topics → partition by contest_id for contest events, by user_id for practice events. Kafka guarantees ordering within a partition. Contest scoring correctness requires that a given user's submissions to a given problem are processed in submit order (so rejectedAttempts and "first accept" are right). Keying by contest_id alone keeps a whole contest's events ordered on one partition — but that recreates a hot partition for a big contest, mirroring the Cassandra problem above. The refinement: key by (contest_id, user_id) (or hash thereof). This preserves per-user ordering — all that scoring actually needs, since applyVerdict() only reasons about one user's problem states at a time — while spreading a contest's traffic across many partitions. We never need a global total order across users.
  • click/analytics topics → partition by user_id, ordering not critical, maximize parallelism.
  • Consumers use the partition key as part of their idempotency to guarantee exactly-once effects (see Feature-Specific Logic, 10b).

Feature-Specific Logic

10a. Real-time contest leaderboard (in-memory data grid)

Why a grid (Ignite/H2) and not Cassandra for live scoring: we need ACID multi-field updates (score, penalty, per-problem state) with sub-second read-after-write for the requesting user, plus fast top-K reads across 200K participants. Cassandra's eventual consistency and lack of read-modify-write transactions make it wrong for the live path; it's perfect for the durable/historical path.

Sub-second updates:

  • The grid holds one Standing object per (contest_id, user_id), co-located (affinity key = contest_id) so a contest's data lives on a bounded set of nodes and rank queries don't cross the whole cluster.
  • Each verdict does an O(log N) update to a per-contest sorted index (see 7.2). Top-K and around-me reads are O(K).
  • The Scoreboard Service subscribes to grid change events and pushes rank deltas over WebSocket/SSE rather than clients polling — this is what makes updates feel instant and keeps egress sane (see the 4.6 bandwidth callout).
Figure 6. Live leaderboard architecture: the in-memory grid is the sole strongly-consistent authority for live standings; the Scoreboard Service pushes rank deltas over WebSocket rather than serving polling reads, while Cassandra receives a parallel durable audit write it is never read from during the contest.

Reconciling grid ↔ durable Cassandra:

  • Every scored verdict is also appended to contest_submissions (salted) — the durable audit log. The grid is the fast authority during the contest; Cassandra is the durable record.
  • The grid runs with persistence enabled + synchronous replicas (ACID + replicas + persistence), so a node loss doesn't lose live standings (see Replication and Fault Tolerance).
  • On end_time, the Contest Service performs a snapshot flush: it reads final standings from the grid, writes past_contest_results to Cassandra, and validates by replaying contest_submissions through the scoring function — if the recomputed standings match the grid snapshot, we publish; if they diverge (should never happen), the Cassandra recomputation is authoritative because it's derived from the immutable submission log. After flush, live reads are redirected to the read-only past-contest DB and the grid partition is evicted.
Figure 7. Grid ↔ Cassandra reconciliation at contest end: the snapshot from the grid and a full replay of the durable submission log are cross-validated before publishing final standings, with the immutable log winning any divergence.

10b. Judge correctness, idempotency & exactly-once scoring

  • Idempotent judging: verdict is a pure function of (solution_id, test_set_version); re-judging is safe.
  • Re-submission handling: each submission is a new solution_id. Practice keeps full history; contest scoring only cares about the first accept per problem and counts prior rejects — later submissions to an already-solved problem are ignored (see if (p.solved) return; in 7.2).
  • Exactly-once scoring despite Kafka redelivery: Kafka gives at-least-once; a verdict_ready event can be redelivered on consumer rebalance/retry. We make the effect exactly-once:
    1. The scoring transaction records processedSolutionIds inside the Standing (grid) and checks it first (if (s.hasScored(solutionId)) return;). Because dedupe state and the score update commit in the same ACID transaction, a redelivered event is a no-op.
    2. Per-user ordering is guaranteed by keying the topic on (contest_id, user_id) (see Data Sharding), so "first accept" and reject counts are computed against the true submit order.
    3. Consumer offsets are committed only after the transaction commits (process → commit-side-effect → commit-offset), so a crash between processing and offset-commit replays the event, which the dedupe check absorbs.

10c. Live interview session real-time sync

  • Transport: WSS to the Realtime Collaboration Gateway; connection pinned (sticky, consistent-hash by session_id) to the Session Server that owns the doc.
  • Concurrency model: the Session Server is the single writer. v1 = server-authoritative sequenced broadcast: each edit gets a monotonic seq; the server applies and rebroadcasts {op, seq, author}; clients apply in seq order and buffer/reorder out-of-order arrivals. v2 (if free-form multi-cursor editing needs it) upgrades to OT or a CRDT (e.g. Yjs) so concurrent inserts converge without a round-trip to the server for every keystroke.
  • Presence: heartbeats over the socket; presence + cursor positions fan out via Redis pub/sub so all Session Server replicas see join/leave/typing. TTL-based expiry removes ghosts.
  • Reconnect/resume: the server keeps the last N ops + periodic snapshots. On reconnect the client sends its last-seen seq; the server replays the delta (or ships a fresh snapshot if the client is too far behind). The document is periodically checkpointed to Redis/S3 so a Session Server crash loses at most the last checkpoint interval; a standby takes over the session_id and rehydrates from the checkpoint + op log.
  • Recording pipeline: the ordered, timestamped op stream is appended to S3 (the "code timeline"); AV is recorded by the SFU provider and its URL stored on the session. Playback replays ops against wall-clock offsets aligned to the AV timeline. Shared "Run" reuses the Code Executor; output is broadcast over the same socket.
Figure 8. Interview session reconnect/resume: the Session Server buffers recent ops and periodic checkpoints so a dropped connection can resume via delta replay (or a fresh snapshot if too far behind) without losing edits.

Circuit breakers & graceful degradation

  • Practice/Contest services wrap Code Executor and downstream DB calls in circuit breakers (e.g., Resilience4j). If the executor pool is saturated, submissions are accepted and queued (202 PENDING) rather than rejected; the user sees "queued", protecting the SLA shape.
  • Leaderboard degradation during a contest: if the grid is under stress or a region is degraded, leaderboard reads fail over to replicas / a short-TTL cached snapshot serving stale-but-available ranks (banner: "updated N seconds ago"), while the write/scoring path stays strongly consistent.
  • Bulkheads: the interview real-time plane, the judge, and the request/response services have isolated thread pools and capacity so a contest spike cannot starve interviews (and vice versa).
We degrade reads before we ever degrade scoring
A wrong-but-available leaderboard is tolerable for a few seconds — a banner saying "updated N seconds ago" is a minor UX blemish. Wrong scoring is not tolerable at all, since it directly determines contest outcomes and is effectively "money on the line." So every degradation path in this system is designed to shed load on the read side first (stale cached snapshots, replica reads, coalesced fan-out) while the write/scoring path on the ACID grid keeps its consistency guarantees intact until it is physically impossible to serve it — at which point we queue and shed new submissions rather than accept them with weaker guarantees.

Monitoring, Logging, Analytics & Notifications

Key SLIs / metrics

  • Judge: end-to-end verdict latency (submit → verdict) p50/p95/p99; executor queue depth; sandbox utilization; per-language compile/run failure rate; retry rate; sandbox-teardown/escape alarms.
  • Leaderboard: rank-update lag (verdict-commit → client push) p95 (< 1 s SLO); grid transaction latency; WebSocket fan-out delivery lag; connected-client count.
  • Submission pipeline: submission success rate (accepted-for-processing / attempted), Kafka consumer lag per topic, DLQ size.
  • Contest health: active participants, submissions/s vs capacity, executor autoscale headroom, board-freeze status.
  • Interview plane: WS reconnect rate, op-apply latency, presence accuracy, recording upload success.
  • Infra: MySQL replication lag, Cassandra LOCAL_QUORUM latency, grid backup sync lag, S3 request throttling.

Logging pipeline via Kafka

All services emit structured logs/audit events to Kafka audit/logs topics (as drawn on the reference whiteboard). A logging consumer group ships them to a search/observability store (ELK/OpenSearch) and cold storage. Kafka decouples log volume spikes (contest finale) from the log store. Submission audit events are the source of truth for disputes ("prove my submission was at T").

Analytics use cases

  • Question difficulty calibration — compute real acceptance rate, avg attempts-to-solve, time-to-solve distributions; reclassify difficulty vs the authored label.
  • Contest participation funnels — registered → joined → first-submission → first-accept → finished; find drop-off (e.g., problem 3 is a wall).
  • Fraud/abuse signals — anomalous submission timing, mass identical solutions (feeds plagiarism), clock-skew exploitation attempts.
  • Capacity planning — submission arrival curves to right-size the executor autoscaler and grid.

Notification triggers

  • "Contest starting in 15 min" (scheduled, from contest config).
  • "Your rank changed / you were overtaken" (from score_updated, throttled/coalesced to avoid spam).
  • "Contest results & plagiarism outcome published."
  • "Interview session invite / reminder / it's starting now."
  • Streak reminders, "new questions in your favorite tag." Delivery via email/push/in-app; per-user preference + rate limits.

Security Considerations

  • Sandbox escape prevention — untrusted code runs in Firecracker microVMs / gVisor (not bare containers) with network=none, read-only rootfs, dropped Linux capabilities, seccomp syscall allowlist, non-root uid, cgroup CPU/mem/pids caps, and per-execution teardown. No secrets, no cloud metadata endpoint (169.254.169.254 blocked), no shared writable volumes. Executor hosts run on an isolated network segment with egress firewalled.
  • Rate limiting submissions — per-user and per-IP token buckets at the API Gateway; stricter caps during contests (e.g., max N submissions/min per problem) to stop brute-forcing hidden tests and to protect the judge. Compile/run abuse (crypto-mining via "Run") is bounded by wall-time/CPU caps and cost accounting per user.
  • Contest question leakage prevention — questions are gated: GET /contests/{id}/questions returns 403 until start_time (server-clock enforced). Test-case blobs are never sent to the client; only sample I/O is public. Per-contest question sets can be freshly authored/embargoed; access to Cassandra Q&TC is service-only (no direct client path). Detect leakage via analytics (someone solving instantly at T=0).
  • Clock-skew / late-submission exploitation — the server timestamps submissions at ingress; end_time is enforced against the server clock, never the client's. Requests arriving after end_time (even with a client-forged earlier timestamp) get 409 CONTEST_ENDED. A small server-side grace for in-flight requests is defined explicitly and applied uniformly (see the follow-up Q&A below). NTP-synced servers; the ingress timestamp is the one written to the audit log and used for penalty math.
  • Interview session access control — signed, single-use, time-boxed join tokens per role (interviewer vs candidate); candidate tokens can't reach interviewer-only endpoints (rubric, notes, other questions, feedback). Session membership checked on every WS message. Recordings are access-controlled to the hiring org; AV media is brokered by the SFU with short-lived tokens.
  • General — TLS everywhere, JWT with short expiry + refresh, WAF at the edge, PII encryption at rest, audit trail for admin actions (contest config changes, disqualifications), and least-privilege service credentials (client code paths can never read the Q&TC store directly).

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design.

Scoring, Sharding & Consistency

How do you prevent a hot partition when 50K users submit to the same contest_id in the last 60 seconds?
Salt the partition key: PRIMARY KEY ((contest_id, bucket), …) with bucket = user_id % B, spreading writes across B replica sets instead of one. Size B so each bucket stays under Cassandra's per-partition write ceiling. Mirror the same idea in Kafka by keying on (contest_id, user_id) so one contest's events fan out across partitions while preserving per-user ordering. The live leaderboard read never hits Cassandra — it comes from the in-memory grid — so the salted layout only affects fan-out on the (rare) admin/archival read.
How do you guarantee exactly-once contest scoring if Kafka redelivers a verdict_ready event?
Kafka is at-least-once, so we make the effect idempotent. The scoring transaction stores processedSolutionIds inside the same Standing row it mutates and checks it first; dedupe-check and score-update commit in one ACID transaction on the grid, so a redelivered event is a no-op. Commit the consumer offset only after that transaction commits, so a crash mid-processing simply replays and is absorbed by the dedupe check.
How do you keep the leaderboard sub-second for 200K participants without melting the read path?
Don't poll and don't re-sort N rows per event. Maintain a per-contest sorted index in the grid (O(log N) update per verdict, O(K) top-K read), and push rank deltas to clients over WebSocket/SSE instead of full-board polling — cutting egress ≈25×. Keep exact rank only for top-K and each requester's own row; refresh full absolute ranks on a 2–5 s cadence.
In-flight requests at end_time — accept or reject? How do you make it fair?
Define an explicit, uniform policy up front, e.g., "a submission counts if it was received at the gateway before end_time," and stamp receipt time at ingress before any queueing. Apply the same rule to everyone; publish it in contest rules. Optionally a fixed, announced grace (e.g., 0 s or a defined buffer) — the key is that it's deterministic and based on server-side receipt, not on when judging happens to finish.
Why an in-memory grid for live scoring but Cassandra for history — why not one store?
Live scoring needs ACID read-modify-write on multi-field standings with read-your-writes and fast top-K over 200K rows; Cassandra's eventual consistency and lack of transactional RMW make it wrong for that path. Cassandra is ideal for the durable, write-once, read-mostly historical record with high durability (RF=3) and cheap storage. We use each for what it's good at and reconcile at contest end by snapshot-flush + replay validation.
Read-your-writes vs eventual consistency — where exactly is each required, and how do you implement RYW on the leaderboard?
Strong/RYW is required for the submitting user's own standing and submission history, and for contest scoring/end_time enforcement. Eventual is fine for other users' leaderboard rows, practice aggregates, analytics, and plagiarism. RYW on the board is delivered by having the scoring transaction commit to the grid and immediately push the requester's updated row/rank to their socket; other users' rows may propagate a beat later via the delta stream or a short-TTL cached snapshot.
Two accepted submissions to the same problem — how are penalty and "solved" computed correctly under reordering?
Only the first accept solves the problem and freezes its penalty (minutes-from-start + 20×prior-rejects); later submissions to a solved problem are ignored. Correctness under reordering is guaranteed by per-user ordering on the Kafka partition (keyed by (contest_id, user_id)), so events for one user hit the scorer in submit order, and by the idempotent dedupe on solution_id inside the ACID scoring transaction.
Storage is growing ≈13 TB/year of submissions and ≈330 GB/year of MySQL index. How do you keep it sustainable?
Compress code blobs (≈4:1) and tier S3 to infrequent-access at 90 days and Glacier at 12 months; keep only pointers + verdict in MySQL, never code. Shard MySQL by user_id so the index grows horizontally, and archive/partition old user_solutions_index rows by time. The billed driver is S3 request count (2.7B PUTs/year), mitigated by batching tiny objects and lifecycle rules — raw byte cost is minor.

Judge, Security & Fault Tolerance

A code-executor microVM hangs or looks compromised mid-judge. What happens to that submission and the fleet?
The sandbox is disposable: hard wall-time/CPU limits SIGKILL it, the host tears down the microVM, and the submission is retried on a fresh sandbox (safe because judging is idempotent — pure function of (solution_id, test_set_version)). A bounded retry count guards against poison inputs (→ DLQ + manual review). Executor hosts sit behind a queue and on an isolated network segment, so one bad execution can't affect neighbors or leak data.
How would you detect and handle a participant exploiting clock skew to submit after contest end?
The client clock is never trusted: the server timestamps at ingress and enforces end_time against the server clock, returning 409 CONTEST_ENDED for anything arriving late regardless of client-supplied times. Servers are NTP-synced; the ingress timestamp is what's written to the immutable audit log and used for penalty math. Any client-forged timestamp is ignored, and repeated late attempts surface as an abuse signal in analytics.
The in-memory grid loses a node mid-contest. Do live standings survive?
Yes. The grid runs with synchronous backups (primary + ≥1 backup on another node/AZ) and native persistence (WAL). Node loss promotes the synchronous backup with zero standings loss; a restart replays the WAL. Worst case (loss of a whole affinity group) is recoverable by replaying the durable, salted contest_submissions log through the deterministic scoring function.
How do you handle a submission storm that exceeds executor capacity without dropping submissions or blowing the SLA?
Accept-and-queue: the API returns 202 PENDING, the submission goes on a bounded queue, and the executor fleet autoscales on queue depth. Circuit breakers around the executor shed load gracefully (queue, don't 500). We provision for a committed drain rate tied to the "verdict within 10 s" SLA rather than instantaneous arrival, and pre-warm a microVM pool to avoid cold-start latency during the burst.
How does the plagiarism check avoid being fooled by variable renaming and reformatting, and why is it off the hot path?
It tokenizes and canonicalizes (strip comments/whitespace, rename identifiers to positional tokens, normalize literals) before fingerprinting, so cosmetic changes don't alter the token stream. It then uses MOSS-style k-gram winnowing fingerprints and Jaccard similarity within a (contest, question) cohort, subtracting shared starter-code fingerprints. It runs as a Kafka consumer off contest.ended because it's O(N²)-ish and latency-tolerant — putting it on the submit path would wreck judge latency.
How do you prevent contest question/test-case leakage, and detect it if it happens?
Questions are gated behind server-clock start_time (403 before), hidden test blobs never leave the server (only sample I/O is public), and the Q&TC store is reachable only by services, never by a client path. Per-contest sets can be freshly authored and embargoed. Detection is analytics-driven: instant solves at T=0, abnormally high first-attempt accept rates, or clusters of near-identical early solutions feed the abuse/plagiarism pipeline and trigger review/disqualification.

Interview Sessions & Extensions

How do you support real-time collaborative editing in interviews, and what breaks at scale/conflict?
v1 is a server-authoritative sequenced broadcast: the Session Server is the single writer, stamps each edit with a monotonic seq, and rebroadcasts; clients apply in order. This is simple and correct but serializes through the server. If simultaneous free-form multi-cursor editing causes contention or laggy round-trips, upgrade to OT or a CRDT (e.g. Yjs) so concurrent edits converge locally without a server round-trip per keystroke. Presence/cursors fan out via Redis pub/sub across Session Server replicas.
An interviewer or candidate drops their connection mid-session. How do you resume without losing work?
The Session Server keeps the last N ops plus periodic snapshots (checkpointed to Redis/S3). On reconnect the client sends its last-seen seq; the server replays the delta or ships a fresh snapshot if it's too far behind. Connections are sticky by session_id; if the owning Session Server itself dies, a standby takes over the session and rehydrates from the latest checkpoint + op log, losing at most one checkpoint interval.

Key Takeaways

Remember
Frame this system around three surfaces with three different consistency postures sharing one platform: Practice is read-heavy and tolerant of eventual consistency; Contests demand a strongly consistent, exactly-once scoring path (the ACID in-memory grid) that never gets slower even when reads degrade; Interview Sessions are a real-time collaboration product bolted onto the same judge and identity layer. The single most important design-driving number in the whole system is the 200 MB/s naive-polling egress that forces a push-based, delta-diffed leaderboard down to ≈8 MB/s. The single most important sharding lesson is the contest_submissions hot partition — recognize the symptom (one contest_id absorbing 3,333 writes/s), apply the fix (salt with bucket = user_id % B), and know exactly which reads get more expensive in exchange (the rare admin fan-out query, never the live leaderboard). The judge is stateless and idempotent by construction, which is what makes disposable sandboxes, safe retries, and exactly-once scoring despite Kafka's at-least-once delivery all fall out of the same design principle. And the guiding operational rule under stress is simple: degrade reads before you ever degrade scoring.
