SYSTEM DESIGN

Designing CricInfo / CricBuzz

A complete, interview-ready design walkthrough for a live sports score platform in the style of Cricbuzz, ESPN Cricinfo, or Yahoo Sports: requirements and capacity estimation (including the cache-offload math that is the heart of this design), API design, high-level architecture, low-level domain and service classes, database schema, matchId-based sharding and the "hot match" problem, feature-specific logic (delta computation, Varnish request-coalescing, circuit breaking, token-bucket rate limiting, WebSocket binding and failover), replication and fault tolerance, monitoring/logging/analytics/notifications, and a bank of follow-up interview questions with full answers.

Problem Statement & Scope

Design a live sports score platform — think Cricbuzz, ESPN Cricinfo, or Yahoo Sports — that ingests live match data (cricket, hockey, and other sports) from external feeds and fans it out at scale to three very different classes of consumers: mobile/app users, browser users, and third-party servers that resell or embed the data (e.g. Dream11 pulling live scores to settle fantasy contests, news sites embedding a live scorecard widget).

The product has two faces. First, a live score & commentary product — ball-by-ball commentary, real-time scorecards, notifications for key events (wicket, century, match start/end), and search over historical matches. Second, a public/partner data API — third parties pay (or are metered) for programmatic access to the same live data, with SLAs, rate limits, and API keys.

Why this is a hard/interesting problem
It is a read-heavy, write-light system taken to an extreme: during a marquee match (e.g. India vs Pakistan), millions of clients poll/subscribe to a handful of "hot keys" (one per live match), while the actual source-of-truth update rate is one event every 30–90 seconds (a ball, a goal, a substitution). The whole design is about fanning out a trickle of writes to a firehose of reads without melting the origin. It also combines request/response REST APIs, long-lived WebSocket connections at scale, cache-stampede protection, and multi-tenant rate limiting/billing in one system — a good vehicle to demonstrate breadth in an interview. And traffic is extremely spiky and predictable-yet-unpredictable: known in advance (match schedule) but the actual QPS curve depends on match context — a last-over run chase generates 10x the baseline QPS of the same match's 10th over.

In scope

  • Live score ingestion from external feeds
  • Ball-by-ball (or event-by-event) commentary
  • Real-time push (WebSocket) and pull (REST/AJAX) delivery
  • Third-party partner API with rate limiting and billing metering
  • Search/browse of historical matches
  • Key-event notifications (wickets, milestones, match start/end)
  • Capacity planning, HLD/LLD, schema, sharding, fault tolerance, observability

Out of scope

Called out explicitly to the interviewer, then set aside:

  • Live video streaming
  • In-app payments / fantasy scoring engine itself (Dream11 is a consumer of this system, not part of it)
  • User-generated content (comments/forums) moderation
  • Ad serving logic

Assumptions & Constraints

Explicit assumptions (given)

  • A propagation delay of 2–3 seconds from real-world event to client display is acceptable. This is the foundational assumption that justifies polling intervals, 1-second Redis TTLs, and eventual consistency throughout the design.
  • Rate limiting must exist for third-party API consumers, tied to an api_dev_key, to prevent abuse and to support metered billing.

Additional reasonable assumptions made for this design

  • No user-generated content (comments, forum posts, chat) is in scope — no moderation pipeline needed.
  • The External Score Updater is the single source of truth for live data; the rest of the system (Product API, caches, WebSocket layer) is purely a distribution/fan-out mechanism and never originates score data.
  • Core APIs are polyglot and independently deployable per sport (cricket-core-api, hockey-core-api, …) — different sports have different scoring rules/state machines, and isolating them limits blast radius (an incident in hockey scoring logic can't take down cricket).
  • Historical match data is retained for a minimum of 5 years for search/analytics purposes (regulatory/product decision, tunable).
  • A "live match" universe at any instant is bounded (tens, not millions) — even during the busiest global sports day, the number of concurrently live matches across all supported sports is on the order of 10–50; it's the reader fan-out per match, not the number of matches, that creates scale pressure.
  • Mobile/app clients can hold persistent WebSocket connections; a meaningful fraction of browser clients cannot (proxies, corporate firewalls, older browsers) and fall back to AJAX polling.
  • Third-party servers never hold WebSocket state with us — they always pull via REST (simpler integration contract for partners).

Capacity Estimation and Constraints

Always state assumptions explicitly, then derive numbers — interviewers care about the method, not decimal precision. This section walks through traffic estimation, the cache-offload math that is the core engineering insight of the whole design, storage estimation, WebSocket fan-out bandwidth, and instance sizing.

Traffic estimation

Assumption Global DAU = 50,000,000 (given assumption for a large cricket-focused product)
Concurrent viewers during a marquee live match = 2.5M – 5M (5–10% of DAU tune in concurrently during e.g. India vs Pakistan)
Peak Product API QPS = 5,000 req/sec (given — driven by AJAX-polling browser clients + partner polling + app clients doing periodic REST fetches; not all 5M viewers are on WebSocket, see WebSocket fan-out below)
Core API QPS target = 1–2 req/sec per live data point — a result of the caching chain, not an input; this is the number the whole design engineers towards

Cache offload math (the heart of the design)

Why this is the heart of the design
Every other component in this architecture — Redis, Varnish, the circuit breaker, even the decision to split Core API per sport — exists to protect or extend one single ratio: turning 5,000+ reads/sec at the edge into ~1–2 writes/sec of actual load on the source-of-truth tier. Get this math right and almost everything downstream (instance counts, fault-tolerance strategy, even the choice of NoSQL replica sizing) falls out of it directly.

Given: Redis cache TTL = 1 second, incoming Product API read rate = 5,000 req/sec for a single match's score key.

Within any 1-second TTL window 1st request → cache miss → fetch from Core API, populate cache (1 request reaches Core API)
Remaining requests in that same window → cache hit, served from Redis (4,999 requests absorbed)
Offload ratio = 4,999 / 5,000 = 99.98%
Core API load = 5,000 req/sec × (1 − 0.9998) ≈ 1 req/sec (matches the 1–2 req/sec target)

This is why the TTL is tuned to 1 second: it is short enough that data staleness (max 1s) fits comfortably inside the 2–3 second acceptable-delay budget, yet long enough that it collapses 5,000 reads/sec down to ~1 read/sec against the expensive Core API tier.

The catch — and why Varnish exists
At the exact instant the 1-second key expires, if all 5,000 concurrent requests happen to arrive within the same few-millisecond window (very likely under sustained high QPS), naively all 5,000 would see a cache miss simultaneously and stampede the Core API — a classic thundering herd. Varnish's request-coalescing sits directly in front of Core API specifically to convert "5,000 simultaneous misses" back down to 1 actual upstream call, with the other 4,999 callers blocked/parked and served the same response once it returns.
Combined effect Steady state (mid-TTL-window): ~1 req/sec reaches Core API (Redis absorbs the rest)
Worst case (TTL-expiry stampede): ~1 req reaches Core API per expiry event (Varnish collapses the burst)
→ Core API sees a near-constant ~1–2 req/sec regardless of front-end QPS, by design.
Figure 1. Cache-offload math end to end: Redis absorbs steady-state reads at a 99.98% hit ratio, and at the instant a key expires, Varnish's request-coalescing collapses the resulting stampede of simultaneous misses into exactly one upstream Core API call.

Storage estimation (match/ball-event data, 5-year retention)

Assumptions: average ~500 discrete events per match (blended across T20 ~240 balls, ODI ~600 balls, Test ~2,000+ balls, plus hockey-style event streams), each raw event ≈ 200 bytes (compact structured payload: over, ball, runs, wicket flag, players, timestamp). Commentary text adds roughly one entry per event, ~150–300 bytes each.

Per match (raw) Raw ball/event data: 500 events × 200 bytes = 100,000 bytes (~100 KB)
Commentary text: 500 entries × 250 bytes (avg) = 125,000 bytes (~125 KB)
Scorecard / snapshot / metadata overhead (est.) = ~50 KB
Total per match (raw) ≈ 275 KB

Match volume: across all supported sports and leagues worldwide (international fixtures, domestic T20/ODI leagues, county cricket, hockey pro leagues, etc.) assume an average of ~200 matches/day globally.

5-year footprint Matches over 5 years = 200 matches/day × 365 days × 5 years = 365,000 matches
Raw storage = 365,000 matches × 275 KB ≈ 100 GB
With 3× replication factor (NoSQL, cross-AZ) = 100 GB × 3 ≈ 300 GB
With index overhead (~30%) ≈ 390 GB total footprint over 5 years

Takeaway: the historical dataset is not the hard problem in this system (it's a manageable few hundred GB) — the hard problem is the read amplification on live matches, which storage size alone doesn't capture.

WebSocket fan-out bandwidth estimation

During a marquee match with 2.5M–5M concurrent viewers, assume the following split across delivery channels:

ChannelShareConcurrent count (at 5M peak)
Mobile/app via WebSocket60%3,000,000
Browser via AJAX polling (fallback)30%1,500,000
Third-party servers via REST (not persistent)10%~500,000 effective pull rate, folded into Product API QPS
Bandwidth WebSocket push payload size (delta update, JSON) ≈ 500 bytes
Push frequency per connection (matches 2–3s delay budget, throttled to real event cadence) ≈ 1 update / 2.5 sec average
Aggregate egress bandwidth = 3,000,000 sockets × 500 bytes / 2.5 sec = 3,000,000 × 200 bytes/sec = 600,000,000 bytes/sec
= 600 MB/sec ≈ 4.8 Gbps sustained egress across the WebSocket handler fleet

Handler fleet sizing: assuming each WebSocket handler node comfortably holds 50,000 tuned persistent connections (typical ceiling for an event-loop based server, e.g. Netty/Node, with OS ulimit tuning):

Fleet size Nodes needed = 3,000,000 / 50,000 = 60 nodes
+ redundancy (N+2 / rolling deploys, failover headroom) ⇒ ~65–70 nodes

Instance sizing for Product API / Core API

Product API Peak load = 5,000 req/sec
Per-instance capacity = ~500 req/sec (simple cache-fronted read, JSON serialize, auth check)
Base instances needed = 5,000 / 500 = 10
With 2x headroom (burst/failover) = ~20 instances (per region)
Across 3 active regions = ~60 instances globally
Core API (per sport) Concurrent live matches (worst case, global) ≈ 20–50 across all sports
Load per match (post-cache-offload) ≈ 1–2 req/sec
Total Core API load ≈ 20–50 × 2 = 40–100 req/sec (aggregate, all sports)
Per-instance capacity (heavier compute) ≈ 100 req/sec
Instances needed per sport (HA minimum = 3) ⇒ e.g. cricket-core-api: 3–4 nodes, hockey-core-api: 2–3 nodes, etc.

The contrast is the entire point of the design: Product API needs ~60 lightweight instances to survive 5,000 req/sec, while Core API needs only a handful of instances per sport because the caching chain has already absorbed 99.98%+ of the traffic before it gets there.

High-Level Design

Narrative walkthrough

Three client types enter the system: mobile/app users and browser clients (using AJAX polling as a fallback when WebSockets aren't viable) hit the API Gateway, and third-party servers (Dream11, news sites) hit the same gateway via a public REST surface with an API key.

The API Gateway is the single front door and is responsible for: SSL termination, authentication (user login sessions), authorization (role-based — end user vs. partner vs. admin), offloading static content to a CDN, rate limiting and billing metering for third-party API keys, and circuit breaking at the edge.

Behind the gateway there are two API tiers. Product API faces all frontend/user traffic directly, built for very high QPS (5,000 req/sec at peak during a big live match); it is thin — parse request, check the cache, serialize response. Core API is heavier, slower, and split per sport (cricket-core-api, hockey-core-api, …), each independently deployable/scalable. It does the real domain logic: assembling scorecards, computing run rates, resolving match state. It's engineered to receive only 1–2 req/sec per data point, thanks to everything sitting in front of it.

Between Product API and Core API sits the caching chain, the core of the design. First, Redis cache (1-second TTL) absorbs 4,999 of every 5,000 reads. The Product API also continuously pushes delta updates into this same Redis layer as new data arrives ("push delta changes") so that the "get updates" read path always finds fresh-enough data without hitting Core API. A reporting/logging sink taps off this Product API cache layer for analytics. Second, Varnish sits directly in front of Core API. When the Redis key expires, it collapses many simultaneous identical requests into a single upstream Core API call and fans the one response back out to all waiters (request coalescing), preventing a thundering herd at the exact TTL-expiry instant. Third, a circuit breaker (Hystrix-style) sits before Varnish/Core API. If Core APIs are stuck or overloaded (e.g. several simultaneous live games spiking aggregate load), the breaker trips open, stops sending requests downstream, and the system fails fast / serves the last known-good cached value instead of queuing requests against a struggling backend.

Core API reads/writes the NoSQL database, which is also the landing zone for the External Score Updater — an ingestion component that receives automated live updates from stadium data feeds or screen-reader/OCR pipelines, normalizes them into generalized raw data (score, commentary, event), and pushes them into the NoSQL DB / Core API layer. This is the single source of truth for live data; everything above it is a distribution mechanism.

On the real-time push side, a pool of WebSocket Handlers maintains persistent connections to mobile/app and browser clients. Because handler nodes are stateless and horizontally scaled, a WebSocket Manager coordinates the pool and maintains a Redis mapping/binding table (which user → which handler instance/connection), since any given user's live socket could be sitting on any node at any time. When new data lands, it flows API Gateway → WebSocket Handlers → the specific bound connections for interested users. Browser clients that cannot hold a WebSocket (proxy/firewall constrained) fall back to AJAX polling through the ordinary API Gateway → Product API path. Third-party servers never hold sockets — they always use plain REST through the gateway.

Service / infra classes

// Ingests the normalized feed from stadium/OCR sources; single writer path to NoSQL + cache
class ScoreIngestionService {
  onRawEvent(feedSourceId: string, rawEvent: RawFeedPayload): void
  normalize(rawEvent: RawFeedPayload): BallEvent
  reconcile(existing: BallEvent, incoming: BallEvent): BallEvent   // conflict resolution across redundant feeds
  persist(matchId: string, event: BallEvent): void                // writes NoSQL, bumps Match.currentVersion
  publishDelta(matchId: string, event: BallEvent): void            // hands off to DeltaCacheUpdater
}

// Computes and pushes incremental diffs into Redis rather than re-fetching whole documents
class DeltaCacheUpdater {
  computeDelta(previous: ScoreSnapshot, current: ScoreSnapshot): Delta
  applyDelta(matchId: string, delta: Delta): void      // Redis: merge into match:{matchId}:score
  pushToSubscribers(matchId: string, delta: Delta): void  // hands off to WebSocketConnectionRegistry
}

// Hystrix-style breaker guarding Core API
class CircuitBreakerPolicy {
  state: enum { CLOSED, OPEN, HALF_OPEN }
  failureThreshold: int
  resetTimeoutMs: int
  recordSuccess(): void
  recordFailure(): void
  allowRequest(): boolean   // false when OPEN -> caller falls back to stale cache
  attemptReset(): void      // transitions OPEN -> HALF_OPEN after timeout
}

// Owns the user <-> WebSocket handler node binding (backed by Redis binding table)
class WebSocketConnectionRegistry {
  bind(userId: string, handlerId: string, connectionId: string): void
  unbind(userId: string): void
  lookup(userId: string): HandlerBinding?
  routeMessage(userId: string, payload: object): void   // finds handler node, forwards via internal RPC
  onHandlerNodeDown(handlerId: string): void             // triggers rebind/reconnect for affected users
}

// Token-bucket limiter keyed by partner api_dev_key
class RateLimiter {
  capacity: int             // bucket size, e.g. 1000
  refillRatePerSec: float
  tryAcquire(apiDevKey: string, cost: int = 1): boolean
  remaining(apiDevKey: string): int
  resetTimestamp(apiDevKey: string): long
}

End-to-end sequence: "external update arrives → propagated to a live client"

  1. Stadium feed / OCR screen-reader emits a raw event ("wicket, over 32.6") → External Score Updater receives it on one of possibly multiple redundant feed connections.
  2. External Score Updater normalizes the payload and hands it to ScoreIngestionService.onRawEvent(). If a second, independent feed reports the same ball with conflicting details, reconcile() applies a resolution policy (e.g. majority-feed-agreement, or "official data provider" feed wins) before persisting.
  3. ScoreIngestionService.persist() writes the new BallEvent + updated ScoreSnapshot to the NoSQL DB, bumping Match.currentVersion.
  4. ScoreIngestionService.publishDelta() invokes DeltaCacheUpdater, which computes the diff versus the last known snapshot and calls applyDelta() to merge it into the Redis cache key match:{matchId}:score (this is the "push delta changes" sub-flow feeding the Product API cache layer). The reporting/logging sink also receives a copy of this delta for analytics.
  5. DeltaCacheUpdater.pushToSubscribers() calls into WebSocketConnectionRegistry, which looks up the Redis binding table to find, for every user subscribed to this matchId, which WebSocket Handler node currently owns their connection.
  6. The registry routes the payload to each relevant handler node (internal RPC/pub-sub); each WebSocket Handler writes the delta frame to its locally-held socket(s) for the bound users.
  7. In parallel, any browser/partner client doing a pull (GET /score or GET /commentary?since_ball=) hits the API Gateway → Product API → Redis cache; since the cache was just updated in step 4, the very next poll (within the 2–3s acceptable delay window) returns the fresh delta with no Core API involvement at all. Only if the Redis key had already expired (TTL boundary) does the read path fall through Circuit Breaker → Varnish → Core API → NoSQL, and Varnish ensures that even a stampede of simultaneous pulls at that instant results in exactly one Core API call.
Figure 3. End-to-end sequence: an external score update lands in NoSQL and Redis, then fans out over WebSocket to subscribed clients, while pull/poll clients in parallel get the same fresh delta from Redis (or, only at TTL-expiry, via the Circuit Breaker → Varnish → Core API fallback path).

Data Sharding

Primary sharding key: matchId, using consistent hashing across NoSQL partitions/replica sets. Rationale:

  • Every hot-path query (GetLiveScore, GetCommentary) is scoped to a single matchId. Sharding on it guarantees that all reads/writes for a given match are served by a single partition/replica set — no cross-shard fan-out on the critical path.
  • Consistent hashing means adding/removing shards only reshuffles a small fraction of matches, not the whole keyspace.

The "hot match" problem

Consistent hashing distributes matches roughly evenly, but it does not equalize load per match. A World Cup final or India-vs-Pakistan match can generate orders of magnitude more read traffic than a routine domestic fixture on the same shard. Mitigations:

  • Dedicated capacity / read-replica fan-out: identify marquee matches ahead of time (known schedule) and pre-provision extra read replicas for that specific match's partition, with the Product API's read path load-balancing across replicas.
  • Cache absorbs the read skew first: because Redis + Varnish already knock 5,000 req/sec down to ~1–2 req/sec before it reaches the NoSQL-backed Core API, the hot-match problem is mostly solved above the database tier — the DB shard mainly needs to survive the ingestion writes and the low-rate Core API reads, not the raw 5,000 req/sec.
  • Manual/automatic shard rebalancing: if a hot match is detected co-located with another busy match on the same physical shard, migrate one to a dedicated shard for the duration of the game.
Figure 4. Sharding on matchId via consistent hashing spreads match documents evenly across shards, but a marquee "hot match" still needs pre-provisioned, dedicated read-replica fan-out layered on top, since load-per-match is not equalized by the hash function alone.

Functional/vertical sharding of Core API per sport

cricket-core-api, hockey-core-api, etc. are independently deployed and scaled services — this is sharding along a functional axis rather than a data-key axis. Benefits: independent scaling (cricket gets 10x the traffic of hockey — provision accordingly), independent deploys/rollbacks (a bad hockey release can't take down cricket), and independent data models (cricket's innings/overs model is structurally different from hockey's period/goal model), while all sports still funnel through the same Redis/Varnish/circuit-breaker chain and the same NoSQL cluster (logically partitioned by sport + matchId).

Feature-Specific Logic

Delta computation algorithm

Goal: clients should never have to re-fetch a whole match document; they should be able to ask "give me everything since version X / since ball Y."

function computeDelta(previousSnapshot, currentSnapshot):
  delta = {}
  for field in [runs, wickets, overs, runRate, requiredRunRate]:
    if currentSnapshot[field] != previousSnapshot[field]:
      delta[field] = currentSnapshot[field]   // only changed fields included
  delta.version = currentSnapshot.version     // always bump version
  delta.newEvents = eventsSince(previousSnapshot.version)  // new BallEvents/CommentaryEntries
  return delta
  • Every Match/ScoreSnapshot carries a monotonically increasing version. Clients (and internal cache layers) can always ask since_version=N or since_ball=N and get exactly the missing slice — this is what makes both the WebSocket push path and the REST polling path efficient and idempotent (a client that misses one push can always catch up via a since_version REST call).
  • Deltas, not full snapshots, are what gets written into Redis (applyDelta merges into the existing hash rather than overwriting), which is cheaper both to compute and to transmit over the WebSocket fan-out.

Varnish request-coalescing mechanics

  • Varnish maintains, per cache key (e.g. matchId), a notion of "request currently in flight to origin."
  • When request #1 arrives for a key with no valid cached value, Varnish marks that key as "fetching" and issues exactly one upstream call to Core API.
  • Requests #2 through #N for the same key, arriving while #1 is still in flight, are parked/queued by Varnish rather than each issuing their own upstream call.
  • When the origin response returns, Varnish populates its own short-lived cache and replies to all N parked requests with that single response simultaneously.
  • Net effect: N concurrent requests → 1 upstream call, precisely the protection needed at the moment the Redis TTL boundary is crossed, when otherwise all 5,000 req/sec would hit Core API at once.

Circuit breaker state machine

  • CLOSED: normal operation, requests flow through to Varnish/Core API; failures are counted in a rolling window.
  • OPEN: tripped — failure rate (or timeout rate) exceeded threshold (e.g. multiple concurrently live games overwhelming Core API). All requests are failed fast without touching Core API; the caller (Product API) instead serves the last known-good value from Redis/local cache, even if past its normal TTL, rather than serving an error.
  • HALF_OPEN: after resetTimeoutMs, the breaker allows a small number of trial requests through. If they succeed, transition back to CLOSED; if they fail, go back to OPEN and restart the timeout.
  • This is orthogonal to Varnish: Varnish protects against a stampede on one key at TTL expiry; the circuit breaker protects against sustained Core API distress across many keys/matches (e.g. an under-provisioned Core API pod during 3 simultaneous marquee matches).
Figure 5. Circuit breaker state machine: CLOSED transitions to OPEN once the failure rate exceeds threshold; OPEN transitions to HALF_OPEN after resetTimeoutMs; HALF_OPEN returns to CLOSED on successful trial requests or back to OPEN on failed ones.

Token-bucket rate limiting per api_dev_key (with billing metering)

class TokenBucket {
  capacity: int              // e.g. 1000 tokens
  tokens: float
  refillRatePerSec: float    // e.g. 16.6/sec => ~1000/min
  lastRefillTs: timestamp

  tryAcquire(cost=1):
    now = currentTime()
    elapsed = now - lastRefillTs
    tokens = min(capacity, tokens + elapsed * refillRatePerSec)
    lastRefillTs = now
    if tokens >= cost:
      tokens -= cost
      return true    // allowed; X-RateLimit-Remaining = floor(tokens)
    return false      // 429, Retry-After = ceil((cost - tokens) / refillRatePerSec)
}
  • Bucket state lives in Redis (ratelimit:{apiDevKey}:bucket), shared across all API Gateway nodes so the limit is enforced globally per key, not per node.
  • Every accepted request also increments a billing/usage counter (partner:{apiDevKey}:usage:{date}) independent of the rate-limit bucket itself — rate limiting protects capacity in real time; the usage counter feeds the monthly billing pipeline. Different partner tiers (free, paid, enterprise) simply get different capacity/refillRatePerSec configs.

WebSocket-to-user binding, reconnection & handler-node failover

  • On connect, WebSocket Manager assigns the client to a handler node (e.g. least-connections load balancing) and writes ws:user:{userId}:handlerId → {handlerId, connectionId} into the Redis binding table.
  • To push a message to a user, any producer (DeltaCacheUpdater) asks the registry to lookup(userId), gets the owning handler node, and forwards the payload to that node over internal RPC/pub-sub — the producer never needs to know which physical node holds the socket.
  • Handler node death: each handler renews a heartbeat key (ws:handler:{handlerId}:heartbeat, short TTL). If the WebSocket Manager detects a missed heartbeat, it treats all bindings pointing at that handler as stale, proactively invalidates them, and the affected clients' next reconnect attempt (client-side exponential backoff, standard practice) gets rebound to a healthy node — old socket is simply gone, client library reconnects and resubscribes to its matchId, and catches up via since_version so no events are silently lost even though a few seconds of push delivery were interrupted.
  • Idempotent resubscription plus the version-based delta protocol means a dropped connection never causes a missed event — only a bounded delay in delivery, which is within the accepted 2–3s tolerance if reconnection is fast, or a slightly longer but self-healing gap otherwise.
Figure 6. WebSocket fan-out and binding: incoming deltas hit the WebSocket Manager, which consults the Redis binding table to resolve userId → owning handler node, then forwards the payload to only that node for delivery to the bound socket.

Follow-up Interview Questions

Interviewers commonly push into these areas after the base design. Grouped below by theme so you can rehearse how you'd actually talk through each one out loud.

Ingestion, Caching & Consistency

What happens if the External Score Updater receives conflicting data from two independent feeds (e.g., stadium feed says "4 runs", OCR feed says "6 runs")?
ScoreIngestionService.reconcile() needs an explicit conflict-resolution policy — e.g., trust a designated "official" feed over a screen-reader/OCR feed, require N-of-M feed agreement before committing, or hold the ambiguous ball briefly (within the 2–3s budget) pending a second corroborating source, and log all conflicts for offline review.
How do you guarantee no missed ball events if a WebSocket handler crashes mid-match?
Because every event carries a monotonically increasing version/sequenceId, no delivery mechanism needs to be lossless — a client detects a gap on reconnect and calls GetCommentary(matchId, since_ball=lastSeen) to backfill. The push channel is a latency optimization, not the source of truth.
Why is the Redis TTL exactly 1 second — why not 5 or 0.1?
It's a trade-off between staleness and Core API offload: 1s keeps staleness well inside the accepted 2–3s end-to-end delay while still collapsing 5,000 req/sec down to ~1 req/sec. A much shorter TTL raises Core API load roughly proportionally; a much longer TTL risks visibly stale scores during high-drama moments (e.g. a wicket).
How is Varnish different from the Redis cache — why do you need both?
Redis is the primary data cache with delta-aware updates and a 1s TTL, absorbing steady-state read volume. Varnish is a request-coalescing layer that only matters at the instant a Redis key expires, converting a burst of simultaneous cache-misses into one upstream call — it protects against a temporal stampede that Redis's TTL alone can't prevent.
What consistency guarantee do you actually provide, and is it good enough?
Eventual consistency with a bounded staleness window (~1–3s) at the read/cache layer; the NoSQL write path itself should be strongly consistent per-match (single primary per shard) so the source of truth is never ambiguous — only the cached view of it is eventually consistent.

Scaling, Sharding & Ops

How do you handle a hot/viral match generating 10x the expected traffic (e.g., an unexpectedly close finish)?
Pre-provisioned capacity is based on schedule, but real load can spike organically. Mitigate with auto-scaling on Product API/WebSocket handler pools keyed off real-time QPS metrics, dedicated read-replica fan-out for the specific hot matchId shard, and leaning harder on the Redis+Varnish chain since Core API load stays flat regardless of front-end QPS by design.
How do you prevent a third party like Dream11 from scraping/overloading the system beyond their rate limit using multiple API keys?
Rate limiting alone isn't sufficient; pair it with partner-level anomaly detection (unusual key-creation velocity, correlated IP ranges), contractual API terms, and optionally IP/ASN-based secondary throttling in the gateway independent of the per-key token bucket.
How would you shard/scale the commentary collection differently from the score collection?
Both can share matchId as the shard key, but commentary has a much higher per-match document count (append-heavy, hundreds of entries); consider a wide-column/append-optimized store (Cassandra-style) for commentary specifically, while score snapshots (small, frequently overwritten) fit a simpler document/KV model.
How do you test/validate the circuit breaker and Varnish coalescing actually work under load?
Chaos/load testing: inject synthetic Core API latency/failure and confirm the breaker trips within the configured failure-rate window and that stale-cache fallback serves correctly; separately, fire N concurrent identical requests at a cold cache key and assert exactly one upstream Core API call is observed (Varnish log/metric assertion).
Why split Core API per sport instead of one generic Core API with a sport-agnostic schema?
Different sports have fundamentally different state machines (overs/innings/wickets vs. periods/goals/penalties) — forcing a single generic schema either over-generalizes (losing domain-specific query efficiency) or leaks sport-specific fields everywhere; per-sport services also isolate failure domains and allow independent release cadences (cricket ships far more frequently given its traffic dominance).

Extensions & Edge Cases

How would you extend this design to support live video + score overlay?
Treat video as an orthogonal delivery pipeline (CDN-backed HLS/DASH streaming) and use the existing delta/version stream to drive a synchronized overlay client-side; the harder problem becomes clock-syncing the video stream's timestamp to the score-event timestamp so the overlay doesn't precede or lag the visible action.
How do you roll out a schema change to the Match document without downtime, given live matches are in progress?
Use additive, backward-compatible schema changes (new optional fields) during live windows; version the document schema (schemaVersion field) and handle multiple versions in the read path; avoid destructive migrations while any match referencing the old shape is still LIVE.
What's your disaster-recovery story if an entire region goes down mid-match?
Cross-region replica sets allow another region's Core API + NoSQL replica to take over as primary; WebSocket clients in the failed region reconnect (client-side retry) and get rebound via the WebSocket Manager to a healthy region's handler pool; some in-flight pushes are lost but recoverable via since_version catch-up.
How do you decide which matches get "dedicated capacity" ahead of time, and what if an unscheduled match becomes unexpectedly popular?
Use historical viewership data + team/tournament prestige signals (e.g. India vs Pakistan, World Cup final) to pre-provision; combine with real-time auto-scaling triggers (QPS/connection-count thresholds) to catch surprise breakouts (e.g. an unheralded match going into a viral last-ball finish) that weren't predicted in advance.
How would you support "second screen" use cases — e.g., a user watching TV wants ball-by-ball push perfectly synced to broadcast?
This tightens the acceptable delay assumption significantly (broadcast delay is often ~5–10s itself, but sync mismatch between the app and the TV feed is jarring); would likely need a configurable low-latency mode with a shorter effective cache TTL and a more aggressive WebSocket push cadence for that specific use case, at the cost of higher Core API traffic for those sessions.

Key Takeaways

Remember
This system is fundamentally about fanning a trickle of writes (~1 ball every 30–90 seconds) out to a firehose of reads (5,000+ req/sec, millions of concurrent viewers) without ever letting that fan-out reach the expensive source-of-truth tier. The cache-offload math — Redis's 1-second TTL absorbing 99.98% of reads, with Varnish's request-coalescing collapsing the remaining TTL-expiry stampede down to exactly one upstream call — is the single idea that makes the whole design work, and it is why Core API needs only a handful of instances per sport while Product API needs dozens. The circuit breaker is a second, orthogonal safety net: where Varnish protects one key at one instant, the breaker protects the whole Core API tier across sustained distress, falling back to stale-but-available data rather than an error. Shard by matchId via consistent hashing because every hot-path query is single-match scoped, but remember that hashing balances match count, not match load — a marquee fixture still needs dedicated read-replica fan-out layered on top. Split Core API per sport to isolate blast radius and allow independent scaling and release cadence. And because every event carries a monotonically increasing version/sequenceId, no delivery path — WebSocket push, AJAX poll, or partner REST pull — needs to be lossless; a client can always catch up with a since_version fetch, which is what turns "acceptable 2–3 second staleness" into a design that tolerates dropped connections, handler-node failures, and even TTL-boundary stampedes without ever losing an event.
