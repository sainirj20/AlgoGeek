Multithreading & Concurrency

Overview

Concurrency questions probe whether you can reason about shared mutable state across threads — where races, visibility bugs, and deadlocks come from, and which tool in java.util.concurrent solves which problem. Expect a mix of conceptual questions (what does volatile actually guarantee?) and applied ones (how would you run five tasks in parallel and combine their results?).

Thread vs. Runnable

You can create a thread of execution two ways: extend Thread and override run(), or implement Runnable (a functional interface with a single run() method) and pass it to a Thread or an executor. Runnable is almost always preferred: Java has single class inheritance, so extending Thread burns your one extends slot, and Runnable decouples the "what to run" from the "how it's executed" (letting you hand it to a thread pool instead of manually managing threads).

// Preferred: Runnable + executor, no Thread subclassing needed
Runnable task = () -> System.out.println("running on " + Thread.currentThread().getName());
new Thread(task).start();

The synchronized Keyword and Intrinsic Locks

Every Java object has an associated intrinsic lock (monitor). Marking a method or block synchronized forces a thread to acquire that object's monitor before entering, and release it on exit (even if an exception is thrown). This guarantees both mutual exclusion (only one thread executes the critical section at a time) and visibility (changes made inside a synchronized block by one thread are visible to the next thread that acquires the same lock, thanks to the Java Memory Model's happens-before ordering).

public class Counter {
    private int count = 0;

    public synchronized void increment() { // locks "this"
        count++;
    }

    public synchronized int get() {
        return count;
    }
}

volatile

volatile guarantees visibility (every read sees the most recent write from any thread — the value is never cached in a CPU register or per-thread cache) and prevents instruction reordering around the variable, but it does not provide mutual exclusion. A compound operation like count++ on a volatile int is still not atomic (it's a read-modify-write of three steps), so volatile is appropriate for simple flags (e.g. a shutdown boolean checked in a loop), not for counters or anything requiring atomic updates — use AtomicInteger or synchronized for those.

The java.util.concurrent Package

UtilityPurpose
ExecutorServiceManages a pool of worker threads; submit tasks instead of creating raw Threads
Future / CompletableFutureRepresents the result of an asynchronous computation; CompletableFuture adds composable, non-blocking chaining (thenApply, thenCombine)

ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Integer> future = pool.submit(() -> {
    Thread.sleep(100);
    return 42;
});

// CompletableFuture: non-blocking composition
CompletableFuture
    .supplyAsync(() -> fetchOrderTotal(), pool)
    .thenApply(total -> total * 1.08)          // apply tax
    .thenAccept(finalTotal -> System.out.println(finalTotal))
    .exceptionally(ex -> { log(ex); return null; });

int result = future.get(); // blocks until the task completes
pool.shutdown();
Thread-pool sizing guidance For CPU-bound work: threads ≈ N_cpu + 1
For mixed CPU/I‑O-bound work: threads ≈ N_cpu × (1 + wait_time / compute_time)
Example: 8 cores, tasks spend 80% of their time waiting on I/O (wait/compute = 4) → threads ≈ 8 × (1 + 4) = 40

ConcurrentHashMap Internals

Unlike Collections.synchronizedMap(new HashMap<>()), which serializes every operation behind a single lock, ConcurrentHashMap divides the table into fine-grained lock domains. In Java 7 this was explicit "segments" (16 by default); since Java 8, the implementation locks at the level of individual bucket heads (using synchronized blocks on the first node of a bin, plus CAS operations for lock-free reads and initial inserts). Reads are largely lock-free, and writes only contend if they target the same bucket — two threads writing to different buckets proceed in parallel. This makes ConcurrentHashMap dramatically more scalable under high concurrency than a globally-synchronized map, at the cost of only weakly-consistent iterators (fail-safe, not fail-fast).

Deadlock: Conditions and Prevention

A deadlock requires all four Coffman conditions to hold simultaneously: mutual exclusion (resources can't be shared), hold and wait (a thread holds one lock while waiting for another), no preemption (a lock can't be forcibly taken away), and circular wait (a cycle of threads each waiting on a resource held by the next). Break any one condition and deadlock becomes impossible.

  • Lock ordering — always acquire multiple locks in a fixed, global order to eliminate circular wait.
  • Lock timeout — use tryLock(timeout) from java.util.concurrent.locks.Lock instead of blocking synchronized, and back off/retry on failure.
  • Reduce lock scope — hold locks for the shortest time possible and avoid calling out to unknown code while holding one.
  • Prefer higher-level utilities — java.util.concurrent classes (e.g. ConcurrentHashMap, atomics) sidestep the need for manual locking in many common cases.
Classic example
Thread A locks account X then tries to lock account Y to perform a transfer; Thread B simultaneously locks Y then tries to lock X for the reverse transfer. Both threads block forever. Fix: always lock accounts in a consistent order (e.g. by account ID) regardless of transfer direction.

Common Interview Questions

What's the difference between synchronized and a ReentrantLock?
synchronized is a JVM-managed intrinsic lock — simpler syntax, automatic release on block exit/exception, but blocking-only and no fairness control. ReentrantLock (from java.util.concurrent.locks) offers tryLock() with timeouts, interruptible lock acquisition, fairness policies, and multiple condition variables via newCondition() — at the cost of requiring an explicit finally block to release the lock.
Does making a variable volatile make compound operations like i++ thread-safe?
No. i++ is read-modify-write; volatile only guarantees each individual read/write is visible across threads, not that the whole sequence is atomic. Two threads can both read the same value before either writes back, losing an update. Use AtomicInteger.incrementAndGet() or synchronization for atomic increments.
How does CompletableFuture improve on plain Future?
Future.get() blocks the calling thread and offers no way to chain follow-up work or combine multiple futures. CompletableFuture supports non-blocking composition (thenApply, thenCompose, thenCombine), exception handling (exceptionally, handle), and manual completion, making it suitable for building async pipelines.
Why is ConcurrentHashMap preferred over Collections.synchronizedMap for high-throughput code?
synchronizedMap wraps every method call in a lock on a single monitor, so all threads serialize even on unrelated keys. ConcurrentHashMap locks at the bucket level (Java 8+) and uses lock-free reads, so unrelated writes proceed concurrently and reads almost never block — giving far better throughput under contention.
How would you size a thread pool for a service that's mostly waiting on network calls?
Since the workload is I/O-bound, the wait_time/compute_time ratio is high, so the pool should have more threads than cores — apply threads ≈ N_cpu × (1 + wait/compute). Oversizing a pool for CPU-bound work wastes memory and increases context-switch overhead; oversizing for I/O-bound work is usually safe and often necessary to keep the CPU busy while other threads wait.

Key Takeaways

Remember
synchronized/intrinsic locks give you mutual exclusion + visibility; volatile gives you visibility only. Prefer java.util.concurrent building blocks (executors, atomics, concurrent collections) over hand-rolled locking. Deadlocks require all four Coffman conditions — breaking circular wait via consistent lock ordering is usually the cheapest fix.
