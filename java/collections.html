Collections Framework

Overview

The Java Collections Framework (JCF) is a unified architecture for storing and manipulating groups of objects. It's built around a small set of core interfaces — Collection, List, Set, Queue, and Map — each with multiple concrete implementations that trade off ordering, uniqueness, and performance differently. Interviewers use this topic to check whether you understand not just the API, but the underlying data structures (arrays, linked nodes, hash tables, red-black trees) and can reason about time complexity.

ArrayList vs. LinkedList

ArrayList is backed by a resizable array, so random access via get(i) is O(1), but inserting/removing from the middle is O(n) because elements must shift. LinkedList is a doubly-linked list — O(1) insert/remove once you have a reference to the node (e.g. at the head/tail via Deque methods), but O(n) random access since it must walk the list. In practice, ArrayList is the default choice; reach for LinkedList only when you need cheap insert/remove at both ends (it also implements Deque).

HashMap Internals

A HashMap stores entries in an array of "buckets." A key's hashCode() is passed through a supplemental hash function and masked against (capacity - 1) to pick a bucket. Collisions within a bucket are handled with a linked list of entries — or, since Java 8, a red-black tree once a bucket holds more than 8 entries (TREEIFY_THRESHOLD), which caps worst-case lookup at O(log n) instead of O(n). When the number of entries exceeds capacity × loadFactor (default load factor 0.75), the table resizes (doubles) and everything is rehashed.

Average-case complexity get(key) = O(1)  |  put(key, value) = O(1)  |  worst case (heavy collisions, pre-treeify) = O(n)
Resize threshold: size > capacity × loadFactor (default capacity 16, loadFactor 0.75 → resize at 12 entries)

HashMap vs. LinkedHashMap vs. TreeMap

  • HashMap — no ordering guarantee; fastest general-purpose map.
  • LinkedHashMap — maintains insertion order (or access order, useful for building an LRU cache) via an internal doubly-linked list.
  • TreeMap — keeps keys sorted using a red-black tree; get/put are O(log n), and it implements NavigableMap (floorKey, ceilingKey, etc.).

Java Comparable

Comparable<T> is a single-method interface a class implements to define its own natural ordering — the one, canonical way instances of that class sort by default. It lives in java.lang (no import needed), and is what powers Collections.sort(list), Arrays.sort(array), and sorted structures like TreeSet/TreeMap when no explicit Comparator is supplied. Many core JDK classes already implement it — String (lexicographic), the numeric wrapper classes (numeric order), and LocalDate/LocalDateTime (chronological) all have a natural ordering out of the box.

The compareTo Contract

public interface Comparable<T> {
    int compareTo(T o);
}

Its return value follows the same convention as C's strcmp: negative if this comes before o, zero if equal for ordering purposes, positive if this comes after o — only the sign matters. The contract imposes real invariants for every non-null x, y, z:

  • Sign consistency: sgn(x.compareTo(y)) == -sgn(y.compareTo(x)).
  • Transitivity: if x.compareTo(y) > 0 and y.compareTo(z) > 0, then x.compareTo(z) > 0.
  • Consistency across equal comparisons: if x.compareTo(y) == 0, then x.compareTo(z) and y.compareTo(z) must share the same sign, for any z.
  • Strongly recommended — consistency with equals: x.compareTo(y) == 0 should imply x.equals(y). Violating this is legal but dangerous: TreeSet/TreeMap use compareTo as their sole notion of equality, so two "equal-by-compareTo" objects that aren't .equals() will silently collapse into one entry.
  • Unlike equals(Object), compareTo is not required to accept null — by convention it should throw NullPointerException.

Implementing Comparable

public class Employee implements Comparable<Employee> {
    private final String name;
    private final int yearsOfService;

    public Employee(String name, int yearsOfService) {
        this.name = name;
        this.yearsOfService = yearsOfService;
    }

    @Override
    public int compareTo(Employee other) {
        int bySeniority = Integer.compare(other.yearsOfService, this.yearsOfService); // most senior first
        if (bySeniority != 0) return bySeniority;
        return this.name.compareTo(other.name); // tie-break: alphabetical
    }
}

List<Employee> team = new ArrayList<>(List.of(
    new Employee("Ana", 3), new Employee("Ben", 5), new Employee("Cy", 3)
));
Collections.sort(team);        // uses Employee.compareTo — no Comparator needed
// [Ben(5), Ana(3), Cy(3)]
The classic subtraction bug
return this.value - other.value; for int fields looks correct but silently overflows when the two values are far apart, producing a wrong sign and breaking the contract intermittently. Always use Integer.compare(a, b) (or the equivalent for other primitive types) instead — it's exactly as short and never overflows.

Comparable Is a Single, Fixed Ordering

Because compareTo is defined once on the class itself, a class can only have one natural ordering. If you need to sort the same objects different ways in different contexts (employees by name in one screen, by salary in another), that's exactly the gap Comparator fills — see below.

Comparable and Sorted Collections

TreeSet and TreeMap use compareTo (or a supplied Comparator) as their sole mechanism for both ordering and uniqueness — they never call equals/hashCode at all. Inserting an object whose class doesn't implement Comparable into a no-argument TreeSet/TreeMap throws ClassCastException at runtime, the moment an actual comparison is attempted:

TreeSet<Employee> bySeniority = new TreeSet<>(team); // fine — Employee implements Comparable

class Widget { int id; }
TreeSet<Widget> widgets = new TreeSet<>();
widgets.add(new Widget()); // throws ClassCastException — Widget has no natural ordering

Java Comparator

Comparator<T> is a functional interface that defines an ordering as a standalone, external strategy object rather than baking it into the class being compared. Where Comparable gives a class exactly one fixed natural ordering, a Comparator can be created on the fly, passed around, composed, and swapped — so the same class can be sorted a dozen different ways in a dozen different contexts without ever being modified.

public interface Comparator<T> {
    int compare(T o1, T o2);   // the single abstract method
    // ... plus many default/static methods added in Java 8
}

Creating a Comparator: the Evolution

// 1. Anonymous inner class (pre-Java-8 style)
Comparator<Employee> byDept1 = new Comparator<Employee>() {
    @Override
    public int compare(Employee a, Employee b) {
        return a.getDepartment().compareTo(b.getDepartment());
    }
};

// 2. Lambda (Java 8+) — same logic, far less ceremony
Comparator<Employee> byDept2 =
    (a, b) -> a.getDepartment().compareTo(b.getDepartment());

// 3. Comparator.comparing + method reference — the idiomatic modern form
Comparator<Employee> byDept3 = Comparator.comparing(Employee::getDepartment);

A Common Pitfall: Inconsistent Comparators

Broken sort contract
A Comparator must satisfy the same sign-consistency and transitivity rules as Comparable. Collections.sort/Arrays.sort can throw IllegalArgumentException: Comparison method violates its general contract! at runtime (Java's TimSort actively detects certain contract violations) — treat that as a sign the comparator logic is wrong, not a JDK bug.

The Collections Utility Class

java.util.Collections is a final utility class made up entirely of static methods that operate on collections — sorting, searching, wrapping for thread-safety/immutability, and producing small special-purpose collections. It's the collections analogue of java.util.Arrays.

"Collections" vs. "Collection" — not the same thing
Collection<E> (singular) is the root interface of the framework covered earlier on this page — List, Set, and Queue all extend it. Collections (plural, this section) is an unrelated static utility class — it does not implement Collection and doesn't represent a group of elements at all; it's just a toolbox of helper methods that happen to take Collection/List arguments. If asked "what's the difference between Collection and Collections," this distinction is the entire answer.

Immutability & Thread-Safety Wrappers

unmodifiableCollection/List/Set/Map(...) each return a thin wrapper that blocks mutation attempts made through that wrapper — add/remove/put/clear on the returned object throws UnsupportedOperationException. Crucially, this is a view, not a copy — it holds a reference back to the original and simply reads through it.

Gotcha: changes to the backing collection leak through the "read-only" view
List<String> original = new ArrayList<>(List.of("a", "b"));
List<String> readOnlyView = Collections.unmodifiableList(original);
System.out.println(readOnlyView); // [a, b]

original.add("c");                // mutate the BACKING list directly, not the view
System.out.println(readOnlyView); // [a, b, c]  ← the "read-only" view just changed!
The view never promised the data was frozen — only that you can't mutate it through that particular reference.

synchronizedList/Set/Map(...) return a wrapper where every individual method call acquires an internal lock before delegating — making single operations like add or get thread-safe.

Gotcha: iteration is NOT automatically synchronized
A single lock per call doesn't help a for-each loop, since that's many separate calls (hasNext(), next()) with no lock held across them. The Javadoc requires wrapping the whole iteration yourself: 
synchronized (syncList) {
    for (Integer n : syncList) { System.out.println(n); }
}

Contrast — the truly-immutable List.of/Set.of/Map.of (Java 9+): these return genuinely immutable collections with no mutable backing to leak from; any mutation attempt always throws UnsupportedOperationException. Use List.of/etc. when creating a brand-new immutable collection from scratch; use Collections.unmodifiableX when you already have a mutable collection and want to hand out a protective read-only view of it (with the leak-through caveat in mind).

Collections and Streams

The Stream API doesn't exist in isolation — almost every stream pipeline starts life as a Collection and usually ends up back as one. See the Java 8+ Features (Streams & Lambdas) page for stream/lambda basics (lazy operations, functional interfaces, method references, Optional) if needed — this section assumes that and focuses on collection-specific patterns and the Collectors API.

From Collection to Stream and Back

Every Collection<T> inherits stream() and parallelStream() as default methods (backed by its Spliterator). Getting back out of a stream is the job of Collectors, passed to the terminal collect(...) operation:

record Employee(String name, String department, double salary, int age) {}

List<Employee> employees = List.of(
    new Employee("Ana", "Engineering", 95000, 29),
    new Employee("Ben", "Sales",       72000, 34),
    new Employee("Cy",  "Engineering", 110000, 41),
    new Employee("Dee", "Sales",       68000, 26),
    new Employee("Eli", "Engineering", 88000, 31)
);

// toList()/toSet(): no guaranteed implementation type or mutability
List<String> names = employees.stream().map(Employee::name).collect(Collectors.toList());

// toUnmodifiableList()/toUnmodifiableSet() (Java 10+): genuinely immutable by contract
List<String> immutableNames = employees.stream().map(Employee::name)
    .collect(Collectors.toUnmodifiableList());

// toCollection(supplier): guaranteed concrete type, e.g. a sorted, mutable TreeSet
TreeSet<String> sortedDepartments = employees.stream().map(Employee::department)
    .collect(Collectors.toCollection(TreeSet::new));

The toMap duplicate-key gotcha
// Three employees share the "Engineering" department key
Collectors.toMap(Employee::department, e -> e);
// throws IllegalStateException: Duplicate key Engineering

// Fix: supply a merge function (3rd arg)
Collectors.toMap(Employee::department, e -> e,
    (existing, replacement) -> existing.salary() >= replacement.salary() ? existing : replacement);

// groupingBy: classifier + downstream collector
Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::department, Collectors.counting()));
// {Engineering=3, Sales=2}

// partitioningBy always produces exactly two buckets: true/false
Map<Boolean, List<Employee>> bySalaryOver90k = employees.stream()
    .collect(Collectors.partitioningBy(e -> e.salary() > 90000));

// summarizing as a groupingBy downstream
Map<String, IntSummaryStatistics> ageStatsByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::department, Collectors.summarizingInt(Employee::age)));

Prefer a purpose-built collector (summingDouble, counting, etc.) over generic reducing whenever one exists — it states intent directly rather than making the reader reconstruct it from a combiner lambda.

Common Collection-Specific Stream Patterns

Collection.removeIf(predicate) is a default method, not a stream operation, but frequently compared to stream().filter(): removeIf mutates in place, while filter() produces a new stream and leaves the source untouched.

// WRONG: removing from a collection while iterating it with a plain for-each
for (Employee e : mutableRoster) {
    if (e.salary() < 70000) mutableRoster.remove(e); // throws ConcurrentModificationException
}

// RIGHT: removeIf is designed exactly for conditional in-place removal
mutableRoster.removeIf(e -> e.salary() < 70000);

Iterable.forEach(action) and stream().forEach(action) look interchangeable for the sequential case and visit elements in encounter order for an ordered source — but Stream.forEach makes no ordering guarantee in general for parallel/unordered streams (use forEachOrdered if order must be preserved). Map has its own forEach((k, v) -> ...) taking a BiConsumer.

Parallel Streams Over Collections — Caveats

collection.parallelStream() splits work using the source's Spliterator. Array-backed structures (ArrayList) split cheaply and evenly — good parallel candidates. LinkedList has no random access, so finding a split point means walking node-by-node — splitting is expensive and uneven, so it typically parallelizes poorly despite compiling and running fine.

// UNSAFE: manually accumulating into a shared, non-thread-safe ArrayList from parallel forEach
List<String> unsafeNames = new ArrayList<>();
employees.parallelStream().forEach(e -> unsafeNames.add(e.name())); // don't do this

// SAFE: built-in collectors like toList() are specifically designed for parallel use
List<String> safeNames = employees.parallelStream().map(Employee::name).collect(Collectors.toList());

Parallel streams have real coordination/splitting/merging overhead that only pays off on large collections with non-trivial per-element work — for small collections, sequential is typically faster.

Fail-Fast vs. Fail-Safe Iterators

Most JCF iterators (e.g. ArrayList, HashMap) are fail-fast: they track a modCount and throw ConcurrentModificationException if the collection is structurally modified while iterating (except via the iterator's own remove()). Collections designed for concurrent use — CopyOnWriteArrayList, ConcurrentHashMap — are fail-safe: they iterate over a snapshot or use lock-free traversal, so they never throw, though you may not see the very latest updates.

Thread safety note
Plain ArrayList/HashMap are not thread-safe. Options: Collections.synchronizedList(...) (coarse locking), CopyOnWriteArrayList (read-heavy, rarely-mutated lists), or ConcurrentHashMap (segmented locking, high-concurrency maps). See the Multithreading & Concurrency page for details.

Common Interview Questions

Collections Framework Basics

Why must you override both equals() and hashCode() when using an object as a HashMap key?
HashMap uses hashCode() to locate the bucket and equals() to confirm the exact key within that bucket. If two "equal" objects return different hash codes, they can land in different buckets and the map will treat them as distinct keys — breaking lookups.
How would you build an LRU cache using JCF?
Extend LinkedHashMap with accessOrder=true and override removeEldestEntry to evict the oldest entry once the cache exceeds its capacity — roughly 10 lines of code.
What happens internally when a HashMap resizes?
A new bucket array of double the capacity is allocated, and every existing entry is rehashed and redistributed into the new array. This is an O(n) operation, which is why specifying an expected initial capacity can avoid repeated resizes in hot paths.
ArrayList vs. Vector — why prefer the former?
Vector synchronizes every method, adding overhead even in single-threaded code, and its "grow by 100%" default differs from ArrayList's tunable growth. ArrayList is unsynchronized (faster) and is the idiomatic modern choice; use explicit concurrency utilities instead of relying on Vector.

Comparable & Comparator

Why would you implement Comparable instead of always passing a Comparator?
When a class has one obvious, canonical ordering that essentially every caller wants by default, implementing Comparable means callers can just call Collections.sort(list) or drop instances straight into a TreeSet without supplying any comparison logic themselves. Comparator is for orderings that are situational rather than canonical.
What goes wrong if compareTo is inconsistent with equals?
Plain collections like ArrayList/HashMap are unaffected. But TreeSet/TreeMap use compareTo as their only notion of "same element," so two objects that are compareTo-equal but .equals()-different are treated as duplicates — adding the second one silently does nothing (or replaces the first, for maps).
Why is return a - b; a bug-prone way to implement compareTo for int fields?
Subtracting two ints can overflow the 32-bit range when the values are far apart, silently producing a value with the wrong sign. Integer.compare(a, b) is the same length to write and immune to overflow.
Can a class implement Comparable more than once with different orderings?
No — compareTo is a single method with one implementation per class, so there's only one natural ordering. Multiple, situational orderings require external Comparator objects instead, which can be created and swapped freely without touching the class.
What's the difference between thenComparing and just chaining another comparing call, mechanically?
thenComparing is only consulted when the preceding comparator(s) return 0 (a tie) — it sorts primarily by the first key, and only falls back to break ties, never overriding the first comparator's result when it already distinguishes two elements. That tie-break semantics is exactly what "chaining" means for comparators.
Comparator.reverseOrder() vs. comparator.reversed() — what's the difference?
Comparator.reverseOrder() reverses the elements' own natural (Comparable) ordering, requiring the elements to implement Comparable. comparator.reversed() reverses whatever arbitrary comparator you already built, regardless of whether the elements implement Comparable — it's the general-purpose one.
When would you reach for a Comparator even though the class already implements Comparable?
Whenever you need an ordering other than the class's one fixed natural order — e.g. employees sorted by name on one screen and by salary on another — or when the class comes from a third-party library you can't modify to add/change compareTo. The natural ordering stays available via Comparator.naturalOrder() alongside any number of ad-hoc comparators.
How do you sort by multiple fields where some are ascending and others descending?
Chain Comparator.comparing(...) with .thenComparing(...), and call .reversed() (or pass Comparator.reverseOrder() as the key comparator) on only the fields that need descending order — each field's direction is controlled independently within the chain, e.g. Comparator.comparing(Employee::getDept).thenComparing(Employee::getSalary, Comparator.reverseOrder()).

The Collections Utility Class

What's the difference between Collections.unmodifiableList(list) and List.of(...)?
unmodifiableList returns a live view wrapped around an existing mutable list — changes made directly to the original backing list are still visible through the view. List.of(...) creates a genuinely immutable collection with no mutable backing at all. Use List.of for fresh immutable data; use unmodifiableList to hand out a protective façade over a list still mutated elsewhere.
Individual calls on a Collections.synchronizedList(...) are thread-safe, so why can iterating over it still throw ConcurrentModificationException?
The wrapper synchronizes each method call independently. A for-each loop is really a sequence of separate hasNext()/next() calls with no lock held across the whole sequence, so another thread can sneak in a structural modification between two calls. Callers must wrap the entire iteration themselves in synchronized (list) { ... }.
What precondition does Collections.binarySearch(list, key) have, and what happens if you violate it?
The list must already be sorted (naturally, or per the Comparator passed to the three-arg overload). If it isn't sorted, the method doesn't detect or throw anything — it silently returns an unreliable index, since binary search blindly trusts the sortedness precondition to run in O(log n).
Why is Collections.nCopies(n, obj) only safe to use freely with immutable objects?
All n "copies" are the exact same object reference repeated n times, not independently-allocated clones. For an immutable type like String this is harmless. If obj were mutable, mutating it through any one "copy" would change what every index appears to hold, since they all alias the same instance.
What happens if you call add() directly on an unmodifiableList view, versus adding to the backing list it wraps?
Calling add() on the view throws UnsupportedOperationException immediately. Calling add() on the original backing list succeeds normally, and because the view just reads through to that same backing list, the new element instantly becomes visible through the "read-only" view too.

Collections and Streams

Why does Collectors.toMap(keyFn, valueFn) throw IllegalStateException, and how do you fix it?
The 2-arg toMap has no strategy for what to do when two stream elements map to the same key, so it fails fast rather than silently overwriting or dropping one. The fix is the 3-arg overload with a BinaryOperator<V> merge function telling it how to combine colliding values, e.g. (existing, replacement) -> existing to keep the first one seen.
What's the difference between groupingBy and partitioningBy?
groupingBy buckets by an arbitrary classifier and can produce any number of groups. partitioningBy is specialized for a boolean predicate — it always produces exactly two groups, true and false, with both keys always present even if one list is empty.
Why does removing an element during a plain for-each loop throw ConcurrentModificationException, and what does removeIf do differently?
A for-each loop uses an Iterator internally and tracks a modCount; calling list.remove(...) directly changes that count out from under the iterator, which detects the mismatch and throws. Collection.removeIf(predicate) manages safe removal internally, making it the correct way to conditionally remove elements while iterating.
Why does a parallel stream over a LinkedList often perform worse than expected?
Parallelizing requires the source's Spliterator to split data into independent chunks. For ArrayList that's a cheap O(1) midpoint calculation; for LinkedList, there's no random access, so finding a split point means walking node by node — an O(n) operation repeated as data keeps subdividing, easily outweighing any parallelism gain.
Why prefer Collectors.summingDouble/averagingDouble over Collectors.reducing for simple aggregations?
Both can compute the same result, but summingDouble(Employee::salary) states intent directly, while reducing(0.0, Employee::salary, Double::sum) requires reconstructing that intent from an identity, mapper, and combiner. Reach for reducing only when no purpose-built collector expresses the fold you need.

Key Takeaways

Remember
Pick the implementation based on the operation you do most: ArrayList for random access, LinkedList/ArrayDeque for queue-like access at the ends, HashMap for O(1) average lookups, TreeMap when you need sorted keys, and LinkedHashMap when you need predictable iteration order. Comparable gives a class exactly one fixed natural ordering via compareTo; Comparator is external and composable via comparing/thenComparing — use Integer.compare over subtraction in either. The Collections utility class (distinct from the Collection interface) supplies sorting/searching/wrapper/factory methods — remember binarySearch needs a pre-sorted list and unmodifiableX is a view, not a frozen copy (prefer List.of for true immutability). Every Collection exposes stream()/parallelStream(); Collectors.toMap/groupingBy/partitioningBy cover most aggregation needs, removeIf is the safe way to conditionally remove elements in place, and parallel streams only pay off on large, array-backed sources.
