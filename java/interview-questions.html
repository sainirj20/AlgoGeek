OOP Concepts

Object-oriented programming is the design foundation of virtually every Java codebase. These questions test whether you understand the four pillars — abstraction, polymorphism, inheritance, encapsulation — as more than textbook definitions: how they show up in real code, why the language enforces the constraints it does, and how to correctly model relationships between objects.

What are OOPS concepts?
The four pillars of object-oriented programming, easy to remember as A-PIE:
  • Abstraction — hiding implementation detail and exposing only relevant behavior (via abstract classes/interfaces).
  • Polymorphism — the same operation behaving differently depending on the object it's invoked on.
  • Inheritance — a class acquiring the state and behavior of another, enabling reuse and an IS-A relationship.
  • Encapsulation — bundling data with the methods that operate on it and restricting direct outside access.
Together they let you model real-world entities as loosely-coupled, reusable, maintainable units rather than a pile of global functions and data.
What is a Class, and what is an Object?
A class is a blueprint/template — it describes the fields and methods that objects of that type will have, but it consumes no object memory by itself. An object is an instance of a class: it has its own state (field values), behavior (methods it can execute), and identity (a distinct reference in memory, even if two objects hold identical state).
class Car {              // class = blueprint
    String color;
    void drive() { ... }
}
Car myCar = new Car();   // object = instance, has its own state
What is Inheritance?
Inheritance is the mechanism by which one class (the subclass) acquires the fields and methods of another (the superclass) using extends. It establishes an IS-A relationship — e.g. SavingsAccount extends Account — and is the foundation that makes runtime polymorphism possible, since a subclass reference can be treated as an instance of its supertype.
Why did Inheritance come into the picture — what problem does it solve?
  • Code reuse — common fields/behavior live once in a superclass instead of being copy-pasted across siblings.
  • Natural modeling — many real domains are genuine taxonomies (a Manager really is an Employee).
  • Polymorphic APIs — a method written against the supertype works unmodified for any subtype (Liskov substitution), so new subtypes can be added without touching existing code (open/closed principle).
What is the diamond problem, and how does Java avoid it?
The diamond problem arises in multiple inheritance when a class inherits the same method signature from two different parents that each provide their own implementation — the compiler has no unambiguous way to pick one. Java sidesteps this for classes by allowing only single inheritance of implementation (extends takes exactly one class).

Interfaces can still be implemented in unlimited numbers, and since Java 8 interfaces can carry default method bodies — which reopens the same ambiguity if two interfaces provide a default method with the same signature. Java requires the implementing class to resolve it explicitly:
interface Parent1 { default void greet() { System.out.println("Parent1"); } }
interface Parent2 { default void greet() { System.out.println("Parent2"); } }

class Child implements Parent1, Parent2 {
    @Override
    public void greet() {
        Parent1.super.greet();   // must explicitly pick one (or write new logic)
    }
}

If Child doesn't override greet(), the code simply fails to compile — Java forces the ambiguity to be resolved at compile time rather than guessed at runtime.

What is Polymorphism?
Literally "many forms" — the ability of a reference, method, or object to behave differently depending on context. In Java this shows up as one method name resolving to different behavior depending on either the arguments passed (overloading) or the actual runtime type of the object it's called on (overriding).
What are the types of polymorphism in Java?
  • Compile-time (static) polymorphism — method overloading. The compiler picks the matching method based on the number/type of arguments at compile time; there's no runtime decision involved.
  • Runtime (dynamic) polymorphism — method overriding. The JVM resolves which implementation to invoke based on the actual object's type at runtime (virtual method dispatch), even though the reference variable is declared as a supertype.
Animal a = new Dog();
a.makeSound();  // resolved at runtime to Dog's override, not Animal's
What is the difference between encapsulation and abstraction?
Abstraction is a design-level concept — it hides complexity and exposes only the "what" (the contract), typically via abstract classes and interfaces; the caller doesn't need to know how a method is implemented. Encapsulation is an implementation-level concept — it hides data, bundling fields with the methods that operate on them and restricting direct access via access modifiers (private fields plus public getters/setters). In short: abstraction hides implementation detail, encapsulation hides internal state. They're complementary — a well-encapsulated class is usually also a good abstraction.
Give an example of encapsulation from code.
Any class with private fields exposed only through controlled accessors:
public class BankAccount {
    private double balance;              // hidden internal state

    public double getBalance() {         // controlled read access
        return balance;
    }
    public void deposit(double amount) { // controlled write access, with validation
        if (amount > 0) balance += amount;
    }
}

Nothing outside BankAccount can set balance to an invalid value directly — every mutation goes through a validated method.

What is Association?
Association is a relationship where two objects are connected but each has its own independent lifecycle — neither owns the other. Example: Teacher and Student — multiple students can associate with one teacher and vice versa, but a teacher isn't "owned" by any student, and both can be created and deleted independently.
What is Aggregation?
Aggregation is a specialized form of association implying a "has-a" relationship with weak ownership: the child can still exist independently of the parent, and a child cannot belong to more than one parent at a time. Example: a Department has Teachers, but deleting the Department object doesn't destroy the Teacher objects.
What is Composition?
Composition is a stronger, specialized form of aggregation — sometimes called a "death" relationship. The child has no independent lifecycle: if the parent is destroyed, all its composed children are destroyed with it, and a child cannot be shared by two different parents. Example: a House has Rooms — a room cannot outlive its house, and the same room can't belong to two houses.
Ownership strength increases top to bottom: association has none, aggregation is a loose has-a, composition binds the child's lifecycle to the parent's.
Design Tip

Prefer composition over inheritance where either would work. Composition keeps classes loosely coupled (you depend on a small interface, not a whole parent's implementation), avoids the fragile base class problem, and lets you change behavior at runtime by swapping the composed object — something static inheritance can't do.

What are the SOLID principles, and why do they matter?
SOLID is a set of five OOP design guidelines that keep code maintainable as it grows:
  • S — Single Responsibility: a class should have exactly one reason to change.
  • O — Open/Closed: open for extension, closed for modification — add new behavior via new subclasses/implementations, not by editing existing tested code.
  • L — Liskov Substitution: a subtype must be usable anywhere its supertype is expected without breaking correctness.
  • I — Interface Segregation: many small, focused interfaces beat one large "fat" interface that forces implementers to support methods they don't need.
  • D — Dependency Inversion: depend on abstractions (interfaces), not concrete implementations, so high-level and low-level modules can vary independently.
Interviewers use SOLID questions to check whether a candidate can justify design decisions ("why does this violate SRP?") rather than just recite OOP definitions.

Java Basics & Language Fundamentals

Fundamentals of the Java language itself — keywords, binding, initialization order, and the handful of methods every object inherits. These questions are deceptively simple; interviewers use them to check whether a candidate actually understands what the compiler and JVM are doing, not just what compiles.

Can we create an instance of an interface or an abstract class?
Not directly with new — both are incomplete types. You can, however, create an instance of an anonymous inner class that implements/extends them on the fly, which is why the syntax can look deceptively like instantiating the interface itself:
Runnable r = new Runnable() {   // anonymous class implementing Runnable
    public void run() { System.out.println("running"); }
};
Why is multiple inheritance not supported in Java?
To remove ambiguity — the classic diamond problem. If class C could extend both A and B, and both defined a method with the same signature but different implementations, the compiler would have no unambiguous rule for which one C inherits. Java avoids this by allowing only single inheritance of implementation for classes; multiple interface implementation is still allowed because interfaces (pre-Java 8) carried no implementation to conflict over, and post-Java 8 conflicting default methods must be resolved explicitly by the implementing class.
Can you use both this() and super() in a constructor?
No. Both this(...) (call another constructor of the same class) and super(...) (call the parent constructor) must be the first statement in a constructor, so only one of them can appear — a constructor can't have two "first" statements. If you call this(...), the chain still eventually reaches a constructor that implicitly or explicitly calls super(...).
What do you mean by dynamic binding vs static binding (early vs late binding)?
Static (early/compile-time) binding — the compiler resolves which method to call at compile time, based on the declared type. This applies to private, static, and final methods, and to overload resolution. Dynamic (late/runtime) binding — the JVM resolves the call at runtime based on the actual object's type, via virtual method dispatch. This applies to overridden instance methods — it's exactly what makes runtime polymorphism work.
Animal a = new Dog();
a.makeSound();   // dynamic binding: Dog's override runs, decided at runtime
What is method overloading, and what is method overriding?
Overloading — multiple methods in the same class share a name but differ in parameter list (type, number, or order). Resolved at compile time based on the arguments passed; return type alone cannot distinguish overloads. Overriding — a subclass redefines a method it inherited from its superclass with the exact same signature, to provide specialized behavior. Resolved at runtime based on the actual object's type; the override must not have a more restrictive access modifier or a broader checked-exception list than the method it overrides.
What is the difference between an IS-A relationship and a HAS-A relationship?
IS-A is inheritance — "A is a type of B". Car IS-A Vehicle, Apple IS-A Fruit. It's uni-directional: a House IS-A Building, but not every Building IS-A House. HAS-A is composition — an object holds a reference to another object as an instance variable rather than inheriting from it. Car HAS-A Engine, House HAS-A Bathroom. (See the Association/Aggregation/Composition diagram in the OOP Concepts section above for how HAS-A itself splits into weaker and stronger forms of ownership.)
What is the difference between an interface and composition?
They solve different problems and aren't really direct alternatives — an interface is about type (what a class can be treated as: implementing Comparable means "this IS-A Comparable"), while composition is about structure (a class HAS-A another object it delegates to). In practice they combine constantly: a class implements an interface as its contract while composing other objects internally to fulfill it.
When is it better to use inheritance instead of just holding an instance of that class (composition)?
Use inheritance when there's a genuine IS-A relationship and you need polymorphic substitution — callers should be able to treat the subtype as the supertype interchangeably, without the subclass violating any behavior the superclass promises (Liskov substitution). Prefer composition (holding an instance rather than extending) when you just want to reuse some functionality without committing to that IS-A contract — it's more flexible, doesn't expose the entire parent API, and avoids the fragile base class problem where a change to the parent unexpectedly breaks subclasses.
Is it possible to override the main method?
No — not in the polymorphic sense. main is static, and static methods are resolved by static binding based on the declared/reference type, not dynamic dispatch — so a subclass "main" with the same signature merely hides the parent's, it doesn't override it. The JVM always invokes main on the specific class named on the command line, so there's no polymorphic overriding behavior to observe.
What is static?
The static keyword ties a member to the class itself rather than to any particular instance, and can be applied to variables, methods, blocks, and nested classes.
  • static variable — one copy shared by all instances, stored in the method area at class-loading time; used for state common to every object (e.g. a counter of how many instances exist).
  • static method — belongs to the class, callable without creating an instance (ClassName.method()); can only directly access other static members.
Restrictions: a static method cannot directly reference non-static (instance) fields or call non-static methods (there's no implicit object to operate on), and this/super are meaningless in a static context.
What is the difference between == and .equals()?
== compares references — for primitives it compares the actual values, but for objects it checks whether two variables point to the exact same object in memory. .equals() is a method (inherited from Object, whose default behavior is the same as ==) that classes can override to define logical/content equality — String, wrapper classes, and most collection classes override it to compare values field-by-field.
String a = new String("hi");
String b = new String("hi");
a == b;          // false — different objects on the heap
a.equals(b);      // true — same character content
Gotcha

Whenever you override equals(), you must also override hashCode() consistently — otherwise the object breaks in hash-based collections like HashMap/HashSet, where equal objects are required to produce equal hash codes.

What is a real-time use of static?
Utility/helper methods that don't need any instance state (Math.max(), Collections.sort()), constants (static final fields), counters shared across all instances of a class, factory methods (static methods that return instances, e.g. Integer.valueOf()), and the classic lazily-initialized Singleton pattern, which relies on a private static instance field.
Can we make a static class?
A top-level class cannot be declared static — only public, final, abstract, or package-private are valid there. A static nested class (a class declared static inside another class), however, is allowed and common: unlike a non-static inner class, it doesn't hold an implicit reference to an enclosing instance, so it can be instantiated on its own — Outer.Nested n = new Outer.Nested(); — without first creating an Outer object.
What is autoboxing and unboxing, and where can they cause bugs?
Autoboxing is the compiler automatically converting a primitive to its wrapper type (int → Integer); unboxing is the reverse (Integer → int). It lets primitives be used wherever an object is required — e.g. inserted into a List<Integer>.
List<Integer> nums = new ArrayList<>();
nums.add(5);              // autoboxed: int -> Integer
int x = nums.get(0);      // unboxed: Integer -> int

Two common gotchas: unboxing a null wrapper (e.g. an Integer field that was never set) throws a NullPointerException the moment it's used as a primitive; and comparing boxed values with == is unreliable because the JVM caches Integer objects only in the range -128 to 127 — Integer.valueOf(100) == Integer.valueOf(100) is true, but Integer.valueOf(200) == Integer.valueOf(200) is false, since values outside the cache create distinct objects. Always use .equals() to compare boxed values.

What is the order of variable/object initialization?
static initializer blocks & static field initializers → the parent constructor (super(...)) → instance initializer blocks & instance field initializers → the rest of the constructor body. Static initialization happens exactly once, the first time the class is loaded — before any object of that class is ever created.
Object creation order — static setup happens once at class-load time; every subsequent new repeats the parent-constructor → instance-init → constructor-body sequence.
What is the difference between "static initialization blocks" and "instance initialization blocks"?
A static initializer block (static { ... }) runs exactly once, when the class is first loaded by the classloader — before main and before any instance exists — and has no access to instance variables or methods (there's no instance yet). It's typically used to initialize static fields that need more than a simple literal assignment.

An instance initializer block (a bare { ... } block inside the class body) runs every time an object is constructed — immediately after the superclass constructor completes and before the rest of that constructor's own body runs. It does have access to instance fields/methods, and is useful when several overloaded constructors need to share the same initialization logic without duplicating it in every constructor.
Can you assign null to the "this" reference?
No. this is an implicit final reference to the current object, supplied by the JVM — it isn't a regular local variable, so it can never be reassigned (to null or anything else); writing this = null; is a compile error.
Explain all access modifiers.
  • private — accessible only within the declaring class.
  • default (package-private, no keyword) — accessible within the same package only.
  • protected — accessible within the same package, plus subclasses in other packages (via inheritance).
  • public — accessible from anywhere.
Visibility increases in that order: private < default < protected < public. Encapsulation is largely enforced by choosing the narrowest modifier that still meets the class's needs.
Why is main() in Java declared as public static void main?
  • public — the JVM launcher calls it from outside the class/package, so it must be visible everywhere.
  • static — the JVM needs to invoke it before any object of the class exists; if it required an instance, the JVM would need some other convention to construct one first, adding ambiguity and overhead for no benefit.
  • void — a Java program doesn't return a value to the JVM/OS the way a native process return code does; to signal an explicit exit status you call System.exit(code) instead.
String[] args is required so command-line arguments can be passed in.
Explain System.out.println("some string").
Reading it left to right: System is a final class in java.lang providing access to standard input/output/error streams, environment properties, and utility methods. out is a public static final field of type PrintStream, instantiated by the JVM at startup and wired to the process's standard output — it's ready to accept data immediately. println(...) is an overloaded method on PrintStream (overloads exist for every primitive type plus Object and String) that writes the argument followed by a line separator; internally it delegates to print(), which delegates to write().
Show the functionality of a static block using code.
A static block runs once, at class-loading time, before main and before any instance is created — it's the standard place to initialize static fields that need computation rather than a literal value.
class Config {
    static final Map<String, String> DEFAULTS;

    static {
        DEFAULTS = new HashMap<>();
        DEFAULTS.put("timeout", "30s");
        System.out.println("Config class loaded");
    }
}
What are the default methods that every class has, and why?
Every class in Java implicitly extends Object, so every class inherits these methods:
  • equals(Object) — logical equality comparison (default: reference equality).
  • hashCode() — integer hash used by hash-based collections; must stay consistent with equals().
  • toString() — human-readable string representation.
  • getClass() — returns the object's actual runtime Class.
  • clone() — creates a copy of the object (protected; requires Cloneable).
  • finalize() — historically called by the GC before reclaiming an object; deprecated and no longer reliable — use try-with-resources or Cleaner instead.
  • wait() / notify() / notifyAll() — thread coordination primitives tied to an object's intrinsic monitor.
Having them on Object guarantees every reference in the JVM supports a minimum common contract — collections, logging, and synchronization all rely on it.
What are the different ways to create an object in Java?
  • new keyword — the normal, direct way.
  • Reflection — via Class.forName(...) combined with reflective instantiation.
  • clone() — copying an existing instance (requires Cloneable).
  • Deserialization — reconstructing an object from a byte stream.
MyObject a = new MyObject();                              // 1. new

MyObject b = (MyObject) Class.forName("com.example.MyObject")
                  .getDeclaredConstructor().newInstance(); // 2. reflection

MyObject c = (MyObject) a.clone();                         // 3. clone()

MyObject d = (MyObject) new ObjectInputStream(in)
                  .readObject();                           // 4. deserialization
Why is the clone() method protected?
Object.clone() is declared protected so that cloning isn't available on every object by default — a class author must explicitly opt in by overriding it as public (and implementing Cloneable). This gives the class control over whether copying even makes sense for it (some objects, like ones wrapping a unique resource, shouldn't be cloneable at all) and over how the copy is made (shallow vs. deep).
Why is the Cloneable interface used?
Cloneable is a marker interface — it has no methods. Its sole purpose is to signal to Object.clone() that the class has opted in to field-by-field copying. If a class calls super.clone() without implementing Cloneable, the JVM throws CloneNotSupportedException at runtime. It's a slightly awkward design (many consider Cloneable a flawed API), which is why copy constructors or static "copy-of" factory methods are often recommended over clone() in modern code.

What are var, records, and sealed classes?
Three features that modernized Java's type system without sacrificing static typing:
  • var (Java 10) — local-variable type inference. The compiler infers the concrete type from the initializer at compile time; the variable is still statically typed (var list = new ArrayList<String>(); is exactly an ArrayList<String>), it just saves boilerplate. Not allowed for fields, method parameters, or return types.
  • Records (Java 16) — a concise syntax for immutable data carriers. Declaring record Point(int x, int y) {} auto-generates a canonical constructor, private final fields, accessors, and value-based equals()/hashCode()/toString() — eliminating the usual boilerplate for simple DTOs.
  • Sealed classes/interfaces (Java 17) — let a type restrict which classes are permitted to extend or implement it via a permits clause, producing a closed, exhaustively-checkable hierarchy (the compiler can verify a switch over a sealed type covers every case).
public sealed interface Shape permits Circle, Square {}
public record Circle(double radius) implements Shape {}
public record Square(double side) implements Shape {}

Strings

String is the most heavily used type in Java and one of the most interview-tested, because answering these questions well requires understanding immutability, the string pool, and the object model underneath a type that behaves like a primitive but isn't one. Expect a mix of "how" and "why" questions here.

What is the difference between creating a String with new() and with a literal?
A literal (String s = "abc";) is looked up in the string pool first — if a string with that exact content already exists there, the existing reference is reused; otherwise the literal is added to the pool. Using new String("abc") always allocates a brand-new object on the heap, bypassing the pool lookup entirely, even if "abc" already exists in the pool (the literal itself is still created/reused in the pool as an intermediate step, but the new object is a separate copy on the heap). This is why new String("abc") == "abc" evaluates to false while .equals() still returns true — == compares references, not content. Calling .intern() on the new-created string forces it back into the pool.

Both are mutable sequences of characters backed by a resizable char[]/byte[] array, and both expose the same API (append, insert, delete, reverse). In practice, default to StringBuilder unless the same instance is genuinely mutated by multiple threads.
How does the substring method work?
s.substring(beginIndex, endIndex) returns a new String containing the characters from beginIndex (inclusive) to endIndex (exclusive). Its internal implementation has actually changed: before Java 7u6, substring shared the same backing char array as the original string, just with a different offset and count — cheap (no copying) but dangerous, since a small substring of a huge string kept the entire original array alive in memory, a classic memory-leak gotcha. Since Java 7u6, substring copies only the required range into a new array (essentially Arrays.copyOfRange), which fixes the leak at the cost of an O(n) copy on every call.
Why is String immutable (and final) in Java?
Several reasons combine to justify it:
  • Security — strings are used for class names, file paths, network hosts, and reflection arguments; if they were mutable, code could pass a validated string, then mutate it after the security check but before use.
  • String pool safety — the pool lets many references share one object; if strings were mutable, changing one reference's content would corrupt every other reference pointing at the same pooled instance.
  • Hashcode caching — String caches its hashCode() the first time it's computed. This is only safe because the content can never change, which is exactly why String is such a popular HashMap/HashSet key type.
  • Thread safety — immutable objects can be freely shared across threads with no synchronization.
The class is also declared final specifically so no subclass can override its methods and break these guarantees (e.g. a subclass that "looks like" a String but mutates its backing array).
How does using a StringBuffer/StringBuilder save memory?
Because String is immutable, every + concatenation creates a brand-new String object — building a string across a loop of n concatenations naively creates up to n throwaway intermediate objects, all needing GC. StringBuffer/StringBuilder instead hold one resizable internal buffer and mutate it in place with append(), only reallocating the backing array when its capacity is exceeded (typically by doubling), so a loop of n appends produces O(log n) reallocations instead of O(n) throwaway String objects. This is why loops that build strings should use StringBuilder rather than repeated + concatenation.
Why is a char[] preferred over String for storing a password?
Because String is immutable, once a password is read into a String, its content cannot be cleared — it sits in memory (potentially pinned in the string pool, or simply un-collectable until GC gets to it) for an indeterminate, uncontrolled amount of time, during which it could be exposed via a heap dump, memory-scanning tool, or core dump. A char[] can be explicitly overwritten the instant it's no longer needed (Arrays.fill(passwordChars, ' ')), minimizing the window sensitive data is exposed. As a smaller secondary benefit, printing a char[] directly (e.g. accidentally via a logging call) prints its object identity rather than its contents, unlike a String, which reduces the risk of accidentally logging a password in plaintext.
What does the String.intern() method do?
intern() looks up the string pool for an entry with the same content as the string it's called on. If found, it returns the pooled reference; if not, it adds this string's value to the pool and returns that new pooled reference. This is the tool for de-duplicating strings that were built via new String(...) or concatenation, so that == comparisons behave like .equals() for interned strings, and so that many logically-identical strings share one object in memory. It's a double-edged tool, though — interning a large number of distinct, rarely-repeated strings adds lookup/insertion overhead to the pool for no memory benefit.
Where does the string pool live in memory? Is its size fixed? How is it implemented?
Prior to Java 7, the string pool lived in PermGen (part of the method area), which had a small, largely fixed size — heavy interning could throw OutOfMemoryError: PermGen space. Since Java 7 (7u40+), the pool was moved into the main heap, where it's garbage-collected like any other object and effectively bounded only by heap size rather than a hard fixed cap. Internally, the pool is implemented as a native hash table (the JVM's "StringTable") mapping string content to a canonical reference; its bucket count is tunable via the JVM flag -XX:StringTableSize, and unreferenced pooled strings can be collected during GC.
What design pattern is the String class built on?
The Flyweight pattern. The string pool avoids creating duplicate objects for identical literal content by sharing one canonical instance across every reference that needs that value — exactly the flyweight idea of sharing fine-grained, immutable objects to reduce memory footprint. This sharing is only safe because String is immutable: if pooled strings could be mutated, one reference changing the value would corrupt it for every other holder of that same shared instance.
What is the difference between == and .equals() when comparing Strings?
== compares references — whether two variables point at the exact same object in memory. .equals() (overridden by String) compares content — whether the character sequences are equal, regardless of which object(s) they live in. Two string literals with the same content are typically ==-equal because both resolve to the same pooled instance, which is what makes this such a common gotcha: "abc" == "abc" is true, but new String("abc") == "abc" is false, while .equals() is true in both cases. Rule of thumb: always use .equals() (or Objects.equals() for null-safety) to compare string values; reserve == for checking reference identity.
What notable changes has the String class had in recent Java versions?
  • Compact Strings (Java 9) — internally, String switched from a char[] (always 2 bytes/char) to a byte[] plus a coder flag, storing Latin-1-only content as 1 byte/char and falling back to UTF-16 (2 bytes/char) only when needed — a significant memory win for typical ASCII-heavy strings, transparent to application code.
  • New instance methods (Java 11) — isBlank(), strip()/stripLeading()/stripTrailing() (Unicode-aware trim), repeat(n), and lines() (splits into a Stream<String> of lines).
  • Text blocks (Java 13, standardized in 15) — """multi-line string""" syntax for multi-line literals (e.g. embedded JSON/SQL) without manual \n and concatenation.
  • StringJoiner / String.join() (Java 8) — convenient delimiter-based joining without manually managing a StringBuilder and trailing separator.

Collections Framework

The Collections Framework is where interviewers separate people who've merely used List/Map from people who understand what's happening underneath — hashing, resizing, iteration semantics, and thread-safety trade-offs. Expect both "how does X work internally" questions and "when would you reach for Y instead of Z" comparisons.

Explain the internal working of HashMap.
A HashMap is backed by an array of "buckets" (Node<K,V>[] table). On put(key, value): the key's hashCode() is computed and then "spread" (XOR'd with its own upper bits, roughly h ^ (h >>> 16)) to reduce collisions caused by poor low-bit distribution; the bucket index is (capacity - 1) & hash. The map then walks that bucket's chain, calling equals() against each existing key — if a match is found the value is replaced, otherwise a new node is appended. When size exceeds capacity * loadFactor (default 0.75), the table resizes (capacity doubles) and every entry is rehashed into the new table. Since Java 8, if a single bucket's chain grows to 8 or more entries and the table has at least 64 buckets, that bucket is "treeified" into a red-black tree, bounding worst-case lookup at O(log n) instead of O(n) — see the diagram below.
When entries collide, they chain as a linked list. Once one bucket holds ≥8 entries and the table has ≥64 buckets, Java 8+ treeifies that bucket into a red-black tree, bounding worst-case lookup at O(log n) instead of O(n).
What are the two parameters used to tune HashMap performance?
Initial capacity — the number of buckets the table starts with; sizing this close to the expected number of entries up front avoids repeated resize/rehash cycles as the map grows. Load factor (default 0.75) — the fraction of capacity that can fill before a resize is triggered. A lower load factor trades memory for fewer collisions and faster average lookups; a higher load factor is more memory-efficient but increases collision chains. The default 0.75 is a deliberate balance between time and space cost.
If elements going into a HashMap are already comparable / naturally ordered, how can that improve performance?
Global insertion order doesn't affect a plain HashMap, since bucket placement is purely a function of hashCode(), not insertion sequence. However, Java 8's treeification optimization specifically benefits keys that implement Comparable: when a bucket is converted to a red-black tree, the JDK needs a total ordering to arrange nodes, and it uses the keys' natural Comparable ordering when available (falling back to a tie-break based on class name / identity hash otherwise). So keys that implement Comparable get a well-defined, efficient O(log n) tree lookup once treeified, rather than relying on the messier fallback ordering — a good reason to make custom key classes implement Comparable even when using them in a HashMap rather than a TreeMap.
How does HashMap handle collisions in hashing?
When two keys hash to the same bucket index, HashMap chains them together in that bucket. Historically (pre-Java 8) this was always a singly-linked list, walked with equals() to find or insert the right entry — O(n) worst case if many keys collide. Since Java 8, once a single bucket's chain reaches the TREEIFY_THRESHOLD (8 entries) and the overall table has at least MIN_TREEIFY_CAPACITY (64) buckets, that bucket is converted into a red-black tree, dropping worst-case lookup within the bucket to O(log n). If the table is later resized and a bucket's entry count drops back below UNTREEIFY_THRESHOLD (6), it's converted back to a plain list.
When do you override hashCode() and equals()?
Override both whenever you want value-based equality for a class — i.e., you want two distinct instances with the same logical content to be treated as equal, particularly if instances will be used as HashMap/Hashtable keys or stored in a HashSet. The contract: if a.equals(b) is true, then a.hashCode() == b.hashCode() must also hold (the reverse isn't required — different objects may share a hash code). Always override them together: overriding only equals() silently breaks hash-based collections (a logically-equal duplicate can land in a different bucket and never be found), and overriding only hashCode() leaves reference-based equality in place. equals() must also be reflexive, symmetric, transitive, consistent, and return false for null. In modern code, Objects.equals() and Objects.hash() make this easy to implement correctly.

What is a fail-safe iterator?

What is a collection?
In the general sense, a "collection" is any object that groups multiple elements into a single unit. In Java specifically, java.util.Collection is the root interface of the Collections Framework, defining the common operations shared by lists, sets, and queues: add(), remove(), contains(), size(), iterator(), and so on. Map is conceptually part of the same framework but notably does not extend Collection, since it stores key-value associations rather than a flat group of elements.
How does Collections.synchronizedXxx() work?
Collections.synchronizedList(list), synchronizedMap(map), synchronizedSet(set), etc. wrap the given collection in a decorator whose every method is guarded by a lock (either the wrapper instance itself, or a mutex object you supply), making each individual call atomic and thread-safe. This does not make compound operations (like "check if absent, then insert" or iterating the whole collection) atomic — a series of otherwise-safe calls can still race between threads. In particular, iterating a synchronized collection still requires the caller to manually synchronized on the wrapper for the duration of the loop, or a concurrent ConcurrentModificationException can still occur.
Difference between Collection and Collections?
Collection (interface) is the root of the Collections Framework's type hierarchy, defining the common contract implemented by List, Set, and Queue. Collections (final utility class in java.util) is a set of static helper methods that operate on or return collections — sort(), reverse(), shuffle(), max()/min(), binarySearch(), unmodifiableList(), synchronizedList(), emptyList(), and more — conceptually analogous to how Arrays provides helper methods for raw arrays.

public class MyArrayList<E> {
    private Object[] data = new Object[10];   // default initial capacity
    private int size = 0;

    public void add(E element) {
        if (size == data.length) {
            data = Arrays.copyOf(data, data.length * 2);   // grow: double capacity
        }
        data[size++] = element;
    }

    @SuppressWarnings("unchecked")
    public E get(int index) {
        if (index < 0 || index >= size) throw new IndexOutOfBoundsException();
        return (E) data[index];
    }

    public E remove(int index) {
        E removed = get(index);
        int numMoved = size - index - 1;
        if (numMoved > 0) {
            System.arraycopy(data, index + 1, data, index, numMoved);   // shift left
        }
        data[--size] = null;   // avoid memory leak on the now-unused slot
        return removed;
    }

    public int size() { return size; }
}
Write code for a simplified LinkedList implementation.
The core mechanics: a Node holding a value plus next/prev references, with head/tail pointers so both ends can be updated in O(1) without shifting anything. 
public class MyLinkedList<E> {
    private static class Node<E> {
        E item;
        Node<E> next, prev;
        Node(Node<E> prev, E item, Node<E> next) {
            this.prev = prev; this.item = item; this.next = next;
        }
    }

    private Node<E> head, tail;
    private int size = 0;

    public void addLast(E element) {
        Node<E> newNode = new Node<>(tail, element, null);
        if (tail == null) head = newNode; else tail.next = newNode;
        tail = newNode;
        size++;
    }

    public E get(int index) {
        if (index < 0 || index >= size) throw new IndexOutOfBoundsException();
        Node<E> current = head;
        for (int i = 0; i < index; i++) current = current.next;   // O(n) traversal
        return current.item;
    }

    public E removeFirst() {
        if (head == null) throw new NoSuchElementException();
        E value = head.item;
        head = head.next;
        if (head == null) tail = null; else head.prev = null;
        size--;
        return value;
    }

    public int size() { return size; }
}

Which is better, ArrayList or LinkedList, and in which conditions?
In practice, ArrayList wins for the vast majority of real-world workloads — even ones with frequent inserts/removes — because modern CPUs punish the pointer-chasing and poor cache locality of a linked structure far more than the cost of shifting array elements, and reaching a middle position in a LinkedList is already O(n) traversal, which usually erases any theoretical advantage from its O(1) unlink. LinkedList only clearly wins when you need genuine Deque behavior (cheap add/remove at both ends) or you already hold an Iterator/ListIterator positioned at the right spot and only need O(1) removal there without shifting, and you don't need random access.
Interview tip

Benchmarks consistently show ArrayDeque outperforming LinkedList even for pure add/remove-at-the-ends workloads, thanks to cache locality. Reach for LinkedList only when you specifically need combined List + Deque semantics on the same object.

How do you make a collection read-only?
Collections.unmodifiableList(list) (and the unmodifiableSet/unmodifiableMap equivalents) wrap a collection in a view that throws UnsupportedOperationException on any mutating call. The important caveat: it's only a view — it doesn't copy anything, so changes made directly to the original underlying collection still show through the "unmodifiable" wrapper. For a genuinely independent, immutable snapshot, use the Java 9+ factory methods instead: List.copyOf(list), Set.copyOf(set), Map.copyOf(map), or literal construction via List.of(...)/Map.of(...) — these are truly immutable and hold their own data.
How do you make any collection synchronized?
Wrap it with the corresponding Collections.synchronizedXxx() factory — Collections.synchronizedList(list), synchronizedSet(set), synchronizedMap(map), or the generic synchronizedCollection(collection). As covered above, remember that this only synchronizes individual method calls; iterating the result still requires the caller to hold a lock on the wrapper for the whole loop, since a fail-fast iterator over a synchronized wrapper can still throw ConcurrentModificationException if another thread mutates it mid-iteration.

So calling add() throws UnsupportedOperationException at runtime.

How does ordering work in TreeMap/TreeSet?
Both are backed by a red-black tree and keep their elements/keys in sorted order at all times — insertion, not just retrieval, maintains the order. By default they use the keys'/elements' natural ordering via Comparable.compareTo(); passing a custom Comparator to the constructor overrides that with any ordering you define (and if you supply one, the keys don't need to implement Comparable at all). What is CopyOnWriteArrayList, and when would you use it?
A thread-safe List variant where every mutating operation (add, set, remove) creates a fresh copy of the entire backing array rather than modifying it in place, then swaps the reference atomically. This makes reads (including iteration) completely lock-free and fail-safe — iterators traverse a fixed snapshot and never throw ConcurrentModificationException, and never need external synchronization. The obvious trade-off is that every write is O(n), and memory usage spikes briefly during the copy, so it's a poor fit for write-heavy usage. It shines in specifically read-heavy, write-rare scenarios — the textbook example is a list of event listeners, which is iterated frequently (on every event) but modified only occasionally (on subscribe/unsubscribe).
What are the Java collection factory methods (List.of(), Set.of(), Map.of()), and how do they differ from Collections.unmodifiableList()?
Introduced in Java 9, List.of(...), Set.of(...), and Map.of(...) (plus Map.ofEntries(Map.entry(k, v), ...) for larger maps) create genuinely immutable collections in one line, without a separate mutable collection to build up first. Unlike Collections.unmodifiableList(), which only wraps a view around an existing mutable collection (so changes to the source still leak through), these factories own their data outright — there is no underlying mutable collection at all, mutating attempts always throw UnsupportedOperationException, and the implementations are typically more compact in memory since they don't need resizing support. A few sharp edges: they reject null elements/keys/values (throwing NullPointerException), and Map.of() throws IllegalArgumentException on duplicate keys instead of silently overwriting.

Multithreading & Concurrency

These questions test whether you understand the JVM's threading model underneath the syntax — how a thread actually moves through its lifecycle, when a lock is genuinely needed versus decorative, and which java.util.concurrent tool replaces the error-prone hand-rolled wait()/notify() code most candidates default to. Expect a mix of fundamentals and the modern executor/atomic/CompletableFuture toolkit interviewers now assume you know.

What is a thread?
A thread is a lightweight sub-process — the smallest independently schedulable unit of execution. It has its own program counter, call stack, and local variables, but shares the process's heap, open files, and other resources with every other thread in that process. Every Java program has at least one thread (main); most real applications spawn more to do work concurrently.
What is multithreading?
Multithreading is running multiple threads within a single process concurrently so independent parts of a program can make progress at (logically or physically) the same time. It improves CPU utilization on multi-core hardware and application responsiveness — e.g. a UI or request-handling thread stays responsive while background threads do I/O or computation — at the cost of added complexity around shared mutable state.
How is multithreading achieved in Java?
By creating and starting instances of java.lang.Thread — either by extending Thread and overriding run(), or (preferred) by implementing Runnable/Callable and handing that task to a Thread or an ExecutorService — then calling start(), which asks the JVM/OS to allocate a new call stack and schedule the thread independently. Every higher-level construct (thread pools, CompletableFuture, the Fork/Join framework, parallel streams) is built on top of this same primitive.
What are the different ways to create a thread in Java?
Four common approaches, in order of preference:
// 1. Extend Thread and override run()
class MyThread extends Thread {
    public void run() { System.out.println("running"); }
}
new MyThread().start();

// 2. Implement Runnable — preferred, leaves the class free to extend something else
class MyTask implements Runnable {
    public void run() { System.out.println("running"); }
}
new Thread(new MyTask()).start();

// 3. Lambda — Runnable is a functional interface
new Thread(() -> System.out.println("running")).start();

// 4. Callable + ExecutorService — when the task must return a value or throw a checked exception
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> future = pool.submit(() -> 42);
Implementing Runnable/Callable is generally favored over extending Thread, since Java has single inheritance and this keeps the task decoupled from the threading mechanism.
How do we make threads synchronized?
With the synchronized keyword — as a method modifier (an instance method locks on this; a static method locks on the Class object), or as a block synchronized on an explicit monitor object, which is preferred because it narrows the critical section to only what genuinely needs protection. Since Java 5, java.util.concurrent.locks.ReentrantLock offers an explicit alternative with capabilities synchronized lacks: a timed tryLock(), interruptible acquisition, and fairness policies.
public synchronized void increment() { count++; }        // locks on 'this'
public static synchronized void resetAll() { }            // locks on MyClass.class

public void increment() {
    synchronized (lockObj) {                                // locks on an explicit monitor
        count++;
    }
}
What are volatile variables?
volatile guarantees visibility and ordering, not atomicity: every read of a volatile field sees the most recently written value from any thread — the JVM forbids caching it in a CPU register or per-thread cache and forces reads/writes through main memory — and it establishes a happens-before relationship that prevents instruction reordering around it. It is not a substitute for synchronization on compound operations: volatile int count; count++; is still a race condition, because increment is read-modify-write, not a single atomic step. Use volatile for simple flags (e.g. a shutdown boolean another thread polls); use AtomicInteger or synchronized when you need an atomic read-modify-write.

Difference between wait() and yield()?
wait() (declared on Object) makes the current thread give up the CPU and the monitor lock, entering WAITING/TIMED_WAITING until notified or timed out — it's a coordination primitive. Thread.yield() is just a scheduling hint telling the JVM "another thread of the same priority may run now" — the thread stays RUNNABLE, releases no lock, and the scheduler is free to ignore the hint and reschedule the same thread immediately. yield() is rarely used in real code because its behavior is unspecified and platform-dependent.
Difference between join() and yield()?
t.join() blocks the calling thread until thread t finishes (or an optional timeout elapses) — used to wait for a specific thread's result. Thread.yield() is a static, argument-less hint that the currently running thread is willing to pause so another equal-priority thread can run — it isn't waiting for anything specific and gives no ordering guarantee at all.

Calling the wrong one when several distinct wait-conditions share one monitor can wake a thread that still can't proceed, leaving the actually-runnable thread asleep — a classic "missed signal" bug.
In which scenario are notify() and notifyAll() used? Give an example.
Classic example: a bounded buffer shared by producers and consumers. Producers wait on "not full", consumers wait on "not empty" — both sets of threads are parked on the same monitor. If you only ever call notify(), you might wake a producer when a consumer actually needed to run (or vice versa), leaving the genuinely runnable thread asleep indefinitely — so notifyAll() is the safe default here. notify() is only safe when there is exactly one wait-condition and any woken waiter can make progress, e.g. a single-slot mailbox with exactly one producer thread and one consumer thread. Why are wait() and notify() defined on the Object class rather than the Thread class?
Because what you actually wait/notify on is an object's intrinsic monitor, not a thread — any object can be a monitor, and a thread calls wait()/notify() on whichever object's monitor it currently holds via a synchronized block. Putting these methods on Thread wouldn't make sense, since a thread doesn't own a monitor — the object being synchronized on does. This is also exactly why calling wait()/notify() outside a synchronized block on that same object throws IllegalMonitorStateException.
If a class is extending Thread but needs functionality from another class, how can that be done?
Java doesn't support multiple class inheritance, so once a class extends Thread its one inheritance slot is used up. The fix is composition over inheritance: implement Runnable instead, put the logic there (that class is now free to extend whatever else it needs), and hand an instance of it to a Thread constructor — new Thread(myRunnable).start() — or submit it to an ExecutorService. This is one of the standard reasons "implement Runnable, don't extend Thread" is the recommended default.
What is a monitor in Java?
A monitor is the mutual-exclusion-plus-condition-variable mechanism built into every Java object: exactly one thread at a time can hold an object's monitor (entered via a synchronized method or block), and any thread that can't acquire it blocks. wait()/notify()/notifyAll() operate on that same object's monitor, letting a thread release it temporarily and be woken later. Conceptually it's the classical Hoare/Mesa "lock + wait-set" pair, built into every object rather than requiring a separate monitor type.
What is the lifecycle of a thread?
Six states, defined by Thread.State: NEW (created, start() not yet called), RUNNABLE (executing, or eligible to run — Java doesn't distinguish "ready" from "actually running"), BLOCKED (waiting to enter a synchronized block/method because another thread holds the lock), WAITING (waiting indefinitely — wait()/join() with no timeout, or LockSupport.park()), TIMED_WAITING (waiting with a bound — sleep(ms), wait(ms), join(ms), park(ms)), and TERMINATED (run() returned normally, or an uncaught exception propagated out of it). What happens if you call the run() method directly instead of calling start()?
run() executes like any ordinary method call — synchronously, on the calling thread, with no new call stack created. The output looks the same, which is exactly what makes this a common bug: no actual concurrency happens. start() is the only way to get the JVM to allocate a new thread of execution and have it eventually invoke run().
What is the memory allocation for threads?
Each thread gets its own JVM stack (one frame per active method call, holding local variables and partial results — this is exactly why local variables are inherently thread-safe), its own PC (program counter) register tracking the next instruction, and its own native method stack for JNI/native calls. All of this is separate from the heap and method area/metaspace, which are shared across every thread in the process — which is exactly why objects on the heap need synchronization while purely local variables don't. Per-thread stack size is tunable with -Xss.
What is synchronization? Explain class-level locking and object-level locking.
Synchronization restricts access to a shared resource so only one thread executes a critical section at a time, preventing race conditions on mutable shared state.
  • Object-level locking — a synchronized instance method, or a synchronized(this) block, locks on the specific object instance. Two threads calling synchronized methods on different instances don't block each other.
  • Class-level locking — a synchronized static method (or synchronized(MyClass.class)) locks on the Class object itself, which is shared by every instance — so threads operating on different instances still serialize on that one class-level lock. Used to guard shared static state.
Difference between interrupt() and yield()?
t.interrupt() sets a thread's interrupt flag — and, if the thread is currently blocked in wait()/sleep()/join(), throws InterruptedException immediately to unblock it. It's a cooperative cancellation signal, not a forced stop. Thread.yield() is unrelated: it's only a hint that the running thread is willing to let an equal-priority thread run, with no connection to cancellation or interruption at all.
Can the start() method be overridden?
Syntactically, yes — Thread.start() isn't final — but doing so is almost always wrong. If a subclass overrides start() without calling super.start(), the JVM never actually creates a new thread of execution, so run() just executes on the calling thread like a plain method call — the same trap as calling run() directly. If you need to customize behavior around thread startup, override run(), not start().
What is livelock? What is meant by "lock" in livelock?
A livelock is when two or more threads keep actively responding to each other's state changes without making any real progress. Unlike deadlock, the threads aren't frozen — they're busy, constantly changing state, but stuck in a repeating cycle (the classic analogy: two people in a hallway who keep stepping the same direction to let each other pass). The "lock" in livelock is figurative — it describes the threads being locked into that unproductive cycle of mutual reaction, not an actual synchronized lock or mutex being held. It's typically fixed by adding randomized backoff or a priority/ordering rule that breaks the symmetry.
What are the pros and cons of multithreading?
  • Pros: better CPU/resource utilization on multi-core hardware; improved responsiveness (background work doesn't block a UI or request thread); natural fit for inherently concurrent problems (e.g. serving many simultaneous connections); can reduce overall latency for parallelizable workloads.
  • Cons: significantly harder to design, debug, and test (race conditions and non-deterministic bugs that don't reproduce reliably); context-switching overhead; increased risk of deadlock, livelock, and starvation; added synchronization cost under heavy contention.
What is the Executor framework / ExecutorService, and why use it instead of creating threads directly?
java.util.concurrent's Executor framework decouples task submission from thread management. Creating an OS thread per task (new Thread(task).start() everywhere) isn't free, and unbounded thread creation can exhaust memory; an ExecutorService instead runs submitted Runnable/Callable tasks on a managed, reusable pool of worker threads. Executors' factory methods cover common shapes — newFixedThreadPool(n) (bounded pool, unbounded queue), newCachedThreadPool() (grows as needed, reuses idle threads), newSingleThreadExecutor() (sequential execution), newScheduledThreadPool(n) (delayed/periodic tasks). In production, prefer constructing ThreadPoolExecutor directly with an explicit bounded queue and rejection policy — several of the Executors convenience factories create unbounded queues or thread counts that can exhaust memory under load.
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(() -> doWork());
pool.shutdown();               // stop accepting new tasks; let queued ones finish

What is the Fork/Join framework?
A framework (since Java 7) for parallelizing divide-and-conquer algorithms: a task recursively splits into smaller subtasks — RecursiveTask<V> if it returns a result, RecursiveAction if not — until a subtask is small enough to compute directly, then results are combined back up. It runs on a ForkJoinPool, which uses work-stealing: idle worker threads steal queued subtasks from busy threads' deques, keeping all cores busy without a central bottleneck. Parallel streams (.parallelStream()) use the common ForkJoinPool under the hood.
class SumTask extends RecursiveTask<Long> {
    private final int[] arr; private final int lo, hi;
    protected Long compute() {
        if (hi - lo <= THRESHOLD) { /* sum directly, sequentially */ }
        int mid = (lo + hi) / 2;
        SumTask left = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                        // run left asynchronously
        long rightResult = right.compute();  // compute right on this thread
        return left.join() + rightResult;
    }
}

What are atomic classes, and how do they achieve thread safety without locks?
java.util.concurrent.atomic classes (AtomicInteger, AtomicLong, AtomicReference, AtomicBoolean, etc.) provide lock-free, thread-safe operations on a single variable using CAS (compare-and-swap) — a hardware-level atomic instruction: "update this memory location to newValue only if it currently equals expectedValue, in one indivisible step." A thread that loses the race under contention just retries with the newest value instead of blocking, which is typically far cheaper than a lock for simple counters/flags/references — AtomicInteger.incrementAndGet() internally loops on compareAndSet until it succeeds. A subtlety interviewers probe: the ABA problem — a value changes A → B → A between a thread's read and its CAS, so the CAS succeeds even though the value did change in between; AtomicStampedReference/AtomicMarkableReference address this by pairing the value with a version stamp.
What is ThreadLocal, and when would you use it?
ThreadLocal<T> gives each thread its own independent copy of a variable — reads/writes through it never see another thread's value, so it avoids synchronization entirely for genuinely per-thread state: a per-request user/session context, a non-thread-safe SimpleDateFormat instance, transaction IDs, or per-thread random seeds.
Watch for this
In thread-pooled environments (app servers, ExecutorServices), the underlying thread — and anything in its ThreadLocals — outlives a single logical task. Forgetting to call remove() after use leaks memory (the value stays attached to the pooled thread indefinitely) and can leak stale data into the next task that happens to reuse that thread. Always clear a ThreadLocal in a finally block.
What is a deadlock, and how do you prevent or detect it?
A deadlock is a cycle of two or more threads each holding a lock the other needs and waiting forever — e.g. Thread A holds lock1 and wants lock2, Thread B holds lock2 and wants lock1. Four conditions (Coffman conditions) must all hold at once: mutual exclusion, hold-and-wait, no preemption, and circular wait — breaking any one prevents deadlock. In practice: always acquire multiple locks in a fixed global order (eliminates circular wait — the most common fix), use ReentrantLock.tryLock(timeout) to back off instead of blocking forever, keep critical sections small, and prefer higher-level concurrent utilities (ConcurrentHashMap, BlockingQueue, ExecutorService) over hand-rolled multi-lock code. To detect an existing deadlock, take a thread dump (jstack <pid>) — the JVM directly reports "Found one Java-level deadlock" along with the exact threads and locks involved.
Implement the producer-consumer pattern in Java.
The modern, idiomatic version uses a BlockingQueue, which handles all the waiting/notifying internally: put() blocks when the queue is full, take() blocks when it's empty.
BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

Runnable producer = () -> {
    for (int i = 0; i < 100; i++) {
        try { queue.put(i); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
};

Runnable consumer = () -> {
    while (true) {
        try { process(queue.take()); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); break; }
    }
};

new Thread(producer).start();
new Thread(consumer).start();
Pre-Java-5, this was hand-rolled with wait()/notifyAll() on a shared buffer guarded by explicit synchronized blocks — interviewers sometimes ask for that version too, specifically to check you understand what BlockingQueue is doing internally.

Design Patterns

Design pattern questions rarely ask you to recite a GoF definition from memory — they ask what problem a pattern solves and want a minimal, correct code sketch in return. Singleton is the perennial favorite (and the one most likely to come with a "now break it" follow-up about reflection or cloning), but expect the full creational/structural/behavioral spread below.

What are the three categories of GoF design patterns?
  • Creational — object creation mechanics: Singleton, Factory Method, Abstract Factory, Builder, Prototype.
  • Structural — how classes/objects compose into larger structures: Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight.
  • Behavioral — how objects communicate and share responsibility: Observer, Strategy, Command, Template Method, Iterator, State, Chain of Responsibility, Mediator, Memento, Visitor.
Of the 23 original GoF patterns, Java interviews overwhelmingly focus on the dozen or so covered below.
Can we make a private constructor? Why would you?
Yes — private constructors are a normal, common technique, not a special case. Typical uses: preventing instantiation entirely for a utility/helper class that only holds static members (java.lang.Math has a private constructor); controlling instantiation through a static factory method instead of new (returning a cached instance, a subtype, or validating arguments first); and implementing Singleton, where the only way to obtain the instance is a static accessor. A class with only a private constructor also can't be subclassed from outside it (a subclass constructor must be able to call an accessible super-constructor) and can't be instantiated with new from outside the declaring class — only from a static member inside that same class.
Write code for the Singleton pattern that avoids reflection and clone attacks.
The simplest bulletproof option is an enum singleton (Joshua Bloch's recommendation in Effective Java): the JLS guarantees exactly one instance per enum constant, the JVM explicitly refuses reflective instantiation of enum types (Constructor.newInstance() throws IllegalArgumentException for a class with the ENUM modifier), and java.lang.Enum declares clone() as final and always throwing CloneNotSupportedException — so an enum singleton cannot be cloned at all, and its serialization is automatically safe too (deserializing an enum constant returns the existing constant, never a new one).
public enum Singleton {
    INSTANCE;

    private int state;

    public void doSomething() { /* ... */ }
}
// usage: Singleton.INSTANCE.doSomething();
When you can't use an enum (e.g. the singleton must extend some other class), the classic alternative is double-checked locking, with an explicit guard in the constructor against reflection and an overridden clone() that always throws:
public class Singleton implements Cloneable {
    private static volatile Singleton instance;

    private Singleton() {
        // Reflection guard — blocks a second reflective instantiation
        // once getInstance() has already produced the real instance.
        if (instance != null) {
            throw new IllegalStateException("Already initialized — use getInstance()");
        }
    }

    public static Singleton getInstance() {
        if (instance == null) {                 // 1st check, no locking (fast path)
            synchronized (Singleton.class) {
                if (instance == null) {          // 2nd check, inside the lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException("Singleton instance cannot be cloned");
    }
}
Watch for this
instance must be volatile — without it, a second thread can observe a partially-constructed object due to instruction reordering (the classic pre-Java-5-memory-model double-checked-locking bug). Also note the reflection guard only defends against reflective construction attempted after getInstance() has already run once; if reflection is used before any normal call, it slips through. The enum form above has no such gap, which is why it's the preferred answer when the design allows it.
What happens to a singleton class if its object is cloned?
If the class implements Cloneable and does not override clone(), calling instance.clone() invokes Object.clone(), which performs a shallow field-by-field copy without calling any constructor — producing a second, distinct object that is != the original. That silently breaks the singleton guarantee: any code relying on singleton == Singleton.getInstance() reference equality, or on shared mutable state living in the one true instance, now sees two independent copies drifting apart. If the class doesn't implement Cloneable at all, calling clone() simply throws CloneNotSupportedException. The fix, shown above, is to override clone() to unconditionally throw — or to have it return the existing instance instead of a new copy.
Factory Method pattern — what problem does it solve?
Lets calling code ask for an object by intent without knowing (or hard-coding) the concrete class to instantiate — creation logic is centralized in one place instead of scattered new calls, so adding a new type doesn't require touching every call site.
interface Shape { void draw(); }
class Circle implements Shape { public void draw() { System.out.println("circle"); } }
class Square implements Shape { public void draw() { System.out.println("square"); } }

class ShapeFactory {
    static Shape create(String type) {
        return switch (type) {
            case "circle" -> new Circle();
            case "square" -> new Square();
            default -> throw new IllegalArgumentException(type);
        };
    }
}
// usage: Shape s = ShapeFactory.create("circle");
Abstract Factory pattern — what problem does it solve?
Creates families of related objects that must be used together, without the client specifying their concrete classes — a "factory of factories." Where Factory Method produces one product, Abstract Factory produces a consistent set (e.g. all UI widgets from the same look-and-feel).
interface Button { void render(); }
interface Checkbox { void render(); }

interface UIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

class MacFactory implements UIFactory {
    public Button createButton() { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}
class WindowsFactory implements UIFactory {
    public Button createButton() { return new WindowsButton(); }
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}
Builder pattern — what problem does it solve?
Constructs a complex, often-immutable object step by step through named calls instead of a telescoping constructor with many positional (and easily mixed-up) parameters, several of which may be optional.
public final class Pizza {
    private final String size;
    private final boolean cheese;
    private final boolean pepperoni;

    private Pizza(Builder b) {
        this.size = b.size; this.cheese = b.cheese; this.pepperoni = b.pepperoni;
    }

    public static class Builder {
        private String size;
        private boolean cheese, pepperoni;
        public Builder size(String s) { this.size = s; return this; }
        public Builder cheese(boolean c) { this.cheese = c; return this; }
        public Builder pepperoni(boolean p) { this.pepperoni = p; return this; }
        public Pizza build() { return new Pizza(this); }
    }
}
// usage: new Pizza.Builder().size("L").cheese(true).build();
Prototype pattern — what problem does it solve?
Creates new objects by copying an existing "prototype" instance rather than instantiating and re-initializing from scratch — useful when construction is expensive (heavy setup, DB round trips) but a near-identical copy is cheap to produce.
class Sheep implements Cloneable {
    String name;

    @Override
    public Sheep clone() {
        try { return (Sheep) super.clone(); }
        catch (CloneNotSupportedException e) { throw new AssertionError(e); }
    }
}
// usage: Sheep dolly = original.clone();
Observer pattern — what problem does it solve?
Defines a one-to-many dependency so that when a subject's state changes, every registered observer is notified automatically — without the subject knowing anything about the observers' concrete types. It's the basis for event listeners, MVC view updates, and reactive streams.
interface Observer { void update(String event); }

class Subject {
    private final List<Observer> observers = new ArrayList<>();
    void subscribe(Observer o) { observers.add(o); }
    void notifyObservers(String event) { observers.forEach(o -> o.update(event)); }
}
Subject holds a list of Observer references and fans a notification out to all of them whenever its state changes — observers can register or unregister without the Subject ever knowing their concrete type.
Strategy pattern — what problem does it solve?
Lets a class swap its algorithm at runtime by delegating to an interchangeable, interface-implementing strategy object, instead of a large if/switch block picking behavior inline. Since Java 8, simple strategies are often just lambdas implementing a functional interface rather than a full class hierarchy.
interface DiscountStrategy { double apply(double price); }

class NoDiscount implements DiscountStrategy { public double apply(double p) { return p; } }
class TenPercentOff implements DiscountStrategy { public double apply(double p) { return p * 0.9; } }

class Checkout {
    private final DiscountStrategy strategy;
    Checkout(DiscountStrategy s) { this.strategy = s; }
    double total(double price) { return strategy.apply(price); }
}
// usage: new Checkout(p -> p * 0.9).total(100);
Decorator pattern — what problem does it solve?
Attaches additional responsibilities to an individual object dynamically by wrapping it, instead of subclassing every combination of behavior (which explodes combinatorially). java.io streams are the canonical real-world example — new BufferedReader(new FileReader(file)).
interface Coffee { double cost(); }
class SimpleCoffee implements Coffee { public double cost() { return 2.0; } }

abstract class CoffeeDecorator implements Coffee {
    protected final Coffee wrapped;
    CoffeeDecorator(Coffee c) { this.wrapped = c; }
}
class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee c) { super(c); }
    public double cost() { return wrapped.cost() + 0.5; }
}
// usage: new MilkDecorator(new SimpleCoffee()).cost();
Adapter pattern — what problem does it solve?
Converts one interface into another that the client already expects, letting two otherwise-incompatible classes work together without modifying either one. Arrays.asList() adapting an array to the List interface is a familiar JDK example.
interface MediaPlayer { void play(String file); }

class LegacyPlayer { void playOldFormat(String file) { /* ... */ } }

class LegacyPlayerAdapter implements MediaPlayer {
    private final LegacyPlayer legacy = new LegacyPlayer();

Facade pattern — what problem does it solve?
Provides one simplified, higher-level interface over a complex subsystem of classes, hiding internal wiring and coordination from the caller so most client code only ever talks to the facade.
class OrderFacade {
    private final Inventory inventory = new Inventory();
    private final Payment payment = new Payment();
    private final Shipping shipping = new Shipping();

    void placeOrder(Order o) {
        inventory.reserve(o);
        payment.charge(o);
        shipping.schedule(o);
    }
}
Proxy pattern — what problem does it solve?
Provides a stand-in for another object to control access to it — lazy initialization, access control, remote calls, logging/caching — without the client knowing the difference, since the proxy implements the same interface as the real object.
interface Image { void display(); }

class RealImage implements Image {
    RealImage(String file) { loadFromDisk(file); }   // expensive
    public void display() { /* ... */ }
}

class ProxyImage implements Image {
    private RealImage real;
    private final String file;
    ProxyImage(String file) { this.file = file; }
    public void display() {
        if (real == null) real = new RealImage(file); // lazy load
        real.display();
    }
}
Java also ships a built-in java.lang.reflect.Proxy for generating dynamic proxies at runtime — Spring uses exactly this (or CGLIB) to implement @Transactional, @Cacheable, and other AOP-driven annotations.
Command pattern — what problem does it solve?
Encapsulates a request/action as an object, so it can be queued, logged, undone, or parameterized independently of whatever triggers it — decoupling the invoker from the receiver that actually performs the action.
interface Command { void execute(); }

class LightOnCommand implements Command {
    private final Light light;
    LightOnCommand(Light l) { this.light = l; }
    public void execute() { light.on(); }
}

class RemoteControl {
    private Command command;
    void setCommand(Command c) { this.command = c; }
    void pressButton() { command.execute(); }
}
Template Method pattern — what problem does it solve?
Defines the fixed skeleton of an algorithm in a base class, deferring specific steps to subclasses — the overall sequence can't be changed, only individual steps within it.
abstract class DataProcessor {
    // template method — final so subclasses can't reorder the steps
    public final void process() {
        readData();
        processData();
        writeData();
    }
    abstract void readData();
    abstract void processData();
    void writeData() { System.out.println("default write"); } // overridable hook
}
What is Dependency Injection / Inversion of Control, and how does it relate to design patterns?
Not one of the 23 GoF patterns, but a foundational architectural principle interviewers expect alongside them: instead of a class constructing its own dependencies internally (tight coupling, hard to test), the dependencies are supplied — "injected" — from the outside, inverting control of object creation and wiring to a container or framework (e.g. Spring's IoC container). This makes dependencies swappable and mockable in tests, and centralizes how the object graph is assembled. The three common forms are constructor injection (preferred — dependencies are required and immutable), setter injection (optional dependencies), and field injection (concise but harder to test and hides the true dependency list).
class OrderService {
    private final PaymentGateway gateway;
    // constructor injection — dependency supplied, not "new"-ed internally
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }
}

Exception Handling

Exceptions are how Java signals and propagates abnormal conditions without forcing every call site to check return codes. These questions cover the core class hierarchy, the checked/unchecked split, and the control-flow subtleties around try/catch/finally that trip up candidates who've only memorized the keywords.

Every throwable descends from Throwable. Error and its subclasses are always unchecked and generally shouldn't be caught; under Exception, RuntimeException and its subclasses are unchecked, while everything else is checked and compiler-enforced.
What are exceptions?
An exception is an event that disrupts the normal flow of a program's instructions — dividing by zero, accessing an invalid array index, or reading a missing file, for example. Java represents each one as an object (a subclass of Throwable) carrying a message, a stack trace, and optionally a cause. When one occurs, the JVM constructs that object and "throws" it, unwinding the call stack until a matching catch block handles it or the program terminates. Structured exception handling separates normal-path logic from error-handling logic instead of forcing every call site to check return codes.
What is the difference between exception and error?
Both are subclasses of Throwable, but they signal fundamentally different situations. An Exception represents a condition an application can reasonably anticipate and recover from (bad input, a network hiccup, a missing file) and is meant to be caught. An Error represents a serious problem generally outside the application's control — JVM-level failures like running out of memory (OutOfMemoryError) or exhausting stack space (StackOverflowError) — that applications aren't expected to catch or recover from, because the JVM itself may be in an unstable state.
What is the difference between throw and throws?
throw is a statement used inside a method body to actually raise a specific exception instance at that point (throw new IllegalStateException("...")) — at most one throwable is being thrown at a time. throws is part of a method's signature (public void save() throws IOException) that declares which checked exceptions the method might propagate to its caller, letting the compiler enforce handling; it doesn't throw anything itself, and a method can list several exception types separated by commas.
What is the superclass of the Exception class?
java.lang.Exception extends java.lang.Throwable, which itself extends java.lang.Object. So Throwable is the superclass of Exception (and of Error) — it's the root type recognized by the throw/catch mechanism.
What are compile-time and runtime exceptions? Why are they categorized this way?
Java splits exceptions into two buckets based on when the compiler enforces handling:
  • Checked exceptions — subclasses of Exception excluding RuntimeException. The compiler forces every caller to either catch them or declare them with throws. They model conditions a well-written program should anticipate, typically failures external to the JVM (file not found, network timeout, SQL error).
  • Unchecked exceptions — RuntimeException and its subclasses, plus all Errors. The compiler doesn't force handling. They usually indicate programming mistakes (null dereference, bad cast, out-of-bounds index) that are better fixed in code than caught everywhere.
This split keeps recoverable, expected failure modes visible in a method's signature — forcing callers to think about them — while ubiquitous programmer errors don't force a throws declaration onto every method in the codebase.

Can we create user-defined (custom) exceptions? Write code.
Yes — extend Exception for a checked exception or RuntimeException for an unchecked one, and, by convention, provide constructors mirroring the parent's (no-arg, message, message + cause). Custom exceptions let you attach domain-specific fields (an error code, the offending value) and give call sites a precise type to catch instead of a generic Exception.
public class InsufficientFundsException extends Exception {

How can we handle an exception in our class?
Wrap the risky code in a try block and add one or more catch blocks that match the specific exception type(s) it can throw, ordered most-specific to least-specific; optionally add a finally block for cleanup that must run regardless of outcome. At the method level, you can instead declare throws ExceptionType and let the exception propagate to the caller, deferring handling.
Can we handle errors in our class?
Technically yes — Error also extends Throwable, so catch (Error e), or even catch (Throwable t), compiles and will catch it. But you generally shouldn't: most Errors (OutOfMemoryError, StackOverflowError) indicate the JVM itself is in a compromised state, and "handling" them by continuing normal execution is unreliable. Catching Throwable broadly is considered an anti-pattern outside of top-level logging/shutdown handlers.
Is a catch block mandatory after a try block?
No. A try block only requires at least one of catch or finally, not both — try/finally with no catch at all is valid, typically for guaranteed cleanup while letting the exception propagate further up. It's also valid to pair try with resource declarations and no catch, since the resources' close() runs automatically (see try-with-resources below).
What is try-with-resources, and how does it relate to AutoCloseable?
Introduced in Java 7, try-with-resources lets you declare one or more resources in the try(...) parentheses; each must implement AutoCloseable (or the narrower Closeable), and the JVM guarantees close() is called automatically, in reverse declaration order, when the block exits — normally or via exception — eliminating a manual finally block full of null checks. Since Java 9 you can reference an existing effectively-final variable directly without redeclaring it. If both the try body and close() throw, the try body's exception is the one propagated, and the close() failure is attached via addSuppressed() rather than lost.
try (BufferedReader reader = new BufferedReader(new FileReader("data.txt"))) {
    return reader.readLine();
} // reader.close() is called automatically, even if readLine() throws
What is multi-catch, and what are its rules?
Also from Java 7, a single catch clause can handle several unrelated exception types using pipe syntax: catch (IOException | SQLException e). Rules: the listed types must not be subtypes of one another (that would be redundant), and because the compiler can't know which branch actually ran, the caught variable is implicitly final and its static type is the most specific common supertype of the alternatives — you can't reassign it or call a method that exists on only one of the listed types without an explicit cast.
If we return from inside a try block, does control still go to the finally block?
Yes — finally always executes before control actually leaves the method, even if the try (or a catch) block hits a return, continue, break, or throws an uncaught exception. If the try returns a value and finally also contains a return statement, the finally's return silently overrides it — a classic gotcha, and the main reason returning from finally is considered bad practice.
What happens if an exception is thrown from a finally block?
If finally itself throws, that new exception replaces whatever exception (or return value) was already in flight from the try/catch — the original is completely lost unless explicitly preserved via Throwable.addSuppressed() (exactly what try-with-resources does automatically when both the body and close() fail). This is another reason to keep finally blocks minimal and side-effect-focused rather than running risky logic there.
Why is Throwable a class rather than an interface?
Only instances of Throwable (or its subclasses) can be passed to throw and caught by catch — the JVM's athrow bytecode instruction and a compiled method's exception table both require an operand type descending from Throwable. Making it a class, rather than a marker interface implemented by unrelated classes, lets every exception and error share a common implementation for the state that makes exceptions useful: a detail message, an optional cause (for chaining), and a stack trace captured at construction time via fillInStackTrace(). Interfaces couldn't hold that kind of state before Java 8, and even today, sharing it through single inheritance is simpler than requiring every throwable type to reimplement it.
Can we catch a StackOverflowError in a catch block?
Yes — it's a normal object of type Error (specifically a VirtualMachineError), so catch (StackOverflowError e) or catch (Error e) will catch it, and code after the block can keep running. In practice this is rarely useful: by the time it's thrown, the stack has already unwound completely, but the condition that caused the runaway recursion is often still present. It's mostly used for logging/diagnostics right before a controlled shutdown, or to fail one request gracefully in a container without taking down the whole process.

Can we override a superclass method that throws an unchecked exception with one that throws a checked exception in the subclass?

The override can still throw the same unchecked exception, any subclass of it, no exception at all, or arbitrary new unchecked exceptions, since those aren't compiler-enforced.
What is exception chaining, and how do initCause() and the (message, cause) constructors help?
When you catch a low-level exception and rethrow a more meaningful, higher-level one, you should preserve the original as the cause so the root failure isn't lost — either by passing it to a (message, cause) constructor (most Throwable subclasses provide one) or by calling initCause(Throwable) after construction (useful for older exception types that predate the cause constructor; it can only be called once). getCause(), and the default printStackTrace(), then surface a "Caused by: ..." chain — invaluable when a failure crosses architectural layers, such as wrapping a SQLException as a custom data-access exception.

Serialization

Serialization converts an object's state into a byte stream so it can be persisted, cached, or sent across a network — and reconstructed later. These questions probe how much control you actually have over that byte stream, and where the classic pitfalls (versioning, non-serializable fields, singleton leaks) live.

What is the transient keyword?
transient marks a field so the default Java serialization mechanism skips it entirely — it's never written to the byte stream and comes back as the type's default value (null, 0, false, etc.) on deserialization. It's used for fields that either aren't meaningful to persist (caches, derived/computed values, open connections, threads, file handles) or are inherently non-serializable (e.g. a Socket).
What is serialization? Why did it come about, and where have you seen it used in a real system?
Serialization is the process of converting an object graph into a linear byte stream (via ObjectOutputStream) that captures its state, so it can be written to a file, stored in a cache, or sent over a network, then later reconstructed into an equivalent object (deserialization, via ObjectInputStream) — without hand-writing a byte-level encoding for every class. It emerged because distributed and persistent systems needed a language-native way to move live objects across JVM boundaries, or across process restarts, without a custom wire format. Real-world examples: HttpSession replication across servers in a clustered web app, Java RMI passing objects between JVMs, caching frameworks persisting objects to disk, and message queues serializing payloads.
What is a Serial Version UID (serialVersionUID) and why should I use it?
serialVersionUID is a private static final long field that acts as a version stamp for a Serializable class; during deserialization, the JVM compares the UID stored in the stream against the UID of the class currently loaded and throws InvalidClassException if they don't match. You declare it explicitly — rather than relying on the compiler-generated one — so that compatible changes to the class don't spuriously break deserialization of old data, and so you consciously bump it when you make a genuinely incompatible one. It represents your class's version, and should change when the current version isn't backward compatible with earlier serialized data.
What would happen if the serialVersionUID of a class is not defined?
The compiler computes a default value at runtime by hashing structural details of the class — its name, interfaces, fields, and method signatures. This is fragile: because it's derived from the class's shape, almost any change (even a harmless one, like adding a method) can produce a different UID, breaking deserialization of previously-serialized instances with InvalidClassException even though the change may have been perfectly compatible. This is the main reason it's best practice to always declare serialVersionUID explicitly rather than let the compiler generate one.
How can we make a class Serializable?
Implement the marker interface java.io.Serializable — it has no methods to implement. Every non-transient, non-static field must itself be serializable (a primitive, or an object whose class also implements Serializable), or the runtime throws NotSerializableException when it reaches that field. It's also convention to declare an explicit serialVersionUID.
If a class has a transient variable and we want to save its value on deserialization, what can we do?
Provide custom writeObject(ObjectOutputStream out) and readObject(ObjectInputStream in) methods — Serializable's default machinery looks for these specific private methods via reflection and calls them if present. Typically you call out.defaultWriteObject() / in.defaultReadObject() first to handle the normal fields, then explicitly write/read the transient field's value (or a transformed version of it) around that call. This gives you a hook to persist something Java doesn't handle automatically, while keeping default handling for everything else.
private transient String decryptedToken;

private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject();
    out.writeObject(encrypt(decryptedToken));
}

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    decryptedToken = decrypt((String) in.readObject());
}
What happens if your Serializable class contains a member which is not serializable? How do you fix it?
Attempting to serialize an instance throws NotSerializableException at runtime, naming the offending class — it's a runtime failure, not a compile-time error, since the compiler doesn't track this. Fixes: mark the field transient if it doesn't need to survive serialization (and repopulate it after deserialization, e.g. lazily or in readObject()); make the referenced class implement Serializable too, if you own it and all of its fields are serializable; or replace the field with a serializable representation (store a file path or connection string instead of an open Connection, and reconnect on load).

What changes are safe to make to a Serializable class without breaking existing serialized data?
Not every change breaks deserialization of old streams. Compatible changes include: adding new fields (they take default values when reading an old stream), adding classes to the object's hierarchy, and changing a field from static to non-static or from transient to non-transient. Incompatible changes include: deleting an existing field, moving a class up or down the class hierarchy, changing a field's type, or changing a non-static/non-transient field to static/transient — any of these can throw InvalidClassException or silently misread old data. Because this is so easy to get wrong, many production systems avoid the JDK's built-in serialization for long-lived data entirely, in favor of schema-driven formats (Protobuf, Avro, JSON) that version more predictably.
Deserialization seems to bypass constructors — how do you protect a Singleton from being duplicated by it?
Java's default deserialization builds the new instance through internal mechanisms that skip every constructor, which silently breaks the Singleton pattern: deserializing a singleton's serialized form produces a second, distinct instance. The fix is a private Object readResolve() method that returns the canonical singleton instance; if present, the deserialization mechanism calls it and substitutes its return value for the freshly-built object before handing control back to the caller, so no second instance ever escapes.
public class ConfigManager implements Serializable {
    public static final ConfigManager INSTANCE = new ConfigManager();
    private ConfigManager() {}

    protected Object readResolve() {
        return INSTANCE; // replaces the newly deserialized instance
    }
}
Is deserializing data from an untrusted source safe?
No — it's a well-known attack vector. A crafted byte stream can trigger arbitrary code execution through "gadget chains" built from classes already on the classpath (via their readObject() side effects), independent of any bug in your own code. Mitigations: never deserialize data from an untrusted source directly; use ObjectInputFilter (JEP 290, Java 9+, also backported) to allow-list which classes may be deserialized; or avoid native Java serialization for externally-facing data entirely, in favor of a format like JSON that doesn't invoke arbitrary constructors or methods while parsing.

SQL Basics

Even in a Java-heavy interview, SQL fundamentals come up constantly — especially join semantics and set operations, which candidates routinely confuse with each other.

What is the difference between inner and outer join? Explain with an example.
An INNER JOIN returns only the rows where the join condition matches in both tables — rows with no match on either side are dropped. An OUTER JOIN (LEFT, RIGHT, or FULL) keeps unmatched rows from one or both sides, filling the missing columns with NULL: LEFT JOIN keeps every row from the left table, RIGHT JOIN keeps every row from the right, and FULL JOIN keeps every row from both.
-- Employees(id, name, dept_id), Departments(id, name)

SELECT e.name, d.name AS dept
FROM Employees e
INNER JOIN Departments d ON e.dept_id = d.id;
-- only employees that belong to an existing department

SELECT e.name, d.name AS dept
FROM Employees e
LEFT JOIN Departments d ON e.dept_id = d.id;
-- every employee; dept is NULL if unassigned or the department is missing
What is the difference between JOIN and UNION?
JOIN combines columns from two or more tables side by side, based on a related column, producing a wider result (more columns) for each matched row pair. UNION combines rows from two queries vertically — it stacks their result sets into one, so both queries must return the same number of columns with compatible types, and no join condition is involved at all. In short: JOIN grows the result horizontally; UNION grows it vertically.
What is the difference between UNION and UNION ALL?
Both stack the result sets of compatible queries. UNION removes duplicate rows from the combined result, which requires an implicit sort/dedupe step and is slower on large data. UNION ALL keeps every row, including duplicates, and skips that step, so it's faster. Use UNION ALL whenever the inputs can't overlap or duplicates are acceptable.
What is the difference between the WHERE clause and the HAVING clause?
WHERE filters individual rows before any grouping or aggregation happens, and cannot reference aggregate functions directly. HAVING filters groups after GROUP BY has produced aggregated rows, and is specifically designed to filter on aggregate results. When a query has both, WHERE is applied first to cut down rows, then grouping/aggregation happens, then HAVING filters the resulting groups.
SELECT dept_id, COUNT(*) AS emp_count
FROM Employees
WHERE status = 'ACTIVE'
GROUP BY dept_id
HAVING COUNT(*) > 10;

What is a self join, and when would you use one?
A self join joins a table to itself, using two aliases, to compare rows within the same table — typically for hierarchical or relational data stored in one place, like an Employees table with a manager_id that points back to another row's id.
SELECT e.name AS employee, m.name AS manager
FROM Employees e
LEFT JOIN Employees m ON e.manager_id = m.id;
What is an index, and what's the difference between a clustered and a non-clustered index?
An index is an auxiliary data structure (typically a B-tree) that the database maintains alongside a table so it can locate matching rows without scanning every one. A clustered index determines the physical storage order of the table's rows, so a table can have only one; a non-clustered index is a separate structure holding the indexed column(s) plus a pointer back to the actual row, so a table can have several. Indexes dramatically speed up reads (lookups, joins, ORDER BY) but add overhead to writes, since every INSERT/UPDATE/DELETE must maintain them too — a deliberate trade-off, not something to add to every column.

An operation is idempotent if making the same request multiple times produces the same end state as making it once. What is the difference between PUT and PATCH?
Both update an existing resource, but PUT is defined to replace it entirely with the representation supplied in the request body — fields omitted from the body are expected to be cleared. PATCH applies a partial modification, sending only the fields that changed. This is also why PUT is idempotent (sending the same full representation twice yields the same end state), while PATCH's idempotency depends on how the patch is expressed — "set status to CLOSED" is idempotent, "increment retry_count by 1" is not.
What are the categories of HTTP status codes?
Status codes are grouped into five classes by their leading digit: 1xx Informational (request received, processing continues); 2xx Success (200 OK, 201 Created, 204 No Content); 3xx Redirection (301 Moved Permanently, 304 Not Modified); 4xx Client Error — the request itself is the problem (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict); and 5xx Server Error — the server failed to fulfill a valid request (500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable).
Interview tip
401 vs. 403 is a near-universal follow-up: 401 Unauthorized means the caller hasn't authenticated (or authentication failed); 403 Forbidden means they're authenticated but don't have permission to access that resource.
What does "statelessness" mean in REST, and why does it matter?
REST's statelessness constraint means the server holds no client session state between requests — every request must carry all the context needed to process it (auth token, pagination cursor, etc.) rather than relying on server-side session memory. This is what lets REST APIs scale horizontally: any server instance behind a load balancer can handle any request, since none of them are pinned to session state living on a particular node. It's the main behavioral difference from a traditional stateful web session tied to one server.

JVM Internals & Memory Management

Questions about what actually happens under the hood when Java code runs — memory layout, class loading, garbage collection, and reference types. These separate candidates who've memorized syntax from ones who understand the runtime.

Heap and Method Area/Metaspace are shared by every thread; each thread gets its own Stack, PC Register, and Native Method Stack.
What is the difference between JVM, JRE, and JDK?
The JVM (Java Virtual Machine) is the runtime engine that actually executes bytecode — it's an abstract specification with concrete implementations (HotSpot, OpenJ9). The JRE (Java Runtime Environment) is the JVM plus the core class libraries needed to run compiled Java programs, but it has no compiler. The JDK (Java Development Kit) is the JRE plus development tools (javac, jar, javadoc, debuggers) needed to write and compile Java code. So: JDK ⊃ JRE ⊃ JVM.
Explain briefly how the JVM works end to end.
Source (.java) is compiled by javac into platform-independent bytecode (.class). The Class Loader Subsystem loads those classes on demand, verifies the bytecode for safety, and prepares/initializes static data. The Execution Engine then runs the bytecode — interpreting it instruction-by-instruction at first, while the JIT compiler profiles hot methods and compiles them to native machine code for speed. Memory for objects, classes, and threads is managed across the runtime data areas (heap, method area, per-thread stacks) shown above, with the Garbage Collector reclaiming heap memory no longer reachable from GC roots.
What is the JIT (Just-In-Time) compiler?
The JIT compiler is part of the JVM's execution engine. Rather than interpreting every bytecode instruction on every run (slow), it detects "hot" methods/loops executed frequently and compiles them directly to native machine code at runtime, caching the compiled version for reuse. This is why long-running Java processes (like servers) tend to speed up after a warm-up period — the JIT has had time to identify and optimize the hot paths. HotSpot uses tiered compilation (C1 for fast startup, C2 for deep optimization of very hot code).
What is garbage collection? Can we force it to run?
Garbage collection (GC) is the JVM's automatic process of identifying objects no longer reachable from any GC root (local variables on the stack, static fields, active threads) and reclaiming their heap memory, so developers don't manually free memory like in C/C++. You can request a GC cycle with System.gc() or Runtime.getRuntime().gc(), but this is only a hint to the JVM — it's free to ignore or delay it, so you cannot force garbage collection to happen at a specific moment.
What is a class loader, and what are the main types?
The class loader subsystem locates .class bytecode and loads it into the JVM's method area at runtime, following a parent-first delegation model: a request first goes up to the parent loader, and only if the parent can't find the class does the child attempt to load it itself — this prevents core classes like java.lang.String from being silently overridden.
Class loader delegation hierarchy — each loader asks its parent to load a class before trying itself, so core Java classes can never be shadowed by application code.
What are the common types of garbage collectors in Java, and how do they differ?
  • Serial GC — single-threaded, stop-the-world; fine for small heaps/single-core environments.
  • Parallel GC ("throughput collector") — multiple threads for minor/major GC, optimizes for overall throughput at the cost of longer individual pauses.
  • CMS (Concurrent Mark Sweep) — deprecated/removed in modern JDKs; did most marking concurrently with the application to reduce pause times, but suffered from fragmentation.
  • G1 (Garbage First) — default since JDK 9; divides the heap into regions and collects the regions with the most garbage first, balancing throughput and pause time predictably.
  • ZGC / Shenandoah — modern low-latency collectors targeting sub-millisecond pauses even on multi-terabyte heaps, by doing almost all work concurrently with the application.
What is the default heap size the JVM allocates, and how do you change it?
The default is JVM-implementation- and machine-dependent (HotSpot typically defaults initial heap to about 1/64 of physical RAM and max heap to about 1/4 of physical RAM, with platform-specific caps). You control it explicitly with -Xms<size> (initial heap) and -Xmx<size> (maximum heap), e.g. java -Xms512m -Xmx2g MyApp.
What are Weak, Soft, and Phantom references, and why do they matter?
All three let you reference an object without preventing garbage collection, unlike a normal ("strong") reference:
  • SoftReference — cleared only when the JVM is under memory pressure right before it would otherwise throw OutOfMemoryError. Good for memory-sensitive caches.
  • WeakReference — cleared at the very next GC cycle if no strong references exist. Used for metadata that shouldn't keep its key alive — this is exactly how WeakHashMap and the internals of ThreadLocal avoid memory leaks.
  • PhantomReference — the referent is already finalized; get() always returns null. Used with a ReferenceQueue to run cleanup logic after an object is gone but before its memory is reclaimed — the modern, safer replacement for finalize().
What is the difference between deep copy and shallow copy?
A shallow copy duplicates an object's top-level fields, but if a field holds a reference to another object (e.g. an array or nested object), the copy shares that same referenced object with the original — mutating it through one affects the other. A deep copy recursively duplicates every referenced object too, so the copy is fully independent. Java's default Object.clone() performs a shallow copy; a deep copy requires manually cloning nested fields (or using serialization-based cloning).
What is an immutable class, and how do you write one? What are the trade-offs?
An immutable class's state can never change after construction — String and the boxed primitive wrappers are the canonical examples. To write one: declare the class final (prevents subclassing from breaking invariants), make all fields private final, provide no setters, initialize everything through the constructor, and for mutable field types (arrays, dates, collections) return defensive copies rather than the internal reference.

Pros: inherently thread-safe with no synchronization needed, safe to share/cache freely, simpler to reason about. Cons: creating a new object for every "change" can add allocation/GC overhead for frequently-modified data (this is why StringBuilder exists alongside immutable String).
public final class Point {
    private final int x;
    private final int y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }
    public int getY() { return y; }
    // no setters — state can never change after construction
}
What are marker interfaces? How many are there, and why don't they have methods?
A marker interface has no methods or constants — it exists purely to "tag" a class with metadata that the JVM or a framework checks via instanceof at runtime (e.g. if (obj instanceof Serializable)). The classic built-in examples are Serializable, Cloneable, and Remote. They have no methods precisely because their only purpose is the tag itself — behavior is implemented elsewhere (e.g. reflection-driven serialization logic reads the tag, not a method on the interface). Since Java 5, annotations (e.g. a custom @Tag) are generally preferred over new marker interfaces for this purpose, since they support parameters and can be introspected more flexibly — but you can still define your own marker interface simply by declaring interface MyMarker {} with an empty body.
Is the main method compulsory in every Java program?
Today, yes — a public static void main(String[] args) entry point is required, or you'll get a runtime error ("main method not found"). This wasn't always true: prior to JDK 6, a class with no main method but a static initializer block would still execute that block and then throw the "no main method" error only after the block ran, which some older trivia questions exploit — but you cannot rely on this in any modern JDK.
Why do we need explicit Java memory management awareness if the JVM handles GC automatically?
Automatic GC removes manual free()/delete calls, but it doesn't remove memory problems — it changes their shape. Common real issues: unintentionally retaining references (e.g. static collections that grow forever, unclosed resources, listener registrations never removed) causing logical memory leaks GC can't fix because the objects are still technically reachable; oversized or undersized heap settings causing excessive GC pauses or OutOfMemoryError; and generational promotion patterns that matter for tuning latency-sensitive services. Understanding the heap/GC model above is what lets you diagnose and tune these issues.

Spring Framework

Spring and Spring Boot show up in nearly every backend Java interview — not to test whether you've memorized annotations, but whether you understand the container underneath them: how beans are created and wired, what a proxy actually does, and where the "magic" of auto-configuration comes from. The questions below move from core IoC/DI fundamentals through Boot, AOP, transactions, MVC, and security.

What is the Spring Framework, and what core problem does it solve?
Spring is a framework for building Java applications whose central problem to solve is tight coupling and manual object wiring. Without it, a class typically constructs its own dependencies with new, so swapping an implementation, unit-testing in isolation, or adding a cross-cutting concern (logging, transactions, security) means touching code throughout the application. Spring's answer is the IoC (Inversion of Control) container: a class simply declares what it needs (via its constructor, a setter, or a field) and the container — not the class itself — creates the objects ("beans"), wires their dependencies together, and manages their lifecycle. Spring MVC, Spring Data, Spring Security, and Spring Boot are all built on top of this same container.
What is the IoC container, and what's the difference between BeanFactory and ApplicationContext?
The IoC container is the runtime component that reads bean configuration (annotations, Java @Configuration classes, or XML), instantiates beans, injects their dependencies, and manages their life cycle from creation to destruction. Spring exposes this through two container interfaces:
  • BeanFactory — the basic container. Lightweight and lazy: singleton beans are only created the first time getBean() is called for them.
  • ApplicationContext — a superset almost every real application uses instead. It eagerly instantiates singletons at startup (so misconfiguration fails fast, at boot rather than mid-request), auto-registers BeanPostProcessor/BeanFactoryPostProcessor beans, publishes application events, supports internationalization, and integrates cleanly with AOP.
Spring Boot creates and configures an ApplicationContext (e.g. AnnotationConfigServletWebServerApplicationContext) for you automatically.

What is a Spring Bean, and what does its life cycle look like end to end?
A bean is simply an object that the IoC container instantiates, assembles, and manages — as opposed to an object your code creates and manages itself with new. For a singleton bean, the container walks through a well-defined sequence of steps every time the application starts:
  1. Instantiate — the constructor runs and a raw object is created.
  2. Populate properties — dependencies are injected (constructor args were already supplied at step 1; setter/field injection happens here).
  3. Aware callbacks — if the bean implements marker interfaces like BeanNameAware or ApplicationContextAware, Spring calls those setters so the bean can access its own name or the container itself.
  4. BeanPostProcessor.postProcessBeforeInitialization() — runs for every bean in the container, before init callbacks.
  5. Init callbacks — @PostConstruct runs first, then InitializingBean.afterPropertiesSet(), then any custom init-method. This is the classic interview trap: the three are not interchangeable, and @PostConstruct always fires before afterPropertiesSet().
  6. BeanPostProcessor.postProcessAfterInitialization() — also runs for every bean; this is the step where Spring AOP wraps a bean in a proxy if it matches an aspect's pointcut.
  7. Ready — the fully-initialized (and possibly proxied) bean is now handed out to the application.
  8. Destruction — on container shutdown, @PreDestroy runs first, then DisposableBean.destroy(), then any custom destroy-method. Destruction callbacks only fire for singleton-scoped beans — the container does not track prototype beans after handing them out.
A singleton bean's full life cycle — the container drives every step; the "Ready" and "Destruction" stages only apply to singleton-scoped beans.

How does @Autowired work, and how does Spring resolve ambiguous bean candidates?
Spring resolves @Autowired by type first. If exactly one bean of that type exists, it's injected.   • @Primary — marks one candidate bean as the default to use whenever there's ambiguity, without needing a qualifier at every injection point.

What is the difference between Spring Framework and Spring Boot?
Spring Framework is the underlying platform — the IoC container, AOP, transaction management, Spring MVC, and so on — but using it in a plain project meant assembling compatible dependency versions yourself and hand-writing a lot of boilerplate configuration (data sources, view resolvers, a servlet container deployment descriptor). Spring Boot is an opinionated layer on top of Spring Framework, not a replacement for it. It adds three things, following a "convention over configuration" philosophy:
  • Auto-configuration — inspects what's on the classpath and configures sensible defaults automatically (e.g. seeing Spring MVC + Jackson on the classpath wires up a DispatcherServlet and JSON message converters).
  • Starters — curated dependency bundles (e.g. spring-boot-starter-web) so you pull in one artifact instead of hand-picking a set of mutually compatible library versions.
  • Embedded servers & production-readiness — an embedded Tomcat/Jetty/Undertow means "just run the jar" instead of deploying a WAR to an external server, and Actuator exposes health/metrics endpoints out of the box.
You can still use every core Spring Framework concept (beans, DI, AOP, @Transactional) exactly as before — Boot just removes most of the setup ceremony around them.
What does @SpringBootApplication actually bundle?
@SpringBootApplication is a convenience meta-annotation equivalent to combining three annotations, each with its default settings:
  • @Configuration — marks the class itself as a source of bean definitions (it can contain @Bean methods).
  • @EnableAutoConfiguration — turns on Boot's auto-configuration mechanism, which conditionally registers beans based on what's on the classpath and what you've already defined.
  • @ComponentScan — tells Spring to scan the current package and all sub-packages for @Component-annotated classes, which is why the class hosting @SpringBootApplication conventionally sits at the root package of the application.

}
What problem does Spring AOP solve, and what do "aspect," "advice," "join point," "pointcut," and "weaving" mean?
Some concerns — logging, security checks, transaction demarcation, caching — cut across many unrelated classes rather than belonging to any one of them. Writing that logic directly inside every method that needs it duplicates code and tangles unrelated responsibilities together. AOP (Aspect-Oriented Programming) lets you define that logic once and have it applied automatically wherever it's needed, without modifying the target classes.
  • Aspect — the module encapsulating a cross-cutting concern (e.g. a LoggingAspect).
  • Advice — the action taken at a matched point: @Before, @After, @Around, @AfterReturning, @AfterThrowing.
  • Join point — a point during program execution where an aspect can be applied; in Spring AOP this is always a method execution.
  • Pointcut — an expression (using AspectJ pointcut syntax) that selects which join points a piece of advice applies to, e.g. execution(* com.example.service.*.*(..)).
  • Weaving — the process of linking aspects into the target objects. Spring AOP weaves at runtime via proxies (unlike full AspectJ, which can weave at compile time or class-load time) — which is also why Spring AOP only intercepts method calls made through the proxy, not internal calls within the same class.
The most common uses in real applications are declarative @Transactional boundaries, method-level security (@PreAuthorize), caching (@Cacheable), and custom logging/auditing aspects.
How does Spring actually implement AOP — JDK dynamic proxies vs. CGLIB?
Spring AOP wraps the target bean in a proxy object at container startup; callers interact with the proxy, which runs the applicable advice and then delegates to the real object. Which kind of proxy gets created depends on the target:

What does @Transactional do, and what do propagation and isolation control?
@Transactional is a declarative way to demarcate a transaction boundary around a method: Spring wraps the bean in a proxy (see above) that starts, commits, or rolls back a transaction around the method call, instead of you writing that boilerplate by hand.

Propagation controls how a transactional method behaves when it's called while another transaction is already in progress:
PropagationBehavior
REQUIRED (default)Join the existing transaction if one exists, otherwise start a new one
REQUIRES_NEWSuspend any existing transaction and start a new, independent one
NESTEDRun within a savepoint inside the existing transaction; a failure rolls back only to that savepoint

MANDATORYMust run within an existing transaction; throws an exception if none exists
NEVERMust run without a transaction; throws an exception if one exists
Isolation controls how much one transaction can see of another transaction's uncommitted changes:
  • READ_UNCOMMITTED — allows dirty reads, non-repeatable reads, and phantom reads (weakest, fastest).
  • READ_COMMITTED — prevents dirty reads; the common default (PostgreSQL, SQL Server, Oracle).
  • REPEATABLE_READ — also prevents non-repeatable reads; MySQL InnoDB's default.
  • SERIALIZABLE — prevents phantom reads too; strongest and slowest, effectively serializes transactions.
What's the classic @Transactional self-invocation pitfall?
Because @Transactional is implemented via a proxy, the transactional behavior only kicks in when the call comes through that proxy — i.e. when some other bean calls the method. If a method on the same bean calls another @Transactional method using this.otherMethod(), that call goes directly to the real object and completely bypasses the proxy, so no new transaction is started and no rollback rule is applied.
Watch for this
Two related traps show up constantly in interviews: (1) self-invocation silently skips the proxy, so an internal call to a @Transactional method behaves as if the annotation weren't there; and (2) the default rollback rule only triggers on unchecked exceptions (RuntimeException/Error) — if your method throws a checked exception, the transaction still commits unless you add rollbackFor = Exception.class. Spring AOP also simply cannot see private methods, so @Transactional on a private method is silently ignored. The fix for self-invocation is to move the inner call into a separate bean and inject it, so the call goes through the proxy.
Walk through the Spring MVC request life cycle.
Every incoming HTTP request in a Spring MVC (or Spring Boot web) application passes through a single front controller rather than being routed to servlets directly:
  1. The DispatcherServlet receives the request — it's registered to handle all matching URLs and is the single entry point into the framework.
  2. It consults the configured HandlerMapping(s) to find which controller and method should handle this URL/HTTP method combination.
  3. The request passes through any configured interceptors (HandlerInterceptor), then reaches the matched controller method, which executes business logic (often delegating to a service layer).
  4. The controller returns either a logical view name plus a model (traditional MVC), or, for @RestController/@ResponseBody, an object to be serialized directly.
  5. For traditional MVC, the DispatcherServlet asks the configured ViewResolver to turn the logical view name into an actual view (JSP, Thymeleaf template, etc.), which is then rendered with the model data. For REST responses, an HttpMessageConverter (e.g. Jackson) serializes the returned object straight to JSON/XML instead.
  6. The rendered view or serialized body becomes the HTTP response sent back to the client.
Spring MVC request flow — the DispatcherServlet is the single entry point; the last step diverges into either a rendered view (MVC) or a serialized JSON body (REST).
What's the difference between authentication and authorization, and how does Spring Security enforce them?
Authentication answers "who are you?" — verifying an identity, typically via a username/password, token, or certificate. Authorization answers "what are you allowed to do?" — deciding whether an already-authenticated identity can access a given resource or perform a given action. Spring Security enforces both through a chain of servlet filters (a SecurityFilterChain) that every request passes through before reaching your controllers:
  • An authentication filter (e.g. UsernamePasswordAuthenticationFilter) extracts credentials and hands them to the AuthenticationManager, which delegates to one or more AuthenticationProviders to actually validate them (often via a UserDetailsService that loads user data from a database).
  • On success, the resulting Authentication object is stored in the SecurityContextHolder for the duration of the request.
  • Later in the chain, an authorization filter consults the configured access rules (URL patterns, @PreAuthorize expressions, roles) to decide whether the now-known identity is allowed to proceed, throwing an access-denied error if not.
How does Spring handle circular dependencies between beans?
A circular dependency exists when bean A depends on bean B, and B depends back on A. Whether Spring can resolve this depends entirely on the injection style:
  • Constructor injection — Spring cannot resolve it. Both beans need a fully-constructed instance of the other before either constructor can even run, so Spring fails fast at startup with BeanCurrentlyInCreationException.
  • Setter/field injection — Spring can resolve it, using a three-level cache of in-progress singletons (early bean references created before their properties are fully populated, exposed via singleton factories). Bean A can be handed an early, not-yet-fully-initialized reference to B while B is still being built, and the reference gets completed once construction finishes.
This is one of the practical reasons some teams reach for @Lazy on one side of the cycle (deferring creation of one bean until it's first actually used) rather than switching to setter injection purely to dodge the exception — but the better answer in an interview, and in practice, is that a circular dependency is usually a sign the two classes should be redesigned or a piece of shared logic extracted into a third bean.

What are Spring Profiles, and how are they used for environment-specific configuration?

What are Spring Boot starters, and how does auto-configuration actually decide what to configure?
A starter (e.g. spring-boot-starter-web) is just a Maven/Gradle dependency descriptor that pulls in a curated, version-compatible bundle for a feature — spring-boot-starter-web brings in Spring MVC, an embedded Tomcat, and Jackson together, so you don't have to hand-pick compatible versions of each.

Auto-configuration is a set of @Configuration classes shipped inside Spring Boot, each guarded by @Conditional-family annotations — most commonly @ConditionalOnClass (only apply if a given class is on the classpath), @ConditionalOnMissingBean (only apply if you haven't already defined your own bean of that type), and @ConditionalOnProperty (only apply if a given property is set). At startup, Boot evaluates every candidate auto-configuration class's conditions against your classpath, existing beans, and properties, and only activates the ones that match — which is why adding spring-boot-starter-data-jpa to the classpath is often enough to get a working DataSource and JPA setup with zero configuration, while defining your own DataSource bean silently causes Boot's auto-configured one to back off.
What does Dependency Injection actually buy you when it comes to testing?
Because a class receives its dependencies from the outside (typically through its constructor) rather than constructing them itself, a unit test can pass in a mock or stub implementation without needing a Spring container at all — you just call new OrderService(mockPaymentClient, mockOrderRepository) and verify behavior with something like Mockito. This is the practical payoff of "program to an interface, not an implementation": swapping a real PaymentClient for a test double requires no change to OrderService itself, no static state to reset between tests, and no classpath scanning or application context startup slowing the test suite down.

Hibernate & JPA

Hibernate is the most widely used JPA implementation in enterprise Java, and interviewers use it to check whether you understand what the ORM is doing under the hood — not just which annotation to put on a field. Expect questions on the JPA/Hibernate relationship, the persistence context and caching model, fetch strategies, and the N+1 and locking problems that actually bite in production.

What is ORM, and what problem does Hibernate solve?
Object-Relational Mapping (ORM) is a technique for mapping Java objects to relational database tables (and vice versa) so developers work with objects instead of hand-written SQL and JDBC boilerplate. Hibernate is an ORM framework that sits between the application and the database: it generates SQL for CRUD operations, manages the object-to-row mapping via annotations/XML, tracks object state changes automatically (dirty checking), manages transactions, and provides caching — eliminating most of the repetitive ResultSet-to-object mapping code that raw JDBC requires.
What is the difference between JPA and Hibernate?
JPA (Jakarta/Java Persistence API) is just a specification — a set of interfaces and annotations (EntityManager, @Entity, @Id, JPQL, etc.) that define how ORM should behave in Java, with no implementation of its own. Hibernate is a concrete implementation of that specification (as are EclipseLink and OpenJPA), plus a large set of Hibernate-specific extras that go beyond the spec (its own Session API, additional annotations, HQL, extra caching options). Coding against the JPA interfaces keeps you portable across providers; coding against Hibernate's native API locks you into Hibernate but exposes more capability.
What is the difference between Session and EntityManager?
Session is Hibernate's native, pre-JPA API for persistence operations (org.hibernate.Session); EntityManager is the JPA-standard equivalent (jakarta.persistence.EntityManager). Both represent a single-threaded "unit of work" / persistence context bound to one conversation with the database, and internally a JPA EntityManager backed by Hibernate is largely a thin wrapper around a Session — you can even call entityManager.unwrap(Session.class) to drop down to the native API when you need a Hibernate-only feature. Default guidance: prefer EntityManager for portability, drop to Session only when you need something JPA doesn't expose.
What are the entity lifecycle states in Hibernate/JPA?
Every entity instance is in exactly one of four states at a given time:
  • Transient — a plain new object created with new, not associated with any session and not represented in the database.
  • Persistent (Managed) — associated with an open session/persistence context; Hibernate tracks changes to it and will flush them to the database automatically (dirty checking), no explicit save call needed for updates.
  • Detached — was persistent, but its session has since been closed (or it was explicitly evicted); the object still holds data but is no longer tracked, so changes are silently ignored until it's reattached via merge().
  • Removed — scheduled for deletion via remove()/delete(); still managed until the transaction commits, at which point the row is deleted and the instance becomes transient again.
An entity moves between transient, persistent (managed), detached, and removed states — only the persistent state is actively tracked by the session for automatic dirty-checking.
What do @Entity, @Table, @Id, and @GeneratedValue do?
@Entity marks a class as a persistent, mapped type. @Table optionally overrides the table name/schema it maps to (defaults to the class name). @Id marks the field that is the primary key. @GeneratedValue tells Hibernate how to generate that key automatically — common strategies are IDENTITY (DB auto-increment column), SEQUENCE (a database sequence object, generally the best-performing choice on Postgres/Oracle), TABLE (a dedicated key-generation table, portable but slow), and AUTO (Hibernate picks based on the dialect).
@Entity
@Table(name = "employees")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    private String name;
    // getters / setters
}

What is the difference between lazy and eager fetching? What causes LazyInitializationException?
Eager fetching (FetchType.EAGER) loads an association immediately, in the same query or a follow-up query, whenever the owning entity is loaded. Lazy fetching (FetchType.LAZY) defers loading the association until it's actually accessed, returning a proxy in the meantime. JPA defaults @ManyToOne/@OneToOne to eager and @OneToMany/@ManyToMany to lazy, but the strong convention in real codebases is to make everything lazy and fetch explicitly when needed.

LazyInitializationException happens when code tries to access a lazy association after the owning session has already closed — there's no active session left to run the follow-up query, so Hibernate can't populate the proxy. Classic cause: loading an entity in a service method, closing the session, then trying to access a lazy collection from that entity in the view/controller layer. Fixed by fetching what you need before the session closes (fetch joins, entity graphs) rather than widening the session's scope ("open session in view") as a blanket fix.
How do @OneToMany, @ManyToOne, and @ManyToMany map relationships, and what is the "owning side"?
These annotations map foreign-key relationships onto object references. In a bidirectional association, exactly one side is the owning side — the side Hibernate consults to know what to write to the foreign key column — and the other side is the inverse side, marked with mappedBy purely for convenience of navigation. For @OneToMany/@ManyToOne pairs, the @ManyToOne side is always the owning side because that's the side whose table physically holds the foreign key column; the @OneToMany side is the inverse side. A common bug: updating only the inverse side's collection (e.g. adding to department.getEmployees()) without also setting the owning side's reference (employee.setDepartment(dept)) — Hibernate ignores changes made only on the inverse side, so the foreign key never gets written. @ManyToMany uses a join table, and whichever side omits mappedBy is the owner of that join table.
@Entity
public class Department {
    @OneToMany(mappedBy = "department")
    private List<Employee> employees;   // inverse side — read-only for FK purposes
}

@Entity
public class Employee {
    @ManyToOne
    @JoinColumn(name = "department_id")
    private Department department;      // owning side — holds the FK column
}
What is the N+1 select problem, and how do you fix it?
It happens when Hibernate runs one query to fetch a list of N parent entities, then triggers N additional queries — one per row — to lazily load each parent's association, for N+1 total queries where a single well-joined query would do. For example, loading 100 orders where each order's customer is fetched lazily results in 1 query for the orders plus 100 more for the customers.

What is the difference between optimistic and pessimistic locking? How does @Version work?
Optimistic locking assumes conflicts are rare: no database locks are held while reading, and each entity carries a @Version column (or timestamp) that Hibernate increments on every update. On write, Hibernate includes WHERE version = ? in the UPDATE; if another transaction already changed the row (and bumped the version), zero rows match and Hibernate throws OptimisticLockException — the losing transaction retries or fails. Pessimistic locking assumes conflicts are likely: it acquires a database-level row lock (SELECT ... FOR UPDATE, via LockModeType.PESSIMISTIC_WRITE) at read time, blocking other transactions from reading/writing that row until the lock is released. Optimistic locking scales better under low contention; pessimistic locking is safer when contention and retry cost are both high.
@Entity
public class Account {
    @Id
    private Long id;

    @Version
    private int version;      // Hibernate manages this automatically

    private BigDecimal balance;
}
What are cascade types, and why are they dangerous if overused?
Cascading propagates an operation performed on a parent entity to its associated child entities automatically — e.g. CascadeType.PERSIST saves children when the parent is saved, CascadeType.MERGE propagates merges, and CascadeType.REMOVE deletes children when the parent is deleted. CascadeType.ALL applies every cascade type at once. The danger: reaching for CascadeType.ALL on every association is a common anti-pattern — accidentally deleting a parent can silently cascade-delete children that should have been kept (e.g. cascading remove from an Order to a shared Product reference), so cascades should be scoped deliberately to relationships where the child's lifecycle is genuinely owned by the parent (e.g. Order → OrderLineItem), not applied blanket-wide.
What's the difference between Session and SessionFactory — which is thread-safe?
SessionFactory is a heavyweight, expensive-to-create object built once per application (or per database) at startup from the configuration; it is thread-safe and shared across the whole application to produce Session instances. A Session is a lightweight, non-thread-safe object representing a single unit of work / conversation with the database — it should be opened, used by one thread for one logical operation, and closed, never shared across threads or held open for the lifetime of the application.
What are the JPA inheritance mapping strategies?
JPA supports three strategies for mapping a class hierarchy to tables, chosen with @Inheritance(strategy = ...):
  • SINGLE_TABLE — one table for the whole hierarchy, with a discriminator column identifying the subtype. Fastest (no joins), but subclass-specific columns must be nullable, which can leave a wide, sparse table.
  • JOINED — a table per class, linked to the parent table by a shared primary key/foreign key; normalized and space-efficient, but reads require joins across the hierarchy.
  • TABLE_PER_CLASS — a complete, independent table per concrete subclass, with no shared parent table; avoids joins but requires UNION queries for polymorphic queries across the hierarchy and duplicates common columns.

Servlets & JSP

Servlets and JSP predate Spring MVC but remain the plumbing everything else in Java web development runs on — a Spring @Controller method is, underneath, dispatched through a servlet. These questions probe lifecycle, scope, and the forward/redirect distinction to check you understand the request/response model, not just the annotations layered on top of it.

What is a servlet, and what is the servlet lifecycle?
A servlet is a Java class that handles HTTP requests and generates responses inside a servlet container (Tomcat, Jetty, etc.), implementing the jakarta.servlet.Servlet interface (typically by extending HttpServlet). Its lifecycle has three phases, all managed by the container:
  • init() — called exactly once, right after the servlet class is loaded and instantiated, before it serves any requests. Used for one-time setup (e.g. opening a resource, reading init params).
  • service() — called once per incoming request, and internally dispatches to doGet(), doPost(), etc. based on the HTTP method.
  • destroy() — called exactly once, when the container is shutting down or unloading the servlet (redeploy, undeploy), for cleanup.
The container loads and instantiates the servlet once, calls init() once, then reuses that same instance for service() on every subsequent request — dispatched to doGet()/doPost() — until destroy() is called once at unload.
What is the role of the servlet container, and how does it handle concurrent requests to the same servlet?
The servlet container (e.g. Tomcat, Jetty) manages the entire servlet lifecycle: loading the class, instantiating it, calling init()/destroy(), routing incoming HTTP requests to the right servlet, managing the request/response object pool, and multithreading. Critically, the container creates a single instance of each servlet (by default) and handles concurrent requests by running service() for each request on a separate thread from a thread pool — all threads execute against the same shared servlet instance. This is why instance state in a servlet is a thread-safety hazard (see below).

What is JSP, and how does it differ from a servlet?
JSP (JavaServer Pages) lets you embed Java code and expressions directly inside HTML-like markup, as an alternative to writing raw HTML output via PrintWriter inside a servlet. Under the hood, a JSP is not a different technology — the container translates each JSP page into a servlet source file, compiles it, and executes it exactly like a hand-written servlet. The practical difference is authoring style: servlets are Java-centric (you write HTML inside Java), while JSP is markup-centric (you embed Java inside HTML) — which is why JSP is traditionally used for the view layer and servlets for control logic.
What is the JSP lifecycle?
  • Translation — the container parses the .jsp file and generates the equivalent servlet's Java source.
  • Compilation — that generated source is compiled into a .class file.
  • Class loading & instantiation — the container loads the class and creates an instance, same as any servlet.
  • jspInit() — called once, analogous to a servlet's init().
  • _jspService() — called once per request to render the response; this is the generated method, you never write it yourself.
  • jspDestroy() — called once when the page is unloaded, analogous to destroy().
Translation and compilation only happen once (on first request, or when the source changes) — every subsequent request reuses the already-compiled servlet, which is why the very first hit to a JSP page is noticeably slower.
What are the session tracking mechanisms available in servlets?
HTTP is stateless, so the container needs a way to correlate multiple requests from the same client:
  • Cookies — the container sets a JSESSIONID cookie on the first response; the browser automatically sends it back on every subsequent request. The default, most common mechanism.
  • URL rewriting — the session id is appended to every URL as a path parameter (e.g. ;jsessionid=...) — the fallback used automatically when the client has cookies disabled.
  • Hidden form fields — the session id is embedded in a hidden <input> in every form, resubmitted on each POST; only works for form-driven navigation.
  • HttpSession — the actual server-side API (request.getSession()) applications use to store/retrieve per-user data; it's built on top of whichever of the above mechanisms is actually carrying the id.
What is a Filter, and how does it differ from a Servlet?
A Filter intercepts requests and responses around a servlet, letting you implement cross-cutting concerns — logging, authentication, compression, input validation, character encoding — in one place instead of duplicating them across every servlet. Filters are chained: each filter's doFilter() can inspect/modify the request, call chain.doFilter() to pass control to the next filter (or the target servlet), and then inspect/modify the response on the way back out. Unlike a servlet, a filter doesn't generate a response itself (usually) — it wraps the processing that a servlet or another filter does, and multiple filters can be composed in a chain around the same servlet.

Why are servlets not thread-safe by default? How do you make servlet code thread-safe?
The container creates one servlet instance and reuses it across every concurrent request, running each request's service() call on its own thread. Because all those threads execute against the same instance, any instance (non-final field) variable is shared mutable state — one request can read a half-updated value written by another request running concurrently, producing subtle, hard-to-reproduce bugs. To keep servlets thread-safe: avoid instance variables for per-request/mutable data entirely, use only local variables inside doGet()/doPost() (each thread gets its own call stack), favor immutable objects for anything shared, and synchronize explicitly around any genuinely shared mutable resource (e.g. a counter or cache) rather than relying on instance fields as scratch space. The old SingleThreadModel interface (deprecated, then removed) attempted to solve this by giving each request its own servlet instance/pool, but it never protected shared session or static state, so it's a dead end, not a real fix.
What is the difference between ServletConfig and ServletContext?
ServletConfig holds initialization parameters scoped to one specific servlet, configured per-servlet in the deployment descriptor (or @WebServlet annotation) and accessed via getServletConfig(). ServletContext is scoped to the entire web application — one instance shared by every servlet, filter, and JSP in that app — used for application-wide init parameters, storing/sharing global attributes, and dispatching requests to other resources (getRequestDispatcher()). Rule of thumb: ServletConfig is "just for me," ServletContext is "for everyone in this app."
What are JSP implicit objects?
Implicit objects are variables the JSP container makes automatically available inside every JSP page, without the developer declaring them — the generated servlet's _jspService() creates them for you. The main ones: request (HttpServletRequest), response (HttpServletResponse), session (HttpSession), application (ServletContext), out (the JspWriter used to write output), config (ServletConfig), pageContext (access to all the page's scopes and objects), page (the current servlet instance, i.e. this), and exception (available only on designated error pages).
