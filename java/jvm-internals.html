JVM Internals & Memory Management

Overview

JVM internals questions test whether you understand what actually happens between compiling a .java file and running it — where objects live in memory, how classes get loaded, and how garbage is collected without you ever calling free(). You don't need to have implemented a GC, but you should be able to reason about heap layout, generational collection, and the practical impact of common JVM flags.

Heap Layout (Generational Hypothesis)

Heap
+-------------------------------------------+-------------------+
|                Young Generation           |   Old Generation   |
|  +----------+  +----------+  +---------+  |                     |
|  |   Eden   |  |Survivor 0|  |Survivor1|  |   (tenured objects) |
|  +----------+  +----------+  +---------+  |                     |
+-------------------------------------------+-------------------+
                                              Metaspace (native memory,
                                              class metadata — not on heap)

New objects are allocated in Eden. A minor GC copies surviving objects between the two Survivor spaces, aging them each cycle; once an object survives enough minor GCs (the tenuring threshold), it's promoted ("tenured") into the Old Generation. Old-gen collections (major/full GCs) run far less often but cost much more per collection since the region is larger and typically requires compaction.

Generational hypothesis Most objects die young → minor GC (Eden + Survivor) is frequent and cheap, touching only a small, mostly-garbage region.
Few objects survive long → major/full GC (Old Gen) is rare but expensive, often causing longer "stop-the-world" pauses.
Design implication: keep short-lived objects small and scoped so they never leave Eden; long-lived caches belong in Old Gen by design, not by accident.

Class Loading

Classes are loaded lazily, on first active use, by a hierarchy of class loaders following the delegation model: each loader asks its parent to load a class before attempting to load it itself, so classes are only loaded by the most specific loader if no ancestor can find them.

  • Bootstrap ClassLoader — loads core JDK classes (java.lang.*, etc.) from the runtime library; written in native code, has no parent.
  • Extension/Platform ClassLoader — loads classes from the extensions/platform module path.
  • Application (System) ClassLoader — loads classes from the application classpath; the default loader for your own code.

Each loaded class goes through three phases: loading (reading bytecode into a binary form), linking (verification of bytecode correctness, preparation of static fields with default values, and optional resolution of symbolic references), and initialization (running static initializers and assigning declared static field values).

Why delegation matters
The parent-first delegation model prevents a malicious or accidental redefinition of a core class like java.lang.String from your own classpath — the bootstrap loader always gets first crack at loading it, so your version is never used.

Garbage Collection Algorithms (Conceptual)

CollectorApproachBest for
SerialSingle-threaded, stop-the-world for both minor and major GCSmall heaps, single-core environments, simple apps
Parallel (Throughput)Multiple threads collect in parallel, still stop-the-worldBatch jobs prioritizing overall throughput over pause time
G1 (Garbage First)Divides the heap into equal-sized regions; concurrently collects the regions with the most garbage first, targeting a configurable pause-time goalLarge heaps needing a balance of throughput and predictable pauses (default since Java 9)
ZGCFully concurrent, uses colored pointers and load barriers to do marking/relocation work without stopping application threads; pause times stay in the low single-digit milliseconds regardless of heap sizeVery large heaps (multi-GB to TB) with strict low-latency requirements

-Xms / -Xmx Tuning Basics

-Xms sets the initial heap size and -Xmx sets the maximum heap size. Setting them equal (-Xms4g -Xmx4g) avoids the overhead of the JVM repeatedly resizing the heap at runtime, which is common practice for latency-sensitive services. Undersizing -Xmx causes frequent, expensive full GCs (or OutOfMemoryError); oversizing it wastes memory and can increase individual GC pause times (more live data to trace/compact). Related flags: -XX:NewRatio (old:young size ratio) and -XX:MaxGCPauseMillis (a target hint for G1/ZGC, not a hard guarantee).

Common Interview Questions

Why was PermGen replaced with Metaspace in Java 8?
PermGen had a fixed maximum size configured at JVM startup (-XX:MaxPermSize) and commonly caused OutOfMemoryError: PermGen space in applications that loaded many classes dynamically (e.g. app servers with frequent redeploys). Metaspace allocates class metadata from native memory instead, growing automatically (bounded only by available system memory or -XX:MaxMetaspaceSize if set), which eliminated that whole class of failure.
What's the practical difference between a minor GC and a major/full GC?
A minor GC collects only the Young Generation (Eden + Survivor spaces) and is fast because most young objects are already garbage. A major/full GC collects the Old Generation (and often the whole heap plus Metaspace), is far more expensive, and typically causes longer stop-the-world pauses since it deals with more live data and may need to compact memory.
How does G1 GC decide which regions to collect first?
G1 divides the heap into many equal-sized regions rather than one contiguous Young/Old space. It tracks how much garbage each region holds and, to hit a configured pause-time target, prioritizes collecting the regions with the most reclaimable garbage first — hence "Garbage First."
Your service has frequent long GC pauses. What would you check first?
First check the GC logs to see which collector is running and whether pauses correlate with major/full GCs (Old Gen) or Metaspace growth. Common fixes: increase heap size if it's undersized and thrashing, switch to a low-pause collector like G1 or ZGC if using Serial/Parallel, check for memory leaks (Old Gen growing without bound), and verify object lifetimes aren't unnecessarily promoting short-lived objects out of Eden.
Why does setting -Xms equal to -Xmx help latency-sensitive applications?
If the initial heap is smaller than the max, the JVM must periodically pause to expand the heap as demand grows, which adds unpredictable latency. Fixing both to the same value pre-allocates the full heap up front, trading a larger initial memory footprint for consistent, predictable performance.

Key Takeaways

Remember
Most objects die young — that's the whole justification for generational GC and why minor GCs are cheap. Class loading follows parent-first delegation for security and consistency. Pick a collector based on your latency/throughput needs: Parallel for batch throughput, G1 for balanced general-purpose use, ZGC for very large heaps with strict pause-time requirements.
