Java 8+ Features (Streams & Lambdas)

Overview

Java 8 was the language's biggest shift toward functional-style programming: lambdas, functional interfaces, the Stream API, and Optional changed how idiomatic Java code looks. Interviewers use this topic to see whether you reach for declarative, stream-based transformations naturally, and whether you understand the functional interface machinery underneath the lambda syntax.

Lambdas & Functional Interfaces

A functional interface is any interface with exactly one abstract method (it may also have default and static methods). A lambda expression is a compact, anonymous implementation of that single method, and the compiler infers which functional interface it satisfies from the assignment context.

InterfaceAbstract methodTypical use
Function<T,R>R apply(T t)Transform a value of type T into type R
Predicate<T>boolean test(T t)Filtering / boolean checks
Consumer<T>void accept(T t)Side-effecting operations (e.g. printing)
Supplier<T>T get()Lazily produce/supply a value
Predicate<String> isBlank = s -> s.trim().isEmpty();
Function<String, Integer> length = String::length; // method reference
Supplier<List<String>> newList = ArrayList::new;

Method References

A method reference is shorthand for a lambda that does nothing but call an existing method. There are four flavors:

  • ClassName::staticMethod — e.g. Integer::parseInt
  • instance::instanceMethod — e.g. System.out::println
  • ClassName::instanceMethod — e.g. String::toUpperCase (the receiver becomes the first lambda parameter)
  • ClassName::new — a constructor reference, e.g. ArrayList::new

Default Methods on Interfaces

Java 8 allowed interfaces to declare methods with a body via default, so new methods could be added to existing interfaces (like List.sort() or Map.getOrDefault()) without breaking every class that already implemented them. If a class implements two interfaces with the same default method signature, it must override the method itself to resolve the ambiguity — the compiler will not pick one arbitrarily.

The Stream API

A Stream represents a pipeline of lazy, possibly-parallel operations over a source of elements. Streams are built from intermediate operations (lazy, return a new stream — map, filter, sorted, distinct) followed by exactly one terminal operation (eager, triggers execution and produces a result or side effect — collect, reduce, forEach, count). Nothing runs until a terminal operation is invoked, which lets the JVM fuse the whole pipeline into a single pass over the data.

record Employee(String name, String department, double salary) {}

List<Employee> employees = List.of(
    new Employee("Ana", "Engineering", 95000),
    new Employee("Ben", "Sales", 72000),
    new Employee("Cy",  "Engineering", 110000),
    new Employee("Dee", "Sales", 68000)
);

// map/filter/reduce: total salary of Engineering employees earning > 90k
double total = employees.stream()
    .filter(e -> e.department().equals("Engineering"))
    .filter(e -> e.salary() > 90000)
    .mapToDouble(Employee::salary)
    .sum();

// collect: group employees by department, then compute average salary per group
Map<String, Double> avgSalaryByDept = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::department,
        Collectors.averagingDouble(Employee::salary)
    ));
// {Engineering=102500.0, Sales=70000.0}

Optional

Optional<T> is a container that may or may not hold a non-null value, designed to make the possible absence of a value explicit in a method's return type instead of relying on callers to remember a null check. It's intended primarily as a return type for methods where "no result" is a valid outcome — not as a general-purpose replacement for null in fields or method parameters.

Optional<Employee> found = employees.stream()
    .filter(e -> e.name().equals("Ana"))
    .findFirst();

String label = found
    .map(Employee::name)
    .orElse("Unknown");           // avoids explicit null-check branching

found.ifPresentOrElse(
    e -> System.out.println("Found: " + e.name()),
    () -> System.out.println("Not found")
);
Avoid this anti-pattern
Don't call optional.isPresent() followed by optional.get() — that's just a verbose null check. Prefer map/filter/orElse/orElseGet/ifPresent to stay in a functional style, and never use Optional as a field type or method parameter — it adds serialization overhead and boxing with no real benefit there.
Stream pipeline complexity A stream over n elements with k intermediate operations (map/filter/etc.) runs in O(n × k) time, but because Streams are lazily evaluated in a single pass per element, no intermediate collections are materialized — memory stays O(1) beyond the source and result, unlike chaining k separate loops that each allocate a new list.

Common Interview Questions

What makes an interface a "functional interface," and what enforces that?
It must declare exactly one abstract method (it can still have any number of default/static methods, and it may redeclare Object methods like equals without counting toward the limit). The @FunctionalInterface annotation isn't required for a lambda to work, but it makes the compiler enforce the single-abstract-method rule and documents intent.
Why are stream intermediate operations lazy?
Laziness lets the stream pipeline be fused into a single pass and lets terminal operations short-circuit — e.g. findFirst() can stop after processing just enough elements instead of transforming the entire source. If intermediate operations executed eagerly, every map/filter would materialize a full intermediate list, defeating that optimization.
Can a stream be reused after a terminal operation runs?
No — a stream can only be consumed once. Calling a second terminal operation (or trying to add more intermediate operations) on an already-consumed stream throws IllegalStateException. To iterate the same data again, you must build a new stream from the original source.
What's the difference between map and flatMap?
map transforms each element into exactly one other element (a 1:1 mapping), which can result in a stream of streams if the mapping function itself returns a stream. flatMap transforms each element into a stream and then flattens all of those streams into a single stream — useful for cases like turning a List<List<String>> into a flat Stream<String>.
When should you avoid using Optional?
Avoid it as a class field type (it isn't Serializable and adds an unnecessary wrapper allocation), as a method parameter type (overloading or a null check is clearer), and inside performance-critical hot loops where the extra boxing/allocation overhead matters. It's best reserved for method return types where "absent" is a legitimate, expected outcome.

Key Takeaways

Remember
Lambdas are shorthand for implementing a single-method functional interface; streams are lazy pipelines of intermediate operations capped by one terminal operation; Optional makes "no result" explicit in return types but isn't a general null replacement. Together they push Java code toward a more declarative, less imperative style.
