OOP & Core Fundamentals

Overview

Object-oriented programming is the backbone of Java's design, and nearly every Java interview opens with it. Interviewers are rarely looking for textbook definitions — they want to see that you understand why each pillar exists, can produce a concrete example on demand, and can reason about the trade-offs between composition and inheritance, or overloading and overriding, in real design decisions.

The Four Pillars of OOP

1. Encapsulation

Encapsulation bundles data and the methods that operate on it into a single unit (a class), and restricts direct access to internal state via access modifiers (private, protected, public). The class exposes a controlled API (getters/setters, validated mutators) instead of letting callers reach into its fields directly.

public class BankAccount {
    private double balance; // hidden internal state

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        balance += amount;
    }

    public double getBalance() {
        return balance; // read-only view, no direct field access
    }
}

2. Inheritance

Inheritance lets a subclass acquire the fields and methods of a superclass via extends, modeling an "is-a" relationship and enabling code reuse. Java supports single inheritance of classes (multiple inheritance of type is achieved through interfaces).

public class Vehicle {
    protected int speed;
    public void accelerate() { speed += 10; }
}

public class Car extends Vehicle {
    public void honk() { System.out.println("Beep!"); }
}

3. Polymorphism

Polymorphism allows objects of different types to be treated through a common interface, with the actual method invoked determined at runtime (dynamic dispatch) based on the object's real type. This is runtime polymorphism; overloading (below) provides compile-time polymorphism.

Vehicle v = new Car(); // reference type Vehicle, actual type Car
v.accelerate();         // resolved at runtime via the vtable to Car's behavior if overridden

4. Abstraction

Abstraction hides implementation detail and exposes only the essential behavior, typically via interfaces or abstract classes. Callers depend on what an object can do, not how it does it.

public interface PaymentProcessor {
    void process(double amount);
}

public class CreditCardProcessor implements PaymentProcessor {
    public void process(double amount) {
        // card-specific logic hidden from callers
    }
}

equals(), hashCode(), and toString() Contracts

These three Object methods have well-defined contracts that, if broken, cause subtle bugs in collections and logging:

  • equals() must be reflexive (x.equals(x)), symmetric (x.equals(y) == y.equals(x)), transitive, consistent, and x.equals(null) must return false.
  • hashCode() contract: equal objects must produce equal hash codes. The reverse is not required — unequal objects may share a hash code (a collision), which hash-based collections must tolerate.
  • toString() has no strict correctness contract but should return a concise, human-readable representation useful for logging and debugging; overriding it is considered good practice for any domain object.
Common pitfall
Overriding equals() without overriding hashCode() (or vice versa) breaks the contract silently — objects that are "equal" can end up in different HashMap buckets, making lookups fail. Modern IDEs and record types (Java 16+) generate both together to avoid this class of bug entirely.

Composition vs. Inheritance

Inheritance couples a subclass tightly to its superclass's implementation — changes to the parent can silently break children (the "fragile base class" problem), and Java's single-inheritance model means one extends slot is easy to burn on the wrong hierarchy. Composition instead builds behavior by holding a reference to another object and delegating to it, which keeps classes independently testable and swappable.

// Composition: Car "has-a" Engine, not "is-a" Engine
public class Car {
    private final Engine engine;

    public Car(Engine engine) { this.engine = engine; }

    public void start() {
        engine.ignite(); // delegate, don't inherit
    }
}
When to favor composition over inheritance
Favor composition when the relationship is "has-a"/"uses-a" rather than a true "is-a", when the subclass would only reuse a fraction of the parent's API, when the parent class isn't designed/documented for extension, or when you need to swap behavior at runtime. Reach for inheritance only for genuine type hierarchies where Liskov substitution holds — a subclass instance must be usable anywhere the superclass is expected without surprising callers.
Dispatch cost Virtual (polymorphic) method dispatch: O(1) — one indirection through the object's method table (vtable) to find the overriding implementation.
Overload resolution, by contrast, happens at compile time based on static argument types — it adds zero runtime cost but is resolved once, not per-call.

Common Interview Questions

Why does Java not support multiple inheritance of classes, and how do interfaces fill that gap?
Multiple inheritance of state causes the "diamond problem" — ambiguity when two parent classes define the same field or conflicting method implementations. Java sidesteps this by allowing a class to implement multiple interfaces (which historically carried no state) while extending only one class. Since Java 8, interfaces can carry default method bodies, but conflicts between two inherited defaults must be resolved explicitly by the implementing class, avoiding silent ambiguity.
Can you overload a method by changing only its return type?
No. Overload resolution is based on the method signature (name + parameter types), not the return type. Two methods with identical parameter lists but different return types will fail to compile as a duplicate method definition.
What is the difference between static (compile-time) and dynamic (runtime) polymorphism in Java?
Static polymorphism is resolved by the compiler based on the reference type and argument types at compile time — this is method overloading. Dynamic polymorphism is resolved by the JVM at runtime based on the object's actual type via virtual method dispatch — this is method overriding. Only instance methods participate in dynamic dispatch; static, private, and final methods are resolved statically.
If two objects have the same hashCode(), are they guaranteed to be equals()?
No. A shared hash code is a necessary but not sufficient condition for equality — it's a hash collision. HashMap/HashSet handle this by storing colliding entries in the same bucket and falling back to equals() to distinguish between them.
Give a practical example of preferring composition over inheritance.
Modeling a Stack by extending Vector (as the legacy JDK does) exposes the entire Vector API — including insertElementAt — breaking stack semantics. A composition-based design would wrap a Deque internally and expose only push/pop/peek, giving full control over the public contract.

Key Takeaways

Remember
Encapsulation, inheritance, polymorphism, and abstraction each solve a distinct design problem — don't conflate them. Prefer interfaces for capabilities and composition for code reuse; reserve class inheritance for genuine "is-a" hierarchies that satisfy Liskov substitution. Always pair equals() with hashCode().
