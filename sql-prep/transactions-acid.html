Transactions & ACID

Overview

Transaction questions test whether you understand the guarantees a database actually makes when things go wrong — a crash mid-write, two clients touching the same row at once, a query reading data another transaction hasn't committed yet. You should be able to define ACID precisely, map each SQL isolation level to the anomaly it prevents (and the one it still allows), and reason about optimistic vs. pessimistic locking trade-offs.

ACID Explained

  • Atomicity — a transaction's statements succeed or fail as a single indivisible unit; if any part fails, the entire transaction rolls back and the database is left as if it never started (e.g. a funds transfer either debits and credits both accounts, or does neither).
  • Consistency — a transaction moves the database from one valid state to another, never violating declared constraints (foreign keys, unique constraints, check constraints) or invariants, even if it fails partway (atomicity's rollback restores validity).
  • Isolation — concurrent transactions appear to execute as if run one at a time, to a degree controlled by the chosen isolation level; stronger isolation prevents more classes of interference between transactions at the cost of concurrency/throughput.
  • Durability — once a transaction commits, its changes survive any subsequent crash, power loss, or restart — typically guaranteed via a write-ahead log flushed to durable storage before the commit is acknowledged.

*Some engines (e.g. MySQL InnoDB's Repeatable Read via multi-version concurrency control) prevent phantom reads in practice for most query patterns, going beyond the strict SQL standard definition — always verify against your specific database's documentation rather than assuming the standard's minimum guarantee.

  • Dirty read — reading a row that another transaction has modified but not yet committed; if that transaction rolls back, you "read" data that never really existed.
  • Non-repeatable read — re-reading the same row twice within one transaction and getting different values, because another transaction committed an update to it in between.
  • Phantom read — re-running the same range query twice within one transaction and getting a different set of rows (new rows appeared or disappeared), because another transaction inserted/deleted rows matching the condition in between.
Trade-off
Stronger isolation levels prevent more anomalies but reduce concurrency — Serializable often requires range locks or aborts/retries under contention, hurting throughput. Read Committed is the default in most production databases (e.g. PostgreSQL, Oracle, SQL Server) because it's a reasonable balance for most applications; reach for stricter levels only when the anomaly it prevents would cause a real business-logic bug.

Deadlocks in Database Transactions

A database deadlock occurs when two transactions each hold a lock the other needs — e.g. Transaction A locks row 1 then requests a lock on row 2, while Transaction B locks row 2 then requests a lock on row 1. Most database engines run a background deadlock detector that finds this cycle and forcibly aborts one transaction (rolling it back and returning a deadlock error) so the other can proceed. Application code should catch this error and retry the aborted transaction. Prevention strategies mirror those for in-memory deadlocks: always acquire locks on multiple rows in a consistent order (e.g. always by ascending primary key), keep transactions short, and avoid interactive/user-input steps in the middle of an open transaction.

Worked example — isolation vs. throughput effective_throughput ≈ base_throughput / (1 + contention_factor)
e.g. moving from Read Committed to Serializable on a hot table can push the contention_factor from ≈0.1 to ≈0.8, dropping effective throughput from ≈909 tx/sec toward ≈556 tx/sec (base 1,000 tx/sec) as more transactions block or retry on conflicts.
Stricter isolation buys correctness guarantees at a real, measurable throughput cost — pick the loosest level that still prevents the anomalies you can't tolerate.

Common Interview Questions

What's the difference between a dirty read and a non-repeatable read?
A dirty read sees uncommitted data from another transaction — data that might not even end up existing if that transaction rolls back. A non-repeatable read sees data that another transaction has already committed, but between your own transaction's two reads of the same row, causing the value to change out from under you even though every read you performed was of committed data.
Why does Serializable isolation reduce throughput compared to Read Committed?
Serializable must guarantee that concurrent transactions produce a result equivalent to some serial (one-at-a-time) execution, which typically requires broader locking (including range/gap locks to prevent phantoms) or optimistic conflict detection with transaction aborts. Both approaches increase blocking, retries, or lock contention compared to Read Committed, which only needs to hide uncommitted data.
When would you choose optimistic locking over pessimistic locking?
When conflicting writes to the same row are rare — e.g. a user editing their own profile, where two people editing the same profile simultaneously is unlikely. Optimistic locking avoids the overhead and contention of acquiring locks up front and only pays a cost (a rejected commit and retry) in the rare case of an actual conflict. Pessimistic locking is better when conflicts are common enough that retries would be frequent and wasteful, such as a highly contended inventory counter.
How does a database typically resolve a detected deadlock?
A background deadlock detector periodically (or continuously) looks for a cycle in the "waits-for" graph of transactions blocked on each other's locks. When found, it picks a victim (often the transaction that has done the least work, or the one holding the fewest locks) and aborts it with a deadlock error, releasing its locks so the remaining transaction(s) can proceed. The aborted transaction's changes are rolled back and the application is expected to retry it.
Does Atomicity guarantee Consistency, or are they independent guarantees?
They're related but distinct. Atomicity guarantees that a transaction's effects are all-or-nothing; Consistency guarantees that any state the database reaches (including after a rollback) satisfies its declared constraints and invariants. Atomicity is one of the mechanisms that helps achieve consistency (a failed transaction can't leave partial, invalid changes behind), but consistency also depends on the constraints themselves being correctly defined — atomicity alone can't stop a fully-committed transaction from violating a business rule that was never encoded as a database constraint.

Key Takeaways

Remember
ACID = Atomicity, Consistency, Isolation, Durability. Each isolation level trades concurrency for protection against a specific anomaly — Read Uncommitted prevents nothing, Serializable prevents everything (dirty reads, non-repeatable reads, phantom reads) at the highest concurrency cost. Use pessimistic locking under high contention, optimistic locking under low contention, and always design a consistent lock-acquisition order to avoid deadlocks.
