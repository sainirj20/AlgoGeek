Indexing & Query Optimization

Overview

Indexing questions separate candidates who've only written queries from candidates who've had to make a slow one fast. You should be able to explain what a B-tree index actually looks like on disk, why some predicates can't use an index at all, how to read an EXPLAIN plan at a conceptual level, and why column order in a composite index isn't arbitrary.

B-Tree Index Structure

The default index type in almost every relational database is a balanced B-tree (or B+tree). Internal nodes hold only routing keys used to navigate; the actual indexed key values and pointers to the corresponding table rows (or, for a clustered index, the row data itself) live in the leaf nodes, which are linked together to support efficient range scans. Because the tree is balanced, every lookup traverses the same number of levels regardless of which key you search for, and that depth grows only logarithmically as the table grows.

                [ 50 ]
              /        \
         [ 20 ]        [ 80 ]
        /     \        /     \
     [10]   [30,40]  [60,70] [90,99]   <- leaf nodes, linked left-to-right
       |       |        |       |
     row ptrs (or row data, if clustered)
Lookup complexity B-tree index lookup: O(log n) — tree depth grows logarithmically with row count
Full table scan (no usable index): O(n) — every row must be read and evaluated
Example: 1,000,000 rows → indexed lookup touches roughly log₂(1,000,000) ≈ 20 levels/comparisons vs. up to 1,000,000 row reads for a full scan

Composite Index Column Order

A composite (multi-column) index is only efficiently searchable as a left-to-right prefix — like a phone book sorted by (last name, first name): you can jump straight to "Smith, John," but you can't efficiently find everyone named "John" regardless of last name without scanning. An index on (a, b, c) can serve queries filtering on a, or a AND b, or a AND b AND c efficiently, but generally cannot be used efficiently to filter on b alone or c alone. Put the column with an equality filter and/or highest selectivity first, and match the column order to your most common query patterns — or to the ORDER BY clause if you want the index to also avoid a separate sort step.

When a Query Can't Use an Index

  • Leading wildcard LIKE — LIKE '%smith' can't use a standard B-tree index because the tree is sorted by the string's leading characters, which are unknown; LIKE 'smith%' (no leading wildcard) can still use it as a prefix range scan.
  • Functions/expressions on an indexed column — WHERE YEAR(order_date) = 2024 or WHERE UPPER(email) = 'X' prevents the optimizer from using a plain index on order_date/email, because the stored index values don't match the transformed values being searched; rewriting as a sargable range (order_date >= '2024-01-01' AND order_date < '2025-01-01') or adding a functional/expression index fixes this.
  • Implicit type conversion — comparing an indexed numeric column against a string literal (or vice versa) can silently force a conversion on every row, disabling the index.
  • Low selectivity — if a column has very few distinct values (e.g. a boolean flag matching 40% of rows), the optimizer may reasonably prefer a full scan over an index, since scanning that many rows through the index would cost more than reading the table directly.
  • OR across differently-indexed columns — some optimizers won't combine two single-column indexes efficiently for an OR condition and fall back to a full scan; rewriting as a UNION of two indexed queries can help.

Reading an EXPLAIN Plan (Conceptually)

An EXPLAIN (or EXPLAIN ANALYZE) plan shows the sequence of operations the optimizer chose to satisfy a query — read it from the innermost/deepest step outward, or bottom-to-top depending on the engine's formatting. Key things to look for:

  • Scan type — an "index scan"/"index seek" is generally good; a "sequential scan"/"table scan" on a large table is a red flag unless the table is small or you're intentionally reading most of it.
  • Estimated vs. actual rows (in ANALYZE output) — a large gap usually means stale statistics, which can cause the optimizer to pick a bad plan.
  • Join algorithm and order — nested loop joins are efficient when one side is small/well-indexed; hash or merge joins tend to appear for larger, unindexed joins.
  • Cost estimates — relative, unit-less numbers used to compare candidate plans against each other, not an absolute time prediction.
Practical tip
When diagnosing a slow query, look first for any full table/sequential scan on a large table in the plan — that's almost always where an index would help most. Then check whether a composite index's column order actually matches the query's filter and sort columns.

Common Interview Questions

Why can't WHERE last_name LIKE '%son' use a standard index on last_name, while LIKE 'John%' can?
A B-tree index on a string column is sorted by the string's characters left to right, so it can efficiently jump to the range starting with "John" for a trailing wildcard. A leading wildcard means the unknown part comes first, so there's no way to use the sorted order to narrow the search — the engine must inspect every value. Some databases offer trigram or full-text indexes specifically to handle this case.
If you have a composite index on (last_name, first_name), will a query filtering only on first_name use it?
Generally no, or only very inefficiently — the index is sorted by last_name first, so without a last_name filter the engine can't narrow down a contiguous range for first_name alone and would have to scan the whole index. If first_name-only lookups are common, you'd want a separate index on first_name (or lead the composite index with it instead, depending on which query pattern matters more).
What's the difference between a clustered and non-clustered index in terms of lookup cost?
A clustered index's leaf nodes contain the actual row data, so once you reach the leaf, you have everything — one traversal. A non-clustered index's leaf nodes contain only the key and a pointer back to the row, so satisfying the query (unless it's a "covering" index containing every needed column) requires a second lookup to fetch the full row, sometimes called a bookmark lookup or key lookup.
Why might the query optimizer choose a full table scan even though an index exists on the filtered column?
If the filter matches a large fraction of the table (low selectivity — e.g. a status column where 90% of rows are "active"), reading the index and then bouncing back to the table for each matching row can cost more overall than simply scanning the table sequentially. The optimizer's cost estimate, based on table statistics, drives this choice — stale statistics can cause it to guess wrong in either direction.
You wrote WHERE UPPER(email) = 'JANE@EXAMPLE.COM' against an indexed email column and the query is slow. Why, and how do you fix it?
Wrapping the indexed column in a function makes the predicate non-sargable — the index stores raw email values, not their upper-cased form, so the optimizer can't map the search value back to a sorted range in the index and falls back to scanning every row. Fixes: store/compare using a normalized case consistently (e.g. always lower-case emails at write time and compare against a lower-cased literal), or create a function-based/expression index on UPPER(email) if the database supports it.

Key Takeaways

Remember
B-tree indexes give O(log n) lookups versus O(n) for a full scan, but only for sargable predicates — leading wildcards, functions on indexed columns, and implicit type conversions all defeat that benefit. Composite index column order must match your query's filter/sort pattern as a left-to-right prefix. Read EXPLAIN plans by hunting for full scans on large tables first.
