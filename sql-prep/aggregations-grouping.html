Aggregations & Grouping

Overview

Aggregation questions test whether you can collapse many rows into summary statistics correctly — and, critically, whether you know exactly when a filter belongs before or after that collapse. The WHERE vs. HAVING distinction trips up more candidates than any other single SQL concept, so expect it to come up directly or indirectly in almost every SQL interview.

GROUP BY Basics

GROUP BY collapses rows that share the same value(s) in the grouping column(s) into a single output row per group, and every column in the SELECT list must either be part of the GROUP BY or wrapped in an aggregate function (COUNT, SUM, AVG, MIN, MAX, etc.) — otherwise the database wouldn't know which of the many collapsed rows' values to show.

SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM employees
GROUP BY department;

HAVING vs. WHERE

AspectWHEREHAVING
Applied toIndividual rows, before groupingGroups, after aggregation
Can reference aggregates?No — aggregates don't exist yet at this stageYes — that's its entire purpose
Logical orderRuns before GROUP BYRuns after GROUP BY, before SELECT/ORDER BY
PerformanceReduces rows early — generally cheaperFilters after the (potentially expensive) aggregation has already run
-- WHERE narrows rows BEFORE grouping (only active employees are aggregated)
-- HAVING narrows groups AFTER aggregation (only departments averaging > 80k)
SELECT department, AVG(salary) AS avg_salary
FROM employees
WHERE status = 'ACTIVE'
GROUP BY department
HAVING AVG(salary) > 80000
ORDER BY avg_salary DESC;
Rule of thumb
If the condition can be evaluated on a single row without knowing about any other row, it belongs in WHERE (cheaper — filters before aggregation). If it depends on an aggregate result (a count, a sum, an average of the group), it must go in HAVING.

Aggregate Functions

FunctionBehavior
COUNT(*)Counts all rows, including those with NULL columns
COUNT(column)Counts only rows where column is non-NULL
SUM(column)Sums non-NULL values; returns NULL (not 0) if every value is NULL or the group is empty
AVG(column)Mean of non-NULL values — NULLs are excluded from both the sum and the divisor count
MIN / MAXSmallest/largest non-NULL value; works on numeric, string, and date types

GROUPING SETS, ROLLUP, and CUBE

These extensions let a single query produce multiple levels of subtotal in one pass, instead of running several GROUP BY queries and UNION-ing them together:

  • GROUPING SETS — explicitly lists which combinations of columns to group by, including an empty set () for a grand total.
  • ROLLUP — produces a hierarchical set of subtotals for an ordered list of columns (e.g. by region, then region+city, then a grand total) — assumes a hierarchy between the columns.
  • CUBE — produces subtotals for every possible combination of the given columns (the full power set), useful for cross-tab style reports where no hierarchy is assumed.
-- ROLLUP: subtotal per region, then per region+quarter, then grand total
SELECT region, quarter, SUM(revenue) AS revenue
FROM sales
GROUP BY ROLLUP (region, quarter);

-- Equivalent GROUPING SETS spelled out explicitly
SELECT region, quarter, SUM(revenue) AS revenue
FROM sales
GROUP BY GROUPING SETS ((region, quarter), (region), ());
GROUP BY complexity Sort-based aggregation: O(n log n)  |  Hash-based aggregation: O(n) average case (hash table keyed by group)
Most modern query optimizers pick hash aggregation when the number of distinct groups fits comfortably in memory, falling back to sort-based (or disk-spilling hash) aggregation for very high-cardinality GROUP BY columns.

Common Interview Questions

Why can't you filter on an aggregate function using WHERE?
Because of logical query processing order: WHERE executes before GROUP BY/aggregation, so aggregate values like COUNT(*) or SUM(x) simply don't exist yet at that stage. HAVING runs after grouping specifically so it can filter on aggregate results.
Why does COUNT(*) sometimes return a different value than COUNT(some_column)?
COUNT(*) counts every row in the group regardless of column contents. COUNT(column) only counts rows where that specific column is non-NULL. If some rows have a NULL in that column, COUNT(column) will be lower than COUNT(*).
If a department has no employees matching a filter, does it still show a row with SUM = 0?
No — if the filter (in WHERE) eliminates all rows for that department before grouping, the department never appears in the result at all, since GROUP BY only produces rows for groups that have at least one contributing row. SUM returns NULL, not 0, only when a group exists but every value being summed is NULL.
What's the practical difference between ROLLUP and CUBE?
ROLLUP(a, b, c) assumes a hierarchy and produces subtotals for (a,b,c), (a,b), (a), and () — a fixed drill-down path. CUBE(a, b, c) produces subtotals for every combination, including (a,c) and (b,c), which ROLLUP would skip — useful when you need a full cross-tabulation rather than a single hierarchical drill-down.
Can you use both WHERE and HAVING in the same query?
Yes, and it's common: WHERE filters individual rows before aggregation (cheaper, reduces the dataset early), and HAVING then filters the resulting groups based on aggregate conditions. Doing the row-level filtering in WHERE instead of duplicating it as a non-aggregate condition in HAVING is both clearer and more efficient.

Key Takeaways

Remember
WHERE filters rows before grouping; HAVING filters groups after aggregation and is the only place you can reference an aggregate condition. COUNT(*) counts rows, COUNT(column) counts non-NULL values. ROLLUP/CUBE/GROUPING SETS compute multiple subtotal levels in a single pass instead of stacking several queries.
