SQL Fundamentals & Joins

Overview

Every SQL interview starts here: can you write a correct SELECT, filter and order results, and — most importantly — combine rows from multiple tables using the right join type. Interviewers watch for whether you understand what a join actually does to the row set (a Cartesian product filtered by a predicate) rather than just memorizing syntax, and whether you can reason about how NULL behaves in join conditions and filters.

SELECT, WHERE, ORDER BY Basics

The logical processing order of a query is not the order you type it in: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This is why you can't reference a SELECT-defined column alias in a WHERE clause (it doesn't exist yet at that stage) but you generally can in ORDER BY (evaluated after SELECT).

SELECT customer_id, order_date, total_amount
FROM orders
WHERE total_amount > 100
ORDER BY order_date DESC;

Join Types

Given two tables Customers and Orders, where not every customer has placed an order and not every order references a valid customer:

Customers                Orders
+----+---------+         +----+-------------+--------+
| id | name    |         | id | customer_id | amount |
+----+---------+         +----+-------------+--------+
| 1  | Alice   |         | 10 | 1           | 50     |
| 2  | Bob     |         | 11 | 1           | 75     |
| 3  | Carol   |         | 12 | 4           | 20     |  <- orphan (no customer 4)
+----+---------+         +----+-------------+--------+
                          (Carol, id 3, has no orders)

-- INNER JOIN: only rows with a match on both sides
SELECT c.name, o.amount
FROM customers c
INNER JOIN orders o ON c.id = o.customer_id;
-- Alice/50, Alice/75   (Bob and Carol excluded; orphan order 12 excluded)

-- LEFT (OUTER) JOIN: all rows from the left table, NULLs where no match
SELECT c.name, o.amount
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id;
-- Alice/50, Alice/75, Bob/NULL, Carol/NULL

-- RIGHT (OUTER) JOIN: all rows from the right table, NULLs where no match
SELECT c.name, o.amount
FROM customers c
RIGHT JOIN orders o ON c.id = o.customer_id;
-- Alice/50, Alice/75, NULL/20   (order 12's orphan customer_id 4 shows as NULL name)

-- FULL OUTER JOIN: all rows from both sides, NULLs where no match on either side
SELECT c.name, o.amount
FROM customers c
FULL OUTER JOIN orders o ON c.id = o.customer_id;
-- Alice/50, Alice/75, Bob/NULL, Carol/NULL, NULL/20

-- CROSS JOIN: Cartesian product, every row from A paired with every row from B
SELECT c.name, o.amount
FROM customers c
CROSS JOIN orders o;
-- 3 customers x 3 orders = 9 rows, no matching condition at all

-- SELF JOIN: a table joined to itself, typically for hierarchical/comparison data
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
Join typeResult includes
INNER JOINOnly rows with a match in both tables
LEFT JOINAll left rows, matched right columns or NULL
RIGHT JOINAll right rows, matched left columns or NULL
FULL OUTER JOINAll rows from both sides, NULLs where unmatched
CROSS JOINCartesian product — every combination of rows, no condition
SELF JOINNot a distinct join type — a table aliased and joined to itself

NULL Semantics in Joins

NULL represents "unknown," so it never equals anything in a three-valued logic system — not even another NULL. a = NULL, NULL = NULL, and a <> NULL all evaluate to UNKNOWN, which is treated as false for filtering purposes. This has two important consequences for joins: (1) an outer join produces NULLs for the unmatched side, and any subsequent WHERE filter on those columns (instead of the join's ON clause) will silently drop those rows because the comparison evaluates to UNKNOWN; (2) you cannot join two rows purely because both have a NULL in the join column — use IS NOT DISTINCT FROM (Postgres) or explicit COALESCE logic if you need NULL-inclusive matching.

Common bug: filtering an outer join back into an inner join
LEFT JOIN orders o ON ... WHERE o.amount > 50 silently discards every unmatched left row, because NULL > 50 is UNKNOWN, not true. If you need to keep unmatched rows while still filtering matched ones, move the condition into the ON clause instead of WHERE.
Join algorithm complexity Nested-loop join: O(N × M)  |  Hash join: O(N + M)  |  Sort-merge join: O(N log N + M log M)
e.g. joining a 1,000-row table against a 1,000,000-row table: nested-loop ≈ 1 billion comparisons worst case, vs. a hash join ≈ 1,001,000 operations — this gap is exactly why query planners fight to avoid nested-loop joins on large, unindexed tables.

Common Interview Questions

What's the difference between WHERE filtering in the join's ON clause vs. the query's WHERE clause for an outer join?
A condition in ON is applied while the join is being formed, so it only affects which right-side rows are matched — unmatched left rows still appear with NULLs. The same condition in WHERE is applied after the join, so it filters the final result set and will drop any row where the condition evaluates to UNKNOWN/false, including legitimately unmatched left rows — effectively turning a LEFT JOIN back into an INNER JOIN.
How would you find all customers who have never placed an order?
Use a LEFT JOIN from customers to orders and filter for orders.id IS NULL in the WHERE clause (safe here because the filter is on a column that is only NULL for genuinely unmatched rows): SELECT c.* FROM customers c LEFT JOIN orders o ON c.id = o.customer_id WHERE o.id IS NULL. A NOT IN subquery works too but is a trap if the subquery's column can contain NULL — NOT IN against a list containing NULL returns no rows at all.
Is a SELF JOIN a distinct kind of join?
No — it's just any join type (commonly INNER or LEFT) where the same table is referenced twice under different aliases, typically to compare rows within the table (e.g. an employee to their manager, who is also a row in the employees table) or find pairs/duplicates.
When would you deliberately use a CROSS JOIN?
When you genuinely need every combination of two sets — e.g. generating a calendar of all (store, date) pairs to left-join against actual sales data so that days/stores with zero sales still appear as rows with 0, rather than being absent entirely.
Why does NOT IN (SELECT ... ) sometimes return zero rows unexpectedly?
If the subquery's result set contains even one NULL, the entire NOT IN predicate evaluates to UNKNOWN for every row, because comparing against a NULL in the list can never be proven false. The safe alternatives are NOT EXISTS (correlated subquery, unaffected by NULLs) or filtering the subquery with WHERE column IS NOT NULL before using NOT IN.

Key Takeaways

Remember
Query clauses execute in logical order (FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY), not written order. Choose the join type based on which side's unmatched rows you need to preserve, and always double-check whether a post-join filter belongs in ON or WHERE — that choice changes your result set with outer joins. NULL never equals anything, including itself.
