Window Functions

Overview

Window functions compute a value across a set of related rows without collapsing them into a single output row the way GROUP BY does — each input row keeps its identity, but gains access to aggregate/ranking context from its "window" of peer rows. This is the tool interviewers reach for to test whether you can express running totals, rankings, and row-to-row comparisons (like "previous month's value") declaratively instead of with self-joins or procedural loops.

OVER, PARTITION BY, ORDER BY

Every window function uses an OVER (...) clause to define its window:

  • PARTITION BY — splits rows into independent groups (like GROUP BY, but rows aren't collapsed); the function resets for each partition.
  • ORDER BY (inside OVER) — defines the row order within each partition, which matters for ranking functions, LAG/LEAD, and running aggregates.
SELECT
    employee_id,
    department,
    salary,
    AVG(salary) OVER (PARTITION BY department) AS dept_avg_salary
FROM employees;
-- every employee row keeps its own salary, plus its department's average alongside it

ROW_NUMBER vs. RANK vs. DENSE_RANK

FunctionBehavior on tiesGaps after ties?
ROW_NUMBER()Assigns a unique, arbitrary sequential number even to tied rowsN/A — never repeats a number
RANK()Tied rows get the same rankYes — next rank skips (e.g. 1,1,3)
DENSE_RANK()Tied rows get the same rankNo gap — next rank is sequential (e.g. 1,1,2)
SELECT name, score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,
    RANK()       OVER (ORDER BY score DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rnk
FROM exam_results;

-- name    score  row_num  rnk  dense_rnk
-- Ana     95     1        1    1
-- Ben     95     2        1    1
-- Cy      90     3        3    2
-- Dee     88     4        4    3

LAG / LEAD

LAG(column, n) looks back n rows (default 1) within the current partition's order; LEAD(column, n) looks forward n rows. Both accept an optional default value to return when there's no such row (e.g. the very first row has no previous row to look back to).

SELECT
    month,
    revenue,
    LAG(revenue, 1, 0) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue, 1, 0) OVER (ORDER BY month) AS month_over_month_change
FROM monthly_revenue;

Running Totals with SUM() OVER and Frame Clauses

A window frame narrows the set of peer rows a function considers, relative to the current row, using ROWS BETWEEN ... AND ... (or the value-based RANGE). The default frame when ORDER BY is present but no frame is specified is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which is exactly what produces a running total.

-- Running total of revenue per month
SELECT
    month,
    revenue,
    SUM(revenue) OVER (
        ORDER BY month
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM monthly_revenue;

-- Top-2 highest-paid employees per department
SELECT department, name, salary
FROM (
    SELECT
        department, name, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
) ranked
WHERE rn <= 2;
Frame clause reference ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW → running total from the start of the partition to the current row
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW → moving sum/average over the current row plus the 2 preceding rows (a 3-row window)
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING → reverse running total, from the current row to the end of the partition

Common Interview Questions

How would you find the top-3 highest-paid employees in each department?
Wrap a ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) in a subquery or CTE, then filter the outer query with WHERE rn <= 3. ROW_NUMBER is preferred over RANK here when you want exactly 3 rows per department even if there are salary ties; use RANK instead if ties should all be included (which could return more than 3 rows for a department).
What's the key difference between a window function and GROUP BY?
GROUP BY collapses multiple rows into one output row per group, losing row-level detail. A window function computes its result over a window of peer rows but returns one output row per input row, so you keep every original column alongside the computed aggregate/ranking value — enabling things like "this row's value alongside its group's average" in a single row.
Why might a running total computed with SUM() OVER (ORDER BY date) give unexpected duplicate totals for rows on the same date?
The default frame for ORDER BY without an explicit ROWS/RANGE clause is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, and RANGE groups by value, not row position — so all rows sharing the same date value are treated as a single peer group and get the same cumulative total (the total through the end of that date). Switching to ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW makes it strictly row-by-row instead.
How do you compute month-over-month percentage growth using window functions?
Use LAG(revenue) OVER (ORDER BY month) to pull the previous month's value onto the same row, then compute (revenue - prev_revenue) / prev_revenue in the outer SELECT (guarding against division by zero/NULL for the first row with NULLIF or a default in LAG's third argument).
Can you use a window function's result directly in the same query's WHERE clause?
No — window functions are evaluated after WHERE/GROUP BY/HAVING in logical processing order (alongside SELECT), so their results aren't available yet in WHERE. You must wrap the query in a subquery or CTE and filter on the window function's output column in the outer query.

Key Takeaways

Remember
Window functions preserve row-level granularity while adding group-aware context — use PARTITION BY to reset per group and ORDER BY to control ranking/running behavior. Pick ROW_NUMBER/RANK/DENSE_RANK based on how you want ties handled, and be explicit about the frame clause (ROWS BETWEEN ...) whenever row-by-row semantics matter, since the default RANGE frame groups by value on ties.
