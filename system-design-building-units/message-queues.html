SYSTEM DESIGN — BUILDING UNITS

Messaging & Streaming

Overview

Messaging and streaming systems let services communicate asynchronously — a producer emits something and moves on, while one or more consumers process it independently, on their own schedule. This decouples the pace and availability of the sender from the receiver, which is what makes a slow or unreliable downstream step (image resizing, a fraud check, a third-party API call) survivable without forcing the caller to wait. The building blocks below span the point-to-point queue (one message picked up by exactly one worker), the fan-out publish/subscribe pattern (one message copied to every subscriber), Apache Kafka's durable, replayable log (which can behave like either), and event-driven architecture as the broader pattern that organizes services around events rather than direct calls.

Message Queues (Point-to-Point)

A message queue is middleware for asynchronous, point-to-point communication: a producer publishes a message onto a named queue, and exactly one consumer processes it — even when many consumers are attached to that same queue. A broker sits in the middle and stores each message durably until it has been successfully processed, which is what decouples producer and consumer in both time (the consumer doesn't need to be running right now) and space (neither side needs to know about the other directly). When several consumers listen on one queue, they compete for messages — the "competing consumers" pattern — and each individual message still only goes to one of them, giving natural load-balancing across a worker pool. A consumer that fails to acknowledge a message within its visibility/prefetch timeout causes the broker to redeliver it, the basic mechanism behind at-least-once delivery.

Durability is a deliberate trade-off: durable queues combined with persistent messages and publisher confirms survive a broker restart, while non-durable/transient queues trade that safety for speed. Messages that repeatedly fail, expire, or are explicitly rejected are routed to a dead-letter queue (DLQ) — RabbitMQ implements this as a Dead Letter Exchange, SQS as a redrive policy — so a handful of "poison" messages can't block an entire queue behind them. Delivery guarantees range from at-most-once (fast, but a message can be silently lost) to at-least-once (the practical default — guaranteed delivery but possible duplicates, so consumers must be idempotent) to exactly-once, which in practice is only achieved via at-least-once plus deduplication (as with SQS FIFO's dedup window) rather than as a pure network-level guarantee. Ordering is generally not guaranteed on a standard queue; FIFO variants provide strict per-group ordering at a real throughput cost.

Popular tools: RabbitMQ (AMQP broker — producers publish to an exchange that routes to queues via direct/topic/fanout/headers bindings; quorum queues are the modern Raft-based HA option), Amazon SQS (Standard for near-unlimited best-effort-ordered throughput, FIFO for strict per-group order and exactly-once processing via dedup), Apache ActiveMQ Classic/Artemis (JMS-compliant, multi-protocol, XA/JTA transactions), IBM MQ, Azure Service Bus.

When to use it
Background job processing (image resizing, sending email), decoupling a slow downstream service from a fast producer, distributing work across a pool of workers, and any retry-heavy workflow that needs DLQ handling. SQS is the zero-ops default on AWS; RabbitMQ suits flexible content-based routing. Reach for a queue when exactly one worker needs to do the job — if multiple independent services must each see every message, or you need to replay history, look at pub/sub or Kafka instead.
ProsCons
  • Simple mental model and strong decoupling
  • Natural load-balancing across competing consumers
  • Absorbs backpressure when consumers fall behind
  • Built-in retry and DLQ semantics
  • No built-in replay of past messages
  • Ordering is weak by default, or costs throughput to guarantee
  • No native fan-out to independent consumer groups

Publish/Subscribe (Pub/Sub) Systems

Publish/subscribe flips the delivery model: a publisher sends to a logical topic without knowing — or caring — who is listening, and every subscriber attached to that topic receives its own copy of each message. That's fan-out, one message to N subscribers, rather than a queue's one message to one consumer. The broker's job is simply to maintain the list of subscriptions and deliver a copy to each of them; publishers and subscribers are decoupled in both directions, and subscribers can be added or removed without the publisher ever changing.

In managed cloud services, a "subscription" is often itself a durable resource rather than a transient socket — Google Cloud Pub/Sub subscriptions, or SQS queues subscribed to an SNS topic, persist undelivered messages so a slow or temporarily offline subscriber doesn't lose them. This SNS + SQS fan-out pattern is one of the most common building blocks in AWS architectures. Delivery guarantees vary by product: Google Cloud Pub/Sub offers at-least-once delivery with an optional exactly-once mode, ordering keys, dead-letter topics, and schema validation, while Amazon SNS is best-effort with no strict ordering on standard topics (FIFO topics exist when paired with SQS FIFO). Many systems also support subscription-level filters so a given subscriber only receives the relevant subset of a topic's traffic.

Point-to-point queues deliver each message to exactly one competing consumer; pub/sub fans a single message out to every independent subscriber.

Popular tools: Redis Pub/Sub (lightweight, in-memory, fire-and-forget — no persistence, good for ephemeral notifications within a Redis-based system), Google Cloud Pub/Sub (fully managed, push/pull, ordering keys, DLQ, schema enforcement), Amazon SNS (fans out to SQS, Lambda, HTTP/S, email, SMS, mobile push), Azure Event Grid, Apache Pulsar (supports both queue and pub/sub semantics natively).

When to use it
Broadcasting an event to multiple independent, unrelated services — an "OrderPlaced" event triggering email, inventory, and analytics separately without any of them knowing about each other. Also real-time notification systems, chat presence, push notifications, and cache-invalidation broadcasts, or building an event-driven backbone where new consumers should be addable without ever touching the publisher. If you need topic fan-out but also need replay/history, that's a sign to reach for Kafka-style streaming instead.
ProsCons
  • Natural fan-out to many independent consumers
  • Strong decoupling in both directions
  • Trivial to add new subscribers without touching the publisher
  • Messages can be lost for offline subscribers without a durable subscription layer
  • Hard to verify "did everyone process this"
  • Generally no history replay

Apache Kafka — Deep Dive

Apache Kafka is a distributed event streaming platform built around a durable, replicated, append-only commit log — not a traditional queue that deletes a message once it's consumed. Multiple independent consumers can read, and re-read, the exact same data at their own pace, which is the fundamental difference from both message queues and classic pub/sub.

A Kafka topic is split into partitions, which are the unit of both parallelism and ordering — Kafka guarantees order only within a single partition, never across an entire topic. Brokers store partition data, and a cluster is simply many brokers working together; producers write records, optionally with a key, and that key is hashed to deterministically pick which partition a record lands on, which is how per-key ordering is achieved. Consumer groups are the other half of the model: a set of consumers cooperatively reads a topic by splitting its partitions among group members, so within one group each partition is read by exactly one consumer at a time, while separate consumer groups are fully independent of each other and each receives the entire stream. This is what lets Kafka behave like a queue (one group) and like pub/sub (many groups) simultaneously.

Each consumer group tracks its own read position per partition as an offset (stored internally in __consumer_offsets), which enables resuming after a restart and replaying history simply by resetting the offset backward. Every partition is replicated (a replication factor of 3 is typical) with one broker acting as leader for reads/writes and the others as followers that can be promoted if the leader fails. Messages are retained according to a time or size policy regardless of whether they've been consumed — the feature that makes replay and multiple independent consumer groups possible in the first place — and log compaction can instead retain only the latest value per key, useful for changelog/state-restoration use cases. Kafka historically relied on ZooKeeper for cluster metadata and controller election; KRaft, Kafka's own Raft-based consensus layer, replaces it by storing metadata inside Kafka itself, and as of Kafka 4.0 (March 2025) ZooKeeper mode has been fully removed — KRaft is now the only supported mode. Exactly-once semantics are achieved through idempotent producers (a unique ID plus a per-partition sequence number that drops duplicate retries) combined with transactions that atomically commit writes across partitions along with their offsets.

Producers write keyed records into partitions spread across brokers; within Consumer Group A each partition is read by exactly one consumer for parallelism, while an independent Consumer Group B can replay the same partitions from its own offset.

Popular tools: Apache Kafka, Confluent Platform/Cloud (Schema Registry, ksqlDB, connectors), Amazon MSK, Redpanda (Kafka-API-compatible, no JVM or ZooKeeper dependency), Kafka Connect (source/sink connectors), Kafka Streams/ksqlDB (stream processing).

When to use it
Event streaming backbones — clickstream analytics, IoT telemetry, log aggregation, fraud detection — plus any situation where multiple independent downstream systems need the same raw event stream, event sourcing/CQRS backbones, high-throughput microservice decoupling, and change-data-capture pipelines (Debezium). Choose Kafka specifically when multiple teams need the same stream at their own pace, you need replay/backfill, or you need very high sustained throughput with per-key ordering — it's overkill for a simple background job queue or a low-volume system where operational simplicity matters more than throughput.
ProsCons
  • Massive throughput and scalability via partition parallelism
  • Durable, replayable log — read history, not just "now"
  • Multiple independent consumer groups without interfering with each other
  • Strong per-partition/key ordering
  • Heavier operational footprint even under KRaft
  • Producers/consumers must handle partition-key routing logic themselves
  • No global ordering across an entire topic
  • Overkill for simple one-off job dispatch

Event-Driven Architecture (EDA) as a Pattern

Event-driven architecture is an architectural style, not a specific product — services communicate by producing and reacting to immutable events rather than calling each other directly and synchronously, which decouples them in time, location, and implementation. Any of the messaging building blocks above (a queue, a pub/sub topic, or Kafka) can serve as the transport; EDA is the pattern of designing services around events as the primary way state changes propagate through a system.

Events can carry different amounts of information: event notification is a lightweight "something happened" signal that forces the consumer to call back to the source for details, while event-carried state transfer embeds the actual state the consumer needs directly in the event, avoiding that callback at the cost of possible staleness or duplication. Event sourcing takes this further by treating every state change as an immutable, ordered event and deriving current state by replaying those events (or a snapshot plus the events since) — which gives a complete audit trail and the ability to query state as of any point in time, at the cost of schema-versioning and snapshotting complexity. CQRS complements this by splitting the model into a command side that handles writes (often event-sourced) and a query side that builds denormalized, purpose-built read models asynchronously from the event stream, letting reads and writes scale independently.

Because a single ACID transaction can't span multiple services, distributed workflows use the saga pattern: a sequence of local transactions, each with a corresponding compensating action if a later step fails. Choreography lets services react to each other's events with no central coordinator — simple and free of a single point of failure, but harder to trace as the number of participants grows. Orchestration instead uses a central orchestrator to explicitly sequence steps and compensations, giving much clearer visibility into complex workflows at the cost of making the orchestrator itself a critical, must-be-highly-available component.

Popular tools: The event backbone is typically Apache Kafka, AWS EventBridge, Azure Event Grid, or NATS; saga orchestration commonly uses AWS Step Functions, Temporal, or Camunda; event sourcing/CQRS implementations often lean on frameworks like Axon Framework or EventStoreDB.

When to use it
Microservices that need to react to state changes without tight coupling — checkout triggering inventory, shipping, and billing independently. Systems needing a strong audit trail (financial ledgers, healthcare) favor event sourcing; read-heavy systems needing multiple specialized views favor CQRS; distributed transactions across services call for sagas — choreography for a handful of participants, orchestration when you need central visibility into a complex workflow. Skip full event sourcing/CQRS for simple CRUD apps where the added complexity isn't earning its keep.
ProsCons
  • High decoupling and independent scalability of services
  • Resilience — one service's trouble doesn't block others
  • Audit trail and history "for free" with event sourcing
  • Eventual consistency is harder to reason about
  • Distributed debugging/tracing is harder across many services
  • Ongoing event-schema-evolution tax
  • Real engineering overhead for event sourcing/CQRS

Comparison: Message Queue vs. Kafka vs. Pub/Sub

The three patterns above are often confused because they solve overlapping problems — the table below lines them up side by side on the dimensions that actually drive the choice.

DimensionMessage Queue (SQS, RabbitMQ)Event Streaming (Kafka)Pub/Sub (SNS, GCP Pub/Sub, Redis)
ConsumptionOne message → one consumerMultiple independent consumer groups each read the full streamOne message → every subscriber
LifecycleDeleted after ackRetained per policy (replayable)Typically ephemeral unless durable subscription
OrderingBest-effort, or strict FIFO at a throughput costGuaranteed per partition/keyUsually not guaranteed
ReplayNoYesGenerally no
Typical useTask queues, job dispatch, load levelingStreaming, analytics, CDC, event sourcingBroadcast notifications, multi-service fan-out

Rule of thumb: exactly one worker must reliably do a job → queue. Multiple systems must independently react to (and maybe replay) a stream of things that happened → Kafka. Broadcast a fact to whoever is listening right now, possibly across protocols → pub/sub. These are frequently combined in practice — SNS fan-out into per-consumer SQS queues, or Kafka Connect sinking into SQS/SNS for downstream systems that expect queue semantics.
