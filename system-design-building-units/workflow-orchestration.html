SYSTEM DESIGN — BUILDING UNITS

Workflow Orchestration & Job Scheduling

Overview

Orchestration tools solve a different problem than a message queue or a compute engine: given a set of steps with dependencies — some that must run in sequence, some that can run in parallel, some that depend on external conditions like a file landing — how do you schedule, retry, monitor, and recover them reliably? A plain cron job can trigger a script at a fixed time, but it has no concept of upstream dependencies, retries, partial failure, backfills, or observability. Real data, ML, and business pipelines are DAGs (Directed Acyclic Graphs) of steps with dependencies — "run the Spark aggregation job only after today's ingestion job has landed data, and only if yesterday's partition succeeded" — and they need automatic retries with backoff, alerting on failure, backfill support for historical runs, and a UI/API for humans and other systems to inspect status. Workflow orchestrators exist to coordinate exactly this: multi-step, dependency-having jobs, reliably — not just "run X at time Y."

Apache Airflow

Apache Airflow is an open-source, Python-based platform for authoring, scheduling, and monitoring workflows defined as DAGs of tasks. Originated at Airbnb, it's the de facto standard for data-pipeline and ETL orchestration.

Workflows ("DAGs") are written as Python code specifying tasks and their dependencies. A persistent Scheduler process reads serialized DAGs from a metadata database and decides when each DAG run or task should trigger, based on schedule and dependency state; a pluggable Executor (Local, Celery, Kubernetes) decides how and where each task actually runs; the metadata database persists DAG definitions, run history, task states, and connections; and a web UI visualizes DAG graphs, run history, and logs, letting operators retry or clear failed tasks by hand. Airflow ships rich scheduling support — cron-like schedules plus sensors that wait for external conditions such as a file landing or an upstream DAG completing — along with built-in per-task retry/alerting, backfill support for historical runs, a large library of pre-built operators for common systems (Spark, BigQuery, S3, Kubernetes, dbt), and plugin-based extensibility.

A DAG encodes both order and parallelism: extract runs first, transform runs next, load_a/load_b fan out in parallel, and validate is scheduled only once every upstream dependency has succeeded.

Popular tools: Managed offerings — Amazon MWAA, Google Cloud Composer, Astronomer; self-hosted on Kubernetes via the official Helm chart.

When to use it
Classic data-engineering/ETL/ML-pipeline orchestration with relatively short-lived, batch-oriented steps — wait for the nightly file drop, trigger a Spark job, load results into a warehouse, trigger a dbt run, refresh a BI dashboard, alert on-call on any failure. The default choice when the orchestration domain is primarily data/ETL/ML pipelines.
ProsCons
  • Huge ecosystem of pre-built operators and integrations
  • Mature scheduling model (cron schedules, sensors, backfills) purpose-built for data pipelines
  • Large community, extensive documentation, easy to hire for
  • DAGs are batch/schedule-oriented, not a natural fit for long-lived or event-driven business processes
  • Scheduler/metadata-database can become an operational bottleneck at very high DAG/task volume
  • Workflow structure is still a fixed graph defined ahead of time, less flexible than fully dynamic code-as-workflow models

Temporal

Temporal is a durable execution platform for writing and running workflows as ordinary code — Go, Java, TypeScript, Python, .NET, PHP — guaranteeing that a workflow's logic runs to completion across process crashes, deployments, or infrastructure failures, without the developer manually implementing retry or state-persistence logic.

Developers write workflow logic as normal functions; Temporal's runtime automatically records every step and event into a durable "event history," so a crashed worker's progress can be resumed exactly where it left off by replaying that history — no manually built checkpointing required. Long-running "activities" (calls to external services) get automatic retry policies, timeouts, and backoff declared rather than hand-coded, and workflows can run for seconds or literally years, holding state — such as waiting on a human approval or an external signal — without consuming compute while idle. Because workflows are real code with full IDE support, unit testing, and version control, Temporal isn't limited to data pipelines; it's widely used for business-process orchestration (order fulfillment, onboarding, payment processing) and increasingly for multi-step AI/agentic workflows.

Popular tools: Temporal Cloud (managed), self-hosted Temporal Server; client SDKs for Go, Java, TypeScript, Python, .NET, PHP.

When to use it
Long-running, stateful business processes that must survive failures and can span seconds to months or years — an e-commerce order-fulfillment saga (payment → inventory → shipping → possible refund/compensation), multi-day onboarding with human-in-the-loop steps, distributed transaction/saga patterns across microservices, or chains of external API calls each needing independent retry/timeout handling. Less commonly the first choice purely for scheduled batch data pipelines — that's Airflow's niche — and the two are sometimes used together: Temporal for operational logic, Airflow for downstream analytics scheduling.
ProsCons
  • Workflow-as-real-code — full IDE support, unit testing, version control, no YAML/visual DSL
  • Automatic retries and durable state across failures without hand-built checkpointing
  • Strong fit for very long-running, stateful processes (seconds to years)
  • Not purpose-built for classic scheduled batch/ETL pipelines the way Airflow is
  • Requires developers to think in terms of durable-execution semantics (determinism constraints on workflow code)
  • Smaller footprint in traditional data-engineering teams versus Airflow's dominance there

AWS Step Functions

AWS Step Functions is a fully managed, serverless state-machine orchestration service for coordinating AWS-native workflows, defined declaratively in Amazon States Language — a JSON-based DSL.

You define a state machine — steps, branching, parallel execution, error handling/retries, wait states — that Step Functions executes, invoking AWS services (Lambda, ECS/Fargate, Glue, SageMaker, SNS/SQS, DynamoDB) as steps while tracking state itself. Standard Workflows are exactly-once, durable, and auditable, run up to a year, support roughly 2,000 executions per second, and are billed per state transition — good for long-running, auditable processes. Express Workflows are at-least-once, run up to five minutes, support 100,000+ executions per second, and are billed by duration/memory — good for high-volume, idempotent event processing such as streaming ETL or IoT ingestion, further split into synchronous (wait for the result) and asynchronous (fire-and-forget, poll logs) variants.

Popular tools: AWS Step Functions (Standard and Express Workflows); commonly paired with Lambda, Glue, ECS/Fargate, SageMaker, SNS/SQS, and DynamoDB as the invoked steps.

When to use it
Orchestrating multi-step, AWS-native serverless applications or pipelines without operating any orchestration infrastructure yourself — for example a pipeline that triggers a Glue/EMR job, waits for completion, then invokes a Lambda to validate output and a SageMaker job to retrain a model; coordinating microservice call sequences; or high-throughput real-time event processing (Express) like IoT telemetry transformation. Best fit when already AWS-centric and wanting minimal operational overhead versus self-hosting Airflow or Temporal.
ProsCons
  • Fully managed — no orchestration infrastructure to run or scale
  • Deep native integration across the AWS service catalog
  • Built-in error handling/retry/catch per state plus pay-per-use pricing
  • Tied to the AWS ecosystem — poor fit for multi-cloud or on-prem orchestration
  • Amazon States Language is a JSON DSL, less expressive/testable than workflow-as-code platforms
  • Standard Workflows' per-state-transition billing can get costly at very high step counts

The three orchestrators above solve overlapping but distinct problems — the table below summarizes when each is the natural fit.
