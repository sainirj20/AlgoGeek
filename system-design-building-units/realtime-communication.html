SYSTEM DESIGN — BUILDING UNITS

Real-Time Client-Server Communication

Overview

Real-time communication covers the mechanisms by which a server pushes updates to a client — or a client and server exchange data continuously — without the client having to repeatedly ask from scratch. The right choice depends heavily on directionality (does the client need to send data on the same channel, or only receive it?), how many concurrent connections you need to hold open, and what your network path (corporate proxies, load balancers, browsers) will actually allow through. This page moves from the general-purpose, bidirectional options (WebSockets, gRPC streaming) through one-way and legacy-friendly fallbacks (SSE, long polling) to peer-to-peer media (WebRTC), then closes with a side-by-side comparison of all of them.

WebSockets

WebSockets (RFC 6455, standardized in 2011) provide a full-duplex, bidirectional, persistent connection over a single TCP socket, letting client and server exchange messages in either direction at any time without the overhead of a new HTTP request/response for every message. A connection begins as an ordinary HTTP GET carrying an Upgrade: websocket header, a Connection: Upgrade header, and a Sec-WebSocket-Key; the server responds 101 Switching Protocols with a matching Sec-WebSocket-Accept, proving it understood the protocol. After that single handshake, both sides stop speaking HTTP entirely and exchange raw WebSocket frames — text, binary, close, ping, and pong opcodes — on the same open socket indefinitely.

Because an idle TCP socket gives no application-level signal that the other side is still alive, WebSocket implementations rely on ping/pong control frames to detect connections silently killed by NAT devices or proxies, and to measure round-trip latency. The protocol itself is deliberately minimal: it guarantees a bidirectional byte/message channel and nothing else — there's no built-in reconnection, no delivery guarantees, and no authentication scheme, so the application has to build all of that itself on top.

Popular tools: Browser-native WebSocket API; Node's ws and uWebSockets.js; Socket.IO (adds fallback transports, rooms, and auto-reconnect on top of raw WebSockets); Django Channels; Spring WebSocket; ASP.NET SignalR; and managed services (Ably, Pusher, PubNub) for teams that don't want to run the infrastructure themselves.

When to use it
Chat and messaging apps, multiplayer gaming state sync, collaborative editing, and live trading tickers where the client also sends orders or subscription changes — anywhere the client must both receive pushes and send frequent messages on the same channel. If the client only ever receives and never needs to talk back, SSE is usually the simpler choice.
ProsCons
  • True bidirectional, low-latency communication on one connection
  • Efficient for high-frequency exchanges like chat, gaming, and collaborative editing
  • Low per-message overhead versus repeated HTTP requests
  • Stateful connections complicate horizontal scaling and load balancing
  • No automatic reconnection or delivery guarantees — the application must build both
  • Some corporate proxies/firewalls block the protocol upgrade
  • Millions of idle sockets still consume real memory and file descriptors

WebSocket Handlers & Connection Gateway Architecture at Scale

Running WebSockets for millions of concurrent users forces an architectural split that a purely stateless HTTP API doesn't need. Stateless HTTP servers can be load-balanced request by request, since any instance can handle any request — but a WebSocket connection can't be, because a specific client's socket and its per-connection state live in one specific machine's memory. Production systems answer this by running a dedicated, stateful gateway tier that does nothing but hold open persistent connections and route messages, kept architecturally separate from the stateless API tier. Slack's architecture is a clean real-world example: stateful, in-memory Gateway Servers hold each user's subscriptions and are deployed per region so clients connect to the nearest one; separate Channel Servers hold channel state via consistent hashing; Admin Servers remain stateless request handlers; and Presence Servers track who's online — a browser only ever talks to an edge proxy (Envoy) and then a Gateway Server, which never runs business logic, just proxies and fans out messages. Discord follows the same principle, isolating its Gateway (the WebSocket entry point) from its REST API and other backend services. This split creates the classic "sticky session" problem: because a client's socket lives on exactly one gateway node, a load balancer must route that client back to the same node for the life of the connection (via IP hash, cookie, or consistent hash) — which becomes fragile at scale, since a node's death disconnects every client pinned to it at once, and a routine rolling deploy forcibly disconnects clients as nodes drain.

The harder problem is that a message for a given user can originate from any backend server, but only the one gateway node holding that user's socket can actually deliver it. Systems solve this by externalizing connection state into a connection registry — typically Redis — mapping user_id → gateway_node_id, updated on every connect and disconnect; any backend service looks up the owning node before routing a message there, decoupling "who owns the socket" from "who wants to send." For broadcasts, where subscribers to one channel are scattered across many gateway nodes, a pub/sub broker underneath (Redis Pub/Sub, Kafka, NATS) lets a message be published once while every gateway node subscribes only to the topics its local clients care about and re-delivers to local sockets — in Slack's flow this reaches millions of clients worldwide in roughly 500ms. Sharding bounds the blast radius further: Discord requires sharding past 2,500 guilds per connection (recommending roughly 1,000 guilds per shard) so that a shard crash affects only a fraction of users. In practice, a single well-tuned server can hold hundreds of thousands of idle connections (500K+ has been cited with ~16GB of RAM and tuned OS limits), since idle connections cost mostly file descriptors and ~2–10KB of memory each — the real ceiling is usually message throughput and fan-out cost, which is why Discord's gateway optimization focused on reducing per-message dispatch cost (batched dispatch, disabling Nagle's algorithm, async tasks over a small reactor-thread pool) rather than simply adding RAM.

Popular tools: Slack's architecture (Envoy edge proxy → Gateway Servers → Channel Servers, with Consul for service discovery); Discord's Gateway (guild-based sharding, etcd for voice-server discovery); the generic building blocks used to construct one of these yourself — Redis for the connection registry and Pub/Sub, Kafka/NATS for durable high-throughput fan-out, Socket.IO's Redis adapter, Django Channels; and managed alternatives (Ably, Pusher, PubNub) that absorb this entire layer of complexity.

When to use it
Running WebSockets in production at meaningful concurrency — tens of thousands or more simultaneous connections — where a message needs to reach a specific user or room's members regardless of which server they happen to be connected to: chat platforms, multiplayer backends, live-collaboration products spanning more than one server. At small scale (a single server, or a few servers where simple sticky sessions suffice) defer the registry/pub-sub investment, and if you don't want to own any of this, reach for a managed service like Ably, Pusher, or PubNub instead.
ProsCons
  • Scales persistent connections horizontally to millions of concurrent users
  • Cleanly isolates the stateful-connection problem from the rest of the stack
  • Sharding and regional deployment bound blast radius and improve latency
  • Materially more operational complexity — a connection registry and pub/sub backplane to run and monitor
  • A gateway node crash disconnects every client pinned to it at once
  • A registry outage breaks targeted message delivery
  • Requires careful client-side reconnect/resync logic

Server-Sent Events (SSE)

Server-Sent Events (part of the HTML5/WHATWG standard) provide one-way, server-to-client streaming over a plain, long-lived HTTP connection, using the text/event-stream content type and the browser's native EventSource API. The client opens an ordinary GET request; instead of closing the response, the server keeps it open and streams text-formatted events — data:, event:, and id: fields — which EventSource parses as they arrive. Because each event can carry an id, a dropped connection triggers the browser to automatically reconnect and send a Last-Event-ID header, letting the server resume the stream exactly where it left off with no application code required on the client.

SSE is unidirectional by design: the server can push data continuously, but anything flowing client-to-server needs a normal separate HTTP request. Because it's built on plain HTTP/1.1 or HTTP/2 with no protocol upgrade, it passes transparently through most proxies and firewalls that block WebSocket upgrades, and — since the underlying transport is still stateless HTTP — any server instance can pick up a reconnecting client, so it scales with ordinary HTTP autoscaling and needs no sticky sessions or connection registry at all.

Popular tools: Browser-native EventSource; heavily used today for LLM/AI token-streaming responses, live notification feeds, and stock tickers; supported out of the box by most web frameworks, since implementing it server-side is just holding an HTTP response open.

When to use it
Live dashboards, activity and notification feeds, tickers, progress bars, and streaming AI/LLM responses — anywhere the server pushes updates but the client doesn't need to talk back on the same channel. Reach for SSE when you want reconnection "for free," want to avoid standing up a stateful WebSocket gateway tier, or know that some of your users sit behind corporate networks that block WebSocket upgrades but allow ordinary HTTPS.
ProsCons
  • Much simpler than WebSockets — no upgrade handshake, no custom reconnect/resume logic
  • Plays nicely with existing load balancers, proxies, and CDNs
  • Naturally stateless-friendly, scales with ordinary HTTP autoscaling
  • One-directional only — a separate request is needed for client-to-server data
  • Text-only payloads
  • Per-domain connection limits under HTTP/1.1 (mitigated by HTTP/2 multiplexing)

Long Polling / Short Polling

Long and short polling are older, HTTP-native techniques for approximating real-time updates from before WebSockets and SSE were widely available, where the client repeatedly asks "anything new?" instead of the server pushing updates unprompted. Short polling has the client request on a fixed interval, with the server responding immediately every time whether or not there's anything new — simple to implement, but wasteful, and latency is bounded by however long the polling interval is. Long polling instead has the client send a request that the server holds open, without responding, until new data becomes available or a timeout is hit; as soon as the server responds, the client immediately sends another request, so there is effectively always one request "pending" — this gives much lower latency and far fewer wasted round trips than short polling, while still using nothing but plain HTTP request/response semantics.

Both variants run over plain HTTP/1.1 with zero special infrastructure, which is their main appeal. The trade-off is that each long-polling request that's held open still consumes a server thread or connection slot for as long as it waits, and both approaches are fundamentally less efficient than a persistent connection for anything beyond occasional updates.

Popular tools: Historically the basis of Comet-style chat implementations; today mainly seen as a fallback transport — Socket.IO and SockJS transparently fall back to long polling when a WebSocket connection can't be established (for example, blocked by a firewall); AWS SQS's long-polling mode for queue consumption is an intentional, simple design choice rather than a fallback.

When to use it
As an automatic fallback when WebSockets or SSE aren't available on the network path; for low-frequency update scenarios where simplicity matters more than efficiency (checking job or batch status, polling for a long-running task's completion); or when you deliberately want at-most-one-request-in-flight semantics without managing any persistent connection state.
ProsCons
  • Works everywhere plain HTTP works, no special infrastructure required
  • Trivial to implement and debug
  • Degrades gracefully in restrictive network environments
  • Fundamentally less efficient than WebSockets/SSE for frequent updates — repeated HTTP overhead
  • Each held-open long-polling request ties up server resources while waiting
  • Higher latency than a persistent push-based connection

WebRTC

WebRTC is a set of W3C/IETF-standardized APIs and protocols for real-time audio, video, and arbitrary data exchange directly between clients — peer-to-peer — rather than routed through an application server, making it the odd one out on this page: the channel is fundamentally client-to-client, not client-to-server. Before any media or data can flow directly, the two peers need to find each other and agree on parameters through signaling, a step WebRTC deliberately leaves to the application (commonly carried over a WebSocket) to exchange SDP offers/answers and ICE candidates.

Establishing a direct connection across the real internet, where most clients sit behind NAT, requires STUN (which tells a client its own public IP and port), ICE (the framework that gathers and tries candidate connection paths), and TURN — a relay server used as a last resort when a direct path can't be established, at the cost of extra latency and bandwidth since traffic is now relayed rather than truly peer-to-peer. Once connected, encrypted media (SRTP) and/or data (RTCDataChannel) flow directly between the peers or through the TURN relay. Pure mesh peer-to-peer doesn't scale past a handful of participants, which is why group calls in practice route through a media relay — Discord, for instance, runs group voice/video through a homegrown Selective Forwarding Unit (SFU) rather than pure P2P or standard ICE, simplifying NAT traversal and hiding participants' IPs from each other, at the scale of 850+ voice relay servers across 13 regions serving 2.6M+ concurrent voice users.

Popular tools: Google's libwebrtc (used by Chrome and many native SDKs); Discord's customized stack with a homegrown SFU; Zoom and Google Meet (WebRTC-derived, via SFU); coturn (open-source STUN/TURN server); and mediasoup, Janus, LiveKit, and Jitsi as open-source SFU/media-server frameworks.

When to use it
Video/voice calling, live conferencing, in-browser screen sharing, and real-time collaborative tools that need peer-to-peer data channels. Not the right tool for typical chat text, notifications, or general data sync — those should use WebSockets or SSE, since WebRTC's infrastructure cost (signaling, STUN, and especially provisioning TURN relay capacity for worst-case NAT failure) only pays off for actual audio/video/data media exchange.
ProsCons
  • Lowest possible latency for direct media/data exchange when peer-to-peer is achievable
  • Reduces server bandwidth costs for 1:1 calls
  • Standardized and end-to-end encrypted by default (DTLS/SRTP)
  • Significant infrastructure complexity — signaling plus STUN and TURN relay capacity for worst-case NAT failure
  • Doesn't scale to large groups without an SFU/MCU
  • Purpose-built for audio/video/data, not general application messaging

gRPC / HTTP/2 Streaming

gRPC is a high-performance RPC framework built by Google that runs over HTTP/2 and uses Protocol Buffers for schema-defined, binary-encoded messages, supporting four call patterns — including full bidirectional streaming — all multiplexed over a single HTTP/2 connection. It leans on HTTP/2's native multiplexing and framing to let client and server exchange a continuous sequence of typed, Protobuf-encoded messages on a single logical call, with either side able to keep sending after the call starts — similar in spirit to a WebSocket's full-duplex behavior, but layered on RPC semantics (defined service methods, typed messages, deadlines, cancellation, flow control) rather than raw framed bytes. A single .proto file defines the service contract once and generates client/server stubs across languages.

Binary Protobuf encoding is more compact and CPU-efficient than JSON over a WebSocket, and the generated, strongly typed contracts cut down on cross-language integration bugs. The significant limitation is browser support: using gRPC from a browser requires gRPC-Web plus a translating proxy, and gRPC-Web does not support client-streaming or bidirectional streaming in-browser — only server streaming — which is a real gap versus a native WebSocket for a browser client that genuinely needs to stream both ways.

Popular tools: gRPC itself (Google) for service-to-service microservice communication; native gRPC support in Envoy/Istio meshes; Google Cloud APIs; and gRPC-Web paired with an Envoy proxy for the limited browser use cases it supports.

When to use it
Service-to-service (backend-to-backend) real-time or streaming communication in a polyglot microservices architecture that wants a strongly typed contract; mobile app-to-backend streaming where you control the client SDK; and AI/ML inference or data pipelines needing efficient bidirectional streaming between services. Choose WebSockets instead when the client is a browser needing genuine bidirectional streaming, when infrastructure along the path doesn't fully support HTTP/2, or when you want the simpler, more universally supported option.
ProsCons
  • Wins on throughput/latency for high-volume structured data via multiplexing and binary encoding
  • Strong typing and codegen reduce cross-language integration bugs
  • Built-in deadlines, cancellation, and flow control
  • Not natively browser-friendly — needs gRPC-Web plus a proxy, with real streaming limits in-browser
  • Requires full HTTP/2 support from every load balancer/proxy in the path
  • More schema and codegen setup overhead than opening a plain WebSocket
