Big-Data Batch & Stream Processing

Overview

Big-data processing is about running computation across datasets or event volumes too large, too fast, or too continuous for a single machine — historically split into two worlds: batch processing (crunch a large, bounded dataset on a schedule) and stream processing (react to unbounded events as they arrive). This page traces how the dominant compute engine evolved from Hadoop's disk-based MapReduce, to Spark's in-memory unification of batch/SQL/streaming/ML, to Flink's purpose-built low-latency streaming, then closes with the architectural question every data platform eventually faces: how do you combine batch's accuracy with streaming's freshness — Lambda's two-layer approach, or Kappa's single-pipeline alternative?

Apache Hadoop

Apache Hadoop is the open-source framework that established distributed storage and batch processing of very large datasets across clusters of commodity hardware — the foundational big-data platform, originating at Yahoo and inspired by Google's GFS and MapReduce papers. It bundles three components: HDFS for storage, MapReduce for processing, and YARN for cluster resource management.

HDFS follows a master/slave design: a single NameNode holds filesystem metadata in memory while many DataNodes store the actual 128MB data blocks, replicated three ways by default and spread rack-aware for fault tolerance — DataNodes heartbeat to the NameNode, and missed heartbeats trigger re-replication elsewhere (modern deployments add NameNode high availability via an active/standby pair). MapReduce processes data through a Map phase (transform into key-value pairs), a shuffle/sort, and a Reduce phase (aggregate values sharing a key), materializing every intermediate stage to disk — which makes it highly fault-tolerant, since a failed task simply re-runs from persisted input, but slow for multi-step or iterative jobs, since each step pays a full disk-write/read/network-shuffle cost. YARN, introduced to decouple resource management from MapReduce-specific job logic, uses a cluster-wide ResourceManager to allocate CPU/memory, a per-node NodeManager to launch and monitor containers, and a per-application ApplicationMaster to negotiate resources and coordinate tasks — this let Spark, Hive, and Tez run as YARN applications sharing the same cluster instead of being locked to MapReduce alone.

Popular tools: Cloudera/Hortonworks (merged), Amazon EMR, Google Dataproc, Azure HDInsight; ecosystem projects Hive, HBase, Pig, Sqoop, Oozie.

When to use it
Legacy environments already invested in the Hadoop ecosystem (HDFS + Hive + HBase); pure, ultra-large batch ETL where cost-per-TB matters more than latency and the job is simple enough that MapReduce's rigidity isn't a bottleneck; anywhere still needing HDFS specifically as durable, rack-aware, replicated storage underneath other engines. Rarely the first choice for new greenfield projects — new big-data work typically starts with Spark or a cloud-native lakehouse over object storage instead.
ProsCons
  • Mature, battle-tested fault tolerance
  • Cheap commodity storage at massive scale
  • Strong throughput for write-once/read-many workloads
  • MapReduce's disk-heavy model is slow for iterative/interactive jobs
  • Verbose, low-level programming model versus SQL/DataFrame APIs
  • Costlier on-prem cluster operations versus elastic cloud object storage + compute

Apache Spark

Apache Spark is a unified, general-purpose distributed data-processing engine that performs in-memory computation across a cluster — covering batch ETL, SQL, streaming, machine learning, and graph processing on one platform. It has largely superseded Hadoop MapReduce as the default big-data compute engine, mainly by fixing MapReduce's disk-bound weakness.

The foundational abstraction is the RDD (Resilient Distributed Dataset) — an immutable, partitioned collection built through a lineage of deterministic transformations; fault tolerance comes from replaying that lineage rather than restoring from a replica, and Spark keeps intermediate results in memory (spilling to disk only under pressure), which is why it dramatically outperforms MapReduce on iterative workloads like ML training loops or graph algorithms. Execution is lazy — transformations build a DAG and nothing runs until an action triggers it, enabling whole-pipeline optimization. A Driver runs the user's program and schedules tasks across Executors (worker processes holding cached partitions), with a Cluster Manager — YARN, Kubernetes, Spark's own Standalone manager, or local — allocating the actual resources. Spark SQL/DataFrames layer a higher-level, schema-aware API on top of RDDs, optimized by the Catalyst query optimizer and the Tungsten execution engine, while Structured Streaming models a stream as an unbounded, continuously appended table and executes it as a sequence of small micro-batches — reusing the same DataFrame/SQL APIs as batch, but bounding latency to hundreds of milliseconds or seconds rather than true per-event processing.

Popular tools: Databricks (built by Spark's original authors), Amazon EMR, Google Dataproc, Azure Synapse/HDInsight; commonly paired with Delta Lake, Apache Iceberg, or Apache Hudi as the lakehouse table format.

When to use it
ETL pipelines that read raw data from a lake, clean/join/aggregate it, and write curated tables; large-scale data transformation too big for one machine; feature engineering for ML at scale; iterative analytics/ML training that scans the same dataset repeatedly, where in-memory caching avoids MapReduce's repeated disk I/O; and near-real-time (not hard real-time) streaming via Structured Streaming when a few hundred ms to seconds of latency is acceptable and the team wants to reuse the same SQL/DataFrame code as batch. For true low-latency per-event processing, prefer Flink.
ProsCons
  • Much faster than MapReduce for iterative/interactive workloads
  • One engine covers batch/SQL/streaming/ML, reducing tooling sprawl
  • Strong ecosystem and connectors (S3, HDFS, Kafka, JDBC, Delta/Iceberg/Hudi)
  • More memory-hungry/expensive than lean disk-based batch for very simple one-pass ETL
  • Real JVM tuning learning curve (GC, memory/executor sizing, shuffle config)
  • Micro-batch streaming model can't match a purpose-built engine's sub-second per-event latency

Apache Flink

Apache Flink is a distributed stream-processing engine built for continuous, unbounded data — true event-at-a-time (not micro-batch) execution with strong event-time semantics and exactly-once state consistency. It also supports batch processing, treated as a bounded stream, but is streaming-first by design, which is the key architectural difference from Spark Structured Streaming.

Flink processes each event as it arrives through a pipelined dataflow graph rather than collecting events into small batches, which is why it typically achieves tens-of-milliseconds latency versus Spark's hundreds of milliseconds to seconds. It distinguishes event time (when something actually happened) from processing time (when it was observed); watermarks assert that no more events earlier than a given point should arrive, letting Flink correctly trigger time-based computations even with late or out-of-order data. Operators maintain state across events — in memory or in RocksDB for very large state — managed as a first-class, fault-tolerant part of the job, with exactly-once guarantees delivered via checkpointing based on the Chandy-Lamport distributed snapshot algorithm: periodic consistent snapshots of operator state and stream position let Flink restore and replay from the last checkpoint on failure. Flink also supports flexible windowing (tumbling, sliding, session) and complex event processing (CEP) for pattern detection.

Popular tools: AWS Managed Service for Apache Flink, Ververica Platform (Flink's creators), Confluent Cloud for Apache Flink, Alibaba Cloud Realtime Compute; widely used at Alibaba, Uber, and Netflix for high-scale, low-latency streaming.

When to use it
Sub-second/tens-of-milliseconds latency needs (real-time fraud detection, ad-tech bidding, real-time monitoring/alerting, dynamic pricing); significantly out-of-order data requiring rigorous event-time correctness (IoT with variable network delay); or complex, long-lived stateful stream processing — sessionization, pattern detection, continuous joins — with strict exactly-once guarantees, where streaming is the primary workload rather than one part of a broader batch pipeline. Choose Spark Structured Streaming instead when the team already has a Spark-centric batch stack and wants to reuse the same code and skills, and seconds-level latency is fine.
ProsCons
  • Lowest latency true streaming among mainstream engines
  • Superior out-of-order/late-event handling via watermarks
  • Strong exactly-once state consistency
  • Steeper learning curve — event time, watermarks, and stateful operators demand deeper expertise than Spark's batch-like API
  • Smaller ecosystem and hiring pool than Spark
  • Operationally more specialized (state-backend tuning, checkpoint sizing)

Batch vs. Stream Processing & Lambda vs. Kappa Architecture

Batch processing takes a large, bounded dataset and processes it all at once, typically on a schedule — optimized for throughput and completeness over latency, since the whole dataset is available before the job even starts (a nightly job rebuilding a reporting table from the day's transaction logs is the classic example). Stream processing instead processes a continuous, unbounded sequence of events as they arrive, computing incremental, low-latency results without waiting for "all" the data, because there is no "all" — a rolling five-minute fraud-risk score updated as transactions stream in. Most real platforms need both, which raises the architectural question of how to combine them.

Lambda runs a batch layer and a speed layer side by side, merged at serving time; Kappa replaces both with one streaming pipeline fed by a replayable log, reprocessing history by replaying the log instead of running a separate batch layer.

Lambda Architecture tries to get both batch's correctness and streaming's low latency by running three layers side by side: a batch layer (Hadoop/Spark) periodically recomputes accurate, complete views over full history; a speed/streaming layer (Flink/Spark Streaming) processes only recent data in real time for a low-latency, approximate/incremental view that fills the gap until the batch layer catches up; and a serving layer merges both views for querying. The catch is that the same business logic typically has to be implemented twice — once per engine — which doubles development/maintenance effort and risks behavioral divergence between the two paths; this "two codebases" problem is the primary complaint that motivated Kappa.

Kappa Architecture, proposed by Kafka co-creator Jay Kreps in 2014's "Questioning the Lambda Architecture," eliminates the separate batch layer entirely: everything, including historical reprocessing and backfill, runs through a single streaming pipeline. The key insight is that a durable, replayable log with long retention (Kafka) is your batch layer — to reprocess history or fix a bug, you replay the log from an earlier offset through the same (or an updated) streaming job and cut over once it catches up, giving one codebase and one processing model to operate. The trade-off is that this requires a stream engine and log powerful enough to handle both live traffic and full historical reprocessing efficiently — increasingly feasible as Flink, Kafka Streams, and Spark Structured Streaming have matured — though some organizations still keep a dedicated batch layer for very large-scale historical analytics even while defaulting to Kappa for operational pipelines.

Popular tools: Lambda-style stacks — Hadoop/Spark for the batch layer paired with Flink/Spark Streaming for the speed layer. Kappa-style stacks — Kafka as the durable, replayable log feeding a single Flink, Kafka Streams, or Spark Structured Streaming job.

When to use it
Batch-only for reporting/analytics that can tolerate hours of staleness — daily revenue dashboards, monthly billing — the simplest, cheapest, most mature option. Stream-only/Kappa as the modern default when low latency matters and the team already has streaming infrastructure (Kafka + Flink/Spark Structured Streaming) — real-time personalization, fraud detection, operational monitoring, event-driven microservices. Lambda for legacy or specialized cases where the batch and speed layers are already on very different tech that's hard to unify, or where an organization wants an independently computed batch "audit" path alongside a fast approximate streaming path — increasingly rare as a first choice for new systems given the maintenance burden.
ProsCons
  • Lambda: combines an accurate full-history batch view with a low-latency approximate streaming view
  • Kappa: one codebase and one processing model to build, test, and operate
  • Kappa: simpler operationally — no need to keep two engines' behavior in sync
  • Lambda: business logic must be implemented and maintained twice, risking behavioral divergence between layers
  • Kappa: requires a stream engine/log powerful enough for both real-time load and full historical reprocessing
  • Kappa: very large-scale historical recomputation can still be more naturally expressed in a dedicated batch/warehouse engine
