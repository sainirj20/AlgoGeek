SYSTEM DESIGN — BUILDING UNITS

Security & Edge Protection

Overview

Security and edge protection is the set of building blocks that decide who gets in, how much traffic they're allowed to send, and how the system defends its own perimeter and secrets — typically enforced at an API gateway, CDN, or edge layer before a request ever reaches internal services. Authentication and authorization patterns establish identity and permissions at the door; rate limiting protects shared capacity from any single client, well-behaved or malicious; a WAF and DDoS protection defend the perimeter itself against attack traffic; and secrets management protects the credentials and keys every other layer depends on. None of these is a substitute for the others — production systems layer all four as defense in depth.

Authentication & Authorization Patterns (OAuth 2.0, JWT, SSO, API Keys)

Authentication and authorization are distinct concerns enforced at the system's boundary: authentication verifies who is making a request, authorization decides what they're allowed to do once verified. OAuth 2.0/2.1 is a delegation framework, not an identity protocol — a client obtains an access token from an authorization server via a grant flow (Authorization Code + PKCE for user-driven apps, Client Credentials for service-to-service calls) and then presents that token to a resource server on every request. OpenID Connect (OIDC) layers an ID token — a JWT representing identity — on top of OAuth 2.0, which is how OAuth-based systems actually handle authentication rather than just authorization. A JWT itself is a compact, self-contained, signed token (header.payload.signature) carrying claims like user ID, expiry, scopes, issuer, and audience; a resource server validates it locally against the issuer's published JWKS and checks exp/iss/aud without a network round trip back to the identity provider — that statelessness is exactly why JWT dominates authorization at microservice/gateway scale. SSO lets a user authenticate once with an identity provider and reach multiple downstream apps without re-entering credentials, via SAML (older, enterprise/XML) or OIDC (newer, JSON/REST); API keys are a simpler static credential identifying the calling application or tenant rather than an individual user, used where OAuth's flow complexity isn't warranted.

In practice, an API gateway commonly terminates and validates auth at the edge — checking a JWT signature, looking up an API key, validating mTLS — so downstream services trust an already-validated identity forwarded by the gateway instead of every service reimplementing auth from scratch. Token-based auth is stateless and horizontally scalable in a way server-side session cookies aren't, but that statelessness is also JWT's classic weakness: revoking a token before its natural expiry needs either short expiries paired with refresh tokens, or a blocklist/introspection call that reintroduces some statefulness.

The client obtains a signed JWT from the authorization server and presents it to the resource server, which validates the signature locally against the published JWKS instead of calling back to the identity provider on every request.

Popular tools: Identity providers — Auth0, Okta, AWS Cognito, Azure AD/Entra ID, Keycloak. API gateways enforcing these patterns — Kong, AWS API Gateway, Apigee, Envoy/Istio (also mTLS for service identity). Standards — OAuth 2.0/2.1, OIDC, SAML 2.0, JWT (RFC 7519), JWKS.

When to use it
Reach for OAuth2/OIDC plus SSO for consumer or enterprise apps needing delegated third-party access or centralized workforce identity. Use JWT for internal microservice/gateway-to-service authorization needing stateless, scalable validation. Use API keys for simple third-party/partner integrations, and mTLS for zero-trust internal service meshes. A common pattern combines short-lived access tokens with refresh tokens to balance JWT's revocation weakness against the benefits of statelessness.
ProsCons
  • Stateless, horizontally scalable validation (JWT) with no per-request identity-provider round trip
  • Centralized identity and one-time login improves UX and offboarding (SSO)
  • Flexible delegated-access model (OAuth2/OIDC)
  • OAuth2/OIDC flow complexity adds implementation overhead
  • JWTs are hard to revoke before natural expiry
  • API keys are coarse-grained and don't auto-expire unless designed to
  • SSO/IdP is a single high-value target — compromise has a broad blast radius

Rate Limiting / Throttling

Rate limiting caps how many requests a client — or the system as a whole — can make in a given time period, protecting shared capacity and mitigating abuse. Four algorithms cover almost every real-world case. Fixed window counting is the simplest: requests are counted in discrete, non-overlapping buckets (e.g., per minute), but it's exploitable at the boundary — a burst that straddles the edge of two windows can briefly double the effective rate. Sliding window limiting tracks requests over a continuously moving window instead of a fixed bucket, avoiding that boundary-burst problem; a log-based sliding window is precise but memory-heavy (it has to remember every request timestamp), while a counter-based sliding window approximates the same behavior in O(1) memory at the cost of a small amount of drift. Token bucket lets a bucket hold up to N tokens that refill at a fixed rate; every request consumes a token and is rejected once the bucket is empty — this naturally permits controlled bursting while still enforcing a steady average rate, which is why it's the default choice for most public APIs. Leaky bucket instead queues incoming requests and "leaks" (processes) them at a constant rate, dropping anything that overflows the queue — it guarantees smooth, constant output regardless of how bursty the input is, which matters when a downstream system genuinely can't absorb bursts at all.

Where the limit is enforced matters as much as which algorithm is used: it can live in a client SDK (client-side, cooperative but not enforceable against a malicious caller), at the API gateway/edge (the most common server-side enforcement point, stopping abusive traffic before it reaches application code), or in the application layer itself (finer-grained, but adds load to the service being protected). Limits are typically scoped per-user, per-API-key, per-IP, per-endpoint, or globally across the whole system, and in any horizontally scaled fleet, enforcement has to be centralized rather than per-instance — the standard pattern is a shared counter store like Redis, using atomic INCR/EXPIRE operations or a Lua script to keep the count-and-check step atomic across every node making the decision. A client over the limit typically gets back an HTTP 429 with a Retry-After header and often X-RateLimit-* headers indicating the current limit, remaining quota, and reset time.

Popular tools: Redis-backed custom limiters (Stripe, for example, runs a dedicated Redis Cluster purely for this); Kong's rate-limiting plugin, AWS API Gateway usage plans, the Envoy rate limit service, NGINX limit_req; Cloudflare Rate Limiting, Google Cloud Armor.

When to use it
Rate limiting protects public APIs from abuse, scraping, and retry storms; enforces tiered usage plans; protects downstream systems that have a hard capacity ceiling (favor leaky bucket or strict windowing there); and stops one noisy tenant from starving every other tenant on shared infrastructure. It's almost always paired with authentication so limits can be scoped per API key or user rather than just per IP, which is trivial to spoof or shared across many real users behind NAT.
ProsCons
  • Token bucket is flexible and burst-friendly — the industry-favorite default
  • Sliding window is accurate and fair across the boundary
  • Centralizing counters in Redis makes enforcement consistent across an entire fleet
  • Fixed window is exploitable at window boundaries
  • Log-based sliding window is memory-heavy at scale
  • Leaky bucket can add latency or drop bursts a token bucket would have allowed
  • Naive per-IP limiting is easy to spoof or unfairly penalizes shared IPs (NAT, corporate proxies)

Web Application Firewall (WAF) and DDoS Protection

A Web Application Firewall and DDoS protection cover two related but distinct threats at the edge: a WAF blocks application-layer (L7) attacks aimed at the web app itself — SQL injection, cross-site scripting — while DDoS protection absorbs and mitigates volumetric and protocol-level floods (L3/L4) as well as application-layer request floods. A WAF sits in the request path, typically at a reverse proxy or CDN edge, and inspects every request against a rule set: signature-based rules (the OWASP Top 10/Core Rule Set), rate-based rules, geo/IP reputation, and increasingly ML/behavioral anomaly detection — matching requests get blocked, challenged, or logged. Network/transport-layer DDoS protection (L3/L4) absorbs volumetric floods using massive distributed scrubbing capacity, largely automatically; application-layer DDoS (L7) instead mitigates request floods that look like legitimate traffic, using rate limiting, bot detection, and behavioral baselining. Two architectural patterns dominate: an integrated edge network like Cloudflare doing single-pass inspection at every point of presence, versus an assembled hyperscaler stack like AWS Shield + WAF + Firewall Manager + CloudFront + Route 53.

WAF rules commonly target the OWASP Top 10 categories, and bot management is a closely related capability that's often bundled with it. Robust setups layer L3/4 network scrubbing underneath L7 application-aware mitigation rather than relying on either alone, and managed WAF providers can push new rules globally within hours of a critical CVE disclosure — a speed advantage that's hard to replicate with a self-managed setup.

Network-level DDoS scrubbing absorbs volumetric floods, a WAF filters application-layer attacks against clean traffic on its way to the CDN/load balancer and app, while matched malicious requests are blocked or challenged before reaching origin.

Popular tools: Cloudflare (integrated WAF + DDoS + Bot Management); AWS WAF + Shield/Shield Advanced + Firewall Manager + CloudFront/Route 53; Google Cloud Armor, Azure WAF/DDoS Protection, Akamai, Imperva, F5; open-source ModSecurity + OWASP CRS.

When to use it
A WAF and DDoS protection are close to a baseline requirement for any internet-facing web application or API, not an optional extra. E-commerce, fintech, and other high-profile targets should invest in advanced/paid DDoS tiers backed by SLAs. Combine this layer with rate limiting and secrets/auth hardening for genuine defense in depth — a WAF alone won't stop a business-logic flaw or a zero-day without added behavioral detection.
ProsCons
  • Integrated edge-network model (Cloudflare) is simple with fast global rule rollout
  • Assembled cloud-services model is highly configurable and deeply integrated with the rest of the cloud
  • Cheaply reduces risk from known attack signatures
  • Integrated edge model is less granularly composable
  • Assembled cloud-services model needs more setup and tuning
  • Can false-positive; doesn't stop business-logic flaws or zero-days without behavioral augmentation

Secrets Management (HashiCorp Vault, AWS KMS/Secrets Manager)

Secrets management is a dedicated system for securely storing, distributing, rotating, and auditing access to sensitive credentials — database passwords, API keys, TLS certificates, encryption keys — instead of hardcoding them into config or source. A centralized secret store holds the secrets; applications authenticate to it using an IAM role, an AppRole, or a Kubernetes service account, and request secrets at runtime rather than reading them from a file baked into an image. Envelope encryption underpins most of these systems: a root/master key, often HSM-backed, encrypts data encryption keys, which in turn encrypt the actual secret values — the root key itself rarely has to touch data directly and can be rotated independently of everything it protects. Vault's dynamic secrets take this further, generating short-lived, on-demand credentials that auto-expire, shrinking the exposure window if one ever leaks; rotation for many secret types happens automatically on a schedule (AWS Secrets Manager auto-rotating RDS credentials, for instance) without any app redeployment.

KMS-type services manage cryptographic keys, while secret-manager-type services manage the secret values' lifecycle — in practice the two are combined, with a secret's actual value stored in a secrets manager but encrypted under a KMS key. Access control and audit logging provide fine-grained policies plus a full trail of who accessed what and when; versioning enables safe rollback if a rotation goes wrong. Delivery to workloads typically happens via a sidecar/init-container pattern (Vault Agent) or the Kubernetes External Secrets Operator, which keeps secrets out of image layers and out of git history entirely.

Popular tools: HashiCorp Vault (self-hosted/multi-cloud, most feature-rich — dynamic secrets, PKI issuance, transit encryption — but heavier to operate); AWS Secrets Manager (managed, simple, built-in rotation for RDS/Redshift); AWS KMS (centralized key management, envelope encryption, IAM-integrated); Azure Key Vault, Google Secret Manager, Kubernetes Secrets (not encrypted by default — needs pairing with one of the above), SOPS.

When to use it
Needed by any system handling database credentials, third-party API keys, TLS keys, or encryption keys — which is to say, essentially every production system. Reach for dynamic/short-lived secrets in high-security or regulated environments, use KMS specifically for encrypting data at rest (envelope encryption for buckets, databases, or individual fields), and use a managed secrets manager for straightforward cloud-native apps that want rotation without the operational overhead of running Vault. This layer is typically mandatory before a SOC2, PCI-DSS, or HIPAA audit.
ProsCons
  • Removes hardcoded credentials from code, images, and git history
  • Envelope encryption and dynamic secrets shrink the blast radius of a leak
  • Automatic rotation and full audit trails
  • Vault is powerful but operationally heavy to run reliably
  • Cloud-native managed services tie you to one cloud and are less feature-rich for exotic cases
  • Often needs multiple tools layered together (KMS + Vault/Secrets Manager + delivery mechanism) rather than one single choice
