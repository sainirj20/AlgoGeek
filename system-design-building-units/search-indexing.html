SYSTEM DESIGN — BUILDING UNITS

Search & Indexing

Overview

Search and indexing is about answering a fundamentally different question than a normal database query. A relational database or key-value store is built to find rows by an exact key or a narrow predicate; a search engine is built to rank a huge, messy collection of semi-structured or unstructured documents by how relevant each one is to a loosely specified query — "find me the best matches for these words," not "find me the row where id = 42." That shift in optimization target is why search systems have their own storage model, their own query execution flow, and their own scaling story, all covered below.

Search Engines / Inverted-Index Systems (Elasticsearch, OpenSearch, Solr)

A search engine — Elasticsearch, OpenSearch, Apache Solr — is a specialized engine optimized for full-text search, relevance ranking, and analytics over large, semi-structured or unstructured document sets, which is a fundamentally different optimization target than a transactional database built for exact-match lookups by primary key.

The core data structure is the inverted index: rather than mapping documents to the words they contain, it maps each unique term to the list of documents that contain it, along with position and frequency information. That inversion is what turns a full-text search into a fast lookup and intersection of postings lists instead of a document-by-document scan — searching for "red bicycle" becomes look up the postings list for "red," look up the postings list for "bicycle," and intersect them, rather than scanning every document's text.

Before anything is indexed or queried, an analysis (tokenization) pipeline breaks raw text into normalized tokens — lowercasing, stemming words to their root form, and stripping stop words — and critically, the exact same pipeline is applied to both the documents at index time and the query at search time, so "Running" in a document and "run" in a query can still match. Once candidate documents are found, relevance scoring ranks them: BM25, the modern default, scores a document higher when a query term appears frequently in that document (term frequency), appears rarely across the whole corpus (inverse document frequency, which rewards distinctive terms over common ones), and appears in a relatively short field (length normalization, so a match in a short title counts for more than the same match buried in a long article).

Elasticsearch, OpenSearch, and Solr are all built on Apache Lucene under the hood, which stores the index as a collection of immutable segments. New documents are written to an in-memory buffer and periodically flushed into a new segment, and background merges combine smaller segments into larger ones to keep search efficient — this segment-based design is what gives near-real-time search: a newly indexed document typically becomes searchable within about a second, rather than instantly or only after a full rebuild.

Horizontal scale comes from sharding: an index is split into primary shards, each an independent Lucene index, distributed across nodes in the cluster, and each primary has one or more replica shards for both fault tolerance and additional parallel read throughput. A query doesn't hit just one shard — a coordinating node scatters the query out to a primary (or replica) of every relevant shard in parallel, each shard scores and returns its own top matches, and the coordinating node gathers those partial result sets, merges and re-ranks them, and returns the final combined page of results to the client. This scatter-gather flow is what lets a single query search across billions of documents spread over many machines in roughly the time it takes the slowest shard to respond.

The inverted index maps each term to the documents (postings) containing it, turning full-text search into a fast lookup-and-intersect rather than a document-by-document scan.
A query scatters from the coordinating node to a primary or replica of every shard in parallel and gathers the partial results back for merging — the same fan-out/fan-in shape as sharding elsewhere in this section, applied to search.

Popular tools: Elasticsearch (the most widely adopted, core of the Elastic Stack), OpenSearch (the AWS-led open-source fork, API-compatible, adding agentic/vector search), Apache Solr (older, enterprise-search-oriented, uses ZooKeeper for SolrCloud coordination, strong Tika-based rich-document ingestion), and hosted/lightweight instant-search alternatives like Algolia, Typesense, and Meilisearch.

When to use it
Product search, log and event search, e-commerce search-with-facets, or any free-text "search box" that needs relevance ranking or typo tolerance, plus aggregating across terabytes of semi-structured data that a relational database can't efficiently index. It is not the right choice as a primary transactional store or for simple key lookups — a key-value store or a plain relational index is cheaper and simpler there.
ProsCons
  • Extremely fast full-text and analytical queries at scale
  • Flexible query DSL — fuzzy match, phrase match, aggregations/faceting, geo-queries, vector/kNN search
  • Strong ecosystem and tooling
  • Not ACID — no cross-shard joins, denormalization required
  • Eventual consistency for search visibility (near-real-time, not immediate)
  • Heavy operational overhead (JVM/heap/shard tuning)
