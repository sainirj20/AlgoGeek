SYSTEM DESIGN — BUILDING UNITS

Data Storage & Database Patterns

Overview

Every system design interview eventually comes down to "where does the data live, and why." This page covers the storage models and distribution patterns you choose between — not specific vendor comparisons (see the dedicated Database Types section for deep per-product profiles of MySQL, MongoDB, Cassandra, and friends). Here, the focus is the architectural decision itself: which model fits the data shape and access pattern, and how storage scales and stays available once a single machine isn't enough.

Relational Databases (RDBMS / SQL)

A relational database organizes data into fixed-schema tables (rows and columns) related via keys, queried with SQL. Data is normalized to reduce redundancy; a query planner turns declarative SQL into an execution plan (index scans, joins, sorts). Transactions are governed by ACID guarantees, typically implemented via write-ahead logs and concurrency control (e.g. MVCC). PostgreSQL forks a process per connection (strong isolation, more memory overhead); MySQL/InnoDB uses threads per connection (cheaper at higher concurrency). Indexes (B-trees, hash indexes, GiST/GIN) accelerate lookups at the cost of write overhead and storage.

Popular tools: PostgreSQL, MySQL/MariaDB, Oracle Database, Microsoft SQL Server, Amazon Aurora, Google Cloud SQL/AlloyDB, CockroachDB, Google Spanner. See the Relational Databases and NewSQL Databases pages for individual product profiles.

When to use it
Data is highly structured and relationships matter (orders/customers/inventory); you need multi-row/multi-table transactional integrity (banking ledgers, order processing); strong consistency is a hard requirement; the team needs flexible ad hoc querying. Default choice for most business applications unless a specific scale or data-shape problem points elsewhere.
ProsCons
  • Strong consistency and mature ecosystem
  • Powerful ad hoc querying (joins, subqueries, CTEs)
  • Enforced data integrity via constraints
  • Excellent for multi-table transactions
  • Harder horizontal write scaling
  • Costly schema changes at scale
  • Slower join-heavy queries on very large datasets

NoSQL — Key-Value Stores

The simplest NoSQL model: data is stored and retrieved as a value associated with a unique key, with no required schema for the value, accessed via simple GET/PUT/DELETE. In-memory stores (Redis) keep the full dataset in RAM via a largely single-threaded event loop; managed disk-backed stores (DynamoDB) partition data by hashing the key and replicate across nodes for consistent single-digit-millisecond latency at scale. Horizontal scaling is via partitioning/sharding on the key (consistent hashing is common) plus replication.

Popular tools: Redis (and forks Valkey, Dragonfly), Amazon DynamoDB, Memcached, Riak, Aerospike, etcd. See the Key-Value Stores page for individual product profiles.

When to use it
Caching layers (session storage, API response caching), leaderboards/counters, rate limiting, real-time pub/sub, shopping carts, user session stores — anywhere needing single-digit-millisecond lookups by a known key at massive scale. A very common pattern: Redis as a hot cache in front of DynamoDB or a relational DB as the durable source of truth (cache-aside).
ProsCons
  • Lowest latency of any storage tier
  • Trivially horizontal to scale
  • Simple operational model
  • No joins, limited query flexibility
  • In-memory variants bound dataset size by RAM

NoSQL — Document Stores

Stores data as semi-structured "documents" (typically JSON/BSON), where each document can have its own structure, grouped into collections. MongoDB organizes documents into collections with secondary indexes (compound, geospatial, text). High availability comes from replica sets — a primary accepts writes and replicates an oplog to secondaries, which can serve reads and take over via automatic election. Horizontal scale comes from sharding: a shard key partitions data across shards, a router (e.g. mongos) directs requests, and config servers store cluster metadata.

Popular tools: MongoDB, Amazon DocumentDB, Couchbase, Firebase/Firestore, Azure Cosmos DB. See the Document Databases page for individual product profiles.

When to use it
Content management systems, product catalogs with varying attributes, user profiles, mobile/web app backends mapping closely to JSON, rapid-prototyping projects with evolving schemas. Less ideal for complex multi-entity joins or strict referential integrity across many entity types.
ProsCons
  • Schema flexibility speeds iterative development
  • Natural JSON mapping, good horizontal scale
  • Embedding avoids costly joins
  • Weaker enforced consistency without discipline
  • Denormalization creates update-anomaly risk
  • Shard-key decision is hard to reverse

NoSQL — Column-Family / Wide-Column Stores

Stores data in tables where rows can have a dynamic, sparse set of columns grouped into "column families," optimized for very high write throughput across many nodes. Cassandra uses a masterless, ring-based architecture (Dynamo-inspired distribution + Bigtable-inspired storage): consistent hashing assigns each node a token range, gossip handles membership, and an LSM-tree engine optimizes sequential writes — replication factor is configurable, and consistency is tunable per query (ONE, QUORUM, ALL). HBase instead uses a master-slave architecture on HDFS with strong/immediate consistency.

Popular tools: Apache Cassandra, ScyllaDB, Apache HBase, Google Cloud Bigtable. See the Wide-Column / Column-Family Stores page for individual product profiles.

When to use it
Massive-scale write-heavy workloads — logging/event ingestion, IoT sensor data, high-cardinality time-series data — and any system writing huge volumes across geographically distributed data centers with high availability (Cassandra's classic use case).
ProsCons
  • Massive write scalability
  • Multi-datacenter replication built in
  • No single point of failure (Cassandra)
  • Very limited query flexibility, no joins
  • Eventual consistency needs careful handling
  • Operational complexity (JVM tuning, compaction, repair)

NoSQL — Graph Databases

Purpose-built to store and query entities (nodes) and relationships (edges) as first-class citizens. Uses a property graph model with index-free adjacency — relationships are stored as direct physical pointers, so traversing to a connected node is a pointer lookup rather than a join, which is why multi-hop traversal queries run dramatically faster than equivalent multi-join SQL as depth increases. Query languages include Cypher (Neo4j), Gremlin (Neptune/JanusGraph), and SPARQL (RDF-style).

Popular tools: Neo4j, Amazon Neptune, ArangoDB, JanusGraph, TigerGraph. See the Graph Databases page for individual product profiles.

When to use it
Fraud detection/AML (tracing rings of connected accounts), recommendation engines, social networks, knowledge graphs, authorization graphs (who can access what, transitively), supply-chain topology. Avoid as the primary store for simple CRUD apps or heavy aggregate reporting.
ProsCons
  • Extremely fast relationship-heavy queries
  • Intuitive modeling for networked data
  • Strong pattern/fraud detection
  • Poor fit for simple aggregate/tabular analytics
  • Harder horizontal scaling (relationships span shards)
  • Smaller ecosystem

Time-Series Databases

Optimized specifically for data points indexed by time — metrics, events, sensor readings — where the dominant pattern is appending new time-stamped data and querying/aggregating over time ranges. Data is modeled as timestamp + tags (filterable metadata) + fields (measured values). Storage engines are columnar/LSM-based with heavy compression (deltas between consecutive points are small), plus automatic downsampling and retention policies.

Popular tools: InfluxDB, TimescaleDB, Prometheus, QuestDB, Amazon Timestream. See the Time-Series Databases page for individual product profiles.

When to use it
Infrastructure/application monitoring, IoT sensor fleets, financial market tick data, DevOps dashboards. Choose InfluxDB/QuestDB for purpose-built high-ingest scenarios; TimescaleDB when you want time-series without leaving the Postgres ecosystem.
ProsCons
  • Massively more efficient than an RDBMS for time-stamped data
  • Purpose-built aggregation saves app-level work
  • Not designed for relational/transactional workloads
  • High-cardinality tags can degrade performance if modeled poorly

Data Warehouses vs. Data Lakes vs. Lakehouses

Three converging approaches to large-scale analytical storage. A data warehouse stores structured, curated data optimized for fast SQL analytics ("schema-on-write"); Snowflake fully decouples storage from multiple independent compute clusters, BigQuery is fully serverless (billed by bytes scanned). A data lake stores raw files (Parquet, ORC, Avro, JSON) directly on cheap object storage, deferring structure until read time ("schema-on-read"). A lakehouse adds an open table format on top of object storage — Delta Lake or Apache Iceberg — bringing ACID transactions, schema evolution, and "time travel" directly to files in object storage.

Popular tools: Warehouses — Snowflake, BigQuery, Redshift. Lakes — Amazon S3, ADLS, GCS, HDFS. Lakehouse formats — Delta Lake, Apache Iceberg, Apache Hudi. See the Specialized & Legacy Database Types page for Snowflake/BigQuery/Redshift profiles.

When to use it
Use a warehouse for classic BI/reporting with structured data and many concurrent analysts. Use a lake as the low-cost landing zone for raw/ML training data. Use a lakehouse to serve both BI and ML/data-science from one copy of data — increasingly the default for new greenfield analytics platforms.
ProsCons
  • Warehouse: fast, governed BI performance
  • Lake: cheapest, most flexible, any data type
  • Lakehouse: single source of truth for BI + ML
  • Warehouse: pricier, weaker for unstructured/ML data
  • Lake: risks becoming an unusable "data swamp" without governance
  • Lakehouse: newer, more complex ecosystem

Object Storage

Manages data as discrete "objects" (data + metadata + unique identifier) accessed over HTTP(S), rather than a file-system hierarchy or raw disk blocks. Objects live flat within a "bucket" namespace, retrieved by key via REST. Amazon S3, as a reference architecture, is built from hundreds of internal microservices and replicates data across a minimum of three Availability Zones by default, engineered for 99.999999999% ("11 nines") durability — with storage tiering (Standard, Infrequent Access, Glacier) and lifecycle policies.

Popular tools: Amazon S3, Google Cloud Storage, Azure Blob Storage, MinIO, Cloudflare R2.

When to use it
Storing/serving unstructured data at scale (images, video, backups, logs, static assets), and as the foundation under data lakes/lakehouses. Not right for a database's primary transactional volume (use block storage) or workloads needing POSIX semantics (use file storage).
ProsCons
  • Near-infinite scale, very low cost per GB
  • Extremely high durability
  • Ideal backing store for data lakes/lakehouses
  • Not designed for low-latency random read/write
  • No POSIX file-locking semantics
  • Higher per-request latency than block/local storage

Database Sharding / Partitioning

The primary technique for horizontally scaling a database beyond one server's limits: splitting a large dataset across multiple nodes ("shards") so no single machine stores or serves the entire dataset. Range-based partitioning splits by contiguous ranges of the shard key (good for range queries, but can create hot spots on always-increasing IDs). Hash-based applies a hash function for even distribution (inefficient range queries; consistent hashing minimizes data movement on rebalance). Directory-based uses a lookup service to map keys to shards (maximum flexibility, but the directory itself becomes critical infrastructure). The shard key is the single most important decision — it must appear in the most common queries' WHERE clause, or queries degrade into expensive scatter-gather.

The three core sharding strategies — each trades off query flexibility against rebalancing complexity differently.

Popular tools: Native sharding in MongoDB, Cassandra, Elasticsearch; Vitess (MySQL), Citus (Postgres); auto-sharding NewSQL like CockroachDB, Spanner, YugabyteDB.

When to use it
When a single instance can no longer handle data volume/throughput after exhausting vertical scaling and read replicas; multi-tenant SaaS sharding by tenant ID; globally distributed apps needing data locality. Avoid premature sharding — exhaust simpler options first.
ProsCons
  • Near-linear scalability of storage/throughput
  • Smaller working sets per node
  • Expensive/impossible cross-shard joins and transactions
  • Risky rebalancing/resharding
  • Shard key is very hard to change later

Database Replication & the CAP Theorem

Replication maintains multiple copies of data across nodes for redundancy, availability, and read scalability. Three topologies dominate:

Leader-follower (simple, one writer), multi-leader (local writes, needs conflict resolution), and leaderless/quorum (Dynamo-style, W+R>N) replication.

Leader-follower (single-leader): one leader accepts all writes and propagates to followers, which can serve reads and act as failover targets — default in MongoDB replica sets, PostgreSQL/MySQL streaming replication. Multi-leader: multiple nodes accept writes independently and replicate to each other — useful for multi-datacenter low-latency local writes, but requires conflict resolution (last-write-wins, vector clocks, CRDTs). Leaderless (quorum-based): any node accepts a write; clients use quorum math (W + R > N) to guarantee overlap between writers and readers — pioneered by Amazon Dynamo, used by Cassandra/Riak with tunable consistency per query.

CAP theorem & PACELC During a network Partition, a distributed system must choose between Consistency and Availability — this applies only during an actual partition, not as a permanent label on a database.
PACELC extension: even absent a partition (Else), systems trade off Latency vs. Consistency. Cassandra/Dynamo are PA/EL (favor availability/latency); HBase/Spanner lean PC/EC (favor consistency).

Popular tools: PostgreSQL/MySQL, MongoDB replica sets (leader-follower); Cassandra/DynamoDB/Riak (leaderless/quorum); CockroachDB/Spanner/YugabyteDB/etcd (Raft/Paxos strong consistency).

When to use it
Leader-follower for most standard OLTP needing read scaling and failover. Multi-leader for multiple active regions each needing fast local writes with tolerable/resolvable conflicts. Leaderless/quorum when availability under partition matters more than immediate consistency (shopping carts, session data, social feeds). Apply the CAP/PACELC lens whenever choosing a distributed store: can the use case tolerate stale reads (favor AP) or does it require guaranteed-fresh reads (favor CP — account balances, inventory, seat reservations)?
ProsCons
  • Fault tolerance, read scalability, disaster recovery
  • Geographic locality for global users
  • Leader-follower: write throughput capped by one leader
  • Multi-leader: conflict-resolution complexity
  • Leaderless: more complex client logic, eventual-consistency surprises
