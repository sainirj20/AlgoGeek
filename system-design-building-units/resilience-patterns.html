SYSTEM DESIGN — BUILDING UNITS

Resilience Patterns

Overview

Resilience patterns are the building blocks that keep a distributed system functioning — or at least degrading gracefully — when a downstream dependency slows down, errors out, or disappears entirely. Individually, each pattern addresses a narrow failure mode: stopping calls to a dependency that's clearly broken, spacing out retries so they don't pile onto an already-struggling service, isolating one dependency's problems from another's, and signaling upstream to slow down before memory runs out. In production these patterns are rarely used alone — they stack as layered decorators around a single call: a timeout defines what counts as a failure, retries (with backoff and jitter) absorb transient blips without amplifying load, a circuit breaker stops calling a consistently failing dependency, a bulkhead keeps that failure from starving resources needed for other calls, and backpressure ensures that even a slow-but-successful path doesn't overwhelm memory or queues further upstream. Libraries like resilience4j and Polly, and service meshes like Istio/Envoy, let you compose all of them as stacked decorators around the same call.

Circuit Breaker Pattern

The circuit breaker pattern wraps a call from a caller service to a dependency — another microservice, a database, a third-party API — so that when the dependency is failing or too slow, the caller stops sending it requests for a while instead of continuing to hammer a struggling system and piling up threads on doomed calls. It's modeled directly on an electrical breaker that trips to cut current when load becomes dangerous, and was popularized by Michael Nygard's Release It! and later by Netflix's Hystrix. The breaker moves through three core states: Closed, its normal state, where calls pass through while it tracks recent outcomes in a sliding window (count- or time-based); once the failure or slow-call rate crosses a configured threshold, it trips to Open, where calls are rejected immediately — no network call is even attempted — typically invoking a fallback, which frees the caller's own threads and connections rather than letting them block on a hung dependency; after a cooldown period the breaker enters Half-Open, allowing a small number of probe requests through to test recovery — success sends it back to Closed, failure sends it back to Open with the cooldown reset.

Beyond the three core states, mature implementations like resilience4j add operational states for production control — Disabled (always pass through), Forced-Open (a manual kill-switch), and Metrics-Only (observe outcomes without ever tripping, useful for safely tuning thresholds against real traffic before enabling enforcement). The behavior is governed by a handful of tunables: the sliding window's type and size (last N calls or last N seconds), a minimum call count before a rate is even computed (so the breaker doesn't trip on a tiny, unrepresentative sample), a failure-rate and/or slow-call-rate threshold, the wait duration in Open before probing (commonly 10–60 seconds), and the permitted call/success count in Half-Open. A breaker is only as useful as its fallback: strategies range from returning a cached or stale response, to a default/degraded response, routing to a secondary provider or region, queuing the request for later async processing, or simply propagating a fast, clear error. Each downstream dependency typically gets its own breaker instance — per-dependency isolation — so one failing call doesn't trip breakers guarding unrelated, healthy calls.

Closed tracks failures in a sliding window and trips to Open once a threshold is crossed; Open rejects calls fast and falls back until a cooldown elapses; Half-Open probes recovery with a handful of trial requests, returning to Closed on success or back to Open on failure.

Popular tools: resilience4j (the current de facto Java/JVM standard, especially with Spring Boot — lightweight, functional-decorator API with independently composable modules for CircuitBreaker, Retry, RateLimiter, Bulkhead, and TimeLimiter), Netflix Hystrix (the library that popularized the pattern in 2012, thread-pool-based isolation, now in maintenance mode since its 1.5.18 release and not recommended for new projects), Polly (.NET's standard resilience library, offering Circuit Breaker as a fluent policy), Sentinel (Alibaba), and infrastructure-level circuit breaking with zero app-code changes via Envoy Proxy (max-connection/pending/concurrent-request circuit breaking plus outlier detection), Istio (DestinationRule connection-pool and outlier detection settings), and Kong (MeshCircuitBreaker policies).

When to use it
Any call to an external dependency that could become slow or fail — third-party APIs, payment processors, microservice-to-microservice calls in a non-trivial dependency graph — especially in high fan-out systems (a gateway calling many downstream services) where one bad downstream shouldn't take down the whole aggregate response. Use at the mesh/gateway layer (Envoy/Istio/Kong) for uniform policy across polyglot services without touching each service's code, or at the application layer (resilience4j/Polly) when you need fine-grained, call-site-specific fallback logic. Less necessary for calls that are already cheap, fast, and highly reliable — localhost calls, well-provisioned internal caches.
ProsCons
  • Prevents cascading failure and resource exhaustion across a call graph
  • Fails fast, freeing caller threads/connections instead of waiting out timeouts
  • Self-healing via the half-open probe, no manual intervention needed
  • Strong operational signal (state-transition metrics) about which dependency is unhealthy
  • Infrastructure-level options (mesh/gateway) need zero app-code changes
  • Threshold/window/cooldown tuning is easy to get wrong — too sensitive trips on blips, too lax gives no protection
  • Requires thoughtfully designed fallback logic to actually be useful
  • Some requests fail outright during Open even if the dependency could have handled a few
  • Per-instance breaker state can be inconsistent across a fleet unless using a shared/distributed implementation

Retry with Backoff & Jitter

Retry with backoff and jitter automatically re-attempts a failed operation on the assumption that many failures are transient — a brief network blip, a momentary latency spike, a dependency mid-restart. Exponential backoff increases the wait between attempts (1s, 2s, 4s, 8s, capped at some maximum) rather than retrying immediately, giving a struggling dependency room to recover instead of hitting it again right away. Jitter adds randomness on top of that schedule so that many clients who all failed at the same moment don't retry in lockstep — without it, a large batch of synchronized retries can itself create a "thundering herd" that takes down a service that was only mildly struggling.

Retries must be paired with a hard cap on attempt count or a deadline, and should only be applied to idempotent operations (or ones made safe via idempotency keys) — naive retries without backoff, jitter, and a cap are a common real-world cause of retry storms, not just a mitigation for them.

Popular tools: resilience4j's Retry module, Polly's Retry policy (.NET), retry logic built into most cloud SDKs (AWS SDK, Google Cloud client libraries), and retry policies configured directly at the mesh/gateway layer in Istio and Envoy.

When to use it
Network calls prone to transient errors — calling a database, cache, or downstream microservice/third-party API over an unreliable network — combined with circuit breakers (so retries stop once a dependency is confirmed down, not just flaky) and idempotency guarantees (so a retried write doesn't double-charge a customer or double-insert a record).
ProsCons
  • Recovers automatically from transient blips without any user-visible error
  • Jitter prevents synchronized retry storms/thundering herds
  • Simple to bolt onto an existing call with a decorator/library
  • Unsafe for non-idempotent operations unless paired with idempotency keys
  • Poorly configured retries (no cap, no backoff) amplify load on an already-struggling dependency
  • Adds tail latency to the failing-then-succeeding path

Bulkhead Pattern

The bulkhead pattern isolates the resources — thread pools, connection pools — used to call different dependencies, so that one failing or slow dependency can't exhaust the resources needed to keep calling other, healthy dependencies. The name comes from a ship's bulkheads, the watertight compartments that contain a hull breach to one section instead of letting it sink the whole vessel; applied to software, a slow "nice-to-have" recommendation service shouldn't be able to consume every thread in a pool and block a critical checkout call from ever getting one.

Implementations come in two flavors: thread-pool-based, giving each dependency a fully separate executor pool (strong isolation, but each pool costs its own memory and context-switching overhead), or semaphore-based, which is lighter-weight and simply caps the number of concurrent calls allowed to a dependency without a dedicated pool behind it.

Popular tools: resilience4j's Bulkhead module (both thread-pool and semaphore-based implementations), Hystrix's thread-pool isolation (legacy), Polly's Bulkhead policy (.NET), and connection-pool limits configured per-destination in Envoy/Istio.

When to use it
Calling multiple independent downstream dependencies that have different reliability or latency profiles, so a slow or flaky lower-priority dependency can't also block calls to a critical one. Common at aggregation/gateway layers fanning out to many backend services, and anywhere a single shared thread or connection pool is currently serving calls to services with very different risk profiles.
ProsCons
  • Contains one dependency's failure/slowness to its own resource pool
  • Protects critical-path calls from being starved by a noisy or slow neighbor
  • Semaphore variant is lightweight to add with minimal overhead
  • Thread-pool variant adds real memory and context-switch overhead per pool
  • Sizing each pool correctly requires ongoing tuning as traffic patterns shift
  • More moving parts/config to reason about than a single shared pool

Backpressure

Backpressure is the mechanism by which a system signals "slow down" to its upstream producer when it can't keep up with incoming load, instead of buffering the excess unboundedly — risking an out-of-memory crash — or silently dropping data. It's implemented via bounded queues that block or reject new items once full, reactive-streams-style demand signaling (a consumer explicitly requests N more items when it's ready, rather than being pushed data it can't yet handle), or lower-level flow-control primitives like TCP's own windowing.

Without backpressure, a fast producer paired with a slow consumer leads to unbounded queue growth and an eventual crash — a common, very real outage pattern in event-driven and streaming systems where nothing upstream is ever told to pause.

Popular tools: Reactive Streams implementations such as Project Reactor and RxJava, Akka Streams, Kafka consumer flow control (poll-based pull rather than push), gRPC's built-in flow control, and application-level bounded queues (blocking or reject-on-full) sitting in front of a worker pool.

When to use it
Streaming/event-driven pipelines and any producer/consumer relationship where load can spike faster than the consumer can process — message queue consumers, log/metrics ingestion pipelines, real-time data pipelines feeding a slower downstream stage.
ProsCons
  • Prevents unbounded memory growth and out-of-memory crashes under load spikes
  • Applies natural, coordinated throttling instead of uncontrolled buffering or silent data loss
  • Keeps a fast producer and a slow consumer stable together
  • Adds design complexity — every stage in a pipeline needs to participate for it to work end to end
  • Slowing the producer can cascade delay backward through the whole chain
  • Not all protocols/libraries support demand signaling natively, requiring extra plumbing
