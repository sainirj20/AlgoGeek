SYSTEM DESIGN — BUILDING UNITS

Observability

Overview

Observability is the ability to ask new questions about a running system from the outside, without shipping new code first — the difference between monitoring (watching predefined dashboards for problems you anticipated) and true observability (diagnosing failure modes you never thought to instrument for). In practice it rests on three complementary signal types, often called the three pillars: metrics (cheap, aggregated numerical time series, good for trends and alerting), logs (rich, per-event text, good for forensic detail), and traces (request-scoped causal timelines, good for pinpointing exactly where in a distributed call graph something went wrong). No single pillar tells the whole story alone — mature teams instrument for all three and pivot between them as an incident unfolds: metrics flag that something is wrong and roughly when, traces narrow down where in the request path it's happening, and logs supply the exact error detail once the culprit service is known.

Metrics, logs, and traces are complementary signal types — most incidents are diagnosed by starting on one pillar and pivoting to another.

Monitoring & Metrics (Prometheus, Grafana, Datadog)

Monitoring and metrics tooling collects, stores, visualizes, and alerts on numerical time-series data — CPU, request latency, error rates, business KPIs — describing system health over time. Two collection models dominate: a pull model, where a central server like Prometheus scrapes an HTTP /metrics endpoint on each target at a fixed interval (a failed scrape is itself an unambiguous down signal, which works well for stable, discoverable infrastructure), and a push model, where an agent actively ships metrics to a backend — necessary for ephemeral, serverless, or NAT'd targets that can't be scraped. Metrics land in a purpose-built time-series database — Prometheus's own TSDB, often paired with remote-write to Thanos, Mimir, or Cortex for long-term retention at scale, or a vendor's managed backend in Datadog's case — and PromQL-style query languages drive both dashboards and alert-routing rules; Grafana is popular precisely because it visualizes across many of these backends without owning the underlying data.

The data model matters as much as the collection mechanism: counters, gauges, and histograms/summaries are the core metric types, and dimensional/labeled metrics let you slice the same signal by service, region, or endpoint. Alerting layers thresholds, burn-rate rules, and SLO-based rules on top, routed into on-call tooling — but cardinality has to be actively managed, since a label with too many unique values (a raw user ID, say) can blow up storage and cost almost overnight.

Popular tools: Prometheus + Grafana (+ Alertmanager; long-term storage via Thanos, Cortex, Mimir, or VictoriaMetrics) — the de facto open-source, Kubernetes-native combo. Datadog — fully managed SaaS unifying metrics, logs, traces, and APM. Also New Relic, Dynatrace, and AWS CloudWatch.

When to use it
Always needed in any production system — this is the "vital signs" layer. Reach for Prometheus/Grafana when you're Kubernetes-heavy, cost-sensitive, and want full operational control; reach for Datadog when time-to-value and unified cross-signal correlation matter more than owning the stack. Use metrics for aggregate health/trend questions and threshold-based alerting — not for root-causing one specific request, which is what tracing and logging are for.
ProsCons
  • Cheap to store/query at high volume relative to logs or traces
  • Excellent for trend detection and threshold/SLO-based alerting
  • Dimensional labels enable flexible slicing without re-instrumenting
  • Pull model struggles with very ephemeral/short-lived jobs
  • High-cardinality labels can silently blow up storage cost
  • Aggregate by nature — can't reconstruct one specific request's path

Centralized Logging (ELK/EFK, Splunk)

Centralized logging replaces "SSH into each box and grep a file" with one searchable, aggregated system spanning every distributed service and host. Lightweight collection agents — Filebeat, Fluentd/Fluent Bit, Logstash, or Splunk Forwarders — tail logs on each host or pod; a processing/enrichment stage then parses raw text into structured fields and attaches metadata like service name, host, and trace ID, with Logstash offering heavier and more powerful filtering and Fluentd/Fluent Bit favored as a lighter Kubernetes DaemonSet. From there logs land in a storage and indexing layer — Elasticsearch/OpenSearch (the same inverted-index mechanics used for search) or Splunk's proprietary indexers — queried through Kibana or Splunk's Search Head. EFK is simply ELK with Logstash swapped for Fluentd/Fluent Bit to shrink the Kubernetes footprint.

Structured, JSON-formatted logging is what makes this searchable at scale rather than just concatenated text; hot/warm/cold retention tiers balance query speed against storage cost as data ages; and pairing every log line with a trace ID is what lets an engineer jump directly from a slow span in a trace to the exact log line that explains why.

Popular tools: ELK/EFK Stack (Elasticsearch/OpenSearch + Logstash/Fluentd + Kibana, plus Beats); Splunk (enterprise-grade, SPL query language, strong compliance/SIEM use cases, but expensive at scale); Grafana Loki (indexes only metadata/labels, storing content cheaply in object storage — much cheaper at scale, weaker full-text search); cloud-native CloudWatch Logs/Cloud Logging.

When to use it
Needed on essentially any system with more than a handful of instances or containers. Reach for it debugging production incidents and maintaining compliance/audit trails — favoring Splunk or ELK with strict retention policies where regulation demands it — and reach for Loki specifically when log volume is very high and queries mainly filter by label rather than needing rich ad hoc full-text search.
ProsCons
  • Correlates logs across every service in one searchable place
  • Structured/JSON logging makes forensic debugging dramatically faster
  • Retention tiers let you balance cost vs. query speed
  • Operationally heavy to run at scale (ELK/EFK)
  • Licensing costs scale with data volume (Splunk)
  • Cheaper alternatives (Loki) trade away full-text search power

Distributed Tracing (Jaeger, Zipkin, OpenTelemetry)

Distributed tracing follows a single logical request as it hops across multiple services, reconstructing the end-to-end path and timing to answer "where did this request spend its time, and where exactly did it fail?" A trace represents one end-to-end transaction, identified by a globally unique trace ID; a span represents one unit of work inside it — an API call, a database query — carrying timestamps, a service/operation name, a status, and a parent span ID that links it into the trace's causal tree. As a request crosses a service boundary — an HTTP header, gRPC metadata, a queue header — its trace and span IDs propagate with it, which is the exact mechanic that lets independently generated spans from unrelated services stitch back together into one coherent trace. Because tracing every request at high volume gets expensive fast, sampling — either head-based (decided up front) or tail-based (decided after seeing the outcome, better for catching rare slow or error traces) — keeps it affordable at scale.

Tracing answers a different question than metrics or logs: not "is something wrong in aggregate" or "what exactly did this one event say," but "why was this specific request slow or broken." The output is typically visualized as a service dependency graph or a flame-graph-style waterfall of nested spans, immediately showing which downstream hop consumed the most time.

A single trace decomposed into parent/child spans — indentation and color depth show the causal call hierarchy; sibling spans (Payment Service, Inventory Service) run sequentially under the same parent, Order Service.

Popular tools: OpenTelemetry (OTel) — the modern, vendor-neutral instrumentation standard (SDKs, W3C Trace Context propagation, the OTel Collector) feeding into whichever backend you choose. Jaeger (CNCF, originally Uber, rich feature set, tail sampling). Zipkin (originally Twitter, simpler, lower memory footprint). Also Grafana Tempo, AWS X-Ray, Datadog APM, Honeycomb.

When to use it
Reach for distributed tracing in any microservices or service-mesh architecture where a single request touches three or more services — diagnosing which downstream call is causing a slow p99, or exactly where a failed request broke. It's not a substitute for logs or metrics: use tracing to find where in the call graph the problem lives, then pivot to logs and metrics for detail and trend confirmation — the three pillars working together.
ProsCons
  • Dramatically reduces mean-time-to-diagnose for latency and cross-service failures
  • Makes implicit request flow explicit via dependency graphs and flame graphs
  • Requires instrumentation effort across every service in the path
  • Sampling can miss the exact failing request
  • Storage/ingestion cost rises fast at high trace volume
