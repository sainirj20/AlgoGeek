SYSTEM DESIGN — BUILDING UNITS

Caching

Overview

Caching trades a small amount of staleness risk for a large reduction in latency and load on your system of record — and it shows up at every layer of a real system, not just as "add Redis in front of the database." This page moves from the in-memory stores themselves (Redis, Memcached) out to where a cache physically sits relative to the application (distributed, near-cache, and sidecar architectures), the read/write contracts that govern how a cache and its backing store stay in sync (cache-aside, write-through, write-back, and related patterns), how a full cache decides what to evict and when to invalidate, the failure modes a cache can introduce under load (stampede, avalanche, penetration), and finally the network edge and browser layers (CDN edge caching, HTTP caching headers, application-level caching) plus two closely related building blocks — the Varnish HTTP accelerator and the request-coalescing/singleflight pattern that defends against stampedes at the code level.

In-Memory Caches: Redis

Redis (REmote DIctionary Server) is an open-source, in-memory data structure store that doubles as a cache, primary database, message broker, and streaming engine. A single-threaded event loop executes commands one at a time, which makes multi-step operations like incrementing a counter or pushing onto a list atomic without any explicit locking — the whole operation happens server-side in one round trip. Because the dataset lives natively in memory as strings, hashes, lists, sets, sorted sets (leaderboards, rate limiters), streams, bitmaps/HyperLogLogs, and geospatial indexes, Redis often replaces application-side logic that would otherwise need multiple round trips against a plain key-value store.

Durability is optional but well supported: RDB point-in-time snapshots, an append-only file (AOF) command log (tunable from always to everysec durability), or a hybrid of both are the common production setup. Redis Cluster shards data across 16,384 fixed hash slots with masters paired to replicas for failover (a minimum viable HA cluster is 3 masters + 3 replicas), while Sentinel offers monitoring and automatic failover for a single primary/replica pair without sharding. Since Redis 6 and RESP3, client-side caching lets clients keep an automatically-invalidated local "near cache," and the ecosystem now splits between Redis itself (tri-licensed RSALv2/SSPLv1/AGPLv3, restoring OSI-approved open-source status in May 2025) and Valkey, the Linux Foundation's BSD-licensed drop-in fork backed by AWS, Google Cloud, and Oracle. See the Key-Value Stores page for deeper Redis/Memcached product profiles.

Popular tools: Redis OSS, Redis Enterprise/Cloud, AWS ElastiCache for Redis/MemoryDB, Google Cloud Memorystore, Azure Cache for Redis, Valkey, Dragonfly.

When to use it
Session storage, leaderboards/rankings, rate limiting/counters, real-time analytics, pub/sub messaging, job queues — anywhere you need more than plain get/set, durability options alongside cache behavior, horizontal scale-out for a large working set, or atomic multi-step operations. Reach for Memcached instead when you want the simplest, lowest-memory-overhead cache with massive concurrent throughput and no extra features.
ProsCons
  • Extremely fast, in-memory operations
  • Rich data types cut app-side logic
  • Built-in persistence, replication, and clustering
  • Versatile beyond caching (queues, pub/sub, streams)
  • Higher per-key memory overhead than Memcached
  • Single-threaded core can bottleneck on very large values or heavy scripting
  • Cluster/HA setup adds operational complexity

In-Memory Caches: Memcached

Memcached is a simple, high-performance, distributed in-memory key-value store built purely for caching — no persistence, no complex data types, minimal by design. A multi-threaded server design lets it use multiple CPU cores natively, with each thread handling a subset of connections, and it stores arbitrary blobs up to 1MB per item using slab-allocated memory with LRU eviction. Nodes don't talk to each other — there's no built-in clustering — so client libraries handle consistent hashing across a pool of servers, and data is purely volatile: a restart or eviction means it's gone for good.

The practical trade-off against Redis is simplicity versus features: Memcached's multi-threaded architecture often edges out Redis on raw GET/SET throughput at high concurrency and carries lower per-item memory overhead, but it offers nothing beyond key-value blobs — no persistence, replication, pub/sub, or transactions. Most new projects in 2026 default to Redis/Valkey unless simplicity or memory efficiency specifically favors Memcached. See the Key-Value Stores page for deeper Redis/Memcached product profiles.

Popular tools: Memcached, Mcrouter, AWS ElastiCache for Memcached, Google Cloud Memorystore for Memcached.

When to use it
The lightest possible, purely ephemeral cache in front of a database — simple page-fragment or query-result caching — when you want the simplest, lowest-overhead footprint and don't need durability, clustering, or rich data structures.
ProsCons
  • Simplest operational model
  • Very low per-key memory overhead
  • Excellent raw throughput at high concurrency
  • Multi-threaded — uses multiple cores natively
  • No persistence — a restart means a fully cold cache
  • No native clustering/HA (must build at client/proxy layer)
  • No rich data structures, pub/sub, or transactions

Distributed Caching Architecture

This is less about a specific product and more about where a cache physically lives relative to the application, and how multiple app instances share cached state consistently. A centralized/remote distributed cache — a dedicated Redis Cluster or Memcached pool that every app instance calls over the network — gives everyone a consistent shared view but adds a network hop and a shared failure point. Client-side caching (a "near cache") keeps a local in-process cache inside the application, such as Caffeine/Guava or Redis's client-side tracking, avoiding the network hop entirely for hot keys at the cost of needing an invalidation mechanism to stay reasonably fresh. Cache-aside (look-aside) architecture is the simplest topology of all: the cache is a purely passive store that the application checks first and falls back past on a miss.

Two more topologies show up often in interviews: the sidecar cache pattern runs a cache process alongside the app in the same Kubernetes pod, reachable over localhost, trading duplicated memory per instance for reduced cross-pod hops and blast radius versus one shared cluster; and the inline/reverse-proxy cache (Varnish, Nginx, a CDN edge) sits directly in the request path, transparently serving cached responses without the application even being aware a cache is involved. In practice, production systems often layer several of these — local → distributed → CDN/edge → database — each tier trading latency against freshness and hit-rate scope.

Popular tools: Redis Cluster, Memcached + Mcrouter, Hazelcast, Apache Ignite, Amazon DynamoDB Accelerator (DAX), Envoy/Istio sidecars, Caffeine/Guava, Varnish/Nginx.

When to use it
A centralized cluster when many services need a shared, consistent cache view and the working set exceeds one node's memory. A client-side/near cache for extremely hot, small, read-heavy keys — usually layered on top of a distributed cache, not instead of one. A sidecar cache in Kubernetes environments that want per-service locality/isolation without standing up a separate shared cluster.
ProsCons
  • Centralized: one consistent shared view across services
  • Near cache: fastest possible reads, no network hop
  • Sidecar: strong latency/isolation per service
  • Centralized: extra network hop, shared failure point
  • Near cache: staleness risk, duplicated memory per instance
  • Sidecar: more operational units, potential memory duplication

Caching Strategies / Patterns

These are the different contracts for how reads and writes flow between the application, the cache, and the backing data store — arguably the single most-tested caching concept in system design interviews. In cache-aside (look-aside, lazy loading), the application checks the cache first; on a miss it reads the database and writes the result into the cache with a TTL, and writes typically invalidate rather than update the cached entry. Read-through works the same way from the reader's perspective, except the cache layer itself owns miss-handling, so the application only ever talks to the cache and never falls back to the database directly.

On the write side, write-through sends every write to the cache and the store together before acknowledging, so readers always see fresh data at the cost of slightly slower writes; write-behind (write-back) acknowledges the write as soon as it hits the cache and flushes to the store asynchronously, maximizing write throughput but risking data loss if the cache fails before the flush completes. Write-around instead sends writes directly to the database, bypassing the cache entirely, so the cache is populated only on a subsequent read — useful for reducing churn from write-heavy data that's rarely read again soon after.

Cache-aside pulls on miss and populates after; write-through keeps cache and DB in lockstep before acknowledging; write-back acknowledges immediately and flushes asynchronously.

Popular tools: These patterns are usually implemented in application code or a caching library rather than being tied to one product — Spring Cache/Ehcache annotations, AWS DynamoDB Accelerator (DAX, read-through/write-through), Redis/Memcached client libraries for cache-aside, and message-queue-backed write-behind pipelines (e.g. Kafka plus a batch writer) are common building blocks.

When to use it
Cache-aside — default for most read-heavy workloads tolerant of some staleness. Read-through — when you want caching logic centralized in the cache layer/library rather than scattered through app code. Write-through — when correctness matters more than write latency (inventory counts, account balances). Write-behind — write-heavy systems tolerant of a small data-loss window in exchange for big throughput gains (view counters, activity logs). Write-around — lots of writes to data that's infrequently re-read soon after (audit logs, bulk imports).
ProsCons
  • Cache-aside: simple, flexible, only caches what's requested
  • Read-through: one interface for hit/miss simplifies app code
  • Write-through: strong consistency between cache and store
  • Write-behind: fastest possible write throughput
  • Cache-aside/read-through: cold-miss penalty on the first request
  • Write-through: higher write latency (waits on the DB write)
  • Write-behind: risk of data loss if the cache node crashes before flushing
  • Write-around: first read after a write is always a slow miss

Cache Eviction Policies and Invalidation Strategies

Eviction and invalidation solve two different problems that are easy to conflate: eviction policies decide which entries to remove once the cache is full and something has to make room; invalidation strategies decide when a cached entry should stop being trusted because the underlying source data changed. LRU (Least Recently Used) evicts whatever hasn't been touched in the longest time — cheap to implement and a good general default, though a single one-time scan of cold data can flush out an otherwise-hot working set. LFU (Least Frequently Used) evicts by lowest access count instead, which is more scan-resistant but needs frequency decay so yesterday's popularity doesn't pin an item forever. FIFO simply evicts the oldest-inserted entry — trivial to implement but generally the weakest hit rate of the three. TTL expiration sits in a different category entirely: it's a freshness mechanism, not a capacity-driven policy, removing entries after a fixed lifespan regardless of memory pressure, and it's commonly layered on top of LRU/LFU rather than used alone.

On the invalidation side, the options range from passive to active: TTL-based expiration is passive and simplest; active/explicit invalidation on write and write-through propagation keep the cache in lockstep with the source at write time; versioning/cache-busting mints a new key per version (the standard approach for static assets and CDN objects); pub/sub or event-driven invalidation fans a purge message out to every node in a distributed cache; and stale-while-revalidate (RFC 5861) serves the stale value immediately while refreshing it in the background rather than blocking the request.

Popular tools: Redis maxmemory-policy (LRU/LFU/random/TTL variants), Memcached's LRU + slab allocator, Caffeine/Guava (W-TinyLFU), CDN cache-tag/purge APIs, CDC pipelines such as Debezium feeding invalidation events.

When to use it
LRU for general-purpose, recency-biased access. LFU for a stable "hot set" of popular items you don't want a transient scan to evict. FIFO for simple queue-like buffers. TTL for anything with a natural freshness window — tokens, DNS records, pricing, feature flags. Event-driven invalidation for multi-instance or CDN caches where strict freshness matters and TTL alone can't be trusted.
ProsCons
  • LRU is cheap (O(1)) and fits most web workloads
  • LFU protects a stable hot set from transient scans
  • Event-driven invalidation gives strict freshness across distributed nodes
  • LRU can be polluted by a one-off scan of cold keys
  • LFU needs extra bookkeeping (frequency counters/decay) and adapts slowly to shifting popularity
  • FIFO ignores access patterns and gives the weakest hit rate
  • Event-driven invalidation adds fan-out/messaging infrastructure and its own failure modes

Cache Consistency Challenges: Stampede, Avalanche, Penetration

These are three distinct failure modes where the cache, instead of protecting the backing store, amplifies load onto it. A cache stampede (thundering herd) happens when one popular key expires and a large number of concurrent requests all miss at the same instant and all recompute the same expensive value simultaneously. A cache avalanche is the multi-key version: many different keys — often cached in the same batch with the same TTL — expire around the same time, or an entire cache node/cluster goes down, sending a sudden wave of traffic to the database all at once. Cache penetration is different again: repeated requests for keys that don't exist in either the cache or the database (invalid IDs, scraping/probing) never get a cache hit to begin with, so every single request bypasses the cache and lands directly on the database.

The mitigations overlap but map roughly to the failure mode. Locking/request coalescing (singleflight) lets only one request recompute a given key while everyone else waits for that result, directly targeting stampedes on a single hot key. Stale-while-revalidate and probabilistic early recomputation smooth out the same problem by refreshing in the background before or right at expiry. TTL jitter — randomizing expiration times rather than expiring an entire batch at once — is the standard defense against avalanche. Cache penetration is addressed differently: negative caching (caching the "not found" result itself) and Bloom filters (cheaply confirming a key definitely doesn't exist before ever touching the cache or DB) stop the repeated pointless lookups, and input validation closes off the crudest probing. Multi-tier caching/redundancy and circuit breakers/rate limiting act as a last-resort backstop regardless of which failure mode is in play.

Without coalescing, N concurrent misses become N duplicate DB queries; singleflight/request coalescing collapses them into one, fanning the shared result back out to every waiting caller.

Popular tools: Redis SET key value NX PX ttl locks and singleflight libraries for coalescing, Bloom filter implementations (Redis BF.*, Guava), CDN/API-gateway negative-caching and rate-limiting features, and circuit-breaker libraries (Resilience4j and its predecessors) as the backstop.

When to use it
High-traffic systems with a few very hot keys — use locking/coalescing plus stale-while-revalidate. Systems where many keys were cached in the same batch — use TTL jitter. Public APIs vulnerable to ID enumeration or scraping — use negative caching and/or Bloom filters. Any system where a cache outage could dump 100% of traffic onto the database — design for graceful degradation as a backstop, not as an afterthought.
ProsCons
  • Locking/coalescing collapses N duplicate requests into 1
  • TTL jitter prevents synchronized mass expiry
  • Negative caching/Bloom filters eliminate pointless repeated lookups
  • Mitigations compose (jitter + coalescing + stale-while-revalidate)
  • Locking adds latency/complexity for "losing" requests and a new contention point
  • Jitter alone doesn't help a single celebrity key
  • Bloom filters have a small false-positive rate and need periodic rebuilding
  • None of these substitute for capacity planning on the backing store

CDN Edge Caching

A CDN caches content on edge servers physically close to users, so most requests never make the round trip back to the origin. The nearest edge Point of Presence checks whether it holds a valid cached copy of the requested object: a hit is served directly from the edge; a miss triggers an "origin pull" — the edge fetches from the origin, caches the response for the duration of its TTL, and serves it. Origin shielding adds one more layer: instead of every edge PoP independently pulling from the origin (and each one missing on cold start), a designated "shield" PoP sits between the edge tier and the origin and collapses many independent edge-to-origin requests into far fewer — protecting the origin the same way request coalescing does at a single node.

TTL governs how long an edge node is allowed to hold an object before it must revalidate or refetch, and a manual or automated purge lets an operator force immediate removal ahead of that TTL when content changes unexpectedly. Modern CDNs increasingly cache more than static files — via edge compute and cache keys that vary on cookies/headers, they can cache semi-personalized or dynamic responses too, though that requires careful cache-key design to avoid either serving one user's content to another or effectively disabling caching entirely.

Popular tools: Cloudflare, Akamai, Fastly, Amazon CloudFront, Google Cloud CDN, Azure CDN, bunny.net.

When to use it
Static assets, video/media delivery, and semi-static pages for a geographically spread audience, along with cacheable/shared (non-personalized) API responses. Needs careful cache-key and invalidation design for strictly per-user or write-heavy endpoints — CDN/edge caching is fundamentally a caching strategy applied at the network edge rather than a separate networking concern, which is why it's covered here rather than as its own topic.
ProsCons
  • Dramatically reduces latency for geographically distributed users
  • Offloads a large share of traffic from the origin
  • Improves resilience during origin slowdowns or failures
  • Origin shielding further protects the origin during cache-cold events
  • Invalidation/purge across globally distributed edges is harder than a single cache node
  • Poor fit for highly personalized or rapidly changing per-user data without careful cache-key design
  • A misconfigured cache key can leak one user's content to another

Browser/Client-Side Caching and HTTP Caching Headers

This is the mechanism by which browsers — and any intermediate shared/proxy cache or CDN edge sitting between browser and origin — decide whether to reuse a previously stored response or go back to the server, governed entirely by a small set of standard HTTP headers rather than any custom logic. Cache-Control carries the actual directives: max-age=N sets the freshness lifetime, no-cache means it must revalidate before reuse (a common point of confusion — it does not mean "don't cache"), no-store means never cache it at all, private/public control who is allowed to cache it, and immutable skips revalidation entirely for content that will never change at that URL. stale-while-revalidate=N extends the same background-refresh idea from server-side caching down into the browser.

For content that needs periodic revalidation rather than a long flat TTL, ETag gives a content-derived token that the browser resends via If-None-Match, getting back a cheap 304 Not Modified if nothing changed instead of re-downloading the full payload; Last-Modified/If-Modified-Since is the older, time-based equivalent. Because the same headers apply uniformly across the private browser cache, shared proxy caches, and CDN edges, a well-chosen Cache-Control policy does triple duty, and versioned/hashed filenames complement a long max-age/immutable policy by making cache-busting on deploy automatic — the URL itself changes, so there's nothing to invalidate.

Popular tools: Implemented natively by every browser plus any CDN/reverse proxy in the path (Cloudflare, Fastly, Varnish, Nginx) — there's no separate product to adopt, only the headers your origin or CDN sets.

When to use it
Static assets — long max-age plus immutable plus hashed filenames, so a new deploy is a new URL rather than an invalidation problem. Frequently-updated-but-still-cacheable content — short max-age plus stale-while-revalidate. Sensitive or personalized data — no-store/private. Expensive-but-rarely-changing API payloads — ETag/Last-Modified validators to cut bandwidth via 304s instead of re-sending the full body.
ProsCons
  • Zero infrastructure cost — just headers the origin already controls
  • Cuts bandwidth and latency for both validators (304) and immutable assets
  • Works uniformly across browser, proxy, and CDN caches
  • Easy to misconfigure (e.g. caching a private/authenticated response as public)
  • no-cache is commonly misread as "don't cache" and misused
  • No control once a response has left the origin — you can't force-purge a browser's local cache the way you can purge a CDN

Content/Application-Level Caching

This is caching implemented inside the application/backend layer itself, to avoid redundant expensive computation, database queries, or full page renders — distinct from network-edge (CDN) caching or the browser's own cache. Query-result caching stores an expensive database result keyed by the query, refreshed on a TTL or explicitly invalidated on writes. Full-page caching goes further and caches the entire rendered HTML response, serving it directly and bypassing the application and database entirely on a hit. Object/fragment caching sits between the two — caching one reusable widget or aggregate (a sidebar, a computed total) rather than a whole page — and an in-process/local application cache is the fastest option of all, though it isn't shared across instances.

The distinction from CDN caching is granularity and awareness: application-level caching is fine-grained and business-logic-aware (it knows what a "product listing query" or a "user's cart total" is), while a CDN cache is coarser and works purely off URL/TTL/tag rules against whole HTTP responses. The two aren't competing choices — a well-layered system typically uses both, with the CDN protecting the network edge and application-level caching protecting the database and compute tier behind it.

Popular tools: Ehcache/Caffeine and Spring Cache (Java), Django's cache framework/cache_page, Rails fragment caching, Redis/Memcached as the backing store for query-result and fragment caches, and full-page cache modules for CMS platforms (e.g. Magento, WordPress full-page cache plugins).

When to use it
Query-result caching for dashboards or product listings that repeatedly hit the same expensive query. Full-page caching for content-heavy, mostly non-personalized sites — blogs, marketing pages. Fragment/object caching for pages that are mostly static with a few dynamic pieces. In-process cache for ultra-hot, small, single-instance data like compiled config or small lookup tables.
ProsCons
  • Fine-grained, business-logic-aware — caches exactly the expensive thing
  • Protects the database/compute tier directly, complementing CDN/edge caching
  • In-process variants need no network hop at all
  • Not shared across instances unless backed by a distributed cache
  • Invalidation logic lives in application code, so a code path can easily miss invalidating a key
  • Full-page caching is a poor fit once a page has meaningfully personalized content

Varnish Cache

Varnish Cache is an open-source HTTP accelerator — a reverse proxy purpose-built to sit in front of web/application servers and serve cacheable HTTP responses at very high speed, entirely from memory. First released in 2006 specifically to stop dynamic websites collapsing under load, it's still actively maintained today, with a commercial Varnish Enterprise edition adding clustering, TLS, and extra modules. The key distinction from a general-purpose reverse proxy or load balancer like Nginx/HAProxy is focus: those tools can cache as one of many features, while Varnish does one thing aggressively — its object store, threading model, and configuration language are all organized purely around maximizing cache hit ratio and minimizing backend load. It has no native TLS termination in the open-source core, typically pairing with Hitch or a load balancer in front of it.

Configuration happens through VCL (Varnish Configuration Language), a scripting language compiled all the way down to C and then a shared object, giving fine-grained control at each stage of a request's life — vcl_recv for initial routing/normalization, vcl_hash for building the cache key (normally URL + Host), vcl_hit/vcl_miss, vcl_backend_fetch/vcl_backend_response for the real request to origin and how the response is cached, and vcl_deliver for final response shaping. Compilation to native code is why even complex VCL logic still runs extremely fast, and cached objects are stored close to wire format — either in malloc'd heap memory (fastest) or file/mmap storage (allows caches larger than RAM) — so a cache hit is close to a memcpy/sendfile operation. Varnish's standout capability, though, is automatic request coalescing (see below), on by default for cacheable content — something Nginx only approximates via proxy_cache_lock.

Popular tools: Varnish Cache (open source) and Varnish Enterprise (commercial). Real-world adopters include large media/publishing sites (Future Publishing, NZZ, RTÉ), CDN builders like Telia, e-commerce sites (Boozt Fashion, Sheego, and a very common Magento caching layer), and historically Wikipedia/Wikimedia's caching layer in front of MediaWiki.

When to use it
High-traffic content sites (news, media, blogs) with a large share of anonymous/cacheable traffic; e-commerce storefronts facing flash-sale-style spikes; APIs with expensive, cacheable, shared responses requested concurrently by many clients; protecting a slow/expensive origin during cache-cold events like a cluster failover or post-deploy cache invalidation. Less appropriate for highly personalized per-request responses, workloads needing TLS/complex auth at this layer, or mostly non-cacheable writes/mutations.
ProsCons
  • Extremely fast cache-hit delivery
  • Protects origin capacity from duplicate concurrent traffic with zero app code changes
  • Fine-grained VCL control over every stage of the request
  • Edge Side Includes (ESI) for caching page fragments independently
  • Real learning curve — VCL is a genuine programming paradigm
  • Mistakes in vcl_hash normalization can cause cache poisoning or cross-user data leaks
  • No native TLS, auth, or general app-serving
  • Coalescing/grace mode trades a little staleness for protection — unsuitable for always-fresh/personalized content

Request Coalescing / Singleflight Pattern

Request coalescing (singleflight) is the general software pattern behind Varnish's collapsed forwarding, applied at the application/library layer rather than tied to HTTP: when a system detects that multiple concurrent callers are asking for the exact same piece of work — same cache key, same query, same function arguments — it ensures only one underlying execution actually happens, and every caller shares that one result. A request arrives keyed by an identifier; the coalescing layer checks a registry of "keys currently being fetched." If nothing is in flight, it starts the work and registers it; if something is already in flight, the new caller doesn't duplicate the work — it subscribes to (or blocks on) the pending result, and once the original fetch completes, that result is fanned out to every waiting caller at once.

Concrete implementations show up at every layer: Go's singleflight package exposes a Group.Do(key, fn) call where, if invoked concurrently with the same key, only the first fn actually executes and everyone else blocks and gets the same result — used widely in Go backends, including at Cloudflare, to deduplicate cache-fill and downstream calls at the edge. Facebook/Meta's McRouter, a memcached protocol proxy, does the same thing at connection scope — coalescing many clients onto fewer shared backend TCP connections alongside routing, replication, and automatic failover, at a scale of billions of requests/sec. Where an in-process registry can't help — because the callers are spread across a fleet of hosts — teams fall back to a Redis-based distributed lock (SET key value NX PX ttl), where the first process to acquire the lock does the expensive fetch and populates the cache while everyone else waits or polls. Coalescing is one of several stampede mitigations, alongside probabilistic early expiration and stale-while-revalidate/grace periods — it specifically targets duplicate concurrent work, turning one cache miss into one backend call instead of N.

Popular tools: Go's singleflight package, Facebook/Meta's McRouter, Redis-based distributed locks (SET ... NX PX), and Varnish's built-in collapsed forwarding as the HTTP-layer implementation of the same idea.

When to use it
Any read-heavy system with a hot-key problem (a viral post, a trending product); systems where cache expiry is synchronized across many keys at once; any expensive, idempotent, cacheable computation that many concurrent callers might request simultaneously. Not appropriate for non-idempotent or per-caller-unique work — writes, personalized/audited responses — since coalescing only makes sense when sharing one result across callers is actually correct.
ProsCons
  • Dramatically reduces load spikes on the origin/database
  • Cheap to implement within a single process
  • Improves latency for "losing" concurrent requests too, since they share the result instead of queuing behind the DB
  • In-process implementations don't help across a server fleet unless paired with a proxy or shared coordination
  • Distributed locking adds latency and new failure modes like lock contention
  • All coalesced callers share fate if the one real request fails
