SYSTEM DESIGN — BUILDING UNITS

Coordination, Consensus & Compute Orchestration

Overview

Every distributed system eventually needs a small set of nodes to agree on something critical — who is the leader, who holds the lock, what the current configuration is — and to run the actual compute workload somewhere reliable. This page covers both halves of that problem: the coordination layer (ZooKeeper, etcd, Consul, and the consensus math underneath them) that distributed systems build leader election, locking, and service discovery on top of, and the compute orchestration layer (containers, Kubernetes, serverless) that decides where and how application code actually runs. They're related because the orchestration layer is usually itself built on top of the coordination layer — Kubernetes' entire control plane, for instance, is a thin shell around etcd.

Apache ZooKeeper

Apache ZooKeeper is a centralized, highly available coordination service that gives other distributed systems a small set of reliable primitives — a hierarchical namespace, atomic reads/writes, and change notifications — on top of which they build leader election, distributed locks, configuration management, and service discovery. Rather than every service reinventing these primitives from scratch and getting the edge cases wrong, they delegate correctness to a purpose-built ensemble.

Internally, ZooKeeper models data as a filesystem-like tree of znodes. Persistent znodes survive client disconnects; ephemeral znodes disappear automatically the instant the creating client's session ends, which is the key primitive for liveness detection; and sequential znodes get a ZooKeeper-assigned monotonic counter appended to their name, giving a global ordering across concurrent creators. Clients register watches to receive a one-time notification when a znode changes. Underneath it all, ZAB (ZooKeeper Atomic Broadcast) — a Paxos-like consensus protocol — runs across an odd-sized ensemble (3, 5, or 7 nodes): the ensemble elects a leader, and a write commits once a quorum of followers acknowledge it. Common coordination recipes, often implemented via Apache Curator, follow directly from these primitives: leader election and locks use ephemeral-sequential znodes where the lowest sequence number wins, configuration management watches a znode for pushed updates, and service discovery relies on ephemeral registration znodes that vanish automatically when an instance dies.

Popular tools: Apache Kafka (pre-KRaft), Apache HBase, Apache Mesos, SolrCloud, Hadoop YARN (ResourceManager HA), older Apache Pulsar deployments.

When to use it
Reach for ZooKeeper when a dependency you already operate requires it (HBase, older Kafka clusters, Solr, Mesos, Pulsar), or when you need a proven, off-the-shelf lock/leader-election primitive for a JVM-heavy stack. For new systems, most teams now reach for etcd or embed Raft directly — Kafka 4.0 (March 2025) fully removed ZooKeeper support in favor of its own embedded Raft quorum (KRaft), requiring migration via 3.9 first, with reported wins in setup time, infra cost, and partition scalability. ZooKeeper isn't disappearing, though — it still underpins HBase, Solr, Mesos, and YARN HA, and it remains the canonical teaching example of leader election and distributed locks via ephemeral+sequential znodes.
ProsCons
  • Extremely mature and battle-tested
  • Simple, well-understood mental model (znodes + watches)
  • Strong consistency guarantees via ZAB
  • Huge ecosystem of proven recipes via Curator
  • Yet another JVM cluster to operate and tune
  • Disk/GC sensitivity can trigger false failure detection
  • Write throughput bottlenecked through a single leader
  • Increasingly displaced by embedded Raft (e.g. Kafka KRaft)

etcd

etcd is a distributed, strongly consistent key-value store purpose-built to hold small amounts of critical coordination and configuration data reliably — most famously as the backbone of Kubernetes cluster state. Unlike ZooKeeper's hierarchical znode tree, etcd exposes a flat keyspace, but the consensus story is conceptually similar: a small, odd-sized cluster (typically 3 or 5 members) replicates a log via Raft, with a single leader accepting writes and replicating them to followers; a write commits only once a majority quorum has persisted it, giving linearizable consistency and tolerance of minority-node failures.

Two features make etcd particularly well suited to being a control-plane store. MVCC means every write creates a new, immutable revision, which is what lets etcd offer reliable, gap-free watch streams rather than best-effort notifications. And leases provide a TTL mechanism — a client attaches a lease to a set of keys and must keep sending keep-alives, or those keys are automatically deleted — etcd's analogue of ZooKeeper's ephemeral znodes, and the foundation for locks built on top of etcd. In Kubernetes specifically, only the kube-apiserver talks to etcd directly: every other control-plane component goes through the API server, which persists all cluster object state in etcd, uses etcd's watch API to drive its reconciliation loops, and uses leases for TTL-based objects like node heartbeats and leader-election locks — etcd is explicitly the cluster's single source of truth.

Popular tools: Kubernetes (flagship user), CoreDNS, Rook, M3DB, Cloud Foundry components.

When to use it
Reach for etcd when you need a small, strongly consistent store for critical metadata or coordination state — building Kubernetes-adjacent tooling such as operators and custom controllers, or wanting Raft-based consistency with a much lighter operational footprint than a full ZooKeeper ensemble. It's not a good fit as a general-purpose application database or for large-value/high-throughput data.
ProsCons
  • Simple, fast, and strongly consistent (Raft)
  • Small operational footprint versus a ZooKeeper ensemble
  • Proven at massive scale (Kubernetes)
  • Reliable, gap-free watch streams via MVCC
  • Not designed for large values or high-volume data
  • Write throughput bounded by Raft quorum + single leader
  • High sensitivity to disk/network latency between members

Consul (HashiCorp)

Consul is a service networking platform that bundles service discovery, health checking, a key-value store, and, in its modern form, a full service mesh into one system. Where ZooKeeper and etcd hand you low-level coordination primitives and leave discovery and health-checking to be built on top, Consul ships those capabilities natively. Its architecture is two-tiered: a small quorum of server agents holds Raft-replicated state (the service catalog, KV store, ACLs), while lightweight client agents run on every host. Cluster membership and failure detection are handled cheaply by a gossip protocol (Serf/SWIM) rather than by the Raft layer itself, organized as a LAN gossip pool per datacenter plus a WAN pool connecting servers across federated datacenters — which is what gives Consul native multi-datacenter support out of the box.

Health checking (script, HTTP, TCP, gRPC, or TTL-based) is a first-class concept that automatically filters unhealthy instances out of discovery results, and Consul Connect layers on mTLS service identity, automatic Envoy sidecar injection, and authorization "intentions," turning Consul into a full service-mesh control plane rather than just a registry. Compared to ZooKeeper and etcd, Consul is the only one of the three with native service discovery, native health checking, and native multi-datacenter replication built in — the other two require you to build those capabilities yourself on top of their primitives.

Popular tools: HashiCorp Consul (open source and Enterprise), Consul Connect with Envoy sidecars; frequently paired with Nomad or run alongside Kubernetes in mixed VM/container estates.

When to use it
Reach for Consul on heterogeneous infrastructure that mixes VMs, bare metal, and containers together; when you need health-aware discovery without hand-rolling it; when multi-datacenter service discovery is a hard requirement; or when you want a service mesh without committing to Istio or Kubernetes-native tooling.
ProsCons
  • Native service discovery and health checking out of the box
  • Strong multi-datacenter story (LAN + WAN gossip pools)
  • Doubles as a full service-mesh control plane (Consul Connect)
  • Works across mixed VM/container/bare-metal estates
  • Heavier to operate than etcd if you only need a KV store
  • Largely redundant if you're 100% Kubernetes-native
  • Two-tier server/client architecture adds operational surface

Consensus Algorithms (Conceptual): Paxos and Raft

Paxos and Raft are the mathematical foundations that let a cluster of nodes agree on a single value or decision — who is leader, who holds a lock — even as individual machines crash or the network partitions, as long as a majority of nodes (a quorum) can still communicate. Every coordination system covered on this page rests on one of these algorithms under the hood: ZooKeeper's ZAB, etcd's and Consul's Raft implementations, and Kafka's KRaft are all descendants of this same idea.

Paxos works by having nodes propose values tagged with increasing proposal numbers through a two-phase protocol — Prepare/Promise, then Accept/Accepted — and once a majority of nodes accepts a value, it is permanently chosen. It's provably correct, but notoriously difficult to reason about in practice: the original papers describe only a single-decision protocol, leaving "Multi-Paxos" — the version needed to agree on a continuous sequence of decisions — underspecified, which has led to many subtly different real-world implementations. Raft was designed explicitly to fix that understandability problem: it decomposes the same problem into three separate concerns — leader election (via randomized timeouts and per-term majority votes), log replication (a single leader drives replication, and an entry is committed once a majority of nodes persist it), and a set of safety rules that prevent split-brain or data loss across leader changes. Because there is always exactly one leader driving replication at a time, Raft is much simpler to implement correctly, which is exactly why etcd, Consul, and Kafka's KRaft all chose it.

Raft splits consensus into leader election (a candidate wins with a majority of votes) and log replication (an entry is committed once a majority of nodes persist it).

Popular tools: ZooKeeper's ZAB (Paxos-derived); etcd and Consul (Raft); Kafka KRaft (Raft); CockroachDB, Google Spanner, YugabyteDB (Paxos/Raft-based strong consistency).

When to use it
Reach for this framing whenever evaluating why a coordination system — ZooKeeper, etcd, Consul, Kafka KRaft — is sized and architected the way it is. A write is only durable once a majority of nodes hold it; that single fact is what prevents split-brain and lets the system keep making progress while tolerating minority failures. An N-node cluster tolerates ⌊(N−1)/2⌋ failures while still making progress — 3 nodes tolerate 1, 5 tolerate 2 — which is exactly why production deployments are always sized 3, 5, or 7.
ProsCons
  • Formally proven correctness under crash/partition failures
  • Raft's decomposition makes it tractable to implement correctly
  • Well-understood failure math simplifies capacity planning
  • Widely implemented and battle-tested (ZAB, Raft, KRaft)
  • Paxos alone is notoriously hard to reason about and extend safely
  • Single-leader designs still bottleneck writes through one node per term
  • Requires an odd-sized majority-quorum cluster, adding fixed overhead
  • A building block, not a product — doesn't solve discovery/health-checking itself

Containers (Docker / Containerization)

A container packages an application together with all of its dependencies into a portable, consistent runtime unit — virtualizing at the operating-system level rather than the hardware level the way a VM does. Because containers share the host's kernel, they start in a fraction of a second and carry a much smaller footprint than a full virtual machine, at the cost of a weaker isolation boundary than hardware virtualization provides.

Two Linux kernel features do the actual isolation work: namespaces control what a process can see — its own view of PIDs, network interfaces, mounts, and hostname — while cgroups limit and account for how much CPU, memory, and I/O it can consume. On top of that, union/overlay filesystems let a container image be built as a stack of read-only layers, with a thin writable layer added only at runtime, which is why images share layers efficiently and containers start almost instantly. Docker's own architecture reflects a clean separation of concerns: the dockerd daemon talks to containerd for container lifecycle management, which in turn delegates to runc, an OCI-compliant low-level runtime, to actually create the isolated process. An image is an immutable blueprint; a container is simply a running (or stopped) instance of that image with its own isolated process, network, and filesystem view.

Popular tools: Docker, containerd, runc, Podman; the OCI (Open Container Initiative) standardizes image and runtime formats across all of them.

When to use it
Reach for containers when packaging and deploying microservices, running high-density workloads on shared hardware, or building CI/CD pipelines that need consistent dev/prod parity. Avoid them for mutually untrusted multi-tenant workloads (prefer VMs or microVMs) or anything requiring a different kernel/OS than the host.
ProsCons
  • Sub-second startup versus tens of seconds for a VM boot
  • Much smaller footprint than a full VM
  • Portable, consistent behavior across dev/staging/prod
  • High density — many containers per host
  • Weaker isolation boundary than VMs (shared kernel)
  • Not suitable for workloads needing a different kernel/OS
  • Not a hard multi-tenant security boundary on its own

Container Orchestration: Kubernetes

Kubernetes automates the deployment, scaling, networking, and self-healing of containerized applications across a cluster of machines, turning a one-time instruction like "run three copies of this service, exposed this way" into an ongoing, self-correcting reality rather than a fact that only holds true the moment it's applied. It does this through a small set of core objects: a Pod is the smallest deployable unit — one or more containers that share a network namespace and storage; a Node is a worker machine running the kubelet agent, a container runtime, and kube-proxy; a Deployment declares desired state and manages the underlying ReplicaSets, including rolling updates; and a Service provides a stable virtual IP and DNS name in front of a constantly changing set of pod IPs.

The control plane is what makes this self-healing possible. kube-apiserver is the front door and the only component that talks to etcd directly; etcd is the cluster's consistent state store; kube-scheduler decides where new pods should run; and kube-controller-manager runs the reconciliation loops that continuously compare desired state against observed state and correct any drift — restarting crashed containers, rescheduling pods off unreachable nodes, replacing pods that fail liveness or readiness probes. Scaling operates at three levels: the Horizontal Pod Autoscaler adjusts replica count from observed metrics, the Vertical Pod Autoscaler tunes a pod's resource requests/limits, and Cluster Autoscaler (or Karpenter) adjusts the number of underlying nodes. The whole system is declarative and API-driven, and it's designed to be extended — Custom Resource Definitions plus the Operator pattern let teams teach Kubernetes to manage entirely new kinds of application-specific state using the same reconciliation model.

Only kube-apiserver talks to etcd; the scheduler and controller-manager reconcile through it, and worker-node kubelets are watched and reconciled against desired state.

Popular tools: Kubernetes (CNCF); managed offerings (EKS, GKE, AKS); ecosystem (Helm, Istio/Linkerd, Prometheus, ArgoCD/Flux).

When to use it
Reach for Kubernetes when running many microservices that need consistent deployment, scaling, and networking across a fleet, when multi-cloud or hybrid-cloud portability matters, or when variable-load workloads benefit from automated scaling. It's probably overkill for a single small application or a team without the operational bandwidth to run a cluster.
ProsCons
  • Strong self-healing and automated scaling out of the box
  • Huge ecosystem (Helm, service meshes, GitOps tooling)
  • Cloud-portable across on-prem and every major provider
  • Extensible via CRDs and the Operator pattern
  • Significant operational complexity
  • Steep learning curve for teams new to it
  • Overkill for small or simple workloads
  • etcd/control-plane availability becomes a hard dependency for the whole cluster

Serverless / Function-as-a-Service (e.g., AWS Lambda)

Serverless (Function-as-a-Service) compute deploys individual functions rather than servers or containers — the cloud provider handles provisioning, scaling, patching, and availability, and billing is per-invocation and per-unit of execution time rather than for idle capacity. Functions are invoked in response to events: an HTTP request through an API gateway, a file landing in object storage, a message arriving on a queue, a database change stream, or a schedule. AWS Lambda, the archetypal example, runs each function inside a lightweight, secure microVM (Firecracker), and scales near-automatically to handle concurrent events.

The defining operational wrinkle is the cold start — the delay needed to initialize a fresh execution environment before a function can run, typically 200–500ms for lightweight runtimes but potentially multiple seconds for heavier runtimes like Java or for functions attached to a VPC. Providers mitigate this with Provisioned Concurrency (paying to keep a pool of instances warm) or snapshot-restore mechanisms like AWS SnapStart. Functions are also stateless between invocations and bound by hard execution-time limits (15 minutes on Lambda), which shapes the kind of workload they're suited for. Economically, serverless is not simply "cheaper" — it inverts at high sustained load: serverless wins clearly at roughly a 10% duty cycle or below, containers become the cheaper option above roughly 50% duty cycle, and at steady, high traffic some analyses show serverless costing tens of times more than an equivalent always-on container.

Popular tools: AWS Lambda, Azure Functions, Google Cloud Functions/Cloud Run (container-based hybrid), Cloudflare Workers (near-zero cold start), Knative.

When to use it
Reach for serverless for sporadic, unpredictable, or bursty traffic; event-driven glue logic (processing an upload, reacting to a queue message); rapid prototyping; or scheduled, brief cron-style jobs. Reconsider it for long-running processes, high and sustained predictable traffic, or anything needing guaranteed sub-50ms latency on every call — many real architectures land on a hybrid split, serverless for sporadic paths and containers for the always-on core.
ProsCons
  • Zero idle cost — pay only for actual invocations/duration
  • No server management at all
  • Near-instant automatic scaling for bursty workloads
  • Tight native integration with cloud event sources
  • Cold-start latency variability, worse for heavy runtimes/VPC functions
  • Hard execution-time ceilings (e.g. 15 min on Lambda)
  • Statelessness between invocations complicates some workloads
  • Cost can invert and become far more expensive at high sustained duty cycles

Service Discovery (General Concept)

Service discovery is the mechanism by which services find the current network location of the other services they depend on, in an environment where instances are constantly starting, stopping, scaling, and moving — a static config file or hardcoded IP simply doesn't survive contact with that kind of environment. The core piece of infrastructure is a service registry — ZooKeeper, etcd, Consul, or a purpose-built registry like Netflix Eureka — that tracks which instances are currently available. Getting instances into that registry happens one of two ways: self-registration, where an instance registers and deregisters itself, typically backed by a heartbeat or TTL, or third-party registration, where an external registrar or health-checker updates the registry on the instance's behalf.

How a caller then uses that registry splits into two patterns. In client-side discovery, the calling client queries the registry directly and picks an instance itself — the classic example is Netflix Eureka paired with the Ribbon client-side load balancer — which saves a network hop and gives the client full visibility, at the cost of needing that discovery logic embedded in every service and every language in use. In server-side discovery, the client simply calls a stable endpoint, and a load balancer or proxy queries the registry and routes the request on the client's behalf — AWS ALB, or Kubernetes Services backed by kube-proxy, CoreDNS, and etcd, are the canonical examples — which keeps clients simple and uniform across languages, at the cost of an extra network hop and another piece of infrastructure that itself needs to be highly available.

Popular tools: ZooKeeper, etcd, Consul, Netflix Eureka; Kubernetes Services/CoreDNS/kube-proxy; AWS Cloud Map, ECS Service Discovery; Istio/Envoy, Consul Connect.

When to use it
Client-side discovery fits polyglot-but-standardized stacks already invested in a client library ecosystem, or latency-critical paths that can't afford an extra hop. Server-side discovery fits container/orchestration platforms by default — on Kubernetes you get it for free via Services and DNS. Any system built on dynamic, elastic infrastructure needs some form of service discovery; the only real question is which pattern.
ProsCons
  • Client-side: one fewer network hop, full client-side visibility
  • Server-side: simple, "dumb" clients uniform across every language
  • Both patterns eliminate hardcoded/static endpoints entirely
  • Integrates naturally with health checking for automatic failover
  • Client-side: discovery logic must be duplicated across every service/language
  • Server-side: adds an extra hop plus another HA-critical piece of infrastructure
  • The registry itself becomes a critical dependency requiring its own availability story
  • Stale registry entries can route traffic to dead instances if health checks lag
